Persist the event "Cronograma" in the database and the API. Today (front commit fae313a, merged as 806d3f0) the web stores it as text inside the event description, in the "Informacoes uteis" block, sub-section "Programacao". Purpose: stop spending the 4000-character description limit on up to 30 moments, stop showing a schedule as raw text wherever the description is printed raw (the .ics file, the Google Calendar link), and give the schedule a validated, tenant-isolated home.

Output: one expand-only migration (`events.schedule`) with pgTAP, the contract and service changes with unit and HTTP integration tests, the web form and detail reading and writing the new field with a legacy read fallback, and the docs.

Request decisions (from the orchestrator, numbered in order):
- D-01 storage: a column `schedule jsonb not null default '[]'` on `events`, with a shape CHECK (jsonb array, at most 30 items); a table `event_schedule_items` only if the code gives a strong reason, justified here.
- D-02 backend: Drizzle schema in packages/modules/events plus the SQL in supabase/migrations, RLS preserved, pgTAP; Zod contracts (create, update, detail, edit); the new response field optional/tolerant; kernel and routes validate and normalise (sort by day then time, drop duplicates, reject an invalid time); unit and integration tests.
- D-03 web: the form sends schedule as its own field and stops writing Programacao into the description; edit and display read the new field; legacy text-in-description read fallback; NO bulk data migration; the schedule no longer consumes the description limit.
- D-04 docs: docs/pendencias-backend.md item 5 marked done by the backend, plus any pertinent API doc.
- D-05 constraints: migration applied to the LOCAL stack only (`pnpm supabase migration up`; never db reset unless unavoidable, never db push or config push, nothing against production or homolog); pgTAP before the integration suites; TURBO_CACHE=local:r; only the affected events e2e specs run locally; commits carry NO Co-Authored-By; stage explicit paths only; do not push; "tenant" is the organisation and "comunidade" is a product feature, never the tenant.
- D-06 conventions: read the real events layout first and reuse the front's limits by moving them into the contract, if that is how modules share limits (apps/web must not import packages/db).

Design decisions made at planning time, from reading the live code and the live local database (not assumed):
- COLUMN, NOT TABLE (D-01). The code gives no strong reason for `event_schedule_items`, and four for the column: (1) the schedule is only ever written as a WHOLE with the event (the PUT is a whole-event replacement, D-214) and only ever read WITH the event, never queried, filtered, joined or paginated per item; (2) at most 30 items of about 100 bytes, so row size is a non-issue; (3) a table would add a statement to create, to the guarded update and to both reads, which breaks the one-statement projection contract that `feed-query-budget.test.ts` measures and the scripted statement sequences of `events-payload.test.ts`, and it would need a second tenant-first index, a composite FK, a policy and its pgTAP; (4) the column rides the existing `events_tenant_isolation` policy, so there is no new surface to leak across tenants. A table would pay off only if items needed identity (per-item reminders, check-in per session); no source artifact asks for that, and the column can be split into a table later by an expand migration. The SUMMARY must repeat this justification.
- CONTRACT LOCATION. The real layout is not packages/contracts: `packages/contracts/src/events.ts` is the domain-event BUS and "knows no module". Event schemas and limits live in `packages/modules/events/contracts/index.ts` (`EVENT_MAX_*`, `eventInputSchema`, imported by the API and by apps/web as `@rede-social/module-events/contracts`). The shared schedule limits and normaliser go there, and the web's `EXTRAS_CAPS` schedule caps are derived from them so there is ONE definition.
- SHAPE CHECK (probed on the live stack inside a rolled-back transaction, PostgreSQL 17.6). A per-item jsonpath check works and `jsonb_path_exists` is IMMUTABLE: `[]` and valid items pass; `{}`, scalars, non-object items, a missing key, day 0, 32, 1.5 or "1", time 24:00 or 08:60, a blank or 81-character title and 31 items are refused; the key POSIX class `[^[:space:]]` works inside `like_regex`. The CHECK therefore goes beyond the minimum asked (array, at most 30 items) and also guards each item. Extra keys inside an item are tolerated by the CHECK on purpose (the API's strict item schema is what forbids them).
- RESPONSE TOLERANCE AND RELEASE ORDER. The web parses every API answer with strict schemas. `schedule` is `.optional()` on `eventDetailSchema` and `eventEditSchema` (the 261007-gzu `emailUnconfirmed` precedent), so the new web reads an old API's answers, and the release order is migrations, then web, then API. The summary shape (list, write answers) does NOT gain the key: the poster needs no schedule and the list pages stay small.
- REQUEST COMPATIBILITY IN THE WEB-FIRST WINDOW. `eventInputSchema.schedule` is `.optional()`, NOT `.default([])`: the form sends `eventInputSchema.safeParse(payload).data`, and a defaulted `[]` would put a key on every save that an OLD strict API rejects. The form also omits the key when the list is empty. Between the web and the API releases, every save without a schedule still works; a save WITH a schedule is refused loudly by the old API (400) instead of being silently lost, and the old description path is deliberately not kept (D-03). A PUT that omits the key clears the schedule, the established rule for the other optional fields (`category`, `capacity`, `coverAssetId`). Consequence to record in the SUMMARY: a stale cached client from before the web release that edits an event after the API release would clear its schedule on save; the PWA update flow makes this window small.
- LEGACY READ FALLBACK (D-03). Nothing is migrated in bulk (verified: the local database holds 14 events and none has a Programacao block, so the fallback is covered by unit tests and one e2e that inserts such an event). `composeEventDescription` stops writing the programme; `splitEventDescription` keeps parsing it (its exact round-trip check uses a legacy-capable compose internally). The display picks the new field when it has items and the legacy block otherwise. The edit form seeds its schedule from the new field, else from the legacy block; saving writes the new field and a description without the block's programme lines, which migrates that event lazily. The form's `dirty` baseline must compare against the SAME normalised composition (not the raw stored description), otherwise an untouched legacy event would look edited.
- NO NEW COPY. No pt-BR string is added (the editor, the page section and every message already exist), so no catalog change and `scripts/check-ui-literals.sh` is unaffected.
