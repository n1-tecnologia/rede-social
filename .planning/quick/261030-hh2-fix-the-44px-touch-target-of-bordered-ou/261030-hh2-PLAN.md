<objective>
Fix the 44px touch target (UI-D-443) of bordered `sm` buttons that use `hitArea`, at the one place it is defined, and prove it in a browser.

Purpose: the Phase 12 browser run found that the 'Exportar respostas (CSV)' button (variant outline, size sm, hitArea) answers a tap over only 42px at 320px (`{visible:36, run:42, first:299, last:340}`). Cause: the hit area is a transparent `::after` whose vertical reach is an inset from the PADDING box of the button, and the padding box sits inside the border. With the outline variant's 1px border the padding box is 34px, so 34 + 4 + 4 = 42; borderless variants (36px padding box) reach exactly 44. The same defect was found and deferred on 2026-10-21 (Phase 09.1 deferred-items, 09.1-19; `payments-admin.spec.ts` asserts 42 for it). The fix is a box that is 44px tall and centred on the control, which ignores the border, instead of an inset.

## What the code showed at planning time (authority for the edit scope; line numbers approximate)

**The primitive.** `packages/ui/src/primitives/buttonClasses.ts` defines `HIT_AREA` (a const string, line ~49) and `buttonClasses()` appends it when `hitArea` is true. `Button.tsx` calls `buttonClasses`; every link styled as a button calls it too. It is the only place the string exists. The `sm` size is `h-9` (36px); the `outline` variant carries `border border-border-secondary` (1px, border-box sizing from the Tailwind preflight, so the border is inside the 36px). No variant defines `active:scale`, so nothing on the primitive transforms the button.

**The measurement the fix is judged by.** `expectTouchTarget` (profile-form.ts ~line 549) returns early if the element's own box is >= 44px, otherwise calls `expectTapTarget` (payments.ts ~line 500): it scrolls the control to the centre of the screen, walks the column through the control's horizontal centre one pixel at a time from `mid - 44` to `mid + 44`, counts the pixels where `document.elementFromPoint` is the control or a descendant, and passes when that run is >= 43 (`minHeight - 1`). So the proof reads the real hit-testing, `translate` included.

**Generated CSS (Tailwind 4.3.3 of this repo, probed at planning time with `@tailwindcss/postcss` on exactly these candidates).** `after:h-11` -> `height: calc(var(--spacing) * 11)` with `--spacing: 0.25rem` (no override of `--spacing` or of the root font size exists in the repo) = 2.75rem = 44px. `after:top-1/2` -> `top: calc(1 / 2 * 100%)`. `after:-translate-y-1/2` -> `--tw-translate-y: calc(calc(1 / 2 * 100%) * -1); translate: var(--tw-translate-x) var(--tw-translate-y);` — the individual `translate` property, NOT `transform`; `--tw-translate-x/y` are registered with `@property` (initial 0) and also defaulted on `*, ::before, ::after, ::backdrop`, so the pseudo-element is covered. Every `after:` utility also emits `content: var(--tw-content)` (empty string), which is what supplies the pseudo-element. Nothing else sets `transform` or `translate` on the pseudo, so the translate composes with nothing; a transform on the BUTTON (a call site's, an ancestor's) moves the pseudo along with it exactly as it did before.

**Geometry of the final string** `relative after:absolute after:inset-x-0 after:top-1/2 after:h-11 after:-translate-y-1/2`:
- `top: 50%` is 50% of the padding-box height, and `-translate-y-1/2` pulls the 44px box up by half of its OWN height, so the box is centred on the padding box, which is concentric with the border box (the border is symmetric). Result: a 44px box centred on the control, for any border width. For a 36px control: 4px past the visible edge, above and below.
- Borderless sm (padding box = border box = 36px): box top = 18 - 22 = -4px, bottom = +40: identical to the old 4px inset. No behaviour change.
- Outline sm (padding box 34px, border box 36px, border 1px): box top = 17 - 22 = -5px from the padding box = 4px past the visible edge (it was 3px). 42 -> 44.
- Sideways: `after:inset-x-0` is kept, so the width is the padding-box width: never wider than the control. A neighbour in the same row is never covered, which is what the old docblock promised and still holds.
- Vertical neighbours: a bordered control now reaches 1px further per side than before, to the same 4px the ghost call sites already reach. The pseudo is a positioned element, so where a sibling sits closer than 4px below or above a bordered control, that 1px steals taps from the sibling's edge; the Export button sits in a `flex-col gap-1` (4px) block and the other bordered call sites sit in rows or have a larger gap, none closer than 4px was seen. The browser proof in Task 2 measures the two buttons of test 6; the rest are covered by identical geometry, not re-measured (stated in the SUMMARY).
- A fixed `h-11` is not relative to the control. Every one of the 22 call sites is size `sm` (36px) and none overrides the height, so it is the right box for all of them. On a control already 44px or taller the pseudo adds nothing past the control (the old inset would have made a 52px box on `md`), which is the more correct behaviour; the docblock keeps saying only `sm` needs it.
- Why not the alternatives: `after:-inset-y-[5px]` only for bordered variants would leak the variant into `HIT_AREA` and break for any border other than 1px (a call site's `border-2`); `after:top-[calc(50%-22px)]` is equivalent but an arbitrary value that reads worse; the three small utilities of the chosen string are the standard centring idiom and are border-independent.
- tailwind-merge: `after:inset-x-0`, `after:top-1/2`, `after:h-11` and `after:-translate-y-1/2` are four different class groups, and the `after:` modifier keeps them apart from any unprefixed `h-*`/`top-*`/`translate-*` a call site passes in `className`. (The old string was one group, `inset-y`, which also conflicts with `top`/`bottom`; the new one has no such coupling.) Task 1 pins this.
