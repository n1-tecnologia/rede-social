<objective>
Fix the first-admin invite race observed in production on 2026-09-29 (AUTH_ALLOW_LIST=supabase,
DOMAIN_PROVIDER=vercel) and make the invite state explicit in the platform panel.

Timeline of the incident: `platform.domains.attach` 14:17:57 → `verified_at` 14:18:03 →
`mail.sent` + `invite.sent` 14:18:08. `ensureVerifiedSideEffects` PATCHed the Supabase Auth
`uri_allow_list` and called `sendPendingInvites` ~5 s later; GoTrue had not applied the new entry,
dropped the invite's `redirect_to` and fell back to `site_url` (the platform host), and the Send
Email Hook built the CTA from that fallback (`https://<platform-host>?token_hash=…&type=invite`, no
`/auth/confirm`). Why the hook let it through: at the first send the invited membership does not
exist yet (02-05 inserts it after GoTrue returns), so `resolveMailTenant` falls to "no membership,
not a platform admin, host not a tenant" → neutral mail. The same fallback happens locally with any
host outside `supabase/config.toml` `additional_redirect_urls` (e.g. the `.cliente.test` hosts of
platform-domains.test.ts — those cases "pass" today with a broken neutral link).

Three parts:
1. Race fix — the verified transition schedules a delayed, idempotent, retrying `kernel.invite-send`
   pg-boss job instead of sending inline; the manual resend stays immediate.
2. Hook hardening (defense in depth, T-02-26 kept) — a link mail for a tenant recipient whose
   `redirect_to` host is not a verified host of that tenant is refused (500, nothing sent), so GoTrue
   reports failure and the job retries.
3. Panel UX — explicit invite status on the Admins tab, send vs resend labels, disabled-with-reason
   while no verified domain exists, clearer creation-form hint.

Purpose: a tenant's first admin always receives a working link on the tenant's own branded origin
(core value: the tenant's identity everywhere), and the super_admin can see where the invite stands.
Output: the kernel job + scheduler, the hook guard, the panel states, and the tests that prove each.
</objective>
