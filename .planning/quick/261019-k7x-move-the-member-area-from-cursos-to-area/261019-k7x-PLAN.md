Purpose: the member's "area de membros" (the prototype's Inicio, Cursos, Trilhas, Lives, Progresso) was built under `/cursos` by 08.6 (D-435, D-400). The user says that prefix is wrong for the member while the admin needs it to author courses. This reverses ONLY the route prefix of D-435 and D-400; the five chips, the content and the locked-stays-visible rule (08.5 D-419..D-424, confirmed again 2026-10-19) are unchanged and no empty-school logic is touched.

Output: a new `/area-membros` route reusing the shipped member components; a role split on `/cursos` (hub for managers, redirect for everyone else); every member-area href rebased; a role-aware bottom-bar tab; updated e2e specs (not executed).

**Shape.** Task 1 is the end-to-end slice (route + redirect + links: the member can reach and use the area on its new URL). Tasks 2 and 3 expand it (the tab, then e2e and gates). It is `type="auto"`, not `tracer`: the only genuinely end-to-end check is Playwright, and the local stack is down.

**Decisions recorded here (planner, from live code):**

- QD-01 role-aware tab = a host-side rewrite after `buildNav`, not a manifest change and not a redirect alone. Why: the courses manifest `nav` is static data that travels through `bootstrap.modules` from the API (off limits) and is identical for every role, so a role-aware href cannot live there. `buildNav` runs in `apps/web/app/(app)/layout.tsx`, where `bootstrap.permissions` is already in hand, and that layout already post-processes the `ShellNav` with the host-decided `withTabDots`, `withCollapsingTabs` and `withAreas` (the kernel stays module-agnostic, MOD-02). A redirect alone (tab stays `/cursos`) was rejected: the label would still read Cursos and, worse, `activeTabKey` matches by href path, so on `/area-membros` no tab would be current. A bare href rewrite was rejected too: the course page, the player and the live page stay under `/cursos/*` (shared with the admin), so the member tab would lose its current state there. Hence two small kernel additions, generic and key-based like their siblings: `NavItem.matches` (extra paths that also mark a tab current) and `withTabOverrides(nav, { [tabKey]: { href, label, matches } })`; the module-specific knowledge (tab key `courses`, `/area-membros`, `/cursos`, `courses.manage`) lives in the web leaf `apps/web/lib/member-area.ts`.
- QD-02 the `/cursos` split is a server-side `redirect()` in the page (role-aware, so `next.config.ts` redirects and `proxy.ts` cannot do it). Per the Next 16.3.5 docs in `apps/web/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/redirect.md`, inside a streaming context (and `cursos/loading.tsx` makes this one) it emits a meta tag and redirects on the client, so the e2e uses auto-retrying URL assertions, never a status check.
- QD-03 the area lives in `/area-membros/page.tsx` and imports the shipped components from `cursos/` (no file moves, no rewrites): MemberCatalogue, MemberHomeTab, MemberCoursesTab, MemberTracksTab, MemberLivesTab, MemberProgressTab, HubTabs and the `tabs.ts` member registry stay where they are.
- QD-04 the admin preview lands on `/area-membros?ver=aluno`: `/cursos?ver=aluno` redirects there, every preview link keeps the flag, and the PreviewBanner back link still goes to the hub `/cursos`.
- QD-05 role-neutral surfaces keep the bare `/cursos` and ride the redirect: the courses not-found card and the lesson not-found fallback (they serve both roles and cannot know the role). Member-only surfaces link `/area-membros` directly.
- QD-06 push and bell deep links: every server-built url (`packages/modules/courses/server/notifications.ts`) is `/cursos/lives/{id}` or `/cursos/{id}`, both kept routes, so nothing there changes. Only the web bell renderer's degrade-to-list fallback changes (its audience is members only, per `app.course_audience_user_ids` and `app.live_replay_audience_user_ids`).

**Out of scope, carry into the SUMMARY as open points:** (1) the area h1 and subtitle still read "Cursos" / "Cursos e lives de {tenant}." (copy change not requested; one catalog line each if wanted); (2) the prototype's TopBar suffix "· Membros" and area menu (`NavArea`) are not added (the ask was the bottom-bar tab only; it would change the TopBar's right side for members); (3) REQUIREMENTS.md COURSE-16/28 and the 08.6 D-435/D-400 text still say `/cursos`; they are not edited here because the verification digest covers REQUIREMENTS/ROADMAP, so amend them in a separate commit; (4) the member course page back label stays "Voltar para Cursos"; (5) the empty-school logic (Inicio says "Nenhum curso por aqui ainda" for a published course with zero lessons) is untouched on purpose.
