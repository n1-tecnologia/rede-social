<objective>
Stop the Supabase Data API (PostgREST `/rest/v1` and the `/graphql/v1` route) from serving `public` or `graphql_public`. This plan uses the approach the user chose on 2026-10-09 after the first run halted: a dedicated empty schema ("Schema vazio dedicado"). A hand-written migration creates `data_api_closed` with no objects and no grants. `supabase/config.toml` `[api]` exposes only that schema, and `public` leaves `extra_search_path`. PostgREST keeps running and refuses every request fast and identically, both locally and, through the deploy's `supabase config push`, in production. An automated live regression check in the API integration suite pins the result.

Purpose: the API is the only data client. The browser uses Supabase only for Auth (through the Next.js BFF) and read-only Realtime Broadcast. `authenticated` must keep its DML grants on `public`, because the API runs as `api_user` + `set local role authenticated`. `GET /api/realtime/token` hands the raw GoTrue access token to page JavaScript, and the publishable key ships in the bundle. While `public` is exposed, every RLS policy is one claim away from becoming a write path that skips the API's rules (08.2-REVIEW.md CR-01). The two config-only candidates failed (SUMMARY of the halted run). `schemas = []` makes PostgREST fall back to `public`. `enabled = false` leaves Kong's routes pointing at a missing upstream, which hung for about 60 s on this machine. Store tables were fixed in 08.2 and stay out of scope. Revoking table grants is not an option.

Output: one `--custom` migration (with its drizzle journal entry and snapshot), the `[api]` block, `apps/api/tests/integration/data-api-not-exposed.test.ts` (moved in from the parked draft), and a docs/DEPLOY.md section with an hml runbook checkbox. scripts/local-env.sh is expected NOT to change; Task 1 verifies it.
