<objective>
Close finding WR-03 of the Phase 09.3 code review (09.3-REVIEW.md): reactivating an archived Loja product re-opens the D-554 hole for a deleted community.

The hole. D-554 lets an admin delete an ARCHIVED community while only ARCHIVED products link it (archived products do not count, and the delete never touches the Loja, D-553 / D-554). `setProductStatus` can then flip such a product back to `active` with no check. The product is active and buyable (`app.store_purchase` has no community check), and every buyer pays for access to a community that no longer exists. That is the outcome D-554 sets out to prevent ("nobody pays for access that stops existing").

The fix. On a transition to `active` (the product's current status is not already `active`), refuse with `ApiError(409, 'CONFLICT', { store: 'community_deleted' })` when any linked community of the caller's tenant has `deleted_at` set. The community rows are locked FOR SHARE inside the same `withTenantTx`, after the product row, so a concurrent `deleteCommunity` (FOR UPDATE on the community, plain read of the products) and a reactivation serialise: one of them wins, never both. The web shows its own pt-BR copy for the new code.

Purpose: an admin can never end up with an active, buyable product that unlocks a deleted community.
Output: the guard in the store service, the contract code, OpenAPI and README text, seven new integration cases, the web mapping with its messages and two unit-test additions, and three path-scoped commits (no trailer, nothing pushed).

Tracer-first: Task 1 is the tracer. It wires the one refusal path through the contract, the service and the real HTTP route into the database, proved by a real integration test (archive product, archive and delete the community, reactivate, get the 409, row unchanged), plus the two controls that the guard did not break the allowed transitions. Task 2 expands the API proof (tenants, several communities, races) and the published text. Task 3 carries the code to the web.

Known consequence the plan does NOT change (record it in the SUMMARY): `replaceLinks` (the PATCH link replace) deletes links only to ACTIVE, live communities, so a link to a deleted community can never be removed by an edit. Such a product stays archived for good, and the pt-BR copy therefore tells the admin to create a new product. Letting an edit drop links to deleted communities is a separate decision (it touches CR-02 reasoning) and is out of scope here.
</objective>
