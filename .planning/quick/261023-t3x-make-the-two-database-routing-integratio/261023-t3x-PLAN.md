All of it passes locally.

Corrected diagnosis (established at planning time by reading postgres 3.4.9 and running it against a local listener; Task 1 re-confirms it before any edit):
- The leading hypothesis (every failed attempt can take up to connect_timeout = 10 s) is refuted. postgres.js re-arms its connect timer on every attempt and, while the first query is pending, reconnects immediately after a CLEAN close (no error event) with no backoff. So a peer that accepts and closes cleanly makes the query hang for as long as the peer keeps accepting; only an error event (an RST, ECONNRESET) rejects it. On Linux, with the client and the listener in the same process, whether the destroy-on-accept reaches the client as RST or as a clean FIN depends on whether the client's startup bytes were already queued when the listener closed, so it is a race that macOS happens to win (an RST, 4 ms).
- This explains all three CI facts: (1) the test did not take 30 s, it hung; (2) its finally block never even started because the body was stuck awaiting the request, and the afterAll hung in closeAllPools(), which awaits the never-settling connect (packages/core/db/project-pools.ts line 314); (3) the tenant and project rows were never removed. It is consistent with the evidence, not proven on Linux from this Mac (there is no Linux runner here); the mechanism itself is proven on this Mac with the clean-close variants.
