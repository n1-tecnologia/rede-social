<objective>
Make the Web Push fan-out fast enough for the ~10,000-user launch (3 tenants, Supabase moving to Pro on
Small compute) without starving a connection pool, and cap Cloud Run so autoscaling cannot exceed the
Supavisor client limit.

The bottleneck is the serial web-push network send: one `notifications.push-send` job at a time, and
inside it up to 100+ subscriptions sent one after another (about 100-300 ms each). The per-recipient
badge counts (about 100 short tenant-lane transactions, roughly 1 s per job) are NOT the bottleneck and
stay exactly as they are, so the owner-only RLS and the kernel counters seam are untouched. The api
service also has no `--max-instances` (Cloud Run default 100 x 6 pooled clients each).

This plan delivers, in order:
1. (tracer) Bounded-parallel sends inside a job (16 in flight) with byte-identical outcome handling,
   proven by a 5,000-subscription test over the fake transport, plus a per-job proof that a push job
   never holds more than one lane at a time.
2. pg-boss `localConcurrency: 4` for the push queue only, a `DATABASE_POOL_MAX` knob (worker 10, api 5),
   `--max-instances` for api (25) and worker (1) in production and hml, and a "Connection budget (Pro)"
   section in docs/DEPLOY.md with the formula and the worker pool fit.

Out of scope (coordinator decision): batching the badge counts, any migration or security-definer
function, any change to `packages/core/server/modules/counters.ts` or the counters resolver in
`apps/api/src/modules/registry.ts`.

Purpose: a tenant-wide push for 10k subscribers drops from about 100 jobs x 15-30 s serial to roughly
one to two minutes, and a traffic spike can no longer push Supavisor past its client limit.
Output: the parallel send and its tests, the worker concurrency, the pool knob, the deploy flags and the
budget doc.
