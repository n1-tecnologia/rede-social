# Phase 09.1 Plan 04: First-admin invite as a manual access, global list retired at the staff door Summary

**The platform invite now writes the first admin's manual access in the same transaction as the tenant, so the GoTrue creation hook passes at send time with no hand-filled list; staff stay exempt from the payment gate, and the isEmailAllowed compatibility function, the not_allowed validation and the wizard string are deleted.**

## Performance

- **Duration:** 17 min
- **Started:** 2026-10-20T23:24:00Z
- **Completed:** 2026-10-20T23:41:00Z
- **Tasks:** 2 (Task 1 tracer, Task 2 auto)
- **Files modified:** 12 (10 changed or added, 1 deleted, plus the one new core unit test)

## Accomplishments

- Tracer proven against real GoTrue and the real API: on a tenant created for an e-mail with no access row anywhere, `POST /v1/platform/tenants` answers 201 (it was 400 `adminEmail = not_allowed`), exactly one manual active row exists in the new tenant, the invite send reaches `inviteUserByEmail` through the creation hook, the admin accepts, signs in and is served on bootstrap and an admin route with the gate ON, no subscription and the manual row deleted; a fresh sign-in still passes the token hook, and a plain member of the same tenant gets 403 `SUBSCRIPTION_PENDING`.
- `grantManualAccess` is the single writer. `createPendingInvite` calls it in the caller's transaction (assumption A-P3: the creation hook fires at send time), `acceptInvite` re-asserts it at step (c2) in the transaction that flips the membership, and an invite created before this phase is granted at accept.
- `createTenant` no longer asks a list. The D-316 refusal of a platform account stays and is asserted (no tenant, no grant).
- Deleted `packages/core/server/tenancy/email-allowlist.ts`, the wizard's `emailNotAllowed` union member, branch and catalog string. `email_allowlist` now appears only in the schema file, its export, comments and the migration function.
- P18 and P19 are explicit cases: a retried creation, a replayed accept, a legacy invite, a manual block beside the grant, two concurrent accepts, two concurrent creations of one slug, one e-mail administering two tenants.
