<objective>
Move every door that today asks the global hand-filled allowlist onto the per-tenant access records of plan 02, in one step, so no reader of the old table is left behind and no tenant's gate can be bypassed by a stale global list. After this plan a tenant that has not turned the gate on behaves as it always did for everyone (the hooks never bite an existing member), and a tenant that has turned it on refuses sign-up and join for an e-mail without a usable access.

Task 1 is the tracer: ONE gated sign-up through the whole stack (the hook bodies and the data migration, the `access.ts` doors, `signupMember`, the harness) proven against real GoTrue. Task 2 closes the join door, retires the remaining readers (seed, e2e helper, `isEmailAllowed` compatibility) and adapts the integration suites. Task 3 rewrites pgTAP 175 for the new hook matrix and the migration function.

Decisions implemented: D-487 (the allowlist is replaced; its rows migrate as manual), D-491 (a gate that is off changes nothing), D-493 and D-302 (one sentence, no other community), D-494 (any active access opens the door), D-495 (coarse hooks, per-tenant decision in the API).

Purpose: the hooks must stay trivial and cheap (they run inside GoTrue on every token exchange and a 5xx there breaks every login), while the real per-tenant rule lives in the API where the host is known.
Output: three migrations, the `access.ts` doors, the changed sign-up and join services, the retargeted harness, seed and e2e helper, and the adapted suites.

<planning_decisions>
1. **The hooks keep their names.** Production config blocks (`enabled = false`) and the local base blocks name the functions; replacing bodies with `create or replace` keeps the ACLs and needs no `config push`.
2. **No pending-invite disjunct in the creation hook.** The first-admin path writes a manual access when the invite is created (plan 04, assumption A-P3), and that row is what lets `inviteUserByEmail` through; a second path through `tenant_invites` would be a second rule to keep in step.
3. **`isEmailAllowed` survives one plan as a compatibility function.** `createTenant` still pre-checks the first admin's e-mail; making it tenant-aware is plan 04's job (the tenant does not exist yet at that point, so the check disappears there, D-492).
4. **The migration is a function.** The one-off copy of `email_allowlist` is `public.migrate_email_allowlist_to_access_grants()` called by the migration, so pgTAP can run the same logic on a fixture; it is owner-only and a later contract release drops it with the table.
5. **Blocks migrate as manual blocked rows.** A global `bloqueado` row becomes a manual `blocked` row in each tenant where the e-mail has a live membership: a block is the only verdict the old list could carry besides release, and dropping it would silently re-admit someone.
6. **The seed grants through ONE call after the tenants exist**, not inside `ensureUser`, because `ensureUser` runs before a tenant id is known for some identities.
7. **Local config comment only.** `supabase/config.toml` gets its comments updated to the new semantics; no `enabled` value changes.
</planning_decisions>
