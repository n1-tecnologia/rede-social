<planning_decisions>
1. **Both signed-material candidates, one constant-time compare each.** A forger needs the token for either, so accepting both widens nothing; the variant label goes to the log so the real capture settles it.
2. **Tolerant parse, closed output.** The Zod schema reads only the fields the mapping needs (`passthrough` is NOT used, unknown keys are dropped); the neutral event contains no field the access decision does not need, so buyer PII (CPF, phone, address, IP) never enters the result (PR-9).
3. **The cancel semantics are one constant.** `CANCEL_EFFECT = 'suspend'` is D-496 literal; the capture may show that a mid-period cancel keeps `customer_access.has_access` true until `access_until`, in which case the adapter derives the effect from that field (assumption A-P2); nothing outside this file changes.
4. **Fixtures are built from the vendor's documentation, not from a live account.** They use obviously synthetic ids and addresses and carry a header field `_fixture` naming their provenance; plan 20 replaces them with real captures with the personal data redacted.
5. **No network and no SDK.** The adapter is pure functions over bytes; the vendor's management API is opted out (COVERAGE.md).
</planning_decisions>
