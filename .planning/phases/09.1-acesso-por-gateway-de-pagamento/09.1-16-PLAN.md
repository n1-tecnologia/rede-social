<planning_decisions>
1. **The chip list is data-driven and filtered by the module.** The list keeps iterating `ADMIN_MEMBER_STATUSES`; the page passes `paymentsOn` and the list drops `subscription_pending` when it is false, so the contract stays one closed enum and the screen shows only what exists for the tenant.
2. **`parseStatus` is the second guard.** A hand-typed `?status=subscription_pending` on a tenant with the module off reads as 'Todos' before any request, so the API's 400-free path is never relied on for the UI.
3. **`confirmDisable` mirrors `confirmEnable`.** The component stays module-agnostic; the server page owns every string. The dialog tone is fixed to danger because disabling reopens a wall (UI-D-527); cancel changes nothing.
4. **The sheet note is a note, not an action.** A payment cut has no admin action in this phase (D-500: no new notification, no override); the note only explains why the member cannot enter and that it clears itself.
</planning_decisions>
