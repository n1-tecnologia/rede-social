## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The report must pass the account's e-mail in the claims, not `'{}'`**
- **Found during:** Task 2 (before writing the SQL, from reading the hook body)
- **Issue:** the plan's literal statement builds the event with `'claims', '{}'::jsonb`. The token hook reads the e-mail from `event->'claims'->>'email'` for its "active access row anywhere" branch, so with empty claims every account that relies on an e-mail access row (and has no staff or ungated membership) would be listed as locked out although the real hook admits it. The local database holds 18 such manual accesses.
- **Fix:** `'claims', jsonb_build_object('email', u.email)`. Shown by sensitivity: with `'{}'` three tracer cases fail.
- **Files modified:** docs/deploy/payments-hooks-lockout.sql
- **Committed in:** c39ee78c

**2. [Rule 1 - Bug] The gate is read as the JSON boolean, like the hook does**
- **Found during:** Task 2
- **Issue:** `settings ->> 'gate' = 'true'` would also match the string `"true"`, which `app.access_gate_on` (and P14) read as OFF; the report would list a tenant as `gate_on` that the hook treats as ungated.
- **Fix:** `tm.settings -> 'gate' = 'true'::jsonb`; the suite pins the lookalike and the disabled-module cases.
- **Files modified:** docs/deploy/payments-hooks-lockout.sql
- **Committed in:** c39ee78c

**3. [Rule 2 - Missing critical] `API_PUBLIC_URL` is wired into the deploys**
- **Found during:** Task 3 (plan 09's "belongs to the rollout plan", and the phase notes)
- **Issue:** the plan's Task 3 text lists only `PAYMENTS_PROVIDERS` and the secret, but without `API_PUBLIC_URL` the webhook URL the Pagamentos screen shows behind Cloud Run is built from an internal origin (A-P19), and the admin would paste a URL the gateway cannot reach.
- **Fix:** production sets the literal `API_PUBLIC_URL=https://api-253040968821.southamerica-east1.run.app` (the origin `config.toml` already commits for the send-email hook of the same service). hml sets it from a new GitHub environment variable `API_PUBLIC_URL` on `homolog`, which the existing preflight now requires non-empty and refuses when it is production's origin (an empty value would otherwise fail `z.url()` at boot). The variable has a row in the homolog variables table.
- **Impact to know:** **the next hml deploy fails its preflight until a human defines `API_PUBLIC_URL` on the `homolog` environment.** This is the same kind of precondition as the secret and is stated in the runbook's step 1.
- **Files modified:** .github/workflows/deploy-api.yml, .github/workflows/deploy-hml.yml, docs/DEPLOY.md
- **Committed in:** 513a45f5

**4. [Rule 1 - Bug, documentation] The rollback limit does not say "never unlocking anything"**
- **Found during:** Task 3 (writing the rollback limit from plan 02's summary and migration)
- **Issue:** the plan's text for the rollback limit ends "rolling the API back ... never unlocking anything". The gate is enforced by `requireAuth` through the new `_gated` lookups; an older revision calls the 08.1 lookups, which do not read the gate, so while a tenant's gate is on a rolled-back API admits its cut members again.
- **Fix:** the runbook says what the code does: turn the gate off for every tenant that has it on before rolling the API back; the store stays closed in the database for a tenant with a gateway (`app.store_purchase` refuses a non-holder); the webhook route disappears, so no events are received until the revision returns.
- **Files modified:** docs/DEPLOY.md
- **Committed in:** 513a45f5

**5. [Process] The CI job is named `static`, not "lint"**
- **Issue:** the plan says "the CI lint job"; the job that holds the `Lane guard` step is `static` ("lint, typecheck, build gate, unit tests, boundaries, lane guard").
- **Fix:** the new step sits right after `Lane guard` in that job, as the plan's position requires.

**6. [Process] `db:reset` and `db:seed` not run**
- **Issue:** Task 2's verify begins with `pnpm db:reset && pnpm db:seed`; the local database holds the user's own account and manual test data and nobody could be asked mid-run (as in plans 02-17). This plan adds no migration, so nothing needed applying.
