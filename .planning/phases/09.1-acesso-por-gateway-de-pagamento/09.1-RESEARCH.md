## User Constraints (from CONTEXT.md)

### Locked Decisions

### Access model and gateway seam
- **D-485: Two access levels.** PLATFORM access lets an e-mail create an account and log in to one tenant. STORE PRODUCT access is a `store_entitlement` for a product bought inside the platform. They are different records with different keys (e-mail and tenant, versus membership and product) and one gateway product maps to exactly one of the two.
- **D-486: Each tenant has its own gateway account behind a provider-neutral seam.** One adapter per gateway (verify the signature over the RAW body, normalise the payload into a gateway-neutral event), in the `VideoProvider` shape. Kiwify is the first adapter; others are added in code as they appear. The neutral layer (tables, columns, job names, contracts) carries no `kiwify_*` names; only the adapter and its route segment do. — **Reversibility:** costly — every table, job and route name outside the adapter is published in migrations and OpenAPI.
- **D-487: Access is per tenant and e-mail, and `access_grants` replaces `email_allowlist`.** Columns at least: `tenant_id`, normalised e-mail, `source` (`manual` or the gateway), status, validity, the gateway's order or subscription reference. Rows of the old table migrate as `manual` (the production list is empty today; the local seed lists its identities). — **Reversibility:** costly — a table replacement with hooks, API pre-checks, seeds and e2e helpers all reading it.
- **D-488: One mapping table from the gateway's product id to tenant, kind and target.** Kinds are `access` and `store_product` (target = the store product). The gateway plus external product id is globally unique, so a Kiwify product can never mean two things, and the webhook resolves tenant and kind with one lookup. It is NOT a column on `store_products`: access products have no store row, and the store stays free of gateway knowledge. — **Reversibility:** costly — the webhook route, admin forms and RLS are all built on this lookup.
- **D-489: A manual block always wins over the gateway.** The effective state of an e-mail in a tenant is: a manual block if one exists, otherwise the gateway's latest state, otherwise a manual release. `source` is what makes that rule computable.
- **D-490: The checkout e-mail must equal the account e-mail.** A webhook whose e-mail matches no membership is kept as an event in state `sem membership`, never dropped and never guessed at; the admin can grant by hand (D-503). Access records are keyed by e-mail, so a paid access product works before the account exists, which is exactly the intended flow.

### The gate: who passes
- **D-491: The gate is an explicit per-tenant switch.** `admin_tenant` turns on "Exigir assinatura para entrar" after mapping at least one access product. With the switch off (or the `payments` module off) sign-up and join stay open as today.
- **D-492: An admin invite is a manual access, and staff are exempt.** Accepting an invite writes an access with `source = manual` (listed, revocable). `admin_tenant` and `support_tenant` never depend on a subscription, so the first admin of a new tenant is never locked out. `super_admin` stays exempt (D-316 keeps it out of memberships anyway).
- **D-493: Someone without access sees a message and, if possible, an Assinar button.** Copy: "Seu acesso ainda não foi liberado. Use o mesmo e-mail da compra." plus an "Assinar" button when the tenant registered the checkout link of an access product. It appears on sign-up, login and the "Participar" join screen, and never names another community (D-302).
- **D-494: A tenant may map several access products and any active access opens the door.** No difference in level between plans in this phase.
- **D-495: The Auth hooks stay coarse and the tenant check lives in the API.** The token hook and the `before_user_created` hook answer "does this e-mail have any usable access" (an active or manual access in any tenant, a staff membership, or a platform admin) in cheap indexed lookups with 4xx errors only. The per-tenant decision is made by `signupMember`, `joinTenant` (which today does NOT consult the allowlist, because the token hook stood in for it), the first-admin paths in `createTenant` and invites, and `requireAuth`.

### Access lifecycle
- **D-496: A late, canceled, refunded or charged-back subscription cuts access immediately, with no grace.** A later approved or renewed event returns it automatically, with no admin action. Membership, profile and content are untouched throughout.
- **D-497: The cut member sees a dedicated "Assinatura pendente" screen.** `requireAuth` answers with its own error code, a sibling of `MEMBERSHIP_BLOCKED`, NOT `memberships.status = 'blocked'`, so an admin block and a payment cut stay distinct. The screen is full-screen with the tenant's brand, the text "Sua assinatura não está ativa", a "Regularizar" button (the access product's checkout link, when registered) and "Sair". The platform sends no e-mail of its own; the gateway already notifies the buyer. — **Reversibility:** one-way — the error code joins the published `ERROR_CODES` contract and the web app branches on it.
- **D-498: While cut, content stays and the member shows as inactive.** Posts, comments and course progress remain (as in D-330). In the admin members list the member carries an "Assinatura pendente" badge with a filter, drops out of the dashboard's active-member count, and receives no push.
- **D-499: Accept a Realtime and push tail of up to one hour.** Data always comes through the API, which is already cut; Realtime only signals a reload. The cut removes the push subscriptions of that membership. The session is NOT revoked, because the Supabase identity is shared across tenants (08.1) and a sign-out would also drop the person from other communities.
- **D-500: The admin learns of cuts and returns only through the members list.** The badge and filter of D-498; no new notification type.

### Admin configuration
- **D-501: A new `payments` module, switched on per tenant by `super_admin`; `admin_tenant` configures it.** It is its own package (MOD-01..05), depends on the kernel and on the store's published contracts only, and with it off nothing changes for anyone and the gate stays open. The store's gateway-driven purchase requires both `payments` and `store`.
- **D-502: Mappings live where the admin already works.** Access products are registered on the Pagamentos screen (gateway product id plus checkout link, which feeds the Assinar button). Store products carry their gateway product id and checkout link in the PRODUCT FORM next to the price, keeping the product form the single writer of what a product unlocks (D-363, D-418).
- **D-503: A "Eventos recentes" list on the Pagamentos screen.** It shows the latest events with a state (applied, sem membership, produto desconhecido, ignored), "recebido há X" and, on the unmatched ones, a "Liberar manualmente" action (the existing grant). It doubles as the integration test. No raw payload is shown to the tenant.
- **D-504: An "Acessos" tab on the Pagamentos screen replaces the SQL Editor.** One row per e-mail with source, state and validity; actions to release an e-mail before the person signs up, block, and remove a manual access; search by e-mail.

### Store purchases through the gateway
- **D-505: Refund and chargeback always revoke a store entitlement, and an inactive subscription revokes it too.** A one-off purchase is revoked only by refund, chargeback or an admin. A late or canceled subscription revokes like platform access (D-496); its return restores the entitlement. The order becomes `revoked` and the member may buy again (D-359).
- **D-506: With a gateway on, Comprar opens the tenant's checkout link and nothing is faked in the meantime.** The product stays locked until the webhook creates the order; then the app unlocks it through the existing Realtime signal and shows an in-app "Compra confirmada" notification. No local "processando" state.
- **D-507: The order records what the gateway reports as paid.** `amount_cents` is the charged amount in BRL cents (coupon, discount and installments already resolved by the gateway), so the Financeiro dashboard (08.7) sums real revenue. The product's `price_cents` becomes a storefront reference. This supersedes D-361 for gateway orders only. — **Reversibility:** costly — `store_orders` rows written this way mean something different from simulated ones, and the dashboard sums both.
- **D-508: No link, no purchase, and the simulated purchase only exists for tenants without a gateway.** For a tenant with a gateway on, a product without a checkout link has its Comprar button hidden or disabled ("Indisponível") and the product form warns "sem link de pagamento". It never falls back to the simulated `app.store_purchase`, which would unlock for free. Tenants with no gateway keep today's simulated purchase unchanged.
- **D-509: The webhook writes orders and entitlements through new admin-lane definer functions.** The existing `app.store_purchase`, `store_grant` and `store_revoke` read `app.tenant_id()` and `app.user_id()` from the JWT, which a webhook does not have; the new path takes the tenant and the membership explicitly and still never opens a tenant-lane write policy. `store_orders.provider` accepts the gateway name and `provider_ref` carries the gateway's order id; entitlements keep `source = 'purchase'`.

## Summary

The phase is a **kernel refactor plus one new module**. Five facts from the code shape everything:

1. **The admin lane is kernel-only** (Biome `noRestrictedImports` on `@rede-social/core/db/admin-tx`; the allowed kernel folders are `tenancy`, `platform`, `media`). A webhook is unauthenticated, so ingestion, the event inbox and the state changes must run in the admin lane, hence **inside a new kernel folder `packages/core/server/payments/`** (add it to the Biome override exactly as `media` was). The `payments` **module package** owns the admin surface (routes behind `payments.manage`, contracts, props-only UI); the gateway seam, adapters, inbox, apply job, `access_grants` and the gate functions are kernel. This is the `VideoProvider`/`media/video` precedent, not a deviation.
2. **Kiwify is a state-snapshot webhook with an HMAC-SHA1 `signature` query parameter** [CITED: Kiwify's own "Webhooks (pt-br)" page]. There is **no event id**; the signed material is described inconsistently (the JS example re-serialises the JSON, the PHP example uses the raw body). Money is integer cents. `customer_access.has_access` is "the current state when the webhook was sent", and Kiwify itself says delayed/re-sent deliveries carry the state of *now* and may arrive out of order.
3. **Today's allowlist is global and the checks are unconditional** (WR-01). Re-keying to per-tenant `access_grants` with an **explicit per-tenant gate that defaults off** removes WR-01 by construction: nothing is refused until a tenant admin turns the switch on.
4. **`requireAuth` runs one definer lookup per request and never caches** (`app.membership_in_tenant`). The cut check belongs in that same round trip through a new expand-only variant of the function, not in a second query and not in a cache.
5. **Two locked decisions need a one-line confirmation** (see Contradictions): D-495 as literally written would lock members of *ungated* tenants out once the production hooks are on, and D-496 ("canceled cuts immediately") may cut a subscriber Kiwify still considers paid through the period (`access_until`).

**Primary recommendation:** Build `access_grants` + the gate SQL functions + the new `requireAuth` lookup first (kernel, behaviour-preserving while every tenant is ungated), then the webhook seam/inbox/apply job with a `fake` adapter and the Kiwify adapter fed by the official example payload, then the module screens, then the store gateway definers; capture one real "Testar Webhook" delivery from a real Kiwify account in the very first plan and keep every Kiwify-specific decision inside `kiwify.ts`.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Webhook ingestion (verify, dedupe, enqueue) | API (`apps/api` route) + Kernel service (admin lane) | — | Unauthenticated, signature is the auth; admin lane is kernel-only (Biome), so the route calls `packages/core/server/payments/inbox.ts` as `mux.ts` calls `recordProviderEvent`. |
| Applying an event (grant/cut, order/entitlement) | Worker (pg-boss job, kernel handler) | Database (definer functions) | State change must not run in the 40 s Kiwify window; the store writes only via definers (STORE-20). |
| Gateway seam + adapters (Kiwify, fake) | Kernel (`server/payments/`) | — | Same place as `VideoProvider`; module code cannot reach the admin lane or the raw body wiring. |
| Per-tenant secret custody | Kernel (AES-256-GCM, platform key in env/Secret Manager) | Database (ciphertext in a zero-policy table) | Plaintext only exists in API process memory during verification. |
| Gate evaluation per request | Database (one definer function) | API (`requireAuth`) | Must be live (no cache) and cheap; SQL keeps the precedence rule in one place for API, hooks, dashboard and admin list. |
| Coarse Auth hooks | Database (`security definer`, 4xx only) | Supabase Auth | They run inside GoTrue; they cannot know the tenant. |
| Per-tenant sign-up/join/first-admin decision | API (`signupMember`, `joinTenant`, `createTenant`/invites) | Database | The host selects the tenant; the API has it, the hooks do not. |
| Pagamentos screens, permission, settings | Module `payments` (routes + props-only UI) + Frontend Server (RSC pages/actions) | Kernel services for admin-lane reads | Matches how Cursos/Loja screens are built; reads of zero-policy tables go through kernel services with explicit tenant predicates (as `admin-members.ts`). |
| Cut screen, no-access notice, error-code routing | Frontend Server (Next `(auth)` route + BFF counters route) | API | Branches on the published error code. |
| "Compra confirmada" + push cleanup | Worker (event bus → notifications sink) | Realtime Broadcast (`tenant:<t>:user:<u>`) | Existing seam (`membership.blocked` precedent); ids-only signals. |
| Store purchase mode / checkout link | Database (kernel seam functions) | Store module service | The store asks `app.*` functions by name (community-gate precedent), so it stays free of gateway tables (D-488). |

### Delivery and security
- Kiwify POSTs **JSON** to the URL; success is any **2xx**; otherwise **retried up to 5 times**; **3xx counts as failure** (no redirects); **40 s** timeout. The page's own sample handler answers `200 {status:'ok'}` to non-POST (HEAD) requests. `[CITED]`
- Signature: "Em cada requisição POST você vai receber o parâmetro **`signature` na querystring** (na URL)… use o **token do seu webhook** (exibido no painel na hora da criação ou edição)". Formula: `signature = hmac_sha1(JSON.stringify(request.body), secretKey)`; hex digest. `[CITED]`
- **Inconsistency that must be settled by the first captured delivery:** the Node example computes `crypto.createHmac('sha1', secret).update(JSON.stringify(order))` where `order = JSON.parse(rawBody)` (the *re-serialised* object), while the PHP example computes `hash_hmac('sha1', $payload, $secret_key)` over the **raw bytes** (`file_get_contents('php://input')`). `[CITED]` Adapter rule: compute both candidates (raw body, and `JSON.stringify(JSON.parse(raw))`), accept if **either** matches with `timingSafeEqual`; record which one matched in a log field (`sigVariant`) so the capture shows which is real. Accepting both cannot enable forgery (both need the secret).
- Official API: `POST https://public-api.kiwify.com/v1/webhooks` body `{ name, url, products ("all" or ids), triggers[], token }`; response `Webhook` includes `id`, `token`, timestamps. Triggers enum: `boleto_gerado, pix_gerado, carrinho_abandonado, compra_recusada, compra_aprovada, compra_reembolsada, chargeback, subscription_canceled, subscription_late, subscription_renewed`. `[VERIFIED: docs.kiwify.com.br/api-reference/webhooks/create.md, fetched 2026-10-20]` The token is chosen/shown by the producer; our flow is "admin pastes the token" (UI-D-514).
- The signed material contains **no timestamp**: there is no replay window to enforce (see Pitfall 3 for the compensating control).

### Pattern 1: The seam (VideoProvider shape, per-integration instead of per-env)
**What:** `GatewayProvider { name; verify(rawBody, query, secret): void (throws); normalise(rawBody): NeutralPaymentEvent }`. The route resolves the adapter from the **integration row's `provider`**, not from env (Mux is a process singleton; payments are per tenant). `fake` is selectable only when `PAYMENTS_PROVIDERS` env/`NODE_ENV` allows it (production refuses it, mirroring `assertProductionEnv`).
**Example (Kiwify verify, both signed-material candidates, constant time):**
```typescript
// Source: Kiwify Notion "Webhooks (pt-br)" examples (Node + PHP); node:crypto docs
import { createHmac, timingSafeEqual } from 'node:crypto';

function sameHex(a: string, b: string): boolean {
  const x = Buffer.from(a.toLowerCase(), 'utf8');
  const y = Buffer.from(b.toLowerCase(), 'utf8');
  return x.length === y.length && timingSafeEqual(x, y); // length check first: timingSafeEqual throws on unequal length
}

export function verifyKiwify(raw: string, signature: string | undefined, token: string): 'raw' | 'reserialised' {
  if (!signature) throw new GatewayError('invalid_signature');
  const mac = (m: string) => createHmac('sha1', token).update(m).digest('hex');
  if (sameHex(mac(raw), signature)) return 'raw';                       // PHP example
  let reserialised: string;
  try { reserialised = JSON.stringify(JSON.parse(raw)); } catch { throw new GatewayError('invalid_signature'); }
  if (sameHex(mac(reserialised), signature)) return 'reserialised';     // Node example
  throw new GatewayError('invalid_signature');
}
```
**When to use:** always; the variant string goes to the log only.

### Pattern 2: Route = verify, record, enqueue, 2xx (copy `apps/api/src/routes/webhooks/mux.ts`)
Plain `.post` (not an OpenAPI route), `c.req.text()` before any parse, `Cache-Control: no-store`, `403` with a bare body on failure, log `{event, provider, integrationId, requestId}` only — never the body, query string or token (`signature` is in the URL: **do not log `c.req.url`**; the request logger must be checked, see Pitfall 6). Add `.on(['GET','HEAD'], …) → 200 {status:'ok'}` (Kiwify's sample answers non-POST with 200). Unknown or disabled integration id → `404` **before** any DB write or crypto (cheap rejection of random traffic).

### Pattern 3: Inbox idempotency without an event id
`payment_events.dedupe_key = sha256(rawBody)` hex, `UNIQUE (integration_id, dedupe_key)`, `INSERT … ON CONFLICT DO NOTHING RETURNING id`; enqueue only when a row came back (`singletonKey = eventId`). A duplicate whose existing row is not `applied`/terminal **re-enqueues** (so a failed job is recoverable by Kiwify's manual "Reenviar"). Retries re-send identical bytes, so retries and replays collapse to one row. Two genuinely different events cannot share a body (they differ in `order_id`/`webhook_event_type`/`updated_at`).

### Pattern 4: Order-of-events policy (recommended)
Kiwify reports **current state at send time**, not an immutable fact. Therefore:
1. **One-off orders (no `Subscription`)**: key = `order_id`; rank `paid(1) < refunded(2) = chargedback(3)`; a later event never lowers the rank; `refund/chargeback` is terminal. A late `order_approved` after a refund is recorded `ignored: "Evento mais antigo que o último recebido"`. The memory is the inbox itself: before granting, `exists (select 1 from payment_events where tenant_id=$1 and external_ref=$2 and type in ('purchase_refunded','chargeback') and state='applied')` (index `(tenant_id, external_ref)`).
2. **Subscriptions**: key = `subscription_id`; the gateway is the truth, so **arrival order wins** and the state is derived from the payload's state fields (event type first for D-496, `customer_access.has_access` as fallback). Because every delivery attempt re-reads the state at send time, the latest delivery carries the freshest state.
3. **Gateway timestamps are informational only for Kiwify** (`updated_at`/`approved_date` are minute-precision local strings with no timezone) — the adapter returns `occurredAt: null`; a future gateway with reliable ISO timestamps fills it and the apply step then also drops events older than the stored `last_event_at`.
4. A `refund/chargeback` on a subscription charge suspends the subscription key; a later `subscription_renewed` re-grants (new charge). `access_grants.valid_until` stores `Subscription.customer_access.access_until` **for display only**.

### Pattern 5: Gate evaluation in SQL, live (new expand-only definer functions)
```sql
-- kernel migration (custom). All: security definer, search_path = '', stable, EXECUTE to api_user.
create or replace function app.access_gate_on(p_tenant uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.tenant_modules tm
                  where tm.tenant_id = p_tenant and tm.module_key = 'payments'
                    and tm.enabled and tm.settings->>'gate' = 'true')
$$;

-- D-489 precedence for one e-mail in one tenant: blocked > active > (manual release) > inactive > none
create or replace function app.access_effective(p_tenant uuid, p_email text) returns text
language sql stable security definer set search_path = '' as $$
  with e as (select lower(btrim(p_email)) as email),
  g as (select g.source, g.status from public.access_grants g, e
         where g.tenant_id = p_tenant and g.email = e.email)
  select case
    when exists (select 1 from g where source = 'manual' and status = 'blocked') then 'blocked'
    when exists (select 1 from g where source = 'gateway' and status = 'active') then 'active'
    when exists (select 1 from g where source = 'manual' and status = 'active') then 'active'
    when exists (select 1 from g where source = 'gateway' and status = 'inactive') then 'inactive'
    else 'none' end
$$;
```
(See Contradiction C11: this implements D-489 literally, in which a gateway `inactive` outranks a manual release only when no gateway row is active; the alternative ordering is a one-line change.) `app.access_state(p_tenant, p_user)` returns `'open'` (gate off, or role staff) / `'granted'` / `'cut'` / `'blocked'` by joining `public.users.email`; the new `app.membership_in_tenant_gated(p_user, p_tenant)` returns the six existing columns **plus** `access_state`, and `requireAuth` calls it instead of `membershipInTenant` (the old function stays for the still-serving API revision: expand-only). `memberships_of_user` gets the same twin for generic hosts.

### Anti-Patterns to Avoid
- **Caching the cut state** (flags-cache style): D-09 forbids it for blocks and D-496 asks for immediate effect; the gate *switch* may be read through the same live SQL.
- **Reading `tenant_modules` for the gate from the tenant lane inside `requireAuth`**: `requireAuth` deliberately uses bare `api_user` definer calls; do not open a lane there.
- **Persisting or logging the raw webhook body**: it carries CPF, mobile, address and IP. Persist only the normalised neutral fields; job payload is `{ eventId }`.
- **Env-selecting the adapter** (Mux style): the provider is per integration row.
- **A `kiwify` string in schema CHECKs**: use a format check for `provider` (`^[a-z][a-z0-9_]{1,30}$`), not an enum (see C7).
- **Falling back to the simulated purchase** when a gateway product has no link (D-508): enforce in SQL, not only in the UI.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Constant-time compare | `===` on hex strings | `crypto.timingSafeEqual` after a length check | Timing oracle on the only authentication of a public route |
| Secret encryption | Custom XOR/base64 or storing plaintext | `aes-256-gcm`, 12-byte random IV, `key_version` column, integration id as AAD | Authenticated encryption; AAD binds a ciphertext to its row so rows cannot be swapped |
| Idempotent insert + enqueue | read-then-write | `INSERT … ON CONFLICT DO NOTHING RETURNING` + `enqueueInTx` with `singletonKey` in one admin tx | The `recordProviderEvent` shape; races converge |
| E-mail normalisation | JS `toLowerCase` / citext | SQL `lower(btrim())` on both sides + table CHECK | citext `=` does not resolve under `search_path=''`; JS and SQL lower-casing differ for non-ASCII (quick owq IN-03) |
| Live "may this user pass" rule | duplicating precedence in TS, hooks, dashboard, admin list | the `app.access_*` SQL functions | One implementation; pgTAP can pin it |
| Orders/entitlements writes | tenant-lane insert policies | new definer functions (`service_role` EXECUTE only) | STORE-20: the ledgers have no write policy, by design |
| Push cleanup + Realtime nudge on cut | new code path | declare `membership.access_cut` (like `membership.blocked`) and let the notifications module subscribe | Same eager behaviour as a block, no new coupling (MOD-02) |
| Recent-event pruning | cron | `registerSweepFunctions(['payment_events_prune'])` (`app.<name>(p_batch int) returns int`) | The kernel's hourly sweeper already runs these |

**Key insight:** every hard part (per-request enforcement, hook hardening, definer-only ledgers, raw-body webhooks, eager push cleanup) already has a house pattern. The risk in this phase is not missing machinery; it is choosing the wrong layer for the first time (module vs kernel, lane, hook scope).

## Data Model (recommended; planner may rename columns, not the structure)

- **`access_grants`** (kernel, RLS on, **zero policies**; read/written by definers and the admin lane): `id uuid pk`, `tenant_id uuid not null → tenants on delete cascade`, `email text not null check (email = lower(btrim(email)))`, `source text check in ('manual','gateway')`, `status text check in ('active','inactive','blocked')` with `check ((source='manual' and status in ('active','blocked')) or (source='gateway' and status in ('active','inactive')))`, `provider text`, `external_ref text` with `check ((source='gateway') = (provider is not null and external_ref is not null))`, `mapping_id uuid` (hand-SQL FK to `payment_products`), `valid_until timestamptz`, `last_event_at timestamptz`, `terminal boolean not null default false`, `created_by_user_id uuid → users` (manual actor, for audit), `created_at`, `updated_at`. Indexes: unique `(tenant_id, email) where source='manual'`; unique `(tenant_id, provider, external_ref) where source='gateway'`; `(tenant_id, email)`; `(email) where status='active'` (hook, any tenant); `(tenant_id, updated_at desc, id)` for the Acessos list.
- **`payment_integrations`** (zero policies): `id uuid pk`, `tenant_id`, `provider text` (format check), `secret_ciphertext bytea`, `secret_iv bytea`, `secret_tag bytea` (or one `bytea`), `secret_key_id smallint`, `secret_set_at`, `last_event_at`, timestamps; `unique (tenant_id, provider)`. The Pagamentos card reads "Conectado" and `last_event_at` through a kernel service.
- **`payment_products`** (mapping): `id`, `tenant_id`, `provider`, `external_product_id text` (trimmed, ≤ 128), `kind check in ('access','store_product')`, `name text` (A-UI-1; access only), `checkout_url text check (checkout_url ~ '^https://')`, `target_id uuid` (store product; hand-SQL FK added in the **store** migration, MOD-02), `check ((kind='store_product') = (target_id is not null))`; **`unique (provider, external_product_id)`** (global, D-488) and `unique (tenant_id, target_id) where kind='store_product'`. RLS: tenant-lane SELECT/INSERT/UPDATE/DELETE for `admin_tenant` only (`app.tenant_role()='admin_tenant'`, the `tenantReadAdminWritePolicies` write predicate also on read: `external_product_id` is admin information). Members get the checkout URL only through definer seams.
- **`payment_events`** (inbox, zero policies): `id uuid pk`, `tenant_id`, `integration_id → payment_integrations`, `provider`, `dedupe_key text`, `type text` (neutral list), `external_ref text`, `external_product_id text`, `email text` (normalised, nullable), `occurred_at timestamptz` (null for Kiwify), `received_at timestamptz default now()`, `state text check in ('received','applied','no_membership','unknown_product','ignored','failed')`, `effect text`, `mapping_id uuid`; `unique (integration_id, dedupe_key)`; `(tenant_id, received_at desc, id)` for the Eventos list; `(tenant_id, external_ref)` for the terminal check. **No payload column.** Prune via sweep function (retention ≥ 180 days, a discretion default; shorter retention weakens Pitfall 3's replay memory).
- **`tenant_modules` row for `payments`**: `settings = {"gate": true|false}` holds the switch (no new column on `tenants`, SCHEMA-CONVENTIONS (f)). Writes are admin-lane (`gate.ts`), atomic with the optional "release current members" insert.
- **Store seam functions (kernel migration, bodies reference only kernel tables):** `app.payments_gateway_mode(p_tenant uuid) returns boolean` (payments module on **and** an integration row exists), `app.payments_checkout_url(p_tenant uuid, p_product uuid) returns text`. **Store migration:** `app.store_gateway_purchase(p_tenant uuid, p_membership uuid, p_product uuid, p_provider text, p_provider_ref text, p_amount integer, p_paid_at timestamptz) returns table(outcome text, order_id uuid, product_name text)` and `app.store_gateway_revoke(p_tenant uuid, p_provider text, p_provider_ref text) returns table(outcome text)`; both `security definer`, `search_path=''`, `revoke … from public, anon, authenticated`, `grant execute … to service_role` only; every statement pins `tenant_id = p_tenant` and verifies the membership belongs to it. A **paid** order for an **archived** product is still granted (unlike the simulated purchase).

## Common Pitfalls

### Pitfall 1: Hooks that lock out ungated tenants
**What goes wrong:** literal D-495 ("any access in any tenant, staff, or platform admin") refuses the token of a member of an ungated tenant (no access row, not staff) the day the production hook is enabled.
**Why:** the gate is per tenant and defaults off, but the hook is global.
**How to avoid:** add the "membership in a tenant whose gate is off" disjunct (+ `memberships_user_idx`); pgTAP case: member of an ungated tenant passes; member of a gated tenant with no row is refused; mixed memberships pass if any tenant qualifies. **Warning signs:** the "who would be locked out" query returns every member in the first rollout.

### Pitfall 2: Treating the gateway timestamp as ordering truth
**What goes wrong:** Kiwify's `updated_at`/`approved_date` are minute-precision, timezone-less strings; sorting by them reorders or ties events.
**How to avoid:** Pattern 4 — rank for one-off orders, arrival + payload state for subscriptions; the adapter returns `occurredAt: null`.

### Pitfall 3: No replay window is available
**What goes wrong:** the HMAC covers no timestamp, so a captured signed body is valid forever; replaying an old `subscription_canceled` could cut a renewed member.
**How to avoid:** the permanent `(integration_id, dedupe_key)` unique key makes an exact replay a no-op *while the row exists* — so do not prune the inbox faster than your replay-risk horizon (≥ 180 days default), and the apply step never lets a replayed `late/canceled` for a subscription older than the last applied `renewed` land when `occurredAt` is known. Accept and document the residual (an attacker needs a previously delivered signed request, i.e. already a compromise of the tenant's own traffic).

### Pitfall 4: Subscription renewals collide with `store_orders_live_uq`
**What goes wrong:** one live order per member and product (`store_orders_live_uq`, `schema.ts:236`) — a renewal with a **new** `order_id` would try to insert a second live order.
**How to avoid:** a renewal of an *active* subscription creates no new order (state refresh only); after a revoke (`revoked` frees the arbiter) the next paid event creates a new order. Renewal revenue is **not** summed in v1 (see A6/Open Question 4).

### Pitfall 5: Cross-tenant mapping lookups
**What goes wrong:** resolving the product with only `(provider, external_product_id)` lets a webhook signed with tenant A's secret act on tenant B's mapped product.
**How to avoid:** lookup = `integration.tenant_id` **and** provider **and** external id; a hit under another tenant is `unknown_product` for A. pgTAP/integration case: two tenants, A's signed event naming B's product.

### Pitfall 6: The secret in the URL
**What goes wrong:** `?signature=` rides the query string; Cloud Run request logs and any access-log middleware may print it, and the **token** is never in the URL (only the HMAC). A leaked signature is a replay token for that exact body only.
**How to avoid:** never log `c.req.url`/query in the route; check `apps/api/src/http/logger.ts` redaction; the token itself is decrypted in memory only. `[ASSUMED]` that the request logger prints no query — verify in the plan.

### Pitfall 7: `pg-boss` `short` policy is not idempotency
`singletonKey` dedupes only jobs still in `created` state (`boss.ts` QUEUE_POLICY comment). The inbox unique key is the real arbiter; the apply step must itself be idempotent (`select … for update` the event row, skip if `applied`).

### Pitfall 8: Definer functions reading JWT claims in the worker/webhook lane
`app.store_purchase/store_grant/store_revoke` read `app.tenant_id()`/`app.user_id()`; the webhook has none. New functions take explicit args and must verify membership↔tenant themselves (the owner bypasses RLS).

### Pitfall 9: Dashboard/other "live member" predicates are copy-pasted
The live predicate (`status='active' and blocked_at is null and deleted_at is null`) is repeated in ~15 SQL function bodies (notifications fan-out, push subscriptions, dashboard, social, courses). Do **not** edit all of them: D-498 needs only the admin list and the active-member **count**; "no push while cut" is satisfied by deleting the member's subscriptions at cut time (they cannot re-subscribe, `requireAuth` refuses them).

### Pitfall 10: Config drift in homolog
A `[remotes.homolog]` table inherits the base hook blocks (`enabled = true`); without an explicit block and a CI guard, `config push` could enable hooks against an empty hml database.

### Secret custody (AES-256-GCM, AAD = integration id)
```typescript
// Source: Node.js crypto docs (aes-256-gcm); key from PAYMENTS_SECRET_KEY (base64, 32 bytes)
import { createCipheriv, createDecipheriv, randomBytes } from 'node:crypto';
export function seal(plain: string, key: Buffer, integrationId: string) {
  const iv = randomBytes(12);
  const c = createCipheriv('aes-256-gcm', key, iv);
  c.setAAD(Buffer.from(integrationId));
  const ct = Buffer.concat([c.update(plain, 'utf8'), c.final()]);
  return { iv, ct, tag: c.getAuthTag() };
}
export function open(s: { iv: Buffer; ct: Buffer; tag: Buffer }, key: Buffer, integrationId: string): string {
  const d = createDecipheriv('aes-256-gcm', key, s.iv);
  d.setAAD(Buffer.from(integrationId));
  d.setAuthTag(s.tag);
  return Buffer.concat([d.update(s.ct), d.final()]).toString('utf8');
}
```

## Contradictions and Decisions To Confirm (CONTEXT vs the code and the gateway)

- **C1 (D-495 vs ungated tenants) — needs a one-line confirmation.** Literal D-495 makes the token hook refuse a member of a tenant whose gate is off. Resolution proposed: add "a membership in a tenant whose gate is off" to the token hook (and an index on `memberships(user_id)`). Without it, enabling the production hooks locks out every existing member.
- **C2 (D-496 vs Kiwify `customer_access`/`access_until`) — needs a product decision.** Kiwify exposes `Subscription.customer_access.{has_access,active_period,access_until}`; a mid-period cancel very likely keeps access until `access_until` (to be confirmed by the capture). D-496 says canceled cuts immediately with no grace. Default (literal D-496): `subscription_canceled` and `subscription_late` → suspend. Alternative: derive from `has_access`. The adapter isolates the choice; `valid_until` is stored either way.
- **C3 (D-492 timing).** "Accepting an invite writes the manual access" is too late for `before_user_created`, which fires at invite *send*. Write the manual grant when the invite is created (and re-assert on accept), or the hook must also allow a pending `tenant_invites` row.
- **C4 (D-487 migration).** Global rows have no tenant; see A3.
- **C5 (D-499 vs existing precedent).** D-499 accepts a tail of up to one hour; the shipped `membership.blocked` flow already deletes devices and nudges Realtime immediately after commit. Reusing it for the cut (event `membership.access_cut`) makes the tail near zero at no extra design cost.
- **C6 (D-506 "existing Realtime signal").** The existing signal (`notifications.changed`) refetches **counters** (`LiveShell`); it does not refresh a server-rendered product page. A small web handler (refresh on the new notification kind or on a dedicated event) must be planned; UI-SPEC UI-D-525 assumes it exists `[VERIFIED: LiveShell.tsx:82-110 reads only counters]`.
- **C7 (D-486 vs D-509).** "No `kiwify_*` outside the adapter" and "`store_orders.provider` accepts the gateway name" are reconciled by a **format** CHECK, not an enum (the provider name is data).
- **C8 (D-501 vs the Biome lane rule).** A module "depending only on the kernel" cannot host the unauthenticated webhook (no admin lane). Reconciled by kernel-resident ingestion (`server/payments/`) and a module that owns the admin surface.
- **C9 (D-501 "payments requires nothing" vs store seam).** The store learns the gateway mode only through kernel seam functions; with `payments` off the functions answer `simulated`.
- **C10.** `joinTenant` has no allowlist check today (CONTEXT said so): confirmed `[VERIFIED: join.ts:137-264]`; the check is new code, not a refactor.
- **C11 (D-489 literal reading).** "A manual block, otherwise the gateway's latest state, otherwise a manual release" means a gateway `inactive` (canceled subscriber) can outrank a manual release, and an admin cannot keep such a person (gateway rows cannot be removed by hand). Pattern 5 lets any **active** access win and applies `inactive` only when nothing is active; confirm that "release beats a gateway inactive" is *not* wanted.
- **C12 (manual block while the gate is off).** Blocks are inert when the gate is off (D-491). Proposed: while the gate is on, a manual block answers `MEMBERSHIP_BLOCKED`; the Acessos sheet should say a block has effect only while "Exigir assinatura" is on (copy for the planner/UI-SPEC delta).
- **C13.** CONTEXT's reference to `app.store_purchase` consulting the gateway is a new guard, not a feature of the existing function (Exact Code Surface).

## Open Questions

1. **Which signature variant does Kiwify really use?** — Known: two documented variants. Unknown: real behaviour. Recommendation: first plan captures a live delivery; both variants accepted meanwhile.
2. **Does a mid-period cancel keep `has_access = true`?** — Decide C2 with the capture in hand; keep the adapter switch.
3. **Does a subscription renewal carry a new `order_id` and `Subscription.id` stable?** — Determines the access key (`subscription_id ?? order_id`) and Pitfall 4; capture a renewal (Kiwify "Testar Webhook" for `subscription_renewed`, then a real one).
4. **Renewal revenue for recurring *store* products** — v1 records the first charge only; confirm that is acceptable for the Financeiro (CONTEXT defers only *access* subscription revenue).
5. **Currency other than BRL** — plan the `ignored` path now or ask Kiwify accounts to be BRL-only.
6. **Partial failure in the product form** (store save succeeded, payments mapping save failed) — recommendation: the payments save is a separate call; show the field error and keep the product (the form warns "sem link de pagamento" until fixed). Confirm acceptable versus a single transaction.

## Security Domain

### Applicable ASVS Categories (level 1; block on high)
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (webhook) | HMAC verification over the received request, `timingSafeEqual`, 403 on failure, nothing stored; Supabase Auth hooks unchanged in contract |
| V3 Session Management | yes | Cut does **not** revoke the shared Supabase session (D-499); `requireAuth` re-reads state every request |
| V4 Access Control | yes | Gate decided server-side per request; mapping lookup tenant-pinned; Pagamentos routes behind `requireModule('payments')` + `payments.manage`; `404` (not 403) for non-admins |
| V5 Input Validation | yes | Zod on every admin DTO; adapter parses with Zod and drops unknown shapes to `ignored`; `https:` only for checkout URLs; e-mail normalised in SQL |
| V6 Cryptography | yes | AES-256-GCM via `node:crypto` (never hand-rolled), random IV, key id for rotation; HMAC-SHA1 is **mandated by the gateway** (acceptable for HMAC; flagged legacy) |
| V7 Error Handling and Logging | yes | Log ids, type, state only; never body, query string, token, e-mail (e-mail is PII; the existing `signup.not_allowed` precedent omits it) |
| V8 Data Protection | yes | Do not persist the payload (CPF, phone, address, IP); job payload = `{eventId}`; retention sweep |
| V13 API | yes | Webhook is a plain POST outside OpenAPI; rate limiting does not exist in this repo (IN-01 of owq): cheap 404 for unknown integration + size cap on the body are the mitigations; flag rate limiting as an accepted residual |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Forged webhook (grants access / unlocks product) | Spoofing/Tampering | Per-tenant secret HMAC, constant-time compare, fail closed on missing signature/secret |
| Replay of a captured signed request | Tampering | Permanent `(integration_id, dedupe_key)`; no timestamp is signed by Kiwify so retention matters (Pitfall 3) |
| Cross-tenant effect via a payload naming another tenant's product | Elevation | Lookup pinned to `integration.tenant_id`; pgTAP/integration negative |
| Free unlock through the simulated purchase endpoint when a gateway is on | Elevation | DB guard in `app.store_purchase` (PAY-26) |
| Enumeration through the gate message | Information disclosure | One sentence for every refusal; refuse before the duplicate path as today; never name other communities (D-302) |
| Webhook secret disclosure | Information disclosure | Write-only API, encrypted at rest, no log, not in `GET` DTOs, password-type field with no reveal |
| Phishing via the checkout link | Spoofing | Link fetched from the API per request, only stored `https:` URLs rendered (UI-D-532) |
| Lock-out of staff/first admin | Denial of service | Staff/platform-admin exempt in SQL and in hooks; invite writes the manual grant |
| Hook raising / 5xx locks every login | Denial of service | 4xx-only bodies, uuid guard, `search_path=''`, pgTAP malformed-input cases |
| SSRF | — | None: the webhook path makes **no outbound request** (nothing fetched from the payload) |
| E-mail normalisation mismatch (case, whitespace, plus-addressing, non-ASCII) | Spoofing/Denial | `lower(btrim())` in SQL on both sides + CHECK; plus-addressing intentionally *not* folded; non-ASCII fails closed (quick owq IN-03) |
| Timing oracle on signature | Information disclosure | `timingSafeEqual` after length check |
