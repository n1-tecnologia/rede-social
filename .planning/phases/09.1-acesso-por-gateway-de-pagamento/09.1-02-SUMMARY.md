## Accomplishments

- A gated tenant (`payments` row enabled with jsonb `settings.gate = true`) refuses a member with no access row with `403 SUBSCRIPTION_PENDING` (`details.tenantName`), admits her on the very next request after a grant, never touches `admin_tenant` / `support_tenant`, and leaves a tenant with the gate off, absent or disabled exactly as before (tracer, proven against the live stack including the lookalike values, a flip between two requests and a race around a flip).
- The decision lives only in SQL: `app.access_gate_on`, `app.access_effective` (D-489 literal), `app.access_state`, `app.membership_access_cut`, `app.access_cut_user_ids`, plus the `_gated` twins of the 08.1 lookups that return `access_state` in the same statement. The 08.1 functions are untouched (md5 pinned), so the API revision serving during `supabase db push` keeps working.
- `access_grants` is born with RLS on, zero policies, no privilege for `anon` / `authenticated`, five named indexes, five CHECKs; one e-mail can hold a manual release and a manual block (Desbloquear is a delete of the block row).
- Published contract: `SUBSCRIPTION_PENDING` (one-way, user-confirmed), `ERROR_MESSAGES` sentence, `payments` module key last and off by default, `@rede-social/contracts/payments` (enums and the `membership.access_cut` / `payments.purchase_confirmed` events), the two platform catalog strings.
- pgTAP 204 (86 assertions) pins shape, CHECKs, exposure, gate truth table, the D-489 precedence table, the staff exemption, tenant pinning, the gated lookups and the catalog hardening.
