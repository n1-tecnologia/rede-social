<planning_decisions>
1. **The signal already exists; fix the reader.** `releaseEmail` answers the row the screen lists, and its `state` is the database's verdict. Changing the server would add a rule (refuse, or skip the write) the owner did not ask for; changing what the screen says about that verdict is "keep the rule, fix the notice".
2. **A-G1 (the assumption this plan surfaces).** Liberar e-mail on an address the gateway has cut keeps answering 200 and keeps writing the manual `active` row (idempotent, exactly as before; no new refusal, so PAY-22's release before the account exists is untouched). The row is inert while the gateway row stands (it only matters if the gateway rows disappear, which no code path does) and the Acessos list shows one row per e-mail, so it is not listed separately. The honest notice is the fix: the web reads `access.state` and says the address stays without access because the subscription is pending. Alternative not taken, flip-able by one read of `app.access_effective` inside `releaseEmail`: skip the write for a gateway-cut address; it was not chosen because it changes server behaviour beyond "keep the rule, fix the notice" and the integration suite of plan 10 asserts today's writes.
3. **A-G4 (this path).** The stays-cut toast uses the `info` tone and lasts six seconds (`durationMs: 6000`) because nothing was admitted and the line is longer than the three-second default; the success toast of an admitted address is unchanged.
4. **The `blocked` branch reuses a line that exists.** A release that races a block (P55) can come back `blocked`; the host shows `payments.errors.emailBlocked` as an error. No new copy is invented for it.
5. **`ReleaseEmailSheet` stays as it is.** It decides nothing (its own docblock says so): it hands the server's row to the host, which already owns every toast of the Acessos screen.
6. **Assumption-delta: no-change.** The noun that stays primary is "effective access state per (tenant, e-mail)".
7. **File counts.** Task 1 lists five files (two of them tests of one slice); Task 2 five documents. Per-plan file-count warnings are advisory in this phase.
</planning_decisions>
