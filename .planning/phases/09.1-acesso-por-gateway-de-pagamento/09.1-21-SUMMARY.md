# Phase 09.1 Plan 21: Gate release and the gateway cut Summary

**The bulk release "Liberar membros existentes" now counts and writes only effective-none members; the preview and the gate write carry a second database-tallied integer, `gatewayCut`, and the dialog and four toasts tell the admin the lapsed subscribers stay cut, with D-489 and `app.access_effective` untouched.**

## Accomplishments

- `liveMembers` and `tallyMembers` in `packages/core/server/payments/gate.ts` replace the old two-state `releasable` fragment. One statement returns `count(*) filter (where eff = 'none')` and `count(*) filter (where eff = 'inactive')` over one live-member population, and the release insert selects from the same fragment filtered to `eff = 'none'`, so a gateway-cut member never receives a dead manual row and `released` equals the members whose state really changed to `active`.
- `PUT /v1/payments/gate` answers `{ required, released, gatewayCut }`, the cut read by the same tally inside the same transaction when the gate is turned on (0 when turned off); the `payments.gate.set` log line carries both counts and no e-mail.
- The gate dialog shows one stays-cut note whenever `gatewayCut` is above zero (alone when nobody can be released, with no checkbox), the tone still follows the release box alone, and the success toast is one of four lines chosen from the server's `released` and `gatewayCut`; the two that name a cut last six seconds.
- The paper trail the owner asked for: UI-SPEC rows UI-D-516, both confirmation rows, the Gate copy row, A-UI-5, E04 and the preview line amended plus an `## Amendment G-09.1-1` section; OpenAPI descriptions, README and client docblocks updated; A-P9 marked confirmed by the owner and A-G2..A-G5 recorded; WINDOWS entries 132 (copy deviation) and 133 (unrun browser check).
