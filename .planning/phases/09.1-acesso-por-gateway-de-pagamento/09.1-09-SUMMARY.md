# Phase 09.1 Plan 09: The payments admin API and module Summary

**A tenant admin can now do the whole payment setup with HTTP calls and the effects are real: connect a gateway with a write-only token, register access products, map a store product, and switch the gate on with a set-based release of the members who already exist, all through a new kernel-light `@rede-social/module-payments` whose permission is admin-only by construction.**

## Accomplishments

- **Tracer through the real stack.** Overview before and after saving (the webhook URL is identical because the handle is derived from tenant and provider), the 409 `gate_requires_setup` until an integration and a product exist, an access product with a link, a preview equal to an independently computed count (members with no row of any kind), the release inside the switch's transaction (`released` equals the manual rows `adminSql` finds), the released member passing, staff and the manually blocked e-mail untouched, a later arrival 403 `SUBSCRIPTION_PENDING`, a repeat releasing only that arrival and then 0, and `{ required: false }` reopening the tenant. The token appears in no response body.
- **The module.** `@rede-social/module-payments` has no nav, no `requires`, no tables and no jobs of its own; `payments.manage` is composed for `admin_tenant` only (registry cases 20 and 21 pin it, and that adding the entry changes no other module's permissions or bootstrap entry); `sweepFunctions: ['payment_events_prune']`. Every route sits behind `requireAuth`, `requireModule('payments')` and `requirePermission('payments.manage')`.
- **Kernel services hold every admin-lane write.** `saveIntegration` seals the token bound to its row (derived id on first save, the existing row's id afterwards), replaces it atomically with a fresh IV and answers only `{ connected: true }`. `setGate` locks the module row and a per-tenant advisory lock, checks the preconditions, releases with one `insert ... select ... on conflict do nothing returning`, and merges `settings.gate` with `||` so no other key is lost.
- **Access products and the store mapping.** Create/patch/delete through the tenant lane with the explicit tenant predicate too; the oldest product with a link feeds "Assinar"; the last product cannot go while the gate is on; the mapping is confirmed with the store's published `app.store_product_exists(uuid)` by SQL name (this package imports nothing from the store); unknown, foreign and non-uuid ids are the same bare 404; a held gateway id is `409 gateway_product_taken` naming nobody.
- **Hardening proven.** Without the per-tenant lock a gate ON racing the removal of the last product left the gate on with no product at round 9 of 40; with it, no round fails. Concurrent gate writes release everyone exactly once; concurrent first saves leave one row with the derived id and a token that opens.
