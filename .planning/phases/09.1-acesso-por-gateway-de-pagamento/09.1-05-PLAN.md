<planning_decisions>
1. **The sealed secret is one text column.** `secret_sealed text` (`v1:<keyId>:<iv>:<tag>:<ct>`) instead of three `bytea` columns: no custom Drizzle type, one atomic update, the key id travels with the value, and a future algorithm change is a new prefix.
2. **Provider names are data, not an enum.** `payment_integrations.provider` and `payment_products.provider` carry a FORMAT check (`^[a-z][a-z0-9_]{1,30}$`); the set of adapters is code (`adapters.ts`), so a second gateway needs no migration (D-486, RESEARCH C7).
3. **The integration id is the route handle and the AAD.** It is a random uuid generated by the application before the insert (so the secret can be sealed bound to it) and appears in the webhook URL; it is not secret, the signature is the authentication.
4. **Reject cheaply, then decrypt.** Order: uuid shape, integration row (one indexed read), provider match, provider enabled, THEN decrypt and verify. Random traffic costs one primary-key read at most; there is no rate limiting in this repository (assumption A-P20), so the cheap 404 and the body limit are the mitigations.
5. **Events keep neutral fields only.** `payment_events` stores type, effect, `external_ref`, `order_ref`, product id, normalised e-mail, amount, currency and `valid_until`; the e-mail is the only personal datum and the admin needs it to answer a buyer.
6. **`fake` signs with HMAC-SHA256 hex over the bytes in `?signature=`.** Same code path shape as the real adapter (query parameter, raw bytes, constant-time compare) so the integration and e2e suites exercise the real route.
7. **Mapping reads and writes by a tenant lane, not the admin lane.** `payment_products` carries `admin_tenant` policies; plan 09's service uses `withTenantTx` for it, which is defence in depth over an explicit predicate. The two zero-policy tables are admin-lane only.
</planning_decisions>
