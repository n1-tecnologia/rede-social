<objective>
Close gap G-09.1-1 (UAT test 1, review finding WR-03, assumption A-P9) for the BULK release, "Liberar membros existentes" in the gate dialog (PAY-31).

The defect: `gate.ts` counted and wrote a manual `active` row for members whose effective access is `none` AND `inactive`, but `app.access_effective` ranks a gateway `inactive` above a manual release (D-489), so for the lapsed group the rows changed nothing, the preview said "the members a release would admit", the toast said "Acesso liberado para N membros" and N rows of dead data were written.

The owner decided on 2026-10-21 (LOCKED): keep the rule, fix the notice. So after this plan the release counts and writes only `none` members, the preview and the gate result carry a second integer, `gatewayCut`, from the same database tally, and the dialog and the toast say that those members stay cut. The preview count and the inserted-rows count equal the number of members whose state really changes to `active`.

Task 1 is the tracer: one path through every layer (contract field, SQL tally, release predicate, server action, dialog note, catalog line, API and web tests) for the PREVIEW side. Task 2 carries the same figure through the WRITE (result field, four toasts) and runs the edge battery over real rows. Task 3 is the paper trail the owner asked for: the UI-SPEC rows, the OpenAPI descriptions, the README and the assumptions ledger, plus the recorded deviation from sketch 013.

Decisions implemented: D-489 (kept literally: a manual block, then the gateway's latest state, then a manual release), D-491 (the explicit switch and its confirmation), D-492 (staff and blocked e-mails are never counted or released), D-496 (a cut returns by itself on a confirmed payment, which the new copy says).

Not in this plan (deferred or other gaps, do not pull in): WR-05, WR-06, WR-07, the WR-04 residual and IN-01..IN-06 (accepted and deferred by the owner, UAT test 7), the Kiwify capture, the real-device and design-team items (UAT tests 2, 3, 4). The single-address "Liberar e-mail" is plan 22.
