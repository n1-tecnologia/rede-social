# Phase 09.1 Plan 17: The store side of the payment gateway Summary

**A gateway-tenant member buys through a new-tab https checkout link and the product page refreshes itself into the owned block on the Realtime user signal; admins register the gateway product id and link beside the price, and the bell and the grid confirm purchases and flag unbuyable products.**

## Performance

- **Duration:** 17 min
- **Started:** 2026-10-21T10:04:39Z
- **Completed:** 2026-10-21T10:21:52Z
- **Tasks:** 3 (plus the prelude fix)
- **Files modified:** 28 in the plan range (11 created, 17 modified)

## Accomplishments

- **Tracer (Task 1).** `productPageView` returns `buyMode` (`simulated`, `gateway-link`, `gateway-unavailable`), the validated `checkoutHref` and `gatewayZone`. `GatewayPurchase` renders a brand `lg` full-width link (`target="_blank"`, `rel="noopener noreferrer"`, `ShoppingBag`, "Comprar", hidden suffix, helper 8px under it) or the disabled outline "Indisponível" with its note, and joins only the member's own `userTopic` for `notifications.changed` to call `router.refresh()` (1500 ms leading-plus-trailing throttle, first-join skip, re-join and tab-visible refresh, no-op outside a provider). The page wraps the action zone in one `aria-live="polite"` region for every gateway read, owned block included; simulated markup is untouched.
- **Product form (Task 2).** The "Pagamento" block sits after "Preço (R$)" and before "Comunidades liberadas", present only when the `payment` prop is not `null` (module on, `payments.manage` held, read succeeded). Link-needs-ID and the checkout-link rule run before any request; the save is store first, mapping second, with `createdId` and `savedMapping` refs so a failure of the second call keeps the product, the typed values and never repeats a create. `savePaymentMappingAction` puts or deletes (both empty), and the closed-outcome client in `lib/payments.ts` never throws.
- **Bell and pills (Task 3).** `payments.purchase_confirmed` renders "Compra confirmada: “{product}”. Seu acesso foi liberado." on a `ShoppingBag` disc, linking to `/loja/{encoded id}` and degrading to `/loja`. The `noLink` card pill (leading `CircleAlert` 12) and the warning header pill show to managers only, below the archived and owned pills in priority; the grid's load-more and refresh actions read `canManage` from the server bootstrap.

### Auto-fixed Issues

**1. [Rule 1 - Bug] Flaky post-close dialog assertions in the gate switch tests (prelude, belongs to plan 13)**
- **Found during:** plan 15's full gate, logged in deferred-items.md; fixed first in this run on the orchestrator's instruction.
- **Issue:** the "nobody to cut (count 0)" case of `GateSwitchRow.test.tsx` asserted `queryByRole('dialog')` was null synchronously after the switch flipped; the dialog's exit animation made it fail once under the concurrent gate. Three sibling cases in `AccessProductsCard.test.tsx` had the same post-close synchronous assertion.
- **Fix:** `await waitFor(() => expect(screen.queryByRole('dialog'...)).toBeNull())` in those four cases (the "never opened" assertions were left alone). No production code changed. The deferred-items.md entry is marked resolved.
- **Verification:** the `configuracoes/pagamentos` directory (156 tests) passed 5 of 5 repeats alone, and the web suite passed inside the concurrent turbo gate (twice).
- **Committed in:** `4f0de0d0` (outside plan 17's `commits:` measurement).

**2. [Rule 3 - Supporting tests] Test files beyond the plan's `files_modified` list**
- Added `app/(app)/loja/[productId]/page.test.tsx` (the plan asked for a page-level test, no file was named), `payment-actions.test.ts`, `actions.test.ts` (the grid actions' bootstrap rule) and `lib/product-payment.ts` + `lib/product-payment.test.ts` (one shared server loader so the two form pages do not duplicate the overview and mapping reads). All inside `apps/web`, no new dependency.

**3. [Rule 3 - Shape] Small departures from the plan text**
- `GatewayPurchase` takes no `productName` prop (the plan listed it, but the visible and hidden text never use it; the E12 note says the name appears nowhere in the buttons).
- `ProductForm`'s `payment` prop is optional with a `null` default instead of required, so the existing call sites and tests stay byte for byte; both pages pass it explicitly.
- The client link rule uses the contract's `isCheckoutLink` (https, host, no userinfo, no whitespace) with the plan's message "Informe um link que comece com https://." instead of a bare `startsWith('https://')`, so the form refuses exactly what the API would.
- `DELETE /v1/payments/store-products/{id}` answers 200 `{ connected, mapping: null }` in plan 09, not 204; the client tolerates both.
- `ProductForm`'s payment inputs are `disabled` while a save runs, like the other blocks.
- The warning pill also appears for a stored non-https link (the page already treats it as unavailable), so the manager's pill and the member's button never disagree.
