<planning_decisions>
1. **One grant function for every manual write.** `grantManualAccess(tx, { tenantId, email, createdBy })` is the only code that inserts a manual `active` row on behalf of an invite or accept; plan 09's release action reuses it. It normalises in SQL (`lower(btrim())`), `on conflict (tenant_id, email, status) where source = 'manual' do nothing`, and never touches a manual `blocked` row (a block outranks, D-489).
2. **The invite never overrides a block.** If the e-mail is under a manual block in the new tenant (impossible for a brand-new tenant, possible on a resend into an existing one), the grant still inserts the `active` row; the effective state stays `blocked` (D-489) and staff are exempt anyway.
3. **No new hook disjunct.** The creation hook keeps its single rule (an active access row); this plan makes the row exist before the send instead of teaching the hook about `tenant_invites` (plan 03, planning decision 2).
4. **Expand-only and no migration.** Nothing in this plan touches SQL.
</planning_decisions>
