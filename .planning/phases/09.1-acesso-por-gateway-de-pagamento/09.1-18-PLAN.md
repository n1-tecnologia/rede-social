<planning_decisions>
1. **The guard reads TOML lines, not a TOML tree.** Node is not on the deploy runners' PATH before `setup-cli`, and the structure it checks is flat (table headers and two keys), so awk and grep over exact header lines is enough and cannot be fooled by a comment (a line is a header only when it starts with `[` at column zero after optional spaces).
2. **The report calls the real function.** A re-implementation of the hook's predicate in the report would drift from the hook; calling `public.hook_custom_access_token_allowlist` per account answers the only question that matters, "would GoTrue refuse this person".
3. **The workflows get the guard, not a new job.** The guard is a bash step in the places where the damage would happen (before `config push`) and in the CI lint job where a PR would introduce it; no new job or runner.
4. **The test adapter is never listed in the hosted env.** The hosted `PAYMENTS_PROVIDERS` names only the real gateway; the signed-delivery proofs of plans 05, 07 and 19 use the local default, which lists every registered adapter.
5. **The runbook is in the deploy contract, not a new file.** `docs/DEPLOY.md` already carries one release section per phase (08.1 to 08.5 and the later ones) with the same subsections; this phase follows that shape.
</planning_decisions>
