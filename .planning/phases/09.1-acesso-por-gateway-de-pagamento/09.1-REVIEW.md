# Phase 09.1: Code Review Report

**Reviewed:** 2026-10-21
**Depth:** standard
**Files Reviewed:** 97
**Status:** issues_found

## Summary

Production, non-UI, non-test code of the payment-gateway access gate was reviewed: the unauthenticated
webhook route and its kernel services, secret custody, the Kiwify and fake adapters, the apply job and
order policy, the SQL gate functions and migrations, `requireAuth`, the admin API, the web server
boundary and the deploy/CI changes.

Tenant isolation holds up well. Every tenant-sensitive statement in the admin lane names `tenant_id`
itself, the apply job derives the tenant from the integration row (never the payload), the product
mapping lookup is tenant-pinned, the store definers re-check membership and product against the passed
tenant, the SECURITY DEFINER functions pin `search_path = ''` with the expected revokes, and
`access_grants`, `payment_integrations` and `payment_events` have RLS enabled with no policy and no
anon/authenticated privilege. The signature compare is constant-time with a length pre-check, the body
is bounded and read as bytes, and the open-redirect surface (`bootstrapRedirectPath`, the counters route)
only ever emits fixed internal paths. No secret is printed in the workflows.

What did not hold up: the replay defence of the webhook can be bypassed by re-serialising a captured
delivery (CR-01); the production-env guard fails open for an unset or mixed `PAYMENTS_PROVIDERS` (WR-01);
the "no PII in logs" requirement is broken by drizzle's error message format (WR-02); the "release
existing members" action creates inert rows for cancelled subscribers and reports them as released
(WR-03); and several operational dead ends (WR-04..WR-07).

## Critical Issues

### CR-01: Webhook replay protection is bypassable: dedupe key is over the raw bytes, authenticity is over the re-serialised JSON

**File:** `packages/core/server/payments/kiwify.ts:85-97,299-312`, `packages/core/server/payments/receive.ts:76-92`
**Issue:** `verify` accepts a delivery when the HMAC matches EITHER the raw bytes OR
`JSON.stringify(JSON.parse(raw))` (kiwify.ts:86-97). `receivePaymentWebhook` then builds the idempotency
key as `sha256(rawBody)` of the RECEIVED bytes (receive.ts:91) and `normalise` parses the same bytes.
These are two different equivalence classes. Scenario: the gateway signs compact JSON `B` (for most
JSON producers raw equals its own canonical form). An attacker holding one captured pair `(B, signature)`
(any party that can read a delivery together with its URL: gateway delivery logs, an intermediary, a log
export) sends `B'` = `B` with extra whitespace, a reordered escape (`A`), or a duplicated key. The
raw candidate fails, the `reserialised` candidate equals `B`, the HMAC matches, the request is accepted,
and `sha256(B') != sha256(B)` so `payment_events_dedupe_uq` does not fire. Every distinct whitespace
variant is a fresh event that is applied. `normalise` reads the same logical event, so a replayed
`subscription_late`/`subscription_canceled` cuts a member who has since renewed, and a replayed
`order_approved`/`subscription_renewed` re-opens a cancelled or charged-back recurring subscription
(recurring sales are "arrival order wins", policy.ts:21). The comment at kiwify.ts:23-24 ("accepting both
widens nothing") and the replay-memory claim in inbox.ts:15-18 are therefore wrong: accepting the
canonical form widens the set of byte strings that verify, while the replay memory keys on bytes.
**Fix:** Key the replay memory on the exact material that was verified. Make `verify` return the signed
bytes (or let the adapter expose them) and hash those:
```ts
// types.ts
verify(input): { variant: string; signed: Buffer };

// kiwify.ts verify(): return the candidate that matched
return { variant: matched.variant, signed: matched.bytes };

// receive.ts
const { variant, signed } = adapter.verify({ rawBody, signature, secret });
...
dedupeKey: createHash('sha256').update(signed).digest('hex'),
```
Because the canonical form collapses whitespace, escapes and duplicate keys, every variant of one
delivery then maps to one `dedupe_key`. Add a unit test: same delivery, two different whitespace
renderings, second one answers `enqueued: false`.

## Warnings

### WR-01: `assertProductionEnv` fails open: an unset or mixed `PAYMENTS_PROVIDERS` runs production on the public development key and accepts the `fake` gateway

**File:** `packages/core/server/env.ts:219-231`, `packages/core/server/payments/secret.ts:43-61`, `packages/core/server/payments/index.ts:25-31`
**Issue:** The key requirement is only asserted `if (e.PAYMENTS_PROVIDERS)` and only when the list does
NOT contain `fake` (env.ts:219-223). Two ways to boot production unsafely and silently: (1) the variable
is unset: `enabledProviders()` then returns every registered adapter including `fake`
(index.ts:26-27), `resolvePaymentsKey` falls back to the development key (secret.ts:57-58), and nothing
throws; (2) `PAYMENTS_PROVIDERS=kiwify,fake` passes the check without `PAYMENTS_SECRET_KEY`, so Kiwify
tokens are sealed with `sha256('rede-social-local-payments-secret-key')`, a constant that is in the
repository. Anyone with read access to the database (backup, replica, support export) can then decrypt
every tenant's webhook token and forge deliveries; and `fake` is a plain HMAC the tenant admin controls,
so an admin could mint "paid" events for any e-mail in their own tenant. The deploy files set
`PAYMENTS_PROVIDERS=kiwify` today, so this is a guard gap rather than a live hole, but the guard exists
precisely for the day someone edits that line.
**Fix:** In production, require the list and refuse `fake` outright:
```ts
const listed = (e.PAYMENTS_PROVIDERS ?? '').split(',').map((n) => n.trim()).filter(Boolean);
if (listed.length === 0) missing.push('PAYMENTS_PROVIDERS (name the real gateway adapters)');
if (listed.includes('fake')) missing.push('PAYMENTS_PROVIDERS must not list the test adapter');
if (!e.PAYMENTS_SECRET_KEY || Buffer.from(e.PAYMENTS_SECRET_KEY, 'base64').length !== 32) {
  missing.push('PAYMENTS_SECRET_KEY (32 bytes, base64)');
}
```
and make `resolvePaymentsKey` take the development-key branch only when an explicit non-production flag
says so, not whenever the list is unset.

### WR-02: Buyer e-mail and amounts reach the logs through drizzle's `DrizzleQueryError` message

**File:** `packages/core/server/payments/apply.ts:418-437` (lines 423 and 435); `apps/api/src/app.ts` `onError` (logs `{ err }`)
**Issue:** The file states that failure logs carry "ids and the error message only: never the e-mail, the
amount or any payload (T-09.1-36, PR-9)". With drizzle-orm 0.45.2 a failed statement is rethrown as
`DrizzleQueryError` whose `message` is `Failed query: <sql>\nparams: <all bound parameters>`
(`drizzle-orm/errors.js`, thrown from `pg-core/session.js` `queryWithCache` for every `tx.execute`).
The apply transaction binds the buyer's e-mail (`findLiveMember`, the `access_grants` insert), the
external ref and `amount_cents`. A deadlock, statement timeout, serialization failure or a CHECK
violation therefore writes the e-mail and the amount into `payments.apply.failed` and
`payments.apply.mark_failed_failed`. The same happens on the webhook request path: `recordPaymentEvent`
fails, the exception propagates to `app.onError`, which logs the whole error object (message and own
properties `query`/`params`). That is personal data in Cloud Logging, against PR-9.
**Fix:** Log a sanitised cause, never the wrapper message:
```ts
const safeError = (e: unknown) => {
  const cause = e instanceof Error && 'cause' in e ? (e.cause as { code?: string; message?: string }) : undefined;
  return { code: cause?.code ?? null, name: e instanceof Error ? e.name : 'unknown' };
};
log.error({ event: 'payments.apply.failed', eventId, tenantId: seen.tenantId, ...safeError(error) }, '...');
```
and give the payments routes (or `app.onError`) the same treatment: strip `query`/`params` from
`DrizzleQueryError` before logging. Add a test that forces a failure with an e-mail parameter and asserts
the e-mail is absent from the captured log line.

### WR-03: "Release existing members" counts and writes inert rows for cancelled subscribers

**File:** `packages/core/server/payments/gate.ts:51-59,108-117`; `packages/core/server/payments/access.ts:231-245`; precedence in `supabase/migrations/20261020225255_access_gate_functions.sql:77-83`
**Issue:** `releasable` selects members whose `app.access_effective` is `none` OR `inactive`, and
`setGate({ releaseExisting: true })` inserts a manual `active` row for each. But `access_effective`
ranks a gateway `inactive` row ABOVE a manual `active` one (migration lines 79-81, assumption A-P9), so
for every member in the `inactive` group the new manual row changes nothing: they stay `cut`. The
preview says "the members a release would admit", the result toast reports `released = N` as if they
were admitted, and N rows of dead data are written (they only start to matter if the gateway row is ever
removed, which no code path does). The same applies to the single-address `releaseEmail`: it answers
200 with an item still in `subscription_pending`. An admin who ticks "release current members" while
turning the gate on believes lapsed subscribers were let in; they are cut on their next request.
**Fix:** Decide the rule once. Either exclude `inactive` from `releasable` (`in ('none')`), which matches
the actual behaviour and keeps lapsed subscribers cut, or, if lapsed subscribers should be releasable,
flip the precedence in `app.access_effective` (move the manual `active` branch above gateway `inactive`)
and cover it with a pgTAP case. Either way make the preview count and the inserted-rows count agree with
the number of members whose state actually changes to `active`.

### WR-04: No minimum strength on the webhook token while the webhook handle is publicly derivable and unthrottled

**File:** `packages/contracts/src/payments.ts:183-187`; `packages/core/server/payments/ids.ts:25-34`; `apps/api/src/routes/webhooks/payments.ts:17-20`
**Issue:** The only authentication of the route is the HMAC under the tenant's token, and the token
schema is `trim().min(1)`. The integration id is `uuid5(namespace, tenantId:provider)` and the tenant id
is returned to every member in the bootstrap, so anyone who is a member of (or merely knows the id of) a
tenant can compute its webhook URL. There is no rate limit (A-P20 is accepted, but its mitigation list
assumes the signature is hard to guess). A tenant that saves a short or human-chosen token (`1234`,
`senha`) can be brute-forced online: each guess is one request, and a hit yields the ability to POST
`order_approved` for any e-mail, i.e. free paid access in that community, plus cuts for arbitrary
members. The 404-vs-403 difference also tells the attacker which tenants have a connected integration.
**Fix:** Enforce a floor in `tokenField` (for example `.min(16)`, or the length the gateway actually
issues; reject all-digit and single-character-class values), and add a cheap per-integration failure
throttle (an in-memory counter or a `payment_integrations.failed_attempts` window) that answers 429/403
without opening the secret after N bad signatures per minute. Consider returning the same 404 for
"unknown" and "bad signature" to remove the existence oracle.

### WR-05: Paying customers can fall into permanent dead ends: `unknown_product` and `failed` events are never replayed and are partly invisible

**File:** `packages/core/server/payments/inbox.ts:74-93`; `packages/core/server/payments/apply.ts:378-381`; `packages/core/server/payments/events.ts:44,95-107`; `packages/modules/payments/server/routes.ts` (no reprocess route)
**Issue:** `unknown_product` is a FINAL state. If the admin fixes or registers the gateway product id after
the first purchase (a typo in the id, a product created later), the buyer's event stays
`unknown_product` forever: a gateway resend carries identical bytes, `recordPaymentEvent` finds the row,
sees a state other than `received`/`failed` and enqueues nothing (inbox.ts:83-85); and there is no
reprocess route (only `POST /events/{id}/grant`, which handles `no_membership` of store products). For
the access gate this is the worst case: a customer paid, is cut, and the only remedy is a manual
release. Separately, a persistently failing apply leaves the row `failed`, and `listEvents` lists only
the four settled states (events.ts:44), so the admin sees nothing; the only signal is a log line.
**Fix:** (a) When an access product or store mapping is created or its `externalProductId` changes
(`createAccessProduct`, `updateAccessProduct`, `putStoreMapping`), re-enqueue this tenant's
`unknown_product` events for that provider and product id, tenant-pinned, in the same transaction.
(b) Add an admin "reprocess" for `unknown_product` rows, or a periodic sweep that re-enqueues `failed`
and long-`received` events. (c) Surface a count of `failed`/stuck events on the overview.

### WR-06: Secret key rotation is documented but not implemented; a rotation or a mismatched key silently disables every webhook

**File:** `packages/core/server/payments/secret.ts:98-101`; `packages/core/server/payments/setup.ts:210-219`; `.github/workflows/deploy-hml.yml` (comment on the shared-database key)
**Issue:** The sealed format carries a key id "so a rotation can recognise what an old key sealed", but
`openSecretWith` accepts only the process's single current id (`keyId !== String(material.keyId)` throws).
Bumping `PAYMENTS_SECRET_KEY_ID` (or changing the key) makes every stored token unreadable: every
delivery of every tenant is answered 403 (`secret_unreadable` is logged, but nothing alerts), no events
are recorded, and a retrying gateway eventually gives up, so members stay cut or uncut wrongly until each
tenant admin re-enters a token. The homologation workflow depends on prod and hml holding the same key
value "by convention" while both write `secret_key_id = 1`, so a wrong hml secret is indistinguishable
from a right one until a webhook fails to open.
**Fix:** Accept a key ring (`PAYMENTS_SECRET_KEYS` as `{ "1": "<b64>", "2": "<b64>" }`), open with the key
named by the stored id, seal with the current one, and ship a one-off "reseal all" script. Add a boot
self-test (seal then open a probe value) that fails the deploy when the mounted key cannot round-trip.

### WR-07: Global unique index on `(provider, external_product_id)` is a cross-tenant existence oracle and a registration-squatting vector

**File:** `supabase/migrations/20261020234833_payments_tables.sql:81`; `packages/core/db/schema/payment-products.ts` (`payment_products_provider_ext_uq`); `packages/core/server/payments/setup.ts:78-96`
**Issue:** A tenant admin who registers gateway product id `X` receives `409 gateway_product_taken`
exactly when ANY other tenant holds `X`. That is a one-bit cross-tenant leak (the project's core value is
zero leakage), and it lets one tenant pre-register another tenant's product id (ids that appear in
public checkout/embedded payloads) and block them from mapping it. The index is not needed for isolation:
`applyInTx` already resolves the mapping with `tenant_id = <integration tenant> and provider and
external_product_id` (apply.ts:363-372), and the webhook is authenticated per tenant.
**Fix:** Make the unique index per tenant, `(tenant_id, provider, external_product_id)`, in a new
expand-then-contract migration, and drop the 409 `gateway_product_taken` wording for the cross-tenant
case. If a global rule is a hard product requirement (D-488), at least return the same generic 409 for
"already yours" and "held elsewhere" and document the accepted leak in the threat model.

## Info

### IN-01: Replay memory and the one-off terminal rule both depend on the 180-day event retention

**File:** `supabase/migrations/20261020234844_payments_functions.sql:81-98`; `packages/core/server/payments/apply.ts:283-295`
**Issue:** `payment_events_prune` deletes events older than 180 days. That deletes the dedupe key (a
replay after day 180 is a brand-new event) and, for store sales, the only record of an applied refund
that `applyStore` uses as the "terminal" fact (`prior` query). A late or replayed approval after
pruning re-grants a refunded product. The comment calls retention "the replay memory (T-09.1-19)".
**Fix:** Keep a small permanent table of `(integration_id, dedupe_key)` and of terminal sale refs, or
record the terminal fact on the store order/entitlement history, and prune only the bulky columns.

### IN-02: Stale documentation after the allowlist retirement

**File:** `packages/contracts/src/errors.ts:14`
**Issue:** The `EMAIL_NOT_ALLOWED` comment still says "an e-mail that is not on the global allowlist", but
the code now means "no usable access in this community" (join.ts, signup.ts, `api-error.ts` message).
**Fix:** Update the comment; same for any remaining references to `public.email_allowlist` readers.

### IN-03: Unthrottled warning log per rejected signature

**File:** `apps/api/src/routes/webhooks/payments.ts:62-67`
**Issue:** Every bad signature on a known integration emits a `warn` line. With no rate limit anyone who
knows a handle can flood Cloud Logging at will. Cloud Run's own request log also records the full URL,
so `?signature=` lands in the platform request logs (harmless without the body, but worth knowing).
**Fix:** Sample or aggregate the rejection log per integration per minute; keep the signature out of the
URL if the gateway allows a header.

### IN-04: Lenient base64 decoding of `PAYMENTS_SECRET_KEY`

**File:** `packages/core/server/payments/secret.ts:49`; `packages/core/server/env.ts:226-229`
**Issue:** `Buffer.from(x, 'base64')` silently ignores invalid characters and accepts the url-safe
alphabet, so a mistyped or truncated secret that still decodes to 32 bytes passes the length check and
boots with a key nobody intended (and differs between environments that must match).
**Fix:** Validate with `/^[A-Za-z0-9+/]{43}=$/` (or `z.base64()`) before decoding, and compare a key
fingerprint (first bytes of `sha256(key)`) stored beside the sealed value.

### IN-05: A NUL in a gateway product id or other free text becomes a 500

**File:** `packages/contracts/src/payments.ts:203-207,243-251`; `packages/core/server/payments/setup.ts:249-251`
**Issue:** `externalProductId` (and the access product `name`) accept U+0000 after trimming; Postgres
`text` refuses it (SQLSTATE 22021), the insert fails inside `withTenantTx` and the admin sees a generic
error/500. The Kiwify and fake adapters already strip NUL; the admin contracts do not.
**Fix:** Add `.refine((v) => !v.includes('\u0000'), 'product_id_required')` (and for `name`) to the Zod
fields.

### IN-06: `payment_events.tenant_id` is not tied to its integration's tenant by the database

**File:** `supabase/migrations/20261020234833_payments_tables.sql:72-73`
**Issue:** `payment_events` has separate FKs to `tenants` and to `payment_integrations`, so nothing in the
schema forbids a row whose `tenant_id` differs from its integration's tenant. The application is
correct today (inbox uses the integration's tenant, apply joins on both), but the invariant is enforced
only by code.
**Fix:** Add `unique (id, tenant_id)` on `payment_integrations` and a composite FK
`(integration_id, tenant_id) references payment_integrations (id, tenant_id)` on `payment_events`.

The preview and the write cannot disagree on who is in the set.
- **Tenant scoping.** Every query binds `m.tenant_id = ${tenantId}`, and `app.access_effective` receives `m.tenant_id`. The tenant comes only from `ctx.tenantId`. The new isolation test (T-09.1-101) plants a foreign tenant's `inactive` row for a lab member's e-mail and shows neither figure moves.

## Warnings

### WR-08: "Stays cut" toast claims the person has no access even when the gate is off

**File:** `apps/web/app/(app)/configuracoes/pagamentos/AccessList.tsx:300-306` (copy in `apps/web/messages/pt-BR/payments.json:241`, route doc in `packages/modules/payments/server/routes.ts:347`)
**Issue:** When the server answers `access.state === 'subscription_pending'`, the toast says "...mas a assinatura está pendente: a pessoa continua sem acesso até o pagamento ser confirmado." That is only true while the access gate is ON. With the gate OFF, `app.access_state` returns `open` for everyone, so a gateway-cut address is not locked out and the toast tells the admin something false. The component already receives `gateRequired` (it feeds the sheet's `blockOffNote` for the same reason), and the sibling block flow has a gate-off note, so the release path is the odd one out. D-489 only makes a gateway cut outrank a release for the purpose of the gate. A toast that says "no access" under a gate that is off also reads as a bug report from the admin ("I released him and the gate is off, why does it say he has no access?").
**Fix:** Branch the message on `gateRequired`. Keep `releasedStaysCut` when the gate is ON. When it is OFF, use a line that does not claim a lockout, for example a new key `releasedGateOff`: "Liberação registrada para {email}. A assinatura está pendente e a liberação passa a valer quando 'Exigir assinatura para entrar' estiver ligado." Add the corresponding case to `AccessList.test.tsx` (gate off, state `subscription_pending`) and to the catalog key test in `payments-messages.test.ts`.
```tsx
if (state === 'subscription_pending') {
  toast.show({
    tone: 'info',
    message: t(
      gateRequired ? 'payments.toasts.releasedStaysCut' : 'payments.toasts.releasedGateOff',
      { email: outcome.email },
    ),
    durationMs: NOTICE_TOAST_MS,
  });
}
```
Add `gateRequired` to the `useCallback` dependency list.

### WR-09: Bulk release leaves out members whose membership is currently blocked, so they are cut with no release when they come back

**File:** `packages/core/server/payments/gate.ts:55-65` (and the preview copy in `apps/web/messages/pt-BR/payments.json:73-74`)
**Issue:** `liveMembers` keeps only `m.status = 'active' and m.blocked_at is null`. A member whose membership is blocked (moderation block, `blocked_at` set) at the moment the gate is turned on gets no manual release. When an admin later unblocks that membership, the member's first request returns `SUBSCRIPTION_PENDING`, although they were a member before the gate and the admin chose "Liberar o acesso dos membros atuais". The dialog counts and names only "membros ... sem acesso registrado" and never mentions blocked members, so the admin has no way to know. It also diverges from the dashboard population: `app.access_cut_user_ids` (migration `20261020225255_access_gate_functions.sql:120-137`) counts every non-deleted `member` membership regardless of `status` and `blocked_at`, so the "cut" counter and the release set describe different people. The first-party rule "staff never need a release" is explained in the comments, but there is no comment explaining why blocked memberships are excluded, so it reads as an unexamined filter.
**Fix:** Decide the product rule explicitly and write it in the `liveMembers` comment. If a currently blocked member should come back with access, drop `m.blocked_at is null` and `m.status = 'active'` from the release fragment and filter only `m.deleted_at is null` and `m.role = 'member'` (a blocked membership is already refused by `requireAuth` before the gate matters, and the manual `blocked` e-mail row still wins in `app.access_effective`). If excluding them is intended, add one line to the dialog or the DEPLOY runbook saying blocked members are not released, and align `access_cut_user_ids` so the dashboard counter does not count them as cut.

### WR-10: The deploy adds two required secrets with no preflight, and a missing one fails after the migrations are applied

**File:** `.github/workflows/deploy-api.yml:168-179, 215-216, 262-263`
**Issue:** The workflow now mounts `vercel-token-prod` and `supabase-pat-prod` on both services and turns on `DOMAIN_PROVIDER=vercel` and `AUTH_ALLOW_LIST=supabase`. `assertProductionEnv` refuses to boot without the secrets and Cloud Run fails a revision whose secret is missing. The file's own comment and `docs/DEPLOY.md` state that this failure "lands after the migrations and the auth configuration are applied", so the first push after this change can leave production with new migrations applied, the old API revision serving, and the worker not deployed. `deploy-hml.yml` has a preflight for its variables; this workflow has none, and the only guard is a sentence of prose and a reviewer approval that the reviewer has to remember. A push that only touches the workflow triggers the deploy.
**Fix:** Add a step before the migration step that fails fast with a readable message when either secret cannot be read, for example:
```yaml
- name: Preflight secrets
  run: |
    for s in vercel-token-prod supabase-pat-prod payments-secret-key-prod; do
      gcloud secrets describe "$s" --project=api-dere-social >/dev/null \
        || { echo "::error::missing secret $s"; exit 1; }
    done
```
Optionally also check `gcloud secrets get-iam-policy` for the runtime service account.

### IN-07: A `null` access in the single-release answer reads as a success toast

**File:** `apps/web/app/(app)/configuracoes/pagamentos/AccessList.tsx:300-314`
**Issue:** The branch is `subscription_pending`, then `blocked`, else success. `outcome.access?.state` is `undefined` when `access` is `null` (the sheet type allows it as "not expected"), and that falls into the success branch, so the admin reads "Acesso liberado para X" for an answer that carried no state at all. An unknown state cannot reach here today because `accessResultSchema` closes the enum and a parse failure becomes the generic error, so the risk is only the `null` case. Fail-open on the one message that tells an admin a person was admitted is the wrong default.
**Fix:** Match the success state positively and treat anything else neutrally:
```tsx
if (state === 'active') success; else if (state === 'subscription_pending') ...; else if (state === 'blocked') ...; else { toast info 'released' generic line + router.refresh() }
```
At minimum, call `router.refresh()` and skip the success tone when `state` is `undefined`.

### IN-08: Deploy skew: a new web against the old API cannot preview the gate

**File:** `apps/web/lib/payments.ts:139-150`, `packages/contracts/src/payments.ts:333-363`
**Issue:** `gatePreviewSchema` and `gateResultSchema` now require `gatewayCut`. The web (Vercel) can ship before the API (Cloud Run, which waits on the production approval). In that window the old API answers `{ count }` and the web's `parse` throws, so the admin sees "Não foi possível verificar os membros atuais. Nada foi alterado." Nothing is written (the preview fails before the write), so this is a transient loss of the feature, not data loss. The reverse order is safe because Zod strips the unknown key.
**Fix:** Either note in DEPLOY.md that the API must deploy first for this change, or give the two response fields `.default(0)` on the web-side parse. The first is cheaper.

### IN-09: `redactDbError` inspects only the top-level error

**File:** `packages/core/server/logging.ts:58-85`
**Issue:** `isStatementFailure` checks the error it is given; the cause chain is walked only after that top-level check passes. If a caller wraps a `DrizzleQueryError` as `new Error('...', { cause })`, the wrapper is not a statement failure, `redactDbError` returns it untouched, and pino's error serialiser prints the cause chain including the `Failed query: ... params: ...` message with the buyer e-mail. No current wrapper was found in the reviewed files (the apply job and `app.onError` receive the raw drizzle error), so this is a hardening note.
**Fix:** Walk the `cause` chain up front (a few levels) and redact when any link is a statement failure, not only the head of the chain.
