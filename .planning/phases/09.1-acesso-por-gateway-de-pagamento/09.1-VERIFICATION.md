# Phase 09.1: Acesso por gateway de pagamento Verification Report

**Phase goal:** Each tenant's payment gateway (Kiwify first, behind a provider-neutral seam) drives access: a signed webhook grants or cuts platform access per tenant and e-mail, replacing the hand-filled global `email_allowlist`, and unlocks store products for members who buy them through the tenant's checkout link.
**Verified:** 2026-10-21
**Status:** human_needed
**Re-verification:** No, initial verification

## Verdict in one paragraph

The code delivers the three claims of the goal. I traced the whole path in the code (not the SUMMARYs) and ran the relevant suites myself: the signed webhook route verifies the gateway signature over the received bytes against a per-tenant sealed token, records the event once and enqueues one job; the apply job turns it into a tenant-pinned `access_grants` row or a store order and entitlement through `service_role`-only definers; `requireAuth` reads the cut decision from the same SQL statement as the membership on every request; sign-up, join and the invite and first-admin paths are gated per tenant; and the global allowlist has no remaining reader or writer in source, helpers or seed. I found no stub, no unreferenced debt marker and no tenant-isolation hole. Nothing that the phase promised is missing or broken, so the status is not `gaps_found`. It is `human_needed` because the Kiwify adapter has never seen a signed real delivery, the design review behind UI-04 is provisional, one product rule (A-P9, WR-03) is unconfirmed and produces a misleading admin result for lapsed subscribers, and real-device, other-project and clean-reset runs were never done.

## Goal claims, traced

### (a) Per-tenant, per-e-mail access driven by a signed webhook: VERIFIED

1. `apps/api/src/routes/webhooks/payments.ts`: `POST /v1/webhooks/:provider/:integrationId`, 256 KiB cap, body read as bytes, no auth other than the signature, `Cache-Control: no-store`, GET answers 200.
2. `packages/core/server/payments/receive.ts`: uuid shape, one primary-key read of `payment_integrations`, provider equality, adapter lookup, only then `openSecret` (AES-256-GCM, integration id as AAD) and `adapter.verify`. Unknown or disabled is 404, bad signature 403 with nothing stored, an unreadable sealed token fails closed as 403. The tenant of the recorded event is the integration row's, never the payload's.
3. `kiwify.ts#verify`: HMAC-SHA1 over the raw bytes or the re-serialised JSON, length check then `timingSafeEqual`, and it now returns the matched bytes. `receive.ts` hashes those `signed` bytes for `dedupe_key` and normalises them (CR-01 fix, commit eadd99ae; I read it and the whitespace-variant test passes).
4. `inbox.ts`: `insert ... on conflict (integration_id, dedupe_key) do nothing returning id`, the integration's `last_event_at` and `enqueueInTx(kernel.payment-event)` in the same admin transaction.
5. `apps/api/src/worker.ts` registers `paymentEventJob`; `apply.ts` locks the event row `for update`, takes an advisory lock per tenant, provider and external reference, resolves the mapping with `tenant_id` pinned (a product mapped by another tenant is `unknown_product` and writes nothing: tests at payments-apply lines 316 and 894), and upserts the gateway `access_grants` row keyed `(tenant, provider, external_ref)` with the e-mail as data (an account is not required, D-490). Order of events lives in `policy.ts` (one-off refund is terminal, recurring is arrival-order).
6. `access_state`/`access_effective` in `20261020225255_access_gate_functions.sql` compute the decision in one place; the `_gated` membership twins return it in the same statement as the membership; `require-auth.ts` answers `SUBSCRIPTION_PENDING` (or `MEMBERSHIP_BLOCKED` for a manual block) on every path except `/v1/me/subscription`, per request, uncached, writing nothing to `memberships`. `payments-apply.test.ts` drives `applyPaymentEvent` and asserts the real bootstrap answers OK, then SUBSCRIPTION_PENDING, then OK (lines 188 to 362).
7. After commit only, `membership.access_cut` is emitted when a live member moved `granted` to `cut` in this apply; the notifications handler deletes the member's push devices and sends the Realtime nudge; the session is not revoked.

Tenant isolation: every admin-lane statement I read names `tenant_id` itself; the definers pin `search_path = ''`; `access_grants`, `payment_integrations` and `payment_events` have RLS on with zero policies and no anon/authenticated privilege (pgTAP 205 and 010 pass); `payment_products` has `admin_tenant`-only policies and `truncate` revoked; the Acessos and Eventos services all carry `tenant_id = ctx.tenantId`; a webhook for tenant A that names tenant B's product writes nothing in B.

Caveat (kept as a human item): the apply job is tested by driving `applyPaymentEvent` on recorded rows, and the route is tested up to the enqueue; the one test that joins them (signed delivery to API to worker to database to UI) is the Playwright store walk on mobile-chromium, which I did not rerun.
