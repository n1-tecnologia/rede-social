## The gap closure, judged against what plans 21 and 22 actually ship

**Rule kept.** `app.access_effective` still ranks a manual block, then any active gateway row, then an all-inactive gateway, then a manual release, else none (lines 68 to 84 of `20261020225255_access_gate_functions.sql`). A gateway `inactive` therefore outranks a manual release, as D-489 and the owner's decision of 2026-10-21 require.

**Bulk release (PAY-31).** In `packages/core/server/payments/gate.ts`:

- `liveMembers(tenantId)` is the single SQL fragment: live `member`-role memberships (`status = 'active'`, `blocked_at is null`, `deleted_at is null`), tenant bound from the argument, each with `app.access_effective(m.tenant_id, u.email) as eff`.
- `tallyMembers` runs one statement, `count(*) filter (where l.eff = 'none')` as `releasable` and `count(*) filter (where l.eff = 'inactive')` as `gateway_cut`, over that fragment. Both are database integers, never a JavaScript sum.
- `previewGate` answers `{ count, gatewayCut }`.
- `setGate` inserts a manual `active` row `from (liveMembers) l where l.eff = 'none'` only, `on conflict ... do nothing returning id`, in one set-based statement inside the existing setup lock and `for update` row lock. `released` is `created.length`. When turning on it then reads `gatewayCut` by the same tally in the same transaction and returns `{ required, released, gatewayCut }` (0 when turning off). The log line carries counts only.
- Contract: `gatePreviewSchema` and `gateResultSchema` both carry `gatewayCut` (non-negative integer).

**Notice (web).** `GateSwitchRow.tsx` shows one `cutNote` paragraph whenever `cut > 0` (alone when nobody can be released, with no checkbox), keeps the tone following the release box only, and chooses the toast from the server's `released` and `gatewayCut` among four catalog lines, the two that name a cut lasting six seconds. `AccessList.tsx#onReleaseSettled` reads `outcome.access?.state`: `subscription_pending` shows the info toast `releasedStaysCut` for six seconds, `blocked` shows the existing error line, anything else keeps the identical success toast. The server's answer and write for the single address are unchanged (A-G1); `releaseEmail` still answers 200 and still writes the idempotent manual row, so releasing before the account exists (PAY-22, D-490) is untouched.

**Tests are real, not tautological.** The G-09.1-1 tracer in `payments-admin.test.ts` builds a member with no row (A), a gateway-cut member (B), a manually blocked member who is also gateway-cut (C), a `support_tenant` with a gateway `inactive` row (S) and a gateway-active member (D); it asserts the preview moves by exactly +1 on `count` and +1 on `gatewayCut` against an independent SQL oracle (`membersCutByGateway`, which does not call `access_effective`), that `released` equals the preview's `count` and the rows created by the admin, that no manual `active` row exists for B, C, S or D, that A passes, B is `403 SUBSCRIPTION_PENDING` and C is `MEMBERSHIP_BLOCKED` on the next request, and that the body contains no `@`. Against the old two-state predicate B would have received a row and the `manualActiveRows(B) === 0` assertion would fail. The cross-tenant negative for the count sits in the isolation case. The single-address case pins the unchanged 200, the `subscription_pending` state, one gateway row plus one manual row, idempotence, the ghost (no account) address whose sign-up is still refused, and the clean address released to `active` whose sign-up succeeds.

**Does the shipped behaviour satisfy the INTENT of PAY-31 and PAY-22? Yes.**

- PAY-31's intent is that turning the gate on does not silently lock out the people who are members today, with the number shown beforehand and reported by the server afterwards, and a cleared box releasing nobody. That holds for every member with no access record. The only members the release does not admit are those the gateway has cut, which the owner decided stay cut (D-489, A-P9 confirmed); they are now counted separately, named in the dialog, never written a dead row, and never reported as released. The old wording "have no usable access" literally includes them, which is why it is stale.
- PAY-22's intent is that an admin can release an address before it has an account, block, unblock, remove a manual release and never remove a gateway row by hand. All of that is unchanged; the only addition is an honest notice when the address is gateway-cut.
