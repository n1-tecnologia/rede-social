<objective>
The Pagamentos screen's frame and its Configuração tab: the admin's whole setup in one place: connect the gateway, register what grants access, and decide whether entering requires a subscription. After this plan an admin can do on a phone everything plan 09 made possible over HTTP, with the gate's confirmation dialog telling them exactly who it will affect and offering to release them.

<planning_decisions>
1. **One catalog file for the whole phase's admin and member copy of Pagamentos.** `payments.json` is written complete here (the UI-SPEC Copywriting Contract is closed and approved), so plans 14-15 only consume keys and the catalog test is one file; the keys for surfaces built later are not "unused" because each later plan's tests reference them.
2. **`PaymentsTabs` is re-declared, not shared.** The Cursos wrapper stays where it is; Pagamentos has its own three-line client wrapper (the UI-SPEC's second option), so no route imports another route's component.
3. **Server actions are thin.** Zod before the request, one `lib/payments.ts` call, a refusal mapped to a catalog code, a navigation only for the bootstrap-known 401/403 codes; views get finished strings from `lib/payments-view.ts` and the server's `serverNow`.
4. **The dialog owns the checkbox state; the row owns the tone.** `GateSwitchRow` passes the checkbox as `children`, reads its checked state through a controlled prop pair, and recomputes `tone` from it, exactly as the UI-SPEC says.
5. **No optimistic switch.** The switch changes only from the server's answer (the Membros rule); a pending write shows `busy`.
</planning_decisions>
