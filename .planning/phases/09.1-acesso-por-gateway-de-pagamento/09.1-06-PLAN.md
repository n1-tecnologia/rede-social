<objective>
The store half of the gateway: orders and entitlements that a signed webhook can create and take away, with the amount the gateway reports, and a simulated purchase that can no longer be reached by a tenant that has a gateway. After this plan the database can (a) record "this member paid this much for this product through this gateway reference" and unlock it, (b) take it away on a refund, and (c) refuse the free simulated unlock for a gateway tenant; the product reads tell the web which mode a tenant is in. Nothing in this plan receives a webhook; plan 07's apply job calls the definers.

Task 1 is the tracer: ONE gateway tenant through the guard, the product read, the two admin-lane definers and the unlock and lock of a community. Task 2 closes the read side (the buyable rule and the dashboard revenue) and the contract. Task 3 proves the definers and the guard in Postgres (pgTAP 206).

Purpose: the simulated purchase unlocks for free by design (it exists for tenants with no payment step), so the day a tenant connects a gateway the free path must close in the database, and the webhook must be able to write the ledgers without ever opening a tenant-lane write policy.

<planning_decisions>
1. **The guard goes after "already held".** A member who already owns the product and replays still gets `owned`; only a NEW purchase under a gateway is refused, with the existing `unavailable` outcome (409 `{ store: 'unavailable' }`), so no new contract word is needed.
2. **A paid order for an archived product is granted.** The simulated path refuses an archived product because nobody should buy it; a gateway sale already happened and the money was taken, so the definer grants it (RESEARCH Data Model).
3. **`already_active` writes nothing** (assumption A-P27): a member who already holds the product through an admin grant and then pays has no second entitlement to create; the event records the outcome `no_effect` and the admin sees it in "Eventos recentes". The cost (an order for revenue that is not linked) is rare and recoverable by hand.
4. **`provider_ref` is the sale's stable key.** For a recurring sale it is the subscription id, so a cancellation finds the live order even though every renewal carries a new charge id (RESEARCH Pitfall 4); for a one-off sale it is the order id.
5. **The unique key covers live orders only.** After a revoke the same reference may create a new live order (a renewal after a late payment), and the revoked row stays as history.
6. **Store knows the payments seam only by SQL name.** `app.payments_gateway_mode()` and `app.payments_checkout_url()` are called from SQL strings in the service; the store package imports nothing from payments and the payments package nothing from the store (MOD-02); the foreign key from the mapping to the product is created in THIS plan's store migration.
7. **Amount bounds are the store's own.** 0 to `STORE_MAX_PRICE_CENTS` (10 000 000); an amount outside is refused by the definer so a corrupt gateway figure never becomes revenue.
</planning_decisions>
