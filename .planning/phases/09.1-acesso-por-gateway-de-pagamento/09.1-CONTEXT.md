# Phase 09.1: Acesso por gateway de pagamento - Context

**Gathered:** 2026-10-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Each tenant's payment gateway (Kiwify first, behind a provider-neutral seam) drives access through a signed webhook:

1. **Platform access.** A subscription product that lets an e-mail create an account and log in, per tenant. It replaces the hand-filled global `email_allowlist` with per-tenant, per-e-mail access records fed by the webhook and by manual admin actions.
2. **Store product access.** A product bought inside the platform through the tenant's checkout link becomes a store order and a `store_entitlement`, and a late, canceled, refunded or charged-back purchase takes it away.

Intended member flow: buy the access product, create the account with the SAME e-mail as the checkout, then optionally buy store products inside the app.

In scope: the gateway seam and the Kiwify adapter, the signed webhook endpoint and its idempotent event inbox, the per-tenant access records and the mapping from gateway products to tenant and target, the access gate at sign-up, join and every authenticated request, the cut and return of access, the admin screens (gateway setup, access products, recent events, manual access), the gateway-driven store purchase and revocation, and the kernel changes to the Auth hooks and API pre-checks.

Out of scope (see Deferred): a second gateway, revenue of access subscriptions in the Financeiro dashboard, access tiers, auto-claim of pending store purchases, billing between the platform and tenants (still Out of Scope in PROJECT.md).

</domain>

<decisions>
## Implementation Decisions

### Access model and gateway seam
- **D-485: Two access levels.** PLATFORM access lets an e-mail create an account and log in to one tenant. STORE PRODUCT access is a `store_entitlement` for a product bought inside the platform. They are different records with different keys (e-mail and tenant, versus membership and product) and one gateway product maps to exactly one of the two.
- **D-486: Each tenant has its own gateway account behind a provider-neutral seam.** One adapter per gateway (verify the signature over the RAW body, normalise the payload into a gateway-neutral event), in the `VideoProvider` shape. Kiwify is the first adapter; others are added in code as they appear. The neutral layer (tables, columns, job names, contracts) carries no `kiwify_*` names; only the adapter and its route segment do. — **Reversibility:** costly — every table, job and route name outside the adapter is published in migrations and OpenAPI.
- **D-487: Access is per tenant and e-mail, and `access_grants` replaces `email_allowlist`.** Columns at least: `tenant_id`, normalised e-mail, `source` (`manual` or the gateway), status, validity, the gateway's order or subscription reference. Rows of the old table migrate as `manual` (the production list is empty today; the local seed lists its identities). — **Reversibility:** costly — a table replacement with hooks, API pre-checks, seeds and e2e helpers all reading it.
- **D-488: One mapping table from the gateway's product id to tenant, kind and target.** Kinds are `access` and `store_product` (target = the store product). The gateway plus external product id is globally unique, so a Kiwify product can never mean two things, and the webhook resolves tenant and kind with one lookup. It is NOT a column on `store_products`: access products have no store row, and the store stays free of gateway knowledge. — **Reversibility:** costly — the webhook route, admin forms and RLS are all built on this lookup.
- **D-489: A manual block always wins over the gateway.** The effective state of an e-mail in a tenant is: a manual block if one exists, otherwise the gateway's latest state, otherwise a manual release. `source` is what makes that rule computable.
- **D-490: The checkout e-mail must equal the account e-mail.** A webhook whose e-mail matches no membership is kept as an event in state `sem membership`, never dropped and never guessed at; the admin can grant by hand (D-503). Access records are keyed by e-mail, so a paid access product works before the account exists, which is exactly the intended flow.

### The gate: who passes
- **D-491: The gate is an explicit per-tenant switch.** `admin_tenant` turns on "Exigir assinatura para entrar" after mapping at least one access product. With the switch off (or the `payments` module off) sign-up and join stay open as today.
- **D-492: An admin invite is a manual access, and staff are exempt.** Accepting an invite writes an access with `source = manual` (listed, revocable). `admin_tenant` and `support_tenant` never depend on a subscription, so the first admin of a new tenant is never locked out. `super_admin` stays exempt (D-316 keeps it out of memberships anyway).
- **D-493: Someone without access sees a message and, if possible, an Assinar button.** Copy: "Seu acesso ainda não foi liberado. Use o mesmo e-mail da compra." plus an "Assinar" button when the tenant registered the checkout link of an access product. It appears on sign-up, login and the "Participar" join screen, and never names another community (D-302).
- **D-494: A tenant may map several access products and any active access opens the door.** No difference in level between plans in this phase.
- **D-495: The Auth hooks stay coarse and the tenant check lives in the API.** The token hook and the `before_user_created` hook answer "does this e-mail have any usable access" (an active or manual access in any tenant, a staff membership, or a platform admin) in cheap indexed lookups with 4xx errors only. The per-tenant decision is made by `signupMember`, `joinTenant` (which today does NOT consult the allowlist, because the token hook stood in for it), the first-admin paths in `createTenant` and invites, and `requireAuth`.

### Access lifecycle
- **D-496: A late, canceled, refunded or charged-back subscription cuts access immediately, with no grace.** A later approved or renewed event returns it automatically, with no admin action. Membership, profile and content are untouched throughout.
- **D-497: The cut member sees a dedicated "Assinatura pendente" screen.** `requireAuth` answers with its own error code, a sibling of `MEMBERSHIP_BLOCKED`, NOT `memberships.status = 'blocked'`, so an admin block and a payment cut stay distinct. The screen is full-screen with the tenant's brand, the text "Sua assinatura não está ativa", a "Regularizar" button (the access product's checkout link, when registered) and "Sair". The platform sends no e-mail of its own; the gateway already notifies the buyer. — **Reversibility:** one-way — the error code joins the published `ERROR_CODES` contract and the web app branches on it.
- **D-498: While cut, content stays and the member shows as inactive.** Posts, comments and course progress remain (as in D-330). In the admin members list the member carries an "Assinatura pendente" badge with a filter, drops out of the dashboard's active-member count, and receives no push.
- **D-499: Accept a Realtime and push tail of up to one hour.** Data always comes through the API, which is already cut; Realtime only signals a reload. The cut removes the push subscriptions of that membership. The session is NOT revoked, because the Supabase identity is shared across tenants (08.1) and a sign-out would also drop the person from other communities.
- **D-500: The admin learns of cuts and returns only through the members list.** The badge and filter of D-498; no new notification type.

### Admin configuration
- **D-501: A new `payments` module, switched on per tenant by `super_admin`; `admin_tenant` configures it.** It is its own package (MOD-01..05), depends on the kernel and on the store's published contracts only, and with it off nothing changes for anyone and the gate stays open. The store's gateway-driven purchase requires both `payments` and `store`.
- **D-502: Mappings live where the admin already works.** Access products are registered on the Pagamentos screen (gateway product id plus checkout link, which feeds the Assinar button). Store products carry their gateway product id and checkout link in the PRODUCT FORM next to the price, keeping the product form the single writer of what a product unlocks (D-363, D-418).
- **D-503: A "Eventos recentes" list on the Pagamentos screen.** It shows the latest events with a state (applied, sem membership, produto desconhecido, ignored), "recebido há X" and, on the unmatched ones, a "Liberar manualmente" action (the existing grant). It doubles as the integration test. No raw payload is shown to the tenant.
- **D-504: An "Acessos" tab on the Pagamentos screen replaces the SQL Editor.** One row per e-mail with source, state and validity; actions to release an e-mail before the person signs up, block, and remove a manual access; search by e-mail.

### Store purchases through the gateway
- **D-505: Refund and chargeback always revoke a store entitlement, and an inactive subscription revokes it too.** A one-off purchase is revoked only by refund, chargeback or an admin. A late or canceled subscription revokes like platform access (D-496); its return restores the entitlement. The order becomes `revoked` and the member may buy again (D-359).
- **D-506: With a gateway on, Comprar opens the tenant's checkout link and nothing is faked in the meantime.** The product stays locked until the webhook creates the order; then the app unlocks it through the existing Realtime signal and shows an in-app "Compra confirmada" notification. No local "processando" state.
- **D-507: The order records what the gateway reports as paid.** `amount_cents` is the charged amount in BRL cents (coupon, discount and installments already resolved by the gateway), so the Financeiro dashboard (08.7) sums real revenue. The product's `price_cents` becomes a storefront reference. This supersedes D-361 for gateway orders only. — **Reversibility:** costly — `store_orders` rows written this way mean something different from simulated ones, and the dashboard sums both.
- **D-508: No link, no purchase, and the simulated purchase only exists for tenants without a gateway.** For a tenant with a gateway on, a product without a checkout link has its Comprar button hidden or disabled ("Indisponível") and the product form warns "sem link de pagamento". It never falls back to the simulated `app.store_purchase`, which would unlock for free. Tenants with no gateway keep today's simulated purchase unchanged.
- **D-509: The webhook writes orders and entitlements through new admin-lane definer functions.** The existing `app.store_purchase`, `store_grant` and `store_revoke` read `app.tenant_id()` and `app.user_id()` from the JWT, which a webhook does not have; the new path takes the tenant and the membership explicitly and still never opens a tenant-lane write policy. `store_orders.provider` accepts the gateway name and `provider_ref` carries the gateway's order id; entitlements keep `source = 'purchase'`.

### Carried forward from earlier phases
- **D-23 [informational] (Phase 1):** the membership is the authority; the host can only deny.
- **D-29 [informational] (Phase 2):** an invite pre-creates an `invited` membership; D-492 adds the manual access.
- **D-302 [informational] (08.1):** no answer reveals in which community an e-mail already has an account.
- **D-305 [informational] (08.1):** a correct password without a membership on the host leads to "Participar", which D-495 gates per tenant.
- **D-309 [informational] (08.1):** each tenant app is isolated; a purchase belongs to one membership.
- **D-316 [informational] (08.1):** a `super_admin` identity never becomes a tenant member.
- **D-330 [informational] (Phase 8):** blocking a member never touches content; D-498 follows it.
- **D-338 [informational] (Phase 8):** moderation and product management belong to `admin_tenant`.
- **D-359 [informational] (08.2):** revoking ends the entitlement and the member can buy again.
- **D-363 [informational] (08.2):** product links are edited only in the product form (D-418 extends it to courses and lives).
- **D-361 [informational] (08.2):** the product price is the only price; D-507 changes this for gateway orders.
- **261018-owq [informational] (quick):** the global allowlist, its two Auth hooks and the API pre-checks are what this phase refactors; hooks are still disabled in production with an empty list, and review findings WR-01 (API pre-checks bite before the hooks are on) and WR-02 (a future remote inherits the enabled hooks) are still open.

### Claude's Discretion
- Where and how the per-tenant webhook secret is stored (encrypted at rest with a platform key, write-only: never returned by the API after saving, never logged), and the route shape that carries the integration id.
- The signature check of each adapter (raw body, timing-safe compare, replay window) once the real Kiwify method is known, and the idempotency key when the payload has no event id of its own.
- The order-of-events policy: the gateway's own timestamp when present, otherwise arrival order, with state kept per order or subscription and only newer transitions applied.
- Column names, types and indexes of `access_grants`, the mapping table and the event inbox; RLS shape (admin lane with no policy for the inbox, as `media_provider_events`; tenant-admin read policies where the screens need them).
- The exact SQL of the coarse hook functions and how they stay 4xx-only and cheap.
- Migrating `email_allowlist` into `access_grants`, enabling the production hooks safely, and closing WR-01 and WR-02 as part of the rollout.
- The Realtime topic and notification type for "Compra confirmada", route names, pg-boss job names, and where the Pagamentos entry sits inside Configurações → Administração.
- All pt-BR copy not quoted above, and the visual design (a UI-SPEC is needed; `reference/frontend-design` has no payments, store or checkout screen).

## Existing Code Insights

### Reusable Assets
- `apps/api/src/routes/webhooks/mux.ts` plus `recordProviderEvent`: the shape of a signed, idempotent, fast-ack webhook with a pg-boss job behind it.
- `VideoProvider` and its fake: the pattern for a provider seam with a local stand-in, which gives a `fake` gateway adapter for dev and tests.
- `withAdminTx` and the zero-policy admin-lane tables: the home for the event inbox and the mapping reads done by the webhook.
- Store services `grantAccess` and `revokeAccess` and the buyers list: the manual "Liberar manualmente" and revoke paths already exist per membership.
- `tenant_modules` and `requireModule`: the per-tenant module switch used by the store and courses.
- Phase 7 notifications, push subscriptions and the Realtime Broadcast trigger pattern: for "Compra confirmada" and for removing push subscriptions on a cut.
- `apps/api/src/routes/admin/members.ts`: the admin members list that gets the "Assinatura pendente" badge and filter.

### Established Patterns
- Tables that no tenant lane may read have RLS enabled with zero policies; adding a policy to them is always a bug.
- Tenant-readable, admin-written tables use the `tenantReadAdminWritePolicies` shape; order and entitlement writes only through SECURITY DEFINER functions.
- Hand-written SQL (functions, grants, hooks) goes in `--custom` migrations applied by the Supabase CLI; drizzle-kit only generates.
- Auth hook functions are 4xx-only, `security definer`, `search_path = ''`, EXECUTE revoked from everyone but `supabase_auth_admin`; `auth.admin.createUser` does not fire `before_user_created`, so the API pre-check is the real gate on that path.
- pgTAP: every policy gets a cross-tenant negative test; `175-email-allowlist.sql` only passes with `000-helpers.sql`.

### Integration Points
- `signupMember`, `joinTenant`, the first-admin and invite paths, and `requireAuth` become per-tenant access checks.
- `store_orders.provider` (CHECK limited to `'none'`) and `provider_ref` take the gateway.
- The 08.7 dashboard functions count active members from memberships; they must learn the "assinatura pendente" state.
- Local seed (`scripts/seed.ts`), `apps/api/tests/integration/setup.ts` and `apps/web/e2e/admin.ts` all call `allowEmail` today and must move to the new records.
