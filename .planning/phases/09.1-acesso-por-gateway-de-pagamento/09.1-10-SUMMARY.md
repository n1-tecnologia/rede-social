# Phase 09.1 Plan 10: Acessos, Eventos and the member-facing payment reads Summary

**The admin API for who has access and what the gateway sent is complete (one row per e-mail whose state is the gate's own `app.access_effective`, block, unblock, release before the account exists, a remove that can never touch a gateway row, the latest 50 events with no payload and a once-only manual store release), and a cut member, the sign-up notice and the join screen each read the one stored `https:` link and the one tenant name they need through a single reader.**

## Accomplishments

- **Tracer through the real stack.** A signed delivery made an access active; the Acessos list shows ONE row for that e-mail with the gateway key, `active`, `hasAccount` and the end date. `block` (even typed in capitals) makes the member's next request `MEMBERSHIP_BLOCKED`; `unblock` returns them to what the gateway says; `release` for an address with no account lets the real sign-up succeed and `remove-release` makes it refused again; `remove-release` on a gateway-only address is the bare 404 with the row intact; `release` under a manual block is `409 blocked`.
- **One row per e-mail, state from SQL.** A grouped CTE over `access_grants` computes the page; the state is `app.access_effective` mapped to three words, the source is `manual` when blocked or when no gateway row exists, and `q` is `position(... in email)` on a bound parameter (a `%` in the box is a literal). The keyset over `(updated_at desc, email desc)` is proved across rows with equal instants at limits 1, 2 and 3.
- **Eventos with no payload.** The select list is the contract and the schema is strict: the latest 50 settled events in `(received_at desc, id desc)`, the store product's name through `app.store_product_name_for`, nothing still `received` or `failed`.
- **Liberar manualmente, once.** Read and validate, then the existing `app.store_grant` in the admin's own tenant lane, then a guarded `no_membership -> applied` update. One grant entitlement with no order and no revenue; a second click returns the same row; two simultaneous clicks and a click racing the webhook apply leave one active entitlement and no 5xx.
- **Three member-facing reads from one reader.** `accessCheckoutUrl` returns the oldest access product's link only while the gate is on. `GET /v1/me/subscription` is reachable while cut; the public tenant record and the join state `access_required` carry the same link; the join state is the same body for never-bought, late, blocked and access-elsewhere, and names no community.
