# Phase 09.1 Plan 12: The cut nudge and the buyer's Compra confirmada Summary

**A subscription cut now makes the member's open app notice (devices forgotten, a `notifications.changed` nudge on their own topic that meets the 403, the Supabase session untouched), and a confirmed store purchase gives the buyer exactly one in-app notice and one push, while every other thing the webhook does stays silent for everyone.**

## Accomplishments

- **Tracer through the real stack.** A signed `subscription_canceled` applied by the real job deletes the member's two devices (another member's survives), publishes one `{ kind: 'membership', id }` signal on `tenant:<t>:user:<u>`, and the next `GET /v1/me/counters` is `403 SUBSCRIPTION_PENDING`. The session is not revoked: the old access token still opens the member's other community, a fresh sign-in is issued, and the membership facts are unchanged. A renewal publishes nothing and deletes nothing; a staff e-mail, a gate-off tenant and a second product that keeps the member active emit nothing.
- **Failure isolation (flagged assumption P36).** With a database trigger refusing the device delete, the first step fails, is logged with ids only and swallowed; the nudge still goes out and the apply result is `applied / access_cut`.
- **The buyer's notice.** `paymentsNotificationSources` turns `payments.purchase_confirmed` into one actor-less intent for the one user id, with facts `{ productId, productName }`, channels `in_app` + `push`, and a sink-instant dedupe key (a retried job cannot duplicate, a repurchase after a refund is a new notice). The integration case proves one row, one push job with the hint, one signal, nothing for the lab admin, another member or the other tenant, a replay that adds nothing, a refund that adds nothing, a repurchase that adds a second row, and a cut buyer who still gets the in-app row but has no devices and no push.
- **Push copy.** `Compra confirmada: {name}` cut on a word to 100 graphemes with an ellipsis only when it cut (the shared `cutOnWord`), covered by unit cases for a 120-character name, emoji and accents, exactly 100 and a short name.
- **Silence.** Twelve different deliveries (cuts, returns, refunds, chargebacks, refused, unknown, ignored, no-account access and store, store refund, store chargeback) each leave the notifications table, the push and fan-out jobs and the admin's counters exactly as they were. The suite was shown to bite.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] The dead-device definer did not treat a cut member as dead**
- **Found during:** Task 1 design (before writing the handler)
- **Issue:** the plan has the subscriber call the existing `app.push_subscriptions_delete_dead(array[userId])`. That definer (07-06) deletes the devices of a member who is not live (blocked, soft-deleted, not active). A cut never writes the membership (D-496, PR-3), so for the one person the cleanup exists for it would delete nothing, the plan's "the member's two devices are gone" could never hold, and the send job's own pre-send sweep would keep pushing to a cut member (D-498).
- **Fix:** one expand-only `create or replace` of that definer (`20261021020907_push_devices_cut_members.sql`, generated with `drizzle-kit generate --custom`, snapshot and journal included): same signature, language, volatility, definer, empty `search_path`, tenant pinning and ACLs; one more reason a device is dead: its owner's subscription is cut. The cut set is read once per call (`app.membership_access_cut` over the listed ids, `app.access_cut_user_ids` for the `null` tenant sweep); both answer empty while the gate is off, `payments` is disabled, or for staff. Applied locally with `migration up`. Section 7 added to pgTAP 153 (6 cases, file now 41/41).
- **Files modified:** supabase/migrations/20261021020907_push_devices_cut_members.sql (+ snapshot, journal), supabase/tests/153-push-subscriptions.sql
- **Verification:** pgTAP 153 41/41; tracer, push, notifications, member-admin and the blocked-member chain pass.
- **Committed in:** `318ab45d`

**2. [Rule 1 - Bug] The plan's push tag fails the kernel's push hint validation**
- **Found during:** Task 2 design (`notificationPushHintSchema`)
- **Issue:** the plan specifies tag `payments.purchase:<productId>` and no topic. The kernel's `PUSH_TAG` is `^[A-Za-z0-9_-]{1,64}$` (no `.` or `:`) and a topic is required (`^[A-Za-z0-9_-]{1,32}$`); a hint that fails is dropped with `notifications.push.bad_hint`, so the buyer would never have been pushed.
- **Fix:** tag `payments-purchase-<productId>` (54 characters) and topic = the product id without hyphens (32 hex). Pinned by the source unit test, and the integration case proves a push job is enqueued.
- **Files modified:** packages/modules/payments/server/notifications.ts, packages/modules/payments/tests/notification-sources.test.ts
- **Committed in:** `9bcdac5d`

**3. [Rule 3 - Blocking] rede-lab has the `notifications` module off**

- **Fix:** the integration file turns the module on for rede-lab for the whole file and restores the previous row in `afterAll` (a local helper, so the shared `setup.ts` is untouched).
