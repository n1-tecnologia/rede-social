# Phase 09.1 Plan 11: Membros marks and filters cut members, dashboard stops counting them Summary

**The Membros list now flags a member whose subscription is not active (`subscriptionPending`, status still `active`), filters them with a fifth `subscription_pending` value, and the owner dashboard's four member-population functions read the same cut set once per statement to leave them out of the active-member figures at the next nightly build; no log row, notification or counter is created.**

## Accomplishments

- **Contract and service (D-498, D-489).** `ADMIN_MEMBER_STATUSES` ends with `subscription_pending`; `adminMemberSchema.subscriptionPending` is optional and emitted only as `true`. `admin-members.ts` cross-joins `app.access_cut_user_ids(ctx.tenantId)` once into the shared projection, so the list, the filter and the sheet read cannot disagree; the flag and the filter both require `status = 'active' and blocked_at is null`, so a blocked-and-cut member shows `blocked` alone. The `m.tenant_id = ctx.tenantId` predicate is on every statement (5 occurrences, as before).
- **Dashboard population (D-498).** One expand-only migration re-creates `app.dashboard_member_actions`, `app.dashboard_member_rows`, `app.dashboard_area_members` (CTE `joins`) and `app.dashboard_area_overview` (KPI `members.count` / `newMembers`), copying the latest body of each and adding only `cross join (select coalesce(app.access_cut_user_ids(app.tenant_id()), '{}') as ids) cx` plus `<> all (cx.ids)`. Signatures, definer, empty `search_path` and the owner-only ACL are unchanged and pinned by pgTAP 207.
- **Nothing else created (D-500, PAY-18).** A cut and a return write no `moderation_log` row, no notification, change no counter and add no notification kind; a block of the same member still writes its row exactly as before; list and log order are unchanged.
- **Tests.** pgTAP 207 (four tenants with one layout: gate on, no payments row, module disabled, a shared identity) fails 17 of 60 against the old function bodies and passes 60 of 60 on the new ones; `payments-members` 16 cases, `dashboard-owner-members` 14 cases (including a tenant whose every member is cut), one `member-admin` pin.

- The access cut set holds a membership that is `status = 'blocked'` and has no access row, so the cut set alone is not "active members who are cut". The projection and the filter therefore require `m.status = 'active' and m.blocked_at is null` themselves; pgTAP 207 and the tracer pin it.
- The rede-lab tenant has the notifications module off, so `GET /v1/notifications` answers `MODULE_DISABLED` there; the "no admin notification" case compares that answer with its per-request id stripped and asserts the stored `notifications` count for the admin, which is the real proof.
- The dashboard builder returns early when a row exists at the current payload version, so every "rebuild" in the tests deletes the day's row first, as `rebuildDashboard` already does.
