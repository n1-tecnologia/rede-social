## Fixed Issues

### CR-01: replay protection bypass — fixed

**Commit:** `eadd99ae`
**Claim verified:** yes. The new integration test failed before the fix (a whitespace re-rendering of an authenticated delivery answered `enqueued: true`).
**Applied fix:** `GatewayProvider.verify` now returns `{ variant, signed }` (new `VerifiedDelivery` type); the Kiwify adapter returns the bytes of the candidate whose HMAC matched, the `fake` adapter returns the received bytes. `receive.ts` hashes `signed` for the `dedupe_key` and also normalises `signed`, so the event applied is the one that was authenticated. Neutral interface stays brand-free (PAY-02 guard passes).
**Existing rows / migration:** none needed. For a delivery signed over the received bytes (the `raw` variant, and every `fake` delivery) `signed` is the received bytes, so its key is unchanged. Only a delivery recorded earlier through the `reserialised` variant with non-canonical received bytes (a pretty-printed body signed over its canonical form) has an old key `sha256(received)` and would key as `sha256(canonical)` now, so one gateway retry of that exact delivery could be applied once more. The signed material the vendor really uses is still unconfirmed (A-P17) and no real signed delivery has been recorded, so the window is believed empty; it is noted rather than migrated.
**Test change you should know about:** the integration case "answers a replay of a delivered body..." replayed the same bytes under the OTHER signed material (a pair only the token holder can produce, and the exact shape the bug exploited). It now replays with the same bytes and signature, which is what a real replay is.
**Regression tests that bite:**
- `apps/api/tests/integration/payments-kiwify-webhook.test.ts`: "dedupes the same authenticated delivery re-sent with different whitespace (CR-01)" (tab-indented, 5-space padded and compact renderings all answer `enqueued: false`, one event row, one job) and "does not collide two genuinely different deliveries (CR-01)".
- `packages/core/tests/payments-kiwify.test.ts`: signed bytes are the received bytes (raw), the canonical bytes (reserialised), identical across renderings, different for different bodies; both signature variants still verify. `payments-fake.test.ts` asserts `signed`.
**Status note:** logic fix, `fixed: requires human verification` is reasonable for the key-continuity paragraph above.

### WR-01: env guard fails open — fixed

**Commit:** `c6047a84`
**Claim verified:** yes (unset list, `kiwify,fake` and `fake` all passed the old guard; 4 new tests failed before).
**Applied fix:** `assertProductionEnv` takes `NODE_ENV`; when it is `production` it requires `PAYMENTS_PROVIDERS` to be set, refuses a list naming `fake`, and always requires a 32-byte base64 `PAYMENTS_SECRET_KEY`. `resolvePaymentsKey` takes a `production` flag (set from `env.NODE_ENV` in `paymentsKey()`) and never derives the development key then. Outside production nothing changed (unset list, `fake`, no key still boot), so local dev, vitest (`NODE_ENV=test`) and the Playwright harness (`next dev`, API `tsx watch`, `PAYMENTS_PROVIDERS ??= 'fake'`) keep working. Only the API and the worker import the kernel env (the web app does not), and both hosted deploys already set `PAYMENTS_PROVIDERS=kiwify` plus the key.
**Regression tests:** `packages/core/tests/payments-secret.test.ts`, two new describes: production (unset, `fake`, `kiwify,fake`, ` fake , kiwify`, missing/short key all throw; `kiwify` + 32-byte key boots), development/test stay valid, and `resolvePaymentsKey` with `production: true`.
**Not done:** `enabledProviders` still returns every adapter for an unset list outside the boot guard; the guard makes that unreachable in production.

### WR-02: buyer e-mail and amounts in logs — fixed

**Commit:** `32993478`
**Claim verified:** yes. drizzle-orm 0.45.2 `DrizzleQueryError` builds its message as `Failed query: <sql>\nparams: <params>` and keeps `query`/`params` as own properties. Both new tests failed before (e-mail present in the log).
**Applied fix:** new `redactDbError` in `packages/core/server/logging.ts` reduces a failed statement to `{ type, sqlstate, constraint, table, column }` (identifiers only: no message, `detail`, stack, SQL or params). Used in `apps/api/src/app.ts` `onError` (webhook request path and every other route) and in `apply.ts` for both `payments.apply.failed` and `payments.apply.mark_failed_failed`. `applyPaymentEvent` also rethrows a `PaymentApplyError` (sqlstate only, no cause) instead of the raw error, because pg-boss persists the thrown message and stack in the job row; non-statement errors propagate unchanged.
**Regression tests:** `payments-apply.test.ts` "WR-02: a failed statement logs and rethrows no e-mail, amount or bound parameter" (forced trigger failure; checks logs, message, stack, no `cause`); `payments-webhook.test.ts` "WR-02: a failed insert answers 500 and logs neither the buyer e-mail nor the amount" (route path); `packages/core/tests/logging-redact.test.ts` (unit). Fictitious values only (`ana.<hex>@exemplo.com.br`, amount 8467135).

### WR-04: webhook token strength — partially fixed

**Commit:** `f12a375b`
**Claim verified:** yes for the missing floor and the missing throttle; the integration id derivation is as described (see below).
**Applied fix:** `tokenField` now requires at least 8 code points (`PAYMENTS_MIN_TOKEN`) with no whitespace or control character inside (value trimmed first), max stays 512. A modest floor, because the gateway issues short tokens of about ten characters (tests assert `k7x9q2m4zp`, `a1b2c3d4`, `Token-1234` are accepted). New refusal code `token_invalid` joins the closed vocabulary (empty stays `token_required` alone) and is wired through the web action, the Pagamentos card and the pt-BR catalog ("O token parece incompleto. Use ao menos 8 caracteres, sem espaços.").
**Regression tests:** `packages/modules/payments/tests/contracts.test.ts` (floor, accepted short vendor tokens, whitespace/control chars, empty stays `token_required`, vocabulary), `apps/api/tests/integration/payments-admin.test.ts` (400 `{ payments: 'token_invalid' }` for `1234`, `senha`, `abcd efgh`; 200 for a ten-character token), `IntegrationCard.test.tsx` (field error). One existing admin test used `token: 'abc'` for a provider-unavailable case and now uses `abcd1234`.

**OWED (not built):**
- **Throttle of failed signature attempts per integration id / per source.** The repository has no request rate-limit helper (the review's own A-P20 says so), so by instruction no new infrastructure was created. Until it exists the online brute-force exposure is bounded only by the token floor, the 256 KiB body cap and the cheap early 404. Suggested follow-up: a Postgres-backed or Cloud Armor/edge limit in front of `/v1/webhooks/*`, keyed on integration id and source IP.
- Existing short tokens already saved (under 8 characters) stay valid until replaced; only new saves are checked.

**Integration-id enumeration, answered:** the claim is accurate. The id is `uuid5(constant namespace, "<tenantId>:<provider>")`; the namespace is in the repository and the tenant id is in the member bootstrap, so any member can compute their tenant's webhook URL, and the 404 (no integration) versus 403 (bad signature) difference reveals whether a tenant has a connected integration. The id is not a secret by design (`ids.ts`, the HMAC is the authentication), and it is why the screen can show the URL before a token exists. NOT changed: re-deriving the id (for example with a server secret) would move every tenant's webhook URL and break every integration already pasted into the gateway; making 403 look like 404 would only remove a low-value oracle and costs admins their diagnostics. Both are product decisions; with a throttle in place the remaining value of knowing the handle is small.
