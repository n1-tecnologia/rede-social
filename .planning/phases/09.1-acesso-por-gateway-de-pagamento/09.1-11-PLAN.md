<planning_decisions>
1. **The flag is a projection, not a status.** `memberships.status` stays `active`; `subscriptionPending` is computed from the same SQL function the gate uses, so the list can never say "pending" for someone the API admits (or the reverse).
2. **Optional and `true`-only.** The contract key is optional and emitted only when true, so an older web build never meets a new required key and an ungated tenant's responses are byte-identical to today's.
3. **One read of the cut set per statement.** `access_cut_user_ids` is evaluated once in a cross-joined subselect; a per-row call would turn a 50-row page into 50 function evaluations and a dashboard build into one per member.
4. **Only member-population CTEs change.** Content, events, finance and support dashboards measure posts, attendances, money and conversations; changing them would silently alter figures D-498 does not mention.
5. **The snapshot is nightly on purpose.** The dashboard reads a once-a-day build (INSIGHT-16); the exclusion appears at the next build, which D-498 accepts ("drops out of the dashboard's active-member count"), while the live Membros filter answers at the read instant.
</planning_decisions>
