# Phase 09.1 Plan 06: Store gateway orders and the closed free unlock Summary

**A tenant with a payment gateway can no longer reach the free simulated unlock (the refusal lives inside `app.store_purchase`), and a signed webhook can record and end a gateway sale only through two explicit-argument, service_role-only definers that write the amount the gateway charged, with no write policy ever added to the ledgers.**

## Performance

- **Duration:** 23 min
- **Tasks:** 3 (Task 1 tracer, Task 2 auto, Task 3 auto)
- **Files modified:** 15 (including two generated snapshots)

## Accomplishments

- **The guard (D-508, T-09.1-26).** `app.store_purchase` is re-created from its LATEST body (`20261009085216_store_purchase_owned_first.sql`) with one added step after the "already held" check: `if app.payments_gateway_mode() then unavailable`. A holder still gets `owned`; a non-holder of a gateway tenant gets 409 `{ store: 'unavailable' }` at any price, for an archived product too, and nothing is written; a stale product read cannot get around it (P61, proven with a read taken BEFORE the integration existed). A tenant with no gateway keeps the simulated purchase unchanged (store.test.ts, 50 cases, only two exact-match assertions gained the new key).
- **The two definers (D-509, D-505).** `app.store_gateway_purchase` writes a `paid` order (`provider`, trimmed `provider_ref`, `amount_cents` as the gateway reports, `currency 'BRL'`, `paid_at`) and a `purchase` entitlement; `app.store_gateway_revoke` ends the active entitlement of the live order of a reference and marks the order `revoked` (`revoked_by_user_id` null), freeing both arbiters so the member can buy again as a new order (D-359). Both take the tenant and the membership as arguments, pin every statement to `p_tenant`, are `security definer` with `search_path = ''`, return outcomes (never raise) and are EXECUTE-able by `service_role` only; a member and an `admin_tenant` lane are refused with 42501.
- **Order data (D-486, D-507).** `store_orders_provider_chk` is now `provider = 'none' or provider ~ '^[a-z][a-z0-9_]{1,30}$'` (a format, never an enum) and `store_orders_provider_ref_uq` allows one live order per `(tenant, provider, provider_ref)`; a revoked row, another tenant and two simulated orders with no reference do not conflict.
- **Read side (D-506, D-508).** Product cards and details carry the optional `purchase { mode, checkoutUrl }` read in the same statement from `app.payments_gateway_mode()` and `app.payments_checkout_url(p.id)` by SQL name (no payments import, `pnpm boundaries` clean). In gateway mode `buyableProducts` of the community, course and live access reads drop products without a stored link; `locked`, `gated`, `archivedTag` and the manager's `products` list are unchanged.
- **Published seam (MOD-02).** `payment_products_target_fk` (`on delete cascade`), `app.store_product_exists(uuid)` (tenant lane) and `app.store_product_name_for(uuid, uuid)` (admin lane) let plans 09 and 10 confirm and name a store product without reading a store table.
- **Revenue (D-507, P60).** The Financeiro sums `store_orders` regardless of provider (no filter existed, `finance.ts` and the SQL functions untouched): a gateway sale of 12345 cents on a product listed at 99900 plus one of 1 cent adds exactly 12346 to the Window30 total, and a simulated purchase beside them still adds the product price.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Two exact-match assertions in `store.test.ts` rejected the new `purchase` key**
- **Found during:** Task 1 verify (`store.test.ts` is a Task 1 verify target)
- **Issue:** the catalogue case and the "empty product" case compare the card and the detail with `toEqual`; the product read now carries `purchase`, so they failed on an additive key.
- **Fix:** both expectations gained `purchase: { mode: 'simulated', checkoutUrl: null }` (the value a tenant with no gateway must see). No behaviour of the simulated purchase changed.
- **Files modified:** apps/api/tests/integration/store.test.ts
- **Commit:** ea2384e0

**2. [Rule 2 - Missing critical] Reference whitespace and control characters (P63)**
- **Found during:** Task 1 design
- **Issue:** the plan says "stored trimmed" and "any non-control UTF-8" but `btrim(text)` trims only spaces, so a reference ending in a tab or newline would be stored with it (and a blank `\t\n` reference would not read as empty).
- **Fix:** both definers use `btrim(p_provider_ref, E' \\t\\r\\n')` and refuse a reference that still contains a control character (`[[:cntrl:]]`); the same normalisation on purchase and revoke keeps the key consistent. pgTAP 206 and the integration file assert the trim, the blank refusal and the control-character refusal.
- **Files modified:** supabase/migrations/20261021001035_store_gateway_functions.sql
- **Commit:** ea2384e0

**3. [Process] `buyableCount` does not exist in the code the plan describes**
- **Found during:** Task 2
- **Issue:** the plan asks to filter link-less products from "the per-row `buyableCount`" of the list reads; the access list rows carry `locked`, `gated` and `archivedTag` only, and `buyableCount` is only a log field derived from `buyableProducts`.
- **Fix:** nothing to filter in the list rows; the log field follows the filtered `buyableProducts`. The rule is applied in `getCommunityAccess` and `accessAnswer` (course and live).
- **Commit:** 5adc17c9

**4. [Process] `db:reset` and `db:seed` not run**
- **Found during:** all three verify blocks
- **Issue:** the verify commands begin with `pnpm db:reset && pnpm db:seed`, which would wipe the local platform-admin account and manual test data; nobody could be asked mid-run. The two new migrations were applied with `scripts/supabase.sh migration up`, as plans 02-05 did.
- **Result:** pgTAP 43 of 44 files pass (206 124/124, 180 and the neighbours included); the one failure is the known `154-moderation-log` test 41 residue. API integration: 79 of 80 files, 1618 of 1623 cases pass; the 5 failures are the known `stories.test.ts` aged-seed cases. `pnpm db:generate` prints "No schema changes".
