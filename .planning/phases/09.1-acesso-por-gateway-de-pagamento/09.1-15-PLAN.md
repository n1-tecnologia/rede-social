<objective>
What the person sees. After this plan a member whose subscription lapsed lands on a calm, branded "Sua assinatura não está ativa" screen from wherever they were (a fresh page, an open app nudged by the cut, an action), with one button that fixes it; and anyone refused at sign-up, login or "Participar" reads the same single sentence with a way to buy when the community registered one.

Task 1 is the tracer: the pending screen and every route into it, end to end from a cut through the open app's nudge. Task 2 adds `AccessNotice` to sign-up, login and join with the catalog rewording. Task 3 pins the edge cases and the secrecy rules.

Decisions implemented: D-493 and D-302 (one sentence, a way to buy, no other community), D-497 (the screen, its three actions, its own error code), D-499 (the session is kept), D-305 (the join screen is gated per tenant), UI-D-521, UI-D-522, UI-D-532.

Purpose: a payment state must read as "what happens next", not as a punishment, and the one link that sends people to pay must come from the API per request, never from a URL a visitor can edit.
Output: the pending page, the notice, the error-code branches in six places, the three screen integrations, the catalog changes and the tests.

<planning_decisions>
1. **A sibling of the blocked flow, not a copy of its session handling.** The mapping, the counters answer and the shell landing all mirror the `MEMBERSHIP_BLOCKED` ones; the single difference is that nothing signs out or clears cookies, because D-499 keeps the shared identity alive.
2. **The link has one reader.** `lib/subscription.ts` is the only place the cut page learns the checkout link, and it validates `https:` with a host before the page renders an `<a>`; the same parse guards the notice.
3. **The notice is a card, not an alert line.** It replaces the red text because "you have not paid" is not an input error; the sign-up form stays under it so a person can retry with another e-mail.
4. **The login notice needs a tenant slug.** On a tenant host the page already knows the slug (`getHostTenant`), reads the public tenant record only on the error path and takes `accessCheckoutUrl` from it; on a generic or platform host there is no community, so the notice shows the sentence without a link.
5. **Join is a screen, not an error.** The `access_required` state arrives from the API's read (plan 10), so `/participar` renders the notice instead of the form rather than letting the person fill it and meet a refusal.
</planning_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL query → rendered screen | `?t=`, `?erro=` and any extra parameter are attacker-editable and must never supply a link, a name beyond text, or a state |

| refused visitor → the answer | the message must not distinguish accounts, communities or payment status |
