<planning_decisions>
1. **One rule, one function.** Every consumer (requireAuth, the admin list, the dashboard, the hooks, the manual-grant guard) asks `app.access_effective` or `app.access_state`; no TypeScript re-implements precedence.
2. **Block is a separate manual row.** `access_grants_manual_uq` is unique on `(tenant_id, email, status)` where `source = 'manual'`, so one e-mail can hold a manual `active` row (a release) AND a manual `blocked` row at once. "Desbloquear" (UI-D-518: "restores the previous state") is then a delete of the blocked row, which leaves a release exactly as it was and leaves a gateway-only e-mail on its gateway state. A single status-toggling row could not remember whether a release existed (assumption A-P13).
3. **The gate lives in `tenant_modules.settings`**, key `gate`, as the module row's own knob (SCHEMA-CONVENTIONS (f): module toggles are rows, no new column on `tenants`). Writes are admin-lane (plan 09); this plan only reads it.
4. **Expand-only.** Two new migrations add a table and functions; nothing is altered or dropped. The previous API revision keeps calling the old lookups.
5. **Staff exemption is by live membership role**, evaluated inside `app.access_state` from `public.memberships`, never from a JWT claim (requireAuth has no lane yet).
6. **`none` is `cut` when the gate is on** (A-P24): a member who exists but has no row sees "Assinatura pendente", which is what the gate dialog tells the admin when the release box is cleared (UI-D-516).
</planning_decisions>

ASVS level 1. Blocking severity: `high`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| member session → any tenant-lane route | the access decision is server-side, per request; the client never says whether it has access |
| API connection (`api_user`) → SECURITY DEFINER functions | the decision functions read zero-policy tables with their owner's rights |
| tenant lane (`authenticated`) → access state of other e-mails or tenants | must stay closed: no function that answers "does e-mail X have access in tenant Y" is executable by a tenant lane |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09.1-03 | Elevation of privilege | a tenant-lane user reading or writing `access_grants` (granting itself access) | high | mitigate | RLS enabled with zero policies, `revoke all … from anon, authenticated`, no write path outside admin-lane definers; pgTAP 204 section 3 and 010 |
| T-09.1-04 | Elevation of privilege | a member keeping access after the gate says cut (a cache, a stale claim) | high | mitigate | the decision is made live in the same SQL statement as the membership lookup on every request; no claim, cache or session flag carries it; the integration case flips state between requests |
