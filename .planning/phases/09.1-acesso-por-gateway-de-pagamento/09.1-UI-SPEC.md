# Phase 09.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Each tenant's payment gateway (Kiwify first, behind a provider-neutral seam) drives who may enter the community and who owns a store product. This phase adds or changes these surfaces:

1. the **Pagamentos** admin screen with three tabs: **Configuração** (integration, access products, the "Exigir assinatura para entrar" switch), **Acessos** (one row per e-mail) and **Eventos** (recent webhook events);
2. the **"Assinatura pendente" screen** a cut member sees (full-screen, tenant brand);
3. the **no-access notice** on sign-up, login and the "Participar" join screen, with the "Assinar" button;
4. the admin **Membros** list: the "Assinatura pendente" badge, its filter chip and its line in the member sheet;
5. the **store product form**: the "Pagamento" block (gateway product id and checkout link) and the "sem link de pagamento" warning;
6. the **store product page**: "Comprar" opening the checkout link, and "Indisponível" without one;
7. the **"Compra confirmada" notification** in the bell and its push banner;
8. the **platform panel** `payments` module row and its disable confirmation;
9. the **Configurações → Administração** entry "Pagamentos".

**Design authority.** `reference/frontend-design/` has no payments, store or checkout screen (CONTEXT Discretion; checked 2026-10-20 with `ls reference/frontend-design/app`). Its `settings` page is the Configurações list geometry, already ported in Phase 2. Every surface here is **[designed]** in the prototype's language from primitives that already ship in `@rede-social/ui`, `@rede-social/core/ui` and the module packages. Nothing is ported, so PROTOTYPE.md's porting rules do not apply; its token rules do (`bg-brand/10`, no hex, no literal text in TSX).

**Inherited design language.** The design language, spacing scale, type scale and colour model are **inherited unchanged** from the approved `02`–`09-UI-SPEC.md`. This document restates them for the checker and records only the Phase 09.1 deltas. The admin patterns reused are named below: `/configuracoes/membros` (search, chips, row, sheet), the store product form (`ProductForm`), the platform `ModuleToggles` row and the `ConfirmDialog`.

**Upstream decisions.**
- `09.1-CONTEXT.md` decisions are cited as **D-485..D-509** (quoted copy: "Seu acesso ainda não foi liberado. Use o mesmo e-mail da compra.", "Assinar", "Sua assinatura não está ativa", "Regularizar", "Assinatura pendente", "Exigir assinatura para entrar", "Eventos recentes", "Liberar manualmente", "Compra confirmada", "Indisponível", "sem link de pagamento"). None is re-litigated.
- The UI questions this phase opens are decided below as **UI-D-513..UI-D-532**. They continue after Phase 09's UI-D-512, the highest id in any UI-SPEC (checked 2026-10-20 with `grep -rhoE "UI-D-[0-9]+" .planning | sort -t- -k3 -n -u | tail -1` → `UI-D-512`).
- Earlier visual decisions keep their numbers: the Membros list (UI-D-271..UI-D-273, UI-D-283), the store (UI-D-369..UI-D-386), the platform module row (UI-D-505), notification rows (UI-D-251, UI-D-460), the suspended screen (D-09).

**Non-interactive session.** No question could be asked in this run. Every open item is decided below with a stated default (**A-UI-1..A-UI-9**) and the three that change what the product does are repeated in **§ Pending User Confirmation**.

**Assumptions made in this session** (the planner may overturn any with one line):
- **A-UI-1.** An access product carries an admin label ("Nome"). CONTEXT fixes the gateway product id and the checkout link (D-502); a label is the minimum for the list and for the event rows to say which product they mean. It is a column the planner adds to the mapping.
- **A-UI-2.** The "Exigir assinatura para entrar" switch is enabled only when the integration is connected AND at least one access product is mapped. D-491 requires the second; the first stops a tenant from locking everyone out with no way to receive a payment.
- **A-UI-3.** The "Assinatura pendente" screen and the join screen carry a "Verificar de novo" outline button. D-497 lists "Regularizar" and "Sair"; without a re-check the member who just paid has no way off the screen except typing the URL.
- **A-UI-4.** There is **no "Desconectar" action** on the integration in this phase. Removing the integration would reopen the simulated store purchase (D-508), which unlocks products for free. See PU-2.
- **A-UI-5.** Turning the gate on shows the exact count of current members who have no access record and would be cut, and does not seed them. See PU-1.
- **A-UI-6.** `super_admin` confirms before disabling the `payments` module (it reopens sign-up and the free simulated purchase).
- **A-UI-7.** The "Assinar" and "Regularizar" link is the checkout link of the **oldest access product that has one** (D-494 allows several, D-493 shows one button). The list marks that row so the admin sees it.
- **A-UI-8.** Member-facing copy says "página de pagamento" and never names the gateway. Admin-facing copy names it through `{gateway}` (the adapter's display name, "Kiwify"), so a second adapter needs no copy change (D-486).
- **A-UI-9.** No toast on purchase confirmation. The bell notification (D-506) and the product page refreshing into its owned state, announced by an `aria-live` region, are the confirmation.

**Interaction truths outside the 8-category state taxonomy.** The planner lifts these as plain truths:
- **E02:** the webhook token is write-only. No API response, log line, HTML or error message after saving carries it (D-486 Discretion, UI-D-532).
- **E04, E05, E06:** the web never decides who has access. It renders the server's state and sends the admin's intent; the effective state follows D-489 (a manual block wins, otherwise the gateway's latest state, otherwise a manual release).
- **E08, E09:** every checkout link on a member surface is fetched from the API per request and rendered only when `https:`. No query string, cookie or draft supplies it.
- **E08, E09:** no refusal on sign-up, login or join reveals whether an e-mail has an account in another community, and none names a community other than the host's (D-302).
- **E08:** the "Assinatura pendente" screen does not clear the session (D-499); only "Sair" does.
- **E11, E12:** a tenant in `gateway` mode never reaches the simulated purchase, and a product without a link is never buyable (D-508). A tenant in `simulated` mode renders today's controls byte-identically.
- **E12:** the web never unlocks a product by itself. The product page leaves its locked state only when the server says so (D-506).
- **E13:** a revocation, a cut and a return create no notification (D-496, D-500).

**Contract requirements this document places on the API** (for the planner; each is a projection of D-485..D-509, not a new rule):
- **Pagamentos overview:** `integration { gateway, gatewayName, connected, webhookUrl, lastEventAt | null }`, `accessProducts[] { id, name, externalProductId, checkoutUrl | null, feedsSubscribeButton }`, `gate { required, canEnable }`, optional `storeProductsWithoutLink` count, and `serverNow`. The token is accepted on write and never returned.
- **Gate preview:** a read returning how many members of the tenant (staff excluded) have no usable access, used by the confirm (UI-D-516). A refusal `last_access_product` on removing the last product while the gate is on.
- **Acessos list (keyset, `q`, `status`):** `items[] { id, email, source: 'manual' | <gateway key>, state: 'active' | 'subscription_pending' | 'blocked', validUntil | null, hasAccount?, updatedAt }`. Writes: release (idempotent; `blocked` 409 when the e-mail is manually blocked), block, unblock, remove release (manual rows only); each answers the updated row.
- **Eventos list (last 50, no payload):** `items[] { id, type, state: 'applied' | 'no_account' | 'unknown_product' | 'ignored', email | null, productName | null, externalProductId | null, effect | null, receivedAt }`. "Liberar manualmente" answers 409 `no_membership` when no membership carries the e-mail.
- **Product write/read:** `gatewayProductId` and `checkoutUrl` on the store product, with refusals `gateway_product_id_required` and `gateway_product_taken`. The product read carries `purchase { mode: 'gateway' | 'simulated', checkoutUrl | null }`, and "buyable" includes the link rule in `gateway` mode.
- **Cut:** a new `ERROR_CODES` entry (a sibling of `MEMBERSHIP_BLOCKED`) from `requireAuth`, and an endpoint reachable while cut returning `{ tenantName, checkoutUrl | null }`.
- **No-access:** the public tenant record (or a join state `access_required`) carries `accessCheckoutUrl | null` for the notice.
- **Membros:** `ADMIN_MEMBER_STATUSES` and the member row gain `subscription_pending`; a block outranks it.
- **Notification:** a purchase-confirmed kind with facts `{ productId, productName }`, retracted when the product is archived.
- **Clocks:** every relative string and every date arrives finished from the server in the tenant timezone (UI-D-288); no `Date.now()` in render.

If the planner drops a field, the surface omits that piece rather than estimating it.
