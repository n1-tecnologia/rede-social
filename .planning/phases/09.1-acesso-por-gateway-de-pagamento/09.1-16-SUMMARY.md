# Phase 09.1 Plan 16: Membros shows who is on a lapsed subscription; the platform Pagamentos row confirms before disabling Summary

**An admin finds members on a lapsed subscription by a warning pill, a fifth filter chip and a one-line sheet note, all present only while the `payments` module is on; the platform owner now gets a danger-tone confirmation, naming the tenant and what reopens, before switching Pagamentos off.**

## Accomplishments

- **Tracer (Membros).** `MemberPills` pushes the warning `StatusPill` "Assinatura pendente" after the role and status pills and before "E-mail não confirmado", only when `subscriptionPending === true` and the member is not blocked, so a blocked-and-cut member shows only "Bloqueado" (D-489). The same component feeds the sheet's identity block, so the pill appears there too. `MemberAdminSheet` renders the 12/400 secondary note as the first child of the controls stack, above the role list, block/unblock and "Ver perfil", for the same condition; nothing else in the sheet moved.
- **Fifth chip and filter.** `AdminMembersList` takes `paymentsOn`, iterates the closed `ADMIN_MEMBER_STATUSES` and drops `subscription_pending` when it is false (the 09.1-11 guard is gone). The chip row stays `overflow-x-auto`, hidden scrollbar, `shrink-0` chips, never wraps. The filter has its own `Users` empty state with the contract words and no action; a search keeps the search copy. A new `FILTER_KEY` table maps the snake_case contract value to the camelCase catalog key.
- **Page and action.** `page.tsx` computes `paymentsOn` from `bootstrap.modules` and passes it; `parseStatus(sp, paymentsOn)` reads a hand-typed `?status=subscription_pending` as "Todos" while the module is off. `loadMoreAdminMembersAction` gained a fourth parameter `paymentsOn` and asks for the unfiltered page in that case (T-09.1-76).
- **Platform row.** `ModuleRowExtras.confirmDisable` (title, body, confirm, cancel, optional icon name) opens the shipped `ConfirmDialog tone="danger"` when a row is switched OFF; only its confirm runs the optimistic flow; switching ON never opens it; a row with no entry is byte for byte as before. `modulos/page.tsx` builds the `payments` extras from `platform.payments.*`: the "Sem o módulo Loja, só a entrada é controlada." note only while `store` is off, no `disabled`, no `confirmEnable`, and `confirmDisable` with the tenant's display name in the title and body and the `credit-card` icon.
- **Catalog.** `admin.json` gained `members.filters.subscriptionPending`, `members.pills.subscriptionPending`, `members.subscriptionPendingEmpty.{title,body}` and `members.subscriptionPendingNote`; `platform.payments.json` gained `payments.noStoreNote` and `payments.disableDialog.{title,body,confirm,cancel}`. No existing key changed value; all ten are pinned in the new `members-payments-messages.test.ts`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The catalog key does not match the contract value**
- **Found during:** Task 1 (GREEN run)
- **Issue:** the list built the chip label with `t('members.filters.<value>')`, but the contract value is `subscription_pending` and the plan's (and the UI-SPEC's) catalog key is `subscriptionPending`; the fifth chip threw MISSING_MESSAGE.
- **Fix:** one explicit `FILTER_KEY` table in `AdminMembersList.tsx` (contract value to catalog key).
- **Files modified:** `apps/web/app/(app)/configuracoes/membros/AdminMembersList.tsx`
- **Commit:** `3b21ad0f`

**2. [Rule 1 - Bug] The shipped busy mark never painted while a change persisted**
- **Found during:** Task 2 (E14 loading test)
- **Issue:** `ModuleToggles.run` set `pendingKeys` inside `startTransition(async ...)`. In React 19 a plain state update made inside an async transition is held until the whole action settles; only the optimistic value shows. So `aria-busy` on the row and `busy` on the switch never rendered mid-flight (and the `pendingKeys` double-tap guard only worked after the fact). The plan's E14 loading row ("aria-busy on the switch while the change persists") would have been untrue.
- **Fix:** `setPendingKeys(add)` now runs just before `startTransition`; the optimistic value stays inside. All 265 platform tests, old and new, pass.
- **Files modified:** `apps/web/components/platform/ModuleToggles.tsx`
- **Commit:** `911de1d5`

**3. [Rule 1 - Bug] The plan's `icon: CreditCard` cannot cross the server-to-client boundary**
- **Found during:** Task 2 (page)
- **Issue:** the plan says the page passes `CreditCard` and the component defaults the icon; `modulos/page.tsx` is a server component and `ModuleToggles` a client component, and a component function is not serialisable as a prop. A mocked unit test would not have caught it; the real route would have failed at render.
- **Fix:** `confirmDisable.icon` is an icon name the shell's `iconFor` already resolves (`'credit-card'`, which plan 13 registered), defaulting to `'users'`, the disc `confirmEnable` defaults to. The component stays module-agnostic. (`confirmEnable.icon` keeps its shipped `LucideIcon` type; the page never passes it.)
- **Files modified:** `ModuleToggles.tsx`, `modulos/page.tsx`
- **Commit:** `911de1d5`

**4. [Rule 2 - Missing critical] The load-more action needed to know the module state**
- **Found during:** Task 1
- **Issue:** the plan says `actions.ts` applies the same normalisation, but the action had no way to know whether `payments` is on.
- **Fix:** a fourth parameter `paymentsOn: boolean`, passed by the list from the prop the page derived from `bootstrap.modules`. It is a consistency rule, not an authority (the API answers an empty set for that filter with the module off); the unfiltered request is `status: 'all'` after the schema default.
- **Files modified:** `actions.ts`, `AdminMembersList.tsx`
- **Commit:** `3b21ad0f`

**5. [Plan wording] Extra test files**
- The plan lists `AdminMembersList.test.tsx` among the tests; it also needed `page.test.tsx` and `actions.test.ts` (the `parseStatus` rule and the action rule live in those modules), and the Módulos page extras needed `modulos/page.test.tsx`. All four are new files under the directories the plan already lists. `AdminMemberRow.test.tsx` did not exist before this plan either.
