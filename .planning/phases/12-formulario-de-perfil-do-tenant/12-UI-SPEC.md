# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 12 lets the tenant admin build a profile form and lets members answer it. Most of it is model, gate and API work; the UI is two audiences and nine surfaces, all in pt-BR:

| # | Surface | Audience | Route (proposed, the planner owns the final names) |
|---|---------|----------|---------------------------------------------------|
| 1 | Form builder: the "Perguntas" tab (summary, list, reorder, empty, module off) | `admin_tenant` | `/configuracoes/formulario-de-perfil` |
| 2 | Question editor sheet (13 types, options, "Outro", limits, switches, LGPD notice, locked states) | `admin_tenant` | sheet over surface 1 |
| 3 | "Arquivadas" tab and "Reativar" | `admin_tenant` | `/configuracoes/formulario-de-perfil?aba=arquivadas` |
| 4 | "Exportar respostas (CSV)" and its result states | `admin_tenant` | action on surface 1 |
| 5 | Impact and removal confirmations ("N membros vão precisar responder", archive, delete, discard) | `admin_tenant` | dialogs over 1-3 |
| 6 | The completion screen / gate (13 input controls, one scrollable screen, "Salvar", "Sair") | `member` | `/completar-perfil` in the `(auth)` group |
| 7 | "Minhas respostas" and the "Há perguntas novas" notice | `member` | `/perfil` |
| 8 | Answers on another member's profile (public ones for members, all ones for staff) | `member`, `admin_tenant`, `support_tenant` | `/membros/[membershipId]` |
| 9 | The platform panel's module switch row | `super_admin` | `/plataforma/tenants/[id]/modulos` |

Not a screen: a "preview" of the form is surface 6 rendered inside a sheet (UI-D-580), so it costs no new layout.

**What has no UI** (said plainly): the sign-up and join screens do not change (D-580); a push or bell notification when the form changes (Deferred); sections and conditional questions (Deferred); state/city and file answer types (D-591); filtering the member list by answer; answers in the 08.7 reports; a per-question "finalidade" field (D-594); drag-and-drop reordering (UI-D-567); a "Duplicar pergunta" action (Not built).

**Design authority.** `reference/frontend-design/` and `.planning/sketches/MANIFEST.md` have no form builder and no profile questionnaire. Every surface is **[designed]** (UI-04) in the prototype's language (Manrope, `#f5f7fb` ground, white cards, 12px radii, 44px touch targets, the tenant's brand as the single accent) from primitives already ported into `@rede-social/ui` and from the components of Phases 3, 08.7, 09.1 and 09.4. Nothing is ported, so PROTOTYPE.md's porting rules do not apply; its token rules do (no hex, no literal text in TSX).

**Inherited, not re-decided.** Spacing, type scale, colour model, the `(auth)` frame and `AuthBrand` (UI-D-521), the settings hub rows and `Group` (UI-D-269), the underline `Tabs` with `?aba=` (UI-D-513), the rules editor frame (UI-D-280), `BottomSheet` and `ConfirmDialog` with its `children` slot (UI-D-516), the module toggle row and `confirmDisable` extras (UI-D-505, UI-D-527), `ProfileSection`, `ProfileEmptyCard`, `ProgressRing` and the completeness card (2026-10-12), the consent checkbox row (UI-SPEC Auth Pages), `SegmentedControl` (UI-D-206) and the `StatusPill` tones. **Phase 12 declares no new token, no new colour, no new type size and no dependency.**

**Upstream decisions.** `12-CONTEXT.md` D-580..D-596 are LOCKED and honoured; every one is traced in the table "How each locked decision shows up" below. There is no `12-RESEARCH.md` yet. The visual and interaction questions this phase opens are decided as **UI-D-564..UI-D-599**, continuing after `UI-D-563`, the highest id in any UI-SPEC (`grep -rhoE "UI-D-[0-9]+" .planning | sort -t- -k3 -n -u | tail -1` returned `UI-D-563` on 2026-10-29).

**Non-interactive session.** No question could be asked in this run. Every choice that was genuinely open took its recommended default and is repeated in **Pending User Confirmation** (PU-1..PU-14), so the orchestrator can confirm it or overturn it with one line. The sketch gate for this phase is a recommendation, not an approval; no sketch was drawn and no approval was written.

| **UI-D-598** | What the UI never shows or trusts (extends the boundary rules). | Every title, help text, option label, answer and tenant name is **React text**; none is parsed as HTML or markdown, none is linkified except a validated `http(s)` **Link** answer (UI-D-591). The `next` destination and the `?t=` name are never trusted: the first is validated (UI-D-587), the second is only a fallback name rendered as text. Answers are **never** in a URL, a log line, a toast, an analytics event, `localStorage` or `sessionStorage`; the builder shows **aggregate counts only** (answers per question and option), never a member's answer; the admin reads a member's answers only on that member's page. Whether a question is public is read from the API's flag on every render. A staff user, a member of another tenant and a blocked member get the same indistinguishable not-found on every route above. | **UI-D-599** | Limits the UI enforces (Claude's Discretion; **PU-13**). | Defaults, one constant each in `@rede-social/contracts`, which the planner may overturn: **30** active questions per form · **20** options per choice question (plus "Outro") · title **120** · help text **300** · option label **80** · "Outro" text **120** · Texto curto **120** · Texto longo **1000**. ## Data the screens read (for the planner; not a UI decision)

The UI assumes these shapes. Names are proposals; the contract is what is shown and what must never be sent.

- **Bootstrap** gains a profile-form block (for example `profileForm: { pendingRequired: number } | null`, `null` when the module is off or the role is not `member`) so `bootstrapRedirectPath` and the `/perfil` notice need no extra call. The gate error code (name left to the planner; the model is `SUBSCRIPTION_PENDING`) carries `details.tenantName` and maps to `/completar-perfil?t=...`; the destination `next` has to come from somewhere the redirect can see (the failing request's path, a short-lived cookie set by the proxy, or the page that caught the error), the planner decides.
- **Member read** (`GET /v1/me/profile-form`, allowed while gated): `mode` (`first | returning | edit`), `missingRequired` (count), `questions[]` in order, each `{ id, type, title, helpText, required, showOnProfile, options: [{ id, label }], allowOther, min, max, answer }` where `answer` is the stored typed value or `null`. Never the answers of anyone else.
- **Member write** (`PUT /v1/me/profile-form/answers`): the whole screen at once, `{ [questionId]: value }`, validated per question by the discriminated schema in `packages/contracts`; answers `{ errors: { [questionId]: code } }` on refusal; `409` with the fresh question list when the form changed. The value shapes per type (string, number, ISO date, option id, option id list, `{ otherText }`, boolean, 1-5) are the contract's, not the UI's.
- **Notice and profile reads**: `newOptionalCount` and `dismissed` (server state), a dismissal write, the member's own answered list with the public flag. **Public block** (`GET /v1/members/{id}/profile-answers`): public AND answered rows only, `.strict()`, one indistinguishable 404 for every miss. **Staff block**: all rows including archived, with `showOnProfile` and `archivedAt`, `admin_tenant` and `support_tenant`, role `member` targets only.
- **Admin reads**: the active list (`{ id, type, title, required, showOnProfile, position, answerCount, options: [{ id, label, answerCount }], allowOther, min, max }`), the archived list (`archivedAt`, `answerCount`, `required`), the summary (`{ total, complete, hasRequired }`), and an **impact read** per intended change (`n` members who would need to answer). Aggregate counts only.
- **Admin writes**: create, update (with the locked-field refusals as coded errors), reorder (the ordered id list), archive, reactivate (to the end of the list), delete (refused when answers exist), **replace** (create plus archive in one transaction), the export (`GET`, attachment), and the member's dismissal write for the notice (UI-D-589). Each admin write re-checks the module and the composed permission and answers 404 `MODULE_DISABLED` / 403 `FORBIDDEN`.
- **CSV** (D-595; for the planner): one row per member (name, e-mail, one column per question, archived included, headers from the question titles), cells beginning with `=`, `+`, `-`, `@` or a tab neutralised, a row written to `moderation_log` for each export. Recommended for pt-BR spreadsheets: `;` as delimiter and a UTF-8 BOM (**PU-9**).
- **Platform**: the module key is appended last to `TOGGLEABLE_MODULES`, off by default (D-596); the toggle row and dialog need only the two catalog entries and one extras entry.
