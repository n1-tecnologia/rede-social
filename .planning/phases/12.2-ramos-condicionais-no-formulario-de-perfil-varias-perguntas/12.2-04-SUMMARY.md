# Phase 12.2 Plan 04: Pure branch rules, tree normaliser, guard codes and chain SQL fragment Summary

**The pure rules the admin services will call: a bounded, cycle-safe `checkBranch` with a documented first-refusal order over a three-level tree, the lock/dependents/move/archive/reactivate rules, the WR-06 privacy twin, `normalizeToTree`, the PF008-PF010 guard map and the single SQL builder of chain visibility, all added beside the 12.1 code with nothing removed.**

## Accomplishments

- `branch-rules.ts` (new): `checkBranch` judges a branch in this order: unknown branch, opener (in list, in layout, active, not a member of the branch), opener type, values (non-empty, unique, tokens of the opener), cycle, `condition_order` naming the FIRST violated pair in the flattened order, `branch_depth`, `branch_limit` (create only), `public_under_private`. Adjacent steps pass, an empty branch passes, the opener must be strictly before every member.
- Every walk is bounded by `branchDepth + 1` hops with a visited set: `branchLevel`, `branchHeight`, `subtreeOf`, the privacy chain walk and the move/cycle walk. A stored cycle (the shortest loop, a loop of two) and a chain of six all terminate; the cases carry a 1 s timeout.
- `checkBranchEdit` (lock by answer COUNT, set comparison so a reordered set is no change), `dependentBranchesOf`, `checkOpenerChange` (archive, retype, removed referenced option -> `has_dependents` with branches and their active titles), `checkMoveIntoBranch` (locked / unknown / archived / descendant / order / depth with the question's own sub-branches / privacy), `checkArchiveBranch` (`has_dependents` naming the nested openers that hold answers), `checkReactivateBranch` and `checkReactivation` (name the ONE thing to reactivate first: `condition_invalid` + `openerId`, `branch_archived` + `branchId`).
- `publicUnderPrivate` lists the public active questions with a private opener anywhere on the chain, at depth 1, 2 and 3; `branchFactsOf` yields the `{ questionId, openerId }` facts `checkLayoutOrder` consumes.
- `layout.ts` `normalizeToTree` is a thin call to `treeOrder` of the contracts; `addQuestionAfterOpener` is untouched (admin.ts still imports it).
- `lock-rules.ts` `GUARD_CODES` maps PF008, PF009 and PF010; the unmapped example in its test is now `PF099`.
- `visibility-sql.ts`: `branchChainOpenSql` and `questionVisibleSql` emit one correlated `exists` over `public.profile_form_branches` with exactly `branchDepth` (3) levels, one `app.profile_form_answer_tokens` overlap per level, no recursion and no `archived_at`; identifiers are validated against `^[a-z_][a-z0-9_.]*$` and a quote, space, semicolon, cast or placeholder throws.
