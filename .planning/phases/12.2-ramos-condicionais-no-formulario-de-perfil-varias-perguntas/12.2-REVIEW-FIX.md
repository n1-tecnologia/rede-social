### WR-01: Required question moved between branches reopens the form without the impact confirmation

**Status:** fixed: requires human verification (logic change in a counting rule and a UI gate)
**Commit:** `99ee2f7a`
**Files modified:**
- `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.ts`
- `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.test.ts`
- `packages/contracts/src/profile-form.ts`
- `packages/contracts/tests/profile-form.test.ts`
- `packages/core/server/profile-form/admin.ts`
- `packages/modules/profile-form/server/routes.ts` (OpenAPI description)
- `packages/modules/profile-form/README.md`
- `apps/api/tests/integration/profile-form-impact.test.ts` (new case, NOT run, see below)

**Applied fix:** `reopeningOf` now returns a reopening in both holes: (1) a required question already required that goes from branch A to branch B (both non-null); (2) an optional question turned required in the same save that changes its branch (any combination, including none to B and A to none). Both use a new impact kind `move_branch`, appended last to `PROFILE_FORM_IMPACT_CHANGES` (the pinned order of the earlier keys holds). `getImpact` counts, for `move_branch` (needs `questionId`, optional `branchId` = destination, absent means "out of any branch"): members who see the question through the NEW chain, lack an answer, and did not already owe it through the OLD chain. An optional question was owed by nobody, so the old-chain exclusion is skipped; a required question with no branch was owed by everyone, so the count is 0; an archived question is 0. The destination must be an active branch of the tenant (unknown, foreign or archived is the same bare 404 as the other kinds). The existing cases are untouched: `A -> none` of an already required question stays `remove_condition`, unchanged make-required stays `make_required`, entering a branch from none still asks nobody.

Design choice taken (needs the owner's eye): the review offered two shapes (a `move_branch` kind, or passing the draft's `branchId` to `make_required` plus an over-counting `create_required` interim). I chose a new kind because `make_required` cannot tell "no `branchId` sent, use the stored one" from "moved to no branch", and the interim over-counts. The cost is one new value in the public impact contract (a web build that predates the API simply never sends it, and an API that predates the web build would refuse the unknown `change` with 400, which the sheet already treats as "could not calculate, nothing is written", so the failure is closed).

Not changed, as the review noted: the server still does not itself enforce that the confirmation happened (the impact read is a UI gate, T-12-34).

Added 2 assertions in the contracts test (the new tail of the pinned order and the new query shape).

### WR-02: Admin-only label edits and empty-branch creation changed every member's `formEtag`

**Status:** fixed
**Commit:** `8dea04c8`
**Files modified:**
- `packages/core/server/profile-form/member.ts`
- `packages/contracts/src/profile-form.ts` (`answerEtag` accepts a string branch "revision")
- `packages/core/tests/profile-form-etag.test.ts` (new)
- `apps/api/tests/integration/profile-form-save-step.test.ts` (new case, NOT run)

**Applied fix:** `formEtagOf` now hashes, per branch, `id` plus a digest of `opener_question_id` and the SORTED opening values, instead of the admin `revision`; and only for branches that hold at least one ACTIVE question of the form. A rename (the `name` is never an input), a revision bump, the creation of an empty branch and a reordering of the values leave the etag unchanged. A change of opener, of values, or of the active-question set (a question joining or leaving a branch, a question revision) still changes it. A form whose branches are all empty hashes exactly like a form without branches, and a form without branches keeps the exact 12.1 text (the existing integration test that spells out that text is unaffected). The two existing integration tests that expect `form_changed` after a branch edit both change `open_values`, so they stay valid.

**Tests:**
- New `packages/core/tests/profile-form-etag.test.ts`: 4 tests (rename and revision ignored; empty branch and value order ignored; all-empty equals no branches; opener, values, active set and question revision still change it).
- `packages/core` full suite: 109 files, 1699 tests passed. `packages/contracts`: 525 passed. `tsc --noEmit` clean in contracts, core, api.
- NOT run: a new integration case in `profile-form-save-step.test.ts` (a PATCH that only renames the branch leaves the member etag unchanged and the in-flight save is not a 409). Typechecks, never executed.
- The integration case for "empty-branch creation" was not added (the unit test covers it; the route-level case would need another fixture).

**Applied fix:** `publicAnswersOf` adds `questionVisibleSql({ question: 'q', tenant: 'a.tenant_id', member: 'a.membership_id' })` to its WHERE; the export joins `profile_form_questions q` inside the per-member answers aggregate and adds the same fragment keyed to `m.id`. Archived questions keep their cells (the fragment has no `archived_at` test). `staffAnswersOf` is deliberately unchanged (staff already get the "Nao se aplica" rendering and see every stored row).

Point worth the owner's attention: `publicAnswersOf` runs under the VIEWER's row-level policy, and `profile_form_answers_public_select` shows the viewer only answers to public, non-archived questions. The fragment reads the target's answers to the OPENERS on the chain under that same policy. For a public question every opener on its chain is public (PFORM-53), so the check resolves correctly; a legacy public question under a private opener now reads as closed and is hidden, which is the safe direction. This is documented in the function's comment. The export runs on the admin lane (RLS off), where the fragment sees every opener.

### WR-04: Edited-branch sheet vanishes when another admin archives or undoes the branch, leaving `branchOpen` stuck true

**Status:** fixed
**Commit:** `2479f73a`
**Files modified:**
- `apps/web/app/(app)/configuracoes/formulario-de-perfil/QuestionBuilder.tsx`
- `apps/web/app/(app)/configuracoes/formulario-de-perfil/builder.test.tsx`

**Applied fix:** an effect in `QuestionBuilder` detects "a branch is being edited but is no longer in the read as active" and calls `setBranchOpen(false)` and `setBranchOpening(null)`. `sheetShowing` therefore goes false (so the existing focus-restore effect runs for a sheet opened from the Fluxo) and the sheet cannot remount by itself if the branch is later reactivated.

Deviation from the review's suggestion, for the owner: the review also asked to "surface the existing 'gone' toast". There is no such string for branches in the pt-BR catalog; the existing `gone` handling in `BranchSheet` (undo, archive) refreshes and closes silently. I matched that and added no copy. If a toast is wanted it needs a new message and a copy decision. The unsaved name/answers draft is still dropped with the sheet (as with every other "gone" answer); no unsaved-changes prompt was added.

**Tests:**
