### Locked Decisions

**What a branch is**
- **D-640:** A branch is its own tenant-owned object: a row with an opener question, the set of answers that open it (the same token shape as 12.1's `condition_values`: option ids, or `true` / `false` for yes/no; ANY of them opens it) and an optional name. The condition moves from the question to the branch (reverses D-621). A question points at its branch; the question no longer carries a condition of its own. — **Reversibility:** costly — a new table, a new column on the questions, the SQL gate, the contracts, the guard, the move order and the whole builder read this shape, and it fans out to every tenant project.
- **D-641:** A question belongs to AT MOST ONE branch; a question with no branch is always visible. A question inside a branch may itself be the opener of another branch: nesting is derived from where the opener lives, there is no separate parent column. The opener must come strictly BEFORE every question of its branch (D-623 generalised to the tree). — **Reversibility:** costly — same shape as D-640.
- **D-642:** The branch name is OPTIONAL (short, same limits as a step title). With no name, the diagram and the lists write a label from the condition ("Se «Qual é o seu perfil?» for «Tenho clínica»"); a name replaces that label. — **Reversibility:** reversible — presentation plus one nullable text column.
- **D-643:** The questions of one branch may sit in DIFFERENT steps; each keeps its own step. The branch only imposes the condition. So the clinic case works as 12.1 intended: the opener in "Informações gerais", the block in a step "Sua clínica" that disappears by itself when the branch is closed (D-628 unchanged). — **Reversibility:** reversible.

**Branches inside branches**
- **D-644:** Maximum depth is 3 levels of branch (a branch in a branch in a branch). The number lives in `PROFILE_FORM_LIMITS` and in a database check that reads it, like the other limits; raising it later is a small migration. A question is visible when EVERY branch on its chain is open (the opener of each branch is visible and holds an answer from that branch's set). The gate `app.profile_form_missing` stays a fixed-size join, no recursion. Reverses D-622. — **Reversibility:** costly — the gate runs on every member request and its twins are published to every tenant project.
- **D-645:** D-624 and D-636 (stored equals visible) are EXTENDED down the chain: when the member's change closes a branch, the answers of every question in that branch AND in every branch below it are deleted in the same transaction, active and archived. The erase dialog of D-626 lists the titles of the ACTIVE closed questions that had answers. — **Reversibility:** costly — same promise as 12.1 (no reader needs a visibility filter), now over a tree.
- **D-646:** The locks of 12.1 extend to branches. A branch with any answered question cannot change its opener or its set of answers; a question with answers cannot be moved into or out of a branch; removing a condition ("Desfazer ramo", D-653) stays allowed. An opener cannot be archived, retyped or lose a referenced option while a branch hangs on it (D-632), and the 409 lists the dependent branches and their questions. — **Reversibility:** reversible — they are refusals plus guard codes; relaxing them is a service rule.

**The diagram ("Fluxo")**
- **D-647:** The diagram is a **"Fluxo" view inside the builder**, a Lista | Fluxo selector over the same data. No new route; the list of today stays as it is. — **Reversibility:** reversible.
- **D-648:** The diagram is READ-ONLY. Tapping a question or a branch opens the existing edit sheet of the builder. Dragging, wiring and creating branches inside the drawing are out of scope. — **Reversibility:** reversible — adding edit-in-place later is additive.
- **D-649:** The drawing is a VERTICAL TREE, top to bottom, indented one step per branch level, with the answer(s) that open the branch written on the connection. It must fit 390px without sideways scroll and not break at 320px (PFORM-42). — **Reversibility:** reversible.
- **D-650:** The sketch gate applies (UI-04, D-635): a new sketch 019 covers the branch UI of the builder, the "Fluxo" view, the branch sheet, the refusal lists, and any change to the stepper reveal and the preview. The executor never writes the approval; no web code before it is on disk. The design questions Igor did not answer in 018 stay his to answer in 019. — **Reversibility:** reversible.

**Building a branch in the builder**
- **D-651:** A branch is created FROM the opener question: any question that can open (dropdown, multiple choice, single choice, yes/no, D-620) offers "Criar ramo"; the admin picks the opening answers, may give a name, and adds questions inside. The branch shows indented right under the opener. An existing question WITHOUT answers can be moved into a branch from its edit sheet. — **Reversibility:** reversible — presentation.
- **D-652:** ORDER is the tree. Inside each step, the questions of a branch stay consecutive, right after the opener when both are in the same step; a branch moves as a block; a nested branch sits inside its parent's block; every reorder rewrites positions to follow the tree. This subsumes quick 261106-ei5 ("a new conditional question lands right after its opener"), whose placement helper is replaced. — **Reversibility:** costly — the layout engine, the reorder and move routes and the tenant-move order change.
- **D-653:** Two actions on a whole branch. "Desfazer ramo": the questions stay and become always visible (removing a condition is allowed, D-625; required ones reopen the form for members who lack the answer, and the impact dialog counts them). "Arquivar ramo": archives the branch and every question inside it; refused when one of those questions opens another branch that has answers. — **Reversibility:** reversible.

## Summary

Phase 12.2 moves the profile-form condition from the question (12.1: `condition_question_id` + `condition_values`) to a new `profile_form_branches` row and adds `branch_id` to the questions. Everything in 12.1 that assumed "an opener carries no condition" is rewritten to walk a chain of at most 3 branches: the SQL gate `app.profile_form_missing`, the purge `app.profile_form_purge_closed`, the guard (PF006/PF007), the pure rules (`condition-rules.ts` becomes branch rules), the layout engine (positions follow the tree), the visibility function with its parity table, the summary/impact/new-optional counts that re-state the gate in TypeScript, the tenant-move order, and the whole builder. The member stepper, erase dialog, one-scroll edit, readers and the CSV are unchanged in shape; they only follow the new visibility rule.

The five findings that shape the plan: (1) **nothing in the repo ever stores a condition outside tests**: seeds do not mention the profile form, the module is not in the default set of a new tenant and only a `super_admin` can turn it on, so expand-only is safe, and a lossless in-migration conversion of any legacy condition into a branch makes the plan correct even if Igor's read-only hosted check finds a row. (2) **The branch table and the questions table reference each other**, which `orderTables` refuses unless every constraint inside the cycle is DEFERRABLE; the `events`/`event_secrets` precedent (hand-written `DEFERRABLE INITIALLY IMMEDIATE`/`DEFERRED` foreign keys, kept out of the Drizzle schema, copied as one group under `set constraints all deferred`) is the route, and it also removes WR-03 for the new model because the copy no longer depends on any row order. (3) **The gate stays a fixed join:** `q` left-joined to `b1`, `o1`, `b2`, `o2`, `b3` (five unique-index joins), "every branch on the chain is open" is a plain AND, and the stale-deeper-answer case is correct without recursion; the purge uses the same predicate negated and MUST NOT read the archive flag of a branch (it would erase archived answers). (4) **The lock order grows by one table:** steps, then questions in `position, created_at, id`, then branches; the member save must lock the branches `FOR SHARE` too, or an admin could change a branch's answers under a member's in-flight answer. (5) **WR-06 has a clean database-level answer** (a whole-tenant AFTER trigger, PF009) and the UI-SPEC default PU-1 "refuse" matches the code: today a public question's answer is exposed to every member by RLS policy `profile_form_answers_public_select`, so the only place to close the leak is the write.

**Primary recommendation:** ship in the 12.1 shape: contracts and pure rules first, then ONE generated migration plus ONE hand migration (FKs, functions, conversion and triggers in a single transaction so the gate swap and the conversion commit together), the API in three plans, the pure web logic, and only then the web plans behind sketch 019. 17 plans in 11 waves (12.1 had 19 in 13); server, SQL and contract plans never wait for the sketch.

### Pattern 1: the unrolled chain predicate (gate; the purge is its negation)

**What:** visibility = AND over the chain of `open(branch)`. The opener of each branch is visible exactly when the branches above it are open, so no separate "opener visible" test and no recursion are needed. [ASSUMED: derivation; to be proven by the chain parity table]
**When to use:** `app.profile_form_missing`, `app.profile_form_purge_closed`, and (as one TS builder) the summary, impact and new-optional queries.
**Example (design sketch, NOT executed; proof is pgTAP 226):**

```sql
-- app.profile_form_missing: only branch 3 of the CASE changes; cases 1 and 2 stay byte-identical.
select count(*)::int
from public.profile_form_questions q
left join public.profile_form_branches b1 on b1.tenant_id = q.tenant_id  and b1.id = q.branch_id
left join public.profile_form_questions o1 on o1.tenant_id = b1.tenant_id and o1.id = b1.opener_question_id
left join public.profile_form_branches b2 on b2.tenant_id = o1.tenant_id  and b2.id = o1.branch_id
left join public.profile_form_questions o2 on o2.tenant_id = b2.tenant_id and o2.id = b2.opener_question_id
left join public.profile_form_branches b3 on b3.tenant_id = o2.tenant_id  and b3.id = o2.branch_id
where q.tenant_id = p_tenant and q.required and q.archived_at is null
  and not exists (select 1 from public.profile_form_answers a
                   where a.tenant_id = q.tenant_id and a.membership_id = p_membership and a.question_id = q.id)
  and (q.branch_id is null or (
        exists (select 1 from public.profile_form_answers x
                 where x.tenant_id = q.tenant_id and x.membership_id = p_membership
                   and x.question_id = b1.opener_question_id
                   and b1.open_values && app.profile_form_answer_tokens(x.value))
    and (b2.id is null or exists (select 1 from public.profile_form_answers x
                 where x.tenant_id = q.tenant_id and x.membership_id = p_membership
                   and x.question_id = b2.opener_question_id
                   and b2.open_values && app.profile_form_answer_tokens(x.value)))
    and (b3.id is null or exists (select 1 from public.profile_form_answers x
                 where x.tenant_id = q.tenant_id and x.membership_id = p_membership
                   and x.question_id = b3.opener_question_id
                   and b3.open_values && app.profile_form_answer_tokens(x.value)))))
```

Notes the planner must carry: (a) `b3` is the deepest level because PF008 forbids a fourth; the join depth equals `PROFILE_FORM_LIMITS.branchDepth`, and a drift test must assert it (see Pitfall 9). (b) A dangling `branch_id` (cannot happen: composite FK) makes `b1.opener_question_id` null, `exists` false, so the question is not owed (fail closed). (c) The purge is `delete from answers a using memberships m, questions q left join ... where q.branch_id is not null and not (open(b1) and ...)` with `a.tenant_id/membership_id` instead of `q.tenant_id/p_membership`, `returning a.question_id`. (d) NEITHER may test `branches.archived_at`: archived questions are excluded by `q.archived_at`, and the purge must keep the answers of archived questions that sit in an archived branch (Pitfall 3).

### Pattern 2: tree order = stable pre-order of a forest, computed by one pure function

**What:** `treeOrder(layout, facts)` where `facts` gives each question's `branchId` and each branch's `openerQuestionId`. Per step: `parent(q)` = the opener of q's branch when that opener is in the same step, else ROOT. Result = pre-order of the forest in which: children of an opener are grouped by branch into runs; a run is contiguous; a question is immediately followed by its own block; sibling runs/units are ordered by the minimum requested index of their members, members of a run by requested index. Foreign-opener runs (opener in another step) are root units like an unconditional question. Idempotent; O(n log n) on at most 30 questions. [ASSUMED: algorithm; the contract is D-652 and UI-SPEC planner item 4 "end of the branch's run in the question's own step, else end of the step"]
**Where it runs:** the builder computes the layout it PUTs with it (arrows move a unit, never change a branch); `reorderQuestions`, `createQuestion`, `updateQuestion`, `reactivateQuestion` run it on the server before `assertLayoutOrder` + `writeLayout`. A normal client request is a no-op for the server's normalisation; any other request is rewritten, which is D-652 ("every reorder rewrites positions to follow the tree").
**D-623/D-641 check after normalisation:** `checkLayoutOrder(facts)` with one fact `(question, its branch's opener)` per active question in a branch. Transitivity covers nested chains, so one fact per question suffices. A same-step violation cannot survive normalisation; only a cross-step one (opener's step after the question's step) is refused with `condition_order`.
**Sibling order of EMPTY branches:** an empty branch has no question to give it a place; order empties by `created_at, id` after the non-empty runs of the same opener (no `position` column on branches). [ASSUMED: planner may prefer a column; see Open Question 5]

### Pattern 3: one TS builder for the chain predicate (do not re-state it five times)

12.1 re-stated the gate in TypeScript in `getSummary`, `SEES_THROUGH`, `LACKS_ANSWER`/`getImpact` and `newOptionalCount` (admin.ts:1123-1266, member.ts:82-117), guarded only by a drift test. With a 5-join chain this would be copied four times. Create `visibility-sql.ts` exporting a function that returns the SQL fragment for "member `m` sees question `q`" (aliases passed in), used by all four, and extend the existing integration drift test (summary `complete` equals members the gate releases) to depth 3. [VERIFIED: admin.ts:1132-1139 says "the integration test asserts the two never drift"]

### Anti-Patterns to Avoid
- **Recursive CTE or PL/pgSQL loop in the gate:** locked out by D-644 and unnecessary at depth 3.
- **A `depth` or `parent_branch_id` column:** nesting is derived (D-641); a stored depth drifts when an opener moves into a branch.
- **Reading `branches.archived_at` in the purge:** erases kept answers (Pitfall 3).
- **Silent re-parenting on "Desfazer ramo" of a nested branch:** see Open Question 1; the literal D-653 is "always visible".
- **`ON DELETE SET NULL` on `questions.branch_id`:** an accidental branch delete would silently widen visibility; keep NO ACTION (DEFERRABLE INITIALLY IMMEDIATE).

### Item 3. The circular FK pair in the move/copy engine (and WR-03)

**Why it fails today if left naive.** `orderTables` builds the parent->child graph from `pg_constraint`; a strongly connected group of more than one table is allowed only when every constraint between its members is `condeferrable`, otherwise `unsortable_tables`. [VERIFIED: fk-order.ts:141-152: `const hard = pairs.some((edge) => members.has(edge.child) && members.has(edge.parent) && !edge.deferrable); if (hard) refused.push(...group);`] A self-reference is allowed only for a table in `SELF_REF_ORDER`: [VERIFIED: fk-order.ts:25-32 `feed_comments: 'parent_depth'` and `profile_form_questions: 'condition_question_id'`]. A `branches.opener_question_id -> questions` plus `questions.branch_id -> branches` pair with ordinary FKs is therefore refused.

**Route (recommended).** Declare **both** new foreign keys `DEFERRABLE INITIALLY IMMEDIATE`, hand-written, outside the Drizzle schema, exactly as `events`: [VERIFIED: 20260927145318_events.sql header "HAND-WRITTEN: the two foreign keys ... drizzle-kit cannot express DEFERRABLE, so they cannot live in the TS schema; they are absent from the snapshot `drizzle-kit generate` diffs against"; `ALTER TABLE "event_secrets" ADD CONSTRAINT "event_secrets_event_fk" ... DEFERRABLE INITIALLY DEFERRED`]. Then `orderTables` returns one group `['profile_form_branches', 'profile_form_questions']` (sorted by name) and `copyRows` runs it in one target transaction under `set constraints all deferred`. [VERIFIED: copy-rows.ts:107-123; the same group handling exists in `delete-source.ts:113-115` and `rollback.ts:289-291`, so the source delete and the rollback need no change.] `INITIALLY IMMEDIATE` keeps ordinary API writes checked at end of statement as in 12.1; only the move opts into deferral. `SET CONSTRAINTS ALL` affects only deferrable constraints. [CITED: postgresql.org/docs/current/sql-set-constraints.html — "`SET CONSTRAINTS ALL` changes the mode of all deferrable constraints."]

Consequences the plan must carry:
- Any hand-written `DELETE` in a fixture/cleanup (`setup.ts`, `platform-reviewer.test.ts:97-103`, `isolation.test.ts`) that removes questions and branches in separate statements now violates a FK at statement end unless run in a transaction with `set constraints all deferred`. Provide one helper `deleteProfileFormTenantData(tenantId)` in the integration `setup.ts` and use it everywhere. (The same thing already forced "steps after questions" in `platform-reviewer.test.ts`.)
- Row order inside the group no longer matters, so **WR-03 is closed for the new model at any depth** (a chain through archived dependents can no longer break a move). The legacy self-reference `profile_form_questions_condition_fk` stays one release with its `SELF_REF_ORDER` entry (the stale columns can still hold a chain only if someone wrote them, and PF010 now forbids that); the cleanup migration removes both. Expected effect on tests: `packages/core/tests/move-fk-order.test.ts` gains a case "a deferrable pair `profile_form_branches` <-> `profile_form_questions` is one group and the planner raises no `unsortable_tables`", the existing `Object.keys(SELF_REF_ORDER)` pin at lines 147-148 is unchanged until the cleanup, and `apps/api/tests/integration/move-copy.test.ts:327-331` pin `expect(plan.tables.length).toBe(55)` becomes 56 with `toContain('profile_form_branches')`. A real-copy case (like `move-copy.test.ts:994-1130`) with a depth-3 tree whose ids sort adversarially (deepest opener id `ffff…`, dependents `0000…`) proves the copy and the answers.
- Triggers: `copyRows` disables user triggers of the group tables during the copy (`alter table ... disable trigger user`), so the new guards and the default-step trigger do not fire on a copy. [VERIFIED: copy-rows.ts:111-120]

**Alternative considered and rejected:** keep `branches.opener_question_id` without a foreign key and validate with a trigger (acyclic graph, no engine change). It breaks the project rule that every tenant reference is a composite FK and gives up Postgres's own catch of a bad id.

## Common Pitfalls

### Pitfall 1: missing one of the places that read the condition
**What goes wrong:** a reader keeps the old single-level predicate, so one surface disagrees with the gate (the admin summary says 40 members complete, the gate holds 12).
**Why:** 12.1 re-stated the gate in TS four times and in SQL twice. **How to avoid:** the plan carries a checklist grep, `rg "condition_question_id|conditionQuestionId|condition_values|conditionValues"` over `apps packages supabase` (about 37 files today across apps, packages, supabase and docs, including 3 drizzle snapshot files; found by this session's grep), and the final plan asserts the only remaining hits are the retired columns' schema line, the conversion, the PF010 guard and the cleanup list. The shared `visibility-sql.ts` and the chain parity table are the structural cure.
**Warning signs:** `getSummary().complete` differs from the number of members `profile_form_missing` releases (the existing drift test, extended to depth 3).

### Pitfall 2: stale deeper answers
**What goes wrong:** a member changes the top answer; sub-opener answers still exist in the snapshot; a naive "opener has an answer" test keeps depth 2 and 3 visible. **How to avoid:** the AND over the whole chain (Pattern 1), the case `Q1=trabalha, Q2=true, Q5=true -> only Q1 visible` in the chain parity table, and the purge deleting those rows in the same transaction.

### Pitfall 3: the purge erases archived answers
**What goes wrong:** if the purge (or a shared `open()` helper) tests `branches.archived_at`, "Arquivar ramo" followed by any member save deletes the archived answers D-588 promises to keep. **How to avoid:** openness = opener answer overlaps the set, nothing about archive state; archived questions are filtered by `q.archived_at` in the gate only. A pgTAP case: archive a branch with answered questions, run the purge as the member, assert the archived answers survive while a *really* closed one is deleted.

### Pitfall 4: archive order trips PF007
**What goes wrong:** "Arquivar ramo" updates the opener question of an inner branch to archived while the inner branch is still active -> the guard raises PF007. **How to avoid:** inside the one transaction update the branches first (`archived_at = now()` for the whole subtree), then the questions. Use the SAME `now()` for the cascade: it identifies the cascade set on "Reativar ramo" (`archived_at = branch.archived_at`), so a question archived alone earlier (different instant) stays archived, as UI-D-674 requires.

### Pitfall 5: member save vs admin branch edit
**What goes wrong:** the member's `FOR SHARE` on questions does not conflict with an admin `UPDATE` of a branch row, so an admin can change a branch's answers while a member inserts an answer to a question of that branch; both commit and the lock D-646 is violated (the guard cannot see an uncommitted insert). **How to avoid:** `lock_branches()` in the member save and `readLayout(... lockRows)` locking branches after questions; the branch guard checks answers after its row lock; add a concurrency test next to `profile-form-concurrency.test.ts`.

### Pitfall 6: cleanup and fixtures
**What goes wrong:** every helper that deletes a tenant's profile-form rows (`setup.ts`, `platform-reviewer.test.ts:97-103`, isolation sweeps, `seedProfileFormQuestion`) breaks on the circular pair. **How to avoid:** one deferred-constraints helper (Item 3), and rewrite `seedProfileFormQuestion({ conditionQuestionId, conditionValues })` to `branchId` plus a new `seedProfileFormBranch`.

### Pitfall 7: pgTAP conventions
`supabase/tests/220-profile-form.sql:123` has `columns_are('public', 'profile_form_questions', array[... 'step_id','condition_question_id','condition_values'])`: add `'branch_id'`. `040-schema-conventions.sql:295-304` pins which `app` functions may contain `limit 1`: write none. `040` also checks every tenant table is indexed tenant-first: the branches indexes start with `tenant_id`. `225-profile-form-steps-conditions.sql` (937 lines, `plan(218)`) builds its tenant A and B fixtures with `tests.pf_q(..., p_cond, p_vals)` (lines 95-120) and sections 3, 6, 10 and 11 assert on them: after PF010 those inserts raise at fixture time, so move the condition fixtures and assertions (sections 3, 6, 10, 11) to the new `226-profile-form-branches.sql` with branch fixtures, and keep sections 1, 2, 4, 5 (token helper, unchanged), 7, 8, 9, 12 of 225 (steps, token helper, default-step trigger, backfill, layout statement, lock_v2) on unconditional fixtures. Update both `select plan(N)` counts.

### Pitfall 9: the depth literal drifts from the constant
The trigger SQL has a literal depth (4-join test, "3" in comments and messages). ### Pitfall 10: the "Outro" and any-of token rules
"Outro" has no option id and opens nothing (12.1 CHECK comment, contracts case 'Outro on a single choice opens nothing'). ### Pitfall 11: the 12.1 "Etapa" snap-back and the branch select

### Contract skeleton (pure; browser-safe)

```ts
export type ProfileFormBranch = { id: string; openerQuestionId: string; values: readonly string[] };
export function isQuestionVisible(
  question: { branchId: string | null },
  tree: {
    branch: (id: string) => ProfileFormBranch | undefined;
    branchIdOf: (questionId: string) => string | null | undefined; // undefined = unknown question
  },
  tokensOf: (questionId: string) => readonly string[] | undefined,
): boolean {
  let branchId = question.branchId;
  for (let hops = 0; branchId !== null; hops += 1) {
    if (hops >= PROFILE_FORM_LIMITS.branchDepth) return false; // deeper than the limit: fail closed
    const branch = tree.branch(branchId);
    if (branch === undefined) return false;
    const tokens = tokensOf(branch.openerQuestionId);
    if (tokens === undefined || !branch.values.some((value) => tokens.includes(value))) return false;
    const next = tree.branchIdOf(branch.openerQuestionId);
    if (next === undefined) return false;
    branchId = next;
  }
  return true;
}
```
This replaces the 12.1 function quoted at profile-form.ts:401-408. The loop is a bounded walk, not recursion, and mirrors the SQL join level for level (the parity table is what keeps the two equal).
