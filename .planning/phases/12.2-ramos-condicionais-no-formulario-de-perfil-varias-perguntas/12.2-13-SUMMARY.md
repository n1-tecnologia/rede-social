## Accomplishments

- **Task 1 (tracer).** `visibility.ts` keeps every exported name and signature and now reads `form.branches ?? []` and each question's `branchId` through `isQuestionVisibleInTree`; `isNotApplicableInTree(row, rowsById, branches)` is the staff twin. `branch-tree.ts` builds, from the admin read, the per-step Lista structure (`stepTree`: root questions, under each opener the runs of its branches, a run per step, nested to three levels, foreign-opener runs among the roots, empty branches last) with `countsOf`, `opensCountOf`, `referencedOptionCounts`, `branchChain`, `branchLevel` and `branchHeight`. `describe-branch.ts` gives the label parts (unnamed: condition parts; named: the name plus the same parts) and `capAnswers`. - **Task 2.** `eligibleBranchesFor`, `eligibleOpenersFor`, `publicUnderPrivateTitles` and `flowTree` in `branch-tree.ts`; `branch-layout.ts` with `layoutOf`, `treeLayoutOf`, `moveUnit`, `moveBranchRun`. Every move result is checked to keep the id multiset and step of every id, to be a fixed point of `treeOrder`, and to keep each opener before its questions.
- **Task 3.** `steps.ts` types accept `branches`; the condition cases of `steps`, `form-state` and `profile-reads` tests are ported to branches with new nested-block and closed-chain cases; `validateAll` and `wireAnswers` take the form's branches; `loadMemberAnswers` gives the staff payload an always-present `branches` list; `loadAdminForm` and `loadArchived` return the branches of their reads.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] `validateAll` and `wireAnswers` take the form's branches**
- **Found during:** Task 3
- **Issue:** both take only `questions`; with the chain rule failing closed, every question that names a branch would be hidden, never validated and left out of the save body. The plan names `mergeFreshForm` and the loaders but not these two.
- **Fix:** an optional fourth parameter `branches` (additive, no caller breaks). `flaggedIds` and the step types accept `branches` too.
- **Files modified:** `form-state.ts`, `steps.ts`
- **Commit:** `0a6f62c2` (RED signature in `2b698c55`)

**2. [Rule 3 - Blocking] `turbo typecheck` not used**
- The plan's Task 3 verify names `pnpm turbo typecheck --filter=@rede-social/web`, whose task graph depends on `^build` (forbidden). `cd apps/web && pnpm exec tsc --noEmit` was run instead, exit 0 after every task.

**3. [Additive] `loadArchived` also returns `activeBranches`; `moveBranchRun` takes an optional `stepId`**
- The plan says `loadArchived` returns `branches`; reactivation needs the active list's branches too, so they come apart under `activeBranches`. A branch with questions in several steps has a run per step, so `moveBranchRun(layout, tree, branchId, direction, stepId?)` names the step (default: the first step that holds one).

**4. [Fixture detail] `clinicAdminList()` is stored in tree order**
- The contracts' clinic fixture lists Q1..Q7, which is not a tree order (Q3 sits after Q6's block). The server always stores tree order, so the admin fixture is `Q1, Q2, Q4, Q5, Q6, Q3, Q7`. `clinicForm()` keeps the contracts' order (visibility does not depend on it).

**5. [Interpretation] "a new question after Q1"**
- The plan's behavior line lists B1 and B4 for "a new question after Q1". A new question lands at the end of its step (D-646), so on the full clinic fixture it may enter all four branches (B1, B4, B2, B3 in opener order); the B1-and-B4 case is tested on a form where only Q1 precedes.

**Total deviations:** 5 (1 missing critical, 1 tooling, 2 additive, 1 interpretation, 0 scope creep).
