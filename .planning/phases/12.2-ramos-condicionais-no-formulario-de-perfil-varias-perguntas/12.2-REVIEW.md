# Phase 12.2: Code Review Report

**Reviewed:** 2026-11-06
**Depth:** standard (with targeted cross-file tracing of the privacy, lock-order, SQL-gate and move-engine paths)
**Files Reviewed:** 53
**Status:** issues_found

## Summary

I traced the five risk areas you named against the code. No Critical (BLOCKER) defect was found. What I verified as sound:

- **Name privacy.** The branch name is selected only in `branches.ts` (`readBranches`, `readRuleFacts`) and `layout-store.ts`, all behind `profile_form.manage` (`admin_tenant`). The member path (`member.ts` `readBranches`, `lockBranches`, `profile_form_lock_branches()`) never selects it, and `memberBranchSchema.parse` is `.strict()` on both the member and the staff payload. `describe-branch.ts` and `branch-tree.ts` are imported only from the admin builder directory. `export.ts` and `csv.ts` contain no reference to branches.
- **Authorization.** All 17 branch and question routes carry `requireModule` plus `requirePermission('profile_form.manage')`. Ids reaching `actions.ts` are uuid-validated before they are interpolated into a path.
- **SQL functions.** Every new function sets `search_path = ''`, takes tenant and member from the session claims, and revokes PUBLIC. The gate keeps its `api_user` and `service_role` only grant. The 3-level join in the gate, in the purge and in `visibility-sql.ts` agree with each other and with `branchChainOf`. PF008 (4 branches in a chain, or a cycle) is exactly the complement of what the gate and purge unroll, so a storable row is always evaluated identically in SQL and TypeScript.
- **Lock order.** Member save locks questions then branches (share). Every admin write that can touch either takes steps, then questions, then branches. `updateBranch` takes branches only, with no question lock, so there is no cycle. The deadlock analysis with the per-member advisory lock also holds.
- **Move engine.** The `set constraints all immediate` flush is guarded by the same `group.length > 1` condition as the `deferred` it undoes, runs inside the same transaction before triggers are re-enabled, and on any violation aborts and rolls back the whole group. Single-table groups are untouched. Semantics are unchanged: it only moves the commit-time check earlier.
- **Conversion.** `distinct (tenant, opener, sorted values)` is lossless for legacy rows and idempotent, because the loop selects only rows with a condition and no branch.

The findings below are what a green suite cannot see: one missing read-side layer on the privacy-critical read, one UI contract hole around the "reopening" confirmation, one etag side effect of an admin-only label, one unreachable documented guard, and smaller items.

## Warnings

### WR-01: Required question moved between branches (or made required while moving) reopens the form without the impact confirmation, or with the wrong count

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.ts:490-507` (with `packages/core/server/profile-form/admin.ts:1468-1482`)
**Issue:** `reopeningOf` is the only gate that forces the member-impact read before a write that can hold members back (the T-12-34 contract: "a reopening change is never applied on a guess"). It has two holes, both verified by reading the function:

1. Required question already required, `stored.branchId = A`, `draft.branchId = B` (both non-null). The function falls through every branch and returns `null`, so `write(false)` runs with no count and no dialog. Members for whom B is open and A is closed (and who therefore have no answer, because a question with answers cannot change branch) now owe a required question. Only the `A -> none` case (`remove_condition`) is covered.
2. Question optional becoming required in the same save that changes its branch. The function returns `make_required` with only `questionId`; the server (`getImpact`, line 1468) scopes the count by the STORED `row.branch_id`, not the branch the draft is moving to. Leaving a branch in the same save means every member owes it but the count only covers those who saw it under the old chain; moving A -> B counts the wrong population.

The server does not enforce the confirmation, so nothing downstream catches either case.
**Fix:** In `reopeningOf`, treat any change of `branchId` of a question that ends up required as reopening: for `stored.required && draft.required && (stored.branchId ?? null) !== (draft.branchId ?? null)` return a reopening whose count is of members who see the NEW chain and do not see the old one (extend `getImpact` with a `branchId` for `make_required` / a `move_branch` kind that counts `seesBranch(new) and not seesBranch(old) and lacksAnswer`). For `make_required` combined with a branch change, pass the draft's `branchId` and have the server count with that branch instead of the stored one. Cheap and safe interim: use `create_required` with the destination `branchId` (over-counts, never under-counts).

### WR-02: Admin-only label edits and empty-branch creation change every member's `formEtag`, forcing a `form_changed` 409 on in-flight saves

**File:** `packages/core/server/profile-form/branches.ts:367-374` and `250-259`; `packages/core/server/profile-form/member.ts:279-300`, `372`, `510`
**Issue:** `updateBranch` does `revision = revision + 1` for any change, including a name-only edit, and `createBranch` inserts a new ACTIVE branch. The member etag hashes `id:revision` of every active branch (and appends a whole `;branches=` segment once the first branch exists). Therefore renaming a branch (a label members never see, by D-642) or creating an empty one invalidates the form identity of every member with the form open: their next save returns 409 `form_changed` with the fresh form. No data is lost (`mergeFreshForm` keeps drafts), but the admin-only label now has a member-visible, tenant-wide side effect, and in a tenant with many members it is a burst of 409 responses plus the "form changed" notice for a no-op change to them.
**Fix:** Keep `revision` as the admin-to-admin optimistic lock but build the member etag from member-relevant content only: for branches hash `id:openerQuestionId:sorted(values)` (archived ones are already excluded), not `revision`. An empty branch contributes nothing a member renders, so also skip branches that have no active question.

### WR-03: The read side of the privacy promise has no chain-visibility backstop; "stored equals visible" is protected only by the member's own write-side purge

**File:** `packages/core/server/profile-form/answers.ts:110-119` (member-to-member public read); `packages/core/server/profile-form/export.ts` (no branch reference, confirmed by search)
**Issue:** `publicAnswersOf` returns every answered, `show_on_profile`, non-archived answer of the target member, and the CSV export returns every stored answer. Neither applies the branch-chain predicate. Hidden-branch answers are kept out only because `app.profile_form_purge_closed()` runs inside the member's own `saveAnswers`. I traced the write paths and found no way to break the invariant today (opener changes always go through `saveAnswers`, the per-member advisory lock serialises two saves, PF006 forbids moving an answered question into a branch, and admin opener/value edits are frozen once any question of the branch has an answer). But this phase is exactly the one where a second visibility layer was added (`questionVisibleSql`, built to take a membership column), and the two readers that disclose data to OTHER people do not use it. Any future missed purge path (a restore, an import, a new admin tool, a migration that edits tokens) becomes a disclosure of a branch-closed answer, to other members and to the CSV, with nothing to catch it. The project's own convention is three layers.
**Fix:** In `publicAnswersOf`, join the target and add `and ${sql.raw(questionVisibleSql({ question: 'q', tenant: 'a.tenant_id', member: 'a.membership_id' }))}`. Apply the same predicate to the export query (staff already get a "Não se aplica" rendering client-side, but the CSV should not carry a closed-branch cell). Cost is the same unique-index probes the summary already uses.

### WR-04: Edited-branch sheet vanishes when another admin archives or undoes the branch, leaving `branchOpen` stuck true and focus lost

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/QuestionBuilder.tsx:198-204`, `221-226`, `310-322`
**Issue:** `editedBranch` is `branches.find(... && archivedAt === null)`. When a refresh brings the branch back archived or deleted, `editedBranch` becomes `undefined` and `<BranchSheet>` unmounts mid-edit. Nothing resets `branchOpen`, so `sheetShowing = open || branchOpen` stays true: the focus-restore effect (`trigger.focus()` for a sheet opened from the Fluxo) never runs, the keyboard user lands on `<body>`, the admin's unsaved name/answers draft disappears with no message, and the next `openEditBranch` works only because it also sets `branchOpen(true)` again. The comment on line 220 says "closes the sheet", but it unmounts it instead of closing it.
**Fix:** Derive the close instead of unmounting: when `branchOpening?.branch` is set and `editedBranch` is `undefined`, call `setBranchOpen(false)` from an effect (and `setBranchOpening(null)` after the exit animation) and surface the existing "gone" toast, so the focus-restore effect and the discard path both run.

## Info

### IN-01: `deleteQuestion` and its route document a guard (`condition_locked` via PF006) that cannot fire

**File:** `packages/core/server/profile-form/admin.ts:1106-1108`, `1136-1147`; `packages/modules/profile-form/server/routes.ts:465`; `supabase/migrations/20261106180523_profile_form_branches_functions.sql:478-484`
**Issue:** The docs say an answered question of an archived branch "cannot leave it (the PF006 guard, 409 `condition_locked`) and the delete is refused whole". PF006 in the question guard only fires when `new.branch_id is not null`; setting `branch_id = null` is allowed by design (the trigger comment says so, "leaving a branch passes"). So the dissolve silently detaches answered archived questions, and the documented 409 is unreachable. In practice the opener has no answers (so none of its dependents can hold any under the purge rule), so this is not exploitable; but the contract and the code disagree, and the dissolve also removes the archived branch rows, so "Reativar ramo" is no longer possible afterwards while a later single-question reactivate brings those questions back as unconditional, visible to every member.
**Fix:** Either correct the docs, or add the explicit check in `deleteQuestion` (`count(answers) of the questions about to leave` > 0 -> 409 `condition_locked`) before the update.

### IN-02: Branch `name` is readable by any member lane at the database layer

**File:** `supabase/migrations/20261106174037_profile_form_branches.sql:30`; `packages/core/db/schema/profile-form-branches.ts:86-90`
**Issue:** `profile_form_branches_select` admits `member` and `support_tenant`, and the policy is row-level, so a member JWT that reached the table through any path would read `name`. Today this is mitigated: the API never selects it for members, the member lock function omits it, and `supabase/config.toml` closes the Data API (`data_api_closed`). The privacy promise (T-12.2-03) is therefore held by application code, not by the database.
**Fix:** Defense in depth for a later release: move `name` to a sibling table with an admin-only select policy (a single `authenticated` role means a column revoke cannot separate admin from member), or make the branches select policy admin-only and let members read through the existing definer function.

### IN-03: Web `memberFormSchema` / staff schema make `branches` and `branchId` required: rollout hazard if web ships before the API

**File:** `packages/contracts/src/profile-form.ts:943-950`, `1125-1126`; `apps/web/lib/profile-form/member-form.ts:25`; `apps/web/lib/profile-form/profile-reads.ts:100`
**Issue:** `getMemberForm` ends in `memberFormSchema.parse(...)` and `loadMemberAnswers` parses the strict staff schema. An API revision that does not yet send `branches` / `branchId` (Vercel and Cloud Run deploy independently) makes both throw and render the failure state. `ProfileForm.viewOf` already tolerates a missing `branches` (`form.branches ?? []`), which suggests the intent was to tolerate it. Low risk now (module OFF in production for every tenant), but the DEPLOY notes should say migration, then API, then web, in that order.
**Fix:** Add `.default([])` to the member/staff `branches` and `.nullable().default(null)` to `branchId` in the read schemas for one release, or record the order in the release notes.

### IN-04: Conversion block can create ACTIVE branches that contain only archived questions (unverified on data)

**File:** `supabase/migrations/20261106180523_profile_form_branches_functions.sql:316-323`
**Issue:** Step (c) converts archived dependents too and creates the branch with `archived_at null`. A legacy (opener, values) pair whose dependents are all archived becomes an active, empty branch: it counts toward the 15-branch limit and, through PF007, blocks archiving or retyping its opener with a `has_dependents` list that names no question. Not reachable in production today (no legacy rows, module off), and I could not check any hosted project; flagging it for the owner's read-only "query D" before the module is turned on anywhere.
**Fix:** In (c) set `archived_at = max(q.archived_at)` for groups whose every dependent is archived (`bool_and(q.archived_at is not null)`), or skip creating a branch for them and null their condition.

### IN-05: Privacy switch shows "off" while the draft still sends `showOnProfile: true`

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/VisibilitySwitches.tsx:105-107`
**Issue:** With a private opener on the chain the switch is rendered `checked={false}` and disabled, but `draft.showOnProfile` is untouched. For a stored question that is already public under a (legacy) private opener, the sheet displays "off" while a save sends the unchanged `true`; the server tolerates the stored violation (`newPublicUnderPrivate`), so the admin believes the answer is private when it is not.
**Fix:** When `privateOpener` is set and the draft is `true`, show it checked with the reason text and enable only the turn-off, or force `showOnProfile: false` into the draft when the branch is chosen.
