# Phase 12.2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 12.2 turns the single per-question condition of Phase 12.1 into a **branch** (one condition, several questions, up to 3 levels deep) and adds a read-only **"Fluxo"** view that draws every fork as a vertical tree. The UI work is: (1) branch blocks in the builder list, (2) a branch sheet and a "Ramo" field in the question sheet (replacing the per-question condition editor), (3) the Lista | Fluxo view and the Fluxo itself, (4) refusal, undo, archive and archived-tab states for branches, (5) the member form revealing a whole block at once. Everything else (stepper, erase dialog, one-scroll edit, readers) stays as Phase 12.1 shipped it and only follows the new rule "visible when every branch on the chain is open".

**Baseline.** `12-UI-SPEC.md` (UI-D-564..UI-D-599) and `12.1-UI-SPEC.md` (UI-D-642..UI-D-664) are inherited whole: Manrope, `#f5f7fb` ground, white cards, 12px radii, 44px targets, the 12/14/16/24 type scale with weights 400/700, the tenant brand as the single accent, `BottomSheet`, `ConfirmDialog`, `StatusPill`, `Switch`, `SegmentedControl`, the step well, `DependentsAlert`, the neutral left rule of a revealed question. **Phase 12.2 declares no new token, colour, font, type size, weight, spacing value or dependency.** This file lists only what is new and says which shipped component each new surface extends.

**Upstream decisions.** `12.2-CONTEXT.md` D-640..D-653 are LOCKED and honoured (traced in "How each locked decision shows up"). The visual and interaction questions this phase opens are decided as **UI-D-665..UI-D-684**, continuing after `UI-D-664`, the highest id in any UI-SPEC (`grep -rhoE "UI-D-[0-9]+" .planning | sort -t- -k3 -n -u | tail -1` returned `UI-D-664` on 2026-11-06).

**Non-interactive session.** No question could be asked in this run. Every choice CONTEXT left open took a default and is repeated under **To confirm with Igor** (PU-1..PU-12), so the orchestrator can confirm or overturn it with one line. The headline ones: **PU-1** (WR-06, a public question under a private opener is refused) and **PU-2** (the Fluxo is a tree by branch, not by step).

**Sketch gate (UI-04, D-650).** This phase has no approved sketch. Sketch 019 is a **plan-time deliverable gated by Igor's approval**; the executor never writes the approval (see "Sketch gate"). Sketch 018 (Phase 12.1) is still `pending` in `MANIFEST.md` on 2026-11-06 and 019 extends its look; if Igor changes 018, the affected 019 frames are redrawn.

## Data the screens read (for the planner; not a UI decision)

- **Admin read:** the steps, the **branches** (id, opener question id, the answer tokens that open it, optional name, archived flag, position in layout) and per question its `stepId` and `branchId` (no per-question condition any more). Derived on the client from that one read: the tree (`branchTree`), the chain of a question, the depth, the labels, the eligible branches of a question, the eligible openers of a branch. Counts the screens need: active questions per branch (direct and subtree), per opener the count of questions in its direct branches (the "Abre N" pill), and which options are referenced by a branch (for "Abre N ramos").
- **Member read:** `steps`, `branches`, per question `stepId` and `branchId`, the stored answers (the erase dialog's baseline), `mode`, `missingRequired`, `formEtag` (covers branches, CONTEXT discretion).
- **409s:** dependents as **branches with their question titles** for archive, delete, retype and remove-option of an opener; a branch-archive refusal (opener of a branch with answers); the privacy refusal (UI-D-675); the order refusals that name the pair of questions (as 12.1); a branch-stale refusal; the branch-limit and depth refusals.
- **Visibility:** one pure `isQuestionVisible` in contracts walks the chain; parity table gains depth-2 and depth-3 rows.
- **No answer value** ever reaches a toast, an announcement, a log or the erase dialog; **no branch name or label** ever reaches a member surface.

**Planner-owned items this contract does not decide:** (1) table, column, trigger and refusal-code names, the contracts' shape, how `formEtag` covers branches, whether the gate is one function or split (CONTEXT discretion); (2) whether the server accepts an **empty branch** (the UI creates a branch first and then fills it, UI-D-671; if the server refuses an empty branch the create flow must create the branch and its first question in one write); (3) where a reactivated question lands when its branch or step is gone (UI-D-674 assumes refusal); (4) the exact layout-rewrite rule that places a question moved into a branch whose run is in another step (UI-D-669 says: end of the branch's run in the question's own step, else end of the step); (5) the move-engine order for the circular pair branch <-> question (CONTEXT research item).

## Findings against CONTEXT (surfaced, not decided here)

- **F-1 (D-651 vs D-640).** CONTEXT never says whether an opener may carry **several branches** (for example one for "Tenho clínica" and another for "Estou aprendendo"). It is the natural reading and the clinic case needs it, so the Lista, the sheet and the Fluxo all assume yes (consecutive blocks, one edge each, `lista-ramo-varios`, `fluxo-varios-ramos`). Branches of one opener may have overlapping answer sets (a question belongs to one branch, so there is no conflict). Confirm (PU-4).
- **F-2 (D-642).** The label with no name reads like a sentence and the Fluxo edge already sits under its opener, so the edge uses the short form "Se for ..." and a named branch shows **both** the name and the answers; otherwise the name would hide the very thing the connection must say (D-649).
- **F-3 (D-641, D-643).** A block whose opener is in another step is not "revealed in place": in the stepper it is just present or absent on arrival, and in the one-scroll edit it can change off-screen. UI-D-679 adds the other-step announcements (edit only) for that case; it is the only new member string.
- **F-4 (D-646, D-653).** "Arquivar ramo" is refused when a question of the subtree opens a branch **with answers**, while "Desfazer ramo" is always allowed. The refusal hint therefore tells the admin to undo those inner branches (UI-D-672). If the server instead refuses undoing an inner branch with answers, the hint must change.
- **F-5 (D-651).** "Adicionar pergunta ao ramo" opens the question sheet; the new question counts against the 30-question limit and the existing limit line applies.
- **F-6 (WR-06).** Decided here as a default (refuse), because the Fluxo and the strips make the dependency visible and a refusal with the one-tap way out costs the admin one switch. It is still the product call of CONTEXT's specifics; overturn with PU-1.
