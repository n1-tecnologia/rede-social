# Phase 12.2 Plan 10: The member lane on the branch tree Summary

**The member's read, save, report, notice and the staff row now run on branches: the form carries `branchId` and the strict, name-free branch list, the etag covers branches only when there are any (the 12.1 etag is byte-identical otherwise), and the save settles visibility in one pass in form order and purges down the chain in the same transaction.**

- **Files:** 6 changed, 1109 insertions and 129 deletions

## Accomplishments

- **Task 1 (tracer).** `member.ts` now reads `branch_id` (`lock_active_v3`), reads the tenant's branches without the name (`readBranches` for the GET, `lockBranches` through `app.profile_form_lock_branches()` in the save, right after the question lock), builds the tree with `branchTreeOf` and returns `branches` (parsed by `memberBranchSchema`), `branchId` per question and `condition: null`. `formEtagOf(questions, steps, branches)` renders the branch id as a fourth segment only for a question that has one and appends the branches only when at least one is active. `saveAnswers` is one pass over the questions in form order: a row that `isQuestionVisibleInTree` says is hidden is skipped (no value, no error), a visible in-scope row is parsed, validated and its valid value is applied to the effective answers at once so the next rows see it. The 12.1 two-pass code, `conditionOf` and every use of the legacy condition columns are gone. `reportMissing` and `newOptionalCount` landed in the same commit because `member.ts` had to stay coherent: the report decides visibility with the tree, and the notice with `questionVisibleSql` fed by a one-row derived table (`me.tenant_id`, `me.membership_id`) with the tenant and the user bound as parameters.
- **Task 2 (TDD).** Tests for the report equal to the SQL gate level by level, the order by `position, created_at, id`, adjacency (close A and open B in one save), the 30-question / 15-branch boundary with the 31-key refusal, the notice at depth 1 to 3 (and the stale-answer trap under a closed branch), and the gate on a depth-3 tree. All passed on their first run (see TDD Gate Compliance).
- **Task 3 (TDD).** `staffAnswersOf` returns `branchId` per row and a top-level `branches` list (every branch of the tenant, active and archived, `id`, `openerQuestionId`, `values`, parsed by the strict shape). `publicAnswersOf` and the CSV are untouched.
