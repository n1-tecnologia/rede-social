# Phase 12.2: Ramos condicionais no formulário de perfil - Context

**Gathered:** 2026-11-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 12.1 (live in production since 2026-11-06) lets the admin attach ONE condition to ONE question: "show this question only if [an earlier choice or yes/no question] was answered [with one of these options]". The admin asked, the same day, for three things on top of it.

This phase delivers: (1) a **branch** as a first-class object: one condition (an opener question plus the answers that open it) that holds SEVERAL questions, created once and filled; (2) **branches inside branches**, up to 3 levels, so a question that lives in a branch can itself open another branch; (3) a **"Fluxo" view** in the builder that draws every fork as a vertical tree, read-only, where tapping a node opens the editor you already have.

The member side keeps what 12.1 built (stepper, reveal in place, erase-answers dialog, one-scroll edit, "Não se aplica" for staff); it only has to follow the new rule that a question is visible when every branch above it is open.

What this phase does NOT deliver: a condition that depends on more than one opener or on an AND/OR of answers, a condition on a whole step, editing by dragging or wiring inside the diagram, a "go to step" jump or an early end of the form, notifications when the form changes, anything in Phase 13.

Origin: Igor, 2026-11-06, after seeing the 12.1 builder: "hoje eu só consigo adicionar uma pergunta a uma condição; agora vou precisar adicionar várias, meio que criar um branch condicional; também uma condicional dentro de uma condicional; e um diagrama/fluxograma que mostra de maneira visual essas bifurcações."

This phase REVERSES D-621 (the condition lives on the shown question) and D-622 (one level only) of Phase 12.1. The module is OFF in every tenant, so no condition is stored in production and the model can change without migrating client data (to be re-verified, see Claude's Discretion).

</domain>

<decisions>
## Implementation Decisions

### What a branch is
- **D-640:** A branch is its own tenant-owned object: a row with an opener question, the set of answers that open it (the same token shape as 12.1's `condition_values`: option ids, or `true` / `false` for yes/no; ANY of them opens it) and an optional name. The condition moves from the question to the branch (reverses D-621). A question points at its branch; the question no longer carries a condition of its own. — **Reversibility:** costly — a new table, a new column on the questions, the SQL gate, the contracts, the guard, the move order and the whole builder read this shape, and it fans out to every tenant project.
- **D-641:** A question belongs to AT MOST ONE branch; a question with no branch is always visible. A question inside a branch may itself be the opener of another branch: nesting is derived from where the opener lives, there is no separate parent column. The opener must come strictly BEFORE every question of its branch (D-623 generalised to the tree). — **Reversibility:** costly — same shape as D-640.
- **D-642:** The branch name is OPTIONAL (short, same limits as a step title). With no name, the diagram and the lists write a label from the condition ("Se «Qual é o seu perfil?» for «Tenho clínica»"); a name replaces that label. — **Reversibility:** reversible — presentation plus one nullable text column.
- **D-643:** The questions of one branch may sit in DIFFERENT steps; each keeps its own step. The branch only imposes the condition. So the clinic case works as 12.1 intended: the opener in "Informações gerais", the block in a step "Sua clínica" that disappears by itself when the branch is closed (D-628 unchanged). — **Reversibility:** reversible.

### Branches inside branches
- **D-644:** Maximum depth is 3 levels of branch (a branch in a branch in a branch). The number lives in `PROFILE_FORM_LIMITS` and in a database check that reads it, like the other limits; raising it later is a small migration. A question is visible when EVERY branch on its chain is open (the opener of each branch is visible and holds an answer from that branch's set). The gate `app.profile_form_missing` stays a fixed-size join, no recursion. Reverses D-622. — **Reversibility:** costly — the gate runs on every member request and its twins are published to every tenant project.
- **D-645:** D-624 and D-636 (stored equals visible) are EXTENDED down the chain: when the member's change closes a branch, the answers of every question in that branch AND in every branch below it are deleted in the same transaction, active and archived. The erase dialog of D-626 lists the titles of the ACTIVE closed questions that had answers. — **Reversibility:** costly — same promise as 12.1 (no reader needs a visibility filter), now over a tree.
- **D-646:** The locks of 12.1 extend to branches. A branch with any answered question cannot change its opener or its set of answers; a question with answers cannot be moved into or out of a branch; removing a condition ("Desfazer ramo", D-653) stays allowed. An opener cannot be archived, retyped or lose a referenced option while a branch hangs on it (D-632), and the 409 lists the dependent branches and their questions. — **Reversibility:** reversible — they are refusals plus guard codes; relaxing them is a service rule.

### The diagram ("Fluxo")
- **D-647:** The diagram is a **"Fluxo" view inside the builder**, a Lista | Fluxo selector over the same data. No new route; the list of today stays as it is. — **Reversibility:** reversible.
- **D-648:** The diagram is READ-ONLY. Tapping a question or a branch opens the existing edit sheet of the builder. Dragging, wiring and creating branches inside the drawing are out of scope. — **Reversibility:** reversible — adding edit-in-place later is additive.
- **D-649:** The drawing is a VERTICAL TREE, top to bottom, indented one step per branch level, with the answer(s) that open the branch written on the connection. It must fit 390px without sideways scroll and not break at 320px (PFORM-42). — **Reversibility:** reversible.
- **D-650:** The sketch gate applies (UI-04, D-635): a new sketch 019 covers the branch UI of the builder, the "Fluxo" view, the branch sheet, the refusal lists, and any change to the stepper reveal and the preview. The executor never writes the approval; no web code before it is on disk. The design questions Igor did not answer in 018 stay his to answer in 019. — **Reversibility:** reversible.

### Building a branch in the builder
- **D-651:** A branch is created FROM the opener question: any question that can open (dropdown, multiple choice, single choice, yes/no, D-620) offers "Criar ramo"; the admin picks the opening answers, may give a name, and adds questions inside. The branch shows indented right under the opener. An existing question WITHOUT answers can be moved into a branch from its edit sheet. — **Reversibility:** reversible — presentation.
- **D-652:** ORDER is the tree. Inside each step, the questions of a branch stay consecutive, right after the opener when both are in the same step; a branch moves as a block; a nested branch sits inside its parent's block; every reorder rewrites positions to follow the tree. This subsumes quick 261106-ei5 ("a new conditional question lands right after its opener"), whose placement helper is replaced. — **Reversibility:** costly — the layout engine, the reorder and move routes and the tenant-move order change.
- **D-653:** Two actions on a whole branch. "Desfazer ramo": the questions stay and become always visible (removing a condition is allowed, D-625; required ones reopen the form for members who lack the answer, and the impact dialog counts them). "Arquivar ramo": archives the branch and every question inside it; refused when one of those questions opens another branch that has answers. — **Reversibility:** reversible.

### Claude's Discretion
- Compatibility with 12.1: the production tables already have `condition_question_id` and `condition_values` on the questions, unused. The default is expand-only (add the branch table and the `branch_id` column, keep the old columns one release, stop accepting a per-question `condition` in the API and contracts). The research must CONFIRM that no tenant has a condition stored (the module is off everywhere; a read-only check on each hosted project is Igor's to run or to approve) before the plan relies on it.
- How many branches a form may hold (a limit in `PROFILE_FORM_LIMITS`; the cap on openers is already implied by the 30 questions).
- How several questions appear at once when a branch opens (the 12.1 reveal animates one question; here a block), and how the erase dialog presents many titles (count plus list, grouping by branch).
- Table, column, trigger and refusal-code names (the next codes after PF007), the contracts' shape, how `formEtag` covers branches, how the admin preview follows branches, and whether the "Fluxo" shows step headings and answer counts.
- Whether to keep `app.profile_form_missing` as one function with a fixed-depth join or to split it; the pgTAP and parity-table coverage of a depth-3 tree.
- pt-BR copy of every new string (the existing `profileForm.*.json` catalogs) and the PFORM-43.. requirement ids.

</decisions>

## Existing Code Insights

### Reusable Assets
- `isQuestionVisible` / `answerTokens` / `visibleSteps` and the 18-row `PROFILE_FORM_VISIBILITY_CASES`: the single visibility rule shared by the stepper, the preview and the readers; it becomes "every branch on the chain is open", and the parity table gets depth-2 and depth-3 rows.
- `app.profile_form_missing`, `app.profile_form_answer_tokens` and `app.profile_form_purge_closed`: the SQL that must learn the chain; the purge already deletes active AND archived closed answers in the member's own transaction.
- `ConditionEditor`, `DependentsAlert`, `StepWell` and `StepSheet`: the pickers, refusal lists and sheets the branch sheet can reuse; `describe-condition.ts` already writes the condition as a sentence for the label of D-642.
- `layout.ts` (pure operations plus `assertLayoutOrder`) and `layout-store.ts` (`readLayout`, `writeLayout` with the canonical lock order): the discipline D-652 extends; the quick's `addQuestionAfterOpener` is the first step toward a tree order.
- `RevealedField`, `EraseAnswersDialog`, `StepProgress`: the member pieces that need to cope with a block of questions opening or closing at once.

### Established Patterns
- Completeness is computed, never stored (D-585); stored equals visible (D-624/D-645); a gate never mutates membership state.
- Tenant-owned rows carry `tenant_id` first in every index, composite `(tenant_id, …)` foreign keys, RLS on every table; hand SQL goes in `--custom` migrations, the schema source of truth is Drizzle, migrations are expand-only and the old function twins stay one release.
- Every layout write takes `adminLock` first, locks rows in the canonical order and renumbers in one set-based statement; an append to the very end touches nobody.
- Screens the prototype lacks go through a UI-SPEC and a sketch gate (UI-04); all strings come from the pt-BR catalogs; 44px targets, 320px must not break.

### Integration Points
- `requireAuth`: the visibility join runs inside the single membership lookup; a depth-3 chain must not add a round trip nor grow for a tenant with the module off.
- `GET /v1/me/profile-form`, `PUT /v1/me/profile-form/answers`: the member form carries the branch tree and the save recomputes visibility over it.
- `/v1/profile_form` admin routes: branches (create, rename, edit the condition, undo, archive), moving a question in or out, the layout body that now follows the tree.
- The tenant move / copy engine: it must copy branches and questions in an order that satisfies both foreign keys (a circular pair).
- `docs/DEPLOY.md`: the release repeats the 12.1 order and, because the gate function changes, publishes new twins to every tenant project.

<specifics>
## Specific Ideas

- Igor's own words for the branch: "meio que criar um branch condicional, entendeu?" — one condition, many questions, created once. The label of the diagram edge is the answer that opens it.
- The first client's case still drives the test data: "tem clínica / trabalha em clínica / está aprendendo". A natural depth-2 example for tests and the sketch, built on the clinic example and not on invented client wording: "tem clínica" opens a branch with its own sub-question that opens a deeper branch (never invent the client's wording; the real list is not in the repository).
- WR-06 is not closed by this phase and gets worse to ignore: decide, in research or in the sketch review, whether a public question under a private opener is refused, hidden from the public block, or accepted explicitly.
- The diagram should read like the member's journey: top to bottom, indented by level, each connection carrying the answer that opens it, so an admin can answer "who sees this question?" at a glance.

</specifics>

<deferred>
## Deferred Ideas

- A condition that depends on more than one opener, or an AND/OR of several answers (the branch has exactly one opener; ANY of its answers opens it).
- A condition on a WHOLE step ("show the step only if…"): a branch with questions in one step approximates it; revisit if admins keep building one-step branches.
- Editing inside the diagram: dragging a question into a branch, wiring a branch to an answer, creating a branch on the canvas.
- More than 3 levels of nesting (raising `PROFILE_FORM_LIMITS` is a small migration).
- A horizontal flowchart (left to right with arrows) as an alternative drawing for wide desktop screens.
- A "go to step" jump or an early end of the form, notifications when the form changes, state/city and file answer types (deferred since Phase 12).

None of the above was a todo; no pending todo matched this phase.

</deferred>
