<planning_decisions>
1. **One action stream.** `app.dashboard_member_actions(p_from date, p_to date)` returns one row per counted action of the caller's tenant's active role-member memberships: `(membership_id, user_id, at, day, action, strong, post_id, community_id, on_post)` (`action` in like, comment, post, rsvp, checkin, order; `on_post` true when the action is on a post or on a comment of a post, so the tenant-wide feed is `on_post and community_id is null`). `p_from` null means no lower bound (used for the since-joining aggregates). Every source predicate carries `tenant_id = app.tenant_id()` and joins memberships on `(tenant_id, user_id)` (R-Pitfall 1).
2. **Likes on content later deleted still count** as the member's action (the like row exists); comments only while live. Recorded as R-A2 extended.
3. **Member rows then aggregates.** The builder writes member rows first, and the members area function aggregates those rows in the same transaction, so a band list (plan 04) always has exactly the band's count.
4. **Insights stored per member** in `insights` jsonb: `last30` (`activeDays`, `likes`, `comments`, `checkIns`, `orders`, `strongActions`), `weeklyActiveDays` (12), `communities` (actions since joining per community id, the tenant-wide feed as `null`, most first) and `postTypes` (likes and comments since joining per post kind). `top_community_id` is the first non-null community of that list.
5. **Community bands per member** in `community_bands` jsonb (`{ "<communityId>": "<band>" }`), only for members in that community's base; the tenant-wide feed is not a band-scope card (it has no base, cover or description), only a row in interaction breakdowns (UI-D-475; surfaced below).
6. **Module flags are an API concern.** The builder computes community and event scopes regardless of flags; the service drops `communityEngagement` with `communities` off and `eventEngagement` with `events` off (D-460), reading flags before the lane.
</planning_decisions>
