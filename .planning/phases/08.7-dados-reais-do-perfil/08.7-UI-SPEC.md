# Phase 08.7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** The two report panels on `/perfil` already exist. They were ported from the dashboard project in the FRONT-AJUSTES merge (9706aa7f):
- **"Sua atividade"**, role `member` only: `apps/web/components/profile/activity/*`;
- **"Visão do dono"**, role `admin_tenant` only: `apps/web/components/dashboard/*` and `packages/modules/dashboard/ui/*`.

This phase does **not** redesign them. It keeps their layout, order (D-457), surfaces, charts and shipped classes. It contracts only the **new states and copy** that real data brings:
1. the single **"Em breve"** state (D-455, D-456, D-458), in four forms: tile, line, block, and a list that does not open;
2. the **snapshot freshness line** (D-464), plus rewording of the strings that say "agora" or "hoje" about a midnight number;
3. the **"preparing"** state before a snapshot exists;
4. the **privacy floor** rendering of a server-typed `Floored` value (D-462);
5. **module-gated areas** (D-460), with the area row reflow and the `?area=` fallback;
6. **wired versus still-disabled actions** (D-461);
7. **loading, error and empty** states for data that can now be missing or empty.

**Upstream.**
- `08.7-CONTEXT.md` decisions are cited as **D-455..D-465** and are not re-litigated.
- `08.7-RESEARCH.md` is cited as **R-§**, **R-A1..A9** (assumptions), **R-OQ1..9** (open questions) and **R-Pitfall n**. Its draft requirements are **INSIGHT-01..19**.
- The UI decisions this phase opens are **UI-D-466..UI-D-490**. They continue after 08.6's UI-D-465, the highest id in `.planning`, checked 2026-10-18 with `grep -rhoE "UI-D-[0-9]+" .planning | sort -t- -k3 -n -u | tail -1` → `UI-D-465`.

**Non-interactive session.** No question could be asked in this run. Every research open question and assumption that changes what the screen shows is decided below with a recommended default. Each one is repeated in **§ Pending User Confirmation**, so the orchestrator can confirm it with the user or overturn it with one line.
