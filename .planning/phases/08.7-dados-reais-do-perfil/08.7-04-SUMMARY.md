# Phase 08.7 Plan 04: Named lists behind Membros Summary

**The admin's API can now open every Membros number. It lists the members of any band (the whole base, one community's base, or one event's "vou" RSVPs), paged by a keyset that never repeats or skips a row. It opens one member's detail: band history, 30-day numbers, live events, purchases and support counts. It also pages through the member's own likes, comments, strong actions and active days inside the snapshot's 30 days. Only `admin_tenant` of the same tenant gets an answer. Every other id is the same bare 404.**

## Accomplishments
- **The contract** (`contracts/member-lists.ts`):
  - Strict schemas for the band row and answer, the member detail and the four list rows.
  - No comment body, message text, email or offer id on any of them.
  - `expiresAt` is always `{ measured: false, reason: 'needs_access_expiry' }`.
  - `dailyMinutes` and `postsSeen` are not measured.
- **`server/paging.ts`.** It clamps `limit` to 1..50 (defaults 10 and 20) and checks the cursor's `n` against the list's order: an ISO instant, an ISO date for active days, or the `never` sentinel for a member who never acted. Anything else reads page 1, never 500.
- **`GET /v1/dashboard/owner/members/bands/{band}`** reads the band from the newest build's member rows:
  - `base` reads `band`.
  - `community` reads `community_bands ->> scopeId`.
  - `event` reads the RSVPs "vou" answered before `untilAt`, the same predicate as the payload.
  - Rows are keyset-ordered on `(coalesce(last_active_at, '-infinity'), membership_id)`.
  - `total` comes from the same build's payload.
  - A scope whose module is off is 404 `MODULE_DISABLED`. A foreign, unknown or absent `scopeId` is the bare 404.
- **`GET /v1/dashboard/owner/members/{membershipId}`** returns:
  - the band history at D-60, D-30 and D;
  - `last30`, `weeklyActiveDays` and `postTypes` from the member row;
  - live community names and the top community;
  - events: RSVPs "vou" and walk-ins, each attended, missed or still to come;
  - purchases: the member's first paid order is `primary`, the rest `secondary`;
  - support turns of the 8 weeks with the median minutes to a staff answer;
  - a suggestion.
- **`GET /v1/dashboard/owner/members/{membershipId}/lists/{list}`** returns the member's own rows between `from30At` and `untilAt`, with the action stream's predicates:
  - `likes`;
  - live `comments`, each naming the post with a 120-character excerpt;
  - `strong-actions`: comments, check-ins and walk-ins, paid orders;
  - `active-days`.
- **The membership gate.** One gate (`tenantMember`: role `member`, not deleted, this tenant) runs before any snapshot read. Unknown, other-tenant and staff ids get an identical `{ error: { code: 'NOT_FOUND', message, requestId } }` (EP-17).
- **Tests:**
  - Unit: `paging.test.ts` (13 cases) and `member-lists-contract.test.ts` (17).
  - Integration: `08.7 member lists` (20 cases).
  - Sweep: three inventory entries, and the 08.7 owner sweep now covers all three routes.

## Decisions Made
Planning decisions 1-4 were followed as written (see `key-decisions`). These choices were made during execution:
- **Support "conversations" are member turns.** Each member has one support thread, so a count of threads would only ever be 0 or 1. A turn is the first member message after a staff message, or the thread's first message. It is the same turn plan 11 uses for its medians. Days since the last turn and the median minutes to the next staff message are bounded by `untilAt`. **To confirm.**
- **The detail's events include walk-ins** (as attended). It shows the latest 50 events and the latest 50 purchases, oldest first, which bounds one person's history (T-08.7-15).
- **Live labels beyond the fixture shapes**, so the web can render without the fixture lookups:
  - events carry `title` and `startsAt`;
  - purchases carry `orderId` and `productName`;
  - communities carry `name`, with null for the tenant-wide feed.
- **Comment rows also carry `storyId`.** A comment on a story still counts in the stream, so its list row says where it was written.
- **`strong-actions` has no `post` kind.** Members cannot post in V1, so the list equals `strongActions` today. A V2 member-post row will need a new variant.
- **Band-list totals for scopes missing from the payload.** For a scope id the payload does not hold (an archived community, an event outside the panel's six upcoming plus last-30-days), `total` is counted over the same rows with the same predicate.
