## Narrative Findings (AI reviewer)

## Summary

The review covered the snapshot pipeline (definer builder v1..v8, area functions, retention prune, kernel daily dispatcher, build job), the API service layer and routes, and the web owner/member panels. Production code got more weight than tests.

These parts hold up:
- **Tenant pinning in every definer.** Every `security definer` function pins `tenant_id = app.tenant_id()` on each source and joins memberships on `(tenant_id, user_id)`.
- **Grants.** The area helpers have EXECUTE revoked from every role. The builder is gated on the zero-uuid `sub`, which a request lane cannot forge because claims come from a verified JWT. The prune is `service_role`-only.
- **Role gating.** Every owner route carries `requireRole('admin_tenant')`. Module-gated areas use `requireModule` before the role.
- **Member isolation.** The member route has no user-id parameter. It reads by `app.user_id()` behind the own-or-admin policy.
- **Window and timezone math.** The SQL is consistent: local midnights are converted once with `::timestamp at time zone tz`, and the 7-day block index arithmetic is correct.
- **Paging.** Keyset cursors are validated before they reach SQL, with one exception (WR-07).

The main defect is in the privacy floor:
- **Subtraction bypass (CR-01).** Some floored money groups sit beside exact unfloored totals of the same partition. A floored product's revoked orders, or a floored product inside a post's sales, can be recovered by subtraction. The floor's own C-1 doc comment warns against exactly this.
- **Builder robustness.** An older-day build overwrites the "latest only" member rows (WR-01), and the retention prune can delete a tenant's only snapshot (WR-02).
- **Module gating.** Several places miss the D-460 gating server-side (WR-03, WR-04).

## Critical Issues

### CR-01: Privacy floor bypassable by subtraction for revoked orders and per-post product sales

**File:** `packages/modules/dashboard/server/finance.ts:137-183` (with `supabase/migrations/20261019022117_dashboard_finance_functions.sql:152-203, 469-505`)

**Issue:** `applyFinanceFloor` floors each group on its own, but the partitions it floors are shown next to exact sums of the same rows. That is the attack `mergeBandsBelowFloor`'s doc comment (C-1, `contracts/floor.ts`) describes: "the total minus the shown bands gives it back".

1. **Revoked orders.** `revoked.current` is shown exactly once its buyers reach 5. Each product's `revoked` (from `prv`, `grp = 'cur'`) is floored separately in `GET /owner/finance/products/{id}`. Every revoked order belongs to exactly one product in `pr`, so Σ product revoked orders and cents equals the area total. With one product floored, the admin opens the other products' details, subtracts, and gets that product's exact revoked orders and cents for 1-4 people. No named list of revoked orders exists:
   - the member detail lists only `status = 'paid'`;
   - the strong-actions list lists only `status = 'paid'`.

   So the floor is the only protection, and it is defeated.
2. **Products within a post's sales.** In `contentSales.posts[i]`, the post's sales are shown once its buyers reach 5. Its `products[]` are floored one by one. `cs` is distinct per `(order, post)` and each order has one product, so a post's orders and cents partition exactly by product. A single floored product is the post total minus the shown products. No named list of "buyers of product X associated with post Y" exists.

This breaks D-462 ("every group total below 5 people or orders reads 'menos de 5' … applied by the API").

**Fix:** Floor partitions the way the band split does: never let exactly one hidden member remain beside an exact total. For example, merge the floored remainder into an "outros" bucket that is itself floored, or floor the parent when any child is floored.

```ts
// finance.ts — a post's products: hide the remainder as one "others" group
function floorPartition<T extends { productId: string } & FinanceTotals>(parent: FinanceTotals, parts: T[]) {
  const shown = parts.filter((p) => !floorMoney(p).belowFloor);
  const hidden = parts.filter((p) => floorMoney(p).belowFloor);
  if (hidden.length === 0) return { parts: shown.map(/* … */), others: null };
  const rest = { orders: parent.orders - sum(shown, 'orders'), cents: parent.cents - sum(shown, 'cents'),
                 buyers: Math.max(0, parent.buyers - sum(shown, 'buyers')) };
  // If the remainder is still < 5 buyers, floor the PARENT too (or fold the smallest shown part in).
  return { parts: shown.map(/* … */), others: floorMoney(rest) };
}
```

For revoked orders, either do not expose per-product revoked numbers when the area total is shown, or only show per-product revoked numbers when every product's group is at or above the floor.

## Warnings

### WR-01: An older-day build overwrites the latest-only member rows behind a newer snapshot

**File:** `supabase/migrations/20261019035403_dashboard_overview_functions.sql:105-133`

**Issue:** The builder refuses only `p_day >= local today`. For any older `p_day` that has no row at the current version, it deletes all of the tenant's `dashboard_member_snapshots` and rewrites them for `p_day`. The newer `dashboard_snapshots` row stays the one `readLatestSnapshot` returns.

The member rows are "latest only" and the band lists filter `s.snapshot_day = snapshot.day` (`member-lists.ts:131`). After such a build:
- every band list of the newest snapshot is empty while its count says N;
- the member detail and "Sua atividade" silently show the older day.

This happens when a job of day D (a retry, a manual re-enqueue, a stale `created` job after an outage) completes after day D+1 was built. The state persists until the next night.

**Fix:** In the builder, after the guards:

```sql
if exists (select 1 from public.dashboard_snapshots s
            where s.tenant_id = v_tenant and s.snapshot_day > p_day) then
  return false;  -- never rewind the latest-only member rows
end if;
```

### WR-02: Retention prune can delete a tenant's only (latest) snapshot

**File:** `supabase/migrations/20261019035403_dashboard_overview_functions.sql:175-195`

**Issue:** `dashboard_snapshots_prune` deletes every row older than local today - 8 with no "keep the newest per tenant" guard. If a tenant's builds fail for more than 8 days, the hourly sweeper deletes the last good snapshot, and the panel turns from a clearly dated stale state into `preparing`. A build can fail for that long when, for example, the 120 s statement timeout is hit as history grows, since several area functions scan `dashboard_member_actions(null, p_day)` over all history.

Separately, `now() at time zone t.timezone` raises for an invalid timezone. A single bad tenant row then aborts the cross-tenant prune for everyone. The dispatcher filters on `pg_timezone_names`, but the prune does not.

**Fix:** Keep the newest row per tenant, and skip invalid zones:

```sql
where o.snapshot_day < (now() at time zone t.timezone)::date - 8
  and t.timezone in (select z.name from pg_catalog.pg_timezone_names z)
  and o.snapshot_day < (select max(x.snapshot_day) from public.dashboard_snapshots x
                         where x.tenant_id = o.tenant_id)
```

### WR-03: Overview's `perPost` reports post KPIs while `feed` is off

**File:** `packages/modules/dashboard/server/overview.ts:158-169`

**Issue:** `perPost` is built from `payload.content.kpis` whenever `feed || stories` is on. `kpis` is posts-only: `app.dashboard_area_content` computes it from `feed_posts`, and `getOwnerContent` emits it only with `feed` on (`content.ts:291-304`). A tenant with `stories` on and `feed` off therefore gets "interações por post" from the disabled feed module's rows on Visão geral, while the Conteúdo area correctly hides them. This is a D-460 inconsistency between the overview card and its owning area.

**Fix:** Gate on `flags.feed` only, matching `getOwnerContent`:

```ts
if (flags.feed) { /* perPost from content.kpis */ }
```

### WR-04: Member detail lists and fragments ignore the store, events, feed and notifications module flags

**Files:**
- `packages/modules/dashboard/server/member-lists.ts:296-340, 462-540`
- `packages/modules/dashboard/server/member-detail.ts:161-165`
- `packages/modules/dashboard/server/members.ts:61`

**Issue:** The member detail omits `purchases` and `events` when their modules are off. The lists do not:
- `GET /owner/members/{id}/lists/strong-actions` returns paid orders with product names and cents, and check-ins with event titles, whatever the `store` and `events` flags.
- `likes` and `comments` ignore `feed`.
- `last30.orders` and `last30.checkIns` are always sent.

Likewise, `atRiskWithPush` and each community's `atRiskWithPush` are sent with `notifications` off. The overview drops `withPush` server-side (`overview.ts:213`); here only the web hides it.

D-460 and the route docs promise that gated parts are "OMITTED, never zeroed" by the API.

**Fix:**
- Read `moduleFlags` first in `listOwnerMemberItems`.
- In `strongActions` and `activeDays`, drop the `store_orders` branch without `store` and the `event_attendances` branches without `events`.
- Return 404 `MODULE_DISABLED` for `likes`/`comments` without `feed`.
- Omit `last30.orders` / `last30.checkIns` per flag.
- Drop `atRiskWithPush` when `notifications` is off.

### WR-05: Finance band split and never-again are floored per band without merging (C-1)

**File:** `packages/modules/dashboard/server/finance.ts:138-143`

**Issue:** `byBand` and `neverAgain` floor each band on its own. `totals.current` (orders, cents, buyers) is exact and equals Σ `byBand`, because `pnb` joins every counted buyer to a member row of the same build. So whenever exactly one band is floored, its orders, cents and buyers come back by subtraction. This is the exact C-1 case `floorMoneyBands` merges for a product.

The `band`/`never` named lists currently expose the same people anyway, so the floor on these two blocks protects nothing. Either way, the code is inconsistent with its own stated rule.

**Fix:** Use `floorMoneyBands(payload.byBand)` (merged groups) for the area too, and a merged split for `neverAgain`. Otherwise drop the floor on these two blocks, and document that the named lists make them non-protected.

### WR-06: VIP and summary counts leave the API unfloored

**File:** `packages/modules/dashboard/server/finance.ts:347-374`

**Issue:** `vip` is sent raw:
- `holders`, `fading.atRisk`, `fading.inactive` and `fading.withPush`;
- `prospects`, the superfãs/engajados who entered through a product and do not hold the VIP. This group has no named list.
- `revenueCents`.

`summary.previous` (`rebought`, and `timeToSecondDays`, which is a single person's exact value when `rebought = 1`) describes a state 30 days ago that no list reproduces. The route description says every group of 1-4 people is `{ belowFloor: true }`; these are groups of people that skip `applyFinanceFloor`.

**Fix:** Pass `vip.prospects`, `vip.fading.*` and `vip.holders` through `floorCount`. Floor `summary.previous.rebought` and null `timeToSecondDays` when its group is below the floor. Alternatively, record an explicit decision that these are listable.

### WR-07: A tampered `time-to-second` cursor returns 500 instead of page 1

**Files:**
- `packages/modules/dashboard/server/paging.ts:26`
- `packages/modules/dashboard/server/finance-lists.ts:145-152`

**Issue:** `INTEGER = /^\d{1,15}$/` accepts values up to 999,999,999,999,999. The `time-to-second` keyset casts `${after.n}::int`, so any `n` above 2,147,483,647 raises `integer out of range` and the request returns 500. This breaks the module's "TOTAL: a malformed or tampered cursor reads page 1" contract (T-08.7-15).

**Fix:** Cast to `::bigint` in `listOrder` (as `lifetime` does), or give the day cursor its own kind with a tighter bound (e.g. `/^\d{1,6}$/`).

### WR-08: `check-dashboard-fixtures.sh --self-test` has inverted exit codes

**File:** `scripts/check-dashboard-fixtures.sh:23-28, 63-73`

**Issue:** The self-test exits 1 when the guard works and 0 when the guard is broken. Any CI step or script that runs `--self-test` and checks for success will pass on a broken guard and fail on a working one. That defeats the negative control.

**Fix:** Exit 0 when the planted import is found and the test copy is not. Exit non-zero (1 or 2) for each BROKEN branch.

### WR-09: `listOwnerFinanceBuyers('vip-fading')` uses the stored VIP community without checking it is still live

**File:** `packages/modules/dashboard/server/finance-lists.ts:220-223`

**Issue:** `getOwnerFinance` sets `vip` to null when the community was deleted or archived since the build (`liveCommunityName`). The `vip-fading` list still lists holders of the stored `communityId` with `communities` on. The list and its number therefore disagree: the area shows no VIP card while the list endpoint still names its members.

**Fix:** Apply the same `liveCommunityName` check before building the list, and return the empty list when it is null.
