# Phase 08.7: Dados Reais do Perfil - Context

**Gathered:** 2026-10-16
**Status:** Ready for planning

<domain>
## Phase Boundary

The FRONT-AJUSTES merge (9706aa7f, 2026-10-16) put two report panels on `/perfil` that render sample numbers. This phase replaces those samples with the tenant's own data:

- **"Sua atividade"** (role `member` only). The member's own activity.
- **"Visão do dono"** (role `admin_tenant` only). The tenant's numbers across six areas: Visão geral, Membros, Conteúdo, Eventos, Financeiro, Atendimento.

The screens already exist. The work is a read API over rows the database already records, the snapshot job that feeds it, and wiring the existing components to it, with the decided "Em breve" state wherever no data source exists.

Out of this phase:
- New event tracking (sessions, views, reach, playback, saves, shares, story taps, link clicks).
- New product capabilities (member leave or removal flow, support subjects, timed store access, offers, bulk push, recovery campaigns).
- Per-community membership (pendências item 8).

</domain>

<decisions>
## Implementation Decisions

### Carried forward (locked before this discussion)
- **D-440 [informational] (08.6):** every date is bucketed in the tenant's timezone (`tenants.timezone`, SQL `AT TIME ZONE`), and streaks are computed on the server, never trusted from the client. This phase reuses that rule for the 7-day and 30-day windows and the week streak.
- **Communities [informational] (Phase 5, PROJECT.md):** every member sees every community in V1, and `community_members` exists but is unused. "Onde você mais participa" and the per-community views count interactions by `feed_posts.community_id`, not by membership.
- **Directory [informational] (quick 261016-jsq):** `GET /v1/members` is staff-only. The owner panel's member lists are new admin-only reads, not a reuse of the directory.

### Cards with no data source
- **D-455:** a card, number or line that has no data source today shows **"Em breve"**. The card stays in its place with no number and a short notice that the measurement does not exist yet. It never shows a sample value, a zero or a dash pretending to be a measurement. Today this covers:
  - usage time and peak hours;
  - posts seen and post views;
  - reach;
  - video and reel playback (count, minutes, retention);
  - saves and shares;
  - story taps, link clicks and carousel progress;
  - the waitlist;
  - event ticket price and sales;
  - store offers;
  - support subjects;
  - members who left;
  - accesses about to expire.

  The existing `ReportValue` / `NotMeasuredReason` types in `packages/modules/dashboard/fixtures/shared.ts` are the natural carrier for this state.
- **D-456:** the same rule applies to the member panel and the owner panel. There is one "Em breve" behaviour and one notice string family.
- **D-457:** the prototype's order is kept. No card moves because it lacks data, so "Sua atividade" may open with its "Em breve" usage block (daily average, week chart, peak hours) on top. The user chose this over moving the real cards up.
- **D-458:** a mixed card shows its real parts with their numbers and marks only the missing lines "em breve". For example, "O que você viu" shows stories seen and marks posts and videos "em breve".

### Owner panel scope
- **D-459:** all six owner areas are wired in this phase, with every number that existing rows can answer and "Em breve" for the rest. When the phase closes, no runtime code path renders a fixture value.
  - Fixtures may stay for tests and component previews, but `apps/web` runtime imports of `@rede-social/module-dashboard/fixtures` values go away.
  - The panel keeps its 30-day window and its comparison with the 30 days before.
- **D-460:** an area disappears when the tenant's module behind it is off:
  - Eventos needs `events`;
  - Financeiro needs `store`;
  - Atendimento needs the support chat module;
  - per-community tabs, bands and cards need `communities`.

  The Visão geral cards that depend on a module that is off disappear too, as do the URL routes into a hidden area (`?area=…`), which fall back to Visão geral. Today the areas render regardless of module flags.
- **D-461:** action buttons are wired only where a screen already exists:
  - "Ver todos" opens the list behind the number;
  - "Responder" opens the support conversation or the post;
  - opening a member opens the member detail, and opening a post opens the post.

  Actions that need a new capability stay disabled, as today: "Enviar push" to a group and "Recuperar quem está em risco" as a campaign. "Ver operação do dia (painel do admin)" keeps opening Configurações.
- **D-462:** the per-member behavioural detail and every named list are readable by `admin_tenant` of the same tenant only. Named lists include:
  - members of a band;
  - who liked or commented;
  - a member's interactions, events and purchases;
  - who bought and how much.

  `support_tenant`, `member` and any other tenant get 403 from the API, not just a hidden screen. Every group total below 5 people or orders reads "menos de 5". The floor is applied by the API before the response leaves the server, not only by the web's `PRIVACY_FLOOR` helper. Pending, not code: the privacy policy must describe this before the pilot go-live.
- **D-463:** "Sua atividade" stays visible to role `member` only, and it reads only the caller's own rows. The API takes the user from the session and has no user-id parameter. The member window is the last 7 complete days compared with the 7 before. Attendance uses the last 30 days, as the sample does.

### Refresh and data gaps
- **D-464:** the numbers are computed **once a day**. A worker job (pg-boss) builds each tenant's snapshot after local midnight in the tenant's timezone, and both panels read the stored snapshot instead of computing on open. The panels show when the snapshot was taken ("Atualizado às …"). The windows end yesterday; today is never included. — **Reversibility:** costly — the snapshot tables and the job are migrations plus a worker contract. Moving to on-open computation later means new read paths and dropping those tables.
- **D-465:** the three recorded-but-never-written columns are **not** filled in this phase, and their numbers show "Em breve" (D-455):
  - `memberships.deleted_at`: "saíram" and the net balance. No leave or removal flow exists. Blocks stay visible through the moderation log in Atendimento.
  - `chat_conversations.subject`: support subjects. Filling it would change the chat screens.
  - `store_entitlements.expires_at`: accesses expiring in 7 days. Timed access is a new store concept.

  The user left this to Claude's judgement. The reason is that each one is a new product capability, not a gap in a read.

### Claude's Discretion
- Lists behind an "Em breve" number do not open, and the number's "Ver todos" is disabled with the card.
- Rates whose input is missing are "Em breve" too: engagement rate over reach, reach by band, first-48h views, video retention.
- Rates whose inputs exist are real: interactions per post, RSVP-to-check-in attendance, repeat purchase.
- The engagement bands use only the actions that exist: like, comment, post, RSVP "vou", check-in and paid order, as `docs/pendencias-backend.md` item 10 lists them. The band thresholds follow the dashboard project's definitions in the fixtures.
- What a tenant sees before its first nightly snapshot (a new tenant, or the first deploy). It can be a one-off computation on first open or an explicit "primeira atualização amanhã" state, as long as it never falls back to samples.
- The snapshot's storage shape (one row per tenant per day with JSON, per-metric rows, or materialized views), the job schedule per timezone, retention of old snapshots, and how the 12-week trend and the cohort heatmap are stored.
- The API shape (one route per area, following the panel's `?area=` split, or a single route), as long as each area's numbers and paged lists are reachable and each is gated per D-460 and D-462.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- The fixture types in `packages/modules/dashboard/fixtures/` are the contract to implement. Moving them, or their zod twins, into a contracts surface lets the API and the web share them.
- `ReportValue<T>` (Measured | Example with `NotMeasuredReason`) already distinguishes measured values from unmeasured ones. "Em breve" (D-455) maps onto the not-measured branch, with the example value dropped.
- The web components are presentational and receive data as props or through the `lib/owner-*.ts` view helpers. About 25 web files import fixture values directly, and that set is the wiring surface.
- The tenant-timezone helpers: SQL `AT TIME ZONE tenants.timezone`, plus `tenantDayKey` (`apps/web/lib/events-view.ts`) and `tenantDayKeys` (`apps/web/lib/chat-view.ts`).
- pg-boss workers already run scheduled and armed jobs (08.6 live reminders, Phase 7 event reminders). The nightly snapshot is one more job.

### Data available today (from the codebase scout)
- **Interactions:**
  - `feed_likes` covers posts, comments and stories;
  - `feed_comments` has `deleted_at`, `parent_id` and `story_id`;
  - `feed_posts` has `community_id`, `media_kind` (none/gallery/video), `feed_post_media` and `link_preview_id`;
  - `story_views` holds unique story views.
- **Events:** `event_attendances` has one row per user with status going / not_going / checked_in / walk_in and `checked_in_at`, plus `events.capacity`, `format`, `starts_at` and `ends_at`.
- **Store:** `store_orders` has `paid_at`, `revoked_at` and `amount_cents`, plus `store_entitlements` and `store_product_communities`.
- **Support:** `chat_conversations` (kind support, `last_staff_seq`) and `chat_messages` (`author_side`, `author_user_id`) give the queue and the first-response time.
- **Moderation:** `moderation_log` records comment_removed, member_blocked and member_unblocked.
- **Members:** `memberships.joined_at` and `blocked_at`, and `push_subscriptions` for "with push".
- **Recorded but never written:** `memberships.deleted_at`, `chat_conversations.subject` and `store_entitlements.expires_at` (D-465).
- **No table at all:** usage sessions, post views and reach, playback, saves, shares, carousel and link clicks, story taps, the waitlist, tickets and offers (D-455).

### Established Patterns
- Business reads go through the Hono API with RLS and the `api_user` role. Aggregates that cross member rows are likely security-definer functions with explicit tenant and role checks, like the 08.6 member projection. Every new route joins the isolation route inventory (`apps/api/tests/integration/isolation.test.ts`) and gets cross-tenant pgTAP negatives.
- Module flags gate UI and API alike (`moduleFlags()` in `apps/web/lib/profile-activity-view.ts` on the web).

### Integration Points
- `/perfil` (server component) builds both panels. The URL state of the owner panel (`?area=`, `&faixa=`, `&membro=`, `&lista=`, `&vista=`, `&post=`, `&produto=`) stays as is.
- The worker service (`apps/worker`, pg-boss) runs the nightly snapshot job.
- Migrations: new snapshot storage and any definers. This phase runs after 08.6, so its migrations chain after 08.6's.

## Specific Ideas

- The panels must make it obvious when the numbers were taken ("Atualizado às …"), because they are a day behind by design (D-464).
- "Em breve" is a promise that the number is coming, not an apology. The copy is decided in the UI-SPEC, in pt-BR, and is identical across both panels (D-456).
