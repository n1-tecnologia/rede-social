## Summary

The two `/perfil` panels are already built as presentational RSC components fed by fixtures that are shaped like API answers (cents, ISO dates, enums). The phase is a read path: (1) a nightly per-tenant snapshot built by the worker in the tenant's timezone, (2) admin-only and member-only Hono routes that read that snapshot (numbers) and bounded live queries (the named lists behind the numbers), and (3) re-wiring 27 web runtime files from fixture values to API answers, with one "Em breve" state for everything that has no source.

Every metric that the CONTEXT lists as computable was verified against the drizzle schemas and migrations this session. Corrections to the CONTEXT summary: there is no `apps/worker` (the worker is `ROLE=worker` of `apps/api`, `apps/api/src/worker.ts`); `moderation_log` has a fourth action `role_changed`; `stories` has no `community_id` (stories never count per community); `push_subscriptions`, `notifications` and `store_orders` are owner-only (or own-or-admin) under RLS, so the snapshot cannot be built from a plain tenant lane and needs a SECURITY DEFINER builder; `user_id` is shared across tenants since 08.1, so every per-member aggregate must pin `tenant_id` as well as `user_id`.

The repo has **no scheduler** (`boss.schedule()` is unused on purpose; periodic work re-arms deferred jobs under a constant `singletonKey`). The recommended design keeps that: a kernel "daily per-tenant dispatcher" that re-arms hourly and enqueues one idempotent build job per active tenant for its local yesterday, plus a dashboard-owned build job that calls one definer `app.dashboard_build_snapshot(p_day date)`. Storage: one row per tenant per day (JSONB payload of aggregates and ids, retained ~8 days) plus one row per member per tenant (latest only, overwritten) holding band, band history, insight numbers and the member's own "Sua atividade" payload. Materialized views are rejected (no RLS, all-tenant refresh).

**Primary recommendation:** Build a tracer first (snapshot tables + definer + dispatcher/build job + `GET /v1/dashboard/owner/overview` + the Visão geral members card wired + isolation and pgTAP entries), then one plan per area, each owning its SQL area function, its routes, its web wiring and its tests. Compute numbers set-based in SQL, shape and floor them in TypeScript, join names and captions live at read time.

## Snapshot Design (D-464)

### Storage (recommended)

```
dashboard_snapshots            -- one row per tenant per local day (aggregates + ids, no names)
  tenant_id uuid  → tenants   (PK part)
  snapshot_day date           (PK part; = D, the last complete local day)
  payload_version int         (bumped when the payload shape changes)
  built_at timestamptz        ("Atualizado às")
  window jsonb                ({ day30From, dayTo, day7From, … } as ISO dates)
  payload jsonb               ({ overview, members, content, events, finance, support } aggregates)
  RLS: select to authenticated using (tenant_id = app.tenant_id() and app.tenant_role() = 'admin_tenant')
  no insert/update/delete policy (written only by the definer)

dashboard_member_snapshots     -- one row per member per tenant, LATEST only (overwritten nightly)
  tenant_id uuid, membership_id uuid, user_id uuid   (PK (tenant_id, membership_id); index (tenant_id, user_id))
  snapshot_day date, band text, band_d30 text, band_d60 text, last_active_at timestamptz,
  active_days_30 int, strong_30 int, top_community_id uuid, community_bands jsonb,
  has_push boolean, insights jsonb (last30 counts, weeklyActiveDays[12], communities, postTypes),
  activity jsonb (the member's own "Sua atividade" numbers)
  RLS: select using (tenant_id = app.tenant_id() and (user_id = app.user_id() or app.tenant_role() = 'admin_tenant'))
```

Why this shape:
- Numbers come from the snapshot (D-464); names, captions, covers and community titles are joined **live at read time** from ids, so edits, deletions and privacy changes take effect immediately and no member name is ever stored in a snapshot.
- Movement, cohorts, 12-week trends and deltas are computed **inside each build** from raw rows (the previous window is just another range), so no history table is needed. Keep tenant rows ~8 days (diagnostics), member rows latest only.
- Size: tenant payload ≈ 20–60 KB (61 posts × ids/counts, events, heatmap cells, weekly arrays) × 8 days; member rows ≈ 0.5–1 KB × members. A 1,000-member tenant ≈ 1 MB total. Free plan budget is 500 MB `[CITED: supabase.com/pricing]`.

### Build (one definer, many area functions)

- `app.dashboard_build_snapshot(p_day date) returns void` — `language plpgsql security definer set search_path = ''`, every statement pins `tenant_id = app.tenant_id()`, refuses unless the claims are the dashboard system lane (zero user `00000000-0000-0000-0000-000000000000`, the courses/events system-context convention `[VERIFIED: packages/modules/courses/server/system-context.ts:8-34]`) and `p_day < (now() at time zone tz)::date` (today is never included). It deletes and re-inserts the tenant's member rows and upserts the `(tenant_id, p_day)` tenant row **in one transaction** (atomic swap).
- Per-area helper definers (`app.dashboard_area_members(p_day)`, `…_content`, `…_events`, `…_finance`, `…_support`, `…_overview`) return `jsonb`; EXECUTE revoked from PUBLIC and granted to nobody (only the owner-run builder calls them). Each area plan adds its function and replaces the builder (`create or replace`) to include its key. This maps one plan to one function, which keeps plans independent.
- Why a definer and not a plain tenant lane: `push_subscriptions` select is owner-only (`tenant_id = app.tenant_id() and user_id = app.user_id()`) `[VERIFIED: packages/modules/notifications/db/schema.ts:170-174]`; `store_orders` is `OWN_OR_ADMIN` `[VERIFIED: packages/modules/store/db/schema.ts:203]`; member-lane restrictive community gates hide locked posts and comments. The definer reads everything of one tenant in one statement set.

### Schedule (no cron; the repo's re-arm pattern)

1. **Kernel dispatcher** `kernel.daily-tenant-dispatch` in `packages/core/server/tenancy/` (admin lane allowed there by Biome): every run reads `select id, timezone, ((now() at time zone timezone)::date - 1) as day from tenants where status = 'active'` and, for every queue registered through a new seam `registerDailyTenantJobs([...])` (the `registerSweepFunctions` pattern, `packages/core/server/jobs/sweep-functions.ts:20-35`), enqueues `{ tenantId, day }` with `singletonKey = "<tenantId>:<day>"` and a short `deleteAfterSeconds`; then re-arms itself `startAfter: 3600` under a constant singleton (the `armSweeper` shape `[VERIFIED: packages/core/server/media/service.ts:1092-1101]`). Armed best-effort at worker boot, like the sweeper. The kernel names only its own `tenants` table (MOD-02 holds).
2. **Dashboard build job** `dashboard.snapshot-build` (exported from `@rede-social/module-dashboard/server`, composed in `apps/api/src/worker.ts` and registered in `apps/api/src/modules/registry.ts` because the dashboard has no manifest/ModuleKey): validates the payload with zod (drop a bad payload, never throw — the reminder rule), opens `withTenantTx(dashboardSystemCtx(tenantId))` and runs `select app.dashboard_build_snapshot(${day}::date)`. Idempotent: the builder returns early when a row for `(tenant, day)` already exists at the current `payload_version`.
3. Effect: every tenant gets its snapshot during the first dispatcher run after its local midnight (≤ 1 h late), missed nights self-heal, a deploy (new worker revision) rebuilds every tenant within minutes, a `payload_version` bump rebuilds stale shapes. DST-safe because local days come from `AT TIME ZONE` in SQL; `America/Sao_Paulo` has had no DST since 2019 `[ASSUMED]`.

### Before the first snapshot / gaps
- No snapshot row (new tenant, first deploy before the worker ran) → the API answers `200 { state: 'preparing' }` and the panel renders an explicit "preparing" card (copy in UI-SPEC: e.g. "Seus números ficam prontos em até 1 hora"). Never a sample, zero or dash. GETs stay side-effect free (no enqueue from a read); the hourly dispatcher covers it.
- A member with no member row (joined after the last build) → `{ state: 'preparing' }` for "Sua atividade" ("Seus números aparecem amanhã").
- A snapshot whose `payload_version` is older than the API's → treat as `preparing` for the changed area (the dispatcher rebuilds it).
- The latest snapshot is older than yesterday (a failed build) → serve it and show its real date in "Atualizado em …" (honest, never re-labelled).

### Lists: snapshot or live? (recommendation)
- **Numbers**: always snapshot (D-464).
- **Band membership, band history, insight numbers**: snapshot (member rows) — so a band list has exactly the band's count.
- **Named rows behind a number** (who liked post X, a member's likes, buyers of a product, interactions): **live reads in the admin's tenant lane, bounded by the snapshot's window** (`created_at >= window start and < end of D`, passed from the snapshot row, never `now()`), joined to live profiles and to the member rows for bands. They then agree with the number except for rows deleted since the build (acceptable; a deleted comment disappears from both on the next build).
- Paging: keyset with `@rede-social/core/server/paging` (opaque cursor, `limit` clamp 1..50), most recent first.

### Retention
Register `app.dashboard_snapshots_sweep(p_batch int) returns int` (deletes tenant rows older than 8 days, at most `p_batch`) through `registerSweepFunctions` in the app registry; the hourly media sweeper runs it in the admin lane `[VERIFIED: packages/core/server/media/sweep-job.ts:56-62, 95-108]`. Member rows need no sweep (overwritten); rows of memberships that became blocked are dropped at the next build.

```sql
b as (
  select tz.timezone,
         ((p_day - 29)::timestamp at time zone tz.timezone) as from30,   -- local midnight D-29 → instant
         ((p_day + 1)::timestamp  at time zone tz.timezone) as until     -- local midnight D+1 → instant
    from tz)
select (l.created_at at time zone b.timezone)::date as day, count(*)
  from public.feed_likes l cross join b
 where l.tenant_id = app.tenant_id()
   and l.created_at >= b.from30 and l.created_at < b.until
 group by 1;
```

### Pattern 2: Bands in one pass
```sql
-- days(user_id, day, strong) built from the counted-action union (see Metric Inventory), back to D-119
select m.membership_id, m.user_id,
  case
    when (m.joined_at at time zone b.timezone)::date > p_day - 30          then 'new'
    when count(d.day) filter (where d.day > p_day - 30) >= 12
     and coalesce(sum(d.strong) filter (where d.day > p_day - 30), 0) >= 3 then 'superfan'
    when count(d.day) filter (where d.day > p_day - 30) >= 4              then 'engaged'
    when count(d.day) filter (where d.day > p_day - 30) >= 1              then 'occasional'
    when count(d.day) filter (where d.day between p_day - 59 and p_day - 30) >= 1 then 'at_risk'
    else 'inactive'
  end as band
from members m cross join b
left join days d on d.user_id = m.user_id          -- days already pinned to this tenant
group by m.membership_id, m.user_id, m.joined_at, b.timezone;
-- NB: count(d.day), not count(*): the left join's null row must not count as an active day.
```
The same expression with `p_day - 30` and `p_day - 60` gives `band_d30` / `band_d60` (movement, band history).

### Pattern 3: Week streak (gaps and islands over ISO weeks)
```sql
with w as (select distinct date_trunc('week', d.day)::date as wk from days d where d.user_id = $user),
anchor as (select case when exists (select 1 from w where wk = date_trunc('week', p_day)::date)
                       then date_trunc('week', p_day)::date
                       when exists (select 1 from w where wk = date_trunc('week', p_day)::date - 7)
                       then date_trunc('week', p_day)::date - 7 end as s),
isl as (select wk, wk - 7 * (row_number() over (order by wk))::int as grp from w)
select coalesce((select count(*) from isl where grp = (select i.grp from isl i join anchor a on i.wk = a.s)), 0);
```

```typescript
owner.use('*', requireAuth);

```

### Pattern 5: "Em breve" and floor in the contract
```typescript
// zod, packages/modules/dashboard/contracts — NO ExampleValue in any API schema (D-455)
export const notMeasuredSchema = z.object({ measured: z.literal(false), reason: notMeasuredReasonSchema });
export const measured = <T extends z.ZodTypeAny>(v: T) =>
  z.discriminatedUnion('measured', [z.object({ measured: z.literal(true), value: v }), notMeasuredSchema]);
export const flooredCount = z.discriminatedUnion('belowFloor', [
  z.object({ belowFloor: z.literal(true) }),                 // no value field at all
  z.object({ belowFloor: z.literal(false), value: z.number().int().nonnegative() }),
]);
```

### Anti-Patterns to Avoid
- **Computing on open:** contradicts D-464 and is the costly path; only names/rows behind numbers are live.
- **`(created_at at time zone tz)::date between …` in WHERE:** defeats indexes; use Pattern 1.
- **Filtering only by `user_id`:** a shared identity (08.1) has the same `user_id` in two tenants.
- **Reading `like_count`/`comment_count` for windowed numbers:** includes today and staff; count rows up to end of D.
- **Storing names, captions or comment text in a snapshot:** labels are joined live; snapshots hold ids and numbers.
- **Sending a floored value with a flag:** the number must not be in the JSON at all.
- **Validating URL params against fixtures:** replace with syntactic parse + data check after the fetch.

## Common Pitfalls

### Pitfall 1: Shared identity leaks across tenants
**What goes wrong:** per-member aggregates keyed only by `user_id` merge a person's activity in two tenants.
**Why:** 08.1 dropped `memberships_one_tenant_per_user_v1` (`DROP INDEX "memberships_one_tenant_per_user_v1";`) `[VERIFIED: supabase/migrations/20261006195908_multi_tenant_identity.sql:1]`.
**How to avoid:** every source table predicate carries `tenant_id = app.tenant_id()`; member rows keyed by `(tenant_id, membership_id)`. **Warning sign:** a pgTAP `160-shared-identity` case shows tenant B's like in tenant A's count.

### Pitfall 2: Story view privacy regression
**What goes wrong:** exposing who viewed a story, or a per-band split that singles someone out.
**Why:** the 05.2 rule on `story_views` says "No endpoint, event, payload or log line reveals which member saw which story, and no view COUNT exists anywhere" `[VERIFIED: packages/modules/stories/db/schema.ts:254-256]`; this phase introduces aggregate counts (ROADMAP SC 2: "unique story views as totals").
**How to avoid:** totals only, story reach by band floored/merged, no list for views/reach (P3); update that schema comment and the stories README in the same plan.

### Pitfall 3: Snapshot shape drift after deploy
**What goes wrong:** a new API parses an old payload and 500s, or renders missing keys as zero.
**How to avoid:** `payload_version`; zod-parse per area; older version → `preparing` for that area; the dispatcher rebuilds on the next run.

### Pitfall 4: Counting today or staff
**What goes wrong:** numbers move during the day; admins' own likes inflate engagement.
**How to avoid:** windows end at end of D; count rows by `role = 'member'` authors for member metrics; never `like_count`.

### Pitfall 5: Soft-deletes and cancellations
**How to avoid:** `feed_posts.deleted_at is null`, `feed_comments.deleted_at is null` (moderated comments never count), `stories.deleted_at is null`, `events.status = 'active' and deleted_at is null`, store `status = 'paid'` (revoked rows keep `paid_at`), communities `status`/`deleted_at` for labels, chat `deleted_at`.

### Pitfall 6: RSVP dating
**What goes wrong:** using `created_at` for "RSVP vou" or counting `not_going`.
**Why:** `responded_at` is "The LAST RSVP answer's instant, kept after check-in. Null only on a walk-in" `[VERIFIED: packages/modules/events/db/schema.ts:269]`.
**How to avoid:** RSVP action = `status in ('going','checked_in')` dated `responded_at`; check-in dated `checked_in_at`.

### Pitfall 7: Fixture-validated URL params
**What goes wrong:** `owner-band-scope.ts` accepts only `om-NN` ids and `c-` slugs (`OWNER_MEMBER_IDS = ownerBandRoster.map(…)`); real uuids fall back silently forever.
**How to avoid:** syntactic parse (uuid/enum) then data check against the API answer; keep D-06 "fall one level up".

### Pitfall 8: Heatmap slots do not cover the day
**What goes wrong:** the fixture slots are `[7,10],[12,14],[18,20],[20,22]` `[VERIFIED: packages/modules/dashboard/fixtures/owner-content.ts:506-511]`; a post at 15:00 lands nowhere and rows stop adding up to `byWeekday`.
**How to avoid:** API defines a full-day partition (or an "outros horários" bucket); UI-SPEC confirms the slot labels.

### Pitfall 9: Streak and window edges
**How to avoid:** pgTAP cases at 02:30 UTC (= 23:30 previous day in São Paulo), D-29 vs D-30, 11/12 active days, 2/3 strong actions, joined 29/30 days ago, week anchor when the current week has no action yet.

### Pitfall 10: No scheduler, queue policy
**What goes wrong:** creating a queue with another policy, or expecting cron.
**Why:** `createQueues` throws "pg-boss queue policy mismatch" when a queue exists with a different policy `[VERIFIED: packages/core/server/jobs/boss.ts:77-91]`.
**How to avoid:** new queue names, created by `createQueues` at worker start and lazily by the API; never pre-create by hand.

### Pitfall 11: Lane restrictions
**What goes wrong:** a module importing `@rede-social/core/db/admin-tx` (Biome error "Admin lane is kernel-only") or `@rede-social/core/db` ("A module reaches data only through withTenantTx").
**How to avoid:** the tenant enumeration lives in `packages/core/server/tenancy/`; the module job uses `withTenantTx(systemCtx)`.

### Pitfall 12: pgTAP 040 conventions
**What goes wrong:** a definer with `limit 1` trips 040's allow-list (`p.prosrc ilike '%limit 1%'`) `[VERIFIED: supabase/tests/040-schema-conventions.sql:263-271]`.
**How to avoid:** no `limit 1` in new definers; `search_path = ''`; revoke from PUBLIC.

### Pitfall 13: Test data has no history
**What goes wrong:** the seed writes everything "now" (local: 20 memberships, 24 likes, 0 orders); integration counts depend on run time; seed-pinned tests break (memory).
**How to avoid:** integration tests insert rows with explicit timestamps through `adminSql` and build with an explicit `p_day`; `pnpm test:integration -- x` does not filter (use `pnpm --filter @rede-social/api exec vitest run tests/integration/<file>`); run pgTAP before integration.

### Pitfall 14: Module gating side effects
**What goes wrong:** Atendimento also holds Moderação; with chat off, moderation disappears with the area (D-460 literal reading). Feed off empties Conteúdo (not covered by D-460).
**How to avoid:** Open question 2.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-tenant id probing (member, post, event, product ids) | Information disclosure | Tenant-lane RLS + bare 404, isolation sweep with positive control |
| Member reading another member's activity | Information disclosure | No user parameter; self-only RLS row |
| `support_tenant` reading named lists | Elevation of privilege | `requireRole('admin_tenant')` + admin-only RLS on snapshots |
| Small-group inference (subtracting bands from totals) | Information disclosure | Floor + `mergeBandsBelowFloor` in the API |
| Definer misuse from a request lane | Tampering / DoS | Zero-user guard, tenant pin, idempotent upsert, EXECUTE revoked from PUBLIC; Data API closed (`20261009111139_data_api_closed_schema.sql`) |
| Shared identity cross-tenant merge | Information disclosure | `tenant_id` on every predicate; pgTAP 160 case |
| Expensive list queries | DoS | Bounded windows, keyset paging, indexes (Risk 1) |

## Risks

1. **Query cost on large tenants.** `feed_likes` has only `(tenant_id, post_id)` and per-user unique indexes; `feed_comments` has per-post/parent indexes; `store_orders` has `(tenant_id, user_id)`. A window scan by `created_at` is a sequential scan at scale. Recommendation: add expand-only indexes `feed_likes (tenant_id, created_at)`, `feed_comments (tenant_id, created_at)`, `store_orders (tenant_id, paid_at)` in the feed/store drizzle schemas, and pin their existence in pgTAP (a plan assertion is meaningless on the 24-row seed). Log build duration per tenant.
2. **Free-plan database.** Shared compute; builds run one tenant per transaction in the worker (concurrency 1), off-peak (after local midnight). Storage is negligible with the recommended shape.
3. **Timezone edge cases.** `tenants.timezone` is free text with no CHECK; an invalid zone makes `AT TIME ZONE` raise, failing only that tenant's build (isolated job). Platform schema exposes but does not write it today.
4. **Week streak definition** (A1) and **band thresholds** — copy the fixture constants into one SQL place and test their edges; `MIN_STREAK_WEEKS = 2` stays a web display rule.
5. **Privacy policy text** (D-462 pending, not code): the go-live checklist must include it; the README privacy sections already list the notices.
6. **Payload growth across plans:** each area plan bumps `payload_version`; the dispatcher rebuilds — remember to bump.
