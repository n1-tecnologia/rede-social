<objective>
The feed tracer (FEED-02, FEED-08, MOD-03, UI-02): `@tria/module-feed` becomes the first real feature module and one thin path is wired through every layer this phase will touch — `feed_posts` in Postgres under RLS, a keyset-paginated `GET /v1/feed` and a permission-guarded `POST /v1/feed/posts` in the Hono tenant lane, the after-commit `post.published` domain event, the single `apps/web/lib/feed.ts` fetch implementation, and a D-55 home-slot widget that renders the tenant's posts as `PostCard`s on `/inicio`.

Purpose: this is the architecture-proving slice. Every later plan in the phase expands outward from it — likes and comments hang off `feed_posts`, media hangs off the create path, the composer and the post page reuse `lib/feed.ts`, and Phases 5-7 copy the keyset/event/permission conventions fixed here. If the shape is wrong, it is wrong after one commit rather than after ten.
Output: the `packages/modules/feed/**` package skeleton, the `feed_posts` migration with its isolation cases, the kernel `requirePermission` seam, the web fetch + home slot + pt-BR catalog, and the integration/e2e/unit tests that drive the whole path.

**Phase goal (ROADMAP, verbatim — not in user-story form; see the planner note at the end of this file):** "`admin_tenant` publishes rich posts from a phone and members consume and interact with them in the branded feed; this phase fixes the content conventions (likes/comments shape, one-level replies, keyset pagination, after-commit domain events, share deep links) every later module copies."

**Decision — `requirePermission` is a kernel seam fed by the app tier.** FEED-08 requires the route guard and the composer's visibility to read ONE composed value, but `defaultRolePermissions` live in `apps/api/src/modules/registry.ts` and the kernel may never import a module (MOD-02). This plan adds `packages/core/server/rbac/permissions.ts` with `setPermissionResolver(fn)` — exactly the inversion `registerJobQueues` already uses for queue names — so the module's route can say `requirePermission('feed.post.create')` while the composition stays in the app tier.
</objective>

<assumption_delta_decision>
**Signal.** The assumption-delta detector fired two `pluralization` signals over this phase's scope: *"multiple images (swipeable carousel)"* and *"a member of another tenant"*. Both ask the same question — does the current identity model still name the right noun?

**Noun that is now primary: the generic `author_user_id` (any tenant member), not "the tenant's admin".**

**Decision: `promote`.** `feed_posts.author_user_id uuid not null references users(id)` is the primary authorship column from the first migration, and "only the admin may write" is demoted to a *permission value* (`tenant_modules['feed'].settings.postingPolicy`) rather than a schema fact. There is no `admin_user_id` column and no admin-only foreign key anywhere; the V1 restriction exists in exactly one place, and V2 member posting is a value change (FEED-08, V2-CONT-01).

Rationale: adding a member-author path alongside an admin-author column would silently contradict FEED-08's stated intent and would make V2 a migration. The promote is free today because no row exists yet.

**Companion invariant test (added as real work in Task 3):** `apps/api/tests/integration/feed.test.ts` contains a posting-policy case that flips `settings.postingPolicy` to `'members'`, has a plain `member` session create a post, and asserts the post round-trips through the same `author_user_id` path and renders in the feed — with no schema change and no route edit between the two runs. A future phase that reintroduces an admin-only authorship assumption goes red there.

(The second noun — a post's media as a *collection* rather than a single image — is promoted in 04-04, where `feed_post_media` is born as a positional child table with a `media_kind` discriminator on the parent rather than image columns on `feed_posts`.)
