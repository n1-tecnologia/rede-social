<objective>
The feed as a member actually uses it (FEED-02, FEED-04, UI-02): infinite scroll and pull-to-refresh over the single fetch implementation, the ported `PostCard` action and meta row, an optimistic like that reverts cleanly, and a double-tap on the gallery that likes exactly once.

Purpose: this is the plan that turns 04-01's card into the prototype's card. Roadmap criterion 2 names these interactions by name — "using the prototype's ported PostCard / CommentSheet interactions" — and this plan ships the PostCard half.
Output: the action row, the like control, the meta-row builder, the widget with its four states, the four server actions, and the mobile e2e that drives a real gesture.

**Decision — no client data-cache library.** `.claude/CLAUDE.md`'s stack table lists a client query cache, but the repo has never installed one and Phase 3 established the "one fetch implementation shared by the page and the load-more server action" pattern that already handles infinite scroll (03-05, `apps/web/lib/profile.ts`). Introducing a second data-fetching paradigm for the first feature that needs paging would fork the pattern. RESEARCH A1 flags the divergence from the CLAUDE.md table; this plan records the choice rather than making it silently, and Phase 7 — where Realtime invalidation genuinely wants a cache — is the natural place to revisit it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → server action | a server action is a public endpoint: its input is untrusted and is validated with the same schema the API route uses |
| optimistic client state → the count a member reads | the client may render ahead of the server but is never the arbiter; the server's value replaces it on response |
| server component → client component | only serialisable values and server-action references cross; a component object or a bare function does not |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-38 | Tampering | a forged post id or cursor sent to a server action | high | mitigate | Every action parses its input with the shared Zod schema before issuing a request, and the API re-authorises independently; a malformed value returns the generic key and never reaches SQL |
| T-04-39 | Spoofing | a member inflating a visible like count through the optimistic path | medium | mitigate | The optimistic value is local and is overwritten by the server's authoritative response; counters are trigger-owned, so no client path can write one |
| T-04-40 | Information Disclosure | a refusal message leaking why a request failed | medium | mitigate | Actions return the generic catalog key only; the shape-only console log carries no post content |
| T-04-41 | Denial of Service | a scroll burst issuing many load-more requests | medium | mitigate | The sentinel hook's re-entrancy guard allows one page in flight; a failed page stops the loop and waits for an explicit retry |
| T-04-42 | Tampering | copy injected through a server action's return value | low | mitigate | Actions return catalog keys, never text; the client translates, so no server-controlled string reaches the DOM unescaped |
</threat_model>
