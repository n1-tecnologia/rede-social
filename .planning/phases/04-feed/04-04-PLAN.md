<objective>
The media half of FEED-01: a post carries either an image gallery or one video — never both — plus any number of file attachments up to the cap, all of it reusing the Phase 3 broker end to end and adding zero upload, resize or transcode code.

Purpose: D-53's gallery-XOR-video rule is the constraint every renderer, every composer branch and Phase 5's stories inherit. Making it a *declarative database* rule rather than a composer rule is what stops a post existing that no renderer can draw.
Output: `feed_post_media` with its composite-foreign-key discriminator, the API-side asset validation, the `PostMedia` renderer with its gallery carousel and attachment rows, and the pgTAP/integration/e2e proof.

**Decision — `MediaImage` is promoted, `VideoPlayer` is injected.** `packages/modules/feed/ui` may not import from `apps/web` (MOD-02), but the post gallery must render through Phase 3's `MediaImage`. `MediaImage` depends only on `@tria/contracts/media` and `@tria/ui`, so it moves into `@tria/core/ui` with a one-line re-export left behind at its old path — every Phase 3 call site is untouched. `VideoPlayer` does NOT move: it binds an app-scoped server action for the per-request playback token (D-44) and the next-intl catalog, so `PostMedia` accepts it as a `video?: ReactNode` prop — an already-created client element, which crosses the RSC boundary safely (unlike a component object, which is what 02-08 found Flight refuses).

**Decision — the attachment download is a fetch-then-save through the BFF, not a signed URL in a payload.** 03-01 forbids a signed Storage URL in any API payload, so there is no "give me a download URL" route. The row fetches `/v1/media/{assetId}/original` through the existing Next BFF handler (which forwards the API's tenant-checked 302), reads the response as a blob, hands it to the browser through a temporary object URL and revokes it. That gives UI-D-23 its real pending and error states, keeps the signed URL inside the redirect chain, and adds no API surface. The 25 MiB attachment cap bounds the memory cost.
</objective>

<assumption_delta_decision>
**Signal.** The `pluralization` signal *"multiple images (swipeable carousel)"* asks whether a post's media identity is still singular.

**Noun that is now primary: the ordered media COLLECTION (`feed_post_media` rows), not "the post's image".**

**Decision: `promote`.** There is no `image_asset_id` or `video_asset_id` column on `feed_posts` and none is added. The parent keeps only a `media_kind` discriminator, and every asset — first image, tenth image, the single video, every attachment — is a row in `feed_post_media` with a `position`. A single-image post is the one-row case of the collection, not a special column.

Rationale: adding `image_asset_id` alongside the collection "for the common case" would give two sources of truth for the same fact and would make the carousel's ordering ambiguous. The promote is free today because no row exists yet, and it is what lets D-53's rule be a constraint on the parent's discriminator rather than a coordination problem between two columns.

**Companion invariant (real work in Task 3):** `apps/api/tests/integration/feed-media.test.ts` asserts that a single-image post and a ten-image post round-trip through the *same* `feed_post_media` path with the same projection shape, and that no response field names a singular image asset. A future phase that reintroduces a singular column goes red there.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Storage | signed direct upload and signed read only; bytes never pass through Cloud Run |
| composer input → `feed_post_media` | an asset id in a request body is untrusted: it is validated against the caller's own tenant, purpose and status before it becomes a row |
| attachment bytes → the viewer's device | the download resolves through the tenant-checked `/v1/media/{assetId}/original` redirect; no signed URL is ever handed to application code |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-22 | Elevation of Privilege | attaching another tenant's asset id to a post | high | mitigate | The validation read runs in the tenant lane, so a foreign asset simply does not come back; the refusal is `400 { media: 'asset_not_usable' }` with no id echoed, and an integration case asserts the body names no tenant |
| T-04-23 | Information Disclosure | a signed Storage URL leaking into a payload, log or the DOM | high | mitigate | Images render through the stable `/v1/media/{assetId}/{variant}` redirect; the attachment download reads the redirect's body rather than its Location; a grep gate bans a signed-URL field from the attachment component |
| T-04-24 | Tampering | a post that presents both a gallery and a video | medium | mitigate | Composite foreign key plus CHECK on `post_media_kind`, and a partial unique for the single video — enforced at the index, pgTAP-pinned on four illegal shapes |
| T-04-25 | Denial of Service | a post with thousands of media rows | medium | mitigate | `FEED_MAX_IMAGES` and `FEED_MAX_ATTACHMENTS` are enforced in the create path before any insert; the arrays are bounded by Zod before the handler runs |
| T-04-26 | Denial of Service | an oversized attachment exhausting the viewer's memory during download | low | accept | Attachments are PDF-only at 25 MiB (Phase 3's `MEDIA_LIMITS`), which bounds the blob; a streaming save would need a signed URL in a payload, which 03-01 forbids |
| T-04-27 | Tampering | an unplayable source (HEVC/MOV) stored as the playback source | medium | mitigate | Video goes through the Phase 3 `VideoProvider` seam; the feed never references a raw video object, only the provider-brokered asset |
| T-04-28 | Information Disclosure | a filename disclosing internal structure in the card | low | accept | The stored filename is the one the admin uploaded; it is the admin's own tenant's content |
