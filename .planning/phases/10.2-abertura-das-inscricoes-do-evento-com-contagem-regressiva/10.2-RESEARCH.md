# Phase 10.2: Abertura das inscrições do evento com contagem regressiva - Research

**Researched:** 2026-11-13
**Domain:** extending the Phase 10.1 paid event (events module read models and write path, the SQL definers behind them, the payments Eventos recentes list) with an optional, lockable opening instant, a server-seeded live countdown and an early-payment mark
**Confidence:** HIGH on every codebase fact (each discrete value below was read from the file this session, with path and line range); MEDIUM on Postgres lock ordering between a BEFORE UPDATE trigger and the grant definer (reasoned, to be proved by a two-connection integration test); LOW on whether Apple/Google store policy reaches event tickets (not decided here, see Open Questions)

## Summary

The phase is small in new tables (none) and wide in touch points: two nullable columns, one redefined read definer, one new trigger, one extended grant, one extended reset, about six read-model and view-model files, one new client component, one pure formatter and one form field. Everything it needs already exists in 10.1: the paid flag (`app.event_is_paid`), the single link decider (`app.event_checkout_url`), the lock count (`app.event_ticket_lock` / `app.event_ticket_admin.sold`), the omit-keeps / null-clears write rule (`ticketPriceCents`), the wall-clock pair and its SQL zone conversion, `useBoundaryRefresh`, and the persistent live wrapper of `PaidEventZone`.

Four findings change the plan relative to CONTEXT and UI-SPEC and are listed first under "Corrections to carry into planning". The ones that matter most: (1) `responded_at` is NOT a stable early-payment marker, because the grant's upgrade branch (an existing `going` row that becomes `ticket`) never touches it; a dedicated instant written by the grant is the fix; (2) the web cannot place `Venda indisponível` before `Em breve` from `checkoutUrl` alone (null for both reasons), so the detail needs one more boolean fact; (3) the countdown seed should be the database `now()` of the same transaction that decided the link, carried by the API, not the web server's `Date.now()`; (4) the native plan 13-18 does not cover the event ticket zone at all, contrary to CONTEXT.

**Primary recommendation:** ship three migrations (one generated: two nullable columns and two CHECKs; two hand-written: the definers, the opening trigger, the grant and guard redefinitions), keep `app.event_checkout_url` as the only place the link is decided and make it return null before `registration_opens_at` by the DB clock, put the lock in a BEFORE UPDATE trigger on `events` (not in the service), clear the date inside `app.event_ticket_reset` so it is atomic with the mapping removal, and carry `registrationOpensAt` + `serverNow` (both `.optional()`, only on paid events) through the shared projection.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Who it applies to, and the rules (answered by Igor on 2026-11-13)**
- **D-780: The opening applies only to paid events** (an event with a linked gateway product, D-740). A free event has no field, no `Em breve`, no opening countdown, and keeps its `Faltam N dias` untouched. — **Reversibility:** reversible — extending it to free events later is a new rule on the same column, no migration.
- **D-781: The opening date is optional; no date means open at once.** Every existing event has no date and behaves as today. The column is nullable and the migration is expand-only. — **Reversibility:** reversible — a nullable column added to `events`, nothing rewritten.
- **D-782: A payment that arrives before the opening confirms the presence anyway.** The money is already charged and D-750/D-751 already say the paid path never refuses a willing buyer. The grant definer gets **no** opening-time check. The presence is marked `Antes da abertura` for the admin (D-791). — **Reversibility:** costly — refusing early payments later would mean refunds and a new refusal path in the webhook branch.
- **D-783: Once the event has at least one paid presence, the opening date cannot be changed.** Same lock family as D-747 (the product locks after the first sale). **Only a paid presence locks it**: a courtesy (`Cortesia`) and a presence made before the ticket existed (`Anterior ao ingresso`) do not, so an old event with confirmed people can still be given an opening date. The refusal is a stable machine code from the API and the database, not only a disabled field. How a fully refunded sale counts follows `app.event_ticket_lock` (the planner reads it and states the rule). — **Reversibility:** costly — the refusal code joins the closed `EVENT_ISSUES` list, which is an external contract once released.

**The event while it is "Em breve" (answered by Igor on 2026-11-13)**
- **D-784: The card's tag is `Em breve` in place of `Pago` while the sale is closed.** One tag, not two. When the sale opens the card goes back to `Pago` (D-753). A member who already holds a presence never sees `Em breve` (they see their confirmed state, D-790). — **Reversibility:** reversible — copy and one view-model branch.
- **D-785: The countdown shows on the card and on the page.** The card, which is small, carries a short text, `Abre em 2 d 4 h 13 min`. The page carries three blocks, `02 dias · 04 horas · 13 min`. — **Reversibility:** reversible — presentation only.
- **D-786: On the page the buy zone is replaced by the countdown block plus the exact opening date and time** in the tenant's time zone (for example `20 nov, 10:00`). The reference price (D-755), when the admin filled it, **stays visible** on the card and on the page while the event is `Em breve`. — **Reversibility:** reversible — presentation only.
- **D-787: Units that are zero disappear.** With one day left the counter reads `23 h 40 min`; under an hour, `40 min`; under a minute, `Menos de 1 min`. The same rule applies to the countdown to the event (D-790). — **Reversibility:** reversible — a formatting function.
- **D-788: At zero the page swaps to the buy zone by itself, with no manual reload.** The countdown starts from **server time**, not from the device clock, and the link appears only when the API returns it (the page re-reads the event at the boundary). A phone with a wrong clock must not show a wrong count nor reveal a link early. *(Taken from the brief and Igor's rule that the server blocks; not asked as a separate question.)* — **Reversibility:** costly — the seed of the countdown becomes part of the event read model that older and newer clients parse.
- **D-789: The server blocks the purchase, the screen only reflects it.** Before the opening the API does not return the purchase link (`checkoutUrl`) and the web shows no `Comprar ingresso`. The link is returned only on the event detail today and only through `app.event_checkout_url`, which is the single SQL place that decides (research confirms; it must return null before the opening, by the database's own clock). — **Reversibility:** costly — the definer is a published SQL name used by the read model.

**The countdown to the event (answered by Igor on 2026-11-13)**
- **D-790: A member who holds a presence in a paid event (paid, courtesy or before-the-ticket) sees days, hours and minutes to the event, always, not only in the last week.** It replaces `Faltam N dias` on the event page's hero and on the `Meus eventos` cards **for paid events only**; a free event keeps `Faltam N dias`. Near the start it hands over to what already exists: the check-in window (D-209), `Ao vivo`, `Hoje`. — **Reversibility:** reversible — presentation, plus one new live component.

**A payment before the opening (answered by Igor on 2026-11-13)**
- **D-791: The admin learns about it only through a mark, with no new notification.** In `Participantes` the presence shows `Pago` and, next to it, `Antes da abertura`; the delivery in `Eventos recentes` carries the same marker. The mark is derived by comparing the moment the presence was confirmed with the opening instant (never stored apart from the event, because the date is locked once a paid presence exists, D-783). The member who paid early gets the same `Presença confirmada` notice as anyone (D-756) and sees their confirmed state with the countdown to the event. — **Reversibility:** reversible — a derived mark.

**The admin's form (answered by Igor on 2026-11-13)**
- **D-792: The field `Abertura das inscrições` lives inside the `Ingresso` section**, only visible when `Cobrar ingresso` is on, right below the reference price. It is a date and a time in the tenant's time zone, the same wall-clock pair as the event's start and end, converted to UTC in SQL like them. — **Reversibility:** reversible — form placement.
- **D-793: Turning `Cobrar ingresso` off clears the opening date.** The event becomes free and open at once; the form warns before saving; turning the ticket on again means typing the date again. — **Reversibility:** reversible — a form and write rule.
- **D-794: With a paid presence the field is read-only** and says so in the pattern of the locked product (`N ingressos vendidos`): the opening date, and the reason it cannot change. — **Reversibility:** reversible — presentation of D-783.

### Claude's Discretion
- **The date must be before the event's start.** A date already in the past is **accepted** (it simply means open), so editing an old event never fails because its opening passed. The issue codes for this are the planner's, added to the closed list as optional-compatible additions.
- **Precedence of states in the buy zone:** cancelled or ended first, then `Venda indisponível` (D-746, the module is off or the gateway is disconnected), then `Em breve`, then `Esgotado`, then `Comprar ingresso`. Before the opening nobody can buy, so `Esgotado` never shows early.
- **Precedence in a presence holder's view:** a member who holds a presence is never in the `Em breve` state; they get the confirmed state and the countdown to the event.
- **Tick rate:** the counter changes at minute granularity, so it ticks once a minute aligned to the minute change, and stops when the tab is hidden.
- **Exact column and function names, the migration shape, the closed-list issue codes, the copy keys and every pt-BR string** (the ICU plurals follow the existing `events.json` style under `ticket.*`).
- **How the live seed is carried** (server instant plus a client offset against `Date.now()`, or an equivalent) and how to avoid a hydration mismatch, since no ticking client counter exists today.
- **Accessibility:** a countdown that changes every minute must not be announced every minute; the planner picks a polite, non-chatty pattern and respects reduced motion.
- **Native app:** nothing to build, the shell shows the web screens (Phase 13); the purchase-switch plan 13-18 already covers `Comprar ingresso` and is unaffected.

### Deferred Ideas (OUT OF SCOPE)
- **A notice "as inscrições abriram"** (in-app and push) for the tenant's members: not asked, left out. Roughly one extra plan if wanted.
- **A notification to the admin when a payment arrives before the opening:** offered and declined; the mark is enough.
- **A "me avise" button** on an `Em breve` event: new capability, not requested.
- **An opening date for free events** (the `Vou` as the registration): decided out; it would be a new rule on the same column.
- **Scheduling the sale inside Kiwify** so the external link itself is closed before the opening: depends on the gateway and on the admin; the system only controls its own screen and API.

## Corrections to carry into planning (contradictions, reported, not silently resolved)

These are the places where CONTEXT or UI-SPEC disagree with the code or with each other. The planner must decide each with Igor or state the choice; each has a recommendation.

1. **D-791 and CONTEXT code_context name `responded_at` as the early-payment instant. It is wrong for the upgrade case.** `app.event_gateway_grant` writes `responded_at = now()` only in the INSERT and in the `not_going -> going` UPDATE; the third branch (`going` rsvp or courtesy, `checked_in`, `walk_in`) changes `origin`, `order_provider`, `order_ref`, `refunded_at` and nothing else [VERIFIED: supabase/migrations/20261113144645_event_gateway_grant_replay_first.sql:155-178]:
   ```
   155	  -- 10. ONE write.
   161	    elsif v_att_status = 'not_going' then
   164	             responded_at = now(),
   170	    else
   171	      -- `going` (rsvp / courtesy), `checked_in` or `walk_in`: the status stays, origin and order change.
   173	         set origin = 'ticket',
   ```
   So a member who had a `Vou` before the link (or a courtesy) and pays after the opening keeps an old `responded_at` that sorts before the opening: the mark would say `Antes da abertura` for a payment made after it. The manual release (`p_admin_release`) has the opposite error: `responded_at` is the admin's click time, not the payment time. **Recommendation:** a dedicated nullable instant on `event_attendances`, written by the grant on all three write paths (§C). This is within Claude's Discretion ("exact column names, migration shape") and keeps D-791's spirit (the mark is still derived, never stored).
2. **UI-D-781 puts `Venda indisponível` before `Em breve`, but the web cannot tell the two apart from `checkoutUrl`.** The link is null for module off, gateway disconnected, no link, and (new) before the opening. **Recommendation:** one new tenant-pinned boolean definer (`app.event_sale_ready`: mapping exists AND gateway mode AND `https:` link, ignoring the clock) surfaced as an optional detail key (§D, §I). Without it the web would show a countdown on an event whose module is off.
3. **UI-SPEC's server view-model says the seed is "the same instant the server used to decide the state"; two server clocks exist here.** The link is decided by the Postgres clock inside `withTenantTx`; `events-view.ts` runs on the web server with its own `Date.now()`. If the web decided `soon` from its own clock there would be a window where the page shows `Comprar ingresso` with no link, or `Em breve` after the database opened. **Recommendation:** `serverNow` = `now()` of the SAME statement that calls `app.event_checkout_url` (transaction timestamp, so identical by construction [CITED: postgresql.org/docs/current/functions-datetime.html "their values do not change during the transaction"]), and the web decides `soon` from `registrationOpensAt` vs `serverNow` only.
4. **CONTEXT says "the purchase-switch plan 13-18 already covers `Comprar ingresso` and is unaffected". It does not.** Plan 13-18's `files_modified` lists Loja, community, course, lesson, post and `(auth)` files and no `eventos` file; `grep -i "ingresso\|PaidEventZone"` over every Phase 13 artifact prints nothing, and `apps/web/lib/purchase-visible.ts` does not exist yet [VERIFIED: .planning/phases/13-app-nativo-ios-e-android-por-tenant-white-label/13-18-PLAN.md:1-30; grep over .planning/phases/13-*/ returned no match; `ls apps/web/lib | grep -i purchase` returned nothing]. Phase 13 was planned on 2026-11-04, before 10.1. The paid event zone (10.1's `Comprar ingresso`, and this phase's `Em breve` zone with a price row) is therefore outside the native purchase switch. Nothing for 10.2 to build, but Igor should know: this is a Phase 13 gap, to be decided there (see Open Question 1).
5. **A-UI-15 versus D-790 wording** (already flagged by the checker): D-790 says the countdown "hands over to ... the check-in window, `Ao vivo`, `Hoje`"; UI-SPEC A-UI-15 keeps the count running through the check-in window and does not use `É hoje!` for a paid holder. Not a code problem; Igor confirms at the sketch 022 gate. The code supports either (one branch in `heroOverline` and `eventCardNote`).
6. **UI-SPEC UI-D-786 says the list passes `Em breve` openings to the shared boundary refresh; the `/eventos` page has no such island today.** `useBoundaryRefresh` is used only by `EventActions` and the shell's `TabDotRefresh` [VERIFIED: grep -rl useBoundaryRefresh apps packages]. A new small client island on the gallery is needed, and the hook has a horizon gap (§E, Pitfall 3).
7. **UI-SPEC says "views never receive instants"; the poster `note` and hero overline become live.** `eventCardView` is also returned through a server action (`apps/web/app/(app)/eventos/actions.ts` imports it) and is consumed by `perfil/ProfileEventsRail.tsx` and `components/platform/preview/TenantAppPreview.tsx`. The view model must return plain serializable data (a countdown descriptor), not a React node; the host island builds the node (§E).

|------------|-------------|----------------|-----------|
| Withholding the purchase link before the opening | Database (`app.event_checkout_url`, DB clock) | API (spreads the definer's answer) | D-789: the single decider; the browser and the web server never decide |
| Lock of the opening after the first paid presence | Database (BEFORE UPDATE trigger on `events`) | API (maps the refusal to 409), Browser (disables the field) | D-783: "not only a disabled field", must hold for every writer |

| The count's seed | API (DB `now()` of the deciding transaction) | Web server (passes it through), Browser (offset) | D-788: server time, one clock for decision and display |
| Minute-by-minute ticking, hidden-tab handling, re-seed | Browser (one client component in the app tier) | — | nothing server-side can tick; the module UI packages stay props-only (MOD-02) |
| Swap at zero | Browser (timer) -> Web server (`router.refresh()`) -> API (re-read) | — | the screen only reflects; the API answers whether the link exists |

| `Antes da abertura` mark | API projection (admin lane) | Web view model | derived from the stored confirmation instant and the locked opening |

### §C. The early-payment marker (Q3)

**Recommended derivation:** `ticket_confirmed_at` (set by the grant to `now()` on every write that makes the row a ticket) compared to the event's `registration_opens_at`:
`before_opening = (a.origin = 'ticket' and a.ticket_confirmed_at is not null and ev.registration_opens_at is not null and a.ticket_confirmed_at < ev.registration_opens_at)`.
- **Upgrade case, proved:** the three grant branches all write `ticket_confirmed_at = now()` of the confirming transaction, whatever the row held before (INSERT; `not_going -> going`; `going`/`checked_in`/`walk_in` upgrade). An old `responded_at` is irrelevant. A presence from before the link that pays after the opening gets `ticket_confirmed_at >= registration_opens_at` and is not marked; one that pays before it is marked.
- **Stability:** the opening cannot change while any row has `origin = 'ticket'` (§B), and the marked row IS such a row. So for as long as the mark exists the inputs are frozen. If every ticket row is refunded the rows are deleted, the mark disappears with them, and the date may then be edited; nothing stale remains. A checked-in refunded row stays and keeps the lock, so its mark is stable too.
- **Boundary:** strict `<`; a confirmation at the exact opening instant is "open". It matches `event_checkout_url`'s `<= now()`.
- **Manual release** (`p_admin_release = true`) stamps the admin's click time; the mark then reflects when the presence was confirmed, which is D-791's literal wording ("the moment the presence was confirmed").
- **Existing rows:** `ticket_confirmed_at` is null for every ticket row written before this release; the marker treats null as "not early", and no event has an opening yet, so nothing can be mis-marked.
- The CHECK `ticket_confirmed_at is null or origin = 'ticket'` makes the column impossible to leave on a non-ticket row; `app.event_ticket_reset` only flips `courtesy -> rsvp` and never touches it. `app.event_gateway_revoke` deletes or flags and needs no change.

### §E. The live counter (Q4)

**Server string equals first client render.** `LiveCountdown` (app tier, `apps/web/components/events/`) receives plain props: `targetIso`, `seedIso` (= `serverNow`), a `kind` (`opening` | `event`), a `variant` (`text` | `blocks`) and its translations through `useTranslations('events')` (client components already do this). **After mount** one effect computes `offset = Date.parse(seedIso) - Date.now()` (the ONLY device-clock read) and re-renders from `target - (Date.now() + offset)`. **One `setTimeout` per instance**, re-armed to the next minute change: `delay = remaining % 60_000 || 60_000` plus a few ms of margin (the floored count changes when `remaining` crosses a multiple of 60 000). No `setInterval`. The effect depends on `seedIso` and `targetIso`, so every `router.refresh()` that returns a new seed recomputes the offset. `visibilitychange` to hidden clears the timer; to visible recomputes at once and, if hidden for more than 60 s, asks one `router.refresh()`; `pageshow` with `persisted` does the same (bfcache). [CITED: developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event: "Transitioning to `hidden` is the last event that's reliably observable by the page ... a good point at which pages can stop making UI updates"; MDN did not document pageshow/timer throttling on that page, so the `pageshow` handling and background-timer behaviour are [ASSUMED].]
**Offset accuracy is conservative.** `offset` is computed at hydration from a seed taken at render, so the client's estimate of server time lags the true server time by the render-to-hydration latency L. The count shows at most L too much and reaches zero at most L late; it never reaches zero early and never reveals a link (the link only comes from the API). A device whose clock is wrong, fast or in another year is corrected by the offset. The 60 s re-seed bounds the drift after sleep.
**Who refreshes at zero.** `useBoundaryRefresh(boundaries, phase)` (`apps/web/components/events/useBoundaryRefresh.ts`) is reusable but has two gaps for this phase: (1) it reads the DEVICE clock (`const now = Date.now()`, line 35-38) so a wrong device clock schedules the refresh at the wrong time, or never (`next - now > BOUNDARY_HORIZON_MS` returns without arming); (2) it arms ONCE at mount and never re-arms when a boundary later enters the 24 h horizon, so a page opened three days before the opening and left open never schedules the refresh. **Recommended extension** (backward compatible, one optional third argument): `useBoundaryRefresh(boundaries, phase, serverNowIso?)` computes `now = Date.now() + offset` inside the effect when a seed is given, and caps the timer at the horizon, re-evaluating when it fires instead of returning. Pass `[checkinOpensAt, startsAt, endsAt, registrationOpensAt]` and a `phase` key that also carries the sale state (`${phase}:${sale.kind}`), because "its retries re-arm only when `phase` changes" (UI-SPEC) and the swap at zero changes the sale kind, not the phase. The existing chain `BOUNDARY_RETRY_DELAYS_MS = [2_000, 5_000, 15_000, 30_000]` covers about 52 s of skew between the DB clock and the seed. The `/eventos` gallery needs a small client island that passes every `Em breve` opening within 24 h of its cards to the same hook (ONE refresh per page, however many cards).
**Accessibility pattern** (UI-D-787, A-UI-14): digits `aria-hidden`, a visually hidden `role="timer"` outside the persistent polite wrapper holding the current spoken value, and at most four polite sentences (three thresholds plus the swap). ### Anti-Patterns to Avoid
- **Deciding `soon` from the web server's `Date.now()` or the device clock:** shows a button with no link, or a countdown after the DB opened (Correction 3).
- **A client `Date.now()` during render:** hydration mismatch; the only device-clock read is the offset in one effect.
- **`setInterval`, or a timer per digit:** one `setTimeout` per instance, aimed at its own next minute change.
- **Putting the count inside the `aria-live` wrapper:** it would be spoken every minute (UI-D-787); the wrapper holds only the threshold sentences and the swap.
- **Reusing `ticket_locked` for the opening:** two refusals under one string.
- **An advisory lock inside the events trigger:** inverts the grant's lock order (§B).
- **Importing the payments module from the events module** (or the reverse): the clear rides the SQL definer the kernel already calls; `pnpm boundaries` and `boundaries:negative` gate it.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Deciding whether the link may be shown | a client or web-server clock comparison | `app.event_checkout_url` (DB `now()`) + `serverNow` of the same transaction | one clock; D-789 |
| Wall clock to UTC | JS timezone math | the existing SQL conversion `(date \|\| ' ' \|\| time)::timestamp at time zone t.timezone` and its `to_char` inverse | DST folds, one rule for start, end and opening |
| The lock | a service-level count | the BEFORE UPDATE trigger + `app.event_ticket_lock`'s predicate | every writer, no check-then-write race |
| Clearing the date with the mapping | a third request or a second transaction | `app.event_ticket_reset` inside `deleteEventMapping`'s transaction | atomic, no module import |
| A ticking client clock | `setInterval` / `useNow` | one `setTimeout` per instance + server offset | hidden-tab and drift handling |
| Pluralising a count | string concatenation | ICU plurals in `events.json` (`countdown.*`) | pt-BR forms, the existing `ticket.*` style |
| A "paid before opening" flag | a stored boolean or `responded_at` | `ticket_confirmed_at` vs the locked opening | stable, derivable, correct on upgrades |

**Key insight:** every fact the screen needs is a one-line projection of a value the database already decides; the risk in this phase is clocks and write ordering, not features.

## Common Pitfalls

### Pitfall 1: `responded_at` as the early marker
**What goes wrong:** an upgraded presence (`going` -> `ticket`) keeps its old `responded_at`. **How to avoid:** the dedicated instant (§C). **Warning signs:** a pgTAP case "member with a Vou before the link pays after the opening" showing the mark.

### Pitfall 2: Lock-order deadlock between the grant and an events update
**What goes wrong:** grant = advisory lock, then `for share` on the event row; `updateEvent` = row lock, then (if the trigger took the advisory lock) advisory. **How to avoid:** the trigger takes no advisory lock; the row lock serialises (§B). **Warning signs:** `deadlock detected` in a two-connection integration test.

### Pitfall 3: `useBoundaryRefresh` never arms for a page opened days before the opening
**What goes wrong:** the hook returns when the boundary is more than 24 h away and never re-checks; `Abrindo agora` stays forever on a long-lived tab, and a wrong device clock mis-schedules everything. **How to avoid:** extend the hook with the seed and a re-arming cap (§E). **Warning signs:** a component test with a 3-day target and fake timers advanced to the target that expects exactly one `router.refresh`.

### Pitfall 4: A guard exit list that does not know the new column
**What goes wrong:** the grant's upgrade UPDATE changes `ticket_confirmed_at`, stops matching the guard's 1b bookkeeping exit and runs the full rule list; and a member lane can touch the column on an `rsvp` row. **How to avoid:** add the column to 1a and 1b in the same migration (§A.3) and add a 234 case per row kind. 

### Pitfall 5: Unpaid events leaking a stale opening
**What goes wrong:** a create with a date whose mapping call failed leaves a stored opening on a free event; a later direct reader shows `Em breve` on a free event. **How to avoid:** every projection spreads the opening only when `pd.paid` (§D), and the form always sends the field explicitly with the switch on.

### Pitfall 6: Cached or restored pages showing a stale seed
**What goes wrong:** a bfcache restore after hours has an old `serverNow`, so the offset is off by the age. **How to avoid:** `pageshow persisted` and the more-than-60-s hidden rule re-seed through `router.refresh()`; the service worker never caches RSC or navigations (verified above), so a refresh always returns a fresh seed.

### Pitfall 7: Server action returning a React node
**What goes wrong:** the sections action returns finished card views to the client; a JSX `note` makes that payload non-plain. **How to avoid:** descriptors in the view model, nodes only in the client island (Correction 7).

### Pitfall 8: Disk and the local stack
`apps/web/.next` and `.turbo/cache` fill the disk (16 GiB free, 92% used now): clear `apps/web/.next/cache` after `next build`; run gates with `TURBO_CACHE=local:r` and `--concurrency=4`; run pgTAP before integration; `db:reset` only on Igor's word [CITED: user memory index]. `pnpm test:integration -- x` does not filter: name the file with `vitest run tests/integration/<file>`.

// Source: this research, §E (UI-D-786). Names are proposals.
'use client';
export function LiveCountdown({ targetIso, seedIso, kind, variant }: Props) {
  const t = useTranslations('events');
  const target = Date.parse(targetIso);
  const seed = Date.parse(seedIso);
  const [remaining, setRemaining] = useState(target - seed); // pure: same on server and first client render
  useEffect(() => {
    const offset = seed - Date.now();                        // the only device-clock read
    let timer: number | undefined;
    const tick = () => {
      const left = target - (Date.now() + offset);
      setRemaining(left);
      if (left <= 0 || document.visibilityState === 'hidden') return;
      timer = window.setTimeout(tick, (left % 60_000 || 60_000) + 25);
    };
    const onVisibility = () => { window.clearTimeout(timer); if (document.visibilityState === 'visible') tick(); /* >60 s hidden: router.refresh() */ };
    document.addEventListener('visibilitychange', onVisibility);
    tick();
    return () => { window.clearTimeout(timer); document.removeEventListener('visibilitychange', onVisibility); };
  }, [seed, target]);
  return /* formatCountdown(remaining) through t(...), role="timer" hidden node, aria-hidden digits */ null;
}
