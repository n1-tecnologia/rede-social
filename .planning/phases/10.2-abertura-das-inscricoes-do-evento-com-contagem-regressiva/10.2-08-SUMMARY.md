# Phase 10.2 Plan 08: The payments half of the opening Summary

**The Pagamentos Eventos recentes list marks a ticket paid before the event's opening with an optional neutral `beforeOpening` key from the events-owned SQL definer, an early signed delivery is proved through the real webhook and apply path, and removing the product link is proved to clear the opening in the same transaction.**

## Performance

- **Duration:** about 6 min of execution after the context reads
- **Started:** 2026-11-13T23:32:38Z
- **Completed:** 2026-11-13T23:40:00Z
- **Tasks:** 3 (task 1 tracer, tasks 2 and 3 auto)
- **Files modified:** 7 (all existing)

## Accomplishments

- `listEvents` and `readItem` (one shared column list) gain `before_opening`: `case when p.kind = 'event' and e.outcome in ('ticket_granted','ticket_granted_over_limit') then app.event_ticket_before_opening(e.tenant_id, p.event_id, e.provider, e.external_ref) end`. `toItem` sets `beforeOpening = true` only when the row says true. The kernel never imports the events module (grep of `modules/events|module-events` prints nothing).
- `eventItemSchema` (still `.strict()`) gains `beforeOpening: z.boolean().optional()`; the contract test pins parse with, parse without, refusal of a string or null, and refusal of an unknown extra key.
- Tracer test through the real signed route, inbox and apply job: an early delivery is `applied` with `ticket_granted`, one `ticket` attendance with the confirmation instant set, listed with `beforeOpening: true` and exactly the ticket key set plus that key. A late delivery, a replay (`no_effect`), a refunded early order (purchase row and `ticket_revoked` row), an ignored delivery and a store delivery have no such key at all. The buyer has exactly one notice and the admin's notification count is unchanged. The raw body names no opening instant.
- Mapping removal: the cleared case reads mapping, opening, courtesy row (back to `rsvp`), and the released central route after one request, and the member's detail shows no sale link and none of `registrationOpensAt`, `serverNow`, `saleReady`; a sold ticket gives `409 ticket_locked` with mapping, opening, route and ticket untouched; an unmapped removal leaves an opening stored on the unpaid event; a foreign tenant admin gets the bare 404 and the owner's removal then works.
- EP-60: five rounds of two deliveries of one order reference with different bytes applied through `Promise.allSettled([runApply, runApply])`: both fulfilled, one `ticket_granted` and one `no_effect`, one presence, the confirmation instant byte-identical after a second round, one notice, no deadlock line in the output.
- OPEN-23: each tenant's admin list holds only its own early delivery (with a shared order reference in both tenants), and the definer called with a foreign tenant argument, or with a reference that exists only in the other tenant, answers false beside positive controls.

## Decisions Made

- The marker is guarded by the two granted outcomes in SQL, so replay, refund, ignored and non-event rows never ask the definer. The refunded early purchase row also loses the marker because the presence row is deleted, which the test pins.
- The manual release answer (`readItem`) uses the same column list, so an admin-released early payment shows the marker too; no separate code path.
- The member detail does not expose the opening facts yet (plan 07), so the "reads as a free event" assertion pins a null sale link and the absence of the three future keys; once plan 07 lands these assertions stay valid and should be strengthened by plan 07's own tests.
