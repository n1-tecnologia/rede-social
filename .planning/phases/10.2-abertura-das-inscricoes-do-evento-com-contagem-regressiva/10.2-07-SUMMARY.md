# Phase 10.2 Plan 07: The read models of the registration opening Summary

**A paid event's list, next, detail and edit reads now carry the opening and the database instant of the deciding statement (six-digit UTC strings), the detail carries `saleReady`, the edit read gives the opening back as the tenant's wall clock, and Participantes derives `beforeOpening` for early payers, all optional keys that a free event never grows.**

## Accomplishments

- The shared `eventColumns` projection selects `registration_opens_at` and `server_now` inside `case when pd.paid then ... end`, in the same statement as the link, so the instant that decided `checkoutUrl` is the instant the web counts from. The list and next stay ONE statement each (`feed-query-budget` list cases green; no WHERE or ORDER BY touched).
- `toEvent` spreads `serverNow` for every paid event and `registrationOpensAt` only when stored; `getEvent` adds `app.event_sale_ready(e.id)` and spreads `saleReady` for a paid event only. `checkoutUrl` is non-null exactly when `saleReady` and the opening is not after `serverNow`, asserted over a matrix through the API.
- `getEventForEdit` reads the pair (`to_char(... at time zone t.timezone ...)`), the UTC instant and `now()` only when `ta.external_product_id is not null`, and returns `registrationOpens`, `registrationOpensAt`, `serverNow` for the admin of a paid event; a 23:30 local time that is the next UTC day reads back as the typed day.
- `attendeeProjection` derives `before_opening` with the expression of pgTAP 234 section 8 (text equality verified after whitespace collapse); `toAttendee` spreads `beforeOpening: true` only inside the paid block and only when true.
- The strict schemas gained only `.optional()` keys (summary: `registrationOpensAt`, `serverNow`; detail: `saleReady`; edit: `registrationOpens`, `registrationOpensAt`, `serverNow`; attendee: `beforeOpening`). No route, table or permission was added.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Test design] The microsecond boundary trio is not asserted through the API**
- **Found during:** Task 3
- **Issue:** the deciding instant is the `now()` of the request's own transaction, which a test cannot pin, so "one microsecond after, at, and one microsecond before" cannot be produced through the API without a race.
- **Fix:** through the API the opening is set seconds ahead and seconds behind (the link is held back and handed out), and every matrix row is judged by the answer's OWN `registrationOpensAt` and `serverNow` (`checkoutUrl !== null` iff `saleReady` and `registrationOpensAt <= serverNow`, compared as plain strings). The exact microsecond boundary stays proved by pgTAP 234 section 3 (plan 04), which was green when plan 04 closed.
- **Files modified:** `apps/api/tests/integration/events-opening.test.ts`
- **Committed in:** `13a5a32a`

**2. [Rule 3 - Test design] The paid `next` item is proved at unit level, not through the route**
- **Found during:** Task 1
- **Issue:** `GET /v1/events/next` answers the lab tenant's earliest active event, which is a seeded free event that is already in progress, so a test event cannot be the next one.
- **Fix:** the paid next item is asserted in `events-payload.test.ts` 9u (keys spread, no link, no readiness, one statement); the integration case reads the real route and asserts the free item keeps the 10.1 key set.
- **Committed in:** `73670321`, `13a5a32a`

**3. [Process] Implementation written before the first red run**
- **Found during:** Task 1 and Task 2
- **Issue:** the plan asks for a failing test first; the service and contract edits were made before the new integration cases were run, so no red run was recorded for them.
- **Impact:** none on the result (the cases assert behaviour that did not exist before the edits and all pass), but the red evidence is absent.

**4. [Process] Task 1 and Task 2 share two production files**
