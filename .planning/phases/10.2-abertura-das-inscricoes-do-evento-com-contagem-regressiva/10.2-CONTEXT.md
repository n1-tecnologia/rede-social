<domain>
## Phase Boundary

Phase 10.1 (closed 2026-11-13) lets a tenant sell an event: an event with a linked Kiwify product is a **paid event**, the member sees `Comprar ingresso`, and the presence is created only by an approved payment or by the admin. Today the purchase is open from the moment the event exists. This phase lets the admin say **when the purchase opens**, and makes the wait visible.

What the phase delivers (Igor's request of 2026-11-13, answered the same day):

- **An optional opening date and time on a paid event**, set in the `Ingresso` section of the event form. Empty means "open at once", so every event that exists today behaves exactly as now.
- **Before the opening**, the member still sees the event, with an `Em breve` tag and a live countdown in days, hours and minutes to the opening. The member cannot buy: the API does not return the purchase link and the page shows no `Comprar ingresso`.
- **At the opening** the page swaps to the buy button by itself.
- **After the opening**, a member who holds a presence in the paid event sees a live countdown in days, hours and minutes to the event itself, on the event page and on `Meus eventos`.
- **A payment that arrives before the opening** (someone with the direct Kiwify link) still confirms the presence and is marked `Antes da abertura` for the admin.
- **A free event does not change at all**: no field, no tag, no opening countdown; its `Faltam N dias` stays as it is.

Out of scope (capabilities that belong elsewhere or nowhere): a push or in-app notice "as inscrições abriram", a notification to the admin on an early payment, a "me avise" button, opening dates for free events, scheduling the sale inside Kiwify. See the deferred list.

</domain>

<decisions>
## Implementation Decisions

### Who it applies to, and the rules (answered by Igor on 2026-11-13)
- **D-780: The opening applies only to paid events** (an event with a linked gateway product, D-740). A free event has no field, no `Em breve`, no opening countdown, and keeps its `Faltam N dias` untouched. — **Reversibility:** reversible — extending it to free events later is a new rule on the same column, no migration.
- **D-781: The opening date is optional; no date means open at once.** Every existing event has no date and behaves as today. The column is nullable and the migration is expand-only. — **Reversibility:** reversible — a nullable column added to `events`, nothing rewritten.
- **D-782: A payment that arrives before the opening confirms the presence anyway.** The money is already charged and D-750/D-751 already say the paid path never refuses a willing buyer. The grant definer gets **no** opening-time check. The presence is marked `Antes da abertura` for the admin (D-791). — **Reversibility:** costly — refusing early payments later would mean refunds and a new refusal path in the webhook branch.
- **D-783: Once the event has at least one paid presence, the opening date cannot be changed.** Same lock family as D-747 (the product locks after the first sale). **Only a paid presence locks it**: a courtesy (`Cortesia`) and a presence made before the ticket existed (`Anterior ao ingresso`) do not, so an old event with confirmed people can still be given an opening date. The refusal is a stable machine code from the API and the database, not only a disabled field. How a fully refunded sale counts follows `app.event_ticket_lock` (the planner reads it and states the rule). — **Reversibility:** costly — the refusal code joins the closed `EVENT_ISSUES` list, which is an external contract once released.

### The event while it is "Em breve" (answered by Igor on 2026-11-13)
- **D-784: The card's tag is `Em breve` in place of `Pago` while the sale is closed.** One tag, not two. When the sale opens the card goes back to `Pago` (D-753). A member who already holds a presence never sees `Em breve` (they see their confirmed state, D-790). — **Reversibility:** reversible — copy and one view-model branch.
- **D-785: The countdown shows on the card and on the page.** The card, which is small, carries a short text, `Abre em 2 d 4 h 13 min`. The page carries three blocks, `02 dias · 04 horas · 13 min`. — **Reversibility:** reversible — presentation only.
- **D-786: On the page the buy zone is replaced by the countdown block plus the exact opening date and time** in the tenant's time zone (for example `20 nov, 10:00`). The reference price (D-755), when the admin filled it, **stays visible** on the card and on the page while the event is `Em breve`. — **Reversibility:** reversible — presentation only.
- **D-787: Units that are zero disappear.** With one day left the counter reads `23 h 40 min`; under an hour, `40 min`; under a minute, `Menos de 1 min`. The same rule applies to the countdown to the event (D-790). — **Reversibility:** reversible — a formatting function.
- **D-788: At zero the page swaps to the buy zone by itself, with no manual reload.** The countdown starts from **server time**, not from the device clock, and the link appears only when the API returns it (the page re-reads the event at the boundary). A phone with a wrong clock must not show a wrong count nor reveal a link early. *(Taken from the brief and Igor's rule that the server blocks; not asked as a separate question.)* — **Reversibility:** costly — the seed of the countdown becomes part of the event read model that older and newer clients parse.
- **D-789: The server blocks the purchase, the screen only reflects it.** Before the opening the API does not return the purchase link (`checkoutUrl`) and the web shows no `Comprar ingresso`. The link is returned only on the event detail today and only through `app.event_checkout_url`, which is the single SQL place that decides (research confirms; it must return null before the opening, by the database's own clock). — **Reversibility:** costly — the definer is a published SQL name used by the read model.

### The countdown to the event (answered by Igor on 2026-11-13)
- **D-790: A member who holds a presence in a paid event (paid, courtesy or before-the-ticket) sees days, hours and minutes to the event, always, not only in the last week.** It replaces `Faltam N dias` on the event page's hero and on the `Meus eventos` cards **for paid events only**; a free event keeps `Faltam N dias`. Near the start it hands over to what already exists: the check-in window (D-209), `Ao vivo`, `Hoje`. — **Reversibility:** reversible — presentation, plus one new live component.

### A payment before the opening (answered by Igor on 2026-11-13)
- **D-791: The admin learns about it only through a mark, with no new notification.** In `Participantes` the presence shows `Pago` and, next to it, `Antes da abertura`; the delivery in `Eventos recentes` carries the same marker. The mark is derived by comparing the moment the presence was confirmed with the opening instant (never stored apart from the event, because the date is locked once a paid presence exists, D-783). The member who paid early gets the same `Presença confirmada` notice as anyone (D-756) and sees their confirmed state with the countdown to the event. — **Reversibility:** reversible — a derived mark.

### The admin's form (answered by Igor on 2026-11-13)
- **D-792: The field `Abertura das inscrições` lives inside the `Ingresso` section**, only visible when `Cobrar ingresso` is on, right below the reference price. It is a date and a time in the tenant's time zone, the same wall-clock pair as the event's start and end, converted to UTC in SQL like them. — **Reversibility:** reversible — form placement.
- **D-793: Turning `Cobrar ingresso` off clears the opening date.** The event becomes free and open at once; the form warns before saving; turning the ticket on again means typing the date again. — **Reversibility:** reversible — a form and write rule.
- **D-794: With a paid presence the field is read-only** and says so in the pattern of the locked product (`N ingressos vendidos`): the opening date, and the reason it cannot change. — **Reversibility:** reversible — presentation of D-783.

### Claude's Discretion
- **The date must be before the event's start.** A date already in the past is **accepted** (it simply means open), so editing an old event never fails because its opening passed. The issue codes for this are the planner's, added to the closed list as optional-compatible additions.
- **Precedence of states in the buy zone:** cancelled or ended first, then `Venda indisponível` (D-746, the module is off or the gateway is disconnected), then `Em breve`, then `Esgotado`, then `Comprar ingresso`. Before the opening nobody can buy, so `Esgotado` never shows early.
- **Precedence in a presence holder's view:** a member who holds a presence is never in the `Em breve` state; they get the confirmed state and the countdown to the event.
- **Tick rate:** the counter changes at minute granularity, so it ticks once a minute aligned to the minute change, and stops when the tab is hidden.
- **Exact column and function names, the migration shape, the closed-list issue codes, the copy keys and every pt-BR string** (the ICU plurals follow the existing `events.json` style under `ticket.*`).
- **How the live seed is carried** (server instant plus a client offset against `Date.now()`, or an equivalent) and how to avoid a hydration mismatch, since no ticking client counter exists today.
- **Accessibility:** a countdown that changes every minute must not be announced every minute; the planner picks a polite, non-chatty pattern and respects reduced motion.
- **Native app:** nothing to build, the shell shows the web screens (Phase 13); the purchase-switch plan 13-18 already covers `Comprar ingresso` and is unaffected.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `eventSaleState` (`events-view.ts:286`) with `PaidEventZone.tsx`: first match wins among `none | salesClosed | unavailable | soldOut | buy`. `Em breve` is a new kind placed before `unavailable` and `buy` (after the precedence in Claude's Discretion).
- `useBoundaryRefresh` (`components/events/useBoundaryRefresh.ts`): one timer on the next ISO boundary within 24 h, then `router.refresh()` with a retry chain. Pass the opening instant as one more boundary, with a key that also changes with the sale state (its retries re-arm only when `phase` changes).
- The poster `tag` slot (`EventPoster`, `EventHero`) and the `StatusPill` marks of `Participantes`: `Em breve` rides the `tag`, `Antes da abertura` is a new `AttendeeMark` next to `paid`.
- The `ticketPriceCents` write rule in `updateEvent` (omitted keeps, explicit null clears) is the precedent for the new field, so a cached older client never wipes the date.
- The wall-clock pair `wallClockSchema` and the SQL conversion `(date || ' ' || time)::timestamp at time zone t.timezone` (create at `service.ts:543`, update at `1189`, edit read at `963`).

### Established Patterns
- New keys on the strict event contracts are `.optional()` (release order: migration, web, then API); the event PUT replaces the whole event except the price rule above.
- Expand-only migrations, `create or replace` of definers, every table keeps RLS and a cross-tenant negative pgTAP test. `events_tenant_isolation` exposes every column to every member of the tenant, which is fine here: the opening instant is meant to be seen.
- The purchase link is never in a list payload, only in the detail, and only through `app.event_checkout_url` (D-753 family).
- Free events keep today's exact key set: paid fields are conditionally spread everywhere.
- Brand neutrality in copy: the gateway name is only the `{gateway}` slot.
- `events-view.ts` is pure and clock-free: every function takes `nowMs` from the server, once per request, and client components get finished strings. **No ticking counter exists anywhere** (no `setInterval`, no `useNow`).

### Integration Points
- A new nullable timestamptz column on `events`, a check that ties it to the event's start, the redefinition of `app.event_checkout_url`, and the guard on the update path that refuses a change once a paid presence exists.
- The read model: the opening instant (and the server instant that seeds the countdown) in the summary, detail and edit shapes, plus the opening wall clock in the edit shape and the early-payment marker in the attendee shape.
- The grant definer must **not** gain an opening check (D-782); the marker compares `responded_at` (the webhook's processing time, written by `now()`; an upgrade of an existing `going` row does not touch it) with the opening instant. The planner must check that this derivation is stable and say so.
- The event form's two-step save (event first, then the mapping) and `saveTicket`: turning the ticket off must clear the date in the same transaction as the event write.

</code_context>

<specifics>
## Specific Ideas

- Igor's wording: "quando for criar um evento eu preciso conseguir definir quando é a data daquele evento, mas agora preciso definir quando as inscrições daquele evento irão abrir. Até o dia da abertura preciso de um contador que vai mostrando dias, horas e minutos para a data de abertura do carrinho. E depois, para quem comprou o evento, um contador de quanto tempo falta para o evento. O user vai conseguir ver o evento mas como uma tag de 'Em breve' com o contador mostrando a contagem regressiva para a abertura do carrinho. Antes dessa data não vai conseguir comprar."
- The tag reads `Em breve`; the field reads `Abertura das inscrições`; the admin mark reads `Antes da abertura`.
- Igor's working style: short pt-BR, UI first, no `.env` or code per tenant.

</specifics>

<deferred>
## Deferred Ideas

- **A notice "as inscrições abriram"** (in-app and push) for the tenant's members: not asked, left out. Roughly one extra plan if wanted.
- **A notification to the admin when a payment arrives before the opening:** offered and declined; the mark is enough.
- **A "me avise" button** on an `Em breve` event: new capability, not requested.
- **An opening date for free events** (the `Vou` as the registration): decided out; it would be a new rule on the same column.
- **Scheduling the sale inside Kiwify** so the external link itself is closed before the opening: depends on the gateway and on the admin; the system only controls its own screen and API.

None of these were folded into this phase.

</deferred>
