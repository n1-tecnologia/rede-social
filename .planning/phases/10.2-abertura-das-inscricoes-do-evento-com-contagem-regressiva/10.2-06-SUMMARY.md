# Phase 10.2 Plan 06: The write half of the registration opening Summary

**The admin PUT and POST carry an optional opening as a wall-clock pair converted in SQL in the tenant's zone (omitted keeps, null clears), the CHECK and the lock trigger reach the web as `400 opening_after_start` and `409 opening_locked`, both appended to the closed issue list.**

- **Completed:** 2026-11-13T23:31:25Z
- **Tasks:** 3
- **Files modified:** 6 (1 created, 5 modified)

## Accomplishments

- `eventInputSchema` gained `registrationOpens: wallClockSchema.nullable().optional()` (no default, so the web's parsed output never grows a key an older strict API rejects) and a `superRefine` branch beside `end_before_start` that refuses an opening at or after the start with the message `opening_after_start` at the path `registrationOpens`.
- `createEvent` stores the pair in the same INSERT ... SELECT with the start's cast; `updateEvent` reads the stored opening as a microsecond ISO string and picks one of three bound-parameter expressions in TypeScript, with the column on both sides of the `is distinct from` tuple, so an opening-only edit is a real change and an identical body still leaves `updated_at` alone.
- `checkViolation` maps `events_registration_opens_chk` to `400 opening_after_start` in both writes and `events_opening_locked` to `409 opening_locked` in the update; the database trigger remains the only judge of the lock.
- `EVENT_ISSUES` is append-only (24 entries); pinned by slice, distinctness, prefix-freedom and `EVENT_ISSUE_SET.has('')` being false.
- 14 new integration cases, including the two two-connection cases (a PUT waits for an in-flight grant and is refused; a grant waits for an update and is judged against the new opening) with no deadlock.
