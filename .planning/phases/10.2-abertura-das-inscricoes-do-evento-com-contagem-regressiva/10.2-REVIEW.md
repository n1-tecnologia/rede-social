## Summary

The phase is carefully built. No critical defect was found. The areas you flagged hold up under adversarial reading:

- **Tenant isolation and the purchase link (held).** `app.event_checkout_url` and `app.event_sale_ready` are `security definer` with `search_path = ''`, fully qualified names, `app.tenant_id()` pinned, EXECUTE revoked from `public` and `anon`. `app.event_checkout_url` returns null while `registration_opens_at > now()`. Its `now()` is the same transaction instant that `server_now` is printed from in the same statement, so the web's `opens > seed` string comparison and the database decision cannot disagree (`<=` opens, `>` stays closed). I found no other member-reachable path that returns the link or the date: every `payment_products.checkout_url` read outside the events service is in the admin setup routes, and no module other than events reads `events.registration_opens_at`. The list and detail SQL wrap `registration_opens_at` and `server_now` in `case when pd.paid`, so an unpaid event never exposes a date.
- **Lock trigger and the grant (held).** `events_opening_guard` (`before update of registration_opens_at ... when (old is distinct from new)`) reads `event_attendances` with `origin = 'ticket'` in the same tenant. The research claim about ordering is correct. `updateEvent` takes `FOR UPDATE` on the event row first. The grant takes the advisory lock and then `FOR SHARE` on the same row. `deleteEventMapping` takes the advisory lock and then updates the event row. Nothing on the `updateEvent` path takes the `event_ticket:` advisory key, so the lock-wait graph has no cycle. A `BEFORE UPDATE` trigger fires after the row lock is acquired (waiting if needed), and the trigger's query takes a fresh read-committed snapshot, so a ticket row committed by a grant that held `FOR SHARE` is seen. There is no check-then-write window.
- **Grant and guard bodies.** The new `app.event_gateway_grant` differs from the previous definition by exactly the three `ticket_confirmed_at = now()` writes. `app.event_attendance_guard` differs only by the new column in step 1a and step 1b. Both were confirmed by diffing against the previous migrations.
- **Clock rules (held).** `serverClock.ts` is the only reader of the device clock in the countdown stack. A grep found no `setInterval` and no `Date.now` or `new Date()` outside `serverClock.ts` in `components/events`, `lib/event-countdown.ts`, `lib/event-opening-form.ts` and the opening code in `lib/events-view.ts`. The server-side `Date.now()` calls in pages are server clock, not device clock. The first client render is `target - seed` from props alone. The chain and timer bookkeeping in `useBoundaryRefresh` and `useCountdownClock` is clean (cleanup clears the only timer, a same-id re-run carries the retry chain, a phase or zone change resets it, and no timer outlives unmount).
- **Contracts (held).** Every new response key is `.optional()` and is spread only for a paid event, so free events keep their exact key set. `EVENT_ISSUES` is append-only (`opening_locked`, `opening_after_start` at the end). `eventEditSchema` and the attendee and event-item schemas stay `.strict()`.
- **Known open items.** Confirmed as described and not re-reported: the per-instance re-seed guard in `useCountdownClock` (two mounted countdowns in the zone, `LiveCountdown` and `SoonStatus`, each ask for one refresh after a long hide), the `É hoje!` versus `Acontecendo agora` P2 render of the `Meus eventos` Reine card for a paid holder (UI-D-788), and the unrelated test residue.
- **Copy and accessibility (held).** I compared the new `events.json` and `payments.json` strings against the UI-SPEC copy table and they match. No gateway brand string appears in the new keys. `role="timer"` is a sibling of the polite wrapper in `PaidEventZone`, and the blocks variant is `aria-hidden` with a separate `sr-only` timer.

The three warnings below are real behaviour gaps (none leaks a link or a date). The info items are maintainability.

## Warnings

### WR-01: A stale stored opening on an unmapped event comes back to life, and the admin form cannot show it

**File:** `packages/modules/events/server/service.ts:1020-1031` (edit read gated on `ta.external_product_id is not null`), with `apps/web/lib/event-opening-form.ts:76-100` (`openingKey`) and `apps/web/app/(app)/eventos/EventForm.tsx` (create then second write)
**Issue:** The API accepts `registrationOpens` on any event (create and update never check for a mapping), and the form writes the date with the event save before the mapping save. If the second write fails (`saveTicket` returns `failed`), or the admin abandons the screen, the event is stored with a date and no mapping. The edit read then hides it (`registrationOpens`, `registrationOpensAt` and `serverNow` are all null unless the definer row exists), so the next edit loads `openingStored = null`. If the admin now turns the switch on, enters the link and leaves the (visibly empty) date field empty, `openingKey` returns `{}` (empty typed, no stored), so the stale date is neither shown nor cleared. The moment the mapping is created, the stale date goes live: members see `Em breve` and a countdown to a date the admin sees as blank, and the sale is closed until then. This is the A-10.2-STALE-DATE hazard the read models hide while unmapped, but nothing removes it before a mapping reappears. Only the form's own `deleteEventMapping` path clears it (D-793). `releaseUnsoldEventMapping` (soft delete) and any API-direct write do not.
**Fix:** Make the stored date visible to the admin whether or not a mapping exists, so the form reflects the truth and the admin can clear it. In `getEventForEdit`, drop the `ta.external_product_id is not null` gate for the admin lane (return the date only when the caller got the admin ticket row or holds `events.event.manage`, which already guards this route) and keep the member-facing reads gated by `pd.paid`. Alternatively clear the column in `app.event_ticket_reset` callers and in the event create-then-failed-mapping path. Add a test: create an event with an opening and no mapping, re-open edit, expect the stored pair.

### WR-02: Gallery refresh ignores openings further than 24 hours away, so a tab left open never swaps `Em breve` back

**File:** `apps/web/components/events/GalleryBoundaryRefresh.tsx:30-38`
**Issue:** `near` drops every opening more than `GALLERY_OPENING_HORIZON_MS` after the seed and passes only the rest to `useBoundaryRefresh`. The hook already handles far boundaries correctly (it waits in `BOUNDARY_HORIZON_MS` steps and re-evaluates without refreshing). The pre-filter removes that capability. A member who opens `/eventos` 30 hours before an opening and leaves the tab visible (desktop, or a mobile PWA left in the foreground) gets no timer for that card at any point: once the page is within 24 hours the schedule is never re-evaluated. Nothing re-seeds the page while the tab stays visible (the countdown only re-seeds after a hide of more than 60 s or a bfcache restore), so the card counts down to `Abrindo agora` on the text note and stays `Em breve` with no refresh until the user reloads or pulls to refresh. The comment says a farther opening is "picked up by whatever re-seeds the page", which is not true for a continuously visible tab. The detail page does not have this gap (`EventActions` passes the opening unfiltered).
**Fix:** Pass every opening to the hook and let it cap the waits:
```tsx
export function GalleryBoundaryRefresh({ openings, serverNow, tags }: GalleryBoundaryRefreshProps) {
  useBoundaryRefresh(openings, tags, serverNow);
  return null;
}
```
If a bound on the number of timers is the concern, it is already one timer (one `useBoundaryRefresh`). Remove `GALLERY_OPENING_HORIZON_MS` and update its test.

### WR-03: The seed offset is anchored at effect time, so a payload older than hydration delays the swap and the doc claim is false

**File:** `apps/web/components/events/serverClock.ts:28-40` (claim in the header, lines 7-10), used by `useCountdownClock.ts:60` and `useBoundaryRefresh.ts:57`
**Issue:** `serverClock` computes `offsetMs = seed - Date.now()` at creation and then `now() = Date.now() + offsetMs`. By construction the estimate equals the seed at the instant the effect runs, whatever the age of the seed. The header says the estimate "lags the true server time by at most the render-to-hydration latency". That is true only for a payload rendered moments before hydration. A page restored from the client router cache on back or forward navigation, or served by the service worker, hydrates with a seed that can be minutes old. The countdown then shows too much time, and the boundary refresh fires late by the age of the payload. The safe direction holds (never early, and no link is shown, because the link only comes from the server), so this is a delayed swap for a willing buyer, not a leak. Recovery today depends on `pageshow` with `persisted` (true bfcache) or a hide of more than 60 s, neither of which covers an in-app back navigation that reuses a cached RSC payload.
**Fix:** Confirm what the router cache serves on back navigation for this page (`staleTimes` is not configured, and `cacheComponents` is on). Then either document the limit in the header or add a one-shot guard: when the first computed `offsetMs` is more negative than a threshold (for example `-30_000`, meaning the seed is much older than the device now), call `router.refresh()` once per mount lineage (a ref, never on the refreshed seed's own re-run). A device whose clock is simply ahead takes the same single refresh and then settles, so there is no loop.

### IN-01: `app.event_checkout_url` and `app.event_sale_ready` now also require a live event (undocumented behaviour change)

**File:** `supabase/migrations/20261113230509_event_opening_reads.sql:52-67`
**Issue:** The previous `app.event_checkout_url` (`20261113010607_event_ticket_reads.sql:51`) read only `payment_products`. The new one joins `public.events` with `e.deleted_at is null`. This is a sensible tightening (a soft-deleted event no longer yields a link), but the header describes the change as the opening check only and says names and behaviour are otherwise unchanged. A reader of the migration will not know the soft-delete rule is new.
**Fix:** Add one line to the migration header ("also null for a soft-deleted event") and a pgTAP case if one is missing.

### IN-02: Duplicate constants for the same horizons

**File:** `apps/web/components/events/GalleryBoundaryRefresh.tsx:4`, `apps/web/app/(app)/eventos/[eventId]/PaidEventZone.tsx:94-96`
**Issue:** `GALLERY_OPENING_HORIZON_MS` repeats `BOUNDARY_HORIZON_MS` (24 h), and `PaidEventZone` redefines `MINUTE_MS` which `lib/event-countdown.ts` already exports. If WR-02 is fixed the first goes away. The second can import the shared constant.
**Fix:** Import `MINUTE_MS` from `@/lib/event-countdown`; delete the gallery constant with WR-02.

### IN-03: A server `opening_after_start` refusal tries to focus a disabled input when the date is locked

**File:** `apps/web/app/(app)/eventos/EventForm.tsx` (the `openingFocus` effect and the `opening_after_start` branch)
**Issue:** When tickets are sold, the opening inputs are `disabled`. If the admin then moves the start earlier than the locked opening, the CHECK raises `opening_after_start`. The form sets the field error, `setStep(1)`, and `setOpeningFocus(true)`. The effect calls `.focus()` on a disabled input, which does nothing, so keyboard focus stays where it was and the error appears under a locked field with no cue that the start is the thing to change.
**Fix:** When `soldNow > 0`, skip the focus effect and point the message at the start field (focus `event-start-date`), or word the locked variant to name the start.

### IN-04: Opening round trip through a wall-clock pair is lossy for a fold hour and for seconds

**File:** `packages/modules/events/server/service.ts:1022-1026`
**Issue:** The edit read returns the opening as `YYYY-MM-DD` and `HH24:MI` in the tenant zone. Two stored instants can map to the same pair: a value with non-zero seconds (the e2e helper `setEventOpening` writes `now() + secs`, and any non-form writer can too), and the repeated hour of a daylight-saving fold in a tenant zone that has one. The form's `sameInstant` check then sees "no change" and sends nothing, which is safe. But if the admin re-saves with the pair unchanged after a fold or seconds mismatch, nothing is rewritten, so no data loss and no spurious `opening_locked`. The risk is only that the displayed value differs from the stored instant by seconds or by one hour inside a fold. Brazilian zones (the pilot) have no DST, so this is theoretical today.
**Fix:** None required for the pilot. If a tenant in a DST zone appears, return the six-digit UTC instant the read already carries (`registrationOpensAt`) and have the form compare against that rather than the wall-clock pair.
