# Phase 09.2 Plan 15: The migration fan-out, the stored schema state and the updating gate Summary

**One command (`ROLE=migrate` / `pnpm db:migrate-all`) applies the central set and then the tenant set to every ready project with per-project isolation, a dry run and exact selectors, records each project's applied-versus-required state in the registry, the API image carries both sets with a deterministic manifest so it knows its required schema without a database call, a tenant that is behind waits behind `TENANT_UPDATING` while the rest serve, and a self-re-arming job heals what failed**

- **Duration:** about 32 min (00:49 to 01:21 local; start approximate, not recorded by command)
- **Tasks:** 3 (1 tracer, 2 auto) plus the plan-13 clock fix as its own commit
- **Commits:** 4

## Accomplishments

- **Tracer.** A freshly built `rede_tenant_b` holding 145 of the 147 tenant files is registered as a ready project (a sealed `postgres` DDL URL). `migrateAll` applies the central set first (nothing pending), then the two missing files with the real runner; B's ledger holds 147 rows, `platform.project_schema_state` reads applied = required = 147 with equal heads and `current`, and a second run reports `applied: 0`. No line contains a connection string.
- **The command.** `migrateAll` validates every argument before any query, resolves selectors read-only, applies the central set (a failure there stops everything, exit 1), then migrates the projects through a pool of `--concurrency` (default 4) in ascending `ref`, dedupes by project id, isolates every failure (`failedVersion`, content-free `errorCode`), and prints central, projects and a summary. `--strict` turns a tenant failure into exit 1; `--dry-run` writes nothing at all (not even project 0's registry fix-up); usage errors exit 2 with one line.
- **State.** `recordSchemaState` upserts the row (keeping the previous applied numbers when a project could not be read), `stateOf` is the single arithmetic (unknown / behind / current), and the host cache of the project's tenants is dropped when the row changed, so a lifted hold-out shows on the next request.
- **The image.** `scripts/build-migrations-manifest.mjs` copies both sets and `roles.sql` byte for byte and writes a sorted, timestamp-free, path-free `manifest.json`; the Dockerfile builds it in the stage that has the whole repository, copies it to `/app/migrations` and sets `MIGRATIONS_DIR`. `getRequiredTenantSchema()` reads the manifest (the repository outside production); `assertManifestPresent()` runs at the top of `main.ts` and stops a production boot with `migrations manifest empty`.
- **The gate and the job.** With the manifest live, a project behind is answered `updating` from the cached host answer, `requireAuth` answers 503 `TENANT_UPDATING` before any key fetch while a project-0 tenant answers 200; `platform.migration-retry` re-runs the fan-out for behind or failed projects every 300 s and is armed at worker boot.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Bootstrap steps stamped `finished_at` with the process clock**
- **Found during:** plans 11 and 14 (flaky ordering case), assigned to this plan by the handoff
- **Issue:** `claimStep` stamps `started_at = now()` (database) while `finishStep` and `failStep` stamped `new Date()`, so step N+1 could start a millisecond before step N ended.
- **Fix:** both use `sql\`now()\``. New case in `project-bootstrap.test.ts`: with only `Date` faked an hour behind, a run that finishes `verify` and fails `roles` must never end a step before it started. Mutation-checked: with the old `new Date()` the case fails (`1792724044367 >= 1792727644381`).
- **Files modified:** packages/core/server/projects/bootstrap.ts, apps/api/tests/integration/project-bootstrap.test.ts
- **Commit:** 2eaa9885

**2. [Rule 3 - Blocking] `defaultMigrationDir` and `readRolesSql` knew only the repository**
- **Issue:** in the image a bundled `dist/main.js` cannot derive the repository from its own location, so the bootstrap steps (and `migrate-set.ts`) would look for `supabase/migrations` in a place that does not exist there, even though the image now carries the files.
- **Fix:** both honour `MIGRATIONS_DIR` (`tenant/`, `central/`, `roles.sql`); unset, nothing changes. `sets.ts` is outside the plan's file list.
- **Commit:** ba4e0224

**3. [Rule 1 - Bug in earlier tests] Four assertions assumed the schema gate was off by default**
- **Found during:** Task 2 (core unit run and `project-auth.test.ts`)
- **Issue:** with the requirement now derived from the repository outside production, `getRequiredTenantSchema()` is no longer `null` by default. Plan 08's "gate off" case in `project-auth.test.ts`, plan 08's "gate is off" and "test seam" cases in `tenant-host.test.ts` and plan 14's "unknown requirement" case in `project-database-state.test.ts` read the old default.
- **Fix:** each states what it means (`setRequiredTenantSchemaForTests(null)`, or `required: null`); the seam case now expects the repository's count after the override is cleared.
- **Files modified:** apps/api/tests/integration/project-auth.test.ts, packages/core/tests/tenant-host.test.ts, packages/core/tests/project-database-state.test.ts
- **Commit:** acf28ffa

**4. [Plan wording] The verify chains' `pnpm db:reset && pnpm db:seed && db-two-databases.sh --reset` were not run**
- No SQL, migration or seed changed in this plan. The suites rebuild `rede_tenant_b` themselves (bare and lagging) and restore the full state at the end; the local stack was left with project 0 only, no schema-state rows, no health rows, no queued retry jobs, `rede_tenant_b` at 147 ledger rows and no tenants.

**5. [Plan wording] `main.ts`'s "exported guard"**
- `main.ts` has top-level side effects and cannot be imported by a test. The production-boot assertion is `assertManifestPresent()` (unit-tested for missing, unreadable, empty and valid manifests) and a source test proves `main.ts` calls it before any role branch.

**6. [Plan wording] Where the `stateOf` table lives**
- Task 3's file list has no test for `schema-state.ts`, so the P50-P52 table is in `migrations-required.test.ts` (it imports `stateOf` directly, no database).

**7. [Plan 14 suggestion, not done] `checkProject` once after a bootstrap ends `ready`**
- Not small and not safe in the files this plan touches: it would run the env-selected provider against the project inside the bootstrap's own tests, writing an `unreachable` health row for a ref the global provider does not map and flipping the host to `unavailable`. Left for a later plan: call `checkProject` from `bootstrap-job.ts` (outside the engine, with the job's provider) so the overview reads `ready` instead of `unchecked` until the first sweep.
