<planning_decisions>
1. **Reference, not secret, in the URL.** `hookRef` is 16 random bytes in base64url (22 characters, generated at bootstrap in plan 13); it only SELECTS a project, the HMAC secret is what authenticates. The legacy path stays so production's Auth config needs no change before the move.
2. **Secret cache is registry cache.** `resolveHookProject` caches the registry row (including the sealed secret, opened on use) for 5 minutes in a bounded map; the plaintext secret is opened per request and never cached.
3. **One reconcile, per project.** There is no new recurring job for the allow-list: a `supabase config push` only ever touches project 0 (tenant projects are configured through the Management API alone), so the reconcile runs at worker boot for each project through the supervisor hook, as it does today for project 0.
4. **Held-out tenants and sign-up.** The slug routes apply the same status precedence as the host answer (plan 08), through the same resolver, so a tenant being prepared or updated cannot be signed up to.
5. **The web is told, never the service key.** `supabaseUrl` and `publishableKey` are public by design; no sealed value is ever part of a public answer.
6. **Serialised after plan 13.** The ordering dependency on plan 13 carries no code dependency: both plans edit `apps/api/src/worker.ts` (the platform job list), which two plans of one wave must never share.
</planning_decisions>
