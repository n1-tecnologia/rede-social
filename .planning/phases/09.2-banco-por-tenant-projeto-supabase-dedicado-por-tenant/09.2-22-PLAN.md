<objective>
Build the engine that moves one tenant's data to its own project: rows, accounts, files and the URLs inside them, verified.

D-534 says every existing tenant leaves the shared project through one reusable tool that copies the tenant's rows (by `tenant_id`), its Auth accounts (same ids, password hashes preserved) and its Storage objects into a project bootstrapped exactly like a new tenant's. This plan is the copy and its proof; plan 23 wraps it in the state machine (suspend, quiesce, cutover, rollback, audit, the command).

The risky parts are all catalog facts: 157 foreign keys (one non-deferrable self reference, one deferrable two-table cycle), generated columns, GoTrue's version-dependent `auth` columns, absolute Storage URLs inside `tenants.branding`, and the person who holds accounts in two tenants. The engine derives order and columns from the catalogs at run time, fails a dry run on any table it cannot classify (so a table added by a later phase cannot be silently skipped), and refuses to merge identities.

Tracer: the seeded rede-lab tenant is copied, rows and accounts, into a freshly bootstrapped second database, with counts equal and nothing of any other tenant present. Tasks 2 and 3 add Storage, URLs, jobs, checksums and the edge cases.

Heavy plan, justified: the engine is a pipeline whose stages share one plan object; the rehearsal on two real databases is the only honest proof until a hosted project exists (H6).

Decisions implemented: D-534 (every existing tenant moves through one tool; same ids, hashes preserved), D-536 (reuses the bootstrap target, `--dry-run`), D-533 (one account per tenant, no merge).

<planning_decisions>
1. **Everything derived from catalogs.** Tables, order, columns and generated-ness are read from `pg_catalog` of the SOURCE and checked against the TARGET; nothing is a hand-written table list except the explicit exclusions and special cases, which are named in `plan.ts` with the reason for each.
2. **The dry run is the safety net for future phases.** A table that gains a `tenant_id` column in a later phase appears in `uncovered` until someone decides its handling; the move refuses to start with a non-empty `uncovered`.
3. **Copy reads, never writes, the source.** The source connection is `read only`; deletion belongs to plan 23's explicit `--confirm-delete`.
4. **Auth over SQL.** The Admin API documents no password-hash import or custom id, so the accounts are copied with SQL over the `postgres` connection (RESEARCH Q11); hosted behaviour of `postgres` on `auth.*` is assumption A10, verified in H6.
5. **Rehearsal fixture is the seed.** `rede-lab` carries rows in most modules; the test never deletes from the source and resets the second database between runs.
</planning_decisions>
