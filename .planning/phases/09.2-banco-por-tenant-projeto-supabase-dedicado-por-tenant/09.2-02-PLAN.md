<planning_decisions>
1. **Runner, not `drizzle-kit migrate`.** CLAUDE.md forbids a second history table; the runner writes the CLI's own ledger (`supabase_migrations.schema_migrations`), so production's 146 existing rows are the baseline with no backfill and `supabase migration list` / `db push --db-url` stay a working manual path.
2. **Central ledger lives in `supabase_migrations`, not `platform`** (deviation from RESEARCH Q3, assumption A-02-1): the first generated central migration creates schema `platform`, so a ledger inside it would have to be created by the runner BEFORE the migration that creates the schema. `supabase_migrations.central_migrations` exists in every Supabase project's reserved schema, is created by the runner on first use, and is still absent from tenant projects because the central set is never applied there.
3. **Checksum side table.** `supabase_migrations.rede_checksums (set, version, sha256)` records the file hash at apply time. For rows the CLI applied before the runner existed (production's 146) the first run ADOPTS the current file hash; the guard then catches every later edit (DEPLOY.md: never edit an applied migration).
4. **Registry tables created now, written later.** Plan 02 creates all five registry tables (`projects`, `tenant_projects`, `project_bootstrap_steps`, `project_schema_state`, `project_health`) in one expand migration so plans 07, 12-15 add no central migration for them; each later plan owns the writes. Route indexes (plan 10), `tenant_moves` (plan 23) and `pgboss_platform` (plan 09) are their own later central migrations.
5. **Default project flag.** `is_default` (at most one true) is what keeps raw `insert into public.tenants` working for the existing 23 integration files, the e2e fixtures and pgTAP `tests.tenant()`; production clears it after the last move (plan 25 runbook), after which an unbound insert fails at commit.
6. **No package is added.** `postgres`, `drizzle-orm`, `tsx` are already dependencies.
</planning_decisions>
