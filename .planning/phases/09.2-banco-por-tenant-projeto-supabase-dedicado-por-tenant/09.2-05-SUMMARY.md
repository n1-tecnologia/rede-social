# Phase 09.2 Plan 05: Tenant-scoped admin-lane sites, key-routed Storage and per-project sign-up Summary

**The admin lane of tenancy, payments and media now addresses a tenant's own database (`withAdminTx({ tenantId })` at every site that already holds the tenant id), Storage resolves the Supabase project from the tenant segment of the object key, and sign-up creates and compensates the Auth user through the tenant's project, with a tenant admin on database B editing rules, listing members, using payments and starting an upload against B alone**

## Accomplishments

- Tracer: an `admin_tenant` whose tenant lives only in `rede_tenant_b` reads `/v1/admin/rules` from B, saves a new text (`rules_version` 4 -> 5 in B, the central row of the same tenant id keeps 'Regras centrais' / 1), saves the same text again (still 5, change-only bump holds in B), and `/v1/admin/members` lists B's three members and not the central-only one.
- 43 sites moved: tenancy 12 (rules 2, admin-members 2, member-admin 2, accept-invite 1, join 2, signup 3), payments 15 (access 5, events 4, setup 2, gate 2, status 1, apply's failed-marking step 1), media 16 (service 9 of 10, derive-job 2, video/event-job 4 of 5, video/fake 1). The inventory guard lists exactly the pending remainder. The predicates `id = ${tenantId}` / `tenant_id = ${tenantId}` of T-08-36 were not touched.
- `storage.ts`: `bucketFor(key)` replaces the module-level `bucket()`. It takes the first path segment, refuses anything that is not a lower-case uuid with the content-free `invalid media key` before resolving, and returns `supabaseAdminFor(await resolveProject(tenant)).storage.from(MEDIA_BUCKET)`. `removeObjects` refuses a batch that names more than one tenant. Exports, signatures and return values are unchanged, so `signReadFor` callers in the courses module and the seed needed no edit.
- `signupMember`: one `supabaseAdminFor(await resolveProject(tenantId)).auth.admin` is taken once and used for `createUser` and for the compensating `deleteUser`.
- `startVideoUpload`: the verified-primary-host read moved out of the tenant transaction into `primaryOriginOf` (platform lane), since `tenant_domains` is the central mirror; the quota check and the `media_assets` insert still share one transaction.
- Payments on B: a central integration row of the same tenant id does not make the overview say "connected"; the token save and the access product land in B only. Media on B: the pending `media_assets` row exists only in B and its key resolves to B's project, with the project's service key sealed from the local stack's key so the sealed-client path really signs the upload.

## Deviations from Plan

### Auto-fixed Issues

**1. [Plan wording / classification] `applyPaymentEvent` has no tenant in scope; re-classed N, plan 10**
- **Found during:** Task 2
- **Issue:** the plan (Task 2 action, truth D-538 and threat T-09.2-26) says the apply job reads the event row first and takes its `tenant_id`. But `kernel.payment-event` receives the event id alone and the row is read INSIDE the one admin transaction that must already be open on some database. On a tenant on another project that transaction would open on project 0 and find nothing (the job would silently log "no such event"). Inventing an id or defaulting to project 0 is exactly what PR-3 forbids.
- **Fix:** only `markFailed(eventId, tenantId)` (which holds the tenant read from the row) migrated; the `applyInTx` site stays on the deprecated overload and its inventory row is now `N`, plan 10, with the reason. A comment at the site says so. T-09.2-26 still holds: the tenant is taken from the stored row, never from a webhook payload; what remains for plan 10 is finding the row's database through the central index (or adding the tenant id to the job payload, which the receive path knows).
- **Files modified:** packages/core/server/payments/apply.ts, apps/api/tests/admin-lane-inventory/payments.ts
- **Verification:** inventory guard 20/20; payments-apply, payments-events and payments-cut suites green on project 0.
- **Committed in:** 7d741923

**2. [Plan wording] Task 2 acceptance count for receive.ts / inbox.ts reads 1, not 2**
- **Found during:** Task 2 acceptance run
- **Issue:** the criterion greps `withAdminTx(<...>)?\(\s*async`; `receive.ts` calls `withAdminTx(` and puts its callback on the next line, so only `inbox.ts` matches.
- **Fix:** none needed; both files are untouched (`git diff --stat` on them is empty) and both remain `pending` N rows in the inventory, which is what the criterion protects.
- **Committed in:** n/a

**3. [Rule 3 - Blocking] The inventory helper could not mark one row of a mixed file migrated**
- **Found during:** Task 1
- **Issue:** the group helper hardcoded `status: 'pending'`; `service.ts` and `event-job.ts` interleave migrated and pending sites in site order.
- **Fix:** an optional fifth tuple element (status) on the three area files' helper. The payments and media files were only edited in their own tasks, so the guard stayed green at every commit.
- **Files modified:** apps/api/tests/admin-lane-inventory/{tenancy,payments,media}.ts
- **Committed in:** 586d945f, 7d741923, 0a5f0d54

**4. [Plan wording] The fake provider's schedule seam gained a tenant argument**
- **Found during:** Task 3
- **Issue:** `enqueueSyntheticReady(event)` is a T site but the normalised event carries no tenant id.
- **Fix:** `createDirectUpload` already holds `input.tenantId`; the seam is now `scheduleReady(event, tenantId)`. The one test override (`media-video.test.ts`) takes only the event and still type-checks.
- **Committed in:** 0a5f0d54

**5. [Plan wording] Storage tests mock `supabaseAdminFor` and `resolveProject` with `vi.mock` instead of an injected registry**
- **Found during:** Task 3
- **Issue:** `storage.ts` binds the admin client and the resolver at module level (the existing test already mocked the module that way); adding an injection seam to production code only for the test was not worth the surface.
- **Fix:** one Storage recorder per project behind the mocked `supabaseAdminFor`; the sign-up test uses the real `createSupabaseAdminRegistry` with fake clients, so the memoisation and the env/sealed split are exercised there.
- **Committed in:** 0a5f0d54, 586d945f
