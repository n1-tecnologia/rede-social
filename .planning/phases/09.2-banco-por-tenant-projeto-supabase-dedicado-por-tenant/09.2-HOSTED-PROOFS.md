# Phase 09.2 hosted proofs (H1 to H8)

This file is the ledger of the proofs that only a person with the hosted accounts can run: a real Supabase
organisation and token, real Pro projects, a real Cloud Run Job, an isolated homolog, real people signing in
with the passwords they had, and a phone. Everything an agent could build is built and proved on the local
stack and on two local databases (plans 02 to 23); what is left here cannot be faked, so nothing in this
file is ever recorded as done by an agent.

**The rule.** Every row ships `pending`. A row becomes `passed` only when Igor pastes the evidence of its
steps and the date, in the row, himself. An agent never edits a Status line, never writes evidence it did
not see, and never edits the `contract_gate` line of the front matter. A phase whose ledger has a `pending`
row closes `human_needed`, never green (assumption A-25-1).

**The evidence rule.** Paste shapes, counts, statuses, HTTP codes, exit codes and the words the screens
show. **Never** a key, a password, a token, a connection string, a webhook token, an e-mail address of a
member, or a project ref of a customer. Replace a ref by `<ref>` and a host by `<host>` in what you paste.
The commands below were written with placeholders (`<token>`, `<ref>`, `<slug>`); put real values only in
your own shell, and prefer `read -s` over typing a secret on a command line.

**The procedures** are in `docs/DEPLOY.md`, "Phase 09.2 release (database per tenant)". The gates G1 to G6
named below are in its "Human gates" table: G1 an empty Pro project and the platform token with the
organisation slug; G2 the three release secrets, their access and the deploy account's rights; G3 the
sketch review; G4 the production reviewer; G5 the Job-versus-revision answer (done: a Job); G6 each
production move.

## H1 — The platform token's scopes and the organisation's reach

- **Proves:** DBT-20 (the Management API client does what the plans assume with a real token), and decides
  two open questions: whether the token can reveal a project's keys (`automatic`, or the panel asks for the
  manual fields) and which key kind the registry should store as the service key (A-12-1).
- **Needs:** G1.
- **Where:** your shell, against one EMPTY Pro project of the platform organisation. Read-only: it changes
  nothing.
- **Steps:**
  1. Export the token and the organisation for this shell only, with `read -s`:
     `read -s SUPABASE_PAT; export SUPABASE_PAT SUPABASE_ORG_SLUG=<slug>`
  2. From the repository root (its `apps/api/.env.local` supplies the local kernel variables):
     `pnpm exec tsx scripts/probe-management-api.ts --ref <ref>`
  3. Again with the key exercise (three GET requests per key kind):
     `pnpm exec tsx scripts/probe-management-api.ts --ref <ref> --exercise-keys`
  4. Read the single JSON object. Note `recommendation`, the key kinds present, the pooler host SHAPE, and the
     `pass` or `fail` of each of auth, storage and realtime for each key kind. The realtime check is the weak
     one (the service exposes no documented read-only route, so `pass` means "not refused"); say so in the
     evidence if it decides anything.
- **Evidence to paste:** the probe's JSON object (it holds shapes and booleans only; read it before pasting),
  and one line: which key kind you chose for the registry and why.
