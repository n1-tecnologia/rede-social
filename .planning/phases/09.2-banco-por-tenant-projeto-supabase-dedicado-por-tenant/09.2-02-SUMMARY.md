# Phase 09.2 Plan 02: Runner, second local database and central registry Summary

**An in-house migration runner applies the 146-file tenant set to a second local database (`rede_tenant_b`) with the Supabase CLI's own ledger, plus a separate central set that creates the zero-policy `platform` registry and a deferred trigger that binds every tenant to a project or refuses the commit**

## Performance

- **Duration:** 13 min
- **Started:** 2026-10-22T21:17:00Z
- **Completed:** 2026-10-22T21:30:00Z
- **Tasks:** 3
- **Files modified:** 23 (task commits, excluding this plan's metadata)

## Accomplishments

- Tracer: `bash scripts/db-two-databases.sh` builds `rede_tenant_b` in the local Postgres, restores the auth/storage/realtime schemas (tolerating exactly the three known errors), and applies 146 files through the same runner production will use; the second run reports `applied: 0`, `platform` and the central ledger are absent there.
- The runner (`applyDirectory`) is postgres-only, takes a per-set session advisory lock with a 15 s timeout, writes each file together with its ledger and checksum rows in one transaction, adopts hashes for CLI-applied rows, refuses edits (`checksum_changed`) and out-of-order files, stops at the first failure and is idempotent.
- The central set (`supabase/central/migrations`, own drizzle config, ledger `supabase_migrations.central_migrations`) creates `platform.projects`, `tenant_projects`, `project_bootstrap_steps`, `project_schema_state`, `project_health`; `pnpm db:reset` now runs the CLI reset, then `pnpm db:central`, then the api_user login script, and the local-stack CI action applies the central set too.
- `tenants_bind_default` (deferred constraint trigger) binds an unbound tenant to the `is_default` project or raises P0001 at commit; project 0 is registered (`is_central`, `is_default`, `credential_source = 'env'`, `ready`) and every existing tenant is bound to it. The existing 44 pgTAP files and the hosts integration suite stay green.

## Issues Encountered
