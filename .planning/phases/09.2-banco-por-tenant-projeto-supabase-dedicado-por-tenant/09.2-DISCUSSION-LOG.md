## Identidade e tenants existentes

### Conta do membro com um Auth por projeto

| Option | Description | Selected |
|--------|-------------|----------|
| Conta por tenant | Same e-mail in two tenants = two independent accounts, own password and session; the 08.1 join, existing-identity invite and shared-password notice leave. | ✓ |
| Login central, dados por tenant | One Auth in the central project, tenant projects only hold data; keeps 08.1, but Realtime and Storage of each project would not accept another project's token and Auth stops being isolated. | |
| Conta por tenant, com vínculo opcional | Per-tenant accounts plus a central e-mail → tenants index for the super_admin; adds a cross-tenant e-mail index and touches D-302. | |

**User's choice:** Conta por tenant (D-533)

### Tenants que já existem no banco compartilhado

| Option | Description | Selected |
|--------|-------------|----------|
| Migrar todos, com ferramenta reutilizável | A "move tenant" tool copies rows, Auth accounts (ids and hashes kept) and Storage objects into a bootstrapped project, with cutover and rollback. | ✓ |
| Só tenants novos agora; os atuais ficam no central | Registry marks old tenants as "central project", code serves both models, migration left to a later phase. | |
| Recriar do zero, descartando os dados atuais | Only if no current tenant has real data to keep. | |

**User's choice:** Migrar todos, com ferramenta reutilizável (D-534)

### Corte de um tenant existente

| Option | Description | Selected |
|--------|-------------|----------|
| Suspender durante a cópia | Reuses the tenant suspension (D-32) as the write freeze; registry switches at the end; members sign in again. | ✓ |
| Cópia ao vivo com replicação lógica | Near-zero downtime, per-table publication/subscription, much more complex. | |
| Janela noturna, sem suspender | Nothing new to build, but writes during the copy are lost or inconsistent. | |

**User's choice:** Suspender durante a cópia (D-535)
**Notes:** Surfaced during this area: the gateway webhook resolves its tenant through a global product mapping (09.1 D-488), so that index must stay central; recorded under Claude's Discretion.

| Option | Description | Selected |

**User's choice:** Escopo explícito na assinatura (D-538)

## Migrations em todos os bancos e worker

### Quem dispara a migration em todos os projetos

| Option | Description | Selected |
|--------|-------------|----------|
| No deploy, com a API nova sem tráfego | CI brings up the new revision without traffic and triggers "migrar todos" inside it; same command by hand with `--dry-run` and `--tenant`. | ✓ |
| Comando seu, separado do deploy | Requires N-1 compatibility on every release; forgetting leaves mixed versions. | |
| O worker aplica sozinho ao subir | No approval gate, two workers racing on one migration, no rehearsal. | |

**User's choice:** No deploy, com a API nova sem tráfego (D-544)

### Falha da migration em um tenant

| Option | Description | Selected |
|--------|-------------|----------|
| Tenant atrasado sai do ar; os outros seguem | Branded "em atualização" screen for the tenant behind, automatic retry, "atrasado" badge. | ✓ |
| Tudo ou nada: o deploy para | Same version everywhere, but one broken project blocks every release. | |
| Atrasado segue na versão anterior (N-1) | Requires every release to be compatible with the previous schema. | |

**User's choice:** Tenant atrasado sai do ar; os outros seguem (D-545)

### Filas do pg-boss

| Option | Description | Selected |
|--------|-------------|----------|
| Uma fila em cada banco de tenant | `pgboss` schema in the tenant set, enqueue stays transactional; worker keeps one instance per tenant plus a central one. | ✓ |
| Fila central com outbox por tenant | One set of pollers, scales to many tenants, but a relay is a new critical piece. | |
| Só fila central, enqueue após o commit | Simplest, loses the transactional enqueue guarantee. | |

**User's choice:** Uma fila em cada banco de tenant (D-546)

### Conjuntos de migration

| Option | Description | Selected |
|--------|-------------|----------|
| Dois conjuntos: tenant e central | The 147 existing files are the tenant set; central-only tables go in a new central set. | ✓ |
| Um conjunto só, em todos os projetos | Simpler runner, but the sealed credentials table would exist in every tenant project. | |

**User's choice:** Dois conjuntos: tenant e central (D-547)

## Claude's Discretion

- Registry and mirror table shapes, the sealing helper, master-key rotation, the encoding of the schema version.
- The connection pool cache and its sizing against per-project pooler limits.
- Which project a token is verified against: the host selects the project, never the token's own `iss` (not discussed with the user; confirm in research).
- Routes with no tenant host (gateway webhook, Mux webhook, the Send Email Hook of each project, sign-up by slug) and the central index each resolves through.
- How the web app and the Realtime client receive each tenant's public URL and key.
- What the Management API can and cannot do for the Auth configuration step.
- Rewriting absolute Storage URLs in copied rows, a fake project provider for local runs, the split of the 17 jobs between central and tenant queues, and all pt-BR copy.

## Deferred Ideas

- Creating the Supabase project from the panel through the Management API.
- Projects in the customer's own Supabase account.
- Tenants on the Free plan with a keep-alive per project.
- A central pg-boss queue with a per-tenant outbox.
- Live copy with logical replication.
- A "Mover para projeto próprio" button in the panel.
- Cross-tenant statistics in the panel.
- Revoking sessions on a payment cut or a block now that Auth is per tenant.
- A central login with a cross-tenant identity link (rejected).
