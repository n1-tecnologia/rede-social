# Phase 09.2 Plan 16: The deploy workflows around the migrate Job Summary

**Both deploy workflows now run a Cloud Run Job (`migrate`, the same image digest, `ROLE=migrate`) after the project-0 migrations and before the API and worker, wait for it and stop the deploy on a central failure; a release preflight names every missing secret at once, homolog refuses the shared-with-production mode, and two repository guards with self-tests keep the order, the concurrency group and the secret lists from drifting.**

## Accomplishments

- **Decision recorded (Task 1).** Igor chose option A on 2026-10-23: "A: Cloud Run Job (Recomendado)". A-16-1 in `09.2-ASSUMPTIONS.md` holds the answer, the date and the reason; the open-decision row is marked answered. The executor only recorded it.
- **Production sequence.** `deploy-api.yml` authenticates to Google Cloud first (moved from after the config push), runs `scripts/check-release-env.sh --env prod`, keeps `supabase db push --include-roles`, the api_user password, the hook guard and the guarded `config push` unchanged, then deploys the Job `migrate` from `needs.build.outputs.image`, executes it with `gcloud run jobs execute migrate ... --wait` (step summary with the execution name and exit code; non-zero fails the step), and only then deploys the API and the worker. `concurrency: deploy-prod-serial`, `cancel-in-progress: false` is untouched.
- **New environment.** Both services: `PROJECT_PROVIDER=supabase`, `SUPABASE_ORG_SLUG` (a GitHub environment variable), secrets `PLATFORM_MASTER_KEYS` (`platform-master-keys-prod`) and `PROJECT_AUTH_SMTP_PASS` (`resend-smtp-pass-prod`); the worker also `MIGRATION_DATABASE_URL` (`migration-database-url-prod`) and `API_PUBLIC_URL`. The header comment documents each name and that the secrets must exist before the push.
- **Homolog.** The same sequence under `migrate-hml` and the `-hml` secrets. The preflight in `build` now fails on `shared-with-production` with the reason and a pointer to plan 25; the isolated-only step conditions were removed so nothing in the sequence can be skipped silently.
- **Release preflight.** `check-release-env.sh` collects the four items (variable plus three Secret Manager secrets with an enabled version) and fails once with one list. It reads names only, and a permission error is a warning, not a false "missing".
- **Guards.** `check-workflows.sh` splits each deploy job into step blocks and asserts order, adjacency, no step-level `if`, `--wait`, concurrency, one image, secret lists, secrets absent from `env_vars`, `PROJECT_PROVIDER`, Job flags and the hml refusal. Its self-test passes a valid copy, then fails a copy with two real step blocks swapped and nine single mutations. `pnpm guard:workflows` runs it plus the release-env self-test, and the CI `static` job runs it.
- **CI.** The local-stack action gained a `second-database` input that installs `postgresql-client-17` from PGDG and puts it first on PATH; only the `db` job passes it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The Job also needs `API_PUBLIC_URL`, `PAYMENTS_PROVIDERS` and `PAYMENTS_SECRET_KEY`**
- **Found during:** Task 2
- **Issue:** the image sets `NODE_ENV=production`, so `assertProductionEnv` runs in the Job. It refuses a production process with no `PAYMENTS_PROVIDERS` or a missing/invalid `PAYMENTS_SECRET_KEY`, and with `PROJECT_PROVIDER=supabase` it also requires `API_PUBLIC_URL`. The plan's Job list had neither, so the Job would have died on boot with "Invalid kernel environment" before touching a database.
- **Fix:** the Job lists `API_PUBLIC_URL`, `PAYMENTS_PROVIDERS=kiwify` and the secret `PAYMENTS_SECRET_KEY`, in both workflows.
- **Files modified:** .github/workflows/deploy-api.yml, .github/workflows/deploy-hml.yml
- **Commit:** a66fd2cd

**2. [Rule 3 - Blocking] The worker also needs `API_PUBLIC_URL`**
- **Found during:** Task 2
- **Issue:** the plan called `API_PUBLIC_URL` "already a literal", which is true of the API only; the worker had none, and `PROJECT_PROVIDER=supabase` makes `assertProductionEnv` require it.
- **Fix:** added to the worker in both workflows (the same literal in production, the `API_PUBLIC_URL` variable in homolog).
- **Commit:** a66fd2cd

**3. [Plan wording] `SUPABASE_URL` is a mounted secret on the Job, not an env value**
- The plan listed it under env; the services mount `supabase-url-prod`, so the Job does the same and the guard's secret-list rule stays uniform.

**4. [Plan wording] `guard:workflows` also runs `check-release-env.sh --self-test`**
- So the CI `static` job exercises the preflight's self-test too; the plan's verify command runs it separately as well.

**5. [Plan wording] The preflight treats a Secret Manager permission error as unverifiable**
- The documented deploy account holds `run.admin`, `artifactregistry.writer` and `iam.serviceAccountUser` only. Counting a `PERMISSION_DENIED` as missing would fail every deploy; it is a warning instead, and the missing grant is a step for plan 25 (below).

**6. [Rule 3 - Plan wording] Job display names changed**
- The job labels now read "Production (migrations -> migrate job -> API -> worker)" and "Homolog (migrations -> migrate job -> API -> worker)". No step name was removed; the unnamed `uses:` steps that gained a `name:` (Authenticate, Deploy the API, Deploy the worker) are the same actions.
