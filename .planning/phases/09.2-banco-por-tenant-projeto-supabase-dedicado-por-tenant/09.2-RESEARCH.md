## User Constraints (from CONTEXT.md)

### Locked Decisions

**Identity and the tenants that exist today**
- **D-533: One account per tenant.** Each tenant's Auth (the Auth of its own project) holds its own accounts. The same e-mail in two tenants is two independent accounts, each with its own password and session. The Phase 08.1 flows that exist only because one identity spans tenants no longer apply: "Participar de [B]" on sign-up and login (D-301, D-305, D-306), the existing-identity invite (D-314), the shared-password notice (D-312) and the generic-host community picker (D-308). The sign-up of an e-mail that already has an account in the same project keeps the Phase 1 answer (D-04). — **Reversibility:** one-way — after the move each project's `auth.users` is independent, and merging identities again would be a new data migration plus a new identity model.
- **D-534: Every existing tenant is moved.** The production tenants, `rede-demo` and `rede-lab` all leave the shared project through one reusable tool. It copies the tenant's rows (by `tenant_id`), its Auth accounts (same user ids, password hashes preserved) and its Storage objects into a project that was bootstrapped exactly like a new tenant's. A person who held memberships in two tenants ends up with an account in each, with the password they had. After the last move the central project holds platform data only. — **Reversibility:** costly — the move rewrites where production data lives, and it can only be undone while the old rows are kept.
- **D-535: Cutover by suspension.** While a tenant is copied it is suspended (D-32), and members see the branded "temporariamente indisponível" screen. When the copy is verified the registry points at the new project and the tenant is reactivated. Sessions do not migrate (each project signs with its own keys), so members sign in again. The old rows are kept until the super_admin confirms, which is the rollback window.
- **D-536: The move is a command, not a screen.** A pnpm script that Igor runs once per tenant. It reuses the creation bootstrap, offers `--dry-run`, writes an audit row to the registry and can roll back by pointing the registry at the old project again. No new panel screen, so no design gate for it. A panel button can wrap the same code later.

**Central project, mirror and routing**
- **D-537: The central project mirrors each tenant.** The current project becomes the control plane. For every tenant it keeps a mirror (name, brand, status, enabled modules, primary host, project coordinates), so the panel list, `GET /v1/public/tenants/by-host` and the branded "indisponível" screen work while a tenant's project is down or paused. Ownership is split by who edits: the tenant's project owns the brand and the rules text (the `admin_tenant` edits them), and the central project owns status, modules, domains and the project registry (the `super_admin` edits them) and pushes a copy to the tenant's project. A reconcile job heals drift. — **Reversibility:** costly — the by-host answer, the panel list and the flag lookups all read the mirror.
- **D-538: Routing is explicit in the signature.** `withTenantTx` resolves the tenant's project from `ctx.tenantId`. `withAdminTx` now requires the tenant, and a separate platform-lane function opens the central project. There is no ambient per-request context (no AsyncLocalStorage). The Biome restriction that confines the admin lane to the kernel stays. Each of the 119 `withAdminTx` call sites is classified as tenant-scoped or platform. — **Reversibility:** costly — 197 `withTenantTx` and 119 `withAdminTx` call sites sit behind these signatures.
- **D-539: Credentials are sealed in the registry.** The database URL, service key, publishable key and project ref of each project are stored in the registry table, sealed with a platform master key held in Secret Manager. In the panel they are write-only: never returned by the API, never logged. The API opens them in memory when a pool is created. It follows the scheme already built for the gateway secret (`packages/core/server/payments/secret.ts`: AES-256-GCM, a key id for rotation, the row id as authenticated data), extracted into a kernel helper. — **Reversibility:** costly — every stored credential is sealed under the scheme.
- **D-540: A project may serve several tenants outside production.** The registry accepts several tenants pointing at one project, so local development, CI and homologation keep one stack with `rede-demo` and `rede-lab` together. Only the production panel refuses a project already used by another tenant. The schema is identical in every project, with `tenant_id` and RLS on every table: the single-tenant schema was rejected because it would rewrite 147 migrations and break the shared non-production model. The existing two-tenant isolation suite stays as the second layer, and a small set of tests over two databases proves the routing.

**Creating a tenant and the bootstrap**
- **D-541: The panel asks for the project ref.** The projects live in Igor's Supabase organization. He creates an empty project and pastes only its project ref in the "Novo tenant" form. The system obtains the keys, the pooler address and the Auth configuration with the platform token, and generates the password of the `api_user` role itself. Research must confirm what the Management API delivers (keys, running SQL, database password). Where it falls short, the form also asks for the `postgres` password and the keys, and the Auth configuration still goes through the token.
- **D-542: The bootstrap is a list of idempotent steps.** Each step can run again without damaging what is done, and the panel shows the status of every step (running, done, failed with the reason). The tenant stays "em preparação", accepts no login, until every step passes, and "Tentar de novo" resumes at the step that failed. The steps are at least: verify the project, create the roles (`api_user` without `BYPASSRLS`, `supabase/roles.sql`), apply the tenant migration set, configure Auth (the two access hooks, the Send Email Hook, SMTP, redirect allow-list, signing keys), create the buckets, create the Realtime policies, insert the tenant row and its modules, and schedule the first-admin invite (D-30: it is sent when the primary domain is verified).
- **D-543: Every production project is on Pro.** The registry keeps the plan as information only. A health job checks each project (reachable, paused, behind on migrations) and the panel shows a badge. The connection budget stops being one global ceiling and is computed per project (every project has its own pooler), which `docs/DEPLOY.md` "Connection budget (Pro)" must restate. Phase 01's keep-alive stays for the central project.

**Migrations and the worker**
- **D-544: The fan-out runs at deploy, on the new revision.** In the production deploy the CI brings up the new API revision without traffic and triggers "migrar todos" inside it, so the sealed credentials never leave GCP. Traffic moves only after it passes. The same command runs by hand with `--dry-run` and `--tenant <slug>`, and the panel shows each tenant's schema version. It replaces the single `supabase db push` for tenant projects and keeps the D-12 order (migrations, API, worker). — **Reversibility:** costly — both deploy workflows and `docs/DEPLOY.md` are rewritten around it.
- **D-545: A tenant that is behind is held out.** The API compares each tenant's schema version with the version it requires. For a tenant that is behind, it answers with a branded "em atualização" screen (the same mechanism as the suspended tenant, D-32) until the migration passes, while the other tenants keep running. The job retries by itself and the panel shows "atrasado". There is no N-1 compatibility requirement on releases, and one failing project never blocks the release of the others. — **Reversibility:** costly — the per-request version check becomes part of every release.
- **D-546: Every tenant database has its own pg-boss queue.** The `pgboss` schema ships with the tenant migration set and the enqueue stays transactional inside the tenant's own transaction (`enqueueInTx`). The worker keeps one pg-boss instance per tenant plus one central instance for the jobs that are about the platform (domain verification, invite sending and the like). The polling and session-connection cost grows with the number of tenants, which is acceptable for dozens of tenants and is revisited past that. — **Reversibility:** costly — queue names, the worker boot and the connection budget are all built per database.
- **D-547: Two migration sets.** The 147 existing files become the tenant set, which "migrar todos" applies to every tenant project. The tables that must exist only in the central project (registry, sealed credentials, mirror, migration ledger) live in a new central set applied only to the central project, so they never exist in a tenant's project. Local, CI and homologation apply both sets to their one stack. — **Reversibility:** costly — the directory layout, the CI steps and the drizzle-kit `out` path change.

### Claude's Discretion
- The shape of the registry and mirror tables, the sealing helper's name and key variable, the master-key rotation procedure, and the encoding of the schema version (a ledger row per applied file versus a single counter), as long as D-537, D-539 and D-545 hold.
- How the connection pools are held: one pool per tenant project with a bounded, least-recently-used cache and a small `max` per pool, sized against the per-project pooler limits and the Cloud Run instance count.
- How the API picks the project to verify a token against: the host (or the platform host) selects the project first and the token must verify against that project's keys and issuer, never the project named by the token's own `iss`. This was not discussed with the user and has to be confirmed in research, because it is also what keeps a token of tenant A from ever verifying on tenant B.
- Routes with no tenant host (the gateway webhook, the Mux webhook, the Send Email Hook of each project, sign-up by slug on generic hosts): the opaque per-tenant reference they carry, and the central index each one resolves through. Mux assets and gateway products need the tenant recorded at creation time.
- The web side: how `proxy.ts` and `@supabase/ssr` receive the tenant project's public URL and publishable key (from the by-host answer), and the same for the Realtime client and its token source.
- What the Management API can and cannot do for the Auth configuration step (including that `supabase config push` is a per-project CLI run today, and the runtime allow-list adapter and its reconcile job in `packages/core/server/platform/reconcile-allow-list.ts`).
- Rewriting of absolute Storage URLs inside copied rows (`tenants.branding` and any other jsonb that stores a bucket URL) during the move.
- The fake project provider for local runs, in the shape of `VideoProvider` and the domain provider, so no local or CI run touches a real Supabase project.
- Which of the 17 jobs are platform jobs (central queue) and which are tenant jobs, and how the per-tenant daily dispatcher (`kernel.daily-tenant-dispatch`) loops projects.
- All pt-BR copy not quoted here, including the "em atualização" and "em preparação" screens, and the visual design of the panel changes.

### Deferred Ideas (OUT OF SCOPE)
- Creating the Supabase project itself from the panel through the Management API (the operator would pick only a name and a region). Today the project is created by hand and only its ref is pasted.
- Projects in the customer's own Supabase account. The platform token would not reach them, so the Auth configuration would become a manual checklist.
- Tenants on the Free plan with a daily keep-alive per project.
- A central pg-boss queue with a per-tenant outbox, for the day the number of tenants makes one polling instance per database too costly.
- Live copy with logical replication, for a move with almost no unavailability.
- A "Mover para projeto próprio" button in the panel that wraps the D-536 tool.
- Cross-tenant statistics in the panel (member counts, activity): the list shows only what the mirror holds.
- Revoking a member's session on a payment cut or a block, now that Auth is per tenant (the reason in 09.1 D-499 ended, the behaviour was left as it is).
- A central login with a cross-tenant identity link, discussed and rejected in favor of D-533.

## Summary

Phase 09.2 is an infrastructure and integration phase. Three findings shape the whole plan. **(1)** The Management API (PAT) can, on an existing project and from the OpenAPI document alone, read or create API keys (`GET/POST /v1/projects/{ref}/api-keys`), read the Supavisor pooler config (host, port, `connection_string`), **set the database password** (`PATCH /v1/projects/{ref}/database/password`), read project status and service health, and read/patch the Auth config including all hook fields, SMTP, site URL, redirect allow-list and mailer templates, the signing keys, the PostgREST exposed schemas, the Storage global file limit and the Realtime `private_only` flag [CITED: https://api.supabase.com/api/v1-json fetched 2026-10-22]. Because the platform can set the `postgres` password itself, the D-541 fallback (ask the operator for password and keys) is only needed if the PAT lacks the key-secret scope. The docs do not say which role `database/query` runs as nor whether multiple statements run in one transaction, so the plan should **not** use that endpoint for the schema: connect as `postgres` through the Supavisor **session** pooler (IPv4) with postgres.js and apply files with a small in-house runner that writes the Supabase CLI's own ledger. **(2)** The routing change is mechanical and compiler-checkable: making `withAdminTx` take a target turns the 119 call sites into type errors, and a bounded pool cache keyed by project replaces the process singleton in `packages/core/db/client.ts`. The subtle parts are not the pool but the things that silently assumed one database: pg-boss's queue cache is read from the boss instance's own database (so the enqueue sender must be per project), token verification (module-level JWKS), the host answer, three no-host webhooks, `tenants.branding` absolute URLs, the Docker image (which does not contain the migrations), and `tenant_invites.created_by` (a foreign key to a user that will live in another project). **(3)** The safest tracer is to register the *current* project as "project 0" bound to every existing tenant, ship the seam and registry as a behaviour-identical expand release, bootstrap a new tenant on a second database, and only then move production tenants one at a time; the Phase 08.1 removal is a *contract* step that must wait until the last tenant has moved.

**Primary recommendation:** Build in this order: (a) expand release (registry + sealed credentials + explicit-routing seam + two-set migration runner, project 0 bound to every tenant, behaviour unchanged), (b) bootstrap engine as a durable job on a central pg-boss queue using the fake provider locally and a real empty project as a human gate, (c) fan-out as a **Cloud Run Job on the same image** run before the API/worker deploy, (d) worker supervisor + per-project queues, (e) move tool and the actual moves (one-way door, Igor runs), (f) contract release removing the Phase 08.1 identity flows.

## Research Question 1: what the Management API delivers (D-541, first-plan question)

**Source of truth read this session:** the live OpenAPI document `https://api.supabase.com/api/v1-json` (350,759 bytes, fetched 2026-10-22, parsed locally), the Management API introduction page, and the per-endpoint reference pages [CITED: https://supabase.com/docs/reference/api/introduction]. **Limits and failure modes.** Standard limit **120 requests per minute**, tracked per user, per project-or-organization and per endpoint; excess calls get **429 for the remainder of the minute**; headers `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (seconds to reset); PAT limits are shared by every token of the same user; `POST /v1/projects/:ref/database/migrations` allows 120 requests but has a **3-minute timeout**; recommended handling is exponential backoff using `X-RateLimit-Reset` [CITED: https://supabase.com/docs/reference/api/introduction]. A scoped PAT reaches only the organisations, projects and permissions chosen at creation; a classic PAT ("Legacy") has the user's full privileges. Revealing key values needs **API Keys (Read) plus API Key Secrets (Read)** on a scoped PAT, otherwise 403 [CITED: https://supabase.com/docs/guides/api/api-keys]. Project status enum: `INACTIVE, ACTIVE_HEALTHY, ACTIVE_UNHEALTHY, COMING_UP, UNKNOWN, GOING_DOWN, INIT_FAILED, REMOVED, RESTORING, UPGRADING, PAUSING, RESTORE_FAILED, RESTARTING, PAUSE_FAILED, RESIZING`; per-service health status enum `COMING_UP, ACTIVE_HEALTHY, UNHEALTHY` for services `auth, db, db_postgres_user, pooler, realtime, rest, storage, pg_bouncer` [CITED: api.supabase.com/api/v1-json `V1ProjectWithDatabaseResponse_Output`, `V1ServiceHealthResponse_Output`].

## Research Question 2: schema bootstrap mechanics (146 files, not 147)

**Count correction.** `supabase/migrations/` holds **146 `.sql` files plus the drizzle `meta/` directory**; "147" in CONTEXT counts the `meta` entry [VERIFIED: `ls supabase/migrations | wc -l` → 147, `ls *.sql | wc -l` → 146; local stack ledger `select count(*) from supabase_migrations.schema_migrations` → 146 on 2026-10-22]. Total 777,164 bytes; largest 34,760 bytes (`20261018222405_dashboard_members_functions.sql`). 127 of the 146 contain drizzle `--> statement-breakpoint` markers; none contains `begin`/`commit` or `concurrently` [VERIFIED: grep this session], so every file is safe inside one transaction.

**The CLI ledger.** `supabase_migrations.schema_migrations` has columns `version text`, `statements text[]`, `name text` [VERIFIED: `information_schema.columns` query against the local stack, read-only session]. The runner writes that exact table (version = the 14-digit file prefix, `name` = the rest), so (a) production's existing 146 rows are the baseline with no backfill, (b) `supabase migration list` / `db push --db-url` keep working as the manual path, (c) the "schema version" of a tenant is the set of applied versions compared with the manifest of the running image.

**Runner algorithm (prescriptive).**
1. Connect as **`postgres`** through the session pooler (`postgres.<ref>@<pooler host>:5432`, `prepare:false` irrelevant in session mode, `max:1`). It must be `postgres`: `alter default privileges in schema public ...` in `20260912031029_app_membership_lookup_and_grants.sql:30-38` is *per creating role*, and Supabase's own objects expect `postgres` ownership.
2. `select pg_advisory_lock(hashtext('rede.migrate'))` (session lock) so a Job retry and a hand run cannot interleave; `set lock_timeout = '15s'`.
3. `create schema if not exists supabase_migrations; create table if not exists supabase_migrations.schema_migrations (version text primary key, statements text[], name text)` (the CLI creates the same shape on first push `[ASSUMED]`; local table is the reference).
4. Read the ledger, sort the manifest by version, and for each file not in the ledger: `await sql.begin(async (tx) => { await tx.unsafe(fileText); await tx.unsafe('insert into supabase_migrations.schema_migrations (version, name) values ($1, $2)', [v, n]); })`. `unsafe()` without parameters uses the simple protocol, which accepts a multi-statement string; the Supabase CLI also runs each file inside one transaction [VERIFIED: `20260913150245_pgboss_schema.sql` header: "the Supabase CLI already runs each migration inside one transaction, and a nested COMMIT would close it early"].
5. Optional guard: a runner-owned side table `supabase_migrations.rede_checksums(version, sha256)`; refuse a run when a recorded checksum differs from the file ("never edit the applied one", DEPLOY.md). Cheap and catches the one mistake that silently desynchronises N databases.
6. Re-run on a done project is a no-op (ledger complete).
7. A file's failure rolls back that file only, records `failed_version` + SQLSTATE in the central `project_schema_state`, and stops that project (later files may depend on it). Never continue past a failed file.

**Extensions.** `citext` (app_helpers), `pg_trgm`, `unaccent` (member_profiles_search) are created `with schema extensions` [VERIFIED: grep of `create extension` this session]; available on hosted Supabase `[ASSUMED, production already runs them]`. `pgtap` is created only by test helpers.

**Things in the 146 files that matter for a *remote, fresh, empty* project.**
- `20260912030541_app_helpers.sql:5-12` creates `api_user` if missing (`nologin nobypassrls noinherit`) and the two grants; step 2 and this file are the same block (idempotent). The login password is never in SQL (comment in `supabase/roles.sql`).
- `20260912031030_auth_user_mirror.sql:15-17` does `drop trigger if exists on_auth_user_created on auth.users` then creates it. It works in production today via `postgres`; it will work for a runner connected as `postgres` `[ASSUMED]` (same role).
- Storage/Realtime objects are touched by `20260917021738`, `20260921182426`, `20260922020621`, `20261013214735` (guarded with `to_regclass('storage.buckets') is not null`) and `20260930123213` (policy on `realtime.messages`, `realtime.topic()`) — these require the Supabase platform schemas, which a bare second database does **not** have (see Local/CI shape).
- `20261007153044_confirm_existing_auth_emails.sql` updates `auth.users` (data fix; no-op on an empty project).
- `20261019152008`, `20261020230440` grant `execute` to `supabase_auth_admin` (role exists on hosted).
- **Not safe on a non-empty project:** drizzle emits plain `create table` (no `if not exists`); the pre-check "projeto vazio" is a hard requirement, not a courtesy. The bootstrap must stop with reason `notEmpty` when step 1 finds a ledger row or a `public` table.
- **Central-only tables never collide** with the tenant set because they live in a separate schema `platform` (below); the tenant set has no object in that schema.
- The `pgboss` schema (`20260913150245_pgboss_schema.sql`, 439 lines, pg-boss 12.31.0 verbatim) ships inside the tenant set; the runtime issues no DDL (`migrate: false`, fixed `schema: 'pgboss'`) [VERIFIED: `packages/core/server/jobs/boss.ts:49-50`].
- Time and size: 146 transactions through a pooler hop is minutes at worst; this is why the bootstrap is a durable job, not an HTTP request.

**Layout (prescriptive).**
```

  config.toml  roles.sql  seed.sql  signing_keys.json   # local stack, unchanged
```

Why not put both in `supabase/migrations`: the CLI has no option to change the migrations directory (config reference lists only `db.migrations.schema_paths`, used by the legacy diff engine, and `db.seed.sql_paths`) [CITED: https://supabase.com/docs/guides/local-development/cli/config], so a second directory would be invisible to `db reset`. There *is* a global `--workdir <path to a Supabase project directory>` flag [VERIFIED: `node_modules/.bin/supabase --help`, CLI 2.117.0], but a second workdir would need its own `config.toml` and would share the CLI ledger table with the tenant set (versions "remote only" noise). Use the in-house runner for the central set with its **own ledger** `platform.central_migrations`; the tenant set keeps the CLI ledger.

**Application order everywhere.** Local/CI: `supabase db reset` (tenant set + seed.sql, which is empty) → `pnpm db:central` (central runner) → `scripts/db-local-role.sh` → pgTAP → seed (`pnpm db:seed`, extended to write the registry). Production/hml central project: tenant runner (as for any project; project 0 is registered) then central runner. Tenant projects: tenant runner only. `pnpm db:reset` becomes `bash scripts/supabase.sh db reset && pnpm db:central && bash scripts/db-local-role.sh`.

**Central objects live in schema `platform`, not `public`.** Reasons: pgTAP `010-rls-coverage` and `040-schema-conventions` enumerate `public` tables and demand `tenant_id` or an exemption [VERIFIED: `supabase/tests/010-rls-coverage.sql:8-23`, `:55-67`]; and `platform` can be granted only to the admin lane (`service_role`) while `authenticated` gets nothing (RLS on, zero policies). `api_user` already holds `service_role`, so `withPlatformTx` is `set local role service_role` exactly like today's admin lane. A pgTAP assertion `to_regnamespace('platform') is not null` in the central project and bootstrap post-condition `is null` in every tenant project proves D-547's "never exist in a tenant's project".

### Target design (prescriptive)

```ts
// packages/core/db/ (kernel). Names are suggestions; the shapes are the contract.
export type LaneTarget = { tenantId: string } | { projectId: string };

export function withTenantTx<T>(ctx: Pick<RequestContext,'userId'|'tenantId'|'role'>, fn: (tx: Tx) => Promise<T>): Promise<T>;
//   resolves project := registry.projectOfTenant(ctx.tenantId); pool := pools.get(project); same claims + `set local role authenticated`.
```

### Pool cache design

| Parameter | Recommendation | Reason |
|---|---|---|
| Key | `${projectId}:${credentialVersion}` | a credential replace opens a new pool and drains the old one |
| Capacity | 24 pools per process (LRU) | a Cloud Run instance serving many hosts never holds more than 24 × (3+1) sockets |
| Per-pool `max` | 3 on the API, 4 on the worker | today one instance has 5 for everything; a tenant host concentrates traffic on one project per instance |
| Options | `postgres(url, { prepare: false, max, idle_timeout: 20, max_lifetime: 1800, connect_timeout: 10 })` | `prepare:false` is mandatory in transaction mode [CITED: connecting-to-postgres]; `idle_timeout` makes unused pools shrink to 0 sockets |
| Eviction | `await sql.end({ timeout: 5 })` after removing from the map; the entry keeps an in-flight counter and is not evicted while it is > 0 | postgres.js `end({timeout})` waits for queries then force-closes `[ASSUMED from postgres.js README]`; verify in the unit test |

| Credentials | unsealed once per pool; never kept in a long-lived object that is logged | D-539 |

**Per-project connection budget (restating `docs/DEPLOY.md:967-1050` per project).** Today: `2 × (A × 6 + W × 13) + H × 6 + R ≤ L` with one project, A=20, W=1, L=400 (Small) gives 318 [VERIFIED: docs/DEPLOY.md "Formula" table]. Per tenant project P the load is: API clients `A_P × (M + 1)` where `A_P` ≤ A is the number of API instances that touch P, `M` = per-pool max (3) and +1 is the lazy pg-boss sender (`max: 1`, `enqueueInTx`); worker clients `M_w + 2 + 1 = 7` (pool 4, pg-boss session 2, sender 1); and `R` reserve (migration Job holds 1 session connection, Studio, `psql`). Rollout doubles the API term (old + new revision). So `2 × A_P × (M+1) + 7 + R ≤ L_P`: with A_P = 20, M = 3, R = 20: 2×80 + 7 + 20 = **187 ≤ 200 (Micro)**, **≤ 400 (Small)**; with the realistic A_P of 2–4 instances per tenant it is ~40. The *global* ceiling disappears; what remains global is Cloud Run's per-instance socket count (≤ 24 × 4 = 96) and the central project: platform traffic + unmoved tenants (until the last move) + the platform pg-boss. Write this into DEPLOY.md and keep `--max-instances=20` (CPU quota, deploy-api.yml comment).

## Research Question 5: token verification against the host-selected project (Claude's Discretion, confirmed)

**Design (confirmed as sound).**
1. `resolveRequestHost` already reads the BFF-forwarded `x-tenant-host` header (`TENANT_HOST_HEADER = 'x-tenant-host'`, `packages/contracts/src/hosts.ts:5`) and resolves it to a verified tenant or `unknown`; `Host`/`X-Forwarded-Host` are never read [VERIFIED: `require-auth.ts` doc comment]. Extend `TenantHostResolution.tenant` with `projectId`, `supabaseUrl`, `publishableKey` (public values) and `schemaState`.
2. Select the **verification project before parsing the token**: a registered tenant host → that tenant's project; platform host, unregistered host, Vercel Preview or no header → the central project.
3. `verifyBearer(c, project)`: `jwtVerify(token, jwksFor(project.supabaseUrl), { issuer: <project.supabaseUrl>/auth/v1, audience: 'authenticated', algorithms: ['ES256'] })` (code example below). `jwksFor` memoises `createRemoteJWKSet` for `<url>/auth/v1/.well-known/jwks.json` in a bounded map keyed by project URL (cap 64, a keyset function holds its own cache: fresh for 10 min, refetch on unknown `kid` at most every 30 s, 5 s fetch timeout — the jose defaults quoted above). **Never read `iss` from the unverified token to choose a keyset**: an attacker would pick the JWKS URL.
4. Negative control (DBT-10): a token minted by project A's key (or A's `iss`) sent with host B's `x-tenant-host` fails signature verification → `401 INVALID_TOKEN`. Unit test with two generated ES256 key pairs and an injected `fetch`/local JWKS; integration test with two registry rows whose `supabase_url` point to two in-process JWKS servers (the fake provider can host them).
5. Platform sessions: `requireSuperAdmin` verifies against the central project and keeps its explicit "registered tenant host → 403 `TENANT_HOST_MISMATCH`" rule (a super_admin token presented on a tenant host would fail at step 3 first with 401; keep both). `isPlatformAdmin` becomes `withPlatformTx`.
6. **Key rotation:** Supabase edge caches the JWKS endpoint 10 min and client libraries may cache another 10 [CITED: https://supabase.com/docs/guides/auth/signing-keys]; jose's `cacheMaxAge` default (10 min) matches. After a rotation, wait ≥ token TTL + 15 min before revoking the old key (documented 1 h 15 min for a 1 h token) — an operational note for the runbook.
7. Claims: the app injects its own `request.jwt.claims` per transaction (it does not rely on a custom access token claim), so the only things read from the token are `sub`, `email`, `exp`, `aud`, `iss`, `role`. The hooks stay disabled by default (see Q1).

```ts
// packages/core/server/auth/jwks.ts (target shape)
const keysets = createBoundedTtlCache<ReturnType<typeof createRemoteJWKSet>>(64);
export function jwksFor(supabaseUrl: string) {
  const hit = keysets.get(supabaseUrl);
  if (hit) return hit;
  const set = createRemoteJWKSet(new URL(`${supabaseUrl}/auth/v1/.well-known/jwks.json`));
  keysets.set(supabaseUrl, set, 60 * 60_000);
  return set;
}
```

## Common Pitfalls

### Pitfall 1: runner connected as the wrong role
**What goes wrong:** objects owned by a non-`postgres` role; `alter default privileges` (per creating role) grants differ; later migrations fail on ownership.
**How to avoid:** connect as `postgres.<ref>` on the session pooler; assert `current_user = 'postgres'` as the runner's first statement.
**Warning signs:** `permission denied for table` for `authenticated` on a freshly applied project.

### Pitfall 2: relying on the Beta query endpoint
**What goes wrong:** statement size, role, transactionality undocumented; endpoint "subject to change or removal".
**How to avoid:** use it only for the read-only emptiness probe, with a fallback to `GET /database/migrations`; never for the 146 files.

### Pitfall 3: building the pooler host from the region
**What goes wrong:** the index in `aws-[INDEX]-[REGION]` differs per project; connections fail with tenant-not-found.
**How to avoid:** read `host/port/db_name` from `GET /config/database/pooler`; username `<role>.<ref>`.

### Pitfall 4: a project still `COMING_UP`
**What goes wrong:** step 2 fails in seconds with connection errors and the operator sees "failed" for something that heals itself.
**How to avoid:** step 1 waits on status + health (`auth, db, pooler, realtime, rest, storage` all `ACTIVE_HEALTHY`), 10-minute budget, reason `unreachable` only after it.

### Pitfall 5: cache staleness during a move
**What goes wrong:** an instance with a 60 s old host answer keeps writing to the source after suspension.
**How to avoid:** the quiesce wait of 65 s plus the row-count/`updated_at` stability check; registry TTL 15 s.

### Pitfall 6: one pg-boss sender for all databases
**What goes wrong:** `getQueueCache` reads the queue row from the sender's own database; the insert targets the caller's tx on another database; `Queue ... does not exist` or a wrong partition table name.
**How to avoid:** sender per project, found through the tx's project; guard queue scope.

### Pitfall 7: `tenant_invites.created_by` and other super_admin ids
**What goes wrong:** `createTenant` writes a central user id into a tenant database FK → violation; the first plan to touch it fails late.
**How to avoid:** nullable, FK dropped (DBT-36); grep every write that stores `actor.userId` of a platform actor.

### Pitfall 8: non-deferrable self reference during the move
**What goes wrong:** `feed_comments` replies inserted before parents; `events`/`event_secrets` cycle.
**How to avoid:** order by `parent_depth`; `set constraints all deferred` (both cycle constraints are `DEFERRABLE`).

### Pitfall 9: enabling the access hooks at bootstrap
**What goes wrong:** `hook_before_user_created_allowlist` passes only e-mails with an active `access_grants` row, so an enabled hook on an ungated tenant blocks sign-up; an enabled hook at a missing function answers 500 on every login (`scripts/guard-auth-hooks.sh` header).
**How to avoid:** bootstrap sets URIs and `enabled:false` (production's state); enabling is a deliberate per-tenant step (Open Question 2).

### Pitfall 10: `supabase config push` overwriting runtime allow-list entries
**What goes wrong:** config push sends the whole `[auth]` block and wipes `uri_allow_list` entries written through the API.
**How to avoid:** tenant projects are never touched by config push (only Management API); project 0 keeps the worker-boot reconcile; per-project advisory lock.

### Pitfall 11: image without migrations
**What goes wrong:** the Job starts and finds no SQL; or the API cannot know `REQUIRED_*`.
**How to avoid:** Dockerfile copy + manifest + a boot assertion that the manifest is non-empty.

### Pitfall 12: build-time `NEXT_PUBLIC_*` in client bundles
**What goes wrong:** `SUPABASE_TUS_ENDPOINT` and any inlined URL keep pointing at project 0 after a move.
**How to avoid:** derive from server-provided values; add a unit test that greps the client bundle sources for `process.env.NEXT_PUBLIC_SUPABASE_URL`.

### Pitfall 13: tenant data in a non-empty project
**What goes wrong:** plain `create table` collides; or worse, two production tenants share a project and the isolation story is silently gone.
**How to avoid:** step 1 refuses non-empty projects; the production panel refuses a project bound to another tenant (D-540).

### Pitfall 14: Management API rate limit during fan-out and health
**What goes wrong:** 120/min per endpoint per project/org; allow-list reconcile + health + bootstrap can burst.
**How to avoid:** one client-side limiter (≤ 100/min), exponential backoff on 429 using `X-RateLimit-Reset`, health every 5 min with `timeout_ms` bounded.

### Pitfall 15: central outage takes every tenant down
**How to avoid:** stale-while-error 10 min on binding and host caches; `by-host` stale fallback in the web (already fail-open to generic for 10 s — make sure a known tenant does not degrade to the generic shell on a transient error: keep the last good value).

### Pitfall 16: the fake provider reaching production
**How to avoid:** `assertProductionEnv` refusal and a unit test.

```ts
export async function applyDirectory(sql: Sql, files: MigrationFile[], ledger: 'supabase' | 'central') {
  const [{ u }] = await sql`select current_user as u`;
  if (u !== 'postgres') throw new MigrationError('wrong_role');
  await sql`select pg_advisory_lock(hashtext('rede.migrate'))`;
  try {
    await sql`set lock_timeout = '15s'`;
    const done = new Set((await sql`select version from supabase_migrations.schema_migrations`).map((r) => r.version));
    for (const f of files) {                       // sorted by 14-digit version
      if (done.has(f.version)) continue;
      await sql.begin(async (tx) => {              // one transaction per file, like the CLI
        await tx.unsafe(f.text);                   // simple protocol: multi-statement OK
        await tx`insert into supabase_migrations.schema_migrations (version, name) values (${f.version}, ${f.name})`;
      });
    }
  } finally {
    await sql`select pg_advisory_unlock(hashtext('rede.migrate'))`;
  }
}
```

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Token of tenant A accepted on tenant B (confused project) | Spoofing / EoP | project chosen from the host before parsing; never from token `iss`; negative test DBT-10 |
| Wrong pool for a tenant (routing bug) | Information disclosure | explicit `tenantId` → registry; `tenant_id` + RLS on every table remain; two-database tests; production refuses a project bound to two tenants |
| Credential disclosure via panel, logs, errors, cookies, `sessionStorage` | Information disclosure | allow-list DTOs, redaction, wizard keeps manual secrets in memory only (UI-D-534), response-scan test |
| Master key loss or leak | Denial / Disclosure | keyring rotation procedure; credentials are re-derivable through the PAT (keys re-read, passwords reset) — a documented break-glass `platform:reissue-credentials` command |
| DDL credential blast radius (`postgres` of every project) | EoP | optional two key classes; Job/worker only; audit rows |
| SSRF through a user-supplied ref | Tampering | fixed base URL `https://api.supabase.com`, ref regex, `redirect: 'error'` (as in `auth-allow-list.ts`) |
| Management API PAT abuse | EoP | scoped PAT, organisation-pinned `SUPABASE_ORG_SLUG` check on `GET /v1/projects/{ref}`, secret in Secret Manager |
| Webhook forgery / replay on the new indexes | Spoofing | tenant resolved from an index but authenticity still by the tenant's own token / Mux HMAC / hook timestamp; dedupe stays in the tenant DB |
| Poisoned storage URL after the move | Tampering | origin allow-list rule (`isAllowedIconUrl`), post-copy scan |
| Pool exhaustion / unreachable project DoS | Denial | bounded LRU, circuit breaker, per-project budget |
| Fake provider or fake keys in production | Spoofing | `assertProductionEnv` refusal, unit test |
