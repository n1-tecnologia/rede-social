# Phase 09.2 Plan 07: Central/tenant ownership, the push and reconcile functions, and the S-class sites Summary

**The split of the tenants and tenant_modules rows between the control plane and a tenant's own project is now an explicit table with a guard, copied after commit by push helpers that never fail a request and healed by a reconcile function that cannot cross an ownership line; suspending a tenant in database B is decided centrally and shown by the shell with B closed, a tenant is created as a compensated two-step saga, and the brand, its files, the public tenant and the mail facts follow their owner**

## Performance

- **Duration:** about 30 min (approximate; start not recorded)
- **Completed:** 2026-10-23T00:53Z
- **Tasks:** 3 (1 tracer, 2 auto)
- **Files:** 14 in the task commits (6 created, 8 modified), excluding this plan's metadata

## Accomplishments

- Tracer: a tenant on `rede_tenant_b` suspended through `POST /v1/platform/tenants/{id}/status` flips `tenants.status` in the central project, the push copies it to B, and with B's sealed connection string re-pointed at a closed port `GET /v1/public/tenants/by-host` still answers `suspended` and a member's bootstrap answers 403 `TENANT_SUSPENDED`. Reactivation restores both databases. With B unreachable at push time the request still answers 200, the central status changed, `platform.mirror.push_failed` is logged with the tenant id, the field names and the code `project_unavailable` (no URL, no value), and `reconcileTenantMirror` later writes `tenants.status` into B.
- `mirror.ts`: `CENTRAL_OWNED` (slug, status, display_name, timezone, plan of `tenants`; `enabled` of `tenant_modules`), `TENANT_OWNED` (branding, rules_text, rules_version, settings) and `LOCAL_COLUMNS` are data; `mirror-fields.test.ts` asserts every column of both Drizzle tables is in exactly one list. `pushToTenant` upserts the requested columns (a missing row is created from the central values), `pushToCentral` copies the brand back and drops the host cache, both return `{ pushed: false, reason }` instead of throwing and skip a tenant on the central project (`central_project`, one row serves both roles).
- `createTenant` is a saga: step 1 in one platform transaction (the platform-account refusal, tenant row with derived brand, one module row per toggleable key, the explicit binding to the `is_default` project, `ProjectUnboundError` when no default exists), step 2 in `withAdminTx({ tenantId })` (`createPendingInvite`); a failing step 2 deletes the binding, modules and tenant row (compensation logged, never thrown), forgets the cached binding, and the same slug succeeds on retry. Proved with a real trigger that raises for one invite address.
- `getTenantDetail` reads tenant, modules and domains in a platform transaction and invites and admins in a tenant transaction afterwards; an unknown id is `null` (404) before any tenant lane. `setModuleEnabled` writes `enabled` centrally and pushes it; `readModuleSettings` / `patchModuleSettings` run in the tenant's project after a central existence check.
- Branding: `brandingBucketFor(tenantId)` replaces the module-level bucket, the nine sites run in the tenant's project, every committed write to `tenants.branding` is followed by `pushToCentral(['branding'])` and the host-cache drop, and the public URLs and the origin used to recognise a tenant's own objects come from the tenant's project. `getPublicTenant` reads the identity centrally and the rules text and checkout link from the tenant project; `mail-tenant.ts` resolves the verified host and the brand centrally and the open-invite facts in the tenant project.
- `reconcileTenantMirror` / `reconcileAllMirrors({ concurrency, tenantIds })`: drift healed in each direction writing only what differs (witnessed by `updated_at` on a second run), a missing tenant row seeded from the central values, an unreachable project counted as `failed` without aborting the loop, zero tenants returning zeros.
