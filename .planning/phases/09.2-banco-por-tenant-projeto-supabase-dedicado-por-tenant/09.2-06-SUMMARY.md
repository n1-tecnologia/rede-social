# Phase 09.2 Plan 06: Platform-lane domains, the lane-split invite flow and the lane-aware seed Summary

**Domains, platform admins and the allow-list lock now run only in the central project, a tenant in database B gets its host, verification and primary flag from the central rows alone (by-host answers it with B's pool closed), the invite flow reads invites from the tenant's database, the host from the central domains and mails through the tenant project's own Auth, and the seed writes each datum through the lane that owns it**

- **Completed:** 2026-10-23T00:13Z

## Accomplishments

- Tracer: for a tenant that lives only in `rede_tenant_b`, `POST …/domains` registers a pending non-primary host, "Verificar agora" verifies it with the fake provider and `…/primary` promotes it. `tenant_domains` holds 2 rows for the tenant centrally and 0 in B. With B's sealed connection string re-pointed at a closed port and every pool dropped, `GET /v1/me/bootstrap` answers 503 `TENANT_UNAVAILABLE` while `GET /v1/public/tenants/by-host` answers 200 for the new host (primary) and for the old one (alias naming the new primary), and the platform list of domains still answers. The flow for a project-0 tenant (`rede-lab`) is the same and removes its throwaway host.
- `domains.ts` (23 sites, `recordInviteSendOutcome` included), `platform-admins.ts`, `allow-list-lock.ts` and `reconcile-allow-list.ts` call `withPlatformTx`; no non-comment line of those files names the tenant-data lane.
- `invites.ts` (14 sites) and `invite-send.ts` (2): invite rows, memberships, member profiles and users go through `withAdminTx({ tenantId })`. `centralInviteFacts` (a platform-lane transaction: does the tenant exist in the control plane, and its verified primary host) is read first, before the tenant transaction and before any Auth call, so the link host is known before GoTrue is touched. `authAdminOf(tenantId)` hands out `supabaseAdminFor(await resolveProject(tenantId)).auth.admin` for `inviteUserByEmail` and both `generateLink` calls; the old module-level `supabaseAdmin` import is gone.
- An unknown tenant is a 404 from the control plane (`listTenantInvites`, `resendInvite`) before any tenant database is chosen, instead of surfacing as an unbound-project error; a `kernel.invite-send` job whose tenant lost its binding returns `gone` instead of retrying five times.
- `scripts/seed.ts`: 5 central writes (tenant upsert, icon patch, `tenant_modules`, `tenant_domains`, `platform_admins`) use `withPlatformTx`; 31 tenant sites use `withAdminTx({ tenantId })` with the id of the tenant just created; `grantSeedAccess` looks the tenant up centrally then writes its own rows; `analyze` runs once per seeded tenant. `ensureProjectZero()` is unchanged.
- Inventory: the invite and seed rows are `migrated`; the P rows left the list; `platform/tenants.ts`, `modules.ts` and `branding.ts` stay `pending` (plan 07) and so does `scripts/arm-event-reminders.ts` (class L, plan 9).

**4. [Rule 1 - Bug] An unknown tenant would have stopped answering 404**
- **Found during:** Task 2

- **Fix:** both functions check the tenant in the control plane first (`centralInviteFacts`), then open the tenant lane. `runScheduledInviteSend` maps `ProjectUnboundError` to `gone`.
- **Files modified:** packages/core/server/platform/invites.ts, invite-send.ts (covered by `invites-lanes.test.ts`)
- **Verification:** invites.test.ts (404 cases) green; unit case "a tenant the control plane does not know is a 404 before any tenant lane or Auth call".
