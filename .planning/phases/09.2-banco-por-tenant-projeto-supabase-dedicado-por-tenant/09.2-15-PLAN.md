<objective>
Make 'a migration reaches every tenant database' one command, make the answer to 'where does each tenant stand' a stored fact, and make a tenant that is behind wait politely instead of breaking.

`migrateAll` applies the central set to the control plane, then the tenant set to every ready project (including project 0) with failure isolation, a dry run and a per-tenant selector; it records each project's applied-versus-required state in the registry. The image carries both sets and a deterministic manifest, so the running API knows what schema it needs without asking a database; the host answer compares that with the stored state and holds a lagging tenant out with `updating` while every other tenant keeps running, and a self-re-arming job retries what failed.

Tracer: a database one migration behind is brought current by the fan-out and its state flips to `current`; a second run changes nothing.

Heavy plan, justified: manifest, fan-out, state, gate completion, retry job and the image change are one chain; each of the three tasks verifies its own link.

<planning_decisions>
1. **Include project 0.** It is a tenant project too; when the CLI already applied its set the runner finds the ledger complete and only records the state. A failing project 0 holds its own tenants out like any other project (D-545).
2. **Required schema from files in development.** Outside production, with no `MIGRATIONS_DIR`, `getRequiredTenantSchema()` derives `{ count, head }` from `supabase/migrations/*.sql` of the repository so a developer's stack behaves like the image; in production only the manifest counts.
3. **Retry job vs deploy Job.** The deploy runs the fan-out once; `platform.migration-retry` is the self-heal for transient failures between deploys. Both call the same `migrateAll` (single project via the `projectIds` option) and both are serialised per project by the runner's advisory lock.
4. **Exit codes.** 0 ok, 1 central failure or strict tenant failure, 2 usage; a tenant failure is a warning by default because D-545 says one failing project never blocks the release of the others.
5. **No log carries a URL.** Summary lines hold `ref`, counts, versions and error codes.
6. **No schema change.** The tables exist since plan 02; this plan writes rows only, so there is no schema gate task.
</planning_decisions>
