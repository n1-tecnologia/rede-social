# Phase 09.2 Plan 12: Management API client behind a provider seam Summary

**The platform can read and configure a tenant's Supabase project through one limiter-backed, organisation-pinned adapter that reaches exactly the 20 INTEGRATE operations of COVERAGE.md, or through a network-free fake that cannot be selected in production, and the operator has a read-only probe that prints only shapes**

## Accomplishments

- Tracer: a loopback `node:http` stub implements the read endpoints; `createSupabaseProjectProvider` returns status, health, revealed keys, the PRIMARY pooler entry (host read, never built from the region), migrations and buckets as typed DTOs, with `Authorization: Bearer` and no other credential header. Seven malformed refs produce zero requests; a 3xx is an error and its Location is never requested; every failure message is `<kind> <status>`.
- The limiter holds the process to 100 requests per rolling minute with FIFO admission and a shared 429 pause. `X-RateLimit-Reset` is rounded up to whole seconds, jitter is added after the rounding, a retry is never early, and 5 attempts end in `rate_limited 429`. 250 concurrent calls from two bootstraps never exceed 100 in any minute.
- `waitUntilHealthy` implements the P39 status matrix and the 10 minute budget with the boundary at 599,999 / 600,000 ms; a project whose `db` is healthy while `auth` is `COMING_UP` is not healthy.
- The write surface (database password, Auth, PostgREST, Storage and Realtime configuration, signing keys, key creation) is proven verbatim against the stub, and a test reads the INTEGRATE rows of COVERAGE.md and compares them with the adapter's literals in both directions.
- The fake provider needs no network, answers `COMING_UP` for K polls, records PATCH bodies, supports `failAt` once or always plus `failpoint()` for the steps that are not provider calls, and keeps all state per instance. `readOnlyQuery` against the local database returned rows for a `select` and null for a `create table` (checked by hand).
- `PROJECT_PROVIDER`, `SUPABASE_ORG_SLUG`, `PROJECT_AUTH_SMTP_PASS` are in the kernel env; `assertProductionEnv` refuses an explicit fake in production and demands PAT, organisation slug and master keys for `supabase`.
- `pnpm platform:probe --ref <ref> [--exercise-keys]` / `--fake` prints one JSON object of statuses, key kinds, counts, the pooler host shape and a `recommendation` (`automatic` or `manualAccess`), never a key, password, PAT or connection string.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `PROJECT_PROVIDER` cannot carry a zod default if the production guard is to keep the expand release bootable**
- **Found during:** Task 1 (adding the env variable), Task 3 (the guard)
- **Issue:** the plan asks for `.default('fake')` and for `assertProductionEnv` to refuse `fake` when `NODE_ENV=production`. With a default, every production boot that names no `PROJECT_PROVIDER` (the currently deployed API and worker, and the expand release that plan 03 decision 6 says must boot with no new secret) would resolve to `fake` and fail at import of `env.ts`, before the human gate G2 exists.
- **Fix:** the schema is `z.enum(['fake','supabase']).optional()`. `assertProductionEnv` refuses only an explicit `fake` in production; `projects/index.ts` resolves unset to `fake` and throws a named error in production, so the fake can never be what runs there (T-09.2-59 holds) and nothing breaks until a module actually imports the provider. A test pins both halves.
- **Files modified:** packages/core/server/env.ts, packages/core/server/projects/index.ts
- **Verification:** `project-provider-env.test.ts` (9 cases)
- **Committed in:** 784aa0ce, 5041f588

**2. [Rule 2 - Missing critical functionality] The organisation pin covers every method, not only `describe`**
- **Found during:** Task 1 (threat T-09.2-56)
- **Issue:** the plan pins the organisation in `describe`. A classic PAT reaches projects of other organisations, so revealing the keys or writing Auth config on a foreign ref would succeed through the other methods.
- **Fix:** every method except `describe` and `health` first confirms the ref belongs to the pinned organisation (one `describe` per ref per instance, cached, bounded at 256).
- **Files modified:** packages/core/server/projects/management-api.ts
- **Verification:** the foreign-organisation test asserts no `api-keys` request is made.
- **Committed in:** 784aa0ce

**3. [Rule 2 - Missing critical functionality] `getPostgrestConfig` drops `jwt_secret`**
- **Found during:** Task 2 (reading the OpenAPI schema `PostgrestConfigWithJWTSecretResponse_Output`)
- **Issue:** the PostgREST read returns the project's JWT secret, which nothing in the platform needs.
- **Fix:** the adapter removes it before returning; a test proves it.
- **Committed in:** 784aa0ce (code), efaad6cf (test)

**4. [Rule 3 - Blocking] A shared `wait.ts` was needed**
- **Issue:** both providers need the same wait loop; putting it in either would make one import the other.
- **Fix:** new `packages/core/server/projects/wait.ts` (not in the plan's file list).
- **Committed in:** 784aa0ce

**5. [Plan wording] P42 has two readings**
- The truth says a fractional header falls back to a one-second minimum, the task says `1.2` gives 2000 ms. Both hold: seconds are rounded up first (`1.2` becomes 2 s), then floored at one second (`0.2`, `0`, `-3`, missing and junk give 1000 ms).

**6. [Plan wording] The tracer commit already contains the writers and the wait**
- The adapter is one file, so the Task 1 commit holds all of `management-api.ts`; the Task 2 commit adds `reasons.ts` and the tests that prove the write surface, limiter, polling and picking.
