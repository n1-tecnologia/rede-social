# Phase 09.2 Plan 09: Per-project job queues, platform queue schema and the worker supervisor Summary

**A job now lands in the pg-boss schema of the database that owns the transaction that enqueued it (platform jobs in a new central `pgboss_platform` schema), and the worker keeps one queue consumer per ready project plus one for the platform alive through a supervisor with per-project backoff, a connection cap and a 60 s registry reconcile; the daily dispatcher, the orphan sweeper and the event-reminder backfill run once per project, and project 0 never dispatches a tenant that lives elsewhere**

## Performance

- **Duration:** about 30 min
- **Tasks:** 3 (1 tracer, 1 auto, 1 blocking-schema auto)
- **Files modified:** 20 modified, 11 created (plus the central migration snapshot)

## Accomplishments

- Tracer: `enqueueInTx` reads `{ handle, lane }` from `projectOfTx`, picks the sender of that project and scope, and refuses a wrong-scope enqueue before any insert. Proved against real databases: B's job in B, a project-0 job centrally, a platform job in `pgboss_platform`, three refusals leaving no row.
- `pgboss_platform` generated with the pg-boss CLI like the tenant schema, in the central set, `api_user` only; pgTAP 213 pins it to the shape of `pgboss` so one cannot be upgraded without the other.
- `createSupervisor` with everything environmental injected, 22 unit cases and a real six-case run over project 0, the local second database and a dead project.
- Per-project cadences: `runDailyTenantDispatch(projectId)`, `armDailyTenantDispatch({ projectId })`, `armSweeper({ projectId })`, the sweeper's three sites, and `scripts/arm-event-reminders.ts` (handoff) all open `{ projectId }` lanes; the inventory's L rows are migrated and only the N class stays pending.
- `platform.mirror-reconcile` and the worker-boot calls (`ensureProjectZero`, `armMirrorReconcile`, `reconcileAuthAllowList`) after the platform instance is up; the probe still binds after `supervisor.start()`.

## Next Phase Readiness (and consequences for plan 24, DEPLOY.md)

- **Deploy order is now binding:** the central set (`pgboss_platform_schema`) must be applied to the production central project BEFORE the new API or worker revision runs. A worker whose platform instance cannot start fails its boot; an API whose first domain or invite enqueue meets a missing `pgboss_platform` fails that request. Plan 15's migrate command or `pnpm db:central` applies it.
- **Worker boot now reads the registry:** `listReadyProjects` and `centralProjectId` go through the platform lane, so the worker needs the central set (registry) present. It does NOT import `packages/core/server/projects/index`, so the `PROJECT_PROVIDER` requirement of plan 12 is not triggered by this plan.
- **Connection arithmetic for DEPLOY.md:** per tenant project about 2 session sockets (pg-boss, `max: 2`) + 1 sender (`max: 1`) + up to `PROJECT_POOL_MAX` (4) pooled; project 0 has two pg-boss instances (platform and tenant, 4 sockets) plus the app pool of 10. `SUPERVISOR_MAX_PROJECTS` (default 40, env var) bounds one worker instance; the worker header comment carries the same numbers. Handler concurrency multiplies by project count: re-check the worker's `DATABASE_POOL_MAX` budget.
- **Non-central projects need `database_url_session_sealed`** for the supervisor to poll them; a project without one backs off and logs `worker.supervisor.backoff` (plan 14's bootstrap must seal it).
- **arm-event-reminders output changed** to `{ projects, events, armed, skipped, failedProjects }`; docs/DEPLOY.md line ~932 still shows the old shape (plan 24).
