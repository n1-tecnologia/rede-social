# Phase 09.2: Banco por Tenant - Context

**Gathered:** 2026-10-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Each tenant runs on its own Supabase project (its own Postgres, Auth, Storage and Realtime) instead of the one shared project. Physical isolation is the goal: data, accounts, files and quotas of one tenant can never touch another's.

The operator flow this phase delivers:

1. **Create.** In the platform panel the `super_admin` creates a tenant and informs the Supabase project of that tenant. The system bootstraps the project: schema, roles, Auth configuration, buckets, Realtime policies, the tenant row, the modules and the pending first-admin invite.
2. **Route.** Every request, webhook and job reaches the right project: the API and the worker pick the database of the tenant, the web app talks to the tenant's own Auth and Realtime.
3. **Migrate.** One command rolls a migration out to every tenant project, with a version per tenant, failure isolation and a dry run.
4. **Move.** The tenants that exist today in the shared project are moved to projects of their own by a reusable command-line tool, with a cutover and a rollback.

In scope: the registry of projects and the central mirror of each tenant, the routing seam in the kernel, credential custody, the bootstrap steps and their status, the migration fan-out and the per-tenant schema version, the health check, the per-tenant pg-boss queue, the "move tenant" tool, the removal of the multi-tenant identity flows of Phase 08.1, and the panel and shell screens these need.

Out of scope (see Deferred): creating the Supabase project from the panel, customer-owned Supabase accounts, tenants on the Free plan, a central queue for many tenants, live (zero-downtime) copy, cross-tenant statistics in the panel.

</domain>

<decisions>
## Implementation Decisions

### Identity and the tenants that exist today
- **D-533: One account per tenant.** Each tenant's Auth (the Auth of its own project) holds its own accounts. The same e-mail in two tenants is two independent accounts, each with its own password and session. The Phase 08.1 flows that exist only because one identity spans tenants no longer apply: "Participar de [B]" on sign-up and login (D-301, D-305, D-306), the existing-identity invite (D-314), the shared-password notice (D-312) and the generic-host community picker (D-308). The sign-up of an e-mail that already has an account in the same project keeps the Phase 1 answer (D-04). — **Reversibility:** one-way — after the move each project's `auth.users` is independent, and merging identities again would be a new data migration plus a new identity model.
- **D-534: Every existing tenant is moved.** The production tenants, `rede-demo` and `rede-lab` all leave the shared project through one reusable tool. It copies the tenant's rows (by `tenant_id`), its Auth accounts (same user ids, password hashes preserved) and its Storage objects into a project that was bootstrapped exactly like a new tenant's. A person who held memberships in two tenants ends up with an account in each, with the password they had. After the last move the central project holds platform data only. — **Reversibility:** costly — the move rewrites where production data lives, and it can only be undone while the old rows are kept.
- **D-535: Cutover by suspension.** While a tenant is copied it is suspended (D-32), and members see the branded "temporariamente indisponível" screen. When the copy is verified the registry points at the new project and the tenant is reactivated. Sessions do not migrate (each project signs with its own keys), so members sign in again. The old rows are kept until the super_admin confirms, which is the rollback window.
- **D-536: The move is a command, not a screen.** A pnpm script that Igor runs once per tenant. It reuses the creation bootstrap, offers `--dry-run`, writes an audit row to the registry and can roll back by pointing the registry at the old project again. No new panel screen, so no design gate for it. A panel button can wrap the same code later.

### Central project, mirror and routing
- **D-537: The central project mirrors each tenant.** The current project becomes the control plane. For every tenant it keeps a mirror (name, brand, status, enabled modules, primary host, project coordinates), so the panel list, `GET /v1/public/tenants/by-host` and the branded "indisponível" screen work while a tenant's project is down or paused. Ownership is split by who edits: the tenant's project owns the brand and the rules text (the `admin_tenant` edits them), and the central project owns status, modules, domains and the project registry (the `super_admin` edits them) and pushes a copy to the tenant's project. A reconcile job heals drift. — **Reversibility:** costly — the by-host answer, the panel list and the flag lookups all read the mirror.
- **D-538: Routing is explicit in the signature.** `withTenantTx` resolves the tenant's project from `ctx.tenantId`. `withAdminTx` now requires the tenant, and a separate platform-lane function opens the central project. There is no ambient per-request context (no AsyncLocalStorage). The Biome restriction that confines the admin lane to the kernel stays. Each of the 119 `withAdminTx` call sites is classified as tenant-scoped or platform. — **Reversibility:** costly — 197 `withTenantTx` and 119 `withAdminTx` call sites sit behind these signatures.
- **D-539: Credentials are sealed in the registry.** The database URL, service key, publishable key and project ref of each project are stored in the registry table, sealed with a platform master key held in Secret Manager. In the panel they are write-only: never returned by the API, never logged. The API opens them in memory when a pool is created. It follows the scheme already built for the gateway secret (`packages/core/server/payments/secret.ts`: AES-256-GCM, a key id for rotation, the row id as authenticated data), extracted into a kernel helper. — **Reversibility:** costly — every stored credential is sealed under the scheme.
- **D-540: A project may serve several tenants outside production.** The registry accepts several tenants pointing at one project, so local development, CI and homologation keep one stack with `rede-demo` and `rede-lab` together. Only the production panel refuses a project already used by another tenant. The schema is identical in every project, with `tenant_id` and RLS on every table: the single-tenant schema was rejected because it would rewrite 147 migrations and break the shared non-production model. The existing two-tenant isolation suite stays as the second layer, and a small set of tests over two databases proves the routing.

### Creating a tenant and the bootstrap
- **D-541: The panel asks for the project ref.** The projects live in Igor's Supabase organization. He creates an empty project and pastes only its project ref in the "Novo tenant" form. The system obtains the keys, the pooler address and the Auth configuration with the platform token, and generates the password of the `api_user` role itself. Research must confirm what the Management API delivers (keys, running SQL, database password). Where it falls short, the form also asks for the `postgres` password and the keys, and the Auth configuration still goes through the token.
- **D-542: The bootstrap is a list of idempotent steps.** Each step can run again without damaging what is done, and the panel shows the status of every step (running, done, failed with the reason). The tenant stays "em preparação", accepts no login, until every step passes, and "Tentar de novo" resumes at the step that failed. The steps are at least: verify the project, create the roles (`api_user` without `BYPASSRLS`, `supabase/roles.sql`), apply the tenant migration set, configure Auth (the two access hooks, the Send Email Hook, SMTP, redirect allow-list, signing keys), create the buckets, create the Realtime policies, insert the tenant row and its modules, and schedule the first-admin invite (D-30: it is sent when the primary domain is verified).
- **D-543: Every production project is on Pro.** The registry keeps the plan as information only. A health job checks each project (reachable, paused, behind on migrations) and the panel shows a badge. The connection budget stops being one global ceiling and is computed per project (every project has its own pooler), which `docs/DEPLOY.md` "Connection budget (Pro)" must restate. Phase 01's keep-alive stays for the central project.

### Migrations and the worker
- **D-544: The fan-out runs at deploy, on the new revision.** In the production deploy the CI brings up the new API revision without traffic and triggers "migrar todos" inside it, so the sealed credentials never leave GCP. Traffic moves only after it passes. The same command runs by hand with `--dry-run` and `--tenant <slug>`, and the panel shows each tenant's schema version. It replaces the single `supabase db push` for tenant projects and keeps the D-12 order (migrations, API, worker). — **Reversibility:** costly — both deploy workflows and `docs/DEPLOY.md` are rewritten around it.
- **D-545: A tenant that is behind is held out.** The API compares each tenant's schema version with the version it requires. For a tenant that is behind, it answers with a branded "em atualização" screen (the same mechanism as the suspended tenant, D-32) until the migration passes, while the other tenants keep running. The job retries by itself and the panel shows "atrasado". There is no N-1 compatibility requirement on releases, and one failing project never blocks the release of the others. — **Reversibility:** costly — the per-request version check becomes part of every release.
- **D-546: Every tenant database has its own pg-boss queue.** The `pgboss` schema ships with the tenant migration set and the enqueue stays transactional inside the tenant's own transaction (`enqueueInTx`). The worker keeps one pg-boss instance per tenant plus one central instance for the jobs that are about the platform (domain verification, invite sending and the like). The polling and session-connection cost grows with the number of tenants, which is acceptable for dozens of tenants and is revisited past that. — **Reversibility:** costly — queue names, the worker boot and the connection budget are all built per database.
- **D-547: Two migration sets.** The 147 existing files become the tenant set, which "migrar todos" applies to every tenant project. The tables that must exist only in the central project (registry, sealed credentials, mirror, migration ledger) live in a new central set applied only to the central project, so they never exist in a tenant's project. Local, CI and homologation apply both sets to their one stack. — **Reversibility:** costly — the directory layout, the CI steps and the drizzle-kit `out` path change.

### Carried forward from earlier phases
- **D-20 [informational] (Phase 1):** every tenant has its own custom domain, resolved host to tenant through `tenant_domains`; D-537 mirrors what the host answer needs into the central project.
- **D-23 [informational] (Phase 1):** the membership is the authority and the host can only deny; with one tenant per project the check is also enforced by the project itself.
- **D-36 [informational] (Phase 2):** only verified hosts resolve.
- **D-12 [informational] (Phase 1):** production deploy order is migrations, API, worker, behind one manual approval; D-544 keeps it.
- **D-18 [informational] (Phase 1):** the worker is the same image as the API with `ROLE=worker`.
- **D-30 [informational] (Phase 2):** the first-admin invite is sent when the primary domain becomes verified; D-542 only schedules it.
- **D-32 [informational] (Phase 2):** a suspended tenant keeps a branded "indisponível" screen; D-535 and D-545 reuse the mechanism.
- **D-33 [informational] (Phase 2):** prototype-less screens need a UI-SPEC and an approved mockup before they are coded.
- **D-37 [informational] (Phase 2):** auth e-mails go through the Send Email Hook to the API, then Resend; D-542 configures the hook in every project.
- **D-488 [informational] (09.1):** a gateway product id maps globally to one tenant; the webhook route needs that index in the central project before any tenant database is known.
- **D-495 [informational] (09.1):** the two access hooks stay coarse; they run in every project, and in a production project the single tenant makes the answer exact.
- **D-499 [informational] (09.1):** a payment cut does not revoke the session because the identity was shared; D-533 removes that reason, and the behaviour stays as it is until someone decides otherwise (see Deferred).

### Claude's Discretion
- The shape of the registry and mirror tables, the sealing helper's name and key variable, the master-key rotation procedure, and the encoding of the schema version (a ledger row per applied file versus a single counter), as long as D-537, D-539 and D-545 hold.
- How the connection pools are held: one pool per tenant project with a bounded, least-recently-used cache and a small `max` per pool, sized against the per-project pooler limits and the Cloud Run instance count.
- How the API picks the project to verify a token against: the host (or the platform host) selects the project first and the token must verify against that project's keys and issuer, never the project named by the token's own `iss`. This was not discussed with the user and has to be confirmed in research, because it is also what keeps a token of tenant A from ever verifying on tenant B.
- Routes with no tenant host (the gateway webhook, the Mux webhook, the Send Email Hook of each project, sign-up by slug on generic hosts): the opaque per-tenant reference they carry, and the central index each one resolves through. Mux assets and gateway products need the tenant recorded at creation time.
- The web side: how `proxy.ts` and `@supabase/ssr` receive the tenant project's public URL and publishable key (from the by-host answer), and the same for the Realtime client and its token source.
- What the Management API can and cannot do for the Auth configuration step (including that `supabase config push` is a per-project CLI run today, and the runtime allow-list adapter and its reconcile job in `packages/core/server/platform/reconcile-allow-list.ts`).
- Rewriting of absolute Storage URLs inside copied rows (`tenants.branding` and any other jsonb that stores a bucket URL) during the move.
- The fake project provider for local runs, in the shape of `VideoProvider` and the domain provider, so no local or CI run touches a real Supabase project.
- Which of the 17 jobs are platform jobs (central queue) and which are tenant jobs, and how the per-tenant daily dispatcher (`kernel.daily-tenant-dispatch`) loops projects.
- All pt-BR copy not quoted here, including the "em atualização" and "em preparação" screens, and the visual design of the panel changes.

## Existing Code Insights

### Reusable Assets
- `withTenantTx(ctx, fn)`: already receives `tenantId`, so it is the natural place to resolve the tenant's pool. `withAdminTx(fn)` is the one that has to learn about the tenant.
- `createBoundedTtlCache` (`@rede-social/contracts`), used by `tenant-host.ts`: the shape for the pool cache and the credential cache.
- `packages/core/server/payments/secret.ts`: AES-256-GCM sealing with a key id and the row id as authenticated data, ready to generalize for D-539.
- The domain provider and the `AUTH_ALLOW_LIST` adapter (`local` / `supabase`) plus `reconcile-allow-list.ts`: the pattern, and part of the code, for the Auth configuration step of the bootstrap, with a `fake` implementation for local runs.
- The suspended-tenant branded screen (D-32) and its by-host `status`: the mechanism for "em atualização" and "em preparação".
- `kernel.domain-verify`: the self re-arming job pattern for the health job and for the migration retry.
- `createQueues` is idempotent, and `createBoss` is the one constructor: the base for one pg-boss instance per tenant database.
- `scripts/seed.ts`, `supabase/tests/000-helpers.sql` and the two-tenant isolation suite: kept as the second layer of isolation under D-540.

### Established Patterns
- Hand-written SQL goes in `--custom` migrations applied by the Supabase CLI; drizzle-kit only generates. D-547 splits where those files live.
- Every table keeps `tenant_id` and RLS, and every policy gets a cross-tenant negative test.
- Tables no tenant lane may read have RLS enabled with zero policies.
- Hosted Auth configuration is applied by `supabase config push` per project, and the runtime redirect allow-list is written through the Management API and reconciled at worker boot, because a config push wipes the runtime entries.
- Production is live: migrations run before the new API, and breaking changes are split expand then contract across deploys.

### Integration Points
- The 119 `withAdminTx` call sites (`server/platform` 9 files, `server/tenancy` 8, `server/payments` 8, `server/media` 6) and the 197 `withTenantTx` call sites.
- `listPlatformTenants`, `createTenant`, `getTenantDetail`, `updateTenant`, `setTenantStatus` read and write `tenants`, `tenant_modules` and `tenant_domains` together; they move to the mirror and the registry.
- `resolveTenantHost` reads `tenant_domains` and `tenants` in one admin transaction; it moves to the central mirror.
- `deploy-api.yml` runs `supabase db push --include-roles` and `supabase config push` against one project ref.
- The worker's job list and its pool-fit comment (17 queues against `DATABASE_POOL_MAX`).
- The web app reads one `NEXT_PUBLIC_SUPABASE_URL` and one publishable key for `@supabase/ssr` and for Realtime.

<specifics>
## Specific Ideas

- Igor's words: each tenant gets its own Supabase project "assim vou conseguir isolar tudo"; at tenant creation he fills in the project access and "o sistema faz todo o dump lá nesse novo lugar"; and "sempre que eu precisar rodar uma migration precisarei atualizar os bancos de todos os tenant", so the roll-out must need no per-project manual work. Here "dump" means the bootstrap of a new project (schema and configuration) and, for the tenants that already exist, the data copy of D-534.
- The migrate-all command needs `--dry-run` and `--tenant <slug>`, and the panel needs a schema-version column and an "atrasado" badge, so that one command is also the easy way to see where every tenant stands.
- Frontend work exists (the "Novo tenant" form gains the project ref, a per-step bootstrap status, the health badge and the schema version, plus the branded "em atualização" and "em preparação" screens), so `/gsd-ui-phase 09.2` runs before planning.
- The first plan should check what the Management API delivers (D-541), because the whole "paste only the ref" flow depends on it.

</specifics>

<deferred>
## Deferred Ideas

- Creating the Supabase project itself from the panel through the Management API (the operator would pick only a name and a region). Today the project is created by hand and only its ref is pasted.
- Projects in the customer's own Supabase account. The platform token would not reach them, so the Auth configuration would become a manual checklist.
- Tenants on the Free plan with a daily keep-alive per project.
- A central pg-boss queue with a per-tenant outbox, for the day the number of tenants makes one polling instance per database too costly.
- Live copy with logical replication, for a move with almost no unavailability.
- A "Mover para projeto próprio" button in the panel that wraps the D-536 tool.
- Cross-tenant statistics in the panel (member counts, activity): the list shows only what the mirror holds.
- Revoking a member's session on a payment cut or a block, now that Auth is per tenant (the reason in 09.1 D-499 ended, the behaviour was left as it is).
- A central login with a cross-tenant identity link, discussed and rejected in favor of D-533.

</deferred>
