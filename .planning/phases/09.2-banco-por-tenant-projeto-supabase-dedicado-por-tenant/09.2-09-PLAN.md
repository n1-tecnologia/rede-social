<objective>
Give every tenant database its own job queue, and the control plane its own, without changing what a job does.

Today one pg-boss instance polls one database and the API-side sender is a process singleton; pg-boss reads a queue's definition from the SENDER's own database before inserting through the caller's transaction, so a single sender is only correct while there is a single database. This plan makes the sender follow the transaction's project, splits queues by scope (platform jobs in a `pgboss_platform` schema of the central project, tenant jobs in `pgboss` of each project), and replaces the worker's one `boss.start()` with a supervisor that keeps one instance per ready project alive as the registry changes.

Tracer: a tenant job enqueued for a tenant in database B lands in B's `pgboss.job` and nowhere else; a platform job lands in `pgboss_platform.job`; the wrong-scope enqueue refuses. That is the one place a routing mistake would silently put one tenant's payload into another tenant's database.

Heavy plan, justified: sender routing, scope, the schema, the supervisor and the three loop sites (dispatcher, sweeper arm, mirror job) are one mechanism; the migration is the plan's only schema change and is gated in Task 3.

Decisions implemented: D-546 (a queue per tenant database, one central instance for platform jobs, polling cost accepted for dozens of tenants), D-538 (the project travels with the transaction object), D-537 (the reconcile job).

<planning_decisions>
1. **A second schema, not a second database object kind.** `pgboss_platform` lives in the central project beside `pgboss` (which the central project keeps because project 0 is also a tenant database until the last move). The platform migration is generated the same way as the tenant one (pg-boss's own construction SQL for another schema name) and lives in the CENTRAL set, so no tenant project ever has it.
2. **Handlers get a second, optional argument.** `JobDefinition.handler(payload, ctx?: { projectId: string })`; existing handlers ignore it; only the dispatcher and the sweeper need it. `JobDefinition.scope?: 'platform' | 'tenant'` defaults to tenant.
3. **Sender URL.** A tenant sender connects with the project's transaction-pooler URL (`database_url_tx`, project 0: `DATABASE_URL`); the supervisor's polling instances use the SESSION url (`database_url_session`, project 0: `BOSS_DATABASE_URL ?? DATABASE_URL`) because they hold long-lived listeners.
4. **Cap, not a promise.** `SUPERVISOR_MAX_PROJECTS` (default 40) bounds the sockets one worker instance opens (about 2 session sockets plus pooled sockets per project); past it the supervisor logs `worker.supervisor.cap_reached` and skips the rest. Revisit past dozens of tenants (D-546); the budget arithmetic is written into DEPLOY.md by plan 24.
5. **Project 0 has two instances.** The platform instance and the tenant instance both connect to project 0 (different schemas); the budget counts both.
</planning_decisions>
