# Phase 09.2 Plan 08: Host-selected token verification and the five-value host status Summary

**A bearer is now verified only against the key set and issuer of the project the request host selects (chosen before the token is parsed, ES256 only, never from the token's own iss), the by-host answer and `requireAuth` hold out a tenant that is suspended, preparing, unreachable or behind on its schema in a fixed precedence before any key lookup or tenant connection, and a platform session can no longer cross into a tenant lane or back**

## Performance

- **Duration:** about 22 min (approximate; start not recorded)
- **Completed:** 2026-10-23T00:27Z
- **Tasks:** 3 (1 tracer, 2 auto)
- **Files modified:** 16 (task commits, excluding this plan's metadata)

## Accomplishments

- Tracer: two in-process ES256 JWKS servers play two projects; tenant B's registry `api_url` points at the first. B's bearer on B's host answers 200; another project's key, a real GoTrue bearer of project 0, B's bearer on a project-0 host, a token signed by one stand-in claiming the other's issuer, an expired token and a wrong audience are all 401, and a missing bearer is 401 `UNAUTHENTICATED` with zero key fetches.
- `jwksFor`/`issuerFor` memoise a `createRemoteJWKSet` per registry URL in a 64-entry bounded map; nothing in `jwks.ts` reads token content and the only template-literal inputs are the project URL (asserted by a source test, plus the plan's grep which prints 0). `JWKS` and `JWT_ISSUER` remain the project 0 values.
- `requireAuth` order is now: bearer present, resolve host, host status gate, verify against the host's project, then the membership and the rest exactly as before. `requireSuperAdmin` and `requireIdentity` pass the central project explicitly, so a super_admin bearer never reaches a tenant project's keys and a tenant project's bearer is 401 on the platform host.
- `hostStatus` ranks the control-plane facts (`projects.state`, `project_health`, `project_schema_state` against `getRequiredTenantSchema()`); the resolver gathers them in the same platform-lane read as the host and caches the answer 60 s with the host. `status` in the by-host contract grows to five values; the optional `supabaseUrl` and `publishableKey` appear only for a non-central project that has both.
- The three project codes answer 503 without details; `TENANT_PREPARING` and `TENANT_UPDATING` join `ERROR_CODES` with neutral pt-BR messages.
- Concurrency (P22): twenty concurrent first requests fetch the key set once; an unknown `kid` costs at most one refetch inside jose's 30 s cooldown (and an injected-cooldown unit case shows acceptance after it); a JWKS that takes 6 s answers 401 in about 5 s. P37: 50 requests across a `preparing` to `ready` flip see only the gate or a 200; the cached answer is the documented staleness and `invalidateTenantHost` shows the new state to the next request.
