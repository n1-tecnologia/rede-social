<objective>
Build the Management API client behind a provider seam, with a fake that needs no network, so the bootstrap (plan 13), the panel API (plan 14) and the move tool (plan 22) are written against an interface and tested without a Supabase project.

The research found that, with a token that can reveal secrets, the platform can read a project's keys and pooler address, set its database password, and configure Auth, PostgREST, Storage and Realtime by itself; it cannot create buckets or run schema through the API reliably. This plan implements exactly that INTEGRATE surface (and nothing else, enforced by a test against `COVERAGE.md`), the limiter that keeps the process under the platform's request limit, the closed catalog of reason codes that keeps provider text off every screen, and the read-only probe the operator runs against a real empty project to settle the open questions (service-key kind, whether the manual-access form is needed) before the first real bootstrap.

Tracer: the real client reads a project end to end against a local stub of the API: status, health, keys, pooler, migrations, buckets.

Decisions implemented: D-541 (what the Management API delivers and where it falls short), D-540 (a fake implementation for local, CI and test, never in production).

<planning_decisions>
1. **Interface first, two adapters.** `ProjectProvider` is the seam; the bootstrap, health, credentials and move code import only the interface and the `projectProvider` singleton.
2. **No SDK.** A ~200-line typed `fetch` wrapper next to the allow-list adapter; no package is added (RESEARCH: no first-party SDK needed).
3. **Beta endpoints are best effort.** `readOnlyQuery` (Beta, role and transaction semantics undocumented) is used only for the emptiness courtesy of the pre-check and returns `null` on any non-2xx; authority for emptiness is the direct connection check of the bootstrap (`projectIsEmpty`, plan 02).
4. **Refs.** The real adapter accepts only `^[a-z]{20}$` (a Supabase ref); the fake and the registry accept the looser local form `^[a-z][a-z0-9-]{2,39}$`; the HTTP layer validates the stricter form for provider `supabase` (plan 14).
5. **The key kinds.** `listApiKeys` returns every key with a `kind` (`publishable`, `secret`, `legacy_anon`, `legacy_service_role`); which one the registry stores as the service key is decided by the probe on a real project (assumption A-12-1); code that consumes the key treats the kinds uniformly.
6. **Two files that are NOT mine to commit here:** `COVERAGE.md` is written by the planner and committed with the plans.
</planning_decisions>
