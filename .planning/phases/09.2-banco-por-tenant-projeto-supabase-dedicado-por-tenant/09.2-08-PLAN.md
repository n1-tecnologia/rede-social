<objective>
Make the project a request belongs to be decided by the host, once, before anything is trusted, and teach the host answer to say when a tenant must be held out.

Two things become true. (1) A bearer is verified against the keys and issuer of the project the host selects, never the project the token names: that is what stops a token of tenant A from ever verifying on tenant B (the confused-project attack) and it is also what lets a tenant's own Auth, with its own keys, serve it. (2) `status` in the host answer grows from two values to five, with an explicit precedence, and `requireAuth` answers the three new ones before it opens any tenant connection, because a project that is still being prepared, being migrated or unreachable cannot be asked anything.

Tracer: bearers issued by two in-process Auth stand-ins (each with its own ES256 key pair, one registered as tenant B's project, the other as an unrelated project) and a real project-0 bearer; the request on B's host accepts exactly the one signed by B.

Heavy plan, justified: key selection and host status are one decision about the same two lines of `requireAuth` and the same cached resolution; splitting them would make the resolution change twice.

Decisions implemented: D-538 (explicit, host-selected project), D-542 (a tenant being prepared accepts no login), D-545 (a tenant behind is held out, others keep running), D-537 (status is read from the control plane).

1. **Contract first, emission later.** `hostTenantSchema` gains the new status values and the two optional public fields in this plan; the API emits a new status or a field only when a tenant is bound to a non-central project or a schema-state row exists, which no environment has until a human bootstraps a project (plan 25). 2. **`suspended` comes from the mirror.** The status is public (D-32), so `requireAuth` answers `TENANT_SUSPENDED` from the host resolution without opening the tenant database; the one visible change is that a non-member on a suspended host now sees `TENANT_SUSPENDED` instead of `TENANT_HOST_MISMATCH`. Record the change in the SUMMARY and adjust the single existing assertion if there is one.
3. **Identity lane stays central.** `requireIdentity` (Phase 08.1, removed in plan 26) verifies against project 0 explicitly.
4. **Test Auth stand-ins, not a second GoTrue.** `startJwksServer()` serves `/auth/v1/.well-known/jwks.json` for a generated ES256 key and signs bearers; the registry row's `api_url` points at it. A real second GoTrue cannot be proven locally (hosted proof H4).
5. **Error statuses.** The three new codes answer 503 (the tenant exists but cannot serve), `TENANT_SUSPENDED` stays 403. Assumption A-08-1: names and statuses rated `costly`, not one-way.
