# Phase 09.2 Plan 03: Sealed registry, bounded pools and routed lanes Summary

**A tenant that lives only in `rede_tenant_b` is served by an ordinary request: its connection string comes out of the registry as an AES-256-GCM value sealed under a rotatable keyring, its pool sits in a bounded LRU with a per-project breaker, and `withTenantTx` / `membershipInTenant` pick the project from the tenant id with a fail-closed 503 for an unbound or unreachable tenant**

## Accomplishments

- Tracer: `GET /v1/me/bootstrap` with a verified session and the host of a tenant registered only in B answers 200 with `tenant.displayName` read from B's row, while the central project holds the same tenant id under a different name; the user's membership exists in B and in no central table; rede-lab (project 0) is unchanged.
- Sealing exists once: `sealed.ts` opens any key id in the keyring (`PLATFORM_MASTER_KEYS`, `PLATFORM_MASTER_KEY_ID` seals), binds each value to `<projectId>:<column>`, and throws only `sealed value unreadable`. The payments helper now calls it with a one-key ring and its test file is byte-for-byte unchanged and green.
- `pnpm platform:reseal` rotates the master key row by row (ascending id, `for update`, one transaction per row, fixed column order), never touches `credential_version`, is resumable, leaves a row it cannot open untouched and exits 1, and prints ids and numbers only.
- The pool cache is bounded (24 projects, 3 connections each, 20 s idle), creates each pool once under concurrency, never ends an in-flight pool, and opens a breaker at the third consecutive failure that admits exactly one probe at 15.000 s. Project 0 is served by the existing `sqlClient` pool and is never pooled or evicted.
- The resolver serves a binding for 15 s without a registry read, keeps the last good one for 10 minutes only while the central read fails (single-flight, 5 s retry backoff), and fails closed with `TENANT_UNAVAILABLE` past that or on a cold process; no binding is `TENANT_PROJECT_UNBOUND`. Nothing falls back to project 0.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The local second database lacked USAGE on the Supabase schemas for the API roles**
- **Found during:** Task 1 (the first tracer run answered 500 with SQLSTATE 42501 inside the tenant lane on B)
- **Issue:** plan 02 builds `rede_tenant_b` from a `pg_dump --no-privileges` of auth/storage/realtime, so `authenticated` had no USAGE on schema `auth`; an RLS policy or function calling `auth.jwt()` failed. A real Supabase project grants it.
- **Fix:** `scripts/db-two-databases.sh` now runs an idempotent `grant usage on schema auth, storage, realtime, extensions to anon, authenticated, service_role` on every run, so it also repaired the existing database without a reset.
- **Files modified:** scripts/db-two-databases.sh (not in the plan's list)
- **Commit:** afc83581

**2. [Rule 2 - Missing critical functionality] The platform lane had to join the admin-lane import restriction**
- **Found during:** Task 1 (exporting `withPlatformTx` for scripts and the kernel)
- **Issue:** a `service_role` lane reachable from an unrestricted import path would undo the CR-03 rule that keeps `service_role` out of module code.
- **Fix:** `@rede-social/core/db/platform-tx` added to the three `noRestrictedImports` groups in `biome.json` next to `admin-tx`; the package exports only `./db/platform-tx` (not `project-pools` or `project-handle`). Plan 04 still adds the `LaneTarget` signature.
- **Files modified:** biome.json, packages/core/package.json (neither in the plan's list)
- **Commit:** afc83581

**3. [Rule 3 - Blocking] Shared error classes needed a dependency-free home**
- **Found during:** Task 1 (the 503 mapping must be recognised by `api-error.ts`, which should not import the pools or the registry)
- **Fix:** new `packages/core/server/tenancy/project-errors.ts`, re-exported from the registry (`ProjectUnboundError`) and the pools (`ProjectUnavailableError`) so the plan's export names hold.
- **Commit:** afc83581

**4. [Plan wording] The 503 mapping sits in `errorEnvelope`, not at each lane**
- **Found during:** Task 2
- **Issue:** the plan says "mapping at the points the lane throws"; the errors surface from `membershipInTenant` inside `requireAuth` and from any route, so per-lane mapping would miss most paths.
- **Fix:** one mapping in `errorEnvelope` (503, no details). Same observable behavior; the integration cases assert the HTTP envelope.
- **Commit:** b133703a

**5. [Rule 2 - Hardening beyond the plan] Resolver retry backoff, connection-failure counting, stale-version routing**
- **Fix:** `BINDING_RETRY_BACKOFF_MS = 5 s` after a failed refresh; `run()` counts a connection-level driver code (not a query error) toward the breaker; a request still carrying an older `credentialVersion` is served by the newest pool instead of reviving the old one. Each has a unit case.
- **Commit:** afc83581, b133703a

### Environment notes (not code deviations)

- The plan's verify command starts with `pnpm db:reset && pnpm db:seed`; the orchestrator's rules forbid another reset, and plan 02 left the stack reset, seeded and with the central set. The three integration suites were run directly with vitest.
- The seeded local users carry the CI throwaway passwords (`ci-only-*`), while `apps/api/.env.local` holds the developer's own. Suites that sign in as a seed user fail with "Invalid login credentials" unless `SEED_PASSWORD` and `SUPER_ADMIN_PASSWORD` are overridden on the command line. The new suites create their own users, so they pass either way.
