# Phase 09.2 Plan 13: The eight-step project bootstrap Summary

**An empty Supabase project becomes a ready tenant database through eight recorded, idempotent, resumable steps run by a durable platform job: the tracer bootstraps `rede_tenant_b` with the fake provider and then serves `GET /v1/me/bootstrap` from it, every step can fail and resume without repeating a finished step, and no credential ever leaves the sealed registry**

## Performance

- **Duration:** about 35 min (22:20 to 22:55, local time)
- **Tasks:** 3 (1 tracer, 2 auto)
- **Commits:** 5 (three task commits, one follow-up for the admin-lane inventory, one cleanup)
- **Disk:** 9.5 GiB free at the start, 9.0 GiB at the end (the Storage volume grew with the one full integration run)

## Accomplishments

- **Tracer.** On an empty `rede_tenant_b` (the shim's new `--bare` mode: Supabase platform schemas only, like a fresh hosted project), `startBootstrap` writes eight `pending` rows and enqueues one `platform.project-bootstrap` job whose payload is `{ projectId }` and whose singleton key is the project id. `runBootstrap` then ran all eight steps: the project key, `postgres` password and DDL URL were sealed, `api_user` got a password and sealed transaction and session URLs (verified by logging in with both), the 147-file tenant set went through the plan 02 runner, the Data API closure PATCH (`db_schema: data_api_closed`) followed it, `to_regnamespace('platform')` was null, the single Auth PATCH carried the project's hook URI with `enabled: false` on both access hooks, the buckets and Realtime policy were verified, the central `tenants` row and modules were copied with `jsonb_populate_record`, and the first-admin invite was created in the project with `created_by` null. The project turned `ready`, the host answer left `preparing` immediately, and a request with that tenant's host and a real session answered 200 with a display name that exists only in B.
- **Engine.** Steps are claimed with `update ... where status in ('pending','failed') or (running and older than 15 minutes) returning`; a second run gets zero rows and returns `skipped`. A failed step stores `failed`, the attempt and a closed-catalog reason code; `resumeBootstrap` puts only that step back to `pending`. Nothing but ids, step keys, attempts and reason codes is logged, stored or enqueued.
- **Auth template.** `buildAuthConfigBody` is pure and pinned: a unit test reads `supabase/config.toml` (base `[auth]` plus `[remotes.production.auth.*]`) and fails if any shared key diverges.
- **DBT-36.** `tenant_invites.created_by` lost its not-null and its foreign key (expand-only migration generated from the Drizzle schema); `createPendingInvite` accepts `string | null`. pgTAP 212 proves the column, the kept foreign keys, the central-actor case, the unchanged exposure and the new central `pending_invite` column.

### Environment notes (not code deviations)

- `rede_tenant_b` shares its roles with the local cluster. Roles are cluster-wide, so a generated `api_user` password would lock project 0 out. The test default is the fixed local password `postgres`; the single case that proves a generated password (the secrets scan) restores it in a `finally` and `afterAll` restores it once more.
- The fake provider records the `postgres` password it is given but never applies it, so the tests redirect only the DDL connection to the local superuser; the `api_user` URLs are used exactly as stored.
- Not implemented here, on purpose: the `platform.project_schema_state` row (applied count and head) is left to plans 14 and 15, which own the fan-out and the panel; without a row the host is never held out as `updating`.

## DBT-36: other writers of a platform actor's id into a tenant table (`git grep -n "actor.userId\|createdBy" -- packages/core/server`)

- `tenant_invites.created_by`: the only column that had a foreign key to `users` and received a central actor's id. Now nullable, no foreign key. `createTenant` still passes `actor.userId` on the default-project path (project 0, where that user exists); plan 14 passes `null` for a project that is not project 0, and the bootstrap's `invite` step always does.
- `access_grants.created_by_user_id`: no foreign key (by design, "a deleted account must not block history"); `createPendingInvite` writes it through `grantManualAccess`, which already accepts `createdBy: string | null`.
- `payment_products.created_by_user_id` and the payments setup `createdByUserId`: tenant admins of the tenant lane (`ctx.userId`), no foreign key, not platform actors.
- `media_assets.owner_user_id` (foreign key to `users`): written from the tenant lane by the uploading member, never by a platform actor.
- Every other `actor.userId` hit (`branding.ts`, `domains.ts`, `modules.ts`, `tenants.ts` logs, `invites.ts` resend paths) is a log field, not a stored column.

- pgTAP `154-moderation-log.sql` test 41 did not trip: pgTAP ran straight after the reset, before any integration residue.
- **One flaky test in the full run, not this plan's:** `payments-admin.test.ts` "P45: two concurrent first saves of the integration leave one row with the derived id and a token that opens" answered `[500, 200]` instead of `[200, 200]` once (the first PUT of a pair on a freshly reset database).
