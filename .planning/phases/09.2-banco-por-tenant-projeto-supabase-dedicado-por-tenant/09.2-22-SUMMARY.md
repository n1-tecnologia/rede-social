# Phase 09.2 Plan 22: The move engine's copy Summary

**A tenant's rows, accounts (same ids, bcrypt hashes intact), Storage objects, branding URLs and queued jobs are copied into a bootstrapped database in a catalog-derived foreign-key order and verified by counts, checksums, password-hash digest and an old-origin scan, with a dry run that refuses any table or user it cannot place and an engine that cannot write to its source**

## Accomplishments

- **Tracer.** `rede_tenant_b` is bootstrapped by the real plan 13 engine with the fake provider (`tenantsToSeed` names rede-lab although the tenant stays bound to project 0). `planMove` finds 50 copyable tables, no `uncovered`, no `schemaMismatch`, 7 accounts; `copyAuth` writes the 7 accounts, `copyRows` copies about 200 rows in the derived order, `verifyCopy` passes, and no table, `auth.users` row or tenant row of rede-demo exists in the target. The source's whole-table counts are identical before and after.
- **Order from the catalog.** `orderTables` is a pure Tarjan + Kahn: ties by name, a multi-table cycle only when every constraint is DEFERRABLE (the `event_secrets`/`events` pair becomes one group), a self reference only with a rule in `SELF_REF_ORDER` (`feed_comments` by `parent_depth`), anything else `unsortable_tables`. 10 unit cases on synthetic graphs.
- **Rows.** To read: `to_jsonb(t)::text` over a cursor in one repeatable-read read-only source transaction. To write: one target transaction per group, `jsonb_populate_recordset` on the non-generated columns (`pg_attribute.attgenerated`), 500 per batch, `on conflict do nothing`. The two mirrored tables are updated, not inserted: `tenants` takes `branding` (rewritten), `rules_text`, `rules_version`; `tenant_modules` takes `settings`.
- **Accounts.** The intersection of the `auth.users` / `auth.identities` columns of both sides minus generated ones, the e-mail (and identity) conflict check before any write, then users, identities and the source `public.users` rows upserted to match exactly (name, created_at).
- **Files, URLs, jobs.** `copyStorage` over an interface (in-memory pair in the unit tests, the local Storage with two throwaway buckets in the integration test, `supabaseStoragePort` over an injected client for the real thing); `rewriteStorageOrigins` touches only `/storage/v1/object/public/branding/` URLs; `scanForOrigin` counts per column in the target; `requeueJobs` re-sends then cancels.
- **Safety net.** A table the engine cannot place, a table the target lacks, a column mismatch and a row that references a user outside the tenant's accounts each refuse the plan by name before a byte is written.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug avoided] The copy fired the tenant tables' user triggers**
- **Found during:** Task 1 (reading the catalog before the first insert)
- **Issue:** `public` carries insert triggers with side effects: `feed_comments_count`, `feed_likes_count`, `feed_posts_community_stats` (double counts), `chat_messages_seq_trg` (reassigns the sequence), `chat_messages_signal_trg` (broadcasts to Realtime), `member_profiles_from_membership` (creates a default profile ahead of the copied one, which `on conflict do nothing` would then lose). The plan names none of this.
- **Fix:** every table of a group that has user triggers gets `alter table ... disable trigger user` at the start of the group transaction and `enable trigger user` before commit (transactional DDL, so a failed group restores them). Foreign keys stay enforced.
- **Files modified:** packages/core/server/projects/move/copy-rows.ts
- **Verification:** mutation check: with the silencing removed, the tracer fails (`PostgresError: cancelled` from the signal trigger); with it, counts and checksums are equal.
- **Committed in:** 854c1eca

**2. [Rule 2 - Missing critical] A row referencing a user that is not one of the tenant's accounts**
- **Found during:** Task 1 (the catalog shows 39 foreign keys to users, 36 of them single column from copied tables, while the account set is memberships plus invitees)
- **Issue:** such a row would fail its foreign key in the middle of the copy, with a database message that quotes key values, or tempt a future change to widen the set (which PR-7 forbids).
- **Fix:** `planMove` reports `danglingUsers` (`table.column`), `assertCoverage` throws the new code `account_missing`; `copyRows` re-checks. The Auth copy still takes memberships and invitees only. Two other codes the plan did not list were added for the same reason: `tenant_not_found`, `target_not_ready` (the bootstrap did not seed the tenants row).
- **Files modified:** packages/core/server/projects/move/plan.ts, types.ts
- **Verification:** `move-copy.test.ts#refuses a row that references a user outside the tenant accounts` (a stray auth account is referenced by a community; the plan lists it, the Auth copy writes nothing for it).
- **Committed in:** 854c1eca

**3. [Rule 1 - Plan inconsistency] What `uncovered` means**
- **Found during:** Task 1
- **Issue:** the plan derives the copy set from the catalog (every `tenant_id` table minus the exclusions) and also says a new `tenant_id` table must show up in `uncovered`; both cannot hold if "covered" is only "in the derived set".
- **Fix:** `uncovered` is (a) a `public` table WITHOUT `tenant_id` that is neither excluded nor special (tenant data reachable only through a parent) and (b) a `tenant_id` table the TARGET does not hold. A `tenant_id` table present on both sides is copied automatically; `planMove(source)` with no target therefore includes it in the set. The plan's "new table fails the dry run" case runs with a target and with an orphan table.
- **Files modified:** plan.ts
- **Committed in:** 854c1eca

### Plan wording that was read, not a code change

- **`set constraints all deferred` is redundant here.** Both constraints of the cycle are `DEFERRABLE INITIALLY DEFERRED`, so removing the statement does not fail the tracer (mutation-checked). It stays: it is the plan's contract for any cycle whose constraints are deferrable but initially immediate.
- **The seed does not exercise the self-reference rule** (both seeded replies sort after their parents by uuid). A fixture case with a reply whose id sorts first and `batchSize: 1` does; without the rule it fails with `feed_comments_parent_fk`.
- **Checksums use `to_jsonb(t)::text`**, not `t::text`, so the digest is independent of column order. The password-hash digest is reported only as `match`/`mismatch`.
- **`requeueJobs`** receives started pg-boss instances instead of building a sender from a project; plan 23 owns the sealed URLs.
- **`copyStorage`** holds one object in memory at a time per worker (`download` buffers it); the pilot plan caps a file at 50 MB.
- **The 'jobs requeued' case moves a throwaway tenant id's job**, not rede-lab's: rede-lab has 94 real waiting jobs in the shared source and cancelling them would change the seed other suites depend on.
- **The verify chains' `pnpm db:reset && pnpm db:seed` were not run.** No SQL, migration or seed changed; `scripts/db-two-databases.sh --reset` runs inside the suite (1.6 s) and the local stack was left as found. pgTAP was not run for the same reason.
- **The full integration suite was not run** (see Issues Encountered). Run instead: `move-copy` (18) + `project-bootstrap` (26, the only existing suite whose code this plan touches) in one pass, core unit (82 files, 1,127 tests), api unit (11 files, 129 tests), `turbo typecheck lint` for core and api, `pnpm boundaries` (2,009 files) and `pnpm guard:lanes`.
