# Phase 09.2 Plan 23: The move tool Summary

**A tenant is suspended, copied by the plan 22 engine, verified, repointed in one central transaction and reactivated by one command whose every step is a compare-and-set transition with an append-only trail; it can be undone without silent loss, the source is removed only by a typed and confirmed command, nothing can edit or reactivate a tenant halfway through, and the central project can be proved platform-only**

## Accomplishments

- **Tracer.** `runMove` moves a throwaway tenant of project 0 (a member with a password, a community, a post with a comment, an event with its secret) to a bare `rede_tenant_b` that the tool itself registers and bootstraps with the plan 13 engine. The trail is `started, target_ready, suspended, quiesced, copied, verified, cutover, reactivated, done`; the by-host answer is `active` with the target's project and publishable key; a freshly signed-in member is served from the target (B's own tenant row is the one the API reads); source and target hold equal row counts, another seeded tenant is untouched, and `isTenantMoving` is false.
- **State machine.** `tenant_moves` advances only by `update ... where id and state = $from` (zero rows is `move_conflict`), a 15-minute row lease separates two runners (`lease_held`), a partial unique index leaves one open move per tenant (`move_in_progress`), and `tenant_move_events` is append-only (an update raises, even for the service role; the cascade delete stays possible). Event details are refused when they look like an address, a hash, a token, a connection string or a key.
- **Cutover.** From `verified` the source fingerprint is recomputed against the one stored (`source_changed`), then one central transaction locks the move, swaps `tenant_projects` (`previous_project_id` keeps project 0) and sets `cutover` with `cutover_at`. The rest (caches dropped, registry wait, the rewritten branding pushed to the central mirror, every central-owned field pushed to the target, a second queue requeue, reactivation, `done`) is idempotent, so `--resume` from `cutover` repeats only what is safe.
- **Rollback and recopy.** Before the flip a rollback restores the status; after it the tenant is held, the rows written in the target since `cutover_at` are counted (per table, plus rows deleted since) and the rollback refuses with `writes_since_cutover` unless `--accept-loss`, then swaps the pointer back in one transaction, applies the inverse origin rewrite to the central branding, sends the queue back and restores the status. A second rollback is a no-op; `source_deleted` makes it impossible. The recopy wipes only the target (reverse foreign-key order, the cycle deferred), keeps the accounts and restarts the copy.
- **The one deleting path.** `--confirm-delete --confirm-slug` requires the slug typed again, state `done`, a target that still holds the tenant, prints the per-table plan first (as an event and a line), deletes the tenant's rows from the copy-set tables of the source, its files, and only the accounts nobody else uses through the Admin API; a grep test fails if any other file deletes from the source side.
- **Central residue.** `pnpm platform:central-clean [--strict-empty]` lists, in ascending table name, the rows of moved tenants still in the central project, foreign accounts and files, as counts; two runs print the same bytes; exit 0 or 1.
- **Server-side refusal.** `TENANT_MOVING` (409, no project fact) from a middleware on the parent platform router and from `setTenantStatus` itself; the runner passes the move's id. The real `isTenantMoving` and `tenantsMoving` feed the DTO field plan 14 supplied, so the "Em mudança" state, the header pill and the disabled "Reativar tenant" of plans 19 and 20 now come from a real move.
- **Entry points.** `ROLE=move` in the API image and `pnpm platform:move-tenant`; one mode at a time; exit 0 ok, 1 a `MoveError`, 2 usage.

### Plan wording that was read, not a code change

- **The guard is mounted in `routes/platform/index.ts`, defined in `tenants.ts`.** The plan says "a small middleware mounted on `/:id/*`" in `tenants.ts`, but the truth says every non-GET request under `/v1/platform/tenants/:id/**` is refused, and the domains, branding and database routers are siblings of `tenantsRoutes`. The middleware is exported from `tenants.ts` (the acceptance grep finds `assertNotMoving` there) and registered on the parent router right after `requireSuperAdmin()`; the test mutation-checked that without the wildcard mount the module toggle goes through.
- **`startBootstrap` is not called.** The tool runs the eight steps inline with `runBootstrap`, which inserts the step rows itself, so no platform job is enqueued that a running worker could also pick up. The default `tenantsToSeed` carries the move's tenant.
- **`--recopy` continues to `done`.** It wipes the target, puts the move back in `suspended` and continues the normal loop (copy, verify, cutover), exactly as `--resume` would.
- **`already_done`.** A start (or resume) for a tenant whose latest move is `done` to that target answers `already_done` and writes nothing; `already_on_target` is the error for a tenant that lives there without such a move.
- **The verification also checks the quiescence digest.** After `verifyCopy` the source footprint is computed again and must equal the one sampled at quiescence (`source_changed`), so a change between the quiescence and the verification is caught before `verified`, not only at the cutover.
- **Residue accounts are counted only once a move exists** (or with `--strict-empty`): the plan's definition ("neither platform admins nor members of a central tenant") would flag any stray test account on a stack where nothing moved, which contradicts P106. The definition is otherwise the plan's.
- **Extra files:** `context.ts` (the connections, queues and seams of a move), `move-helpers.ts` (the integration harness).
- **A rollback from `done` cannot hold the tenant with the move**, because the move is already closed. It suspends the tenant itself for the length of the rollback; a platform admin could in theory reactivate it in that window. Recorded in `.planning/WINDOWS.md` (deviation).
