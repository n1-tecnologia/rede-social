### CR-01: Any member can delete or rewrite community links and products directly through PostgREST

**Files modified:** `packages/modules/store/db/schema.ts`, `supabase/migrations/20261009084537_store_admin_write_policies.sql` (generated), `supabase/migrations/20261009084554_store_admin_write_truncate.sql` (`--custom`), `supabase/migrations/meta/_journal.json`, `supabase/migrations/meta/20261009084537_snapshot.json`, `supabase/migrations/meta/20261009084554_snapshot.json`, `supabase/tests/180-store.sql`, `packages/modules/store/README.md`
**Commit:** e8404e7
**Applied fix:** The tenant-only `FOR ALL` policies on `store_products` and `store_product_communities` are replaced in a new migration. Each table now has 4 policies: `*_select_tenant` (`tenant_id = app.tenant_id()`), plus `*_insert_admin`, `*_update_admin` and `*_delete_admin`, which also require `app.tenant_role() = 'admin_tenant'`. They are mirrored in the Drizzle schema through a local `tenantReadAdminWritePolicies` helper, and a re-run of `drizzle-kit generate` reports no schema changes. TRUNCATE ignores RLS, so a second `--custom` migration revokes TRUNCATE on both tables from `authenticated`. Before this change, `authenticated` held TRUNCATE on both tables on the local DB.

The predicate is consistent with the routes. `store.product.manage` is composed for `admin_tenant` only, through the store manifest's `defaultRolePermissions`. Settings only affect the feed's posting policy, so no other role can receive it today. This is now pinned by WR-03's tripwire.

pgTAP section 4b in `180-store.sql` adds 21 assertions:
- Member lane: still reads 4 products and 4 links. Inserts on either table raise 42501, updates and deletes touch 0 rows, and TRUNCATE on either table raises 42501. The member still has locked communities afterwards.
- `support_tenant` lane: same refusals on both tables.
- Admin user with a null `tenant_role` claim: writes nothing.
- `admin_tenant` lane: inserts, links, updates, unlinks and deletes a product (1 row each), and still cannot stamp another tenant's id (42501).

The API write path is unchanged. The store integration suites pass with the new policies, including product create, PATCH (with links), status, grant and revoke.

### CR-02: Editing a product's communities silently drops its links to archived communities

**Files modified:** `packages/modules/store/server/service.ts`, `packages/modules/store/contracts/index.ts`, `packages/modules/store/server/routes.ts` (OpenAPI description), `packages/modules/store/README.md`, `apps/web/app/(app)/loja/product-actions.ts` (doc comment only), `apps/api/tests/integration/store.test.ts`, `.planning/phases/08.2-loja-e-acesso-a-comunidades-por-compra/08.2-10-SUMMARY.md`
**Commit:** 411b873
**Status:** fixed: requires human verification (the delete predicate changed)
**Applied fix:** In `replaceLinks`, the delete is now `delete from store_product_communities l using communities c where ... and c.status = 'active' and c.deleted_at is null`. Only links to live, active communities are replaced, which is exactly the set the form can list. Links to archived and removed communities are left untouched. The contract, route and README docs now say "REPLACES the links to ACTIVE communities".

A new integration case covers it. A product links an active, an archived and a removed community, and a PATCH sets `communityIds: [other]`:
- The answer lists only `other`.
- The links are archived + removed + other.
- The archived community still serves the member only its newest post (the sample).
- A following PATCH with `[]` keeps the archived and removed links.

The fix fully closes the 08.2-10 open issue, so a resolution note was appended to the 08.2-10 SUMMARY. The 08.2-12 SUMMARY was left alone, as instructed.

### WR-03: The ledger RLS hard-codes `admin_tenant`, while the routes authorise by `store.product.manage`

**Files modified:** `apps/api/tests/unit/registry.test.ts`, `packages/modules/store/module.ts`, `packages/modules/store/server/routes.ts`
**Commit:** 0a09a67
**Applied fix:** I chose "one authority" by documenting `store.product.manage` as admin-only by construction. The other option was a role comparison in the routes, which `requirePermission`'s FEED-08 rule forbids. Moving the manager reads into SECURITY DEFINER functions would have been a larger redesign.

The manifest and routes docs now explain that the database authorises the same reads and writes by the `admin_tenant` claim:
- the ledger select policies
- the CR-01 write policies
- the grant and revoke definers

New registry case 14 is a tripwire. For every `TENANT_ROLES` value, with every toggleable module on, and with both empty and generous settings, `store.product.manage` must be present only for `admin_tenant`. If anyone ever composes it for another role, the test fails before the buyers list, `holderCount` or the lock preview can silently read zero rows.

### WR-04: The pgTAP plan pins are flaky on dead tuples

**Files modified:** `supabase/tests/180-store.sql`, `supabase/tests/090-feed.sql`
**Commit:** 36139a0
**Applied fix:** I chose a deterministic, transaction-local `set local enable_seqscan = off` around the EXPLAIN blocks, followed by `reset enable_seqscan` right after. The assertions are kept.

The root cause on this stack is index bloat, not heap dead tuples. Measured: `feed_posts` was 2 pages for 65 live rows, but `feed_posts_tenant_created_all_idx` was 406 pages and `feed_posts_tenant_community_created_idx` 492 pages. Every run inserts volume rows and rolls them back, which leaves those index entries behind. A pre-step `VACUUM` would not shrink the btree, and it cannot run inside the pgTAP transaction anyway, so the review's vacuum suggestion would not have been deterministic.

What P41 and the 090 keyset pins protect is index usability: the gate predicate must keep the index able to serve the ordered walk, and the gate must be an InitPlan. Which plan the planner prefers on a bloated table is not that property. With sequential scans disabled, the planner still falls back to one when no index can serve the query, so the index-name and no-Seq-Scan pins stay falsifiable. The InitPlan pin is unchanged.

Reproduced and verified: before the fix, the second run on an unreset stack failed P41 tests 121-122 (`Seq Scan on feed_posts`). After the fix, 180 and 090 passed 3 runs in a row on the same unreset stack.
