# Phase 08.2 Plan 10: The Product Form and the Lock Warning Summary

**Admins now create and edit products at `/loja/novo` and `/loja/{id}/editar`. The form takes an image through the signed upload, shown in the card's 4:5 crop, and a price typed the Brazilian way and kept in integer cents. It also has the community multi-select, which is the only place links are written. Before a save that would make an open community exclusive, the API counts the members who would lose access and a danger dialog shows that number; if the count cannot be read, nothing is saved. The community edit form shows, read-only, which products gate it.**

- **Picker footer and API calls (Task 1).** `CommunityPickerSheet` has a sticky `footer` pinned to the panel's real bottom edge, and the two existing sheets are unchanged. `lib/store.ts` gains `createProduct`, `updateProduct` and `lockPreview`, which return discriminated outcomes and never throw. - **Product form (Task 1).** The `CommunityForm` shell is reused. The image box is 4:5, at most 240px wide, and falls back to the brand gradient. Name and description use the caps and the counter. The price field accepts "19", "19,9", "19,90", "1.234,50" and "1234,50", re-displays two decimals on blur, and refuses "-1", "19.90", "abc" and anything over R$ 100.000,00. The communities field appears only while that module is on. An edit sends only the keys that changed. Archive and reactivate each sit behind their dialog.
- **Lock warning (Task 2).** A save first asks the API's lock preview for any community outside the saved links. A failed preview toasts and saves nothing. No rows means the save goes ahead. Otherwise the danger `ConfirmDialog` with the `Lock` icon opens, naming each community and its exact member count. "Voltar" keeps the selection, and confirming runs the save inside the dialog's pending state.
- **Read-only "Acesso" block (Task 2).** It appears in the community edit form for store managers. Each product is a link to `/loja/{id}`, archived products carry " (arquivado)", and a community with no product reads "Aberta para todos os membros.". If the access read fails, the block is absent.

## Issues Encountered

- During the e2e runs the browser logged `unhandledRejection … reading 'waiting'` and mux-player token messages from the dev server. They appear across every spec in the run, and no test failed.
- Saving a changed link set uses the API's whole-set replace. The edit form can only list ACTIVE linked communities (`productDetailSchema.communities`), so changing the selection on a product that also links an ARCHIVED community drops that archived link. The API refuses archived ids (`community_invalid`), so the form cannot re-send them. A save that leaves the selection unchanged sends no `communityIds` and keeps every link. Recorded for plan 12 or a later API change (for example, archived links shown read-only in the form). **Resolved by the 08.2 code review fix CR-02 (2026-10-09):** the API's replace now deletes only the links to live, ACTIVE communities, so a save that changes the selection keeps every link to an archived or removed community, and that community stays locked (integration case `CR-02` in `apps/api/tests/integration/store.test.ts`). Showing archived links read-only in the form remains an optional UX improvement, not a correctness issue.
