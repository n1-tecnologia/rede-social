### Claude's Discretion
Each item has a stated default. The planner may refine it but should not reverse it without asking.
- **Comments on the visible newest post.** Default: non-buyers see the comment count but not the comment list. Comments are community content, and every comment endpoint (list, replies, thread) refuses for a non-buyer.
- **A share or notification link to a hidden post (`/post/{postId}`) opened by a non-buyer.** Default: it renders the locked state with the buy section, never the post. `getPost` refuses server-side.
- **Access duration.** Default: lifetime until revoked. The order and entitlement model leaves room for an expiry later, but nothing expires in this phase.
- **Who manages products.** Default: `admin_tenant` only, for product CRUD, the buyers list, grant and revoke. `support_tenant` still sees every community in full (success criterion 4) but has no store admin.
- **A locked community with no posts.** Default: the normal empty state plus the top buy section.
- **The entitlement storage.** The researcher and planner decide whether the gate reads the existing, unused `community_members` seam or a new product-entitlement table joined through product–community links. The rule: the RLS gate must stay cheap (indexed lookups) and must not break any existing two-tenant isolation assertion.
- **The product image media purpose.** The planner decides whether to reuse `cover` or add a `product` value to `MEDIA_PURPOSES`.
- **Store ordering.** Default: newest first. The planner may reuse the communities `position` / `PUT /order` pattern if it is cheap.
- **Money formatting.** Add one shared BRL formatter (`Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' })`) in contracts or ui. Nothing exists today.

### Deferred Ideas (OUT OF SCOPE)
- **Payment gateway.** A later phase. It plugs into the order created here (roadmap).
- **Sale notification to the admin, and grant or revoke notifications to the member.** These are new notification types and are not built in this phase.
- **A delivery note for products with no community.** An admin-written text or link shown to the buyer after purchase. Offered and declined for now (D-353).
- **Grant and revoke from the member admin sheet.** A "Produtos" section in `MemberAdminSheet`. Only the buyers list has it in this phase (D-360).
- **Editing product links from the community form.** Read-only there for now (D-363).
- **Expiring or subscription access.** Access is lifetime until revoked in this phase.
- **A separate "Minhas compras" screen with dates and amounts.** The chip filter covers it for now (D-352).

## Summary

The store itself is ordinary CRUD in this codebase's style: a new module package `packages/modules/store` with four tables (products, product–community links, orders, entitlements), a Hono router mounted at `/v1/store`, a TopBar nav entry, and a `store` key in `tenant_modules`. No new npm package is needed. The image reuses the `cover` media purpose and the existing signed-upload flow. Money is an integer-cents column plus one shared `Intl.NumberFormat` helper.

The hard part is the gate. Today no table has a per-user content policy: every community policy is `tenant_id = app.tenant_id()`, and the feed reads community posts with no filter at all (D-73). The gate has to reach every consumer of community content: Início, Reels and its lanes, the community page, the `/post/{id}` share target, comments, replies, threads, likes, community highlights, notification fan-out, and video playback tokens. I recommend one SQL seam that answers "which communities are locked for this lane", evaluated **once per statement** as an `InitPlan`, and used in three places:

1. a **restrictive** select policy on `feed_posts` that hides a locked community's posts except its newest one (the free sample, D-356);
2. restrictive policies on `feed_comments` (select) and `feed_likes` (insert), so comments of locked posts are invisible and interactions on the sample fail in the database too;
3. explicit predicates in the feed, stories and notification services (Início/Reels exclusion, a `403` on interactions with the sample, the highlight place seam, the fan-out audience).

A rolled-back probe on the local stack (PG 17.6, 3,000-post volume fixture) confirmed that this policy keeps the existing index plans (`feed_posts_tenant_created_all_idx` for Início, `feed_posts_tenant_community_created_idx` for a community page), that the gate functions run as two `InitPlan`s per statement, and that a member lane sees exactly one post (the newest) of a locked community holding 202.

**Primary recommendation:** Store entitlements in new store-owned tables, not in `community_members`. Expose the gate as kernel-declared SQL functions (`app.community_locked_ids()` and two siblings), created as stubs by a kernel migration and given their real bodies by the store migration. Feed, stories and notifications then depend only on kernel names (MOD-02). Enforce the gate with restrictive RLS policies plus explicit service predicates. Write orders and entitlements only through `SECURITY DEFINER` functions.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Store on/off per tenant | API (platform lane, `setModuleEnabled`) | Database (`tenant_modules` row read by the gate functions) | Flags already live in `tenant_modules`. The gate reads the row in SQL, so RLS and API agree. |
| Product CRUD, links, lock preview | API (`/v1/store`, `requirePermission('store.product.manage')`) | Database (tenant isolation policy) | Same shape as communities and events. |
| Purchase, grant, revoke | Database (`SECURITY DEFINER` functions) | API (route guards, idempotent response) | Authorization source of truth (who holds access) must not be writable by a member lane. The `memberships` precedent applies. |
| "Is this community locked for me?" | Database (kernel SQL seam, store implementation) | API services (explicit predicates) | Must be identical for RLS, the services and the worker. A single SQL definition can't drift. |
| Hiding hidden posts, comments, media ids | Database (restrictive RLS on feed tables) | API (projection never returns them) | Criterion 7: hiding in the UI is never enough. RLS is the structural guarantee. |
| Excluding locked posts from Início/Reels | API (feed service predicate) | — | RLS admits the sample post, so Início must exclude it explicitly. |
| Refusing interactions on the sample | API (403 before the write) | Database (restrictive `with check` on `feed_likes`, select policy on `feed_comments`) | A distinguishable refusal for the UI, with RLS as the backstop. |
| Fan-out audience for locked communities | Worker (feed notification source) | Database (`app.community_viewer_ids`) | The worker lane is `support_tenant` and bypasses the gate, so the resolver must filter explicitly. |
| Lock tags, buy section, store grid | Frontend server (RSC composition in `apps/web`) | Browser (pop-ups, chips) | Web composes the communities API with the store API. The communities module stays ignorant of products. |
| BRL formatting / parsing | Shared contracts (`@rede-social/contracts/money`) | Browser and server | Pure function, used by web and tests. Integer cents end to end. |

### Pattern 1: The gate as a kernel SQL seam with a store implementation

**What:** Three kernel-declared SQL functions. Every consumer calls them by name; the store module gives them their bodies.

| Function (proposed names) [ASSUMED] | Lane | Answer |
|---|---|---|
| `app.community_locked_ids() returns uuid[]` | request lane (claims) | communities locked for `app.user_id()`; `'{}'` for `admin_tenant`/`support_tenant` |
| `app.community_locked_ids_for(p_user uuid) returns uuid[]` | any lane of the tenant (worker) | same rule for an explicit user, role read from `memberships` |
| `app.community_viewer_ids(p_community uuid) returns uuid[]` | worker | `null` = not gated (everyone); otherwise the live `member`-role user ids holding access |

**Why a stub first:** the restrictive policies on `feed_posts` must reference a function that exists when the generated migration runs. The stub (`select '{}'::uuid[]`) exists from `<t1>`, and `<t3>` swaps the body with `create or replace` (same signature, same OID, so the policies keep working). A project that reuses feed without the store keeps the stub and the gate is a no-op. This is the `setPermissionResolver` inversion done in SQL.

**Store body (sketch, [ASSUMED] names; columns from the proposed schema below):**

```sql
-- <t3>_store_functions.sql (--custom). Owner postgres has rolbypassrls (the notifications_fanout
-- Pitfall 2): every statement pins tenant_id = app.tenant_id() itself.
create or replace function app.community_locked_ids_for(p_user uuid) returns uuid[]
language sql stable security definer set search_path = '' as $$
  select coalesce(array_agg(distinct l.community_id), '{}'::uuid[])
    from public.store_product_communities l
   where l.tenant_id = app.tenant_id()
     and exists (select 1 from public.tenant_modules tm
                  where tm.tenant_id = l.tenant_id and tm.module_key = 'store' and tm.enabled)
     and not exists (select 1 from public.memberships m
                      where m.tenant_id = l.tenant_id and m.user_id = p_user
                        and m.role in ('admin_tenant', 'support_tenant') and m.deleted_at is null)
     and not exists (
       select 1
         from public.store_product_communities l2
         join public.store_entitlements e
           on e.tenant_id = l2.tenant_id and e.product_id = l2.product_id
        where l2.tenant_id = l.tenant_id and l2.community_id = l.community_id
          and e.user_id = p_user and e.status = 'active')
$$;

create or replace function app.community_locked_ids() returns uuid[]
language sql stable security definer set search_path = '' as $$
  -- Staff by CLAIM (set per request from the membership row, AUTH-06); a null role fails CLOSED.
  select case when app.tenant_role() in ('admin_tenant', 'support_tenant') then '{}'::uuid[]
              else app.community_locked_ids_for(app.user_id()) end
$$;
```

The `memberships` role CHECK is verbatim `in ('admin_tenant','support_tenant','member')` [VERIFIED: packages/core/db/schema/memberships.ts:37] and `app.tenant_role()` reads the `tenant_role` claim [VERIFIED: supabase/migrations/20260912030541_app_helpers.sql:30-33 `select nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'tenant_role'`], which `withTenantTx` sets from `ctx.role` [VERIFIED: packages/core/db/tenant-tx.ts:25-30 `tenant_role: ctx.role`].

### Pattern 2: Restrictive RLS policies on the feed tables

**What:** Restrictive policies AND with the existing permissive `*_tenant_isolation` policy. PostgreSQL: "All restrictive policies which are applicable to a given query will be combined together using the Boolean AND operator … there needs to be at least one permissive policy" [CITED: postgresql.org/docs/17/sql-createpolicy.html]. Every feed table already carries `tenantIsolationPolicy` [VERIFIED: packages/modules/feed/db/schema.ts:175, 260, 429, 514].

```ts
// packages/modules/feed/db/schema.ts — proposed additions. Fragments come from the kernel
// (packages/core/db/community-gate.ts) so the function names live in one place.
// IMPORTANT: `x <> all ((select f()))` does NOT parse as an array comparison (Pitfall 1);
// the coalesce wrapper makes it an expression while keeping the InitPlan.
const LOCKED = sql`coalesce((select app.community_locked_ids()), '{}'::uuid[])`;
const SAMPLE = sql`coalesce((select app.feed_sample_post_ids()), '{}'::uuid[])`;

pgPolicy('feed_posts_community_gate', {
  as: 'restrictive',
  for: 'select',
  to: authenticatedRole,
  using: sql`community_id is null or community_id <> all (${LOCKED}) or id = any (${SAMPLE})`,
}),
// feed_comments: post comments of a post that is visible AND whose community is not locked.
// Story comments (post_id null) are untouched. The inner feed_posts read is itself RLS-scoped.
pgPolicy('feed_comments_community_gate', {
  as: 'restrictive',
  for: 'select',
  to: authenticatedRole,
  using: sql`post_id is null or exists (
    select 1 from public.feed_posts p
     where p.id = feed_comments.post_id
       and (p.community_id is null or p.community_id <> all (${LOCKED})))`,
}),
// feed_likes: a like on a locked post (the sample) or on a hidden comment cannot be inserted.
pgPolicy('feed_likes_community_gate', {
  as: 'restrictive',
  for: 'insert',
  to: authenticatedRole,
  withCheck: sql`(post_id is null or exists (
      select 1 from public.feed_posts p
       where p.id = feed_likes.post_id
         and (p.community_id is null or p.community_id <> all (${LOCKED}))))
    and (comment_id is null or exists (
      select 1 from public.feed_comments c where c.id = feed_likes.comment_id))`,
}),
```

**Probe evidence** (rolled back, local stack, 3,000 extra posts in `rede-demo`, member lane) [VERIFIED: psql EXPLAIN this session]:

```

 Limit
   InitPlan 1 -> Result
   InitPlan 2 -> Result
   ->  Index Scan using feed_posts_tenant_created_all_idx on feed_posts p
         Filter: ((deleted_at IS NULL) AND ((community_id IS NULL) OR (community_id <> ALL (COALESCE((InitPlan 1).col1, '{}'::uuid[]))) OR (id = ANY (COALESCE((InitPlan 2).col1, '{}'::uuid[])))))
== visible posts in the locked community (expect 1 = the sample)   →  1
== post_count of that community                                    →  202
== community page plan
   ->  Index Scan using feed_posts_tenant_community_created_idx on feed_posts p
```

The sample function must be `SECURITY DEFINER`. It reads `feed_posts`, and an invoker function called from a `feed_posts` policy would recurse into the same policy. Supabase's guide recommends the same: "Wrapping the function causes an initPlan to be run … 'cache' the results per-statement" and definer functions "avoid triggering the reciprocal policy check" [CITED: supabase.com/docs/guides/database/postgres/row-level-security].

### Pattern 3: The service applies the same seam explicitly

RLS admits the sample post, so RLS alone would put it in Início. The feed service therefore adds the predicate itself:

```ts
// packages/modules/feed/server/service.ts — listFeed (line 373) predicate, both module states:
const NOT_LOCKED = sql`and (p.community_id is null or p.community_id <> all (${LOCKED}))`;
// listFeed:            sql`${communitiesEnabled ? NOT_LOCKED : sql`and p.community_id is null`} ${mediaPredicate(query)}`
// listVideoCommunities (line 501): `and c.id <> all (${LOCKED})` inside the existing where clause
// listCommunityFeed (line 426): read `locked` with the community probe; when locked and media=video
//   → { items: [], nextCursor: null }; when locked otherwise → limit 1, no cursor (Pitfall 4)
```

Interactions get a guard (one statement, inside the existing transaction, before the write):

```ts
// 404 when RLS hides the post (unknown, foreign, hidden); 403 { access: 'community_locked' }
// when the post is the visible sample of a community locked for this member.
const rows = await tx.execute<{ locked: boolean }>(sql`
  select (p.community_id is not null and p.community_id = any (${LOCKED})) as locked
    from feed_posts p where p.id = ${postId}::uuid and p.deleted_at is null`);
if (!rows[0]) throw new ApiError(404, 'NOT_FOUND');
if (rows[0].locked) throw new ApiError(403, 'FORBIDDEN', { access: 'community_locked' });
```

`FORBIDDEN`, `NOT_FOUND`, `CONFLICT` and `VALIDATION_FAILED` already exist in the error vocabulary [VERIFIED: packages/contracts/src/errors.ts:31,35,39,34 `'FORBIDDEN'`, `'NOT_FOUND'`, `'CONFLICT'`, `'VALIDATION_FAILED'`]. The `details.access` value is a new closed vocabulary in `@rede-social/contracts` [ASSUMED name], so feed can emit it without importing store.

### Pattern 4: Orders and entitlements through definer functions

Follow SCHEMA-CONVENTIONS §(l) and the `memberships` precedent ("a `FOR ALL` policy would let any request in the lane promote itself" [VERIFIED: packages/core/db/schema/memberships.ts:40-45]). Members SELECT their own rows, `admin_tenant` SELECTs the tenant's rows, and nobody gets an insert/update/delete policy. Writes go through:

- `app.store_purchase(p_product uuid, p_expected_amount int) returns table (outcome text, order_id uuid)`. Outcomes: `purchased | owned | unavailable | price_changed | not_found`.
- `app.store_grant(p_product uuid, p_membership uuid) returns table (outcome text, entitlement_id uuid)`. The function itself refuses unless `app.tenant_role() = 'admin_tenant'`.
- `app.store_revoke(p_entitlement uuid) returns table (outcome text)`. Admin only.

Style: `language plpgsql volatile security definer set search_path = ''`, every statement pinned to `app.tenant_id()`, `revoke all … from public; grant execute … to authenticated` (the `app.events_check_in` precedent [VERIFIED: supabase/migrations/20260928085140_event_check_in_ceiling.sql:26-29, 31-33]).

### Pattern 5: Notification audience for a gated community

`resolvePostPublished` (feed/server/notifications.ts:57) today returns `audience: { type: 'members' }` (line 100). Change it to:

```ts
// In the worker lane (role 'support_tenant', so app.community_locked_ids() is '{}' — Pitfall 6).
// null = not gated → the broadcast stays 'members'; an array → users audience (D-229's
// member-only rule is kept because the function returns member-role ids only).
const [gate] = await tx.execute<{ viewers: string[] | null }>(sql`
  select app.community_viewer_ids(${row.community_id}::uuid) as viewers`);
const audience = row.community_id === null || gate?.viewers == null
  ? { type: 'members' as const }
  : { type: 'users' as const, userIds: gate.viewers };
```

For `resolveCommentLiked` and `resolveCommentCreated`, join the post's `community_id` and drop the recipient when `community_id = any(app.community_locked_ids_for(recipient))`. The fan-out definer accepts exactly `'members'` and `'users'` [VERIFIED: supabase/migrations/20260930123214_notifications_functions.sql:50-51 `p_audience not in ('members', 'users')`] and keeps a `users` audience on the live-membership predicate. Push recipients are exactly the in-app recipients [VERIFIED: packages/modules/notifications/server/channels/push.ts `candidates = recipients`], so filtering the audience filters push too.

### Pattern 6: Hidden-post deep links

A hidden post is invisible to RLS, so `getPost` cannot tell "hidden" from "absent". Add a feed definer `app.feed_locked_post_community(p_post uuid) returns uuid` [ASSUMED name]. It returns the community id only when the post is live, in the caller's tenant, and in a community locked for the caller. On an RLS miss, `getPost` calls it: a non-null answer becomes `403 FORBIDDEN { access: 'community_locked', communityId }`, and null stays the bare 404. `loadPost` (apps/web/lib/feed.ts:130) maps 403-locked to `redirect('/comunidades/{communityId}')`, which renders the locked page with the buy section. This reveals "this uuid is a post in community X" only inside the tenant and only for unguessable ids. That is accepted (Security table, T-08.2-09).

### Pattern 7 (recommended, small): Gate video playback tokens

`serveVariant` reads nothing from the database by design [VERIFIED: packages/core/server/media/service.ts:677-700, "ZERO database reads"]. `playbackTokens` already reads `media_assets` in the tenant lane [VERIFIED: service.ts:762-775]. Add a second kernel stub, `app.media_asset_hidden(p_asset uuid) returns boolean` (stub `false`). Feed's migration gives it the real body: the asset is attached to a post hidden from the caller and to no visible post. `playbackTokens` then answers the bare 404 when it is true. Feed needs a new index `feed_post_media (tenant_id, media_asset_id)` for this lookup; none exists today [VERIFIED: packages/modules/feed/db/schema.ts:253-260 lists only `feed_post_media_video_uq`, `feed_post_media_position_uq`, `feed_post_media_tenant_post_idx`]. Images and PDFs stay id-capability URLs (Open Question 2).

### Anti-Patterns to Avoid

- **A permissive gate policy.** A second permissive select policy ORs with `tenant_isolation` and widens access. The gate must be `as: 'restrictive'`.
- **An invoker sample function.** It recurses into `feed_posts` RLS. Use `SECURITY DEFINER` with an explicit `tenant_id = app.tenant_id()`.
- **Calling the gate function per row.** Always wrap it as `coalesce((select app.f()), '{}'::uuid[])` so it runs as an InitPlan (Pitfall 1).
- **Checking the lock in the web only.** Criterion 7 forbids it. The page may render tags from the store API, but feed, stories and the worker enforce the gate independently.
- **Reading `moduleFlags` inside an open tenant transaction** for the store flag. The SQL gate reads `tenant_modules` itself. Any TS flag read happens before `withTenantTx` (the `readPlaceGate` rule, stories/service.ts:1156-1168).
- **Trusting `priceCents` from the client.** The order amount comes only from the product row inside `app.store_purchase`.
- **Materialising access into `community_members`** (see §Entitlement storage).

### Option A: materialise access into `community_members`

2. insert or delete one row per (user, community) on every purchase, grant, revoke, link add and link remove. Revoking product P1 must keep the row when P2 also unlocks the community, so the rows need reference counting or a recompute;
3. write a table owned by another module (MOD-02 smell) and share it with V2 opt-in membership, whose semantics differ.

The RLS check becomes one indexed `exists`, but every trigger above is a drift risk. pgTAP 110 also treats the table as the born-unused V2 seam.

## Orders, Entitlements and Idempotency

**Repo precedents for natural arbiters:**
- likes use partial unique indexes plus `on conflict … do nothing` and always answer 200 with the current state, never 409 [VERIFIED: packages/modules/feed/server/service.ts:1340-1381; schema.ts:508 `uniqueIndex('feed_likes_post_uq').on(t.userId, t.postId).where(sql\`post_id is not null\`)`];
- event RSVPs use `on conflict (tenant_id, event_id, user_id) do update` [VERIFIED: packages/modules/events/server/service.ts:727];
- event check-in uses an advisory lock in a definer [VERIFIED: grep hit in supabase/migrations/20260928083828_event_check_in_lock.sql].

**`app.store_purchase(p_product, p_expected_amount)` flow, all inside one definer call:**
1. No claims → `not_found`.
2. Read the product `where id = p_product and tenant_id = app.tenant_id() for share`. Missing → `not_found`; `status = 'archived'` → `unavailable`; `price_cents <> p_expected_amount` → `price_changed`.
3. An active entitlement already exists for `(tenant, app.user_id(), product)` → `owned` (fast path, no write).
4. `insert into store_orders (…, status 'paid', amount_cents = product.price_cents, currency = product.currency, provider 'none', paid_at now()) on conflict do nothing returning id`. No row → `owned`.
5. `insert into store_entitlements (…, source 'purchase', order_id) on conflict do nothing returning id`. No row (a concurrent grant won) → `raise` a sentinel SQLSTATE so the whole call rolls back, caught in TS → answer `owned`.
6. Return `purchased`.

**Concurrency:** two simultaneous calls by the same member block on the partial unique index of step 4; the second sees the first's committed row and inserts nothing. No orphan order is possible: step 5's sentinel rolls step 4 back.

**API answer:** `POST /v1/store/products/{id}/purchase` → `200 { owned: true, communities: […] }` for both `purchased` and `owned`, mirroring the likes posture. `409 { store: 'unavailable' | 'price_changed' }` for the two state refusals (the communities vocabulary splits state refusals as 409). `404` bare for `not_found`.

**Revoke (`app.store_revoke`):** admin only. Sets the entitlement to `revoked`, `revoked_at`, `revoked_by_user_id`; if `order_id` is not null, sets that order to `revoked` too (D-359). Re-buying then creates a NEW order and a NEW entitlement (both partial uniques are free again), so history is kept.

**Grant (`app.store_grant`):** admin only. Resolves `p_membership` in `app.tenant_id()` (active, not deleted), inserts `source 'grant'`, `granted_by_user_id = app.user_id()`, `on conflict do nothing` → `granted | already_active | not_found`. A membership of another tenant is invisible → `not_found` → bare 404. This closes the cross-tenant grant (SC 8).

**R$ 0:** the same path, `amount_cents = 0`. **Lifetime:** `expires_at` exists, nullable, never set; nothing reads it in 08.2. **Archive keeps access:** step 2 refuses only NEW purchases.

## Common Pitfalls

### Pitfall 1: `<> all ((select f()))` is not an array comparison
**What goes wrong:** `ERROR: operator does not exist: uuid <> uuid[]`. PostgreSQL parses `ALL ((select …))` as the subquery form [VERIFIED: probe error output this session].
**How to avoid:** `community_id <> all (coalesce((select app.community_locked_ids()), '{}'::uuid[]))`. The coalesce makes it an array expression and keeps the InitPlan [VERIFIED: probe plan shows `InitPlan 1` and `ALL (COALESCE((InitPlan 1).col1, …))`].

### Pitfall 2: Migration ordering between generated policies and custom functions
**What goes wrong:** `drizzle-kit generate` puts the feed restrictive policies in a migration whose `CREATE POLICY` must resolve `app.community_locked_ids()`. SQL-language function bodies are validated at creation, so the store body cannot exist before the store tables do.
**How to avoid:** kernel stub migration first (`<t1>`), then the generated migration (`<t2>`), then the store/feed custom bodies (`<t3>`, `<t4>`) with `create or replace` (same signature).
**Warning signs:** `function app.community_locked_ids() does not exist` during `pnpm db:reset`.

### Pitfall 3: The sample post leaks into Início and Reels
**What goes wrong:** RLS deliberately admits the newest post, so the unfiltered merged feed (D-73) shows it.
**How to avoid:** `listFeed` and `listVideoCommunities` add the `NOT_LOCKED` predicate; `listCommunityFeed` returns no item for `media=video` on a locked community. Test: a member without access never sees the sample's id in `/v1/feed` or `/v1/feed?media=video`.

### Pitfall 4: The locked community page walks the whole community
**What goes wrong:** the probe's community-page plan scans `feed_posts_tenant_community_created_idx` with a filter. Filling `limit 11` when only one row passes walks every post of the community (202 in the probe).
**How to avoid:** when the community probe says locked, query with `limit 1` and return `nextCursor: null`. The sample is the newest row, so the scan stops at once.

### Pitfall 5: Invoker trigger functions now see a filtered `feed_posts`
**What goes wrong:** `app.community_post_stats()`, `app.feed_like_count()` and `app.feed_comment_count()` are invoker plpgsql [VERIFIED: 20260923204828_communities_counters.sql:51-52; 20260922162449_feed_counters.sql:33-34, 64-65]. `community_post_stats` recomputes `last_activity_at` with `select max(p.created_at) from public.feed_posts` (line 79). Run by a non-staff writer, that read would ignore hidden posts.
**How to avoid:** today only `admin_tenant` writes posts (bypass) and likes and comments are refused on locked posts, so nothing changes in 08.2. Record it for Phase 9/10 (member posting), or make those triggers `SECURITY DEFINER` then.

### Pitfall 6: The notifications worker lane bypasses the gate
**What goes wrong:** the fan-out runs as `support_tenant` [VERIFIED: system-context.ts:22], so the lane form of the gate returns `'{}'` there and every member would get a post from a locked community.
**How to avoid:** resolvers use the explicit-user forms (`community_viewer_ids`, `community_locked_ids_for`). Test: an integration case publishes into a locked community and asserts that a non-holder has no `feed.community_post` row and no push job.

### Pitfall 7: `store` cannot be toggled from the platform panel
**What goes wrong:** the toggle route validates against `REAL_TENANT_DEFAULT_MODULES` (see §Module toggle).
**How to avoid:** switch the four vocabularies to `TOGGLEABLE_MODULES`, or add `store` to the default list (on by default). Update `platform-tenants.test.ts`/e2e expectations that count module rows.

### Pitfall 8: Flags cache vs the SQL gate
**What goes wrong:** `moduleFlags` caches per instance for 30 s [VERIFIED: packages/core/server/modules/flags-cache.ts `MODULE_FLAGS_TTL_MS = 30_000`], while the SQL gate reads `tenant_modules` live. Right after a toggle, Loja routes may 404 or answer for up to 30 s on other instances while the gate already changed.
**How to avoid:** accept it (content consistency is SQL-driven). Tests that toggle `store` call `moduleFlags.invalidate(tenantId)`, as the shared-identity suite does [VERIFIED: isolation.test.ts:4327, 4361].

### Pitfall 9: Query-budget and EXPLAIN pins move
**What goes wrong:** `feed-query-budget.test.ts` counts statements in `pg_stat_statements` by regex [VERIFIED: apps/api/tests/integration/feed-query-budget.test.ts:1-40]. If `pg_stat_statements.track = all`, statements inside the definer gate functions that read `feed_posts` (the sample function) could start counting. The pgTAP EXPLAIN assertions in `090-feed.sql`, `110`/`111` and `130-reels.sql` pin index names on volume fixtures.
**How to avoid:** run both suites in Wave 0 after the policies land. The probe shows the same indexes are chosen, but budgets may need a recorded bump with the reason.

### Pitfall 10: Strict response schemas and the deploy window
**What goes wrong:** `feedPostSchema` is `.strict()` [VERIFIED: packages/modules/feed/contracts/index.ts:459-499], and the web parses API answers with it. If the API (Cloud Run) starts emitting a new `access` key before the web (Vercel) is on the new contract, the old web's parse fails.
**How to avoid:** ship the field optional (`access: z.enum(['full','sample']).optional()`, absent = full) or accept a brief window. Do the same for any new key on community or store payloads.

### Pitfall 11: API code calling functions the database lacks
**What goes wrong:** the new feed and stories SQL references `app.community_locked_ids()`. An API deployed before the migration 500s on every feed read.
**How to avoid:** migrations first (expand-only, safe with old code), then the API, then the web. Record this in DEPLOY.md's release notes for 08.2.

### Pitfall 12: BRL strings in tests
**What goes wrong:** `R$ 19,90` contains U+00A0, so `toHaveText('R$ 19,90')` with an ASCII space fails.
**How to avoid:** compare against `formatBrl(1990)` or normalise ` `.

### Pitfall 13: Seed-pinned tests and the TopBar
**What goes wrong:** enabling `store` in the seed adds a TopBar slot, which can break shell/nav e2e that count slots. Adding a linked product to a seeded community locks seeded posts for seeded members, which breaks many seed-pinned integration tests (project memory: "the seed is the fixture").
**How to avoid:** seed `store` enabled on `rede-demo` with **no products** (no behaviour change except the icon), and update shell expectations. Tests create their own community + product + link and remove them in `afterAll`. Run pgTAP before integration, and `pnpm db:reset && pnpm db:seed` between runs (memory).

### Pitfall 14: Comments policy must ignore story comments
**What goes wrong:** `feed_comments` also stores story comments (`story_id` set, `post_id` null) [VERIFIED: packages/modules/stories/server/service.ts:999-1012 inserts into `feed_comments`]. A policy written as `exists (select … where p.id = post_id)` without the `post_id is null or` branch hides every story comment.
**How to avoid:** the leading `post_id is null or …`. A pgTAP case asserts a story comment stays visible in a member lane with a locked community present.

### Money helper (`packages/contracts/src/money.ts`)

```ts
import { z } from 'zod';
export const STORE_MAX_PRICE_CENTS = 10_000_000; // [ASSUMED] R$ 100.000,00
export const priceCentsSchema = z.number().int().min(0).max(STORE_MAX_PRICE_CENTS);
const BRL = new Intl.NumberFormat('pt-BR', { style: 'currency', currency: 'BRL' });
export const formatBrl = (cents: number): string => BRL.format(cents / 100);
/** "19,90" | "19" | "1.234,5" → integer cents; anything else → null. Never parseFloat. */
export function parseBrlToCents(raw: string): number | null {
  const m = /^\s*(?:R\$\s*)?(\d{1,3}(?:\.\d{3})*|\d+)(?:,(\d{1,2}))?\s*$/.exec(raw);
  if (!m) return null;
  const reais = Number(m[1].replaceAll('.', ''));
  const cents = Number((m[2] ?? '').padEnd(2, '0'));
  const total = reais * 100 + cents;
  return Number.isSafeInteger(total) ? total : null;
}
```
