# Phase 08.2 Plan 05: Store API (catalogue, admin writes, access, platform switch) Summary

**Seven new `/v1/store` routes complete the store API. Members get a keyset catalogue (`all`, `owned`, manager-only `archived`), the product read, and per-community access (`locked`, `gated`, `archivedTag`, buyable products). Admins get the product edit, whose `communityIds` is the only place a link is written (the whole set is replaced under a row lock), plus idempotent archive and reactivate, which never touch an entitlement, and an exact lock preview. The `super_admin` panel now toggles `store` per tenant over `TOGGLEABLE_MODULES`, with `store` off by default.**

## Accomplishments

- **Catalogue and access reads (Task 1).** `listProducts` uses three literal statements (active, archived, and the caller's active entitlements). Pages are keyset on `(created_at desc, id desc)`, or on the entitlement's own key for `owned`, and over-fetch one row. A cursor this service did not issue answers 400. `getProduct` returns the bare 404 for an archived product unless the caller holds it or manages the store, and adds an exact `holderCount` for managers. `listCommunityAccess` and `getCommunityAccess` read `locked` from the kernel seam (`LOCKED_COMMUNITY_IDS`), so they agree with the feed gate by construction.
- **Admin writes (Task 2).** `updateProduct` locks the product row, then validates the image and communities with the same helpers `createProduct` uses. It updates only the keys sent and replaces the link set in the same transaction. Five rounds of two concurrent patches always left exactly one submitted set. `setProductStatus` is idempotent and touches no link and no entitlement. Archive keeps the holder reading every post, keeps the product under the holder's `owned`, and makes new purchases answer 409 `unavailable`. `lockPreview` lists only the communities that no product gates today and counts live `member` memberships without the product, exactly.
- **Platform switch (Task 3).** The toggle route, `realModuleKeySchema` (create body and tenant detail), `getTenantDetail`, and the panel's page, action and loading skeleton all move to `TOGGLEABLE_MODULES`. `REAL_TENANT_DEFAULT_MODULES` and the creation wizard are unchanged. The new `platform.store.json` adds "Loja" / "Produtos que liberam comunidades exclusivas".
- **Proof.** `store.test.ts` now has `catalogue`, `community access` and `product admin` (24 cases in the file). The isolation sweep covers all nine store routes, `platform-tenants.test.ts` has case 17b, and `platform-tenants.spec.ts` passes 15/15 (one skip, which is pre-existing by design). Full regression on a fresh reset: pgTAP 1065/1065, API integration 55 files / 977 tests.

## Decisions Made

- A tampered list cursor gets 400 (truth P17), not page 1. A `limit` outside 1..50 also gets 400, not a clamp.
- `community-access` includes gated communities that are archived but not deleted, so manager views of archived communities can tag them.

- PUT status to the current status leaves `updated_at` unchanged.
- `getTenantDetail` lists all eight toggleable keys (see Deviation 1).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The tenant detail's module list still iterated `REAL_TENANT_DEFAULT_MODULES`**
- **Found during:** Task 3
- **Issue:** `getTenantDetail` (in `packages/core/server/platform/tenants.ts`, not in the plan's file list) built `modules` from the seven default keys. The panel page reads `enabled` from that list. Once a `super_admin` turned `store` on, the Loja switch would still have rendered off, so the toggle could not be used.
- **Fix:** The detail now maps `TOGGLEABLE_MODULES`, and the unused import was removed. `platform-tenants.test.ts` cases 4, 10 and 13 now expect eight keys with `store` off and the defaults on.
- **Files modified:** packages/core/server/platform/tenants.ts, apps/api/tests/integration/platform-tenants.test.ts
- **Verification:** platform-tenants 47/47 with store; the full integration suite 977/977.
- **Committed in:** 47b54c9

**2. [Rule 1 - Bug] The lab tenant has the communities module off, so the isolation sweep could not create a lab community through the API**
- **Found during:** Task 1 (verify 2)
- **Fix:** The lab community, and later the fresh one for the preview, are inserted through the admin connection. The store reads community rows by SQL whatever that module's flag says.
- **Files modified:** apps/api/tests/integration/isolation.test.ts
- **Committed in:** cafa0c3

**3. [Rule 1 - Bug] P09's "UTF-16 code units" premise does not hold for Zod 4.6**
- **Found during:** Task 2 (P06/P09 through the API)
- **Issue:** Zod 4.6 `.max()` counts code points, so 41 emoji (82 UTF-16 units) passed `max(80)`. The contract comment said the browser `maxLength` and `.max()` count the same unit.
- **Fix:** No behaviour change; this keeps the communities rule, which uses the same Zod calls. The store contract comment now states the real rule: the browser is the stricter side, so the form never sends a value the API refuses. The test pins 80 emoji accepted and 81 refused at the API, and keeps 80 BMP characters accepted and 81 refused.
- **Files modified:** packages/modules/store/contracts/index.ts, apps/api/tests/integration/store.test.ts
- **Committed in:** 51fbd86

**4. [Rule 3 - Blocking] The wizard's switch count was not the Módulos tab's**
- **Found during:** Task 3
- **Issue:** The plan asked to change the spec's switch count to 8. That count (line 301) is the creation wizard's, and the plan also says the wizard keeps its seven default keys.
- **Fix:** The wizard assertion now derives from `REAL_TENANT_DEFAULT_MODULES.length` (7). After creation the spec opens the Módulos tab and asserts `TOGGLEABLE_MODULES.length` (8) switches, with "Ativar ou desativar Loja" visible and unchecked, the description shown, and the `store` row false.
- **Files modified:** apps/web/e2e/platform-tenants.spec.ts
- **Committed in:** 47b54c9

**5. [Rule 2 - Missing critical] `PATCH` used a hand-built patch schema, not `productInputSchema.partial()`**
- **Found during:** Task 1/2 (checked with a Zod probe)
- **Issue:** In Zod 4, `.partial()` keeps defaults, so `{ priceCents }` would have parsed to `description: ''`, `imageAssetId: null`, `communityIds: []`. That would wipe the description and image and unlink every community, which is a silent loss of access for buyers.
- **Fix:** `productPatchSchema` is built from the shared field rules with no defaults. A contract test pins that a price-only patch parses to `{ priceCents }`.
- **Committed in:** 51fbd86

Also, outside the plan's file list: `loading.tsx` (the plan's action names it) and `server/index.ts` (the new exports). The store README also documents the write routes.
