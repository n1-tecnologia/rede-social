# Phase 08.2 Plan 08: Purchase pop-up Summary

**A member taps "Comprar" ("Obter" at R$ 0) on a product page and confirms in a pop-up that uses the app's own confirmation shell. The same panel then turns into "Compra concluída" with the right action for zero, one or several unlocked communities. When the member came from a locked community, the app goes straight back there with a toast. The server action sends only the product id and the price the page showed, and every refusal (price changed, archived, gone, store off, failure) ends on a screen that tells the truth.**

## Decisions Made

- No `revalidatePath` in the purchase action (see Deviation 1).
- The confirm step is built on the server from the product read. The success step is built on the client from the purchase answer, so a first purchase and a replay draw the same thing.
- "A, B e mais 2": the two names come from `Intl.ListFormat` `formatToParts`, and the catalog's "e mais {n}" (which already has its "e") is appended after them.
- `PurchaseDialog` imports `motion/react` for the shell's spring, as the feed and stories module UIs do. It imports nothing from `@rede-social/core`.
- `productPageView` returns `'buy'` only for an active product. An archived product that a non-manager does not hold never reaches the page (404), and it stays `'none'` in the view.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `revalidatePath` in the action closed the dialog before its success step**
- **Found during:** Task 2 (first e2e run)
- **Issue:** The first action called `revalidatePath('/loja')` and `revalidatePath('/loja/{id}')` on success. In Next 16, that re-renders the current page inside the action's response, so "Comprar" (and the dialog it owns) turned into the owned block before "Compra concluída" could show. 6 of 16 purchase cases failed.
- **Fix:** Removed the revalidation, with a comment that explains why. The store pages are dynamic and no router cache keeps them, and the control refreshes the page when the success step closes.
- **Files modified:** apps/web/app/(app)/loja/actions.ts
- **Verification:** `store.spec.ts -g "purchase|browse"` after reset + seed: 31 passed, 1 skipped (the 320px case is phone-only by design).
- **Committed in:** 3f81f0d

**2. [Rule 3 - Blocking] The owned block's id cannot be exported from the client control**
- **Found during:** Task 2
- **Issue:** The server page needs the same id the client control focuses. A value exported from a `'use client'` module reaches a server component as a client reference, not as the string.
- **Fix:** `STORE_OWNED_BLOCK_ID` lives in `lib/store-view.ts`, which both sides import.
- **Committed in:** 3f81f0d

**3. [Rule 2 - Missing critical] `purchaseProduct` also returns `redirect`**
- **Found during:** Task 2
- **Issue:** The plan's union has no case for a 401, a blocked member or a suspended tenant. Without one, those would show the generic inline failure.
- **Fix:** `purchaseProduct` returns `{ status: 'redirect', path }` from `bootstrapRedirectPath`, and the action calls `redirect()` outside any try/catch, which is the `getProduct` and `product-actions.ts` convention. The action's public union stays the plan's five cases.
- **Committed in:** 3f81f0d
