# Phase 08.2: Code Review Report

**Reviewed:** 2026-10-09T03:53:07Z
**Depth:** standard
**Files Reviewed:** 158

## Narrative Findings (AI reviewer)

## Summary

I reviewed the seven migrations and the gate seam first. Then I traced every server path that can return a locked community's content: the feed list, the community feed, getPost, comments, replies, threads, likes, Reels lanes, highlights, playback tokens and the notification fan-out. After that I reviewed the store service, its routes, the web server actions and the UI.

What holds up:
- Tenant isolation inside the definers. Every SECURITY DEFINER function uses `search_path = ''`, fully qualified names and `tenant_id = app.tenant_id()` pinning.
- The purchase path. The amount comes from the product row, the amount is never taken from the client, the partial unique arbiters settle races, and no orphan order is left behind.
- The read-side gate on posts, comments and likes.

Two problems are serious enough to block shipping. Both are ways locked content reaches members who hold no entitlement, without anything showing it:

1. **CR-01.** The table that defines the gate (`store_product_communities`), and the products themselves, can be written by any member through the Supabase Data API. A member can get a raw access token from `/api/realtime/token`. The phase revoked member write privileges on the two ledgers, but not on these two tables.
2. **CR-02.** The known open issue from 08.2-10 is more serious than recorded. It is not only a lost link. The archived community becomes **readable to every member as soon as the save commits**, because archived communities stay readable and the gate no longer covers them.

## Critical Issues

### CR-01: Any member can delete or rewrite community links and products directly through PostgREST, unlocking every paid community

**File:** `supabase/migrations/20261008171623_store.sql:128-129` (with `supabase/migrations/20261008171645_store_functions.sql:67-68`)

**Issue:** `store_product_communities_tenant_isolation` and `store_products_tenant_isolation` are permissive `FOR ALL TO authenticated` policies. Their only predicate is `tenant_id = app.tenant_id()`. Since `20260912031029_app_membership_lookup_and_grants.sql`, `authenticated` holds `select, insert, update, delete` on every `public` table, and `supabase/config.toml` exposes the `public` schema to the Data API. `app.tenant_id()` reads the claim from `request.jwt.claims`, and PostgREST sets that claim from the bearer token.

Any logged-in member can obtain their own raw Supabase access token from `GET /api/realtime/token`. The publishable key is shipped to the page. With those two values, the member can send:

```
DELETE {SUPABASE_URL}/rest/v1/store_product_communities?tenant_id=eq.<their tenant>
PATCH  {SUPABASE_URL}/rest/v1/store_products?id=eq.<id>   {"price_cents":0}   (or {"status":"archived"})
POST   {SUPABASE_URL}/rest/v1/store_product_communities  (link an open community, locking everyone out)
```

Deleting the links empties `app.community_locked_ids()` for the whole tenant, so every paid community and its media opens to every member. It also destroys the admin's configuration. RLS allows all three writes, and the API's `requirePermission('store.product.manage')` is never involved.

The phase recognised this exact threat for the ledgers (`revoke insert, update, delete, truncate … from authenticated`, T-08.2-03). It missed the two tables that actually define the gate. `020-tenant-isolation.sql:1208-1252` only proves cross-tenant writes fail. It never asserts that a member cannot write their own tenant's products or links.

**Fix:** Keep SELECT open to the tenant, and allow writes only for the admin claim. The API's product writes already run in the admin lane, so they keep working:

```sql
drop policy "store_products_tenant_isolation" on public.store_products;
create policy store_products_select on public.store_products for select to authenticated
  using (tenant_id = app.tenant_id());
create policy store_products_admin_write on public.store_products for all to authenticated
  using (tenant_id = app.tenant_id() and app.tenant_role() = 'admin_tenant')
  with check (tenant_id = app.tenant_id() and app.tenant_role() = 'admin_tenant');
-- same split for store_product_communities
revoke truncate on public.store_products, public.store_product_communities from authenticated;
```

The equivalent `pgPolicy` split also has to be made in `packages/modules/store/db/schema.ts`. Add pgTAP negatives in 180: a member-lane `delete`, `update` and `insert` on both tables must affect 0 rows or raise 42501.

Separately, consider removing `public` from the Data API's exposed schemas, because the API is the only data client. As things stand, the same member-token-plus-PostgREST path also reaches `communities`, `feed_posts` and the other `FOR ALL` tables. That broader posture predates this phase, but it now protects paid content.

### CR-02: Editing a product's communities silently drops its links to archived communities and immediately exposes their paid content (08.2-10 open issue, re-rated)

**File:** `packages/modules/store/server/service.ts:587-603` (`replaceLinks`), together with `:113-129` (`resolveCommunities`) and `:131-147` (`linkedCommunities`)

**Issue:** The edit form receives only ACTIVE linked communities (`linkedCommunities` filters `c.status = 'active'`), and `resolveCommunities` refuses archived ids. `replaceLinks` then runs `delete from store_product_communities where product_id = …` with no status filter. So any save that changes the selection deletes the product's links to archived communities.

SUMMARY 08.2-10/12 records this as "drops that archived link", which undersells it:
- `listCommunityFeed` (`packages/modules/feed/server/service.ts:459-470`) serves archived communities to members. It filters only `deleted_at`.
- The P80 rule keeps the normal page for archived communities.
- `NOT_LOCKED` in `listFeed` excludes only communities that are still in `community_locked_ids()`.

So once the link row is gone, the archived community's full post history, comments and media become readable by every member who did not pay. This happens at the commit of an unrelated edit, with no lock warning and nothing shown in the UI. The data loss is also permanent: no UI can re-link an archived community.

**Fix:** In `replaceLinks`, replace only links to communities the form could have listed, and preserve the rest:

```ts
await tx.execute(sql`
  delete from store_product_communities l
   using communities c
   where l.tenant_id = ${ctx.tenantId}::uuid
     and l.product_id = ${productId}::uuid
     and c.id = l.community_id and c.tenant_id = l.tenant_id
     and c.status = 'active' and c.deleted_at is null`);
```

Add an integration test: a product links active C1 and archived C2, a PATCH sets `communityIds: [C3]`, and C2 must still be locked for a non-holder.

## Warnings

### WR-01: A purchase replay answers 409 instead of `owned` after a concurrent archive or price edit

**File:** `supabase/migrations/20261008171645_store_functions.sql:173-188`

**Issue:** `app.store_purchase` checks `archived` and `price_changed` before it checks for an active entitlement. Two cases break the idempotency the header promises ("owned: an active entitlement already exists (idempotent replay, P32)"):
- A member's first request commits, then the admin archives the product or edits its price before the replay (a double tap or a second tab) arrives. The replay answers 409 `unavailable` or `price_changed`.
- A holder calls the endpoint with a stale price.

The client then toasts an error ("price changed" or "unavailable") for a purchase that actually succeeded.

**Fix:** Move step 3 (the "already held" check that returns `owned`) to directly after the product lookup, before the archived and price checks. An existing holder should always get `owned`, whatever the product's current state.

### WR-02: The "lost access mid-session" reaction almost never fires; hidden posts answer a bare 404

**File:** `packages/modules/feed/server/service.ts:1419-1427` (`assertPostInteractive`), with `apps/web/components/feed/FeedSurface.tsx:28-45` and `apps/web/app/(app)/inicio/feed-actions.ts:67-84`

**Issue:** UI-D-376 and the comments on `useCommunityLockedRefusal` describe the case of a member who loses access mid-session (a revoke, or a newly linked product). That member is supposed to get the "esta comunidade agora é exclusiva" toast and a refresh into the locked page.

In practice, after a lock every post of the community except the newest one is hidden by RLS, and `assertPostInteractive` answers those with the bare 404. Only the sample post produces `community_locked`. So liking or commenting on any other card from an already-loaded feed, Reels lane or post page gives a generic error toast and no refresh. The stale card stays on screen, and its comment sheet shows a generic failure.

**Fix:** Either use `app.feed_locked_post_community(postId)` on the RLS miss in `assertPostInteractive` (as `getPost` already does) and answer 403 `community_locked` there too, accepting the same same-tenant disclosure as T-08.2-09. Or treat a 404 on a like or comment as "refresh the route" in the web hosts. Correct the doc comments to match whichever is chosen.

### WR-03: The ledger RLS hard-codes `admin_tenant`, while the routes authorise by `store.product.manage`

**File:** `supabase/migrations/20261008171623_store.sql:126-127`; `packages/modules/store/server/service.ts:451-459, 726-786, 815-900`

**Issue:** The routes gate every manager read on the permission `store.product.manage`. The permission system is designed so tenants can flip values (FEED-08). But `store_entitlements_select_own_or_admin` and `store_orders_select_own_or_admin` admit other users' rows only for the `admin_tenant` claim.

If the permission is ever composed for another role, three reads go wrong without any error:
- `listBuyers` returns `total: 0` and an empty page.
- `holderCount` reads 0.
- `lockPreview` counts every member as "losing access", because the `not exists` over invisible entitlements is always true.

The grant and revoke definers return `forbidden` for such a role, which is at least explicit. The read paths silently give wrong numbers.

**Fix:** Pick one authority. Either assert in `canManageStore` and `requirePermission` that the role is `admin_tenant` (document the permission as admin-only by construction), or move the manager reads into SECURITY DEFINER functions that apply the same check as `store_grant`, so the database and the routes agree.

### WR-04: The pgTAP plan pins are flaky on dead tuples

**File:** `supabase/tests/180-store.sql:587-638` (P41, tests 96-97); also `supabase/tests/090-feed.sql` test 33

**Issue:** These tests assert `InitPlan` and an index scan in the `EXPLAIN` text. 08.2-12 observed `Seq Scan on feed_posts` when about 66k dead tuples from earlier rolled-back volume fixtures were present. Running `supabase test db` twice without a reset fails CI or local gates for reasons unrelated to the code under test. 08.2-12 records this as open, not as accepted.

**Fix:** Run `vacuum analyze public.feed_posts` before the EXPLAIN. `vacuum` cannot run inside the pgTAP transaction, so it has to be a separate pre-step, or the fixture has to be enlarged enough that the index plan wins regardless. Alternatively, assert only the `InitPlan` (the property that matters for correctness) and drop the index-name pin.

## Info

### IN-01: The definer gate helpers accept an arbitrary user or community and are granted to every `authenticated` lane

**File:** `supabase/migrations/20261008171645_store_functions.sql:70-142`

**Issue:** `app.community_locked_ids_for(p_user)` and `app.community_viewer_ids(p_community)` are SECURITY DEFINER and executable by `authenticated`. Any lane that can run SQL can call them to learn which communities another member of the same tenant has bought, or to list every holder of a community. Today only the worker calls them, and the `app` schema is not exposed to PostgREST, so they are not reachable from outside. The exposure is latent.

**Fix:** Grant EXECUTE on these two functions only to the role the worker uses, or make each function return `'{}'` / `null` unless `app.tenant_role()` is a staff claim.

### IN-02: The `community_locked_ids_for` staff branch ignores membership status and block

**File:** `supabase/migrations/20261008171645_store_functions.sql:77-79`

**Issue:** The staff exemption checks only `m.role in ('admin_tenant','support_tenant') and m.deleted_at is null`. It does not check `status = 'active'` or `blocked_at is null`, unlike `community_viewer_ids` and `store_grant`. A blocked admin or support membership is still treated as "sees everything" in the worker's recipient checks.

**Fix:** Add `and m.status = 'active' and m.blocked_at is null` to the staff `not exists` clause.
