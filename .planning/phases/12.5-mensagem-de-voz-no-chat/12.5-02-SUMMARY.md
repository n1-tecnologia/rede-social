# Phase 12.5 Plan 02: Voice recording pipeline in the kernel media broker Summary

**A member or staff user uploads a WebM, MP4 or Ogg take straight to Storage, complete checks its signature, and the existing derive job normalizes it with a boxed-in ffmpeg to one mono AAC audio/mp4 object with an exact stored duration (or rejects it), with no chat code touched.**

## Performance

- **Duration:** 9 min

- **Completed:** 2026-11-17T22:06:00Z
- **Tasks:** 3
- **Files modified:** 7 (2 modified, 5 created)

## Accomplishments

- `startUpload` for the `audio` kind runs a permission check first (`chat.support.contact` for a member, `chat.support` for `support_tenant` and `admin_tenant`), so a refused caller learns no limit and costs no database access. The kernel names the strings and never imports the chat module.
- `completeUpload` reads a 16 byte ranged prefix for `audio`, judges the signature the DECLARED mime demands (EBML at 0, `ftyp` at 4, `OggS` at 0), and leaves the row `processing` with ONE derive job (singleton key = the asset id). A repeated `complete` answers the same body and queues nothing.
- `voice.ts` normalizes in the worker: `execFile` with an argument array, `-nostdin`, `-protocol_whitelist file`, the demuxer (`matroska`, `mov`, `ogg`) and decoder (`opus`, `aac`, `opus`) pinned from the mime, `-vn -sn -dn -map 0:a:0`, 20 s kill, `mkdtemp` removed in `finally`, output capped at 8,000,000 bytes.
- The audio branch of `deriveAssetVariants` overwrites the same `original` key with the normalized object (cache-control 3600) and sets `mime = audio/mp4`, `bytes`, `duration_seconds`, `status = ready`, `ready_at`. A file's fault turns the row `rejected` (`transcode_failed`, `duration_too_long`, `format_mismatch`), removes the object and returns the new outcome `rejected` without throwing; a machine fault throws and the job's retry applies unchanged.
- Evidence for the SUMMARY asks of the plan: ffmpeg and ffprobe 9.0.2; the derive of the 2 second fixture took 443 ms inside the job (the pino line `media.voice_normalized` reports `ms: 443`, 13,396 bytes out of 11,013 in, duration 2); the Range probe passed: `GET /v1/media/{id}/original` answered 302 and a ranged request (`Range: bytes=0-1`) to the signed URL answered 206 with a `content-range: bytes 0-1/...` and a 2 byte body, so the player's seeking is supported by Storage.

## Decisions Made

- Placed `-t 302` as an output option (as the research verified), which bounds the decode just as an input option would and keeps the verified semantics.
- Added `-map_metadata -1` to the ffmpeg arguments so no tag from the recorder (device, software) is carried into the stored file. This is one flag beyond the plan's list, checked against `ffmpeg -h` of 9.0.2 and covered by the real runs.
- The derive branch keeps the signature fallback described in key-decisions: not asked by the plan, needed so a crash after the overwrite does not reject a good take on retry.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The audio signature lookup crashed on a mime named like an Object prototype key**
- **Found during:** Task 2 (the unit test of an unlisted mime)
- **Issue:** `AUDIO_SIGNATURES['constructor']` resolved to `Object.prototype.constructor`, so `inspectAudioSignature` threw a TypeError instead of `format_mismatch`.
- **Fix:** both lookups in `inspect.ts` use `Object.hasOwn`. The same `in` pattern of the older `FILE_SIGNATURES` and `MIME_TO_FORMAT` tables was left alone (out of scope, and the request path refuses an unlisted mime at start before it reaches them).
- **Files modified:** `packages/core/server/media/inspect.ts`
- **Verification:** `media-inspect-audio.test.ts` passes, 9 of 9
- **Committed in:** `60fa67d4`
