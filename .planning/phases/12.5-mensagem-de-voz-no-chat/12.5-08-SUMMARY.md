## How the purge no longer loops on the message foreign key (hand-off answer)

Choice: **keep the row as a tombstone** (not skip, not null the reference, not remove the message). `purgeAsset` removes the Storage objects as before, then tries the row delete; if Postgres refuses it with SQLSTATE `23503` (the `chat_messages.media_asset_id` NO ACTION key) the transaction has already rolled back, so a second admin transaction sets `status = 'failed'`, `failure_reason = 'purged_referenced'` (tenant predicate explicit; `deleted_at` stays set), logs `media.purge.row_kept` at info and returns `{ purged: true, objects }`. Every other error still throws.

Why it works: the sweeper's collector reads only `pending` (older than a day), `deleted` and `rejected`, so a `failed` row is never selected again; the second sweeper run in the integration test changes nothing, and a direct `purgeAsset` on the tombstone returns `{ purged: true, objects: 0 }` instead of throwing. Why it satisfies D-868/D-869: the message row is never touched or deleted (so it stays with its `media_asset_id` and `voice_seconds`), `deleted_at` remains set so the message projection answers `voice.deleted: true` ("Mensagem de voz apagada"), every tenant lane hides the asset, the retired helper answers hidden at once, byte sums skip it, and the bytes are gone. A never-sent deleted recording has no reference and is deleted with its row (asserted beside the sent one in the same sweeper run).
