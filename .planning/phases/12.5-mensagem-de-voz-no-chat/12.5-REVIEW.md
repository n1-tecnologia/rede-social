# Phase 12.5: Code Review Report

**Reviewed:** 2026-11-17
**Depth:** standard

**Status:** issues_found

## Summary

Attention went to the priorities in the order given: the SQL read gate and the seven migrations, the replaced
`app.account_anonymise`, the ffmpeg path and the media service, the two send routes, then the web orchestration,
service worker rule and recorder/player. Test files and fixtures got a quick pass only (no `.only`, `skip`,
`TODO`, `console.log` or secrets found in any changed file).

No blocker was found. The tenant-isolation core holds up:

- `app.account_anonymise` (migration 20261117230638) was diffed against the body in
  `20261105152916_reports_blocks_functions.sql`. The only difference is the one added `voice` statement, scoped by the
  locked row's `tenant_id` and `owner_user_id`. The `revoke`/`grant` pair is restated and matches the original.
- `chat_messages_insert` keeps every earlier predicate and adds the asset clause (own, same tenant, `audio`/`voice`,
  `ready`, not deleted, equal duration). The content CHECK, the single-use partial unique index and the NO ACTION foreign
  key close the "text xor recording" and "one take, one message" rules at the table.
- `app.chat_asset_hidden` is SECURITY INVOKER with `search_path = ''`, fully qualified names and fail-closed handling in
  `serveVariant`. `app.voice_asset_retired` is a tenant-pinned definer that answers one boolean. ACLs revoke PUBLIC and
  grant `authenticated` only. The two sweep and anonymise definers are `service_role`-only (and `api_user` for the
  latter, as before), and each write re-pins the row's own tenant.
- `voice.ts` uses `execFile` with an argument array (no shell), a pinned demuxer and decoder, `-protocol_whitelist file`,
  a SIGKILL timeout, a per-job `mkdtemp` removed in `finally`, an output size cap and an input duration cap. The input
  path is always a generated absolute path, so there is no option injection. ffmpeg's `-enable_drefs` is off by default,
  so a crafted `dref` cannot read local files.
- The member and staff voice sends keep the text refusal order, the idempotent read first, and recover from the
  `23505` of the single-use index in a fresh transaction. Only the call that stored the message emits the event.
- Recorder tracks, timers and the audio element are released on every exit path I could trace.

The three warnings are robustness and behaviour gaps, not leaks. The info items are hardening and maintainability.

## Warnings

### WR-01: A voice send keeps polling and can still post after the member left the screen

**File:** `apps/web/lib/voice-send.ts:196-205`, `apps/web/app/(app)/suporte/ThreadPane.tsx` (`runVoice`, about 805-845)
**Issue:** The pane documents that leaving the screen "loses every take and starts no further send" (UI-D-847, A-UI-10).
`runVoice` only checks `alive()` before the dynamic import and after `runVoiceSend` returns. `runVoiceSend` itself has
no cancellation input. After unmount it keeps calling `deps.send(mediaId)` every 700 ms for up to 20 s while the worker
normalizes. Each call is a server action and an API request. When the asset turns `ready`, the send succeeds and the
support message is stored although the member left the screen believing the take was dropped. The same applies to the
start, PUT and complete stages when the member leaves between them.
**Fix:** Give `runVoiceSend` a cancellation hook and check it before every stage and every loop iteration.
```ts
export interface VoiceSendDeps<T> {
  // ...
  /** True once the caller no longer wants this take sent (the pane unmounted, the take was cleared). */
  cancelled?: () => boolean;
}
// in the loop:
for (;;) {
  if (deps.cancelled?.()) return failed('retriable'); // or a dedicated 'aborted' kind the pane ignores
  const answer = await deps.send(mediaId);
  ...
}
// in ThreadPane runVoice:
voiceSendDeps<VoiceSentOk>(sendAction), { ...deps, cancelled: () => !alive() }
```
If posting after leaving is the intended behaviour (the bytes are already uploaded), change the comment and the
`aliveRef` docblock to say so, so the contract and the code agree.

### WR-02: The purge tombstone swallows every foreign-key refusal of every media kind, not only recordings

**File:** `packages/core/server/media/service.ts:1510-1541` (`purgeAsset`)
**Issue:** The docblock scopes the new branch to "a voice recording a chat message references", but the catch is
`sqlstateOf(error) !== '23503'` for any asset. Any image, file or video whose row is still referenced by another table
now converts to `status = 'failed'`, `failure_reason = 'purged_referenced'` and reports `purged: true`. Before this
change that case threw and was logged as `media.sweep.purge_failed`, which is how an operator would notice a dangling
reference. The objects are already gone at that point in both versions, so no new loss occurs, but a real bug elsewhere
(an asset retired while a feed row still points at it) is now hidden behind an info log and a row that the collector
never visits again.
**Fix:** Restrict the tombstone to the kind that needs it and let everything else throw as before.
```ts
if (sqlstateOf(error) !== '23503' || row.kind !== 'audio') throw error;
```

### WR-03: A voice take that ends in `closed` or `not_found` disappears with no word to the member or the team

**File:** `apps/web/app/(app)/suporte/ThreadPane.tsx` (`failVoice`, last branch, about 893-898)
**Issue:** For `closed` and `not_found` the bubble is removed, the take is deleted from `voiceTakesRef`, and the page
re-reads. No toast, notice or retained draft is shown. A staff member who recorded a reply and meets a case that was just
closed loses the recording silently; the text path in the same pane returns `false`, keeps the draft and shows the
composer error. The blocked and removed branches do toast. The `not_found` word also covers the "no conversation id or
no voice action" fallback in `sendAction`.
**Fix:** Toast a closed-case sentence before dropping the bubble, as the blocked and removed branches do. For example:
```ts
show({ tone: 'error', message: t('composer.errors.failed') });
```
or reuse the existing closed-case copy the staff strip uses. Keep the re-read after it.

## Info

### IN-01: ffmpeg stderr overflow is reported as an infrastructure timeout, so a corrupt file is retried instead of rejected

**File:** `packages/core/server/media/voice.ts:155-168` (`failureOf`), `:142-146` (`EXEC_OPTIONS.maxBuffer`)
**Issue:** `maxBuffer` is 1 MiB. A corrupt or hostile stream can make ffmpeg emit more than that on stderr even at `-v
error`. Node then kills the child and sets `killed`, which `failureOf` reports as "was killed after 20000 ms", an
infrastructure fault. The job retries and finally marks the asset `failed` with `derive_failed` rather than `rejected`
with `transcode_failed`. The member still gets a permanent `voice_invalid`, so the outcome is acceptable, but the retries
and the log message are wrong. Also, no `-threads` cap is passed, so one hostile take can use every core of the worker.
**Fix:** Check `failure.code === 'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'` before the `killed` test and return
`new VoiceNormalizeError('transcode_failed')`. Add `-threads 1` to `buildNormalizeArgs`.

### IN-02: A five-minute recording made in a throttled background tab can be rejected as too long, permanently

**File:** `packages/core/server/media/voice.ts:49` (`VOICE_REJECT_ABOVE_SECONDS = 301`), `packages/modules/chat/ui/useVoiceRecorder.ts:34,256-262`
**Issue:** The recorder stops at 300 s on a 250 ms timer and also on each 1000 ms `dataavailable`. With a foreground tab
the overshoot is below 0.3 s. When timers are throttled, the stop can land up to one full timeslice late, so the take
measures about 301.0 to 301.1 s and the worker answers `duration_too_long`, which the web treats as permanent. The member
loses a full-length take. This needs a tab hidden for the whole recording, so it is rare on a phone.
**Fix:** Either raise the verdict line to 302 and keep `-t 302` as the truncation guard, or truncate to 300 s instead of
rejecting between 300 and 303 s. Keep the strict rejection for clearly longer files.

### IN-03: `GET /v1/media/{id}` still returns a voice recording's metadata to any `admin_tenant`

**File:** `packages/core/server/media/service.ts:726-742` (`getAsset`), compare `:1132-1136` (`listAssets`) and `:953-965` (`deleteAsset`)
**Issue:** D-870 makes a recording private to its conversation. The library listing and the delete path were closed for
`voice`, but `getAsset` still answers an admin for any voice asset id in the tenant (`isOwnerOrAdmin`): file name, size,
status, duration. No bytes are exposed, because `/original` asks the gate. Ids only reach people who can read the
message, and direct and group chats are not live yet, so the exposure is small today but the rule is inconsistent.
**Fix:** In `getAsset`, return the bare 404 when `row.purpose === 'voice'` and `row.ownerUserId !== ctx.userId`.

### IN-04: `useVoiceRecorder.start` leaves `starting` set on one early return

**File:** `packages/modules/chat/ui/useVoiceRecorder.ts:393-397`
**Issue:** When `getUserMedia` resolves with `token === session` but `getOptions().active` is false, the code stops the
stream and returns without `starting = false`. Every later `start` then returns at the `starting || cap` guard until the
component remounts. The `active` effect calls `teardown`, which bumps `session`, so the branch is nearly unreachable
today, but the invariant depends on effect order.
**Fix:** Set `starting = false` before the early return in that branch.

### IN-05: The value 300 (maximum recording seconds) is duplicated in six places

**File:** `packages/contracts/src/media.ts:109` (`VOICE_MAX_SECONDS`), `packages/modules/chat/contracts/index.ts:190` (`CHAT_VOICE_MAX_SECONDS`), `packages/modules/chat/server/notification-copy.ts:~33` (`VOICE_CLOCK_MAX_SECONDS`), `apps/web/lib/chat-view.ts:~110` (`VOICE_MAX_SECONDS`), `packages/modules/chat/ui/useVoiceRecorder.ts:34`, and the `between 1 and 300` CHECK in `20261117220919_chat_voice_messages.sql`
**Issue:** Each copy has its own reason (client-safe import, no contract import in the copy file), and a contract test
pins the media/chat pair, but the other copies are free to drift. `formatVoiceClock` (server) and `formatVoiceDuration`
(web) are also two implementations of one `m:ss` rule.
**Fix:** Add the web `chat-view` and `notification-copy` constants to the existing contract-equality test, or import the
chat contract's constant where client-safety allows.

### IN-06: `docs/DEPLOY.md` account-function diff command prints trailing lines

**File:** `docs/DEPLOY.md` (Phase 12.5 "Read-only check", the `diff <(awk ...)` line)
**Issue:** Both awk extractions stop at `^\$\$;`. The new migration ends the body with `$$` alone (the `-->
statement-breakpoint`, `revoke` and `grant` follow), so the second extraction runs to end of file. The diff then shows
extra `>` lines beyond the one added statement. The "no `<` line" rule still holds, but the instruction "prints only added
lines" reads as "prints only the voice statement", which is not what the owner will see.
**Fix:** Stop the second extraction at `^\$\$$` (or `^\$\$;?$`), or say in the text that the trailing `revoke`/`grant` lines
are expected.
