## Decisions Made

- The invoker body means the chat gate stays correct if a conversation kind or its policy changes, at the price of a definer-free hot path that depends on `chat_messages_select` being cheap (it is an indexed lookup through the conversation policy).
- A voice asset that is hidden is the same 404 for the sender's peer and for a stranger, and the same body as an unknown id (the tests compare bodies without `requestId`).
- Staff cannot play a member's unsent take (it is hidden until a message references it); only the uploader previews it.

## Hand-off for plan 08 (the media sweeper and the foreign key)

Plan 04 noted that `kernel.media-sweep-orphans` hard-deletes `deleted`/`rejected` assets after an hour, and that `chat_messages.media_asset_id` (NO ACTION) would make that delete fail for a referenced voice asset (a failed item, not a crash). After this plan:

- Through the MEDIA API the case is now unreachable: `deleteAsset` refuses voice for every caller, and a message can only reference a `ready` asset (the insert policy), which no kernel path turns into `rejected` later (the provider webhook is video only).
- It remains REACHABLE by the system actions plan 08 owns: the account-deletion step (soft-deletes a recording a message still references) and any hard delete of a referenced row. Once such a recording is soft-deleted, this gate already serves it to nobody (`voice_asset_retired`), but the hourly sweeper's hard delete of the row would fail on the foreign key every hour. **Plan 08 must handle it**: either the sweeper skips (or nulls the reference of) a voice asset a message references, or the account-deletion step removes the message together with the recording in one admin-lane step. This plan changes neither the sweeper nor `purgeAsset`.
