# Phase 05.3 Plan 02: Reels Lanes Read and List-Equality Proof Summary

**`GET /v1/feed/video-communities` gives the Reels lane row its data in one statement: the active communities holding a ready video, in the Comunidades order, capped at 50, and an honest empty list when communities are off. It shares feed's `READY_VIDEO_POST` fragment with the list, so a lane can never open empty. The plan also proves that `?media=video` is exactly Início's ready videos with communities on and off, that it keeps the total order across page boundaries, that it never crosses tenants, and that both reads cost one statement.**

## Accomplishments

- **The lanes read (REELS-04, D-117, D-119, D-120).**
  - `listVideoCommunities(ctx)` reads the `communities` flag before it opens the transaction. With the module off it returns `{ items: [] }`.
  - Otherwise it runs one statement:
    - a constant `ctx.tenantId` on both sides of the `exists`;
    - a literal `c.status = 'active'` plus `deleted_at is null`;
    - `READY_VIDEO_POST` appended inside the `exists`;
    - `order by c.last_activity_at desc, c.id desc limit FEED_VIDEO_COMMUNITIES_CAP`.
  - It logs ids and counts only, never a community name.
  - The route is chained into `feedRoutes` behind `requireAuth, requireModule('feed')`, so `AppType` carries it.
- **Contract.** `FEED_VIDEO_COMMUNITIES_CAP = 50`, plus `videoCommunitiesSchema` (strict, items are `postCommunitySchema`) and its `VideoCommunities` type.
- **Integration battery, reels.test 05.3-4 to 05.3-10:**
  - lane order, and re-ordering after a text post;
  - processing-only and archived communities are absent;
  - every lane opens non-empty;
  - with communities off the lanes are an honest empty list, and turning them on restores the lab lane;
  - equality with Início for demo (on) and lab (off, then on);
  - a `created_at` tie is walked correctly at `limit=1`, and the order is stable;
  - an empty community gives an empty list;
  - the cap.
- **Isolation.**
  - Case b9 uses a lab community that really is a lab lane. Through `?media=video&communityId=` it returns the bare 404, byte-equal (minus `requestId`) to the unknown-id answer. It never appears in the demo lanes. Demo's own lane is the positive control: 200 through both reads.
  - f2's host-mismatch loop now includes the lanes path.
- **Budgets.** `REELS_LIST_STATEMENT_BUDGET = 1` and `REELS_LANES_STATEMENT_BUDGET = 1`, both asserted exactly and with a floor. The lanes read is measured over both the feed tables and the community tables.
- **pgTAP 130, now plan(20):**
  - fact 14: no `Seq Scan on feed_posts` for the verbatim lanes statement;
  - facts 15-16: exactly the 50 active communities, and the 10 archived ones, which do hold ready videos, are absent;
  - facts 17-20: tenant A's community is a real lane in A. Under RLS as V, V's own community is present, A's is absent, and A's statement returns nothing.

## Decisions Made

- **A sibling path, not a parameter.** The lanes read is not a page of posts. It has no cursor, a different item shape, and a different answer with communities off.
- **The other tenant's volume in pgTAP (measured).** See deviation 2.
- **"No Seq Scan" rather than a by-name pin (measured).** The shipped statement is an ordered Index Scan on `feed_posts_tenant_video_created_idx`. With only the literal removed, it becomes a per-community Index Scan on `feed_posts_tenant_community_created_idx`. With only the tenant constant removed, it is a Bitmap Index Scan on the video index. With the correlated tenant form, it is the same Index Scan as shipped. Only when both the tenant predicate and the literal are removed does it become a `Seq Scan on feed_posts` (about 15,700 rows), and fact 14 then fails. The header records all five.
- **The lab flag flip is an upsert with an exact restore.** See deviation 1.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The lab `communities` flag flip did nothing when the row was absent**
- **Found during:** Task 1, on the first RED run. Cases 05.3-6 and 05.3-7 got a 404 from `POST /v1/communities` right after the flip.
- **Issue:** communities.test deletes lab's `communities` row in its `afterAll`, so after a full suite that row is absent rather than disabled, and an `UPDATE` matches nothing.
- **Fix:**
  - `setCommunities` is now an `insert … on conflict do update`.
  - `beforeAll` records the row as found: `null` if absent, otherwise its `enabled` value.
  - `restoreLabCommunities()` puts the row back exactly as found. It runs in every `finally` and again in `afterAll`.
  - Isolation case b9 follows the same rule.
- **Files modified:** `apps/api/tests/integration/reels.test.ts`, `apps/api/tests/integration/isolation.test.ts`.
- **Committed in:** 8429ded and c4bb770.

**2. [Rule 1 - Bug] pgTAP fact 14 was flaky on the planned fixture; 10,000 posts of another tenant were added**
- **Found during:** Task 2, on the first pgTAP run.
- **Issue:** On the planned fixture, V is about 98% of `feed_posts`, and block 3 spreads V's 560 video posts across every heap page. The Seq Scan and the partial-index bitmap therefore cost about the same, and index bloat from rolled-back runs decides between them. Measured:
  - on a fresh `db:reset`, run 1 used the Bitmap Index Scan (index cost 32), run 2 used it too (cost 64), and run 3 chose a `Seq Scan on feed_posts`;
  - growing V's lane posts to 2,000 or 6,000 still seq-scanned in the bloated state;
  - adding 3,000, 5,000 or 10,000 plain posts of tenant B gave a Bitmap Index Scan, a Bitmap Index Scan and an ordered Index Scan, all in that same bloated state.
- **Fix:**
  - Added 10,000 other-tenant posts. `feed_posts` is one table for every tenant, which is exactly why a Seq Scan on it is the wrong plan.
  - The header records the measurements.
  - Fact 14 passed five consecutive runs on an already-bloated database, then again after a fresh reset.
- **Files modified:** `supabase/tests/130-reels.sql`.
- **Committed in:** c4bb770.

**3. [Rule 1 - Bug] pgTAP fixture id collision**
- **Found during:** Task 2.
- **Issue:** Tenant A's post id `…0000000000a1` is hex 161, which is also a lane volume post, so the insert hit `duplicate key … feed_posts_pkey`.
- **Fix:** A's fixture ids now use their own prefixes (`1c00c300`, `1c00f300`, `1c00a300`).
- **Committed in:** c4bb770.

**4. [Interpretation] The lanes fixture's video distribution**
- **Change:** The plan asked for "600 posts, one in ten a ready video". The fixture keeps both numbers, but the 60 video posts are the last 60, exactly one per community.
- **Reason:** Every community, active or archived, then holds a ready video. Fact 16's "exactly the 50 active" and fact 15's "the 10 archived hold ready videos" both follow from that. A `g % 10` spread would have put videos in only 6 communities.

**5. [Interpretation] The path constant in isolation.test**
- **Issue:** The acceptance grep expects the quoted `'/v1/feed/video-communities'` exactly once. Both b9 and f2 use the path.
- **Fix:** The path is named once, as `REELS_LANES_PATH`, and both cases reference it.

**6. [Interpretation] Case 05.3-7 also runs lab with communities ON**
- **Change:** The plan named demo (on) and lab (off). Lab is additionally checked with the flag on, then restored.
- **Reason:** The lab's community video has to be absent when the flag is off and present when it is on. Checking both makes each direction non-vacuous.
