## Warnings

### WR-04: A successful like is forgotten when a later toggle for the same post is refused, so CR-01 comes back on remount

**File:** `apps/web/components/reels/ReelsHost.tsx:712-724`
**Issue:** `trackLike` records an `ok` answer only when its `seq` is still the post's latest (`likeSeq.current.get(postId) === seq`), and it records nothing on a refusal or a rejection. Next runs server actions one at a time on the client, so the requests reach the server in order.

Take a heart tapped twice quickly: like A (`seq` 1), then unlike B (`seq` 2).
1. A reaches the server and succeeds. The host drops it, because `seq` 2 has already been issued.
2. B is refused (a 5xx, a 429 or a network error returns `{ ok: false }`). The host records nothing.
3. The mounted page's engine reverts to B's `previous`, which is A's optimistic pair, so it shows **liked**. That matches the server.
4. The host's map still has no entry, or an older one. When the page leaves ±1 and comes back, or the lane changes and changes back, it remounts from the server's original list view and shows **unliked** with the old count. That is the CR-01 symptom.

The same happens across a remount. A like is in flight from page instance 1, the page remounts (showing the pre-like state), the viewer taps again (`seq` 2), A succeeds and is dropped, and the second request is refused.

Test CR-01 (e) covers only ok followed by ok, so this path is untested.
**Fix:** Keep the last server-confirmed pair per post, and publish it when the latest request settles, whatever the outcome. The mounted page is never re-seeded mid-flight, which is why latest-only was chosen, and a refused latest request still leaves the confirmed pair:
```ts
const confirmed = useRef(new Map<string, LikeState>());

const trackLike = useCallback(
  async (postId: string, nextLiked: boolean): Promise<LikeOutcome> => {
    const seq = (likeSeq.current.get(postId) ?? 0) + 1;
    likeSeq.current.set(postId, seq);
    const publish = () => {
      if (likeSeq.current.get(postId) !== seq) return;       // a newer request will publish
      const settled = confirmed.current.get(postId);
      if (settled) setInteractions((map) => ({ ...map, [postId]: { ...map[postId], like: settled } }));
    };
    try {
      const outcome = nextLiked ? await onLike(postId) : await onUnlike(postId);
      if (outcome.ok) confirmed.current.set(postId, { liked: outcome.liked, likeCount: outcome.likeCount });
      publish();
      return outcome;
    } catch (error) {
      publish();
      throw error;                                           // the engine still reverts
    }
  },
  [onLike, onUnlike],
);
```
Add a CR-01 case: like, then unlike, with the like resolving `ok` and the unlike resolving `{ ok: false }`. Go ±2 and back, and assert that page 0 reads `liked` with count 1.

### WR-05: With the capture-phase release, a second finger's tap on the rail or caption ends the first finger's drag and can change the page or the lane

**File:** `packages/modules/reels/ui/ReelsPager.tsx:334-368,413-414`
**Issue:**
- `origin` stores only `{ x, y }`.
- `onPointerUp` / `onPointerCancel` now run in the stack's capture phase for **every** pointer released anywhere inside the stack, including inside the overlay layer, the rail and the caption.

Before 6ff1ff8, those layers' `stopPropagation` on the bubbling `pointerup` kept a second pointer's release away from the pager. Now, on a phone:
1. Finger 1 rests on the video. The stack's `onPointerDown` sets `origin`.
2. Finger 2 taps the heart. Its `pointerdown` is stopped by the rail, so `origin` is not overwritten.
3. Finger 2's `pointerup` targets the heart (implicit touch capture). The stack's capture handler runs first. It measures finger 2's release point against finger 1's origin, and at the rail's offset from the centre `|dx|` or `|dy|` easily passes `REELS_SWIPE_THRESHOLD_PX`. So `go(index ± 1)` or `onLaneStep` fires.
4. The heart's `click` still fires. One tap therefore both likes and moves to another video or lane.

A second finger's `pointercancel` on the rail also cancels finger 1's drag.

This is a regression the WR-01 fix introduced. It widens IN-04's `isPrimary` gap, which before this plan applied only to a second finger on the media.
**Fix:** Tie the gesture to the pointer that started it:
```tsx
const origin = useRef<{ x: number; y: number; pointerId: number } | null>(null);

const onPointerDown = (event) => {
  if (gesturesDisabled || !event.isPrimary || origin.current) return;
  if (event.pointerType === 'mouse' && event.button !== 0) return;
  origin.current = { x: event.clientX, y: event.clientY, pointerId: event.pointerId };
  setDrag({ active: true, dx: 0, dy: 0 });
};
const onPointerMove = (event) => {
  const start = origin.current;
  if (!start || event.pointerId !== start.pointerId) return;
  …
};
const onPointerUp = (event) => {
  const start = origin.current;
  if (!start || event.pointerId !== start.pointerId) return; // another pointer: not this gesture
  origin.current = null;
  setDrag(IDLE);
  …
};
const onPointerCancel = (event) => {
  if (origin.current && event.pointerId !== origin.current.pointerId) return;
  origin.current = null;
  setDrag(IDLE);
};
```
This also skips the `setDrag(IDLE)` re-render that every rail tap now causes. Add a pager case: `pointerDown` on `media-p0` with `pointerId: 1`, then `pointerUp` on `overlay-p0` with `pointerId: 2` at a far point. Assert that `events` is empty and the drag is still active.

### WR-06: A re-mint that lands after the gesture remounts the page the viewer just activated and restarts it outside the gesture (on WebKit, sound turns off for the visit)

**File:** `apps/web/components/reels/ReelVideo.tsx:319`; `apps/web/components/reels/ReelsHost.tsx:369-382,552-573`
**Issue:** The window effect re-mints every window asset whose token expires within `REELS_TOKEN_REMINT_MARGIN_MS`, including the page that has just become current. Since the fix, a new token remounts `<mux-player>`, and `onController` calls `start(soundOnRef.current)` on the new element because it is the current, unpaused page. That call happens in a promise continuation, not inside the swipe.

Two effects follow:
- **The video restarts.** The one the viewer just swiped to (which `onActivate` started inside the gesture on the old element) goes back to 0 a moment after it began.
- **Sound is lost on WebKit.** With sound on, a new media element's unmuted `play()` outside a user activation is refused. `ReelVideo.play` then re-mutes and calls `onSoundRefused`, which sets `soundOn` to `false` for the rest of the visit. The viewer's sound choice is silently dropped.

When this triggers:
- The viewer stays on one page until the next page's token (checked when that page became a neighbour) crosses the 10-minute margin, then swipes. All tokens from one batch share the same expiry, so any visit longer than about 110 minutes reaches this point.
- The viewer returns to a lane whose first page's token is near expiry. That page starts on `onController` with the old token and then restarts again when the re-mint lands.

This is rare, but it is the fix's own behaviour. The SUMMARY's D5 already marks it `human_judgment: true`.
**Fix:** Never swap the credential of the current page while its held token is still valid. Hold the fresh token and apply it when the page stops being current:
```ts
// in mint(): an asset of the CURRENT page that still has an unexpired token is parked
const currentAsset = state.items[state.index]?.video.assetId;
const heldValid = held && Date.parse(held.expiresAt) > Date.now();
if (outcome.assetId === currentAsset && heldValid) {
  parked.current.set(outcome.assetId, outcome.playback);
  continue;
}
// in the window effect: move parked tokens whose page is no longer current into `tokens`
```
Alternatively, extend the re-mint check to the ±2 ring, so a page is refreshed at least one swipe before it can become current. That still leaves the case where the viewer stays on one page. Keep the phone UAT item open until a real `mux-player` is tested.

### IN-06: A settle that lands between a toggle and React's render re-seeds the mounted page over the newer optimistic state (brief flicker); the docblock says this cannot happen

**File:** `apps/web/components/reels/ReelOverlay.tsx:26-32`; `packages/modules/feed/ui/LikeButton.tsx:63-67`
**Issue:** The docblock says the engine's re-seed "is a no-op on a page that stays mounted". That fails in one window.
1. Request A settles. `setInteractions` is queued at default priority.
2. Before React's default-priority render runs, the viewer taps again. B's optimistic flip is a discrete update and renders first.
3. The default render then sees a new seed. `useOptimisticLike` calls `setState(seed)` unconditionally, so the heart jumps back to A's pair while B is in flight.
4. It corrects itself when B settles.

The window is a few milliseconds, the effect is only visual, and the final state is right.
**Fix:** Correct the docblock. If the flicker matters, skip the re-seed in `useOptimisticLike` while a request is in flight (`requestId` is ahead of the last settled id).

### IN-07: A like still in flight when its page remounts shows the pre-toggle state until it settles

**File:** `apps/web/components/reels/ReelsHost.tsx:712-724,864-881`
**Issue:** The host records a pair only on settle. A page that goes out past ±2 and comes back before its request answers remounts from the old state. A heart tap in that window sends a second, idempotent request. The display corrects itself when the first answer lands. This is harmless, but it is the one remaining gap in "one state per post".
**Fix:** Optional. Record the optimistic target in the host when the request is issued (`{ pending: nextLiked }`), and seed a remounted page from it until the settle replaces it.
