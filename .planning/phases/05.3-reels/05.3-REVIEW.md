## Narrative Findings (AI reviewer)

## Summary

This review covers Reels end to end:
- **API:** the `media=video` filter and `GET /v1/feed/video-communities` in the feed module, `effectiveKeys` in the API registry, and the `reels_module` migration with its backfill.
- **Module package:** `@tria/module-reels` (manifest, constants, props-only UI).
- **Kernel shell:** the media chrome in `@tria/core/ui`.
- **Web tier:** the `/reels` route, its two server actions, `ReelsHost`, `ReelVideo` and `ReelOverlay`.

I diffed every pre-existing file against `ab9a420` and reviewed only the phase's changes to them.

**Tenant isolation holds on every new path I traced.**
- `READY_VIDEO_POST` is appended to the existing `feedPage` predicate. It adds no second query path, so Reels' "Todos" is Início's own predicate plus a narrowing, and a community lane is `listCommunityFeed`'s own predicate (with its visibility check) plus the same narrowing.
- `listVideoCommunities` runs inside `withTenantTx` with a constant `tenant_id` on both sides of the `exists`. Its inner probe runs under RLS on `feed_posts`, `feed_post_media` and `media_assets`, so a lane cannot name another tenant's community, an archived or deleted community, or a community with no post the list would return.
- Both server actions validate their arguments before any request: uuid array `1..3`, nullable uuid, cursor capped at `FEED_MAX_CURSOR_LENGTH`.
- The playback mint goes through the existing `GET /v1/media/{id}/playback`, which answers a foreign asset with a bare 404. An existing action (`configuracoes/midia/actions.ts`) already offers the same capability, so the new action exposes nothing new.
- Credentials never enter the RSC payload and are never logged.

**The module boundary holds.** `@tria/module-reels` depends on `@tria/contracts`, `@tria/core` and `@tria/ui` only, it carries the `module` boundary tag, and no file under it imports another `@tria/module-*`. `effectiveKeys` feeds both the bootstrap and the permission set, so with feed off Reels contributes neither.

**Effect and listener cleanup is sound.** The pager's window keydown listener and non-passive wheel listener are both removed on unmount. So are the rAF pair behind `instantKey`, the host's `visibilitychange` listener and buffering timer, `ReelVideo`'s `MutationObserver`, media listeners and autoplay-check timer, and `DoubleTapHeart`'s two timers. I traced the `suppressResume` flag through every path that sets it (`onActivate`, `selectLane`, `onTogglePause`, `closeSheet`). Each one also flips `effectivePaused` from true to false in the same commit, so the flag is always consumed and never leaks into a later resume.

**One BLOCKER.** A like or comment made in Reels disappears when the viewer swipes two pages away and comes back, or changes lane and comes back. The overlay's like state is local to a component the pager unmounts outside the ±1 window, and the host never writes the result back into its lists. This breaks D-128's "a like in Reels is the same like Início shows" inside Reels itself. On the stale page the rail's heart then sends a like when the viewer means to unlike.

The warnings:
- A mouse drag released over the rail or caption leaves the pager dragging.
- A token re-mint for a mounted page swaps `playback-token` on a live `<mux-player>`, which reloads the source and can freeze the current video with no badge.
- The live region's `{author}` substitution is exposed to `$` replacement patterns.

## Critical Issues

### CR-01: Like state and comment count are lost whenever a Reel's page unmounts and remounts

**File:** `apps/web/components/reels/ReelOverlay.tsx:95-104`, `packages/modules/reels/ui/ReelsPager.tsx:419,429-469`, `apps/web/components/reels/ReelsHost.tsx:235-239,769-786`
**Issue:** `ReelOverlay` holds the page's like state in `useOptimisticLike`, seeded from `view.viewerLiked` / `view.likeCount`, and the comment count in a local `commentDelta`. The pager mounts media and overlay only for `|k - index| <= REELS_MOUNT_RADIUS` (1). Every other page renders `null`, so its `ReelOverlay` unmounts and its state is discarded. Nothing writes the settled like back: the host's `laneStates[*].items` are the server's original `ReelView`s for the whole visit, and `useOptimisticLike` re-seeds only when the seed props change, which they never do here.

Reproduction on a lane with 3 or more videos:
1. Like reel 0 (the heart turns red and the count goes up).
2. Swipe to reel 1, then to reel 2. Reel 0 unmounts.
3. Swipe back to reel 1. Reel 0 remounts from `view.viewerLiked = false` and shows unliked with the old count.

The same happens after switching to a community lane and back, and when the same post appears in both "Todos" and its community lane. The comment count added through the sheet also reverts.

On the stale page the controls then act on the wrong state:
- The rail's heart computes `next.liked = !false` and sends a like while the viewer means to unlike.
- The double tap's `likeOnly` reads `likedRef.current === false` and sends a redundant like.

This contradicts D-128 and REELS-07. None of the 05.3 tests covers a like surviving a remount: the e2e check at `reels.spec.ts:462` only re-reads the post on Início.
**Fix:** Lift the per-post interaction state into the host, keyed by post id, and seed each overlay from it. Alternatively, write every settled like and comment delta back into every lane list that holds the post:
```tsx
// ReelsHost: one map for the visit, keyed by post id
const [likeOverrides, setLikeOverrides] = useState<Record<string, LikeState>>({});
const [commentDeltas, setCommentDeltas] = useState<Record<string, number>>({});

// wrap the actions so the server's authoritative pair is remembered
const onLikeTracked = useCallback(async (postId: string) => {
  const outcome = await onLike(postId);
  if (outcome.ok) setLikeOverrides((m) => ({ ...m, [postId]: { liked: outcome.liked, likeCount: outcome.likeCount } }));
  return outcome;
}, [onLike]);
// …same for onUnlike; the sheet's onCountChange adds to commentDeltas[sheetFor]

// renderOverlay: seed from the override when present
const seed = likeOverrides[view.id];
<ReelOverlay
  view={seed ? { ...view, viewerLiked: seed.liked, likeCount: seed.likeCount,
                 commentCount: view.commentCount + (commentDeltas[view.id] ?? 0) } : view}
  …
/>
```
Because `useOptimisticLike` re-seeds when its seed props change, a remounted overlay (and a mounted one whose seed changed) then shows the last known state. Add a host test: like reel 0, move the index to 2 and back to 1, and assert that reel 0's heart has `aria-pressed="true"`.

## Warnings

### WR-01: A mouse drag released over the rail or the caption leaves the pager stuck in "dragging"

**File:** `packages/modules/reels/ui/ReelsPager.tsx:149-154,327-366,462-465`; `packages/modules/reels/ui/ReelRail.tsx:91-94`; `packages/modules/reels/ui/ReelCaption.tsx:70-75,133-136`
**Issue:** The stack listens for `pointerup` in the bubble phase without pointer capture, and the overlay layer, the rail and the caption all call `stopPropagation()` on `pointerup` and `pointermove`.

Touch is unaffected, because the browser implicitly captures a touch pointer to its `pointerdown` target (the media). A mouse has no implicit capture:
1. A desktop user presses on the video and drags. `origin` is set and `drag.active` is `true`.
2. The user releases over the caption block or the rail, which sit inside the stack. The stack's `onPointerUp` never runs, and `onPointerLeave` does not fire either, because the pointer never left the stack's subtree.
3. `origin.current` stays set and `drag` stays `{ active: true }`. Every later mouse move over the video updates `dy`, so the track follows the cursor (at the rubber-band ratio, with `transition: none`) with no button held, until the next click.

A release over the lower part of the column is the natural end of a downward drag, and the pager explicitly supports mouse drags (`cursor-grab`, `event.button` check).
**Fix:** Decide the gesture in the capture phase. `origin` is set only by a `pointerdown` that reached the stack (one that began on the media), so the overlay's stop rules are unaffected:
```tsx
<div
  data-testid="reels-stack"
  onPointerDown={onPointerDown}
  onPointerMove={onPointerMove}
  onPointerUpCapture={onPointerUp}      // was onPointerUp
  onPointerCancelCapture={onPointerCancel}
  onPointerLeave={onPointerLeave}
>
```
You can also, or instead, ignore `onPointerMove` when `event.buttons === 0` for mouse pointers, which ends a drag that lost its release.

### WR-02: Re-minting a mounted page's token reloads its `<mux-player>` source and can freeze the current video with no badge

**File:** `apps/web/components/reels/ReelsHost.tsx:394-398,496-506`; `apps/web/components/reels/ReelVideo.tsx:183-215,307-314`
**Issue:** On every window change, the window effect re-mints any window asset whose token expires within `REELS_TOKEN_REMINT_MARGIN_MS` (10 minutes of a 2-hour TTL). `mint` stores the new token and bumps `tokenVersion`, and `ReelVideo` passes it to the mounted `<MuxPlayer tokens={…}>`.

In `@mux/mux-video` 0.31.4, a `playback-token` attribute change runs `this.src = H(this)` (`base.mjs`, the `PLAYBACK_TOKEN` case of `attributeChangedCallback`). That runs the media load algorithm, which sets `paused = true` and resets to 0. Two cases follow:
- If the swipe's `play()` is still pending, the `AbortError` retry in `play()` recovers.
- If the page was already playing, nothing re-issues `play()`. `played` is still `true`, so the autoplay check on the next `canplay` returns early. The host still believes the page is playing: no badge, no spinner. The viewer sees a stopped frame and needs two taps (pause, then resume) to recover.

A viewer triggers this by swiping onto a page whose token was minted 110 or more minutes earlier. `onActivate` starts it with the old token, and the re-mint lands a moment later.
**Fix:** Do not replace the credential of a mounted element in place. Only store a re-minted token for an asset whose page is not currently mounted, or key the player on the token so a swap is an explicit remount the controller restarts:
```tsx
// ReelVideo: an explicit remount that the MutationObserver re-attaches and onController restarts
<MuxPlayer key={playback.tokens.playback} … />
```
Alternatively, in `ReelVideo`, listen for `emptied`/`loadstart` and re-issue `play()` when the host has not paused the page (`!hostPaused && propsRef.current.current`).

### WR-03: The live region's `{author}` substitution interprets `$` patterns in a display name

**File:** `packages/modules/reels/ui/ReelsPager.tsx:375-378`
**Issue:** `labels.position.replace('{author}', current.authorName)` passes the member-controlled display name as a replacement **string**, so `$&`, `$$`, `` $` `` and `$'` inside it are expanded. For example, a name containing `$'` splices the rest of the template into the announcement. `ReelOverlay.tsx:150` already guards the same case for `rail.author` with a function replacement. The pager's template is the one spot that does not.
**Fix:**
```ts
labels.position
  .replace('{current}', () => String(index + 1))
  .replace('{author}', () => current.authorName)
```

## Info

### IN-01: Async page loads and mints keep running after the host unmounts and can toast on another screen

**File:** `apps/web/components/reels/ReelsHost.tsx:421-436,472-485,359-407`
**Issue:** `loadMore`, `loadLane` and `mint` continue after `ReelsHost` unmounts. `loadMore`'s failure branch calls `toast.show(...)`, and the `ToastProvider` lives in the persistent `AppShell`. A load-more that fails after the member left Reels therefore shows "Não foi possível carregar mais vídeos." over Início.
**Fix:** Keep an `alive` ref that is set to `false` in an unmount cleanup, and return early from the three continuations when it is `false`.

### IN-02: The rail and caption links are plain `<a>`, so every profile or community tap is a full document load

**File:** `packages/modules/reels/ui/ReelCaption.tsx:138-154`; `packages/modules/reels/ui/ReelRail.tsx:96-102`
**Issue:** UI-D-88 specifies `<Link>` for the author name and the community chip. The module uses plain `<a>` (the same pattern as the feed's `PostHeader`, and documented in 05.3-06-SUMMARY), and the host does not intercept the click. Each tap from Reels reloads the whole shell. Coming back then re-runs the server render, restarts at the top of "Todos" and mints again.
**Fix:** Accept an optional `linkComponent` / `renderLink` prop from the host (the app tier may import `next/link`), or intercept the click in `ReelOverlay` and call `router.push`.

### IN-03: The `reels` flag is enforced only by the page's `notFound()`, not by its server actions or the feed filter

**File:** `apps/web/app/(app)/reels/reels-actions.ts:57-99`; `packages/modules/feed/server/routes.ts:569-571`
**Issue:** With `reels` off and `feed` on, `mintReelPlaybackAction`, `loadReelsPageAction`, `GET /v1/feed?media=video` and `GET /v1/feed/video-communities` all still answer. They expose only data the feed already shows the same member, so there is no leak. The module toggle is advisory for these endpoints, though, which D-121's "no API access" reads more strictly. Record the decision (Reels owns no routes, so its flag gates only the nav and the page), or have the two actions check `bootstrap.modules` for `reels`.
**Fix:** Either note the decision in the module docblock, or add a `requireBootstrap()` check for `reels` at the top of both actions.

### IN-04: Minor input-handling gaps in the pager

**File:** `packages/modules/reels/ui/ReelsPager.tsx:281-285,327-338`
**Issue:**
- `M` has no `event.repeat` guard, so a held key toggles sound many times per second. ↑/↓ and the lane keys already guard against repeat.
- `onPointerDown` / `onPointerMove` do not check `event.isPrimary`. A second finger overwrites `origin`, and the first finger's `pointerup` then measures against the second finger's start point.

**Fix:** Add `if (event.repeat) return;` to the `m`/`M` case. In `onPointerDown`, return early when `!event.isPrimary`, or when `origin.current` is already set.

### IN-05: The partial index is built without `CONCURRENTLY`

**File:** `supabase/migrations/20260926184147_reels_module.sql:29`
**Issue:** `CREATE INDEX "feed_posts_tenant_video_created_idx" ON "feed_posts" …` takes a `SHARE` lock, which blocks writes to `feed_posts` for the duration of the build when Phase 01.1's `supabase db push` applies this migration to the hosted database. At pilot volume this lasts well under a second. The pattern is worth noting before `feed_posts` grows, because Supabase CLI migrations run in a transaction and cannot use `CONCURRENTLY`.
**Fix:** No change is needed for the pilot. For a later index on a large table, ship it as a separate non-transactional step, or build it off-hours.
