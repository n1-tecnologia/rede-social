- **Where `requires` is enforced.** It is enforced in the composition (`effectiveKeys`), not in `requireModule`, because Reels owns no routes. The docblock records that a future module with both routes and `requires` must also teach `requireModule` through a kernel seam (planning decision 7).
- **pgTAP 130 fixture size.** It uses 5,000 posts. The planned 400 was measured to produce a sequential scan; see deviation 5.
- **T-05.3-01 accepted.** `?media=video` answers even with reels off. It only narrows what Início already shows the member.

## Deviations from Plan

### Auto-fixed Issues

**1. [Interpretation] Case 05.3-3 compares error bodies without `error.requestId`**
- **Found during:** Task 1.
- **Issue:** `errorEnvelope` stamps a per-request `requestId` into every error body. As a result, two bodies can never be byte-equal under `JSON.stringify`.
- **Fix:** `requestId` is stripped from both sides before the comparison. `code` and `message` are compared verbatim, and the absence of `details` is asserted.
- **Files modified:** `apps/api/tests/integration/reels.test.ts`
- **Committed in:** 9cb12ae

**2. [Rule 3 - Blocking] `pnpm install` ran in the RED commit**
- **Found during:** Task 1.
- **Issue:** The new package's Vitest could not run until the workspace was linked.
- **Fix:** `pnpm install` ran in RED. The lockfile change is split: the reels importer is in RED 9cb12ae, and the api/web links are in GREEN 21c22bb.
- **Package note:** no external package was added (T-05.3-SC).

**3. [Interpretation] Docblock wording changed so the acceptance grep counts are exact**
- **Found during:** Task 1.
- **Issue:** Prose in the docblocks of `modules.ts` and `reels/module.ts` inflated the counts that the acceptance greps check (`'reels'`, `routes:`).
- **Fix:** The prose was reworded so each grep counts only the code.
- **Committed in:** 21c22bb

**4. [Interpretation] `feedPage`'s third parameter was renamed `predicate`**
- **Found during:** Task 1. The plan explicitly allowed this rename.
- **Change:** `READY_VIDEO_POST` is applied through `mediaPredicate(query)` in both `listFeed` and `listCommunityFeed`.
- **Committed in:** 21c22bb

**5. [Rule 1 - Bug] pgTAP 130's 'Todos' plan fixture was scaled from 400 to 5,000 posts**
- **Found during:** Task 3, on the first pgTAP run. Facts 10-13 failed.
- **Issue:**
  - At 400 posts, with the real `READY_VIDEO_POST` `exists`, the planner chose `Hash Semi Join` over a `Seq Scan on feed_posts`. It estimates the semi-join at about a tenth of the video rows, so the LIMIT promises no early exit.
  - The planning probe that recorded "600 posts chose the index" evidently did not include the `exists`.
  - Rolled-back probes measured a Seq Scan at 400, 600, 1,000 and 3,000 posts on a clean heap.
  - The partial index won from about 4,000 posts (a Bitmap Index Scan).
  - At 5,000 and 10,000 posts it was an ordered Index Scan feeding a Nested Loop Semi Join through `feed_post_media_video_uq`, for both the communities-on and communities-off statements.
  - Local probes also bloat `feed_posts`, and that bloat shifts the choice. A `vacuum full analyze` of the three tables restored a clean heap for the probes; it changes no data.
- **Fix:** The fixture is now 5,000 posts with 500 ready videos. The header records the measurement and the reason, so the by-name assertion is both true and falsifiable.
- **Stability:** The test passed on 4 consecutive runs as dead tuples accumulated, and again on a fresh `db:reset`.
- **Files modified:** `supabase/tests/130-reels.sql`
- **Committed in:** 996cbce

**6. [Interpretation] The case h comment no longer says case c depends on the lab tenant**
- **Found during:** Task 3.
- **Issue:** The plan asked the comment to say "case c still depends on lab's `communities` being off". In fact, isolation case c uses its own no-feed tenant.
- **Fix:** The comment now states the truth. Lab keeps `communities`, `chat` and `notifications` off for its disabled-module role in modules.test cases 4-8 and 13, and case c uses its own tenant.
- **Committed in:** 996cbce

**7. [Interpretation] The `newTenantBody` fixture in platform-tenants.test now includes `'reels'`**
- **Found during:** Task 3.
- **Issue:** The default fixture means "created with every real module". Cases 10, 12 and 13 assert that every module is enabled, which would be false with seven rows and six keys.
- **Fix:** `'reels'` was added to the fixture, following the plan's own rule ("unless the fixture itself now includes `reels`").
- **Unchanged:** The service fixture that was created with an explicit `['feed', 'events']` keeps its pins.
- **Committed in:** 996cbce
