# Phase 05.3: Reels - Research

**Researched:** 2026-09-26
**Domain:** Full-screen vertical video pager over the feed (Next.js 16 + Mux player + Hono/Drizzle feed contract), a new toggleable module key, media chrome in the kernel shell
**Confidence:** MEDIUM-HIGH (codebase facts HIGH; iOS gesture/autoplay behaviour MEDIUM/LOW, real-device only)

## Summary

Reels is a view over data that already exists. Every page is a `feed_posts` row with `media_kind = 'video'` whose video asset is `ready`. The main risk is the architecture boundary, not the data. `turbo boundaries` denies every `module -> module` package edge (`turbo.json` tag rule `"module": { "dependencies": { "allow": ["kernel", "contracts", "tooling"] } }`). A `packages/modules/reels` server therefore **cannot import `@tria/module-feed`**, and a Reels-owned list route would have to duplicate `postProjection`, which D-73 forbids. The recommended placement is a **feed-owned video filter**: `GET /v1/feed?media=video[&communityId=]` through the existing `feedPage`, plus one feed-owned read for the lanes, `GET /v1/feed/video-communities`. The `reels` package then holds the manifest (key, nav, `chrome: 'media'`, `requires: ['feed']`), the props-only pager UI and a few constants. It has no DB and no server routes. Phase 9's follower visibility will then land in one predicate, and Reels and its lanes inherit it.

Playback is the second risk. Three facts drive the design. (1) WebKit allows muted inline autoplay, but sound needs `play()` to run directly inside a `touchend`/`click`/`keydown` handler [CITED: webkit.org/blog/6784]. A React effect runs too late. (2) Next.js dispatches Server Actions **one at a time per client** [VERIFIED: apps/web/node_modules/next/dist/docs/01-app/02-guides/server-actions.md:28-30]. Minting ±1 neighbour tokens with the existing single-asset `fetchPlaybackTokenAction` would queue behind likes and load-more calls. (3) media-chrome, which ships inside the installed `@mux/mux-player@3.13.4`, persists a `media-chrome-pref-muted` localStorage flag and re-applies it to any element that starts unmuted [VERIFIED: node_modules/.pnpm/media-chrome@4.19.2*/dist/media-store/state-mediator.js:158-205]. That would silently break D-126 unless Reels sets `noMutedPref`.

Nothing here needs a new npm package. `@mux/mux-player-react@3.13.4`, `motion@13.3.0` and `lucide-react@1.46.0` are already installed. The module flag needs one migration (widen `tenant_modules_key_chk` and backfill enabled rows), plus one optional partial index for the video list. Adding a tab breaks at least 8 existing test files that pin nav lists or module-key lists. The e2e suite runs `VIDEO_PROVIDER=fake` with Chromium, which cannot prove real playback. Automated proof covers the DOM contract, the data and the gestures. iOS autoplay and sound are phone-UAT items, blocked until Phase 01.1.

**Primary recommendation:** put the video filter and the lane read in **feed's** published HTTP contract. Make `@tria/module-reels` a manifest plus props-only UI package. Gate "requires feed" in the API registry's bootstrap/permission composition. Mint neighbour tokens with **one batched server action**. Drive `play()` imperatively, synchronously inside the gesture handler, with `noMutedPref`/`noVolumePref`/`nohotkeys` and `--controls: none` on the player.

## User Constraints (from CONTEXT.md)

### Locked Decisions
#### Lanes (the top row)
- **D-117:** **The print's lanes ("Para você / Resultados / Bastidores") become "Todos" plus one lane per community.** The first lane holds every video Reels can show. After it comes one lane per community, each holding that community's videos. A horizontal swipe changes lane and a vertical swipe changes video; the dominant axis decides, so one gesture never does both (the prototype's rule). Tapping a lane label also selects it. This uses data that already exists: the chip "Energia de Rainha" in the print is already a community. Admin-chosen tags were considered and rejected for the MVP because they need a new field in the composer and a per-tenant tag list.
- **D-118:** **The first lane is labelled "Todos"**, not "Para você". It is not personalised, and "Para você" would promise a recommendation that does not exist.
- **D-119:** **A community gets a lane only if it is active and has at least one ready video post.** Lanes follow the **Comunidades list order**: most recent post activity first (D-76). Archived communities never get a lane, and no lane is ever empty. When the `communities` module is off there are no community lanes (D-74 applies to "Todos" as well: only posts without a community).
- **D-120:** **When "Todos" is the only lane, the lane row is hidden.** The top shows only the sound button. This covers two cases: no community has a video, or the `communities` module is off. A lone lane is noise, not a choice.

#### The tab and its module flag
- **D-121:** **Reels is its own feature module (`reels`), toggled per tenant by `super_admin` like Comunidades and Eventos (MOD-01, MOD-04, ROLE-04).** It requires `feed`: with `feed` off, Reels contributes nothing (no tab, no API access), whatever its own flag says. It reads posts through feed's published contract, never feed internals (MOD-02); how that query is exposed is a research/planning question (see Claude's Discretion). A tenant that never posts video can hide the tab. — **Reversibility:** costly — the new module key lands in the `tenant_modules_key_chk` check constraint through a migration, in the API and web registries and in the registry test lists; folding Reels back into `feed` later needs a second migration and every consumer of the key.
- **D-122:** **The module is on by default for new and existing tenants.** It is the same default as `feed`, and because Reels is in the MVP, the pilot gets it without a `super_admin` step. `super_admin` turns it off where it makes no sense.
- **D-123:** **The tab is called "Reels" with the print's film-reel icon, and it sits between Comunidades and Eventos**, the print's order. With every module on, the tabs read Início · Comunidades · Reels · Eventos · Perfil. Communities is `order: 20` and Phase 6 plans Eventos at `order: 40` (`06-01-PLAN.md` expects "any tab 05.3 added below 40"), so Reels takes an order between them. The label comes from the catalog (`reels.nav`, PWA-03). Navigation is driven by the module flag, never by data (D-40, D-77): with zero videos the tab stays and shows the empty state.
- **D-124:** **A feed video gets no path into Reels.** A video on Início keeps playing inside its card exactly as today, and Reels is reached only from its tab. Nothing in `PostMedia` or the feed's player changes in this phase.

#### Playback
- **D-125:** **A video loops until the viewer swipes**, like Instagram Reels and TikTok. Moving on is always the viewer's choice; Reels never auto-advances (that is the stories behaviour, not this one).
- **D-126:** **Sound starts off, and once turned on it stays on for every later video and lane until the viewer leaves Reels.** Every new visit to the tab starts muted again, because iOS only lets a video start by itself when it is muted. This is the same rule as the story viewer, which starts `muted: true` for exactly this reason. The choice is not persisted across visits.
- **D-127:** **A single tap pauses and resumes.** While paused, a play icon sits in the centre. The sound button in the top corner is the only sound control.
- **D-128:** **A double tap likes the post**, with the heart overlay the feed's photos already use (`DoubleTapHeart` in `@tria/ui`). It only ever likes, never unlikes, and it writes the same like as the rail's heart. The known cost is accepted: the single-tap pause waits about 250 ms so the two gestures are not confused.

#### The rail, the caption and desktop
- **D-129:** **The avatar and the author's name open the author's profile (D-52), and the community chip opens the community page (D-71).** These are the same destinations as the feed card. A video with no community shows no chip.
- **D-130:** **The rail gains the feed's share button, below comment.** It is the same share as the card: the native share sheet, or copy link on desktop, producing the FEED-07 internal deep link that opens the post after login. The print has no share button; it is added because the feed has three actions and a video is the most shareable content.
- **D-131:** **A long caption is clamped to 2 lines with "… mais".** A tap expands it over a darker veil without pausing the video, and another tap collapses it. Links in the caption stay clickable. This is the feed's `PostCaption` behaviour in a new container.
- **D-132:** **On desktop, Reels is a centred 9:16 column on a dark ground, and the desktop rail stays visible.** The lanes, the rail and the caption live inside the column. Changing video works through on-screen ↑/↓ buttons, the keyboard (↑/↓ change video, Space pauses, M toggles sound) and the mouse wheel.

#### Carried forward (not re-asked)
- D-53: one post is one Reels page (gallery XOR video).
- D-73 / D-74: "Todos" shows exactly the videos Início shows: tenant-wide posts plus posts from visible communities, or only posts without a community when `communities` is off. Order is newest first (roadmap criterion 3).
- D-59 / D-62: comments open the feed's one `CommentSheet` in its threaded variant, with replies and comment likes (these are feed posts, not stories). The video pauses while the sheet is open, as the story viewer does (D-82).
- D-43 / D-44: playback goes through Mux with a signed policy and a short-lived per-request playback token.
- D-33: surfaces the prototype does not cover go through a UI-SPEC and mockup approval before they are coded. Here that means lanes as communities, the share button on the rail, the caption expansion, the empty state and the desktop column.
- The prototype hides the TopBar on `/reels` and floats the BottomNav over the video ("media" mode, PROTOTYPE.md). The print shows the same.

### Claude's Discretion
These were offered to the user as defaults and accepted without discussion. Downstream agents may refine them, but should not reverse them without asking.
- **Only `ready` videos appear.** A video post still transcoding or refused (feed allows publishing during transcode, D-53) is skipped. It appears once its transcode is ready.
- **Empty state:** with no video in any lane, Reels shows the ported `EmptyState` with pt-BR copy, and the tab stays (D-123). The copy comes from the UI-SPEC.
- **Changing lane starts at that lane's first (newest) video**, as the prototype does.
- **Where a returning viewer lands:** each visit starts at the top of "Todos". Resuming the last position is not required.
- **No admin "…" menu inside Reels.** Edit and delete stay on the feed card and the post page (FEED-03).
- **The position indicator** on the right edge (the print's dots) must work with a keyset-paged, open-ended list. A windowed indicator around the current page is fine, since a dot per item is not.
- **Paging and preloading:** keyset pages on the feed's existing cursor convention, with the neighbouring pages kept mounted (the prototype mounts ±1). Preloading the next video, including fetching its signed playback token ahead of time, is a research item ("Research needed: light", ROADMAP).
- **Where the video query lives** under MOD-02: a `mediaKind`/video filter on feed's published list contract (`feedPage` already takes an extra predicate) versus a Reels-owned route that calls feed's contract. The community-lane list (active communities with a ready video, in D-76 order) needs the same kind of decision across the `communities` contract.

### Deferred Ideas (OUT OF SCOPE)
- **Admin-defined lanes/tags** (the prototype's "Resultados / Bastidores" as tags chosen at posting time): rejected for the MVP in favour of community lanes (D-117). Revisit if the pilot admin asks for content categories that cut across communities.
- **Personalised "Para você" ordering**: a recommendation feed. It needs signals V1 does not collect.
- **Opening a feed video in Reels** (a full-screen button on the card that lands on that video): declined for this phase (D-124).
- **Member videos in Reels, visible to followers**: Phase 9, "Rede social" (roadmap criterion 3).
- **Remembering the sound choice across visits**: declined (D-126), because the browser may block autoplay with sound on the next visit.

## Project Constraints (from CLAUDE.md)

- **All business logic goes through the Hono API.** The browser talks to Supabase only for Auth via `@supabase/ssr` and for read-only Realtime Broadcast. Reels fetches pages and lanes through the API (`apiFetch`) and never uses `@supabase/supabase-js` in the browser.
- **Modularity (MOD-01..05).** Each feature is a self-contained package that depends only on the kernel and on other modules' published contracts. It is toggled per tenant. `turbo boundaries` and Biome `noRestrictedImports` enforce this (see `biome.json`: modules may not import `@tria/module-*/server/*`, `@tria/core/db`, or `@tria/api`).
- **Design.** Components are ported from `reference/frontend-design/`, not refactored in place. D-33 requires a sketch plus design review before coding prototype-less surfaces.
- **Infra.** Supabase Free plan in the pilot, so there are no image transforms. Video goes through Mux (dev: `VIDEO_PROVIDER=fake`).
- **Multi-tenant RLS / defense in depth.** Tenant requests run under `api_user` with `withTenantTx`, and cross-tenant misses are a bare 404 (D-23).
- **pt-BR UI.** Every string lives in `apps/web/messages/pt-BR/*.json`. `scripts/check-ui-literals.sh` fails the build on hex colours or pt-BR text inside `.tsx`.
- **Stack pins.** Next.js 16.3 (installed 16.3.5, React 19.3), TypeScript 7, Biome 2.5.13 (no ESLint), Vitest 5, Playwright 1.63, pnpm 12, Turborepo 2.10.12, Node 24.
- **`apps/web/AGENTS.md`:** "This is NOT the Next.js you know… Read the relevant guide in `node_modules/next/dist/docs/` before writing any code." Plans touching Next must cite the local docs.
- **GSD workflow:** file edits happen through GSD commands. Execution in this repo is sequential (no git remote, `ISOLATION=none`), and gate builds use `TURBO_CACHE=local:r` (project memory).
- **Migrations:** Drizzle schema → `pnpm db:generate` → `supabase/migrations` → Supabase CLI applies. Never `drizzle-kit migrate`. Every new table needs RLS plus pgTAP cross-tenant negatives.

### Pattern 1: The video filter on feed's ONE keyset builder (MOD-02 recommendation)
**What:** Extend `feedQuerySchema` with `media: z.enum(['video']).optional()`. Build the predicate inside feed and concatenate it with the existing community predicate in `feedPage`. `listFeed` and `listCommunityFeed` both honour it, so "Todos" (communities on and off) and each community lane come from the same function Início uses.
**Why feed and not reels:**
1. `turbo.json` denies module→module dependencies, so the reels server cannot call `listFeed` [VERIFIED: turbo.json boundaries block].
2. D-73's "one query, one ordering expression" [VERIFIED: packages/modules/feed/server/service.ts:258-266 docblock].

### Pattern 4: Playback control (ReelVideo), following StoryVideo
Base it on `StoryVideo`'s proven bridge [VERIFIED: apps/web/components/stories/StoryVideo.tsx:127-199]:
- A `MutationObserver` attaches to the late-mounted `mux-player`, because `next/dynamic` does not forward refs.

Then add the following changes.
- **Props on `<MuxPlayer>`:**
  - `playbackId`, `tokens`, `streamType="on-demand"`, `playsInline`, `loop`, `nohotkeys`, `noMutedPref`, `noVolumePref`, and **no `autoPlay`**.
  - `preload={isCurrent ? 'auto' : 'metadata'}`.
  - `style={{ '--controls': 'none', '--media-object-fit': fit }}`, where `fit` is `cover` when `width/height ≤ 0.8`, otherwise `contain` (UI-D-83).
  - `--controls: none` hides every control [CITED: mux.com/docs/guides/player-customize-look-and-feel]. `--media-object-fit` is read by `custom-media-element` as `object-fit: var(--media-object-fit, contain)` [VERIFIED: node_modules/.pnpm/custom-media-element@1.4.6/…/custom-media-element.js]. Note: StoryVideo's `className="object-contain"` has **no effect** on the inner `<video>` (object-fit is not inherited). Use the CSS variable.
- **Why `noMutedPref`:** media-chrome's `stateOwnersUpdateHandlers` reads `localStorage['media-chrome-pref-muted']`. When an element is **not** muted and no `noMutedPref` is set, it forces `muted = pref` [VERIFIED: media-chrome@4.19.2 dist/media-store/state-mediator.js:188-205]. A member who once muted a feed card (the feed's `VideoPlayer` shows the default controls) has `"true"` stored. With sound on in Reels, every new page would then be re-muted. `nohotkeys` stops the controller's own Space/`m`/arrow handling [VERIFIED: media-controller.js:509-561] from racing the route's keyboard map.
- **Imperative play, one code path:**
```ts
// Called SYNCHRONOUSLY from the pager's gesture handler for the page being activated,
// and from an effect only as a fallback (initial mount, sheet close, visibility return).
function start(el: PlayableElement, wantSound: boolean) {
  el.currentTime = 0;                 // UI-D-92: a page returned to restarts from 0
  el.muted = !wantSound;
  const p = el.play?.();
  p?.catch((err: DOMException) => {
    if (err?.name === 'AbortError') return;          // interrupted by a fast swipe/pause — not a refusal
    if (err?.name === 'NotAllowedError' && !el.muted) {
      el.muted = true; onSoundRefused();              // flip the route's soundOn to false (UI-D-85)
      el.play?.()?.catch(() => onBlocked());          // muted also refused → play badge (Low Power Mode)
      return;
    }
    onBlocked();
  });
}
```
The story viewer's `autoplayCheckMs` idea (no `playing` within ~400 ms of `canplay` → badge) is kept as a second detector, because Low Power Mode can leave `play()` pending rather than rejecting [VERIFIED: packages/modules/stories/ui/StoryViewer.tsx:534-545; default `autoplayCheckMs = 400` at :273].
- **Pause sources:** the single tap, Space, the sheet being open, and `document.visibilityState === 'hidden'`. The story viewer's OR-ed boolean is the model [VERIFIED: StoryViewer.tsx:335-344, 507-512]. Resume only when the viewer has not paused.

### Pattern 5: Neighbour preloading and token pre-mint
- **Mount window:** `|k − i| ≤ 1` renders `ReelVideo`. Anything farther renders an empty black box, so hls.js buffers are released on unmount.
- **Preload semantics (verified in the installed playback-core):**
  - `preload="none"` defers `loadSource` until `play`.
  - `"metadata"` loads the manifest with `maxBufferLength = 1`.
  - `"auto"` uses the full buffer. The first `play` restores the full buffer [VERIFIED: @mux/playback-core@0.35.4 dist/index.mjs, function `Oe`].
  - Neighbours therefore cost a manifest plus ~1 s of segments on Android/desktop.
- **iOS ignores preload.** Mobile Safari downloads nothing until playback starts [CITED: developer.apple.com Safari "iOS-Specific Considerations"; muxinc/elements#963, "even with preload='auto' the chunks are never downloaded", closed with no fix]. On iPhone the swipe lands on the Mux **poster** (thumbnail token, `thumbnailTime` default 0), then the first frame after a short buffer. The UI-D-92 "no black flash" backstop can only be judged on a real iPhone with real Mux. Locally the fake tokens are not JWTs, so the player declines to build a poster [VERIFIED: apps/web/components/media/VideoPlayer.tsx:60-67 docblock], and the frame is black.
- **Token TTL vs dwell:** `PLAYBACK_TOKEN_TTL_SECONDS = 2 * 60 * 60` [VERIFIED: packages/contracts/src/media.ts:193] against a 300 s maximum post video. Keep a visit-scoped in-memory map `assetId → { tokens, expiresAt }`. Re-mint only on a player error, on retry (UI-D-93b), or when `expiresAt − now < 10 min` [ASSUMED threshold]. The map never goes to storage, a cookie, the router cache or a log (D-44, T-05-34).
- **Sequential dispatch:** Next dispatches Server Actions one at a time per client and recommends doing parallel work inside a single action [VERIFIED: apps/web/node_modules/next/dist/docs/01-app/02-guides/server-actions.md:26-32].
  - Build `mintReelPlaybackAction(assetIds: string[])`, bounded to 3 and uuid-validated. It calls `getPlaybackTokens` with `Promise.all` and follows `fetchPlaybackTokenAction`'s refusal path (409 → `notReady`, 401/403 → redirect) [VERIFIED: apps/web/app/(app)/configuracoes/midia/actions.ts:75-95].
  - Call it once per window change for the assets that have no token yet.
  - Drop stale results with a generation counter.
  - Likes during fast swiping still queue behind mints. This is accepted: the like is optimistic, so the UI never waits.
- **Next page** at `i ≥ loaded − 2` through `loadReelsPageAction(lane, cursor)`.

### Pattern 6: Gesture grammar (ported, with three fixes)
Keep the prototype's rule [VERIFIED: reference/frontend-design/app/(app)/reels/page.tsx:34 `const LIMIAR = 60;`, :90-98 dominant axis, :124-130 transform/transition]. Change three things:
1. **`pointercancel` resets without navigating.** The prototype maps `onPointerCancel={onUp}` [VERIFIED: page.tsx:117], so an OS-cancelled gesture (edge swipe, scroll takeover) can still change video.
2. **No `setPointerCapture` on an ancestor of `DoubleTapHeart`.** With capture, `pointerup` targets the capturing element and the child wrapper's `onPointerUp` never runs. `DoubleTapHeart` only listens to `onPointerUp` today [VERIFIED: packages/ui/src/overlays/DoubleTapHeart.tsx:45-63]. The `tapSlopPx` extension must also add an `onPointerDown` to record the origin.
3. **Wheel** needs a native `addEventListener('wheel', h, { passive: false })`, because React's root wheel listener is passive and `preventDefault` would be ignored [ASSUMED: React 17+ behaviour]. Accumulate to ±50 and lock for 600 ms (UI-D-95).
- **Single versus double tap:** the shipped window is `DOUBLE_TAP_WINDOW_MS = 300` [VERIFIED: DoubleTapHeart.tsx:17]. `onSingleTap` fires when it expires. The resume `play()` then runs from a timer, not a gesture. That is fine: the element was already playing, or is muted, and muted play needs no gesture [CITED: webkit.org/blog/6784]. A sound-on resume after a long pause could be refused. The Pattern 4 fallback covers it.

### Anti-Patterns to Avoid
- **A Reels server package that re-implements `postProjection`.** That is two projections, the drift D-73 forbids. The module→module import is also blocked by `turbo boundaries`.
- **A pathname check (`/reels`) in `@tria/core/ui`.** It couples the kernel to a module (UI-D-81). Use the nav entry's `chrome`.
- **Embedding playback tokens in the `/reels` RSC payload.** It is cacheable (router cache, back/forward reuse) and outlives the request (D-44, T-05-34).
- **`Promise.all` over several `fetchPlaybackTokenAction` calls from the client.** They serialize anyway, so the parallelism is illusory.
- **Treating `AbortError` from `play()` as "blocked".** Every fast swipe would flash the play badge.
- **Relying on `className="object-cover"` on `<MuxPlayer>`.** It has no effect on the inner video. Use `--media-object-fit`.
- **Using the prototype's hex/`#fff` literals.** `check-ui-literals.sh` fails `.tsx` hex colours. Use `white`/`black` alpha utilities.

## Common Pitfalls

### Pitfall 1: Sound-on does not survive a swipe on iOS
**What goes wrong:** after "Ativar som", the next video starts muted or does not start.
**Why:** WebKit needs `play()` with sound to "directly result from a handler for a touchend, click, doubleclick, or keydown event" [CITED: webkit.org/blog/6784]. Setting React state in `pointerup` and calling `play()` in an effect is one task too late. The story viewer documents the same trap for its badge [VERIFIED: StoryViewer.tsx:100-102 "Called SYNCHRONOUSLY inside the play badge's click handler"]. `pointerup` is not in WebKit's published list, though the HTML spec treats non-mouse `pointerup` as activation-triggering [CITED: html.spec.whatwg.org activation-triggering-input-event].
**How to avoid:**
- Have the pager call a host-supplied `onActivate(k)` synchronously from the gesture handler.
- Have the host call `start(el, soundOn)` on the neighbour's already-mounted element.
- On touch devices, also re-issue the same idempotent call from a native `touchend` listener on the stage [ASSUMED: needed on iOS; a real-device check decides].
- The NotAllowedError fallback (Pattern 4) guarantees "sound on" never means "nothing plays".
**Warning signs:** the sound icon flips back to muted after every swipe on a phone.

### Pitfall 2: A stale muted preference re-mutes Reels
**What goes wrong:** sound is on, yet each new page plays muted, on some devices only.
**Why:** see Pattern 4 (`media-chrome-pref-muted`).
**How to avoid:** `noMutedPref` and `noVolumePref` on every Reels `<MuxPlayer>`. Unit-test that the props are passed.

### Pitfall 3: Token mints queue behind other actions
**What goes wrong:** a swipe lands on a black page for seconds while a like or load-more is in flight.
**Why:** Server Actions dispatch sequentially per client [VERIFIED: local Next docs].
**How to avoid:** one batched mint action per window change, fired **before** the load-more when both are due. The generation guard drops stale results.

### Pitfall 4: `play()` promise noise
**What goes wrong:** the play badge flashes on fast swipes, or Low Power Mode shows nothing.
**How to avoid:** ignore `AbortError`, handle `NotAllowedError`, and keep the 400 ms `canplay→playing` check for the silent-pending case.

### Pitfall 5: Adding a tab breaks pinned lists across the suite
**What goes wrong:** a green phase, then red e2e and integration runs everywhere.

### Pitfall 6: `requires` enforced in only one place
**What goes wrong:** feed off plus reels on shows a Reels tab that 404s, or grants a permission the module no longer offers.
**How to avoid:** apply `effectiveKeys()` inside `enabledModulesForBootstrap` **and** `permissionsFor`. Unit-test "reels enabled + feed disabled → no reels entry".

### Pitfall 7: The lanes' `exists` subquery and the list predicate drift
**What goes wrong:** a lane appears but opens empty, violating D-119's "no lane is ever empty".
**How to avoid:** both live in `packages/modules/feed/server/service.ts` and share one SQL fragment for "ready video post". An integration test asserts: for every lane, `GET /v1/feed?media=video&communityId=<lane>` returns ≥1 item.

### Pitfall 8: Seed content changes shift pinned feed counts
`seededFeedPaging.total: 33` and the page-1/page-2 filler captions are pinned [VERIFIED: apps/web/e2e/fixtures.ts:50-67]. Community post counts are pinned too. Create Reels fixtures **per spec** instead of changing the seed. The seed changes only its module flags: demo picks `reels` up automatically through `REAL_TENANT_DEFAULT_MODULES` [VERIFIED: scripts/seed.ts:142]; lab's `modules: ['feed', 'events']` [VERIFIED: seed.ts:183] must add `'reels'`.

### Pitfall 9: The fake provider cannot stream
With `VIDEO_PROVIDER=fake`, tokens are `fake-playback-token.*` strings [VERIFIED: packages/core/server/media/video/fake.ts:150-160], so `stream.mux.com` refuses them and the element errors. Playwright's bundled Chromium also lacks proprietary codecs [ASSUMED]. Consequences:
- e2e can prove the DOM contract: the element exists, the `tokens` property is set (the `media-video.spec.ts:360-372` technique), and the `muted`/`loop`/`playsinline`/`preload` attributes and CSS variables.
- e2e can prove the pager, lanes, like parity and the sheet.
- e2e can prove the playback-error UI by routing `**/stream.mux.com/**` to `abort()`.
- e2e **cannot** prove real playback or autoplay.
- Unit tests prove the play/refusal logic with the StoryVideo stand-in technique [VERIFIED: apps/web/components/stories/StoryVideo.test.tsx:48-75], extended with a `play` that rejects `NotAllowedError` or `AbortError`.

### Pitfall 10: Back navigation shows a stale like on Início
The like actions do not revalidate [VERIFIED: feed-actions.ts only calls `revalidatePath` in update/delete, lines 185-186 and 209-210]. `staleTimes.dynamic` defaults to 0 s, but "This doesn't change back/forward caching behavior" [VERIFIED: next/dist/docs/…/staleTimes.md:36,42]. A tab click to Início shows the like, while browser Back may show the cached card. The e2e like-parity test must navigate through the BottomNav tab. If the user wants Back to be fresh too, that is a separate decision (Open Question 3).

### Pitfall 11: Disk space
The disk is at **96% (9.6 GiB free)** [VERIFIED: `df -h`, this session] and turbo cache grows ~1.3 GB per build (project memory). Run every gate with `TURBO_CACHE=local:r` and delete `.turbo/cache` before long gate runs.

## Open Questions

1. **Should `reels` off also 404 the video list at the API?**

4. **Seed enrichment for UAT and the D-33 sketch review:** demo has one 16:9 tenant-wide ready video; lab has one. | Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-tenant post or community leak through `?media=video&communityId=` or the lanes read | Information disclosure | RLS tenant lane + constant `tenant_id` + the `c.tenant_id = p.tenant_id` join already in `postProjection` (T-05-14); isolation integration test |

| Caption XSS | Tampering | `linkify`, no `dangerouslySetInnerHTML` (D-54) |
| Share URL pointing at an alias or attacker host | Spoofing | Server-composed primary host (FEED-07, T-04-51) |
