## Phase Goal

**As a** member of a tenant, **I want to** open my organization's own domain and see its branded, installable app on phone and desktop — branded already on the login page — **so that** the community feels like my organization's, not TRIA's. **As** TRIA's `super_admin`, **I want to** provision a tenant end-to-end (branding, modules, custom domain, first admin) from the platform panel on the platform domain, **so that** no tenant setup touches the database.

<objective>
Custom domains for a tenant (TENANT-07, D-34/D-35/D-36): a `super_admin` attaches a customer-owned host, the API registers it with the hosting provider through an env-selected adapter (`fake` locally, `vercel` hosted), stores the `tenant_domains` row unverified with the DNS records the customer must create, a `kernel.domain-verify` pg-boss job (and "Verificar agora") polls the provider until ownership + configuration are confirmed, and the verified transition — exactly once — sets `verified_at`, adds the host to the Supabase Auth redirect allow-list, sends the pending first-admin invite (02-05) and invalidates the host cache so the host starts resolving (D-36). Primary switching and removal follow D-35.

Purpose: closes ROADMAP criterion 2's "custom domain" leg through the API, unblocks 02-15 (Domínios tab), 02-10 (invite flow needs a verified primary) and 02-13 (appends to the same platform router).
Output: `packages/core/server/domains/*` adapters + job, `packages/core/server/platform/domains.ts`, `apps/api/src/routes/platform/domains.ts` mounted on the platform router, contracts/error codes, integration + unit + pgTAP tests, `docs/DEPLOY.md` custom-domains section. External-API coverage is governed by `.planning/phases/02-tenant-shell-branding-platform-panel/COVERAGE.md` (Vercel Project Domains and Supabase Management API matrices: every INTEGRATE row is implemented here; OPT-OUT rows are never called).
</objective>

<assumption_delta_decision>
Detector: `kind: chosen` on "custom domain" — until this plan a tenant's host was a provisioning-script constant (`scripts/seed.ts` writes `tria-demo.localhost` / `tria-lab.localhost` as verified rows); from here a tenant's hosts are a chosen, mutable, possibly-plural set managed at runtime by the platform panel.

- **Primary noun:** the `tenant_domains` row — one host of one tenant with a lifecycle (`verification_status`, `verified_at`, `dns_records`, `verify_deadline_at`) and a role (`is_primary`). Exactly one `is_primary` per tenant (partial unique index `tenant_domains_one_primary_per_tenant`); `verified_at is not null` is the routing predicate on both tiers (D-36); the `primaryHost` a client sees is the verified primary or null.
- **Decision: `promote`.** The runtime-managed row is the identity; the seed becomes just an initial writer of rows (it keeps `verified_at` + `verification_status = 'verified'`, no provider call, no job), and no code path may treat "the tenant's host" as a constant or as a single value again (`primaryHost` is nullable everywhere, aliases 308 to the primary in 02-08). No schema change is needed because 02-03 already shipped the promoted shape; this plan adds the invariant tests so the singular assumption cannot come back silently.
- **Accepted debt:** none from add-alongside. Known follow-ups recorded, not debt: provider reconciliation against `tenant_domains` (Phase 8), a Vercel verification webhook instead of polling (CONTEXT Deferred Ideas).
- **Invariant test (Task 2):** `supabase/tests/050-tenant-domains-invariants.sql` + the invariants block of `platform-domains.test.ts` — every tenant has ≤ 1 primary (second primary → 23505), every verified host resolves to exactly one tenant (citext unique host → 23505 for a case variant; by-host 200 for exactly the owner), an unverified host never resolves (by-host 404).
</assumption_delta_decision>
