## Phase Goal

**As a** member of a tenant, **I want to** open my organization's own domain and see its branded, installable app on phone and desktop — branded already on the login page — **so that** the community feels like my organization's, not the platform's. **As** the platform's `super_admin`, **I want to** provision a tenant end-to-end (branding, modules, custom domain, first admin) from the platform panel on the platform domain, **so that** no tenant setup touches the database.

> This plan's slice of the story: the recovery and invite e-mails a member or an invited admin receives carry *their* organization's name, logo and primary color (TENANT-06), never the platform's — and never another tenant's.

<objective>
Branded auth e-mails (TENANT-06) through the Supabase **Send Email Hook → API → Resend** path (D-37, D-38): a mail-transport adapter (`resend` + `local` → Mailpit, never real mail locally), the signed hook route `POST /v1/hooks/auth/send-email` (standard-webhooks signature, secret rotation, `webhook-id` idempotency), tenant resolution from membership → verified `redirect_to` host → neutral platform, pt-BR templates for recovery + invite + a neutral fallback (logo as-is or display name text, primary CTA with the persisted `onPrimary`, plain-text alternative, "Enviado pela plataforma Rede Social" footer), the hook enabled in `supabase/config.toml` for the local stack, and the hosted values recorded in `docs/deploy/auth-mail.md`.

This plan implements the "Supabase Auth Hooks — Send Email Hook" and "Resend HTTP API" matrices of `.planning/phases/02-tenant-shell-branding-platform-panel/COVERAGE.md`; every INTEGRATE row there is a behaviour below, the OPT-OUT rows are out of scope. COVERAGE.md itself is not edited here.
