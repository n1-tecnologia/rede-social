<objective>
Close the invite-flow trio of 02-REVIEW.md on the API side (kernel platform lane + contracts + integration tests). The panel surfaces (toast reasons, field error, refused pill) and the e2e proof follow in 02-20.

**Decisions (stated, per the gap-closure brief):**

- **D-A — refused-invite representation: reuse `expired` with `sent_at = null`, no new status.** A refused invite (`email_in_use` / `user_in_other_tenant`) is terminal until the super_admin resends; the row goes to `status = 'expired'`, `sent_at = null` (`user_id` untouched). No schema change (the `tenant_invites_status_chk` constraint, the contracts enum, the panel pill and pgTAP stay as they are), and `sent_at IS NULL` distinguishes a refusal from a genuinely lapsed link (which always has `sent_at`) — 02-20 derives a "Convite recusado" view state from exactly that pair. A `pending` row was rejected because every domain re-check would re-attempt the send (and, for an unconfirmed identity, GoTrue would re-mail another tenant's user each time). Reversibility: costly — once refused rows exist, a future dedicated `refused` status needs a backfill `where status = 'expired' and sent_at is null`.
- **D-B — one identity rule, one helper: `identityConflict(tx, email, tenantId)`** on the `public.users` mirror (written by `on_auth_user_created`) joined to non-deleted `memberships`: identity with a membership in another tenant → `'user_in_other_tenant'`; identity with no membership (super_admin, orphan, confirmed elsewhere) → `'email_in_use'`; identity with a membership in THIS tenant, or no identity → `null`. V1 rule: the first admin's e-mail must be new to the platform (ROLE-02 one-tenant-per-user); relaxing it in V2 is a change in this one helper. It runs (1) inside `createTenant`'s transaction → `400 VALIDATION_FAILED { adminEmail: 'in_use' }` (the form is where the super_admin can correct it — the reviewer's "consider validating at createTenant time": YES, via the mirror, not via `supabaseAdmin.auth.admin` which has no get-by-email and would need pagination), (2) in `sendPendingInvites` after the claim and before `inviteUserByEmail`, (3) in `resendInvite` before `generateLink`. The GoTrue `email_exists` answer on the first send and the `23505` on `memberships_one_tenant_per_user_v1` remain as race guards mapped to the same refusal.
- **D-C — WR-04 fallback link type: `recovery`** (`/auth/confirm` accepts `recovery` and honours `next=/aceitar-convite`; the `/aceitar-convite` action sets the password through `updateUser`, which a recovery session allows). The invite template is reused unchanged, so the admin receives the same "Convite para administrar {tenant}" mail.
- **D-D — consequence handling:** `ensureVerifiedSideEffects` records `invite:<reason>` for a 409 `INVITE_STATE_INVALID` (else `invite` as today) so the Domínios card names the cause; `setPrimaryDomain` wraps its `sendPendingInvites` call (log `platform.domains.invite_failed`, never fail the primary switch — the invite outcome is visible on the Admins tab). `createTenant`'s post-commit send is left as is: with D-B's create-time check a refusal there is a race-only path.
- **COVERAGE.md:** unchanged — GoTrue admin SDK calls (`inviteUserByEmail`, `generateLink`) are the platform's own auth service, not an external integration row; the phase's matrix already lists the Send Email Hook action types including `recovery`.

Purpose: an e-mail that can never receive the invite is refused where the super_admin can act (form field, 409 reason, `last_error` cause) instead of producing a `sent` row with no membership (WR-02), an opaque 500 / permanent `last_error = 'invite'` (WR-03) or a false "accepted" (WR-04).
Output: two new contract reasons, the refusal + fallback logic in `invites.ts`, the create-time check in `tenants.ts`, the `last_error` cause mapping in `domains.ts`, route descriptions, and eight integration cases across the three existing suites.

**Deferred to hardening:** IN-01..IN-07 — see 02-17-PLAN.md `<objective>`.
