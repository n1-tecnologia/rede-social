## Phase Goal

**As a** member of a tenant, **I want to** open my organization's own domain and see its branded, installable app on phone and desktop — branded already on the login page — **so that** the community feels like my organization's, not the platform's. **As** the platform's `super_admin`, **I want to** provision a tenant end-to-end (branding, modules, custom domain, first admin) from the platform panel on the platform domain, **so that** no tenant setup touches the database.

<objective>
Ship the branded public pages and the host routing rules of Phase 2: `/entrar`, `/cadastro`, `/esqueci-senha` and `/redefinir-senha` ported onto `@rede-social/ui` in the prototype's visual language (logo larger, display name, icon inputs, brand CTA, divider, outline sign-up), with paths, field names and server actions unchanged from Phase 1; `apps/web/proxy.ts` consuming `isPrimary`/`primaryHost` from the by-host contract (verified non-primary host → 308 to the primary preserving path + query; unverified host → generic shell); the branded suspended-tenant screen for `TENANT_SUSPENDED` in the D-09 pattern (`/auth/suspended` → `/comunidade-indisponivel`, "Esta comunidade está temporariamente indisponível.") plus the blocked, host-mismatch and no-community screens restyled as `EmptyState` screens. The prototype's `DeviceShell` mockup is not ported.

Purpose: ROADMAP criterion 1 says the login page is already branded on the tenant's domain; D-35/D-36 say one origin per tenant and verified hosts only. This plan is where a member first meets the brand and where an alias host is folded into the primary origin (PWA installs, cookies and push are per origin).
Output: ported `(auth)` tree on `@rede-social/ui`, `proxy.ts` 308 + PUBLIC entries, `proxy.test.ts`, `/auth/suspended` + `/comunidade-indisponivel`, `unavailable.json`, `signup.fieldErrors`, `auth-pages.spec.ts` + `tenant-fixtures.ts`.

Planner notes (deviations and why):
- UI-SPEC says the "Comunidade: {tenant}" line renders only on generic hosts. D-22 ("`/entrar` shows that tenant's display name") and ROADMAP criterion 1 ("logo, colors **and** display name") are locked and outrank the spec row; the prototype login itself shows the name under the mark as a tagline. The line therefore stays on tenant hosts, as the display-name carrier (also what `login.spec.ts`/`signup.spec.ts`/`branding.spec.ts` assert).
- `TenantLogo` lives in `@rede-social/core/ui` (02-03) but `apps/web` gains the `@rede-social/core` dependency only in 02-07 (same wave, owns `apps/web/package.json`). This plan ships a local `AuthBrand` with the identical D-26 contract; swapping to `TenantLogo size="auth"` is a one-line follow-up recorded in Handoffs (dependency constraint, not a scope cut).
- The suspended screen path is `/comunidade-indisponivel` with namespace `unavailable` (UI-SPEC Copywriting Contract, PATTERNS §11, RESEARCH Pattern 10); the existing `suspended` namespace stays the D-09 member-blocked screen (`/acesso-suspenso`) and is not renamed.
- `proxy.ts` pre-registers the PUBLIC entries for the wave-5 public paths (`/aceitar-convite`, `/convite-expirado`, manifest, `/serwist/`, `/~offline`) because 02-10 and 02-11 share wave 5 and neither may edit `proxy.ts` without a same-wave overlap; a public path that does not exist yet simply 404s.
</objective>
