## Phase Goal

**As a** member of a tenant, **I want to** open my organization's own domain and see its branded, installable app on phone and desktop — branded already on the login page — **so that** the community feels like my organization's, not TRIA's. **As** TRIA's `super_admin`, **I want to** provision a tenant end-to-end (branding, modules, custom domain, first admin) from the platform panel on the platform domain, **so that** no tenant setup touches the database.

<objective>
Platform panel screens I — the `super_admin`'s provisioning UI on the platform host, built on `@tria/ui` primitives per the mockup approved in 02-04 (D-33): the `(platform)/plataforma` route group with its rail, the tenants list (search, status filter, cursor pagination, primary host, status pill, empty states), the single "Novo tenant" form of D-31 (name, slug suggested/editable/immutable after create, primary + secondary hex with live swatch and contrast feedback via `contrastReport`, six module switches with the reference module never listed, first-admin e-mail) and the tenant page with the five tabs Marca · Módulos · Domínios · Admins · Status. The Admins tab (invite states + admin memberships) and the Status tab (suspend with `ConfirmDialog`, reactivate) are implemented here; Marca, Módulos and Domínios keep typed tab-route stubs that 02-14 and 02-15 replace.

Purpose: ROADMAP criterion 2 (UI half) — TRIA provisions a tenant from the panel, never from the database — proven end-to-end under Playwright on the platform host against the real 02-05 API; the tenant page layout and tab routes are the seam every later panel plan (02-10, 02-14, 02-15) mounts into.
Output: `(platform)/plataforma/**` routes + server actions, `components/platform/*`, `lib/platform.ts` (platform RPC client), `lib/slugify.ts`, `messages/pt-BR/platform.json`, `e2e/platform-tenants.spec.ts`.
</objective>
