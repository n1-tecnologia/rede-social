## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → proxy.ts / by-host lookup | `Host`/`x-forwarded-host` is attacker-controlled; it only SELECTS the public shell (D-20/D-23) |
| API by-host route (unauthenticated) | negative + positive answers cached per normalized host |
| tenants.branding jsonb → HTML | brand values (hex, URLs, display name) are rendered into server HTML and inline `style` |
| npm registry → repo | new third-party packages enter the build (supply chain) |
| props → DOM | primitives render caller-supplied strings/URLs (labels, `Avatar src`, `FileDropZone` files) |

| mockup HTML → design team browser | static file, no data |
| super_admin session → /v1/platform/* | cross-tenant writes behind `requireSuperAdmin()` |
| API → GoTrue admin API | `inviteUserByEmail` with a redirectTo built from a verified primary host |

| provider answer → `tenant_domains.dns_records` → panel | third-party strings persisted and later rendered (02-15) |
| pg-boss queue → handler | job payloads are data, replayable; the handler runs with kernel privileges |

| panel toggle → tenant runtime (`tenant_modules`, flags cache, member bootstrap/nav) | a super_admin action changes what a whole tenant's members can reach |

## Non-Blocking Notes

These do not count toward `threats_open`. Neither is a failure of a declared mitigation.

**N-1 — Five summaries declare no `## Threat Flags` section.**
`02-01`, `02-03`, `02-04`, `02-05` and `02-13` never declare new attack surface, although 02-03 and 02-13 introduce the `tenant_invites` table, the mail transport, the public `branding` bucket and `sharp` decoding. The auditor compensated by enumerating the surface independently: all 23 registered paths under `platform/`, `me.ts` and `public.ts` map to a register entry, and no unmapped endpoint was found. The declaration is missing, not the coverage. Process gap only.

**N-2 — 02-REVIEW.md WR-01 remains open (availability, not a control failure).**
In `packages/core/server/platform/invites.ts`, a non-23505 failure in the membership transaction after a successful `inviteUserByEmail`/`generateLink` leaves the invite `sent` with `user_id = null` and no membership. Every later resend then hits `identityConflict` and returns a permanent `email_in_use` refusal with a false diagnostic and no self-service recovery. T-02-151's control ("never mail or re-token a foreign identity") is if anything over-enforcing here. Suggested fix from the review: pass `invite.userId` into `identityConflict` and stamp `user_id` before the membership insert. Destination (Phase 2 follow-up vs Phase 8 hardening) is an open product decision.
