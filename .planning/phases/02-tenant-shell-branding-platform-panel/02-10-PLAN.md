## Phase Goal

**As a** member of a tenant, **I want to** open my organization's own domain and see its branded, installable app on phone and desktop — branded already on the login page — **so that** the community feels like my organization's, not TRIA's. **As** TRIA's `super_admin`, **I want to** provision a tenant end-to-end (branding, modules, custom domain, first admin) from the platform panel on the platform domain, **so that** no tenant setup touches the database.

> This plan's slice of the story: the tenant's first administrator receives the branded invite on the tenant's own domain, sets a password, accepts the tenant rules and TRIA's terms, and lands inside the tenant's app — and TRIA can see the invite's state and resend it from the panel when the mail was lost or the link expired.

Planner notes (decisions taken inside Claude's discretion, recorded for the executor):
- **Resend mechanism.** RESEARCH A3 flags "does `inviteUserByEmail` re-send for an already-invited user?" as an unverified assumption, and every GoTrue-originated send also consumes the `[auth.rate_limit] email_sent` budget (02-06 watch item). Resend of a `sent`/`expired` invite therefore uses `auth.admin.generateLink({ type: 'invite' })` — which never sends mail and returns `properties.hashed_token` — plus the 02-06 template + transport (`renderInvite`, `toMailBrand`, `mailTransport`, `buildActionLink`). This is the "resend-invite fallback" 02-06 anticipated and it also gives the deterministic "old link stops working after a resend" behaviour the e2e relies on (GoTrue replaces `confirmation_token`). A `pending` invite is resent through 02-05's `sendPendingInvites` so the first send has exactly one implementation. **Flagged assumption:** GoTrue's `generateLink` for an existing *unconfirmed* user regenerates the token instead of answering `email_exists`; integration case (10) proves it on the local stack — if it fails, fall back to re-invoking `inviteUserByEmail` for that branch and record it in the SUMMARY.
- **Invited scope.** `requireAuth` keeps letting `invited` memberships through (02-03) but, after the host check, refuses every path except `/v1/me/bootstrap` and `/v1/me/accept-invite` with 403 `MEMBERSHIP_INVITED`. Without this, an invited admin's Bearer could call module routes before accepting the terms (V4 access control, RESEARCH security table). `require-auth.ts` is not listed by any wave-5 plan, so this plan owns the change this wave.
- **Bootstrap for invited** stays a 200 with `membership.status = 'invited'` (RESEARCH Pattern 7, PATTERNS §11): the web guard lives in `requireBootstrap()` so 02-07's `(app)` layout and pages need no change.
- **Catalog file name.** UI-SPEC lists namespaces `invite`/`inviteExpired`; the outline (authoritative for files) assigns `acceptInvite.json`. One namespace `acceptInvite` with an `expired.*` group is used; 02-16's catalog audit may rename without behaviour change.
- **Expiry by time** is GoTrue's `otp_expiry` (3600 s locally; RESEARCH A4 recommends 86400 for hosted). `supabase/config.toml` belongs to 02-13 this wave and is not touched; the e2e proves the expired screen through a superseded token and a consumed token instead of waiting an hour.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| invite e-mail link -> `/auth/confirm` -> session | a one-time `token_hash` (GoTrue) becomes a browser session on the tenant host; the link is the only proof of e-mail ownership |
| browser form -> `/aceitar-convite` server action | password + consents; the password crosses to Supabase only, the consents to the API |

| super_admin session -> `/v1/platform/tenants/{id}/invites*` | cross-tenant read/resend of invites; triggers outbound mail |
| API -> GoTrue admin (`generateLink`) -> kernel mail transport | the API mints an invite token and sends it itself (outside the Send Email Hook path) |
| tenant data (display name, rules text) -> accept screen / mail | tenant-controlled strings rendered to the invited admin |
