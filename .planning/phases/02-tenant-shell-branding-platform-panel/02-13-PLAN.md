## Phase Goal

**As a** member of a tenant, **I want to** open my organization's own domain and see its branded, installable app on phone and desktop — branded already on the login page — **so that** the community feels like my organization's, not TRIA's. **As** TRIA's `super_admin`, **I want to** provision a tenant end-to-end (branding, modules, custom domain, first admin) from the platform panel on the platform domain, **so that** no tenant setup touches the database.

<objective>
Platform branding routes (D-27/D-28): a `super_admin` uploads a tenant's logo (and, optionally, a square app icon) straight to the public `branding` Storage bucket through an API-minted signed URL, the `complete` endpoint validates the object and records it in `tenants.branding`, a kernel pg-boss job derives the favicon + PWA icon set with `sharp` (maskable icon centred on the tenant's primary colour) and persists the versioned URLs, and `PUT …/branding/colors` recomputes the persisted colour derivations with a contrast report in light and dark that warns and requires explicit confirmation instead of blocking. Every mutation invalidates the host cache so the new brand reaches the public pages and the manifest within minutes. The seed derives icons for the two seed tenants so the phase smoke sees per-tenant favicons and manifest icons.

Purpose: closes the "branding" leg of ROADMAP criterion 2 through the API (02-14 builds the Marca tab on these endpoints), gives 02-11's per-tenant manifest real `iconUrls`, and proves TENANT-02's "brand mutation → host cache invalidated → new brand served" truth end-to-end.
Output: contracts (`branding.ts` extended), `packages/core/server/branding/*` (pure derivation + job), `packages/core/server/platform/branding.ts` (admin-lane service), `apps/api/src/routes/platform/branding.ts` mounted on the platform router, worker registration, `[storage.buckets.branding]` + custom bucket migration + pgTAP, seed icons, integration + unit tests.

**Decision recorded — colours have two doors, one persistence path, one gate.** 02-05's `PATCH /v1/platform/tenants/{id}` already accepts `colors` and its contract (`updateTenantBodySchema`, 02-03) has no confirmation field; its tests pin an ungated rebrand. This plan does NOT drop or duplicate it: `PUT …/branding/colors` is the panel's colour endpoint (report in both modes, `confirmLowContrast` gate, `iconVersion` bump), and `updateTenant` is refactored to call the same `applyBrandColors` helper so PATCH also bumps `iconVersion`/re-derives the maskable icon and stays report-carrying through `tenant.contrast` in its detail answer. 02-14 MUST use `PUT …/branding/colors`; PATCH `colors` remains the low-level API-client/script door. `apps/api/src/routes/platform/tenants.ts` is untouched (02-10 owns it this wave).

**No schema change — no drizzle migration.** `iconUrls`, `faviconUrl`, `iconUrl`, `iconVersion` are keys of the existing `tenants.branding` jsonb (02-01 `tenantBrandingSchema`); `pnpm db:generate` must remain a no-op. The single hand-written custom migration seeds the `storage.buckets` row for hosted projects and is applied through the BLOCKING reset gate in Task 3.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| super_admin session → `/v1/platform/tenants/{id}/branding/*` | cross-tenant writes behind `requireSuperAdmin()`; the tenant id in the path is the ONLY source of the Storage key prefix |
| browser → Supabase Storage (signed upload URL) | untrusted bytes land in a PUBLIC bucket without passing through the API; Storage enforces size and mime, the API validates the object afterwards |
| API/worker → Storage (service key) | download of untrusted bytes for header inspection (request path) and full decoding (worker) |
| worker (`sharp`, `png-to-ico`) | native image decoding of attacker-supplied files |
| public bucket → every browser | derived icons and logos are world-readable by design (D-27) |
