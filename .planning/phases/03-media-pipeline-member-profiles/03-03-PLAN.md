## Phase Goal

**As a** member of my organization's community, **I want to** upload my photo from my phone, edit my name and bio, and find the other members by name, **so that** the community is made of recognisable people rather than anonymous accounts.

<objective>
The other half of the people story (PROF-02, PROF-03): `GET /v1/members/{membershipId}` returns another member's photo, display name and bio — and nothing else — and `GET /v1/members?q=&cursor=&limit=` returns a keyset-paginated, accent- and case-insensitive, name-searchable list of the tenant's **active members only, with staff hidden** (D-47). Both run in the tenant lane over the `member_profiles` row 03-02 created, using the `app.imm_unaccent` + GIN-trigram index and the `(tenant_id, imm_unaccent(lower(display_name)), id)` keyset index that already exist — this plan adds a query, not a schema change.

Purpose: closes criterion 2 on the API side ("Member can open another member's profile and browse a paginated, name-searchable member directory that only ever lists members of their own tenant") and establishes the **keyset pagination convention Phase 4's feed inherits** — an opaque base64url cursor carrying the ordered expression plus the row id, `nextCursor` present exactly when another row exists, and an explicit `limit` clamped server-side.
Output: `packages/core/server/profiles/search.ts`, two service functions, `apps/api/src/routes/members.ts` mounted on the app, the list contracts, unit + integration tests.

**Decision — the two routes apply deliberately different predicates and each says so.** The directory excludes staff (`role = 'member'`); the single-member route does not filter on role at all, because D-47 explicitly keeps a staff profile **openable by direct link** (from their content in Phase 4, or the support conversation in Phase 7) while keeping it out of the browsable list. Writing this as a shared helper would collapse the distinction, so the predicate lives at each call site with the D-47 citation next to it.

**Decision — the keyset tiebreaker is `member_profiles.id`, not `membership_id`.** The order index created in 03-02 is `(tenant_id, app.imm_unaccent(lower(display_name)), id)` on `member_profiles`, so the cursor must carry the same column the index does or the page query stops being index-only. The payload still exposes `membershipId` as the item's identity (it is what `/membros/[membershipId]` routes on); the cursor is opaque and its internals are never a public contract.
</objective>
