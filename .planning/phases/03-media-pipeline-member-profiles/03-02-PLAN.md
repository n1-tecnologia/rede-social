## Phase Goal

**As a** member of my organization's community, **I want to** upload my photo from my phone, edit my name and bio, and find the other members by name, **so that** the community is made of recognisable people rather than anonymous accounts.

<objective>
The member profile (PROF-01): a `member_profiles` row hangs off the **membership**, not off `users`, carrying display name, bio, the avatar's `media_assets` id and the first-access nudge state. `GET`/`PATCH /v1/me/profile` let a member read and edit their own; `GET /v1/me/bootstrap` stops hardcoding `membership.profile` at `apps/api/src/routes/me.ts:118` and reads the real row with **no change to `bootstrapSchema`**. The avatar is the media broker's first real consumer: the profile stores an asset id and the payload carries the stable `/v1/media/{assetId}/w128` URL, never a signed Storage URL.

Purpose: PROF-01, and the identity model the whole phase and V2 depend on — `packages/core/docs/SCHEMA-CONVENTIONS.md` §(b)4 states it as a rule ("profile data hangs off the membership, not off `users`: a person may present differently in different tenants") and `users` is pgTAP-pinned to carry no `tenant_id`. This plan also lands the search infrastructure (`unaccent`, `pg_trgm`, `app.imm_unaccent`, the trigram and keyset indexes) that 03-03's directory queries, so the directory arrives as a query over an already-indexed table rather than as a schema change.
Output: `packages/contracts/src/profiles.ts`, `packages/core/db/schema/member-profiles.ts`, two migrations (generated + custom), `packages/core/server/profiles/*`, three routes on `me.ts`, pgTAP `080`, seed members with accented pt-BR names and photos, unit + integration tests.

**This plan implements the `promote` half of the assumption-delta decision recorded in `03-01-PLAN.md`.** The general representation — a member profile row readable by any member of the same tenant — is primary; "my own profile" is demoted to "the row whose membership is `membershipOfRecord(ctx)`". There is deliberately no second storage path. Task 2 carries the invariant test.

**Decision — the eager row is created by a database trigger, not by editing every call site.** RESEARCH R-08 requires one row per membership, eagerly (a lazy row forces the directory into `coalesce(mp.display_name, u.name)` across two tables, which the trigram expression index cannot cover). Memberships are inserted in at least four places today (`tenancy/signup.ts:81`, `platform/invites.ts:282` and `:622`, `scripts/seed.ts:186`) and Phase 8 will add more. An `after insert on public.memberships` trigger makes the invariant structural: a future call site cannot forget it, and pgTAP proves it directly.

**Decision — the two expression indexes, the extensions and `app.imm_unaccent` live in a hand-written custom migration, not in the drizzle schema.** `drizzle-kit` cannot create an extension or a schema-qualified `IMMUTABLE` wrapper function, and declaring the expression indexes in TS while also writing them in SQL would make `pnpm db:generate` non-idempotent. The drizzle file declares the table, its plain indexes and its two policies; the custom migration declares everything drizzle does not model, with a comment saying so. The drift gate in Task 3 is what proves the split is clean.
</objective>
