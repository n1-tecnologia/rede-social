## Phase Goal

**As** the tenant's `admin_tenant`, **I want to** upload a phone-recorded video that just plays for everyone, **so that** the platform accepts every kind of media a real community produces without ever leaking one community's files to another.

<objective>
Video playback and the criterion-4 proof surface (MEDIA-03, TENANT-04): `GET /v1/media/{assetId}/playback` mints a short-lived signed playback token per request against the caller's membership (D-44), `GET /v1/media` lists a tenant's assets for an `admin_tenant`, and `/configuracoes/midia` is the minimal admin screen R-04 chose — one upload zone, a status list, and a player for a ready video. `VideoPlayer` and `MediaAssetRow` are built here; Phase 4's composer reuses the player and the upload hook, not the screen.

Purpose: makes criterion 4 observable ("`admin_tenant` can upload a phone-recorded video … and plays back as HLS with a thumbnail … showing a 'processando' placeholder until ready"). The real-device HLS check on iOS Safari and Android Chrome and the real Mux transcode stay Phase 01.1 UAT lines (03-06's decision); everything else is automated against the fake provider.
Output: the playback and list routes with their contracts, the shared cursor module, `film` in the kernel icon map, `@mux/mux-player-react` + `@mux/upchunk` in the web app, three media components, the `/configuracoes/midia` route, the "Administração" settings group, the video half of the `media` catalog, and integration + Playwright specs.

**Decision — `encodeCursor`/`decodeCursor` move to `packages/core/server/paging.ts` and `profiles/search.ts` re-exports them.** The asset list needs the same opaque `{ v: 1, n, id }` envelope 03-03 established for the member directory. Two copies would drift on the first change; one module with two callers cannot. This is the only edit this plan makes to a 03-03 file.

**Decision — `GET /v1/media` is `admin_tenant`-only in V1.** The `media_assets` select policy is tenant-wide (Phase 4's feed needs it), but the *listing* endpoint is an admin surface: a member has no screen that enumerates the tenant's assets, and exposing one would be a browsable inventory of everything ever uploaded. Phase 4 widens it when the composer needs it.

**No "pick an existing asset" affordance.** CONTEXT §Deferred Ideas is explicit: if a media screen ships in this phase it is for the criterion-4 proof; the reuse affordance belongs to Phase 4's composer.

**Wave note — this plan is wave 6, not wave 5.** Nothing about this plan changed; `03-06` moved to wave 5 to serialise its `pnpm db:reset` against 03-05's Playwright reads (a declared shared-mutable-state edge), and this plan already `depends_on` 03-06, so its wave follows.

**Scope note — why this plan is not sliced (checker `scope_sanity`).** The estimator put this plan at 1.15x the 100,000-token smart-zone budget with 21 `files_modified` against a 15-file advisory threshold. Both signals are uncalibrated: all 20 Phase 2 plans carry `actuals.tokens` in their SUMMARY frontmatter, yet `gsd-tools query estimate-calibration` still returns `{ factor: 1, sample_count: 0 }`, so every Phase 3 ratio is computed at factor 1.0 against a projection method Phase 2 measured as ~3.8x high (1,970,000 projected vs 521,709 actual across 20 plans). Applying Phase 2's **worst** single ratio (0.51) to this plan's 115,000 gives ≈59,000 — under budget. File count is not a predictor here: Phase 2's 41-file plan cost 26,719 tokens while its 8-file plan cost 48,830. Per ADR-2629 Decision 5, over-budget alone never blocks.

Slicing this plan specifically would be wrong: it is one vertical slice — *an admin uploads a video and watches it become ready* — and it is the **only** automated proof ROADMAP criterion 4 has. Splitting the upload (Task 2) from the list and playback routes (Task 1) would leave an admin screen that lists assets nobody can create, or an uploader with nowhere to watch the result; either half proves nothing about criterion 4. The 21 files are that one slice's surface across its layers: one shared paging module, two routes, one icon-map entry, three components, one screen with its states, one catalog and two specs. The `estimate` block is left exactly as the tool produced it (`confidence` is derived, never self-rated); this note is the record.
</objective>

| member session → `GET /v1/media/{assetId}/playback` | a client-chosen asset id is exchanged for a bearer-free token that grants playback of a provider-hosted stream |
| the minted token → any holder | a 2 h credential that is valid outside our infrastructure, at the provider's edge |
| `admin_tenant` session → `GET /v1/media` | an enumeration of everything the community has ever uploaded |
| browser → the provider's direct-upload URL | untrusted bytes leave the device for a third party without passing through our API |
