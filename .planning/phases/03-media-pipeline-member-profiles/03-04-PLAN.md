## Phase Goal

**As a** member of my organization's community, **I want to** upload my photo from my phone, edit my name and bio, and find the other members by name, **so that** the community is made of recognisable people rather than anonymous accounts.

<objective>
The member-facing profile screens (PROF-01, MEDIA-01, MEDIA-02 on the web side): `/perfil` becomes the real profile — the Phase 2 stub's docblock says "Phase 3 replaces it with the profile module UI" — `/perfil/editar` ports the prototype's `EditProfileForm` minus username and website, and the photo travels browser → signed Supabase Storage URL → `complete`, with a plain `PUT` under 6 MiB and `tus-js-client` above it. An iPhone HEIC is re-encoded in the browser before it is ever offered to the server, silently.

Purpose: criterion 1 end-to-end on a phone ("Member can upload a profile photo from a phone … edit their display name and bio, and see the photo served through a signed, tenant-checked URL in display sizes produced by the worker"). It also produces the two components Phase 4's composer reuses unchanged: the generalised `useSignedUpload` hook and `MediaImage`.
Output: `Textarea` in `@tria/ui`, the TUS + canvas-re-encode branches in `apps/web/lib/upload.ts`, `apps/web/components/media/*`, `apps/web/components/profile/ProfileHeader.tsx`, the two `/perfil` routes and their server actions, the `profile` and `media` pt-BR catalogs, the `/configuracoes` row, and two Playwright specs including the iPhone-14 project.

**Design authority.** `reference/frontend-design/` is the visual source for `ProfileHeader`, `EditProfileForm` and `ImagePicker`; port presentational components, never refactor in place. Everything the prototype lacks is specified in `03-UI-SPEC.md` (status `approved`, reviewed 2026-09-21) and was approved through the D-33 review — do not re-decide it here. The UI-SPEC's non-blocking recommendation 1 (aligning "Salvar" with Phase 2's "Salvar alterações") is adopted: use **"Salvar alterações"** so the two kernel forms match.

**Decision — the photo commits independently of "Salvar".** UI-SPEC §Edit profile states it: a member who only changes their photo never presses the button. The upload's `complete` is followed immediately by `setAvatarAction` (a `PATCH /v1/me/profile { avatarAssetId }`), which is also what retires the previous asset server-side — so the form holds no pending photo state and an abandoned form leaves no half-applied change.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| member device → Supabase Storage (signed URL / TUS) | the browser holds a single-object signed upload token; no Supabase session JWT ever reaches the client |
| member device → Next.js server actions | `{ kind, purpose, mime, size, filename }` and an `assetId` cross here — never bytes |
| member-supplied file → browser canvas | untrusted image data is decoded by the browser's own decoder before any upload |
| rendered profile → the member's screen | another member's display name, bio and photo are rendered in this member's document |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-25 | Information disclosure | The signed upload token leaking into logs, analytics or a shared URL | medium | mitigate | the token is passed straight from the server action's return value into the TUS `x-signature` header and the plain PUT URL and is never rendered, stored, or logged; it grants write to ONE object key for its TTL; `apps/web/lib/upload.ts` sends no auth header of any kind |
| T-03-26 | Tampering / XSS | A member's display name or bio rendered on another member's screen | high | mitigate | plain text only — React escapes by default, there is no `dangerouslySetInnerHTML` anywhere in `apps/web/components/profile/*` or the profile routes, and the contract carries no HTML field; a grep for `dangerouslySetInnerHTML` in the new files is an acceptance criterion of 03-05 (where other members' content first renders) |
| T-03-27 | Denial of service | A huge or pathological image OOMing the member's own browser during the canvas re-encode | low | accept | the decode is bounded by the device's own decoder and the member chose the file; `maxSide` 2048 caps the output; a failed re-encode rejects and renders the "Não foi possível preparar esta imagem." copy rather than hanging |
| T-03-28 | Spoofing | A file whose extension or declared type lies about its content | medium | mitigate | the client check is UX ONLY (the 02-14 `classifyFile` posture): the server's `complete` re-reads Storage metadata and decodes the header, so a spoofed file is refused at confirmation time with a code the hook maps to catalog copy |
| T-03-29 | Information disclosure | A raw error, HTTP status or provider message shown to the member | medium | mitigate | the WR-07 boundary: every catch logs `console.error(<event>, { error: String(error) })` and renders `t('media.errors.generic')`; the acceptance criteria pin the absence of a `finally` (which would re-run `fail` on the success path) and the presence of the console-only path |
| T-03-30 | Tampering | A stale service-worker cache serving another member's avatar after a profile change | low | mitigate | the Phase 2 SW allow-list treats `/v1/*` as `NetworkOnly`, so the 302 and its target are never cached cross-session; `revalidatePath('/perfil')` after every mutation refreshes the RSC payload |
