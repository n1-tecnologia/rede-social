<planning_decisions>
1. **Two definers, not one big function (R-Alternatives).** The projection returns rows; the cascades (hero, shelf, track, stats) are pure TypeScript in `contracts/member-area.ts`, unit-tested without a database, with the server as the authority (CONTEXT Discretion "Data"). Only the streak's date bucketing is SQL (D-440, R-Pattern 3).
2. **The overview schema grows in plan 03.** This plan's strict `learnOverviewSchema` carries `serverNow`, `streakDays` and the optional `hero`; plan 03 adds the optional `shelf`, `track`, `live`, `newLessons` and `categories` keys in the same release, before any web plan parses it (no deploy-window break, R-Pitfall 3).
3. **Started = has a progress row.** A course is started when the caller holds any `course_lesson_progress` row on one of its live lessons (the prototype's `startedAt`, written on the first 15-second tick); complete when it has at least one live lesson and all are complete. Every helper of this phase uses these two predicates.
4. **`em_dia` fallback.** When nothing is locked and every unlocked course is complete, the hero is `em_dia` on the most recently touched course with `lessonId: null` (the UI's "Conhecer o curso"), so a finished member still gets a card (R-A2 extended; surfaced in `<flagged_assumptions>`).
5. **The admin guard in the streak** is explicit (`case when app.tenant_role() = 'admin_tenant' then 0`), not only implied by D-422's absent rows.
6. **The reminder table lands here** (not in plan 05) because plan 03's overview reads the caller's own opt-ins for `reminderOn`; its custom recipients definer lands in plan 05 with the worker that needs it.
</planning_decisions>
