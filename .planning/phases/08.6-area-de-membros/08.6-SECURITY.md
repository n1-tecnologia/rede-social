## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| browser/BFF → API | Member reads (`/learn/overview`, `/learn/tracks`, `/learn/progress`) take no parameter; the reminder and reactivation routes take an attacker-controlled live id | session claims, live ids |
| API lane → Postgres (RLS + definers) | The member lane reads through tenant-pinned `SECURITY DEFINER` functions that see rows RLS hides | lesson projection, progress, streak, own opt-ins |
| API → pg-boss / bus → worker | Job and event payloads (`tenantId`, `liveId`, `courseId`, instants) cross into the worker and the notifications fan-out | ids, instants (never authority) |
| worker → notifications fan-out → devices | Recipients, facts and push bodies leave the courses module | recipient ids, titles, tenant-clock times |
| browser → Next RSC / server actions | `?aba=`, `?ver=`, `?trilha=`, `categoria` params and posted live ids are attacker-controlled | query params, uuids |
| API answer / stored facts → render | Server answers and stored notification facts become text and links | titles, ids |
| review artifact → application code; human approval → agent execution | Sketch mockups never ship; gate approvals come from the user | approval keys |
| developer → production | The release is applied by hand from DEPLOY.md | migrations, deploy order |
