#### Streak and hours
- **D-440: A study day is a day on which the member completed at least one lesson, in the tenant's timezone.**
  - It is derived from distinct local dates of `course_lesson_progress.completed_at` (`tenants.timezone`).
  - `completed_at` is written once and never cleared (D-427 one-way), so the history is complete and no new activity table is needed.
  - Playback without completion does not count.
  - Admin rows do not exist (D-422), so a manager has no streak.
  - The server computes the streak. It is never accepted from the client.
- **D-441: The streak survives until the end of the next day.**
  - Following the prototype, if today has no completion the count starts from yesterday. "Sem sequência" shows only after a full local day passes with no completion.
- **D-442: "Horas assistidas" is the sum of the durations of completed lessons, as in the prototype.**
  - A lesson completed by the button counts its full duration.
  - A lesson with no video counts zero.
  - There is no watched-seconds accumulator.
  - The duration source is the lesson's ready video asset (`media_assets.duration_seconds`), the same one `app.course_catalogue_stats()` sums.
- **D-443: The streak is display only.** It is the flame badge on Início and the number in Meu progresso. It has no notification, no reward and no end-of-day nudge.

#### Live reminder
- **D-444: The live reminder is opt-in per live.**
  - "Ativar lembrete" / "Lembrete ativado" toggles on the Início next-live card and on the live page, as in the prototype.
  - Only members who turned it on receive it.
  - The opt-in is stored per membership and live (a new own-row table), with a tenant-scoped RLS policy that lets the member write only their own row.
  - **Reversibility:** costly. A new table, RLS policies, pgTAP and an isolation-inventory entry.
- **D-445: The reminder fires 15 minutes before `starts_at`, which matches the opening of the join link (D-432).** It goes as an in-app notification plus Web Push and opens the live page.
- **D-446: Only a member with access to the live can turn the reminder on.**
  - On a locked live the toggle is replaced by "Comprar para liberar".
  - The API refuses the opt-in for a locked live.
  - At fire time access is checked again. A member who lost access (revoked) receives nothing.
- **D-447: The reminder follows the live.**
  - **Cancelled:** the reminder does not fire, and members who opted in get a "Live cancelada" notice.
  - **Rescheduled:** the reminder moves to the new `starts_at` with no extra notice.
  - **Reactivated after a cancel:** opt-ins that still exist fire again.
  - The arming pattern is the events module's (`armEventReminders` inside the write transaction, delayed pg-boss jobs, a stale-check at fire time).

#### New-content notices
- **D-448: Four publications notify members (course published, new lessons in a published course, live scheduled, and replay available).**
  - **Course published:** draft to published, including a republish.
  - **New lessons:** lessons added to a course that is already published.
  - **Live scheduled:** a live created, or reactivated after a cancel.
  - **Replay available:** the admin sets `replay_lesson_id` on a live that already happened.
  - The courses module today emits no domain events. These are new events and kinds (`courses.<kind>`) with `notificationSources` declared in the courses manifest, using the Phase 7 fan-out pattern.
  - **Reversibility:** costly. Notification kinds are stored strings, and producers and consumers grow around them.
- **D-449: Course and live notices reach every member, including members without access, as a shop window.**
  - A member without access lands on the page with the padlock and "Comprar para liberar".
  - Nothing new leaks, because titles of locked courses and lives are already visible (D-421, D-431). The notice carries no lesson content, asset or link.
  - New-lesson notices reach only members with access to the course.
  - A replay notice reaches only members with access to the live or to the replay lesson's course (the two doors of D-433).
  - Unpublished content is never named to anyone.
- **D-450: New lessons in one course are grouped into one notice within a short window.**
  - The default window is 30 minutes, for example "5 aulas novas em …".
  - It does not repeat for lessons already announced.
- **D-451: Notices go through the notification center and Web Push**, as new posts and new events do (Phase 7 channels `['in_app','push']`). Push reaches only devices where the member enabled it.

### Claude's Discretion
Each item has a stated default. The planner may refine it but should not reverse it without asking.

**Início content**
- **"Novas aulas da semana."** Default: up to 4 lessons created in the last 7 days in published courses that the member can open (not locked by purchase or sequence), newest first. When there are none, the section is hidden. Lessons have no `published_at`, so a lesson's "new" date is its `created_at`, or the course's `published_at` when that is later.

- **"Próxima live."** Default: the live happening now, else the nearest scheduled live (the D-431 order). A locked live shows the padlock and the buy path instead of the toggle. The section is hidden when there is none.
- **Greeting.** Default: a fixed "Bem-vindo de volta." with the tenant's display name in the subtitle, not the prototype's harmonisation copy.
- **Empty school.** Default: a tenant with no published course shows Início with an empty state. The sections that have no data are hidden, never shown as empty cards.

**Meu progresso**
- **Course by course.** Default: every published course the member has started, with percent and the next lesson, ordered by last activity. Locked courses that were never started are not listed.
- **Certificates block.** Default: absent in this phase, with no "em breve" placeholder.
- **"Cursos concluídos".** Default: a course counts when all its live lessons are complete. The count is recomputed if lessons are added later (a completed course can return to in progress).

**Admin and staff**
- **Admin preview.** Default: `?ver=aluno` shows the five chips with the D-422 preview banner. The streak and stats show zero (no rows), and reminder toggles are disabled with a hint.
- **`support_tenant`.** Default: same as 08.5. Staff see everything open and receive notices like a member.

**Notifications**
- **Kinds and copy.** Default kinds: `courses.course_published`, `courses.lessons_added`, `courses.live_scheduled`, `courses.live_reminder`, `courses.live_cancelled`, `courses.replay_available`. Copy lives in the catalog, and each notice opens the course, live or lesson page.
- **Dedupe.** Default: one notice per (kind, entity), plus the lesson-batch window for D-450. A republish within 24 hours does not notify again.
- **Fan-out on module or store state.** Default: no notice when the `courses` module is off. With the store off every course is open, so D-449's shop-window case does not arise.

**Data**
- **Where the derivations run.** Default: one member read (or a small set) on the API returns what Início needs, computed in SQL or in the service from the member's own rows. Pure helpers ported from `members-progress.ts` (`heroResume`, `courseShelf`, `activeTrack`, `overallStats`) stay in sync as shared contract helpers, with the server as the authority. The researcher may pick another split if the server stays the source of truth.
- **Timezone math.** Default: dates are bucketed with `AT TIME ZONE tenants.timezone` in SQL, and the web formats with the same timezone 08.5 already passes (`bootstrap.tenant.timezone`).

## Summary

Phase 08.5 left a complete, database-authorised member lane: one lock evaluator `app.course_lesson_states(p_course)` that already joins the caller's own progress rows, one access answer `app.course_lesson_access`, a titles-only outline, live cards and per-course stats, all `SECURITY DEFINER` functions pinned to `app.tenant_id()`. It also left per-user variants of the store's lock seams (`app.course_locked_ids_for(p_user)`, `app.live_locked_ids_for(p_user)`), which the 08.3 seam comment says were declared for exactly this case: "the member phase's reads and the notifications worker later". Phase 7 left a generic notification seam: a producer declares `notificationSources` in its manifest, emits a domain event after commit, the sink enqueues `notifications.fanout`, and the worker asks the source for intents (`{type:'members'}` or `{type:'users', userIds}`, a `dedupeKey`, channels and a push hint). The events module is a complete template for durable reminders: arm a delayed pg-boss job inside the write transaction with a singleton key that carries the start, re-check at fire time, emit, flush.

So this phase needs no new library and no new architectural idea. It is three kinds of work. (1) One new SQL projection over the existing evaluator (`app.course_member_lessons()` via `cross join lateral app.course_lesson_states(c.id)`, verified to run on the local seed), one streak function using `AT TIME ZONE tenants.timezone` (verified with a probe), three audience definers built on the `_for(p_user)` seams, one batch-claim definer, and one own-row table for the reminder opt-in. (2) Pure TypeScript ports of `heroResume`, `courseShelf`, `activeTrack`, `trackProgress` and `overallStats` in the courses contracts, run by the API over those rows (the server is the authority; the web only renders). (3) Six notification kinds, two jobs and the web route and tab changes.

Two findings change the plan. **There is no way to reactivate a cancelled live today**: `updateLive` refuses a cancelled live with `409 live_cancelled` and the admin routes have only `/lives/{liveId}/cancel` (no reactivate). D-447's and D-448's "reactivated after a cancel" clauses have no write path to hang on, so the planner must either add the route (COURSE-43) or ask the user. And **the opt-in rows are invisible to the worker**: the own-row select policy D-444 asks for hides every row from the notifications worker's zero user, so recipients must be read through a definer, not a lane select.

**Primary recommendation:** Build the member area as one new SQL projection plus pure contract helpers run by the API (three member reads and one reminder route), copy `packages/modules/events/server/reminders.ts` and `notifications.ts` almost line for line into the courses module, resolve every access-filtered audience through new courses definers that call `app.course_locked_ids_for` / `app.live_locked_ids_for` per membership, and settle the live-reactivation gap before planning the reminder plan.

## Project Constraints (from CLAUDE.md)

- All business logic goes through the Hono API on Cloud Run; the web reads data only through the API. The two exceptions are Supabase Auth via `@supabase/ssr` and read-only Realtime Broadcast. Início, Trilhas and Progresso derivations and the reminder writes therefore live in the API and the database, never in the browser.
- Each feature is a self-contained module package (schema, API, UI) that depends only on the kernel and other modules' published contracts (MOD-01..05). The courses module must not import the notifications or store modules. `turbo boundaries` (`pnpm boundaries`) enforces this.
- UI follows the design prototype (`reference/frontend-design/`). Components are ported into module packages, not refactored in place (PROTOTYPE.md). Prototype-less surfaces go through the sketch gate (D-365/D-417).
- Multi-tenant from day one, with tenant-scoped data and RLS as defense in depth. Every policy gets a cross-tenant negative pgTAP test. The `postgres`/`service_role` roles are never used for tenant queries; the API runs as `api_user` + `set local role authenticated`.

### Pattern 3: Streak in SQL, in the tenant's timezone

**What:** A definer returning one int from the caller's own completions. It uses gaps-and-islands over distinct local dates, anchored on today or yesterday (D-441).

**Verified:** The probe below ran on the local Postgres with `now = 2026-10-16 01:30Z` (22:30 on 10-15 in São Paulo) and completions on local 10-15, 10-14, 10-13 (one of them at 02:00Z on 10-14, which is local 10-13) and 10-11. It answered `today = 2026-10-15, start = 2026-10-15, streak = 3`. UTC bucketing would have answered 2. [VERIFIED: local psql probe this session]

```sql
-- Source: probe run this session; tenants.timezone is text not null default 'America/Sao_Paulo'
-- [VERIFIED: packages/core/db/schema/tenants.ts:28 "timezone: text().notNull().default('America/Sao_Paulo'),"]
create or replace function app.course_member_streak() returns int
language sql stable security definer set search_path = '' as $$
  with tz as (
    select t.timezone from public.tenants t where t.id = app.tenant_id()
  ), days as (
    select distinct (p.completed_at at time zone tz.timezone)::date as day
      from public.course_lesson_progress p cross join tz
     where p.tenant_id = app.tenant_id()
       and p.user_id = app.user_id()
       and p.completed_at is not null
  ), today as (
    select (now() at time zone tz.timezone)::date as d from tz
  ), anchor as (
    select case when exists (select 1 from days, today where days.day = today.d) then today.d
                when exists (select 1 from days, today where days.day = today.d - 1) then today.d - 1
           end as s
      from today
  ), islands as (
    select day, day - (row_number() over (order by day))::int as grp from days
  )
  select coalesce((
    select count(*)::int from islands i
     where i.grp = (select i2.grp from islands i2, anchor where i2.day = anchor.s)), 0)
$$;
```
Notes: the streak deliberately counts every own completion in the tenant, even on courses that are now archived (D-440: "the history is complete"). It takes no parameter (D-440: never from the client). `now()` is the transaction instant on the database clock. There is no `limit` (pgTAP 040 keeps an allow-list of `limit 1` functions, `040-schema-conventions.sql:263-271`).

### Pattern 5: Live reminder job, a near-verbatim copy of events reminders

Copy `packages/modules/events/server/reminders.ts` [VERIFIED: read in full, lines 1-215] with these changes:
- one window (`'15m'`), `LIVE_REMINDER_OFFSET_MS = LIVE_JOIN_LEAD_MINUTES * 60_000` (reuse `LIVE_JOIN_LEAD_MINUTES = 15`, `contracts/index.ts:1281`);
- singleton key `{liveId}:{startsAtEpochSeconds}` (events: `{eventId}:{window}:{epoch}`, `reminders.ts:55-61`);
- arm sites: the reminder `PUT` (inside its `withTenantTx`, after the insert), `updateLive` when `startsAt` changed (inside its transaction, only if the live has opt-ins, or always, since the job is a no-op without recipients), and the reactivation path (Open Question 1);
- fire-time read: `select cancelled_at is not null as cancelled, starts_at = $start::timestamptz as starts_match, to_char(starts_at …)` from `course_lives` in `coursesSystemCtx(tenantId)`, plus `moduleFlags.isEnabled(ctx, 'courses')`;
- skip reasons: `not_found | cancelled | moved | started | late | module_off`. Pick a late tolerance below 15 minutes (recommend 10). `!(now < starts_at)` already stops any reminder after the start;
- on pass: `emit(ctx, 'course.live_reminder_due', { tenantId, liveId, startsAt })` then `await flush(ctx)` before returning (`reminders.ts:199-206`).

`enqueueInTx` works from a member's lane: it switches to `api_user` only for the insert into `pgboss` and restores the caller's role [VERIFIED: `packages/core/server/jobs/boss.ts:135-140, 162-190`]. Arming on the member's opt-in is therefore legal and needs no backfill for lives created before this phase.

The `short` queue policy drops a second job with the same singleton key while the first is still `created` [CITED: in-repo docblock `boss.ts:132-133` "a key whose job is still `created` is dropped by the `job_i1` partial unique index and `send` returns `null`"]. So 100 opt-ins arm one job, and a start moved back to its original value reuses the waiting job, whose stale check then passes again.

### Pattern 7: Lesson batching with a watermark

1. Add `course_lessons.announced_at timestamptz` (nullable). The custom migration backfills `announced_at = created_at` for every existing row, so the first batch never announces the back catalogue.
2. `setCourseStatus` on `→ published`, in the same transaction: `update course_lessons set announced_at = coalesce(announced_at, now()) where tenant_id = … and course_id = …`. The course notice covers these lessons.
3. `createLesson` when the module's course is `published`: `enqueueInTx(tx, 'courses.lessons_batch', { tenantId, courseId }, { startAfter: now + 30 min, singletonKey: courseId })`. While that job waits, every later lesson's enqueue is dropped and absorbed.
4. The job, in `coursesSystemCtx`: if courses is off or the course is not published, it ends. Otherwise it runs `select app.course_lessons_claim_batch(courseId)` (a definer `update … set announced_at = now() where announced_at is null and … returning 1`, which returns the count). If count > 0 it emits `course.lessons_added {count, batchAt}` and flushes.
5. Recommended refinement [ASSUMED]: the claim takes only lessons with no video or a `ready` video. If unclaimed lessons remain and the oldest is less than 24 h old, the job re-arms itself +30 min. This keeps "5 aulas novas" from announcing videos still processing (`resolveLessonVideo` accepts any status, `service.ts:486-524`).

### Anti-Patterns to Avoid
- **Deciding a lock in TS.** Never compare entitlements in the service or the web. Read `lock_reason` / `locked` from the definers.
- **Adding keys to an existing strict response schema** (`learnLiveSchema`, `learnCourseSchema`): the web parses with `.parse()` on `.strict()` schemas [VERIFIED: `apps/web/lib/courses-learn.ts:154,191,261`], and the API deploys before the web, so the deployed web would fail every live page until its own deploy. Put the reminder state behind the new `GET …/reminder` route and carry overview data in new schemas.
- **Reading opt-ins with a lane select in the worker** (returns nothing; see Pattern 4).
- **Calling `app.course_locked_ids()` in the worker**: it reads the zero user's entitlements under the `support_tenant` claim and answers `'{}'` (staff branch), so it would report everything open. Use the `_for(p_user)` variants.
- **`limit 1` in a new definer** (pgTAP 040 allow-list).
- **A title in a domain event payload or log line** (T-07-31, T-05-06).
- **Notifying from inside the write transaction.** Emit after commit (the bus does it); only `enqueueInTx` goes inside.

## Common Pitfalls

### Pitfall 1: The live-reactivation path does not exist
**What goes wrong:** Plans implement D-447 "reactivated after a cancel" and D-448 "live … reactivated" against a write path that is missing.
**Why it happens:** `updateLive` throws `409 { courses: 'live_cancelled' }` on a cancelled live [VERIFIED: `service.ts:2479-2481`], and the admin routes list only `/lives/{liveId}/cancel` (`routes.ts:491`). No `reactivate` exists anywhere in the courses module (`grep -n "reactivat"` → nothing).
**How to avoid:** Resolve Open Question 1 before planning. If the route is added, it needs its own isolation entry, a UI control on the admin live form (prototype-less, so sketch gate) and an e2e.
**Warning signs:** A plan task "re-arm on reactivation" with no route task.

### Pitfall 2: The worker cannot see own-row data
**What goes wrong:** The reminder source selects `course_live_reminders` in the fan-out lane and finds nobody.
**Why it happens:** Owner-scoped policies against the zero user (`system-context.ts:7`).
**How to avoid:** Read through `app.course_live_reminder_user_ids` (Pattern 4). pgTAP asserts that the zero-user lane reads 0 rows from the table and N from the definer.

### Pitfall 3: Strict response schemas break across the deploy window
**What goes wrong:** A new key on `learnLiveSchema` makes the old web's `.parse()` throw.
**How to avoid:** Use new routes and new schemas only (Anti-Patterns). Keep every 08.5 response byte-compatible.

### Pitfall 4: Bare `/cursos` links and e2e landings
**What goes wrong:** Category chips, "Todas", e2e specs and the admin preview tests land on Início instead of the catalogue.
**Concrete list** [VERIFIED: grep this session]: `apps/web/lib/courses-member-view.ts:66-68`. `apps/web/e2e/courses-member.spec.ts` lines 135 (D-419 catalogue test), 200-213 (chip hrefs `'/cursos'` and `/cursos?categoria=`), 222, 313-334 (`?ver=aluno` and `?ver=admin` expect `courses-member-catalogue`), 345. `apps/web/e2e/courses-admin.spec.ts` lines 152-153, 452-454 and 485-493 (non-manager or preview expects `courses-member-catalogue` at `/cursos`). `apps/web/e2e/shell.spec.ts:229` lands on `/cursos` but asserts only the nav `aria-current`, which still holds. Also update `apps/web/e2e/affected-map.json` for the new files.
**How to avoid:** Move each landing to `?aba=cursos` (keeping `&ver=aluno` where present) and give Início its own `data-testid` (for example `courses-member-home`) inside the same `courses-member-catalogue` frame, or rename the frame testid deliberately.

### Pitfall 5: `members` audience excludes support staff
**What goes wrong:** Support agents get none of the course notices, against the 08.6 discretion default.
**Why it happens:** `app.notifications_fanout` maps `members` to `m.role = 'member'` only (D-229, `notifications_functions.sql:68`).
**How to avoid:** Use `users` with a definer list (Pattern 6), or confirm D-229 applies (Open Question 2).

### Pitfall 6: A time-window-only batch loses lessons
**What goes wrong:** A lesson whose transaction straddles the batch job's start is enqueued while the job is still `created` (dropped by the singleton) but is not yet visible to the job's read. Nothing ever re-arms it.
**How to avoid:** Use the `announced_at` watermark claim (Pattern 7). A lost-arm lesson is then caught by the next lesson's batch at worst. Document the residual in the code comment.

### Pitfall 7: The reminder fires late or after the start
**What goes wrong:** Copying the events tolerance (30 min) lets a 15-minute reminder fire after the live starts.
**How to avoid:** The `started` check (`now < starts_at`) comes before the late check, and the tolerance is ≤ 10 min. Unit-test the skip table (events precedent `reminderSkipReason`, `reminders.ts:140-154`).

### Pitfall 8: The streak bucketed in UTC or on the web clock
**What goes wrong:** A 22:30 completion in São Paulo counts for the next day.
**How to avoid:** Pattern 3 in SQL. A pgTAP case inserts a completion at `(date_trunc('day', now() at time zone tz) + interval '23 hours') at time zone tz` style local instants and asserts the count. Use the tenant's own timezone (rede-demo `America/Sao_Paulo`, verified).

### Pitfall 9: "Hours watched" double counts or counts invisible lessons
**What goes wrong:** Summing every own completed row includes soft-deleted lessons and archived courses, or counts the replay lesson of a draft course.
**How to avoid:** Derive `lessonsDone`, `secondsWatched` and `coursesDone` from Pattern 1 (published courses, live lessons). The streak alone uses all own rows (D-440). See Assumption A1.

### Pitfall 10: Per-membership `_for()` calls in large audiences
**What goes wrong:** `app.course_locked_ids_for(m.user_id)` runs once per membership (it aggregates the tenant's link table each time).
**Why it is acceptable now:** It is pilot scale (hundreds of members), it runs in the worker and it is bounded by one tenant.
**How to avoid future pain:** Keep it inside a definer so a later set-based rewrite changes one function. Log the counts (ids-only) to watch the duration.

### Pitfall 11: The sketch gate blocks the UI tasks
**What goes wrong:** UI tasks are planned before the UI-SPEC/sketch approval. The memory note "UI gate blocks plan-phase" says frontend phases exit at the UI-SPEC gate after research.
**Prototype-less surfaces that need the sketch:**
- the six notification rows and their glyphs and copy;
- the push banner copy;
- Início's empty-school state and the hidden-section behaviour;
- the locked variant of the next-live card ("Comprar para liberar" instead of the toggle);
- the reminder toggle on the 08.5 live page;
- the admin-preview disabled toggle and its hint;
- the Trilhas list layout for several tracks and the "bloqueada" step (the prototype shows "PREMIUM");
- the Progresso page without the certificates, achievements ("Conquistas") and demo blocks;
- the "Reativar live" admin control, if added.
The prototype covers the hero, shelf, track card, streak badge, chips, StatBlock and course-by-course.

### Pitfall 12: TDD red evidence and integration filtering
**What goes wrong:** The TDD gate expects TAP output and Vitest never emits it. `pnpm test:integration -- x` does not filter. Seed-pinned tests break on UAT residue.
**How to avoid:** Run single files with `pnpm --filter @rede-social/api exec vitest run tests/integration/<file>`, run pgTAP before integration, always `pnpm db:reset && pnpm db:seed` first, and use a throwaway normalizer for TDD red evidence (memory notes).

export async function setLiveReminder(ctx: RequestContext, liveId: string, on: boolean) {
  if (ctx.role === 'admin_tenant') return null;                       // 204, D-422 preview
  return withTenantTx(ctx, async (tx) => {

      select x.locked, x.cancelled_at is not null as cancelled,
             to_char(x.starts_at at time zone 'utc', ${ISO_MICROSECONDS}) as starts_at,
             x.starts_at <= now() as started
        from app.course_live_cards(${liveId}::uuid) x`);
    if (!card) throw new ApiError(404, 'NOT_FOUND');
    if (!on) {
      await tx.execute(sql`delete from course_live_reminders
        where tenant_id = ${ctx.tenantId}::uuid and user_id = ${ctx.userId}::uuid and live_id = ${liveId}::uuid`);
      return { on: false };
    }
    if (card.locked) throw new ApiError(403, 'FORBIDDEN', { courses: 'live_locked' });
    if (card.cancelled || card.started) throw new ApiError(409, 'CONFLICT', { courses: 'reminder_closed' });
    await tx.execute(sql`insert into course_live_reminders (tenant_id, user_id, live_id)
      values (${ctx.tenantId}::uuid, ${ctx.userId}::uuid, ${liveId}::uuid) on conflict do nothing`);
    await armLiveReminder(tx, { tenantId: ctx.tenantId, liveId, startsAt: card.starts_at });
    return { on: true };
  });
}
