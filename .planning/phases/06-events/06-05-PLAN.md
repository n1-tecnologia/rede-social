<planning_decisions>
1. **The function also returns `starts_at`**: `returns table (outcome text, checked_in_at timestamptz, starts_at timestamptz)`. `event.checked_in`'s payload needs the start (Phase 7 reads payloads alone), and the function has already read the event, so a second read would be a second statement for a value in hand.
2. **The upsert's RETURNING is captured into variables**, and the function returns one row after it. When the `do update … where checked_in_at is null` arbiter matches nothing (a racing check-in won), the function re-reads and answers `already` rather than returning an empty set, and the service never sees "no row".
3. **Seed and e2e fixtures read the code only through test helpers** (`adminSql` / the superuser e2e connection). The member-facing app never can. 06-07 shows it to the admin.
</planning_decisions>
