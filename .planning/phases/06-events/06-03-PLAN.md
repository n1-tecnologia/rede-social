<planning_decisions>
1. **The guard is one INVOKER trigger** (RESEARCH §Pattern 4), not a CHECK, because a CHECK cannot read another table. It reads the event `FOR SHARE`, which serialises the answer against a concurrent cancel or edit. Because the refusal is `RAISE … USING errcode = '23514', constraint = '<name>'`, the service maps it exactly as it maps a CHECK violation. Postgres fires `BEFORE INSERT` row triggers before the `ON CONFLICT` arbiter, so the guard sees every attempted RSVP tuple, including one that then conflicts.
2. **The select policy is tenant-wide; the write policies are self-only.** The in-lane counts (`count(*) filter …`) need every row of the event visible to the member's lane. D-206's privacy is an API property: no member payload projects another member's row, which is the flagged prohibition this plan carries. CONTEXT asks for RLS-level secrecy only for the URL and the code, and 06-01 already delivers that.
3. **Counts are read-time, not trigger-owned counters** (RESEARCH alternatives, Pitfall 3). A counter row updated inside the guard's `FOR SHARE` transaction would upgrade the lock and deadlock two concurrent RSVPs.
4. **Seeding answers on started or past events uses the time-travel sequence.** The guard applies to the admin lane too, so the seed inserts or moves the event into a window where the write is legal, writes the attendance, then UPDATEs the event's times. Only attendance writes are guarded, and moving an event's times after answers exist is D-214's own "every field stays editable". Tests and e2e fixtures use the same sequence.
5. **`PUT /v1/events/{id}/rsvp`** carries `requirePermission('events.attendance.respond')` (the locked "every write carries requirePermission('events.…')" rule, RESEARCH permissions table). V1 grants it to all three roles, so no member is refused, but granting or revoking it later is a manifest line.
</planning_decisions>
