<planning_decisions>
1. **D-217 store shape: a separate `event_secrets` table behind an INLINE role-claim policy.** The policy is `tenant_id = app.tenant_id() and app.tenant_role() = 'admin_tenant'`, and RESEARCH's `app.events_staff()` helper is not used. A policy that calls a helper function would need that function created before the generated `CREATE POLICY` statement, and drizzle-kit emits the policy inside the generated file. The inline literal keeps the policy next to its table, reviewable in the schema, and free of any migration-ordering hazard. Widening it later (for example to `support_tenant`, RESEARCH open question 1) is a one-line schema edit that drizzle-kit emits as `ALTER POLICY`, plus one manifest line. Column privileges were rejected because both lanes are the same `authenticated` DB role, so they cannot tell an admin from a member (RESEARCH).
2. **`events` keeps `tenantIsolationPolicy`** (for all). The 06-03 guard trigger reads the event row `FOR SHARE` from a member lane, which needs the UPDATE policy to see the row. This is the same posture every Phase 4/5 content table has, with `requirePermission` as the API write gate.
3. **Two deferrable FKs are hand-written and appended to the generated migration.** drizzle-kit cannot express `DEFERRABLE` (the 05-05 precedent: hand-written FKs survive `db:generate`). The composite FK carries the XOR across the two tables through a redundant `event_format` discriminator (the D-53 pattern), and the existence FK makes "every event has exactly one secrets row" a commit-time fact. Referential ACTIONS cannot be deferred, so `on delete cascade` fires immediately while the update check waits for commit (RESEARCH A1; pgTAP proves it here and 06-04 proves the format switch).
4. **Every check-in code is generated at create time, for both formats** (`checkin_code` is NOT NULL). An online event carries an unused code, so a later format switch to in person (D-214 keeps every field editable) needs no code backfill.
5. **The full refusal vocabulary is declared now.** `EVENT_ISSUES = ['name_required', 'end_before_start', 'location_required', 'url_required', 'url_invalid', 'cover_invalid', 'rsvp_closed', 'cancelled', 'attendance_locked', 'checkin_not_open', 'checkin_closed', 'wrong_code', 'too_many_attempts', 'reactivate_started', 'event_ended']`. Later plans raise the rest, so the web switch is exhaustive from day one (the COMMUNITY_ISSUES `archived` precedent). Input problems are `400 VALIDATION_FAILED`, state and time refusals are `409 CONFLICT`, and misses are a bare `404 NOT_FOUND` (D-23).
6. **`period` is a closed enum that does NOT clamp**, and `limit` clamps (the communities `status`/`limit` split). The web translates its own pt-BR `?periodo=passados` and sends `past` only for that exact single value. Any other URL value lands on Próximos silently (D-93).
7. **A start already in the past is accepted on create (RESEARCH A6).** Such an event goes straight to Passados. A test pins it so it is never a surprise, and a `starts_in_past` refusal can be added later as one code if the pilot objects.
8. **Phase 7 needs the event title for reminder text, and no payload carries it (RESEARCH open question 2).** This plan keeps payloads to ids and instants (the logging rule) and records the gap for Phase 7 in its SUMMARY under "Notes for Phase 7". It does not add a title to the payload.
9. **Nav order 40 / no home slot yet.** The home slot (`order: 7`) lands with its renderer in 06-08. Declaring it now would put a slot with no renderer on the bootstrap.
</planning_decisions>
