# Phase 09.4: Code Review Report

**Reviewed:** 2026-10-27
**Depth:** standard
**Files Reviewed:** 65 (`move/run.ts`, `fake.ts`, `bootstrap.ts` and `tenants.ts` were read through their phase diff and the call sites that matter)
**Status:** issues_found

## Summary

The token handling is sound where it matters most. I found no path by which the management token reaches a log, an audit row, an API answer, argv, env, a Job parameter, React props, `sessionStorage` or a client bundle:

- `ProjectProviderError` and `TokenRefusal` messages carry only a kind, a status or a closed code.
- The pino root logger redacts `token` and its siblings one level down.
- The audit table has no column that can hold a token.
- The strict Zod answers have no token field.
- The wizard keeps the token in provider memory only, outside the `PERSISTED_KEYS` allow-list.
- The CLI scripts read the token only through the TTY-only hidden prompt.

The AAD `<projectId>:mgmt_token` is applied consistently at all four seal sites and by `reseal.ts` (`aadOf` strips `_sealed`). The provider and allow-list caches are keyed `<id>:<credentialVersion>`, and the replace and owner-change paths drop them. Authorization is correct: `requireSuperAdmin()` is on the parent router, and `refuseWhileMoving` already covers the new `PUT /tenants/:id/database/token`, so a replacement during an open move gets 409. The migrations match the Drizzle schema (checks, FK, index, RLS with zero policies). The token state has one derivation (`tokenState`), and the SQL filter for `banco=problema` is the same predicate as `tokenState` for the five attention states.

I found no Critical defect. The six warnings are mostly places where the "a dead credential must not degrade the member-facing tenant" rule or the "one bad project must not stop the others" rule is not honoured at an edge. The other two are an unguarded probe write and a placeholder that still ships in the catalog.

## Warnings

### WR-01: An unreadable sealed token takes a healthy tenant offline for its members

**File:** `packages/core/server/projects/health.ts:136-153` (`judge`); effect at `packages/core/server/tenancy/tenant-host.ts:71`
**Issue:** `getProjectProviderFor(project)` is awaited inside the same `try` as the Management API calls. For a customer project it runs `open(project.mgmtTokenSealed, '<id>:mgmt_token')`, which throws a plain `Error` when the column does not open. That can happen with a corrupted column, an AAD mismatch, or a master key that was dropped before `platform:reseal` finished that row. The `catch` only turns a `ProjectProviderError` with `customerToken` into a token verdict (`tokenVerdictOf`). Anything else returns `{ status: 'unreachable' }`. `tenant-host.ts` maps `unreachable` to `unavailable`, so the tenant's members see the community down while its database is fine. This is the case the module header rules out: "a dead token with a working pool is `healthy` and the tenant is never held out of the shell". An unreadable sealed token is operationally a dead token.
**Scenario:** Master-key rotation. Step 4 drops the old key while one customer row still carries the old key id in `mgmt_token_sealed`. The next 5-minute sweep (`PROJECT_HEALTH_INTERVAL_S`) marks that tenant `unreachable`. Members get `TENANT_UNAVAILABLE`, while the tenant's own DB credentials still open and the DB answers.
**Fix:** Build the provider in its own `try`. For a customer project, a failure to build it must not decide the database state: skip the provider calls, let the pool ping answer, leave `token_check` unchanged, and log a distinct `project.health.token_unreadable` line with the project id only.
```ts
let provider: ProjectProvider | null = null;
try {
  provider = deps.provider ?? (await getProjectProviderFor(project));
} catch {
  if (!customer) return { status: 'unreachable', detailCode: 'unreachable', tokenCheck: null };
  log.warn({ event: 'project.health.token_unreadable', projectId: project.id }, 'sealed token unreadable');
}
if (provider) { /* existing describe/health block */ }
// then fall through to the ping
```

### WR-02: One customer project with an unreadable token aborts the allow-list reconcile for every later project

**File:** `packages/core/server/platform/reconcile-allow-list.ts:113-114`
**Issue:** `const adapter = authAllowListFor(project);` sits outside the per-host `try/catch`. For a customer project (AUTH_ALLOW_LIST=supabase), `authAllowListFor` calls `customerProviderFor`, whose `openToken` is synchronous and throws if the sealed token does not open. That throw leaves `reconcileAuthAllowList` altogether. The docblock promises "a per-host failure ... never aborts the other projects". The worker-start reconcile exists to heal project 0's allow-list after `supabase config push` wipes it (WR-09 in `docs/DEPLOY.md`). Projects are visited in ascending `ref` order, so a customer project whose ref sorts before project 0's leaves project 0's hosts unhealed after that deploy.
**Fix:** Build the adapter inside the guarded section, and count and log the failure per project.
```ts
if (hosts.length > 0) {
  let adapter: ReturnType<typeof authAllowListFor>;
  try {
    adapter = authAllowListFor(project);
  } catch {
    result.failed += hosts.length;
    log.error({ event: 'platform.domains.allow_list_adapter_failed', projectId: project.id }, 'allow-list adapter could not be built');
    total.hosts += result.hosts; total.failed += result.failed; total.projects.push(result);
    continue;
  }
  /* existing host loop */
}
```

### WR-03: Token fields are not trimmed on the create and pre-check paths, so a pasted leading space is reported as "account-wide"

**File:** `packages/contracts/src/projects.ts:297-301` (`customerProjectFields.token`), used by `precheckBodySchema` and `createTenantBodySchema`. Callers: `apps/api/src/routes/platform/projects.ts:175-177`, `packages/core/server/platform/tenants.ts:523`, `apps/web/app/(platform)/plataforma/novo/actions.ts:171-182`.
**Issue:** `replaceTokenBodySchema` trims the token, but `customerProjectFields.token` is `z.string().max(4096).optional()`. `refineCustomerProject` checks `(token ?? '').trim()` for emptiness, and then the raw value goes on. A token copied with a leading space or newline fails `token.startsWith('sbp_fc')` in `validateCustomerToken` and is reported as `token_account_wide` ("Este token vale para a conta inteira"), which is the wrong diagnosis and sends the operator to create a different token. Trailing whitespace passes validation (fetch strips it from the header), but then the padded value is what gets sealed.
**Fix:** Trim in the schema and in the web draft.
```ts
token: z.string().trim().max(TOKEN_MAX_LENGTH).optional(),
```
Also use `(input.token ?? '').trim()` in `customerFields()` in `novo/actions.ts`. The set-owner and move CLIs are already covered because `readSecret` trims.

### WR-04: The post-replacement follow-up is detached in the API process

**File:** `packages/core/server/projects/token.ts:401, 463-487`
**Issue:** `replaceProjectToken` returns right after `startFollowUp(...)`, and the HTTP answer is sent while `runTokenFollowUp` (`checkProject` plus `reconcileProjectAllowList`) is still running as an un-awaited promise. The project's own constraints put the API on request-based CPU (only the worker is "always-allocated"). After the response, Cloud Run may throttle the instance, so the allow-list reconcile that D-575(c) depends on ("re-add the domains that failed while the token was dead") can stall or never finish. The reconcile has no other trigger than worker start or the operator's per-domain "Verificar agora". The token check itself heals on the next 5-minute sweep, but the `allow_list` errors do not. `replaceCredentials` uses the same fire-and-forget pattern for its health check, but there the loss is only a status refresh.
**Fix:** Enqueue the follow-up as a pg-boss job, as the other kernel jobs do. Alternatively `await` it with a short bound before answering, since the operator is already waiting seconds on the validation:
```ts
await Promise.race([Promise.resolve(run(projectId)).catch(failed), new Promise((r) => setTimeout(r, 8_000))]);
```

### WR-05: The probe's `PATCH .../database/password` row sends a type-valid value

**File:** `scripts/probe-management-api.ts:~236-243` (the `PATCH /v1/projects/{ref}/database/password` row of `PROBE_PLAN`, body `{ password: 'x' }`)
**Issue:** The header and the `PlanRow` comment say a `write-invalid` row is sent with "a KNOWN field of the wrong type, a malformed value or an impossible id", so that nothing is applied. Every other row uses an enum, boolean or number of the wrong type. This one uses a string, which is a valid `password` type. The in-repo adapter enforces a 12-character minimum client-side (`MIN_PASSWORD_LENGTH`), which suggests the server does not refuse a short string. If the Management API accepts it, the probe resets the real project's `postgres` password to `x`, which breaks the stored `ddl_url_sealed`. The report would flag `unexpectedSuccess` only after the fact. The mode is documented as run on throwaway tokens and projects, which limits the blast radius but does not remove it.
**Fix:** Use a wrong-typed value so validation always rejects it, like the sibling rows: `body: { password: 12345 }` (or `[]`).

### WR-06: The user-facing `[PENDENTE-PERMISSÕES]` placeholder is still in the shipped catalog

**File:** `apps/web/messages/pt-BR/platform.database.json:140` (`token.howto.step3`), rendered by `TokenHowTo` in the wizard, the Token card and the replace sheet
**Issue:** Step 3 of the "Como criar o token" tutorial reads "Marque as permissões: [PENDENTE-PERMISSÕES]." `TokenHowTo.tsx` and the i18n test document that the marker is waiting for plan 17 and that the test fails while it exists. Until it is filled, an operator creating a customer token is told to tick permissions without being told which, and the test suite is red. It must not ship.
**Fix:** Write the thirteen locked permissions (from probe P1 run A) into `step3` and remove the marker.

## Info

### IN-01: Replacing or re-pinning a token without retyping the date silently erases the stored expiry

**File:** `packages/core/server/projects/token.ts:427, 437-441` (replace); `:659-660` (owner change / re-pin)
**Issue:** `const expiresAt = input.tokenExpiresAt ?? null;` is written unconditionally into `mgmt_token_expires_at`. The expiry field is optional in the sheet. Leaving it blank on an unrelated replacement therefore turns a "Vencendo" token's expiry tracking off ("Sem data de vencimento informada") without telling the operator. A new token does have a new expiry, so this may be intended. If it is, the sheet helper text should say that a blank date clears the old one.
**Fix:** Say so in `expiry.helper` for the replace sheet, or keep the old date when the field is left blank.

### IN-02: The wizard does not clear the token when the project ref changes, although its docs say it does

**File:** `apps/web/components/platform/NewTenantForm.tsx:120-123` (`setRef` only calls `clearAccess()`); contract stated at `apps/web/components/platform/wizard/TenantDraftProvider.tsx:148-151` ("cleared ... when the owner or the ref changes")
**Issue:** A token typed for project A stays in memory (and in the password field) after the operator edits the ref to B. This is not a leak. The new token validation would refuse it as `token_forbidden` or `not_found`, and the field still shows the dots of an invisible value. The comment and the behaviour disagree.
**Fix:** Call `clearToken()` in `setRef`, or fix the comment.

### IN-03: `readSecret` stores the printable tail of escape sequences

**File:** `scripts/lib/read-secret.ts:72-74`
**Issue:** The comment says "Any other control character (arrows, escape sequences) is ignored, never stored". Only the ESC byte (`< ' '`) is skipped. The rest of `\x1b[A` or `\x1b[3~` (`[A`, `[3~`) is printable and is appended to the buffer. An accidental arrow or Delete key press before Enter silently corrupts the token. The result is a confusing `token_invalid` after the operator typed a correct token. The same applies to a bracketed-paste marker split across two chunks.
**Fix:** Drop the whole CSI sequence once ESC is seen, for example by skipping from `\u001b` through the next character in `@-~`.

### IN-04: The customer-project registration is written three times, and the audit differs between the copies

**File:** `packages/core/server/projects/token.ts:283-302`, `packages/core/server/platform/tenants.ts:658-676`, `packages/core/server/projects/move/target.ts:157-177`
**Issue:** The three sites repeat the same insert (owner, org pin, sealed token, expiry, `secretKeyId`, `apiUrlFor`) and the `registered` audit event. Only `registerCustomerProject` records a refusal event (`outcome: <code>`); `createOnProject` and `registerMoveTarget` do not, so the audit trail has gaps for refused wizard and move registrations. Any change to the registration shape (a new column, a new check) has to be made in three places.
**Fix:** Extract `insertCustomerProject(tx, {...})` and a shared `recordRefusal` helper.

### IN-05: "Append-only" audit table still allows DELETE, and project deletion cascades it away

**File:** `supabase/central/migrations/20261027171238_project_token_events_hardening.sql:17, 19-21`; `project_owner_token.sql:34` (`ON DELETE cascade`)
**Issue:** The trigger blocks UPDATE only. `service_role` keeps `delete`, which is every platform-lane statement, and deleting a project removes its token history. The migration says this is deliberate, so it is not a defect. But the name and the T-09.4-07 claim overstate the guarantee. Anyone reading "append-only" will expect a `BEFORE DELETE` guard.
**Fix:** If the history should outlive a project, drop the cascade (`ON DELETE SET NULL`, since `project_id` is already nullable and `project_ref` is kept) and add a `BEFORE DELETE` trigger, or rename the intent to "update-proof".

### IN-06: A stale health result can overwrite a fresh token verdict

**File:** `packages/core/server/projects/health.ts:188-235` against `token.ts:401`
**Issue:** `checkProject` reads the project (old sealed token and `credentialVersion`) at the start and writes its verdict at the end, with no check that the version is still current. If a check that started on the old token finishes after the replacement's follow-up check, it writes `token_check = 'invalid'` over the fresh `ok`. The window is narrow (the 401 normally returns fast) and the 5-minute sweep corrects it, but until then the pill and the "Banco com problema" filter show a dead token that was just fixed.
**Fix:** Make the upsert of the token columns conditional on the version read at the start: re-select `credential_version` in the write transaction and skip the token columns on a mismatch.

### IN-07: Outbound I/O runs inside the central transaction that holds the project lock and a row lock

**File:** `packages/core/server/projects/token.ts:412-436` (`replaceLocked`)
**Issue:** The validation (up to `describe` and `listProjects`, each with 15 s timeouts and up to five 429 retries) runs while the advisory lock and `FOR UPDATE` are held on a central-DB connection. This is deliberate and documented (the same pattern as `replaceCredentials`). Worth knowing: a throttled Management API can keep that transaction open for minutes and block bootstrap claims and `reseal` on the row.
**Fix:** Optional. Validate first outside the lock, then re-validate only the cheap `describe` under the lock.

### IN-08: Smaller points

- `packages/core/server/projects/token.ts:53` — `SCOPED_TOKEN_PREFIX = 'sbp_fc'` has no trailing underscore. If real fine-grained tokens are `sbp_fc_…`, a classic hex PAT whose first two hex digits are `fc` (about 1 in 256) passes the prefix check, and the listing check is then the only thing between it and acceptance. Probe P1 would show the real format. If it has the `_`, use `'sbp_fc_'`.
- `scripts/set-project-owner.ts:113` — the `--actor` label that goes into the audit row is self-asserted. Any operator can write another's name. The web paths use the authenticated `platform:<userId>`.
- `apps/api/src/move.ts:144-147` with `move/target.ts:239-250` — the hidden prompt for the token comes before the typed `--expires` is validated, so a bad date costs the operator a typed token. Check the date shape and range (`tokenExpiryIsValid`) before prompting.
- `packages/core/server/projects/overview.ts:220` — `credentials.updatedAt` is `projects.updated_at`, which a token replacement, a re-pin or a reseal now also moves, so the Credenciais card says "atualizado há X" after a token-only change.
- `packages/core/server/projects/token.ts:506-512` — `OwnerTarget.isCentral` is always `false` (a central target throws before the object is built); the field is dead.
