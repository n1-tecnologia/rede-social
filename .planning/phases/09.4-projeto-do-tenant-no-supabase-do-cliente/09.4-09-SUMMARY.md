# Phase 09.4 Plan 09: Customer token in the pre-check and the tenant creation Summary

A tenant can now be created on a project of the customer's own Supabase account: the pre-check validates the pasted token once with the project, and the creation seals it with the organisation pin learned from the first read in the same transaction that registers the project, audits the registration and binds the tenant. Platform creation is untouched.

- **Files modified:** 5

## Accomplishments

- **Tracer (Task 1, CTK-01).** `precheckProject` with `owner: 'customer'` builds a request-token provider from the pasted token (a missing token is `token_invalid`), checks the ref shape, runs `validateCustomerToken`, and then runs the unchanged status, in-use, paused and emptiness checks through that same provider. A `TokenRefusal` maps to the reason of the same name (`org_mismatch` to `token_forbidden`). A customer 403 on `listApiKeys` is `token_forbidden`; keys listed without values still answer `manualAccess: true`. The route passes `owner`, `token`, `tokenExpiresAt` and builds its answer from `ok`, `manualAccess` and `reason` only, so `learned` cannot leave. The platform path (no `owner`, or `platform`) is not edited.
- **Creation (Task 2, CTK-01).** `createTenant` with `owner: 'customer'` and no `projectRef` is `{ projectRef: 'required' }`. `createOnProject` resolves the customer provider from the token, reads the owner of a known project (must match: `{ owner: 'mismatch' }`, checked again inside the transaction), pre-checks an unknown one with the token, maps a refusal with `mapPrecheckReason`, and adds owner, the learned `orgSlug`, `mgmtTokenSealed` (AAD `<project id>:mgmt_token`), the typed expiry and the current key id to the insert that already registers the project. A `registered` event goes in the same transaction. The private `apiUrlFor` copy is gone in favour of the shared export.
- **Guarantees (Task 3, CTK-01, CTK-14).** Tests-only: the platform pre-check and creation use only the platform token and leave no pin, token or expiry; `token_other_project` and `not_pro` are never emitted, even with a provider whose projects look Free-plan, and a customer project created here has `plan` null; a sweep with a 40-character fake token finds neither the token nor its first 8 characters in any response, captured log line, bootstrap step, audit row, health row, binding, tenant row, job payload or recorded fake call; a creation that hits the slug unique index after the project insert leaves no project row, no event and no steps.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Hardening] The owner of a known project is checked a second time inside the transaction**
- **Found during:** Task 2
- **Issue:** the plan reads the known project before the transaction; a project registered in between (by a concurrent creation or by `registerCustomerProject`) could be bound under the other owner.
- **Fix:** the same owner comparison runs on the row read under the project lock.
- **Files modified:** packages/core/server/platform/tenants.ts
- **Commit:** b00e8666

**2. [Rule 3 - Blocking] The customer test fixtures needed an empty project**
- **Found during:** Task 2 RED
- **Issue:** `rede_tenant_b` is the migrated database by default, so the pre-check answered `not_empty` for every fixture ref.
- **Fix:** the new describe resets B to the bare state in `beforeAll` and restores it in `afterAll`, like `platform-projects.test.ts` does.
- **Files modified:** apps/api/tests/integration/platform-tenants.test.ts
- **Commit:** 2857f627

**3. [Note] Acceptance counts**
`grep -c recordTokenEvent packages/core/server/platform/tenants.ts` prints 2, not 1: one line is the import, one the call. Behaviour is as planned (one call, inside the insert branch). In `platform-projects.test.ts` Biome merged the new `vitest` names into the existing import line, so the file shows one changed import line and no edited case; `platform-tenants.test.ts` shows zero removed lines.
