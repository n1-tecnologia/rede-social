# Phase 09.4 Plan 12: The move to and from a customer project Summary

The existing `platform:move-tenant` now moves a tenant onto a project of the customer's account (`--owner customer`, optional `--expires`), registering a new target with a token typed at the hidden prompt of the local wrapper, and a move back to a platform project is proven to need no new code and to touch nothing in the customer's account.

## Accomplishments

- **Tracer (Task 1, CTK-02).** A project already registered with a sealed token (plan 11) is a valid target as is: the bootstrap resolves its provider per project (plan 06), so every recorded use of the target ref is `customer` and none is `platform`; the Job path asks for nothing. `registerMoveTarget` now selects `owner` and refuses a disagreement as `target_not_ready: ['owner']` (a known platform project asked for as customer, or an explicit `platform` for a customer project); an absent owner accepts whatever the registry says. `apiUrlFor` is the shared export of plan 07 (the private copy is gone).
- **Unknown customer target (Task 2, D-567, D-571).** The token comes only from `deps.readToken`. With none (the Job), or a prompt that fails, the answer is `MoveError('target_not_ready', ['register_first'])` before anything is read or written, plus a usage line pointing at `pnpm platform:set-owner --register`. With a token, the pre-check runs on a request-token provider (`createRequestTokenProvider`, never the platform's) and its closed reasons become the detail; then ONE platform transaction under the project advisory lock inserts the project (owner customer, learned pin, token sealed under `<id>:mgmt_token`, typed expiry, current key id), the `registered` audit event and the move row. `runMoveCli(argv, { readSecret })` builds `readToken` only for a real `start` with `--owner customer`; `--dry-run`, `--resume`, `--rollback`, `--recopy`, `--status` and `--confirm-delete` never build one. `--owner` outside start/dry-run and `--expires` without `--owner customer` are usage errors (exit 2). `scripts/move-tenant.ts` is the only place `readSecret` is imported.
- **The way back (Task 3, CTK-05).** Tests only: a tenant bound to a customer project A (data physically in project 0's database, registry row owner customer) moves to a platform project B. The fake's `tokenUses` holds no entry for A, B's are all `platform`, A's registry row (owner, pin, sealed token, expiry, version, state, source, api url) and its audit count are identical before the move and after `--confirm-delete`, and no token, `sbp_fc`, organisation slug or A's ref appears in the move lines or events. A second case moves A to a registered customer C and shows C's own token was the only one used (A's token reaches only A and would have been refused). A mutation (one customer call on A inside the test) made the first case fail, then was reverted.

## Deviations from Plan

**1. [Rule 3 - lint constraint] Namespace and split imports in `move-run.test.ts`.** The acceptance criterion forbids removing any existing line of `move-run.test.ts` and `move-guard.test.ts`, but Biome merges two imports from one module. New names come from other module paths (`move/target`, `move/types`) and `vitest` extras through `import * as vt from 'vitest'`, so no existing line changed.

**2. [Clarification] Provider no longer built up front in `registerMoveTarget`.** It was built before the known-target check; it is now built only for an unknown platform target (the only place it was used). A known customer target therefore needs no platform provider. Platform behaviour is unchanged (existing cases pass unedited).

**3. [Clarification] `--owner` absent is `undefined`, not `platform`.** The plan says the default is `platform` "so every existing invocation behaves as before"; the equivalent that also satisfies "a known customer target without owner is accepted" is to pass `undefined` for an absent flag. An explicit `--owner platform` contradicts a customer project and is refused.

**4. [Note] Fixture constraints.** The typed expiry may be at most a year ahead (plan 03's rule), so the test uses today + 100 days; the resume test arms the `schema` failpoint, because arming `verify` also trips the pre-check's `describe` and the registration itself fails with `unchecked`.

**5. [Note] Header comment of `apps/api/src/move.ts`** no longer names `scripts/move-tenant.ts` (the acceptance grep for `scripts/` in that file must print nothing); it says "the local move wrapper under the repo scripts folder".

**Total deviations:** 1 lint-driven, 2 clarifications, 2 notes. **Impact:** none on scope; the copy, verify, cutover and rollback code is untouched (D-579).
