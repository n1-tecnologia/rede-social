# Phase 09.4 Plan 10: Replacing the customer token and finishing the recovery Summary

A super_admin can replace a customer project's management token through `PUT /v1/platform/tenants/{id}/database/token`; the new token is validated against the project and the registered organisation pin under the project lock before anything is replaced, and afterwards the system refreshes the token and database states together and re-adds the project's verified domains to its own allow-list, clearing exactly the errors that now succeed.

## Accomplishments

- **Tracer (Task 1, CTK-20).** `replaceProjectToken` follows `replaceCredentials`: resolve the project of the tenant, then in one platform transaction take `pg_advisory_xact_lock(hashtext('project:<ref>'))`, read the row `for update`, refuse a non-customer or central project as 409, validate with `validateCustomerToken` using the stored `org_slug`, and write the sealed token, the expiry, `credential_version + 1` and the `replaced` audit event together. After the commit the registry cache, `dropProjectProvider` and `dropAllowListAdapter` run, the log line `project.token.replaced` carries ids only, and the follow-up starts. The route returns `{ ok: true }` with `no-store` behind `requireSuperAdmin`.
- **Refusals (Task 2, CTK-20).** A `TokenRefusal` thrown inside the transaction rolls it back untouched; the code-only audit event is written after the rollback (best effort) and the API answers 400 `VALIDATION_FAILED` with `{ token: <code> }`, or `{ tokenExpiresAt: 'token_expiry_invalid' }` for the date. Tests prove the row is byte-identical after every refusal (sealed value, expiry, version, `updated_at`), exactly one new event per refusal, an organisation change refused even though the token itself is accepted, an unreachable project as `unchecked`, two racing replacements serialising with the later one winning entirely, and no token or first-8-character fragment in any response, log line or audit row.
- **Follow-up (Task 3, CTK-27, CTK-19).** `runTokenFollowUp` runs `checkProject` (token and database states refresh together, D-573) and then `reconcileProjectAllowList(projectId)` = `reconcileAuthAllowList({ projectId, clearAllowListErrors: true })`, which after each successful `add` calls `clearAllowListError(host)` (`last_error = 'allow_list'` only). The default reconcile (option absent) is not edited. A bootstrap stopped at `verify` with `token_invalid` is untouched by the replacement and proceeds after "Tentar de novo".

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The order of the follow-up could not be observed with a mock on the health module**
- **Found during:** Task 3 (GREEN run)
- **Issue:** a `vi.mock` of `projects/health` did not reach the module `token.ts` imports (the module was already loaded before the mock registered), so the "check first, then reconcile" order was not recorded; a first attempt that imported the suite's `./setup` inside a mock factory hung.
- **Fix:** the mock now wraps only `reconcileProjectAllowList` and reads the stored `token_check` through its own short connection at the instant the reconcile starts; the test asserts `reconcile after token_check=ok` after a verdict that was `invalid` before, which proves the check ran first. `token.ts` imports `checkProject` and `reconcileProjectAllowList` statically.
- **Files modified:** apps/api/tests/integration/project-token.test.ts, packages/core/server/projects/token.ts
- **Verification:** project-token suite 12/12
- **Committed in:** 5d9b45b9

**2. [Rule 2 - Missing critical] A check that throws must not skip the reconcile**
- **Found during:** Task 3
- **Issue:** the plan runs `checkProject` then the reconcile; an exception from the check would have left the allow-list errors in place for no reason.
- **Fix:** the check is wrapped in try/catch (logged by project id only) and the reconcile always runs.
- **Files modified:** packages/core/server/projects/token.ts
- **Committed in:** 5d9b45b9

**3. [Rule 2 - Missing critical] A customer project registered without a pin is pinned by its first replacement**
- **Found during:** Task 1
- **Issue:** `org_slug` can be null on a row; validation then runs in learn mode and the learned organisation would be dropped.
- **Fix:** the UPDATE writes `org_slug = coalesce(<stored>, <learned>)`; a pinned project keeps its pin (it was just enforced).
- **Files modified:** packages/core/server/projects/token.ts
- **Committed in:** 3afa9d77
