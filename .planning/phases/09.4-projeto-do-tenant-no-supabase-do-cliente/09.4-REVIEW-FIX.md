## Fixed Issues

### WR-01: An unreadable sealed token takes a healthy tenant offline for its members

**Files modified:** `packages/core/server/projects/health.ts`, `apps/api/tests/integration/project-health.test.ts`
**Commit:** 734cdb30
**Applied fix:** `judge` builds the provider in its own `try`. For a customer project, a sealed token that does not open records the token verdict `invalid` (an unreadable token is a dead token, the operator must replace it), skips the Management API calls and lets the pool ping answer for the database, like the other token verdicts. One `project.health.token_unreadable` line is logged with the project id only. A platform project keeps the old behaviour (unreachable). Tests: unreadable token with a working pool is `healthy` + `token_check = invalid` and `resolveTenantHost` stays `active`, the log line holds only the event and project id and no token; with a failing pool it is `unreachable` with `token_check = invalid`. The first test failed before the fix (token_check was `null`, and the status was unreachable).
**Note:** this records `invalid` rather than leaving `token_check` unchanged as the review suggested, as the caller asked for a visible token verdict.

### WR-02: One customer project with an unreadable token aborts the allow-list reconcile for every later project

**Files modified:** `packages/core/server/platform/reconcile-allow-list.ts`, `apps/api/tests/integration/allow-list-reconcile.test.ts`
**Commits:** afc6a907, 4a1030f8 (type-narrowing follow-up found by typecheck)
**Applied fix:** Verified real: `authAllowListFor(project)` sat outside any try/catch, and the only outer catch is the worker's, so the throw aborted the whole run. A new `adapterOf(project)` helper catches the throw, logs `platform.domains.allow_list_adapter_failed` with the project id only, and the project is counted `failed` once per host while the loop moves on. Test: the spy wrapper makes the adapter build throw for the project that sorts first by `ref`; the project after it is still fully reconciled and the totals count the failed hosts. It failed before the fix (the error escaped).

### WR-03: Token fields are not trimmed on the create and pre-check paths

**Files modified:** `packages/contracts/src/projects.ts`, `packages/contracts/tests/projects.test.ts`, `apps/web/app/(platform)/plataforma/novo/actions.ts`, `apps/web/app/(platform)/plataforma/novo/actions.test.ts`
**Commit:** 0f3364fb
**Applied fix:** `customerProjectFields.token` is now `z.string().trim().max(TOKEN_MAX_LENGTH).optional()` (shared by the pre-check and create bodies) and the web draft sends `(input.token ?? '').trim()`. The strict-input tests are untouched and still pass: blank tokens are still refused, 4096 characters pass, 4097 fail (the bound now applies to the kept value). New tests: padded token parses to the trimmed value on both bodies, the bound applies after trimming, and the web action posts the trimmed token. Both new behaviour tests failed before.

### WR-04: The post-replacement follow-up is detached in the API process

**Files modified:** `packages/core/server/projects/token.ts`, `apps/api/tests/integration/project-token.test.ts`
**Commit:** 8886729b
**Applied fix:** Smallest safe change, no new job or design decision: `replaceProjectToken` now awaits the follow-up (health check, then allow-list reconcile) for at most `FOLLOW_UP_WAIT_MS` (8 s) before answering, via `runFollowUpBounded` (replaces the fire-and-forget `startFollowUp`). The operator already waits seconds on the validation, and the work now finishes while the request still holds the CPU. A follow-up that outlasts the bound keeps running detached (same as before), and a failing or synchronously throwing follow-up is still logged by project id only and never reaches the answer. Backstops for the over-the-bound case, documented in the code comment: the token verdict heals on the next 5-minute health sweep, the allow-list on the worker's next start reconcile or the domain's "Verificar agora". Test seam `followUpWaitMs` added to `ReplaceTokenDeps`. Test: the follow-up is finished when the call returns, a hanging follow-up is cut at the bound, rejecting and throwing follow-ups are swallowed. It failed before. DEPLOY.md not changed (not needed with this choice).
**Trade-off for Igor:** a replacement answer can now take up to 8 s longer in the worst case (normally the check plus reconcile take well under that). If a pg-boss job is preferred, that is a separate change.
