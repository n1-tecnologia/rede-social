# Phase 09.4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 09.4 lets a tenant run on a Supabase project that lives in the **customer's own Supabase account**, driven by a **scoped access token limited to that one project** (never an account-level token) that Igor creates in the Supabase dashboard and pastes in the platform panel. Almost all of it is server work (provider per project, organisation pin, sealed token column, allow-list, rate limiter per token, health). The UI is small and has **one audience**: the platform operator (`super_admin`) in the platform panel, in pt-BR. **No member-facing screen changes.** This phase adds or changes these surfaces:

1. **"Novo tenant", step Dados**: the "Projeto Supabase" group gains an **owner choice** ("Projeto da plataforma" or "Projeto do cliente"). Only for "Projeto do cliente" it also shows the **token field**, an optional **expiry date**, and a short **"Como criar o token"** helper with one link. "Projeto da plataforma" is today's flow, byte for byte.
2. **Resumo and confirmation dialog**: a "Dono do projeto" row and a "Token informado" line; the dialog's `database` task is unchanged and its failure reasons gain three sentences.
3. **Banco tab**: the overview `dl` shows who owns the project (and the Supabase organisation, for a customer project); a new **"Token de acesso" card** (customer projects only) shows the token state and its replacement; a new **"Substituir token" sheet**.
4. **Error and alert copy** for the new cases: token invalid, without permission, for another project, account-wide, project in another organisation, project not Pro, plus the platform copy that said "na organização da plataforma" made owner-aware.
5. **Recommended beyond the five items Igor listed** (see PU-2): the tenant **header** and the tenant **list** carry a "Token: ..." pill when a customer token needs attention, and "Banco com problema" includes those states. Without it a token that expires in silence is found only by opening every tenant.

**What has no UI** (said plainly): creating the Supabase project from the panel; billing; any member screen (a dead token never reaches members, UI-D-551); the way back from a customer project to a platform one and the transfer of a platform project to a customer account (commands, OQ-7); re-pinning the organisation after a legitimate transfer (OQ-11); filtering the list by owner (Deferred); the per-endpoint permission mapping (OQ-1, decided in discuss-phase); the provider, pin, allow-list and limiter work.

**Design authority.** `reference/frontend-design/` has no platform panel (the prototype is the member app). The approved baseline is `09.2-UI-SPEC.md` and **sketch 014**, whose `README.md` carries `approved: true` (Igor, 2026-10-22, recorded by Claude on his instruction; the `MANIFEST.md` row still reads `pending`, which is stale). Everything here is **[designed]** in that language from shipped primitives. Nothing is ported, so PROTOTYPE.md's porting rules do not apply; its token rules do (no hex, no literal text in TSX).

**Inherited, not re-decided.** Spacing, type scale, colour model, the wizard (`TenantDraftProvider`, `WizardSteps`, `CreateTenantDialog`), the tenant frame (`TenantTabs`), the Banco tab cards (`DatabaseOverviewCard`, `BootstrapSteps`, `CredentialsCard`, `ReplaceCredentialsSheet`, `ProjectAccessFields`), the pill vocabulary (`DatabasePill`), the notice row, the write-only secret field (UI-D-514, UI-D-534, UI-D-538) and the `SegmentedControl` (UI-D-206). **Phase 09.4 declares no new token, no new primitive and no dependency.**

**Upstream decisions.** `09.4-CONTEXT.md` does not exist (discuss-phase has not run). The inputs are the ROADMAP "Phase 09.4" notes and the decisions Igor gave on 2026-10-27 (restated in the prompt and treated as locked): scoped token for one project, sealed per project and write-only, expires in at most 1 year and can be revoked, dies if its creator loses access; customer project always Pro; Igor pastes it. The visual questions this phase opens are decided below as **UI-D-549..UI-D-563** (continuing after `UI-D-548`, the highest id in any UI-SPEC: `grep -rhoE "UI-D-[0-9]+" .planning | sort -t- -k3 -n -u | tail -1` returned `UI-D-548` on 2026-10-27). Earlier visual decisions keep their numbers (UI-D-533..548 of Phase 09.2 apply unchanged wherever this document says "inherited").

**Assumptions made in this session** (the planner may overturn any with one line):
- **A-UI-1.** The owner choice is the shipped **`SegmentedControl`** (two options, "group of pressed buttons"), defaulting to "Projeto da plataforma". Never `null`, so the platform path needs no extra click and its behaviour is unchanged.
- **A-UI-2.** The token **never touches `sessionStorage`**: like the three manual-access secrets (UI-D-534) it lives in `TenantDraftProvider` memory only. The owner choice and the expiry date are not secret and join the persisted draft.
- **A-UI-3.** The Supabase **organisation is read from the project** (the same `describe` the pin uses), never typed. No organisation field in the form. If the token turns out unable to read it, OQ-5 adds a conditional field.
- **A-UI-4.** The **expiry date is typed by the operator** (optional), because nothing sourced says the Management API returns it. With the date the panel can say "Vencendo" before Supabase refuses; without it the card says "Sem data de vencimento informada." and the warning state never appears (OQ-3).
- **A-UI-5.** The **"vencendo" window is 30 days**, one constant in `@rede-social/contracts` (OQ-4).
- **A-UI-6.** The token state is a **separate axis** from the eight database states: it never changes the database pill, and never changes what a member sees (UI-D-551).
- **A-UI-7.** The panel never renders any part of the token: no prefix, no length, no last characters, no "mostrar" control. The only facts shown are the state, the expiry date the operator typed and when it was last verified.
- **A-UI-8.** The permission names are **not** written in the copy. They appear as the marker `[PENDENTE-PERMISSÕES]` in one catalog string (UI-D-557). A catalog test must fail while the marker exists, so it cannot ship by accident.

## Data the screens read (for the planner; not a UI decision)

The UI assumes these shapes. Names are proposals; the contract is what is shown and what must never be sent back.
- **Pre-check** (`POST /v1/platform/projects/precheck`): the body gains `owner` (`platform` | `customer`), and for `customer` the `token` and `tokenExpiresAt` (write-only input, `.strict()`); the answer's reasons gain `token_invalid`, `token_forbidden`, `token_other_project`, `token_account_wide`, `token_expiry_invalid`, `not_pro` (each maps to one field error). A pre-check that cannot run stays `unchecked`.
- **Creation** carries the same `owner`, `token`, `tokenExpiresAt` once; the token is sealed per project (AAD `<id>:mgmt_token`) and never echoed.
- **Overview** (`GET /v1/platform/tenants/{id}/database`): gains `owner`, `organization` (null for platform) and `token: { state, expiresAt, checkedAt } | null` (null for platform). No field of a token kind.
- **Replace** (`PUT …/database/token`): body `{ token, tokenExpiresAt? }`; answer `{ ok: true }` or a coded refusal (`token_*`, `org_mismatch`).
- **Tenant list row**: the existing `database` block gains `token: { state } | null`; the `?banco=problema` filter stays on the API and includes the token states of UI-D-560.
- **`tokenState`** (pure) lives in `@rede-social/contracts/projects` beside `databaseState`; reason codes `token_invalid`, `token_forbidden`, `org_mismatch` join `BOOTSTRAP_REASON_CODES`.
