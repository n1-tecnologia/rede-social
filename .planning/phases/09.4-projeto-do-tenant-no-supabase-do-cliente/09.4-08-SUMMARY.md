# Phase 09.4 Plan 08: The token as its own axis in the health check Summary

The health check now asks a customer project through its own provider and stores the token verdict (`ok`, `invalid`, `forbidden`, `org_mismatch`) beside the database status in one upsert: a refused token falls through to the pool ping, so a dead token with a working pool is `healthy`, no binding or host answer is invalidated, and every change of the derived token state writes one `project.token.state_changed` line of project id, from and to.

## Accomplishments

- **Tracer (Task 1, CTK-17, CTK-18).** `judge` resolves the provider with `getProjectProviderFor(project)` (the platform path is unchanged: a platform project gets the platform provider). For a customer project a caught `ProjectProviderError` with `customerToken` and code `token_invalid`, `token_forbidden` or `org_mismatch` sets `tokenCheck` to `invalid`, `forbidden` or `org_mismatch` and falls through to the ping; every other error (timeout, 5xx, a platform `forbidden`) keeps `unreachable` with today's `codeOf` and `tokenCheck: null`, so the stored check is untouched. A successful `describe` sets `ok`. `checkProject` writes `token_check` and `token_checked_at` only when a verdict exists, in the same upsert; the `changed` branch (`invalidateProject`, `invalidateTenantHost`, `project.health.changed`) is still keyed on the database status alone.
- **State and log line (Task 2, CTK-21, CTK-33).** `token-state.ts` exports `tokenStateOf` (the contracts `tokenState`; `null` for any owner but `customer`; an unknown stored check reads as never checked; `today` defaults to `todayInSaoPaulo()`) and `tokenChangeFields` (exactly `{ event, projectId, from, to }`). `checkProject` derives `from` (stored check) and `to` (new check, or the stored one when the verdict had none) and, when they differ, logs once and returns `{ from, to }` in `HealthResult.token`.
- **Nothing members feel (Task 3, CTK-19, CTK-33).** Tests only, no production change needed: `migrateAll` migrates a customer project whose provider refuses every call (the fan-out uses the DDL connection, zero provider calls); the by-host answer for a tenant on a customer project is byte for byte the same with `token_check = 'invalid'` as with `'ok'` and the tenant stays `active`; the sweep over a platform project, a dead-token customer and a working-token customer leaves the dead one `healthy` and moves no credential version and no queue sender.

## Deviations from Plan

**1. [Note - acceptance arithmetic] `grep -c "getProjectProviderFor" health.ts` prints 2, not 1**
The import line and the single call line both match. `getProjectProvider()` prints 0 and `token_check|tokenCheck` is 19 (at least 4). The intent (one use of the per-project resolver, no platform singleton) holds.

**2. [Note - acceptance arithmetic] `grep -c "project.token.state_changed" token-state.ts` printed 2 on the first draft**
The explicit return type repeated the literal; the return type is now inferred with `as const`, so it prints 1.

**3. [Rule 3 - Blocking] Duplicate import lines in `project-health.test.ts` trip biome**
Adding `./projects-setup` and the boss module as second named-import lines made biome demand a merge, which would remove an existing line (the plan forbids edits to existing lines). Both are namespace imports (`customerSetup`, `bossSenders`), the pattern plan 06 used. Zero removed lines against the plan's base commit in all three integration files.

**4. [Note] The plan's verify names `tests/integration/project-database-state.test.ts`, which does not exist**
Vitest ignores the missing filter; the core unit test `tests/project-database-state.test.ts` (17 cases) ran and passes.

**5. [Note] The sweep case checks three projects, not "checked 3"**
`checkAllProjects` also visits project 0 and any other ready project, as the existing sweep case already notes. The test asserts `failed 0` and the three results of its own projects.

**6. [Note] The in-memory pool is not re-read after a registry edit**
The first draft of the invalidation case swapped the project's sealed URL to force a failing ping; the pool is cached by id and credential version, so the case injects a failing `ping` through `HealthDeps` instead.

**Interpretation to note:** the plan says an unhealthy service "leaves `token_check` as it was". A `describe` that succeeded proves the token works, so a project that is then paused or has an unhealthy service writes `ok` (paused with a working token is `ok` in the plan's own Test 3); only a failed provider call (timeout, 5xx, platform refusal) leaves the stored check alone.
