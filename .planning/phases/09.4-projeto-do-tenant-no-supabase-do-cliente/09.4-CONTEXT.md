# Phase 09.4: Projeto do tenant no Supabase do cliente (INSERTED) - Context

**Gathered:** 2026-10-27

<domain>
## Phase Boundary

A tenant can run on a Supabase project that lives in **its own Supabase account** (the customer's). The platform operator (Igor, `super_admin`) registers that project together with a **scoped personal access token limited to that one project**; the platform stores the token sealed per project and uses it, and only it, for every Management API call about that project. Projects of the platform's own organisation keep the platform token (`SUPABASE_PAT`) and its organisation pin (`SUPABASE_ORG_SLUG`), byte for byte.

Three journeys are in scope (D-566): a **new tenant** created on a customer project (wizard), an **existing tenant moved to** a customer project (command), and the **owner change** of a project that Supabase itself transferred to the customer's account (command). The way back (customer project to platform project) is the existing move with a platform target.

Out of scope: creating the customer's Supabase project from the panel, billing, any member-facing screen, e-mail alerts, a panel button for the move or the owner change (see Deferred).

Execution waits for Phase 09.2 to close (its plan 25 hosted proofs). `plan-phase` may run ahead; STATE stays on 09.2 plan 25 (D-579).

</domain>

<decisions>
## Implementation Decisions

### Already decided before this discussion (Igor, 2026-10-27; restated, not reopened)
- **Locked before this discussion [informational]:** The credential is a Supabase scoped personal access token limited to ONE project, never an account-level token. Expiry up to one year, revocable, and it stops working when its creator loses access. A customer project is always on the Pro plan, the customer owns the project and answers for it, and Igor creates the token and pastes it into the panel (ROADMAP "Phase 09.4" notes).
- **Visual contract [informational]:** The visual contract is `09.4-UI-SPEC.md` (UI-D-549..UI-D-563, approved 2026-10-27): owner choice in "Novo tenant", token field and optional typed expiry date, "Como criar o token" helper, Token card and "Substituir token" sheet in the Banco tab, the "Token: ..." pill in header and list, 30-day "Vencendo" window, a dead token never affects members (UI-D-551). The pending approvals PU-1..PU-5 were accepted by Igor the same day; the approval of sketch 015's README stays in Igor's hand.

### Which journeys are in
- **D-566:** Three journeys. (1) **New tenant on a customer project** through the "Novo tenant" wizard (UI-SPEC). (2) **Move an existing tenant to a customer project** with the existing move command (`scripts/move-tenant.ts`, D-536): the target is a project of the customer's account, bootstrapped like a new tenant's, with its token. (3) **Change the owner of a project already registered** to "customer" when Supabase itself transferred it to the customer's account, with no data copied (D-568). The way back, customer project to platform project, needs no new code (the target is then a platform project); the planner adds a test that proves it and that the command does not touch anything else in the customer's account. — **Reversibility:** costly — the move command and the registry columns of D-571/D-573 carry the owner concept into every project-aware call site.
- **D-567:** Every command that needs a token for a project the registry does not yet know (the move target, the owner change) asks for it through a **hidden terminal prompt**: no echo, never in `argv`, never in an environment variable, never in shell history or the process list. The token is held in memory, sent once to the validation of D-570, sealed, and dropped. Same discipline as the panel's write-only fields (UI-D-561). Commands that act on an already registered project read the sealed token from the registry and ask for nothing.
- **D-568:** **Owner-change command** (name is the planner's; proposal `pnpm platform:set-owner --tenant <slug>`): asks the token (D-567), runs the whole validation of D-569..D-572 (project reachable, token scoped to that project, organisation read), seals the token, stores `owner = customer` and the organisation pin, bumps `credential_version`, writes an audit row (never the token), and copies nothing. No screen and no design gate. It is also the **re-pin path** after a legitimate organisation change of an already customer-owned project: the same command reads the organisation again and stores the new pin (answers OQ-11). Direction customer to platform is the planner's call if it costs nothing; only platform to customer is required. — **Reversibility:** reversible — a registry update and a sealed value.

### What the system refuses (token validation)
- **D-569:** **One permission list** for the token, used for creating, maintaining and the break-glass reissue (no separate "maintenance" token). Thirteen permissions, from the Supabase table read on 2026-10-27 (`https://supabase.com/docs/guides/platform/personal-access-tokens.md`, summarised, levels per operation): **Project Settings** (Read-write: `describe`, `health`, and `PATCH config/auth` needs it at Read-write), **API Keys** (Read-write: `POST api-keys` creates the keys), **API Key Secrets** (Read: reveals the key values), **Connection Pooling** (Read), **Database** (Read: the read-only query), **Database Config** (Read-write: `PATCH database/password`), **Migrations** (Read), **Storage** (Read), **Storage Config** (Read-write), **Auth Config** (Read-write), **Auth Signing Keys** (Read-write), **Data API Config** (Read-write), **Realtime Config** (Read-write). Because the list includes **API Key Secrets**, a customer project never needs the manual-access fallback (answers OQ-10); the fallback stays in the code path for safety. The table came from a summarised page, so **the list is unproven until D-578's probe runs against a real scoped token**; until then `[PENDENTE-PERMISSÕES]` in `TokenHowTo` stays and the catalog test keeps failing (A-UI-8). — **Reversibility:** reversible — copy and a probe list; but a token's permissions cannot be changed after creation, so a wrong list means new tokens for every customer project already registered.
- **D-570:** **Account-wide tokens are refused by two independent checks**, both at registration, replacement and owner change (not on every health tick): (a) the token must start with `sbp_fc` (the documented prefix of scoped tokens; legacy full-access tokens show a Legacy badge and have no documented prefix); (b) a **behavioural check**: list the account's projects (`GET /v1/projects`) and refuse with `token_account_wide` if the answer contains any project other than the target (a 403 or a list holding only the target passes). This call is a 21st operation: `COVERAGE.md` moves `GET /v1/projects` from the `group:listing-and-organisations` OPT-OUT to INTEGRATE, restricted to registration, and the equality test (20 INTEGRATE + OPT-OUT = 169) is updated. What a scoped token really answers to that call (403, empty, or filtered to its own project) is unproven: the probe settles it (D-578) and the researcher reads the answer. If the prefix is wrong but the check passes, or the reverse, the token is refused: both must pass.
- **D-571:** **The organisation is pinned on the first read.** At registration the system reads the project's organisation slug with the token (`describe`), stores it on the registry row, and from then on every Management API call about that project compares it; a mismatch is refused as `org_mismatch` and the token state becomes "Organização diferente" (UI-D-553). The organisation is never typed and the wizard shows no extra line; the Banco tab shows it (UI-D-552). Platform projects keep `SUPABASE_ORG_SLUG` exactly as today. The pin is stored per project, so a platform project and a customer project never share a pin. (Answers OQ-5 and the "organisation pin per project" point of the ROADMAP.)
- **D-572:** **The plan (Free or Pro) is informative.** The researcher looks for a way to read it with a project-scoped token. If one exists, the pre-check refuses a Free customer project with the UI-SPEC sentence (`not_pro`) and the Banco notice appears. If none exists (likely: billing is organisation-level), the Banco shows "Plano: Não informado", nothing blocks, and the proof notes and `docs/DEPLOY.md` say that keeping the project on Pro is the operator's responsibility. No new screen and no confirmation checkbox (answers OQ-8).

### Dead token: what stops and what keeps running
- **D-573:** **The token state is its own axis and never takes a tenant offline** (UI-D-551 confirmed on the server side, answers OQ-2). The health job, for a customer project, first calls `describe` with the token: a refusal sets the token state (`invalid`, `no permission`, `org mismatch`), and the project's database state then comes from the pool ping alone ("Pronto" or "Inacessível"); the one thing lost is the paused or not-paused fact. This needs the provider error to carry a refinement beyond today's `org_mismatch`: `ProjectProviderError.code` gains `token_invalid` (401) and `token_forbidden` (403 on an operation), so `kindOfStatus` no longer folds every 401/403 into one `forbidden`. The token state is derived by one pure `tokenState` function in `@rede-social/contracts/projects` (precedence of UI-D-553). A single check refreshes both the database state and the token state, including "Verificar agora" and the follow-up after "Substituir token" (answers OQ-9).
- **D-574:** What keeps working with a dead token, because it uses the sealed database URL and service key and never the Management API: sign-in and sessions, all member screens, Storage, Realtime, the schema migration fan-out ("migrar todos"), the worker's per-tenant queues. What degrades: the paused-or-not fact, allow-list writes (new domains), the break-glass reissue, the registration of a move target, a bootstrap step that calls the Management API. The tenant is never suspended, never marked "atrasado" and never shown a token message because of this.
- **D-575:** **After "Substituir token" succeeds** (validated against the project and the registered organisation before anything is replaced, UI-D-555), the system on its own: (a) bumps `credential_version` and drops the cached provider and allow-list adapter of that project; (b) runs the follow-up health check; (c) re-runs the existing allow-list reconcile (`platform/reconcile-allow-list.ts`) for the verified domains of the tenants bound to that project and clears `last_error = 'allow_list'` on the ones that now succeed; (d) leaves a bootstrap that stopped on a token step to "Tentar de novo" as in 09.2. Before this decision the only recovery was pressing "Verificar agora" per domain (`ensureVerifiedSideEffects`); that button keeps working.
- **D-576:** **The operator is warned in the panel and in the log**, nothing else. Every token state change writes one structured line (`project.token.state_changed`: project id, from, to; never the token, its prefix or its length) so a Cloud Logging alert can be built on it. An e-mail or push to the operator is a new capability (see Deferred).

### Proof and delivery order
- **D-577:** **The hosted proof uses a second Supabase organisation in Igor's own account** with a Pro project and a scoped token limited to it. It proves the organisation pin, the scoped token, the refusal of an account-wide token, the replacement, and the dead-token states. "Creator lost access" and "token revoked" get the same answer from Supabase, so revoking the token covers both (UI-D-553). A real third-party account is optional and is not a closing condition. The evidence goes in `09.4-HOSTED-PROOFS.md`, in the same shape as `09.2-HOSTED-PROOFS.md`; only Igor writes `passed` in a row (an agent never records a pass for him).
- **D-578:** **The permission probe comes first.** `scripts/probe-management-api.ts` gets a mode that takes the token through the hidden prompt of D-567 and prints, per operation of the INTEGRATE list (and the project listing of D-570), only allowed or denied with the HTTP status: no key, no token, no host with credentials (the existing output rules, T-09.2-60). Igor creates a throwaway token with the thirteen permissions on a scratch project and runs it once; its output fixes the permission list and what a scoped token answers to the listing call, and only then does the catalog string replace `[PENDENTE-PERMISSÕES]`. Igor confirmed on 2026-10-27 that his account shows the scoped-token choice (organisation, project, permissions), so the "alpha, gradual rollout" wording of the Supabase page is not a blocker for him. The probe is a first-wave task with `autonomous: false`.
- **D-579:** **Order:** `plan-phase 09.4` may run now; `execute-phase 09.4` starts only after 09.2 closes, because this phase edits the code 09.2 just delivered (provider, health, move, allow-list) and Igor's plan 25 proofs run against it. One phase at a time stays the rule here.

### Carried forward from Phase 09.2 (still true, amended where said)

### Claude's Discretion
- **Provider per project.** `getProjectProvider()` (zero arguments, env singleton) becomes `getProjectProviderFor(project)`: a platform project returns the env singleton; a customer project builds a provider from its sealed token, cached by project id and credential version and bounded like `authAllowListFor` (least recently used leaves first). Calls made before the project exists (pre-check, owner change, move target) build a provider from the token in the request and never cache it. Callers to change: health, pre-check, credentials, reissue, move target, tenant creation, allow-list.
- **Rate limiter.** One limiter of 100 requests a minute per token instead of one per process; a 429 pauses only that token's limiter. The researcher checks whether Supabase's 120-a-minute limit is per user or per token: if per user, several tokens created by the same person share it, and the existing 429 retry is what absorbs that.
- **Registry.** New columns (or a small table) on `platform.projects` for the owner, the organisation slug, the sealed management token, the typed expiry date and the last token check; a central migration under `supabase/central/migrations/`; pgTAP for them; the re-seal command (`scripts/reseal.ts`) and the credential replacement cover the token; the typed `contracts` schemas (`packages/contracts/src/projects.ts`) stay `.strict()` with no field of a token kind.
- **Allow-list.** `authAllowListFor` takes the project's token instead of `requireEnv('SUPABASE_PAT')`, for reconcile and domain verification alike.
- **Audit.** An audit row for token registration, replacement and owner change, never carrying the token.
- **Reason codes.** `token_invalid`, `token_forbidden`, `org_mismatch`, `token_account_wide`, `token_other_project`, `token_expiry_invalid`, `not_pro` as in UI-SPEC "Data the screens read"; `BOOTSTRAP_REASON_CODES` gains the first three.
- **Fake provider and local stub** mirror every new behaviour so the tests need no network.
- **Docs.** `docs/DEPLOY.md` gets a "Phase 09.4 release" section (order, what a token needs, the probe, the Pro responsibility).

## Existing Code Insights

### Reusable Assets
- `createSupabaseProjectProvider({ pat, orgSlug })` already takes the token and the pin as parameters; only the singleton in `index.ts` and the zero-argument `getProjectProvider()` are env-bound. A per-project provider is a new call to the same factory.
- `createLimiter` is already instance-based; only `defaultProcessLimiter()` is process-wide.
- `authAllowListFor(project)` is already memoised by `project.id:credentialVersion` with an LRU of 64: the template for the provider cache.
- The sealing scheme (`seal(value, '<id>:<column>')`, `credential_version` bump, `reseal.ts`) covers one more column without a new mechanism.
- `reconcile-allow-list.ts` already re-adds every verified host of a project's tenants: D-575 calls it.
- `TenantDraftProvider`, `ProjectAccessFields`, `ReplaceCredentialsSheet`, `DatabasePill`, `SegmentedControl` are the shipped parts the UI-SPEC extends.

### Established Patterns
- Provider errors carry a kind and an HTTP status and nothing else; reasons are a closed catalog and the panel shows a catalog sentence plus a code, never provider text (T-09.2-57, UI-D-561).
- The fake provider mirrors every real behaviour; tests inject it with `setProjectProviderForTests` (refused outside `NODE_ENV=test`).
- Secrets are write-only in the panel and sealed with AAD `<id>:<column>`.
- Commands are `pnpm` scripts with `--dry-run`, an audit row and hidden-secret discipline.

### Integration Points
- `getProjectProvider()` callers: health, precheck, credentials, reissue, move target, tenant creation (`platform/tenants.ts`).
- `SUPABASE_PAT` readers: `env.ts`, `projects/index.ts`, `domains/index.ts`, `scripts/reissue-credentials.ts`, `scripts/probe-management-api.ts`, `scripts/check-release-env.sh`, the deploy workflows.
- Registry reads for the panel: `overview.ts` (Banco), the tenant list row (`database.token`), `TenantLayout`.
