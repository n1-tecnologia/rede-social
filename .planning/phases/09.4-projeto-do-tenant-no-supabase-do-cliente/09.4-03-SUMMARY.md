# Phase 09.4 Plan 03: Token state and token contracts Summary

One pure `tokenState` derivation (seven states, one 30-day constant, calendar-date math) plus the strict, token-free reason codes, input bodies and answer additions that the API and the panel will share.

## Accomplishments

- **Tracer (Task 1, CTK-16).** `tokenState({ check, expiresAt, today })` with the precedence organizacao diferente > invalido > sem permissao > vencido > vencendo > nao verificado > valido; `TOKEN_EXPIRING_WINDOW_DAYS = 30` is the only place the number lives; `tokenExpiryIsValid(expiresAt, today)` is the one rule for the typed date (real date, strictly after today, at most one year ahead). A 25-row precedence table, the window boundary (0, 30, 31 days, yesterday), year-end and leap-day cases, and a test that `DATABASE_STATES` and `databaseState` ignore any token input.
- **Reason codes (CTK-29).** `BOOTSTRAP_REASON_CODES` now has thirteen entries (the first ten unchanged, then `token_invalid`, `token_forbidden`, `org_mismatch`); `PRECHECK_REASONS` has twelve (old six, then `token_invalid`, `token_forbidden`, `token_other_project`, `token_account_wide`, `token_expiry_invalid`, reserved `not_pro`).
- **Inputs (CTK-26).** `customerProjectFields` + `refineCustomerProject` on `precheckBodySchema` and `createTenantBodySchema`: a customer owner needs a non-blank token, a token or expiry without a customer owner is refused, every message is a constant, the token is capped at 4096. `replaceTokenBodySchema` / `replaceTokenAnswerSchema` for the replacement route.
- **Answers (CTK-33).** `tokenSummarySchema` (state, expiresAt, checkedAt only); `owner`, `organization`, `token` added OPTIONAL to `databaseOverviewSchema`; optional `token: { state }` on the list summary. All `.strict()`; tests refuse `token`, `mgmtToken`, `tokenPrefix`, `tokenLength`, `tokenHash`.

Task verification: `vitest run` in contracts is green (258 tests); `tsc --noEmit` is clean for contracts, core, api and web.
