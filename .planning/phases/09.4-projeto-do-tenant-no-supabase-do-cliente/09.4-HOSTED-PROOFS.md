# Phase 09.4 hosted proofs (P1 to P8)

This file is the ledger of the proofs that only a person with a second Supabase organisation can run: a real
scoped token, a real Pro project of an organisation that is not the platform's, a token revoked on purpose,
and a project transferred between two organisations. Everything an agent could build is built and proved on
the local stack and against stubs (plans 01 to 17); what is left here cannot be faked, so nothing in this
file is ever recorded as done by an agent.

**The rule.** Every row ships `pending`. A row becomes `passed` only when Igor pastes the evidence of its
steps and the date, in the row, himself. An agent never edits a Status line and never writes evidence it did
not see. A phase whose ledger has a `pending` row closes `human_needed`, never green (D-577).

**The evidence rule.** Paste shapes, counts, statuses, HTTP codes, exit codes and the words the screens
show. **Never** a key, a password, a token, a connection string, a webhook token, an e-mail address of a
member, or a project ref. Replace a ref by `<ref>` and a host by `<host>` in what you paste. The commands
below were written with placeholders (`<ref>`, `<slug>`).

**The token rule.** Every step that needs a customer token types it at the HIDDEN PROMPT of the command
(nothing shows on screen, it is never in the command line, never in an environment variable, never in the
shell history). Do not paste a token into a shell variable, a file or a message, not even a throwaway one:
the hidden prompt is the only way in, and the commands refuse a pipe or a here-string. The shortcut of the
09.2 ledger (exporting the platform token into the shell) is not reused for a customer token.

**The scratch project.** A Pro project in your SECOND Supabase organisation, empty, used only for these
proofs. The throwaway tokens are created in that organisation, limited to that project, with the shortest
expiry the dashboard offers, and revoked when the proofs end.

**The procedures** are in `docs/DEPLOY.md`, "Phase 09.4 release" (written by plan 17). Plans 02 to 16 built
what P2 to P8 exercise; the steps below name the commands and screens as shipped. Every command is tried
first with a FAKE token under `PROJECT_PROVIDER=fake` (except the scoped probe, which has no fake mode).

## P1 — The permission list and what a scoped token answers

- **Proves:** CTK-06 (the hidden prompt on a real terminal), CTK-07 (the scoped probe against a real token),
  and settles the open questions that fix the thirteen permissions of D-569 and the registration checks of
  D-570: which operations a token with the thirteen answers `allowed`, which `denied` and with which
  permission identifiers, what the token answers to the project listing, whether the organisation is
  readable, whether the plan is readable, and whether any response header carries an expiry. The permission
  sentence of plan 17 (`[PENDENTE-PERMISSÕES]`) waits for this row, and no other plan of the phase does.
- **Needs:** the scratch project and a terminal (an interactive one: not a pipe, not a script).
- **Where:** your own terminal, from the repository root. Read-only: the probe changes nothing (writes are
  sent as invalid requests that are answered by validation or a refusal; a `2xx` on a write row is shown as
  `unexpectedSuccess: true`, and if you ever see it, stop and tell me).
- **Steps:**
  1. Run A (required). In the Supabase dashboard, create a personal access token of the scoped kind (the
     prefix is `sbp_fc`), limited to the scratch project, with these thirteen permissions: Project Settings
     (Read-write), API Keys (Read-write), API Key Secrets (Read), Connection Pooling (Read), Database
     (Read), Database Config (Read-write), Migrations (Read), Storage (Read), Storage Config (Read-write),
     Auth Config (Read-write), Auth Signing Keys (Read-write), Data API Config (Read-write), Realtime Config
     (Read-write). Copy the token once.
  2. Run `pnpm platform:probe --scoped --ref <ref>`. When the line "Cole o token do projeto" appears, paste
     the token and press Enter. Nothing shows on screen while you do it; that is correct.
  3. Read the single JSON object. Check by eye that it holds only statuses, counts, header names and
     permission identifiers, then paste it under "Evidence to paste".
  4. Run B (optional, answers the listing question). Create a second throwaway token with the same thirteen
     permissions plus Projects (account-wide, Read) and run the same command. Paste its `listing` and the
     first row.
  5. Run C (optional, answers what a missing permission looks like). Create a third token without Realtime
     Config and run the same command. Paste the two `config/realtime` rows, which should show `denied`, `403`
     and the identifier in `missingPermissions`.
  6. The revoked token. Revoke the token of run A in the dashboard, run the same command once more with it,
     and paste the status of the FIRST row only (the 401 or 403 answer to a revoked token, for P5).
  7. Answer in one line each: which rows are `denied` with the thirteen; what `listing.status` and the two
     counts show; whether `organisationRead.status` is `200`; whether the plan is readable; whether any
     header name in `responseHeaderNames` looks like an expiry.
- **Evidence to paste:** the JSON object of run A (and of B and C if you ran them), the first-row status of
  the revoked token, and the one-line answers of step 7.

## P2 — A new tenant on the customer project

- **Proves:** CTK-01, CTK-12 (the wizard creates a tenant on a project of the customer's organisation, the
  organisation pin is stored, and a platform project behaves exactly as before).
- **Needs:** P1 `passed` (or at least run A recorded), the scratch project, a scoped token with the
  thirteen permissions that is still valid.
- **Where:** the platform panel, "Novo tenant", against the local stack or homolog as the release notes say.
- **Steps:**
  1. Open "Novo tenant". Under "Projeto Supabase", at "Onde fica o projeto?", choose "Projeto do cliente".
     Type the project ref into "Código do projeto" and the date into "Vence em (opcional)". The "Token de
     acesso do projeto" field is write-only: paste the token into that field only.
  2. Finish the wizard. Open the tenant's "Banco" screen.
  3. Read what it shows: Dono ("Cliente"), Organização (the pinned one), "Plano: Não informado" and the
     "Token de acesso" card with its state ("Válido").
  4. Create a second tenant at "Projeto da plataforma" and confirm nothing changed for it (Dono "Plataforma",
     no "Token de acesso" card).
- **Evidence to paste:** the words the "Banco" screen shows for the customer tenant (Dono, state of the
  token, no slug or ref), and one line saying the platform tenant looks the same as before.

## Advisories

- **The listing check of D-570 (b): what the one real run showed.** The check lists the account's projects
  and refuses a token that lists any project other than the target (`token_account_wide`); a `403` passes.
  On 2026-10-27, P1 run A (token limited to the scratch project, the thirteen permissions of D-569, nothing
  account-wide per Igor) answered the listing with `200`, `projectsTotal` 1 and `projectsOtherThanTarget` 0:
  with the thirteen the listing check WORKS and a scoped token sees only its own project, so the earlier
  worry that it would be a weak check (a `403` for a token without Projects account-wide) did not happen on
  this account. **This rests on ONE run.** Runs B and C were not run, so what a token that also holds
  Projects (account-wide) or an organisation-wide token answers is unobserved, and the status a revoked
  token gets (needed by P5) was not recorded. P3 is the proof of the refusal itself. The thirteen stay the
  list and no fourteenth permission is added (ruling 1, resolved by Igor).
- **The plan (Free or Pro) is not readable** with a project-scoped token; the report of run A does not show
  it. The Banco says "Plano: Não informado", nothing blocks, and keeping a customer project on Pro is the
  operator's responsibility (D-572). The organisation endpoint answered `403`, so the organisation slug is
  learned from the project's own response and pinned. No response header carries an expiry, so the expiry
  date is typed by the operator.
- **Replacing a token has a cost (ruling 4).** Every replacement (the panel's "Substituir token",
  `platform:set-owner` on a customer project) bumps `credential_version`, which recycles that project's
  database pools, admin clients and job senders and triggers a health check and an allow-list reconcile.
  Tokens are replaced when they expired, were revoked or are about to, never in a loop; P4 and P5 replace a
  token a few times on purpose, so run them once.
- **A made-up string without the `sbp_fc` prefix is answered as an account-wide token** (the prefix check
  runs first, no request is made); only a made-up `sbp_fc` string reaches Supabase and gets the "não
  aceitou" sentence (P3 step 2).
- **A past expiry date cannot be typed** (the date must be after today and at most a year ahead), so
  "Vencido" appears only when a stored date passes; P5 step 4 says so.
