# Phase 09.4 Plan 06: Provider per project Summary

One resolver now decides which management token a call uses: a customer project gets a provider built from its own sealed token and organisation pin (cached by project and version, 64-entry LRU, own 100/min limiter), bootstrap, reissue, credentials and the redirect allow-list all run on it, and a source-scan test pins the only three files that may read the platform token.

## Accomplishments

- **Tracer (Task 1, CTK-22, CTK-23).** `getProjectProviderFor` returns the platform provider for a platform project (override first, else the lazy env singleton, as before) and, for a customer one, opens the sealed token (AAD `<id>:mgmt_token`) and builds a customer-kind provider (or a `forToken` view under a token-aware fake). No sealed token throws a fixed message; a wrong AAD surfaces the sealed-unreadable error; neither names the token. `createRequestTokenProvider` builds an uncached provider from the token in a request (learn mode when no organisation is given). `dropProjectProvider` clears every version of a project.
- **Callers (Task 2).** `bootstrap.ts` resolves per project only for a customer project (the platform branch keeps its direct singleton import), `reissue.ts` and `credentials.ts` call `getProjectProviderFor` with the row they already hold (the locked select gained `provider, credential_version, owner, org_slug, mgmt_token_sealed`). The reissue script header now states that a customer project asks for no platform variable and what happens to its sealed token after a master-key loss.
- **Allow-list (Task 3, CTK-27).** `createProviderAuthAllowList` reads and writes `uri_allow_list` through the project's guarded provider with the exact semantics of the platform adapter. `authAllowListFor(project, { mode })` stays synchronous; a customer project in `supabase` mode gets the provider-backed adapter, a platform project the unchanged platform adapter. `dropAllowListAdapter` is the plan-10 seam.
- **Invariant.** `platform-token-readers.test.ts` scans `packages/core/server` and asserts the readers of the platform token are exactly `domains/index.ts`, `env.ts`, `projects/index.ts`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `fake.ts` default organisation did not match the fixture pin**
- **Found during:** Task 1 GREEN run
- **Issue:** the test fake answered its default organisation, so a customer view pinned to `acme` raised `org_mismatch`.
- **Fix:** the test fake world is built with `orgSlug: 'acme'`.
- **Files modified:** packages/core/tests/project-provider-for.test.ts
- **Commit:** d1e03c45

**2. [Rule 1 - Design] Cache entries remember the base they were built from**
- **Found during:** Task 1 design
- **Issue:** a cache keyed only by `<id>:<version>` would serve a view of an earlier test override after `setProjectProviderForTests` changes it.
- **Fix:** each entry stores its `source` (the token-aware base, or undefined for the real adapter); a hit with a different source rebuilds. The key stays `<id>:<version>`.
- **Files modified:** packages/core/server/projects/provider-for.ts
- **Commit:** d1e03c45

**3. [Rule 3 - Blocking] Test-file additions kept additive**
- **Found during:** Task 3
- **Issue:** the acceptance gate wants zero removed lines in `domains-allow-list.test.ts`, which a merge of new names into the existing `vitest` and `domains/index` imports would break.
- **Fix:** new imports are separate lines (namespace imports for the two domain modules); the new describes are appended.
- **Files modified:** packages/core/tests/domains-allow-list.test.ts
- **Commit:** e9493bf7

**4. [Note] `canonical` moved out of the platform adapter's closure**
The plan says to export `ALLOW_LIST_ENTRY` and `canonical` (move, do not copy). Moving `canonical` to module level removed its local definition inside `createSupabaseAuthAllowList`; behaviour of the platform adapter is identical and its tests pass unchanged.

**Total deviations:** 3 auto-fixed (2 blocking, 1 design) plus 1 note. **Impact:** none on scope.
