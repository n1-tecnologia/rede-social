### Which journeys are in
- **D-566:** Three journeys. (1) **New tenant on a customer project** through the "Novo tenant" wizard (UI-SPEC). (2) **Move an existing tenant to a customer project** with the existing move command (`scripts/move-tenant.ts`, D-536): the target is a project of the customer's account, bootstrapped like a new tenant's, with its token. (3) **Change the owner of a project already registered** to "customer" when Supabase itself transferred it to the customer's account, with no data copied (D-568). The way back, customer project to platform project, needs no new code (the target is then a platform project); the planner adds a test that proves it and that the command does not touch anything else in the customer's account. — **Reversibility:** costly — the move command and the registry columns of D-571/D-573 carry the owner concept into every project-aware call site.
- **D-567:** Every command that needs a token for a project the registry does not yet know (the move target, the owner change) asks for it through a **hidden terminal prompt**: no echo, never in `argv`, never in an environment variable, never in shell history or the process list. The token is held in memory, sent once to the validation of D-570, sealed, and dropped. Same discipline as the panel's write-only fields (UI-D-561). Commands that act on an already registered project read the sealed token from the registry and ask for nothing.
- **D-568:** **Owner-change command** (name is the planner's; proposal `pnpm platform:set-owner --tenant <slug>`): asks the token (D-567), runs the whole validation of D-569..D-572 (project reachable, token scoped to that project, organisation read), seals the token, stores `owner = customer` and the organisation pin, bumps `credential_version`, writes an audit row (never the token), and copies nothing. No screen and no design gate. It is also the **re-pin path** after a legitimate organisation change of an already customer-owned project: the same command reads the organisation again and stores the new pin (answers OQ-11). Direction customer to platform is the planner's call if it costs nothing; only platform to customer is required. — **Reversibility:** reversible — a registry update and a sealed value.

### What the system refuses (token validation)
- **D-569:** **One permission list** for the token, used for creating, maintaining and the break-glass reissue (no separate "maintenance" token). Thirteen permissions, from the Supabase table read on 2026-10-27 (`https://supabase.com/docs/guides/platform/personal-access-tokens.md`, summarised, levels per operation): **Project Settings** (Read-write: `describe`, `health`, and `PATCH config/auth` needs it at Read-write), **API Keys** (Read-write: `POST api-keys` creates the keys), **API Key Secrets** (Read: reveals the key values), **Connection Pooling** (Read), **Database** (Read: the read-only query), **Database Config** (Read-write: `PATCH database/password`), **Migrations** (Read), **Storage** (Read), **Storage Config** (Read-write), **Auth Config** (Read-write), **Auth Signing Keys** (Read-write), **Data API Config** (Read-write), **Realtime Config** (Read-write). Because the list includes **API Key Secrets**, a customer project never needs the manual-access fallback (answers OQ-10); the fallback stays in the code path for safety. The table came from a summarised page, so **the list is unproven until D-578's probe runs against a real scoped token**; until then `[PENDENTE-PERMISSÕES]` in `TokenHowTo` stays and the catalog test keeps failing (A-UI-8). — **Reversibility:** reversible — copy and a probe list; but a token's permissions cannot be changed after creation, so a wrong list means new tokens for every customer project already registered.
- **D-570:** **Account-wide tokens are refused by two independent checks**, both at registration, replacement and owner change (not on every health tick): (a) the token must start with `sbp_fc` (the documented prefix of scoped tokens; legacy full-access tokens show a Legacy badge and have no documented prefix); (b) a **behavioural check**: list the account's projects (`GET /v1/projects`) and refuse with `token_account_wide` if the answer contains any project other than the target (a 403 or a list holding only the target passes). This call is a 21st operation: `COVERAGE.md` moves `GET /v1/projects` from the `group:listing-and-organisations` OPT-OUT to INTEGRATE, restricted to registration, and the equality test (20 INTEGRATE + OPT-OUT = 169) is updated. What a scoped token really answers to that call (403, empty, or filtered to its own project) is unproven: the probe settles it (D-578) and the researcher reads the answer. If the prefix is wrong but the check passes, or the reverse, the token is refused: both must pass.
- **D-571:** **The organisation is pinned on the first read.** At registration the system reads the project's organisation slug with the token (`describe`), stores it on the registry row, and from then on every Management API call about that project compares it; a mismatch is refused as `org_mismatch` and the token state becomes "Organização diferente" (UI-D-553). The organisation is never typed and the wizard shows no extra line; the Banco tab shows it (UI-D-552). Platform projects keep `SUPABASE_ORG_SLUG` exactly as today. The pin is stored per project, so a platform project and a customer project never share a pin. (Answers OQ-5 and the "organisation pin per project" point of the ROADMAP.)
- **D-572:** **The plan (Free or Pro) is informative.** The researcher looks for a way to read it with a project-scoped token. If one exists, the pre-check refuses a Free customer project with the UI-SPEC sentence (`not_pro`) and the Banco notice appears. If none exists (likely: billing is organisation-level), the Banco shows "Plano: Não informado", nothing blocks, and the proof notes and `docs/DEPLOY.md` say that keeping the project on Pro is the operator's responsibility. No new screen and no confirmation checkbox (answers OQ-8).

### Dead token: what stops and what keeps running
- **D-573:** **The token state is its own axis and never takes a tenant offline** (UI-D-551 confirmed on the server side, answers OQ-2). The health job, for a customer project, first calls `describe` with the token: a refusal sets the token state (`invalid`, `no permission`, `org mismatch`), and the project's database state then comes from the pool ping alone ("Pronto" or "Inacessível"); the one thing lost is the paused or not-paused fact. This needs the provider error to carry a refinement beyond today's `org_mismatch`: `ProjectProviderError.code` gains `token_invalid` (401) and `token_forbidden` (403 on an operation), so `kindOfStatus` no longer folds every 401/403 into one `forbidden`. The token state is derived by one pure `tokenState` function in `@rede-social/contracts/projects` (precedence of UI-D-553). A single check refreshes both the database state and the token state, including "Verificar agora" and the follow-up after "Substituir token" (answers OQ-9).
- **D-574:** What keeps working with a dead token, because it uses the sealed database URL and service key and never the Management API: sign-in and sessions, all member screens, Storage, Realtime, the schema migration fan-out ("migrar todos"), the worker's per-tenant queues. What degrades: the paused-or-not fact, allow-list writes (new domains), the break-glass reissue, the registration of a move target, a bootstrap step that calls the Management API. The tenant is never suspended, never marked "atrasado" and never shown a token message because of this.
- **D-575:** **After "Substituir token" succeeds** (validated against the project and the registered organisation before anything is replaced, UI-D-555), the system on its own: (a) bumps `credential_version` and drops the cached provider and allow-list adapter of that project; (b) runs the follow-up health check; (c) re-runs the existing allow-list reconcile (`platform/reconcile-allow-list.ts`) for the verified domains of the tenants bound to that project and clears `last_error = 'allow_list'` on the ones that now succeed; (d) leaves a bootstrap that stopped on a token step to "Tentar de novo" as in 09.2. Before this decision the only recovery was pressing "Verificar agora" per domain (`ensureVerifiedSideEffects`); that button keeps working.
- **D-576:** **The operator is warned in the panel and in the log**, nothing else. Every token state change writes one structured line (`project.token.state_changed`: project id, from, to; never the token, its prefix or its length) so a Cloud Logging alert can be built on it. An e-mail or push to the operator is a new capability (see Deferred).

### Discretion areas

## Summary

The phase is mostly a seam change. `createSupabaseProjectProvider({ pat, orgSlug })` already takes the token and the organisation as parameters, so a per-project provider is one more call to the same factory; the env singleton, the zero-argument `getProjectProvider()`, `defaultProcessLimiter()` and `authAllowListFor` (which reads `SUPABASE_PAT` itself) are the env-bound parts to replace. There is one caller the CONTEXT list does not name: `bootstrap.ts` resolves the env singleton directly through `resolveProvider(deps)` (`(await import('./index')).projectProvider`), so the bootstrap steps of a customer project would silently run with the platform token unless that seam changes too.

Supabase facts, read in full this session: the permission table of the PAT page and the machine-readable `x-fga-permissions` of the live OpenAPI document (2026-10-27, 169 operations, same count as COVERAGE.md) agree with the thirteen permissions of D-569 for the 20 INTEGRATE operations. Three things the CONTEXT did not know change planning: (1) `GET /v1/projects` is gated by an account-wide permission ("Projects (account-wide)" Read) that is NOT among the thirteen, so with the locked list the behavioural check of D-570(b) will almost always see a 403 and pass: it cannot detect a token scoped to all projects of an organisation; (2) the plan (Free/Pro) is only on `GET /v1/organizations/{slug}`, which needs "Organization Settings" Read, also outside the thirteen: with the locked list it is not readable, so D-572 resolves to "Plano: Não informado"; (3) the rate limit is per user, per project-or-organisation scope, per endpoint (120/min), so a per-token limiter at 100/min is conservative and tokens of one person only share a quota for user-scope calls such as `GET /v1/projects`. A 403 on a missing permission carries a `missing_permissions` array (changelog 2026-10-06), which the probe can print as identifiers only.

The registry change is two additive pieces: owner, organisation pin, sealed token and typed expiry on `platform.projects`, and the last token-check outcome on `platform.project_health`. The sealing scheme, `reseal.ts` and `credential_version` already cover one more column; `credential_version` also keys tenant DB pools, admin clients and pg-boss senders, so a token replacement recycles those (known side effect, see Pitfalls). The operator commands need a hidden prompt that does not exist anywhere in the repo yet (no `setRawMode`, `readline` or `isTTY` in scripts, apps or packages; only `read -s` in docs).

**Primary recommendation:** Build in this order: (1) probe mode + hidden-prompt helper (autonomous: false, Igor runs it), (2) registry columns + `tokenState` + refined provider error codes, (3) `getProjectProviderFor(project)` with per-token limiter and the bootstrap/allow-list/health/precheck/credentials/reissue/move callers, (4) owner-change command, (5) UI behind the sketch 015 gate, (6) docs and the hosted-proof ledger; keep `kind: 'forbidden'` on every 401/403 and add the refinement only in `code`, set only by customer-token providers, so platform projects stay byte for byte.

| Token validation (prefix, describe, listing check, org read) | API / Backend (kernel `packages/core/server/projects`) | — | Only the server may hold or send the token; the web sends it once and never stores it |

### 2. What a project-scoped token answers to `GET /v1/projects` (D-570)

- VERIFIED [CITED: PAT page "Permission scopes" + OpenAPI]: the operation needs Projects (account-wide) Read (`projects_read`). The page's CLI example says that with that permission `supabase projects list` "lists the projects the token can reach" (i.e. filtered to the token's scope).
- UNPROVEN: the answer of a token that lacks that permission (expected `403` with `missing_permissions`, by analogy with the page's own 403 example on the types endpoint) and the answer of a token that has it but is scoped to one project (expected: a list containing only the target). Settled by: probe line for row 21 printing `status`, `projectsTotal` and `projectsOtherThanTarget` (numbers only) for the operational token.
- **Design consequence the planner must see:** with the locked thirteen (no Projects permission) a token scoped to *all projects of an organisation* also gets 403 on row 21 and therefore **passes** D-570(b). The behavioural check then adds nothing beyond the prefix check (a), and the platform cannot detect "scoped to the whole organisation" at all, because every per-project call succeeds for any project of that organisation. Options (a decision for Igor/planner, not made here): keep (a)+(b) as written and say so in the docs; or add Projects (account-wide) Read as a fourteenth permission so (b) has teeth (a one-project token then lists only itself, an organisation-wide token lists every project); or add a confirmation line in the wizard. Flag as Open Question 1.
- VERIFIED live (made-up tokens, no real credential): the API routes by prefix. `Authorization: Bearer sbp_fc_<zeros>` answered `401 {"message":"JWT could not be decoded"}` while `sbp_<zeros>` answered `401 {"message":"Invalid access token"}`. So `sbp_fc` is a distinct server-side token family, supporting D-570(a); the scoped token looks JWT-shaped, hence **likely much longer than 256 characters**. UI-D-550 specifies `maxLength={256}` on the token input: that would silently truncate a real token. Use the 4096 cap the existing access bodies use (`accessFields`, `.max(4096)`) [VERIFIED: packages/contracts/src/projects.ts accessFields]. Length itself is UNPROVEN (never log or print it; Igor just pastes a real one in P2 and sees it work).

### 5. Do 401 and 403 separate "invalid" from "no permission" (D-573)?

- VERIFIED live (2026-10-27, three requests with made-up tokens, no real credential, `curl` against `https://api.supabase.com/v1/projects/abcdefghijklmnopqrst`): no header -> `401 {"message":"No access token provided"}`; `Bearer sbp_000...` -> `401 {"message":"Invalid access token"}`; `Bearer sbp_fc_000...` -> `401 {"message":"JWT could not be decoded"}`. A never-valid token is 401.
- VERIFIED [CITED: PAT page + changelog]: a valid token lacking a permission gets `403`, with a `missing_permissions` array; the OpenAPI lists `401 Unauthorized` and `403 Forbidden action` on every operation.
- UNPROVEN: what a real *revoked/deleted* token answers (expected 401), an *expired* token (expected 401), a token whose creator lost access (the changelog says "When you lose access, so does the token"; status unknown: 401 or 403), and a token scoped to project A used on project B's ref (403 or 404). Settled by P5 (create a token, revoke it, run the probe's row 1: record the status; and the A-on-B call) and P6/P8 (creator loses access, optional). The code mapping 401 -> `token_invalid`, 403 -> `token_forbidden` is correct for the first two proven cases; if a revoked token turns out to be 403, `token_invalid` for "revoked" would be wrong and the card text for Inválido ("foi apagado ou revogado, ou quem o criou perdeu o acesso") must be read against P5's result.

### 6. Is the 120/min Management API limit per user or per token (limiter)?

- VERIFIED [CITED: `https://supabase.com/docs/reference/api/introduction`, fetched and read in full]: "Rate limits are based on a per-user, per-scope model"; standard limit "120 requests, 1 minute, Per user, per project or organization, per endpoint"; "Personal access tokens: the limit applies to the user, so all tokens created by the same user share it"; calls with no project or organisation scope ("such as `GET /v1/projects` and `GET /v1/organizations`") count against the user; a 429 holds "for the remainder of the minute"; headers `X-RateLimit-Limit/-Remaining/-Reset` (seconds) are returned. The response headers of a live call list them in `access-control-expose-headers` (VERIFIED live).
- Consequence: the existing `X-RateLimit-Reset` handling and `resetDelayMs` stay correct. A limiter of 100/minute across *all* endpoints of one token is far stricter than the real quota (120 per endpoint per project), so it never causes a false 429 and never needs to coordinate with another token: the platform PAT (Igor's user) and a customer token (customer's user, or Igor's second organisation, same user) only share the user-scope calls, and the only user-scope call this phase adds is `GET /v1/projects`, used once per registration. Key the limiter by project id + credential version, not by the token string.

### Pattern 1: Provider per project (extend the existing factory)
**What:** `getProjectProviderFor(project: ProjectRecord): Promise<ProjectProvider>`. Platform (`owner = 'platform'` or `isCentral`) returns today's lazily imported singleton (the lazy import is what keeps a process without `PROJECT_PROVIDER=supabase` booting). Customer: `createSupabaseProjectProvider({ pat: open(project.mgmtTokenSealed, \`${project.id}:mgmt_token\`), orgSlug: project.orgSlug, limiter })`, cached in a `Map` keyed `${project.id}:${project.credentialVersion}`, least-recently-used out at 64, exactly like `authAllowListFor`.
**Template to copy:** `authAllowListFor` [VERIFIED: packages/core/server/domains/index.ts:46-77] — `const key = \`${project.id}:${project.credentialVersion}\``, delete+set on hit, evict `adapters.keys().next()` at `ADAPTER_CACHE_MAX = 64`.
**Fake/local:** if `PROJECT_PROVIDER` selects `fake`, return the fake whatever the owner (the fake has no token); `setProjectProviderForTests` override keeps winning for both owners.
**Uncached builder for pre-registration:** `createTokenProvider({ token, orgSlug?: string })` where an absent `orgSlug` puts the provider in "learn" mode: the first successful `describe` returns `orgSlug` to the caller and pins it for the rest of that instance. Today `createSupabaseProjectProvider` throws `TypeError('project provider: orgSlug is required')` when it is empty [VERIFIED: management-api.ts:255-256], so the option must become optional.

### Pattern 2: Error refinement without touching platform behaviour
**What:** keep `kindOfStatus` returning `'forbidden'` for 401 and 403 and keep the message `"<kind> <status>"`. Add `code: 'token_invalid' | 'token_forbidden'` only when the provider was built with `tokenKind: 'customer'`. `code` is not part of the message [VERIFIED: types.ts:39-57], so existing assertions on `forbidden 403` and the reason catalog tests stay green.
**Why:** every existing consumer tests `error.kind === 'forbidden'` (`precheck.describeFailure`, `reasons.reasonOf`, `health.codeOf`, the `manualAccess` branch); changing `kind` would change platform behaviour.

### Pattern 3: Health for a customer project
`judge()` today: provider failure -> `{ status: 'unreachable', detailCode: codeOf(error) }` and a state change calls `invalidateProject()` and `invalidateTenantHost` for every host [VERIFIED: health.ts judge/checkProject]. That is precisely the path a dead token must NOT take. New order for `owner = 'customer'`: (1) `describe`; on `ProjectProviderError` with `code` in `token_invalid | token_forbidden | org_mismatch` set `token_check` accordingly, skip `health()`, and fall through to the pool ping for the database state; (2) on other provider errors (timeout, 5xx) keep today's `unreachable`; (3) on success set `token_check = 'ok'` and continue as today. Write `token_check`/`token_checked_at` in the same upsert as `status`.

### Anti-Patterns to Avoid
- **Reading `SUPABASE_PAT` inside a function that gets a project** (as `authAllowListFor` does): every such site is a platform-token leak into a customer project.
- **Putting the token, its hash, prefix or length into a cache key, log field or error.** Key by project id + credential version.
- **New `ProjectRecord` fields as required** without updating the five test files that build literals (see Code surface) — make them optional in the type or update the helpers in the same task.
- **A second limiter per call** for pre-registration providers: build one limiter per instance, never `defaultProcessLimiter()` for a customer token.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Sealing the token | A new cipher or a new column format | `seal()`/`open()` with AAD `<id>:mgmt_token` | Same format as every sealed column; `reseal.ts` and `resealWith` already handle key rotation |
| Rotation of the token | A new command | `credential_version + 1` + `invalidateProject()` as `replaceCredentials` does | Pools, clients and senders already key on the version |
| Rate limiting | A token bucket | `createLimiter({ perMinute: 100 })`, one per project-version | Already tested (FIFO, rolling window, shared 429 pause) |
| Cache with LRU | A new cache class | The `Map` delete/set pattern of `authAllowListFor` | Same bound, same test shape (`domains-allow-list.test.ts`) |
| Token state | Ad hoc `if`s in web and API | One pure `tokenState` next to `databaseState` | The 09.2 rule: the card, header, list and filter cannot disagree |
| Management API HTTP client | A second `fetch` wrapper | The existing `call()` (ref validation, timeout, `redirect: 'error'`, status-only errors) | `createSupabaseAuthAllowList` is the one existing exception and is itself a risk (see Pitfalls) |
| Reason-code → sentence | Provider text in the UI | The closed catalog + `BootstrapSteps` map | T-09.2-57 |

**Key insight:** every hard part (sealing, versioned caches, limiter, closed error catalog, write-only fields) already exists and is tested; this phase's risk is *forgetting a call site that still reaches for the env token*, not building a mechanism.

## Registry design facts

- **Sealing today.** `seal(plain, aad)` -> `v1:<keyId>:<iv>:<tag>:<ciphertext>`, AES-256-GCM, 12-byte IV, AAD bound; an empty plaintext is refused; every failure throws `Error('sealed value unreadable')` [VERIFIED: sealed.ts:101-135, 182-188]. AAD of every registry column is `<project id>:<column without _sealed>` (`ddl_url`, `service_key`, `database_url_tx`, `database_url_session`, `hook_secret`) [VERIFIED: scripts/reseal.ts:62; credentials.ts and reissue.ts `seal(..., \`${row.id}:ddl_url\`)`]. So a column named `mgmt_token_sealed` gets AAD `<id>:mgmt_token` with no new mechanism.
- **`credential_version`** integer >= 1, only goes up, bumped in one statement with the changed columns by `replaceCredentials`, `reissueCredentials` and bootstrap `steps.ts:186`. It keys: tenant DB pools (`project-pools.ts` "Keyed `${projectId}:${credentialVersion}`. A new version opens a new pool and drains the old one"), `supabaseAdminFor` clients, pg-boss senders (`boss.ts:154`) and `authAllowListFor` [VERIFIED: grep of `credentialVersion`]. A token-only change that bumps it therefore recycles the project's DB pools, admin clients and job senders: harmless but real churn; D-568/D-575 lock the bump.
- **`reseal.ts`** iterates `SEALED_COLUMNS` (five) for every `platform.projects` row in ascending `id`, one transaction per row `select ... for update`, re-seals under the current key, writes with `coalesce(...)` and `secret_key_id`, does NOT touch `credential_version`, reports `{ rows, resealed, skipped, failed, byColumn }` and never a value. `payment_integrations` is out of scope. ## Common Pitfalls

### Pitfall 1: A dead token takes a tenant offline through the existing health path
**What goes wrong:** `judge()` turns any provider `forbidden` into `unreachable`/`access_denied`; a change then calls `invalidateProject()` and drops every host answer, and the shell treats `unreachable` as held out [VERIFIED: health.ts judge, checkProject].
**Why:** the 09.2 design had one token for everything, so a refusal meant "platform problem".
**How to avoid:** Pattern 3, and a test that a dead-token customer project with a working pool is `healthy`/`ready` and its hosts still resolve.
**Warning signs:** a customer tenant shows "Inacessível" right after a token is revoked.

### Pitfall 2: A call site still reaches for the platform token
**What goes wrong:** `bootstrap.ts` `resolveProvider`, `authAllowListFor`'s `requireEnv('SUPABASE_PAT')`, `reissue-credentials.ts` and the probe all read the env token. Missed, they send the platform PAT to a customer project (which then 403s/404s, or worse, works if Igor's user has access).
**How to avoid:** an integration test with a recording fake: for a customer project, every Management API call is recorded with the *token kind*; assert zero calls with the platform kind. Grep gate in the plan: `grep -rn "SUPABASE_PAT" packages/core/server` must list only `env.ts`, `projects/index.ts` and `domains/index.ts` (platform branch).

### Pitfall 3: Organisation pin on first read (learn mode) and the unpinned allow-list adapter
**What goes wrong:** (a) two concurrent first reads (double submit) could pin different values; (b) `createSupabaseAuthAllowList` makes its own `fetch` to `/v1/projects/{ref}/config/auth` with no organisation check, so D-571 "every call compares the pin" would be false for allow-list writes; (c) the pin is cached per provider instance in the `pinned` Set, so a re-pin must bump `credential_version` or the cached instance keeps the old slug.
**How to avoid:** the learn mode pins inside one instance, the slug is persisted in the same transaction that inserts the row (under `pg_advisory_xact_lock(hashtext('project:' || ref))`, as `createOnProject` and `registerMoveTarget` already do); route the customer allow-list through the guarded provider; the owner-change command bumps the version (D-568).

### Pitfall 4: `credential_version` is shared by far more than the provider cache
**What goes wrong:** every token replacement recycles the project's DB pools, admin clients and pg-boss senders.
**How to avoid:** accept it (locked), but make `invalidateProject()` run after the commit as `replaceCredentials` does, and avoid replacing tokens in a loop. Do not add a second version column unless the planner and Igor accept deviating from D-568/D-575.

### Pitfall 5: Cache and limiter keyed by the wrong thing
**What goes wrong:** keying by token string/hash leaks; keying by project id alone serves a stale token after replacement; a process-wide limiter lets a 429 on one token pause every customer.
**How to avoid:** `${project.id}:${project.credentialVersion}` for both the provider and its limiter; pre-registration providers get a fresh limiter and are never cached.

### Pitfall 6: Token leakage paths
**What goes wrong:** the token in a log field name not covered by `LOG_REDACT`; in a Zod/`ApiError` detail (the platform hook echoes issue `message` and `path`: keep refine messages static); in `ProjectProviderError` text (today `"<kind> <status>"` only: keep); in a React prop or RSC payload (`TokenCard` is a server component and receives state, not the token); in `sessionStorage` (`TenantDraftProvider` persists the draft: the token must be excluded from `STORAGE_KEY`); in the wizard's server action arguments (sent once); in the access log (it logs method, path, status only: fine) [VERIFIED: apps/api/src/http/logger.ts].
**How to avoid:** the T-09.2-67 style scan test over every answer and log capture used in the new tests.

### Pitfall 7: `maxLength={256}` on the token input
**What goes wrong:** scoped tokens are JWT-shaped (see item 2) and probably longer than 256 characters; truncation yields "token inválido" for a perfectly good token.
**How to avoid:** cap at 4096 in the input, the schema and the server action; never display length.

### Pitfall 8: The `GET /v1/projects` check gives a false sense of safety
See item 2: with the locked list it passes for an organisation-wide token. Say so in `DEPLOY.md`; do not claim "account-wide tokens are refused" beyond the prefix check without the extra permission.

### Pitfall 9: Backward compatibility "byte for byte"
**What goes wrong:** widening `ProjectProviderError.code`, adding `ProjectRecord` fields, adding a method to `ProjectProvider` and changing `reasonOf` all ripple into existing assertions.
**How to avoid:** the first task of the provider wave runs `management-api.test.ts`, `project-provider-env.test.ts`, `project-provider-fake.test.ts`, `probe-management-api.test.ts`, `domains-allow-list.test.ts` unchanged (except the intentional 20->21 and 10->13 counts) and the diff of those files must show only additions.

### Pitfall 10: Missing write-level permissions are not detectable at registration
Registration can safely exercise only read operations; the PATCHes (database password, auth, postgrest, storage, realtime, signing keys) would change a project. A token with Read but not Read-write passes every pre-flight read and fails at the bootstrap `auth` or `roles` step with `token_forbidden`. That is acceptable (the dialog sentence and the card cover it) but the planner should not promise "Sem permissão" at registration time.

### Pitfall 11: Execution order and the sketch gate
UI tasks run `grep -q '^approved: true' .planning/sketches/015-phase-09.4-designed-screens/README.md` (UI-SPEC gate mechanics); only Igor pastes the approval. The permission string cannot ship before the probe (CTK-08).

// Source: precedence of 09.4-UI-SPEC UI-D-553; sibling of databaseState in packages/contracts/src/projects.ts
export const TOKEN_EXPIRING_WINDOW_DAYS = 30; // A-UI-5, one constant
export function tokenState(input: {
  check: 'ok' | 'invalid' | 'forbidden' | 'org_mismatch' | null;
  expiresAt: string | null; // 'YYYY-MM-DD' typed by the operator
  today: string;            // injected, so the function is pure
}): 'org_mismatch' | 'invalid' | 'no_permission' | 'expired' | 'expiring' | 'unchecked' | 'valid' {
  if (input.check === 'org_mismatch') return 'org_mismatch';
  if (input.check === 'invalid') return 'invalid';
  if (input.check === 'forbidden') return 'no_permission';
  if (input.expiresAt !== null && input.expiresAt < input.today) return 'expired';
  if (input.expiresAt !== null && daysBetween(input.today, input.expiresAt) <= TOKEN_EXPIRING_WINDOW_DAYS) return 'expiring';
  return input.check === null ? 'unchecked' : 'valid';
}
