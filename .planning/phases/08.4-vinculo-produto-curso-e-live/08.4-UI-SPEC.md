# Phase 08.4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** This phase is admin-only and adds no new screen. It changes three forms that already ship:
- **Product form** (`/loja/novo`, `/loja/[productId]/editar`) gains the blocks **"Cursos liberados"** and **"Lives liberadas"** under **"Comunidades liberadas"**. They are clones of the 08.2 block (UI-D-377, D-363).
- **Course form** (`/cursos/[courseId]/editar`) and **live form** (`/cursos/lives/[liveId]`) lose the product picker block of 08.3 (UI-D-393, UI-D-403). In its place they show the community form's read-only **"Acesso"** line (UI-D-379).

**Design authority.** `reference/frontend-design/` has no store or course authoring screen. The design authority is therefore the two approved sketches these surfaces came from: `.planning/sketches/008-phase-08.2-designed-screens/` (product form, read-only access line) and `009-phase-08.3-designed-screens/` (course picker sheet, 3:4 and 16:10 thumbs, live form). The design language, spacing scale, type scale and colour model are **inherited unchanged** from the approved `02`–`08.3-UI-SPEC.md`. This document restates them for the checker and records only the Phase 08.4 deltas.

**Sketch gate.** **None.** ROADMAP § 08.4 UI hint: "No new sketch is expected unless the planner finds a new surface." Every surface below is built from frames that are already approved:
- the 008 product form block;
- the 008 community "Acesso" line;
- the 009 course picker sheet.

The only visual delta is that the picker sheet gains an optional meta line and a 16:10 thumb shape (UI-D-415). Both are sizes and strings that 009 already approved on the live list rows (UI-D-392), so they need no new frame. If the planner adds any surface beyond this list, the D-365 sketch rule applies again.

**Upstream decisions.** There is no CONTEXT.md for this phase, because the user skipped discuss-phase. ROADMAP § Phase 08.4 is the locked scope. It is cited as **SC 1..6**, and `08.4-RESEARCH.md` is cited as **R-§section / R-A1..A8**. The decision that reverses D-404's write path is recorded by the planner as **D-418**, as R-§"Where D-404 lives" recommends. Earlier visual decisions keep their numbers: UI-D-206, UI-D-288, UI-D-377, UI-D-378, UI-D-379, UI-D-387, UI-D-392, UI-D-393, UI-D-401, UI-D-403, UI-D-409. The UI questions this phase opens are decided below as **UI-D-413..UI-D-422**, continuing after 08.3's UI-D-412.

**Assumptions made in this session.** This is a yolo session with no CONTEXT.md. Each assumption is stated here instead of being asked, and the planner may overturn any of them with one line:
- **A-UI-1. Links to an archived course or a cancelled live are hidden from the product form.** This follows R-A3 and Open Question 1, and mirrors communities (CR-02): the form never shows them, a replace never removes them, and their buyers keep access. If the product owner wants them visible and removable, add a row with the `neutral` pill "Arquivado" / "Cancelada" and include those rows in the delete. That is a one-line contract change plus the API's delete rule.
- **A-UI-2. A linkable course is a draft or a published course (R-A1). A linkable live is any live that is not cancelled, recorded ones included (R-A2).** The picker therefore lists drafts, and a draft says so in its meta line ("Rascunho").
- **A-UI-3. There is no lock-impact dialog for courses or lives (R-A7).** No member reads a course or a live in the app yet, because the member area is deferred. Linking a course takes nothing from anyone in this release. The D-364 dialog stays communities-only (UI-D-378). The member phase must add the course and live branch of that dialog before it opens the catalogue.
- **A-UI-4. The product page (`/loja/[productId]`) does not list linked courses or lives (R-Open Question 3).** SC 1 only asks for the form, and the member product page must not leak draft course titles (R-Pitfall 5).

**Interaction truths outside the 8-category state taxonomy** (lifted by the planner as plain truths; listed here so they are not lost):
- E01, E02: after a row's `X`, focus moves to the next row's `X`, else the previous one, else the "Escolher …" button; closing a sheet returns focus to its opener (UI-D-421).
- E03, E04: each row is one `aria-pressed` button named "{title}, incluído / incluída" or "não incluído / não incluída"; the glyph is never the control.
- E05, E06: the course and live forms render no product picker, no "Escolher produtos" button and no `productIds` in any payload (SC 2); `ProductPickerSheet` is deleted.
- E01, E02 gate: the pages pass `null` unless the `courses` module is on and the viewer holds `courses.manage`; unit-tested as "prop null → no `data-product-courses` / `data-product-lives` in the DOM" (SC 5).
- Members: nothing in this phase reaches a member; `/loja/*/editar` and `/cursos/*` keep their manager gates, and the member product detail never carries `courses` / `lives` (R-Pitfall 5).

**Contract requirements this document places on the API** (for the planner; each is a projection of R-§Pattern 3/4, not a new rule):
- The **manager-only** product detail answers `courses: { id, title, coverAssetId, status }[]` (linkable linked courses: draft and published, `created_at desc, id desc`) and `lives: { id, title, coverAssetId, startsAt, status }[]` (non-cancelled linked lives, `starts_at asc, id asc`; `status` is the API's projection `scheduled | live | recorded`). These feed the selected rows and their metas without a second request.
- The member detail carries neither key.
- The course and live detail keep `products: { id, name, status }[]` (archived included), now read from the store's tables. These feed the read-only line.
- If the planner drops `status` from the course rows, the "Rascunho" meta is omitted rather than guessed.
