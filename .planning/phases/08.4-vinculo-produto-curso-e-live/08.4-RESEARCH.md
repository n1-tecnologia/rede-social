## Summary

Today the course and live links are owned by the **courses** module: `course_products` and `course_live_products` live in `packages/modules/courses/db/schema.ts:319-339` and `:494-511`, their FK to `store_products` is hand SQL in `supabase/migrations/20261013205559_courses_functions.sql:25-32`, and the course/live routes are the only writers (`replaceCourseProducts`, `replaceLiveProducts` in `packages/modules/courses/server/service.ts:934-951`, `:2356-2373`). The four gate bodies that the store module gives the kernel seam read those two tables (`supabase/migrations/20261013205601_store_course_gate.sql:31-127`). The community link is the opposite shape: `store_product_communities` is store-owned (`packages/modules/store/db/schema.ts:121-141`), its `community_id` has no drizzle reference and its FK to `communities` is hand SQL in the store's own migration (`20261008171645_store_functions.sql:62-64`), and the product form is its only writer.

The phase is therefore a schema-ownership move with a write-path reversal. The clean, precedent-backed way is **create, copy, swap, drop** in three migration files, mirroring the 05.2 pin retirement (`scripts/rehearse-highlights-migration.sh`): (1) a generated create-only migration for two new store tables `store_product_courses` and `store_product_lives` (same policy helper as `store_product_communities`); (2) a `--custom` store migration with the hand FKs to `courses`/`course_lives`, `revoke truncate`, the row backfill with a set-equality guard, and `create or replace` of the four gate bodies over the new tables, all in one file; (3) a generated drop-only migration for the two old tables. The kernel seam (`packages/core/db/course-gate.ts`), its four signatures, and both restrictive policies stay untouched, so every consumer keeps calling the same functions. Equal link sets plus an identical body rule give identical answers; pgTAP 190's truth table (fixtures re-pointed at the new tables, assertions unchanged) and a before/after rehearsal prove it.

On the API, the store gains `courseIds`/`liveIds` exactly like `communityIds` (resolve, replace under the product row lock, manager-only `courses`/`lives` in the detail), and the courses contracts lose `productIds` (`.strict()` makes a sent key a 400). The courses service keeps its read-only product reads (course/live detail `products`, lesson `hasProducts`), re-pointed by SQL to the store tables, which is the same cross-module SQL-read posture it already uses for `store_products`. On the web, the product form gets two blocks gated on the `courses` module, and the course and live forms swap their picker for the community form's read-only sentence.

**Primary recommendation:** Three-file migration (create → custom backfill + gate swap → drop-only), store-side `courseIds`/`liveIds` cloned from `communityIds`, courses keep read-only `products` re-pointed by SQL, and a before/after gate rehearsal script cloned from `rehearse-highlights-migration.sh`.

                        where l.tenant_id = c.tenant_id and l.course_id = c.id
                          and l.product_id = ${productId}::uuid))`);
  if ((rows[0]?.found ?? 0) !== courseIds.length) {
    throw new ApiError(400, 'VALIDATION_FAILED', { store: 'course_invalid' });
  }
}

async function replaceCourseLinks(tx: Tx, ctx: RequestContext, productId: string, courseIds: readonly string[]) {
  // CR-02 mirrored: a link to an ARCHIVED course is never removed by a replace.
  await tx.execute(sql`
    delete from store_product_courses l
     using courses c
     where l.tenant_id = ${ctx.tenantId}::uuid and l.product_id = ${productId}::uuid
       and c.id = l.course_id and c.tenant_id = l.tenant_id
       and c.status in ('draft','published')
       and l.course_id <> all (${uuidArray(courseIds)}::uuid[])`);
  if (courseIds.length === 0) return;
  await tx.execute(sql`
    insert into store_product_courses (tenant_id, product_id, course_id)
    select ${ctx.tenantId}::uuid, ${productId}::uuid, ids.id
      from unnest(${uuidArray(courseIds)}::uuid[]) as ids(id)
    on conflict (tenant_id, product_id, course_id) do nothing`);
}
// Lives: same, `course_lives v`, linkable = `v.cancelled_at is null`, issue 'live_invalid'.

### Anti-Patterns to Avoid
- **Renaming the tables in place:** interactive drizzle prompts with no TTY, and course-named policy/index names inside the store.

## Common Pitfalls

### Pitfall 1: The gate reads an empty table between files
**What goes wrong:** every paid course/live opens for members.
**How to avoid:** put the backfill and the four `create or replace` statements in the same custom file, backfill first.
**Warning signs:** pgTAP 190 truth table fails after `db:reset`.

### Pitfall 2: Stale function body after the drop
**What goes wrong:** `relation "public.course_products" does not exist` on any lesson or live read by a member lane.
**How to avoid:** order files 2 before 3. Add a pgTAP assertion that `pg_get_functiondef` of the four functions contains `store_product_courses`/`store_product_lives` and not `course_products`/`course_live_products`.

### Pitfall 3: drizzle-kit rename prompt
**What goes wrong:** `generate` hangs or needs a TTY when one run both adds the store tables and removes the course ones.
**How to avoid:** two separate runs (create-only, then drop-only). If a prompt still appears, the 07-08 workaround is `script` (present at `/usr/bin/script`) choosing "create".

### Pitfall 4: The 08.3 WR-04 rule silently inverted
**What goes wrong:** after the reversal, the "archived thing already linked" is a course or a live, not a product. A replace that deletes every link not in the sent set would drop a link to an archived course or a cancelled live that the form never shows.
**How to avoid:** delete only links whose target is linkable (Pattern 3), accept a re-sent already-linked target, and add an integration test: archive a linked course, PATCH the product with another set, assert the archived link survives and the gate still locks it.

### Pitfall 5: Member product page leaks course titles
**How to avoid:** manager-only detail fields, plus an integration assertion that a member's `GET /v1/store/products/{id}` JSON has no `courses`/`lives` key (strict schema parse).

### Pitfall 6: Verification digests go stale
**What goes wrong:** 08.2 and 08.3 `VERIFICATION.md` list `.planning/REQUIREMENTS.md` and `.planning/ROADMAP.md` in `covered_files` [VERIFIED: both files lines 6-9], so rewording COURSE-08/11 and STORE-03 (and the already-staged ROADMAP insertion) flips them to stale.
**How to avoid:** commit the requirement and roadmap edits in their own commit, then re-attest by recomputing the digest with a "Re-attestation" note (MEMORY: verification-digest-covers-requirements). Do not re-run the verifiers.

### Pitfall 7: Integration test hygiene
`pnpm test:integration -- x` does not filter. Run single files with `pnpm --filter @rede-social/api exec vitest run tests/integration/<file>`. Run pgTAP before integration (integration residue trips pgTAP). `db:reset` must be followed by `db:seed`, or isolation.test.ts aborts with "tenant rede-demo is not seeded". Use `bash scripts/supabase.sh`, not bare `supabase` (MEMORY: integration-tests-filter-and-drift). `courses.test.ts` toggles the demo store with `withDemoStore(enabled, fn)` (STATE.md:690).

### Pitfall 8: Plan-gate decision parser
A new decision written as `- **D-418: Title: more**` (two colons) breaks the decision-coverage gate. Use one colon or an em dash, and tag carried-forward D-404 bullets `[informational]` (MEMORY: plan-gate-parser-quirks).

### Pitfall 9: UI gate
This is a UI phase (ROADMAP "UI hint: yes"). `/gsd-plan-phase` exits at the UI-SPEC gate. Run `/gsd-ui-phase 08.4`, then plan again (MEMORY: ui-gate-blocks-plan-phase). The roadmap expects no new sketch: the blocks reuse D-363 and UI-D-379.

### Known Threat Patterns
| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Cross-tenant link (A's product → B's course/live) | Tampering | `resolveCourses`/`resolveLives` pin `tenant_id = ctx.tenantId` (one `400 …_invalid` for unknown and foreign alike); RLS insert `with check` pins the row's `tenant_id`; the gate joins entitlements on the link's tenant, so a forged row could only lock A's own course, never open B's. Composite-FK hardening is optional (not in 08.2/08.3 either). |
| Member unlocks paid content by deleting/truncating links | Elevation of privilege | Admin-claim-only write policies plus TRUNCATE revoked (new; the old course tables lacked it) |
| Draft course titles leaked through product detail | Information disclosure | Manager-only `courses`/`lives`; integration assertion on a member's response |
| Gate opens during migration | Elevation of privilege | Backfill and body swap in one file; drop after; rehearsal compares answers |
| Stale client sends `productIds` to course routes | Tampering | `.strict()` 400, no write; integration assertion |
