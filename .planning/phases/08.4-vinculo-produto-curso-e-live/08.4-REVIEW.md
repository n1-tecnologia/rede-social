# Phase 08.4: Code Review Report

**Reviewed:** 2026-10-14T23:30:00Z
**Depth:** standard
**Files Reviewed:** 64 (three generated snapshots spot-checked only)
**Status:** issues_found

## Summary

Phase 08.4 moves the course and live unlock links from the courses module (08.3's `course_products` / `course_live_products`) to two store-owned tables (`store_product_courses` / `store_product_lives`). After the move, the product routes are the only code that writes these links (D-418). I reviewed the phase diff (`c277ec3d..HEAD`) for the migrations, the store and courses services, contracts and routes, the web forms and pages, the BFF loaders and actions, and the test, e2e and rehearsal assets.

The core of the move is sound, and I traced each of these points:

- **Gate bodies.** The four re-pointed bodies (`app.course_locked_ids*`, `app.live_locked_ids*`) match the 08.3 bodies token for token except for the table names. I diffed them against `20261013205601_store_course_gate.sql` and they are identical modulo whitespace.
- **Migration order.** The carry-over and the swap share one file, behind a two-way set-difference guard. The drop is a separate, later file.
- **TRUNCATE.** `truncate` is revoked on both new tables, and pgTAP 190 asserts it.
- **Tenant scoping.** Every service statement pins `tenant_id = ctx.tenantId`. A cross-tenant course or live id collapses to one `400 course_invalid` / `live_invalid`.
- **Replace semantics.** A replace deletes only the difference, so links to archived courses and cancelled lives are kept, under the product row lock.
- **Manager-only fields.** The `courses` / `lives` fields of the product detail are only filled on the `canManage` branch, so a member's detail never names a draft course.
- **Leftovers.** No remaining code reads or writes the dropped tables: `grep` over `apps/`, `packages/` and the seed is clean.
- **Checks.** `biome check` on the changed areas and `apps/web` `tsc --noEmit` both pass.

I found no blocker. Three warnings remain:

- **WR-01:** adding keys to a `.strict()` response contract breaks any older web revision during a deploy window or a rollback. `docs/DEPLOY.md` explicitly allows such a rollback.
- **WR-02:** the live picker can list the same live twice.
- **WR-03:** the store module now depends on the courses schema, both in its migrations and in every manager product read, and the store's own docs do not say so.

## Warnings

### WR-01: New `courses` / `lives` keys on a `.strict()` response schema break older web revisions, and DEPLOY.md's rollback guidance allows exactly that combination

**File:** `packages/modules/store/contracts/index.ts:237-252`, `apps/web/lib/store.ts:98,271,295`, `docs/DEPLOY.md:1563`

**Issue:**
- **The contract change.** `productDetailSchema` is `.strict()`, and the web parses every product read and write response with `productDetailSchema.parse(...)`. Phase 08.4 adds two optional keys, `courses` and `lives`, that the API now always sends to a manager on `GET /products/{id}`, `POST /products` and `PATCH /products/{id}`.
- **Which web revisions break.** Any web revision built from the 08.2 contract rejects these responses with "Unrecognized keys". Its `getProduct` then returns `status: 'error'`, so the admin's edit page becomes a not-found and the product page errors.
- **The create path is worse.** `createProduct` / `updateProduct` throw after the API has already committed the write. The old form shows "Não foi possível salvar" for a product that was in fact created, so an admin who retries creates a duplicate product.
- **When this happens:**
  - in any environment where an 08.2 web is live while the 08.4 API deploys (the API is deployed before the web);
  - permanently, if someone follows `docs/DEPLOY.md:1563`'s guidance and rolls the web back "to one older than 08.3", which means an 08.2 revision, while the API stays on 08.4.

**Fix:** Either make the response schemas tolerant of additive keys, or correct the rollback note. Preferably do both.

```ts
// contracts: requests stay strict; responses must accept additive fields from a newer API
export const productDetailSchema = z
  .object({ /* … */ courses: z.array(productCourseSchema).optional(), lives: z.array(productLiveSchema).optional() })
  .strip(); // or a separate strict request schema and a non-strict response schema
```

Then update DEPLOY.md: "Never roll the web back to a revision older than 08.4 while the API is on 08.4. The store detail contract gained keys that an older web rejects."

### WR-02: The live picker can list the same live twice (React key collision)

**File:** `apps/web/lib/courses.ts:900-925`

**Issue:** `listProductFormLives` makes two separate HTTP walks:
- first `filter: 'upcoming'` (end still ahead of the API clock);
- then `filter: 'past'` (end behind the clock).

A live whose end falls between the two requests is returned by both walks. The same applies to any live whose window closes while the `upcoming` pages are still being walked. The live is pushed twice into `items`, so:
- `CoursePickerSheet` renders two `<li key={item.id}>` with the same key, a React duplicate-key error that can make reconciliation drop or misplace rows;
- two rows toggle the same id;
- the `helperCapped` count is inflated.

The window is small, but it is exactly the moment an admin is likely to be editing the product of a live that is about to end.

**Fix:** De-duplicate by id while appending, keeping the first occurrence:

```ts
const seen = new Set<string>();
// …
for (const live of result.items) {
  if (live.status !== 'cancelled' && !seen.has(live.id)) {
    seen.add(live.id);
    items.push(live);
  }
}
```

### WR-03: The store module now hard-depends on the courses schema, and its docs still say it has no `requires`

**File:** `supabase/migrations/20261014201954_store_course_links_functions.sql:37-43`, `packages/modules/store/server/service.ts:615-616` (also `resolveCourses` / `resolveLives` / `replaceCourseLinks` / `replaceLiveLinks`), `packages/modules/store/module.ts:13`, `packages/modules/store/README.md`

**Issue:** Phase 08.4 makes the store depend on the courses schema in two places:
- **Migrations.** The store's own migration adds foreign keys to `public.courses(id)` and `public.course_lives(id)`.
- **Runtime reads.** `readDetail(…, canManage = true)` always runs `linkedCourses` and `linkedLives`. These read `courses` / `course_lives` by SQL table name, whether or not the courses module is installed or enabled.

A project that reuses the store without the courses package (MOD-01..05: "reusable in other projects") would see:
- the store migration chain fail at file 2 (`relation "public.courses" does not exist`);
- if that file were skipped, every manager product read fail with a 500.

The courses README now documents its own reverse debt ("must replace the three read-only product reads"). The store README and `module.ts` still describe the store as self-contained ("No `requires`"), so the new coupling is invisible to anyone reusing the store.

**Fix:** At minimum, document the dependency where a store consumer will see it, in `packages/modules/store/README.md` and the `module.ts` header. For example: "Since 08.4 the store's schema references `courses` / `course_lives` (hand FKs in `*_store_course_links_functions.sql`) and the manager detail reads them by SQL; a course-less reuse must drop that migration and the two `linked*` reads." Optionally, guard the manager-detail reads with `to_regclass('public.courses') is not null`, or skip them when the tenant's `courses` module is off. The web only shows those blocks when courses is on.

## Info

### IN-01: Linking a published course or live locks it with no lock-impact confirmation

**File:** `apps/web/app/(app)/loja/ProductForm.tsx:420-455`

**Issue:** The lock preview and danger confirmation (D-364) only run for added communities. Adding a published course or a live to a product locks it immediately for every non-holder, with no count and no dialog. This follows the documented decision A-UI-3, and today it has no member-visible effect because the member school has not shipped yet. Once the member course screen ships, an admin will be able to silently cut existing learners out of a course they were following.

**Fix:** Track this as a follow-up for the member-school phase: extend `lockPreview` to `courseIds` / `liveIds` before members can read courses.

### IN-02: Links to archived courses and cancelled lives can never be removed

**File:** `packages/modules/store/server/service.ts` (`replaceCourseLinks`, `replaceLiveLinks`, `linkedCourses`, `linkedLives`)

**Issue:** By design, a replace never deletes a link to an archived course or a cancelled live, and the manager detail never lists one. Archiving a course and cancelling a live are both terminal (`status_invalid` out of `archived`; no un-cancel), so no surface (UI or API) can ever remove these rows. They are harmless today: an archived course is invisible to members under RLS. They do, however, accumulate outside the `STORE_MAX_LINKS` cap, which only counts the sent set.

**Fix:** None is required now. Note it in the store README next to the CR-02 rule, so a future "free this archived course" request does not assume a path exists.

### IN-03: Stale doc comments after the link move

**File:** `apps/web/lib/courses.ts:188`, `apps/web/lib/courses.ts:956`, `packages/modules/courses/ui/CoursePickerSheet.tsx:60,69`

**Issue:**
- `lib/courses.ts` still lists `product_invalid` among the course and live refusal codes, but the code was removed from `COURSE_ISSUES`.
- `CoursePickerSheetProps.items` is documented as "The tenant's PUBLISHED courses", and `empty` as "the no-published-course state". The product form now passes draft courses and lives through the same props.

**Fix:** Drop `product_invalid` from the two comments, and make the sheet's prop docs host-neutral ("the host's items, in the host's order").

### IN-04: The link tables do not enforce tenant consistency of their foreign keys

**File:** `supabase/migrations/20261014201933_store_course_links.sql:36-43`, `supabase/migrations/20261014201954_store_course_links_functions.sql:37-43`

**Issue:** `product_id`, `course_id` and `live_id` reference `(id)` only, so the database itself would accept a row with `tenant_id = A` and a course or product of tenant B. The service always validates, and every reader and the gate join or filter on `l.tenant_id`, so I found no leak path. Still, defence in depth stops at the service layer. This is the same posture as the `store_product_communities` precedent.

**Fix:** This is optional hardening for a later migration: add composite FKs, `(tenant_id, course_id) references courses (tenant_id, id)` (which needs a unique `(tenant_id, id)` on the target), and do the same for products and lives.
