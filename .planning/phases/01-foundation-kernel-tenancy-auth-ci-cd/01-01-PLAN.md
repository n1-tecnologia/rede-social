## Phase Goal

**As a** person invited by an organisation that runs a TRIA community (a tenant), **I want to** sign up through that organisation's public link, log in with e-mail and password, stay logged in, recover my password and log out, **so that** I reach my organisation's private community on one URL and the API only ever serves my organisation's data.

(User story derived by the orchestrator from the ROADMAP Phase 1 Goal line + success criterion 1, because the Goal line is not in user-story format.)

Bring up the toolchain and the `@tria/*` monorepo (D-18), then prove the riskiest architecture end-to-end with one tracer: a real Supabase access token for a seeded `tria-demo` member → Hono `requireAuth` (jose JWKS, ES256) → `app.membership_for_user()` → `withTenantTx` (`set_config` + `SET LOCAL ROLE authenticated` through `api_user` on the local transaction pooler) → `GET /v1/me/bootstrap` returning the member's tenant and role. This is the Walking Skeleton's spine (see `SKELETON.md`); plan 01-02 adds the browser login slice on top of it.

Purpose: TENANT-03 (RLS lane under a non-service role), AUTH-06 (JWKS + per-request membership), ROLE-01/02 (roles on memberships, identity ≠ membership), TENANT-01 (tenant from membership, never hostname), MOD-01 (monorepo with kernel package).
Output: runnable monorepo, local Supabase stack with ES256 keys, core schema + migrations + `api_user`, kernel auth/lane code, `/v1/health`, `/v1/me/bootstrap`, seed script, passing integration test.
