<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Next server action | the form passes a `tenantId` argument, which the tenant lane ignores |
| browser → signed Storage URL | upload bytes go straight to Storage under the session tenant's key prefix |
| API → kernel platform services (admin lane) | the services bypass RLS; the tenant id they receive is the only isolation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-31 | Elevation / Tampering | tenant-lane branding routes | critical | mitigate | No tenant id in any path or body; `ctx.tenantId` only; the actions ignore the form's argument; integration proves rede-lab unchanged; grep acceptance for `{id}` absence |
| T-08-32 | Elevation | `PATCH /v1/admin/tenant` | high | mitigate | Strict body `{ displayName }` only; status, slug, modules and domains are unreachable; a body with `status` is a 400 case |
| T-08-33 | Information disclosure / Tampering | upload completion with a foreign `uploadId` | high | mitigate | The kernel completes only objects under the session tenant's prefix; a lab `uploadId` is the bare 404 (T-03-56 rule) |
| T-08-34 | Denial of service | oversized or wrong-type uploads | medium | mitigate | The shipped `brandingUploadBodySchema` and the `branding` bucket's 2 MiB cap and mime list apply unchanged |
| T-08-35 | Repudiation | branding edits by admin_tenant | low | accept | Branding is not a moderation action (MODER-03 lists delete, block, unblock); the kernel services already log `platform.branding.*` lines with the actor id |
</threat_model>
