## Phase Goal

**As an** `admin_tenant`, **I want to** run my community from my phone (brand, members and roles, moderation and community rules), **so that** every action takes effect immediately, is logged, and the pilot can pass its go-live gate. Each slot is taken from the ROADMAP Phase 8 Goal line, which is not written in story form; the planner flagged this in its return.

<objective>
The phase tracer. One moderator action goes through every layer this phase touches: the database (the new append-only kernel table and the `deleted_by_user_id` column), the kernel (the `moderation.manage` permission and the single log writer), a module (the feed's widened comment delete), the API (the new `/v1/admin` mount with the log read), and the web (the moderator's removal control, the new Configurações row, and the Moderação screen).

**Plan story:** **As an** `admin_tenant`, **I want to** remove a member's comment (and its replies) from the post where I see it, and then find that removal in the Moderação history, **so that** I can keep the conversation clean and the removal is on record. Taken from MODER-01, MODER-03 and SC 1.

Decisions implemented: D-334 (cascade, `deleted_by`), D-335 (silence), D-336 (feed half), D-337 (append-only log with excerpt, reversibility costly), D-338 (`moderation.manage` for `admin_tenant` only), D-339 (the Moderação row), D-340 (removal in context) and D-343 (UI-SPEC only, no sketch gate).

Claude's Discretion choices recorded here:
- **Moderation module shape:** moderation is a KERNEL capability, not a `packages/modules/moderation` package. SCHEMA-CONVENTIONS §(f).2 already lists moderation as an always-on capability with no flag, `defineModule` refuses keys outside `TOGGLEABLE_MODULES`, and switching it off would break the atomicity of removals. Feed and stories call a published kernel function inside their own transaction. D-347's "new moderation module" README therefore lives at `packages/core/server/moderation/README.md` (08-09).
- **Role changes are logged:** the action CHECK includes `role_changed` from day one (written by 08-05), as the UI-SPEC assumed.
- **Confirmations, no undo:** removal always goes through the shared `ConfirmDialog`, and no restore exists.

Two CONTEXT corrections apply (08-UI-SPEC): D-340's "⋯ menu" is the shipped `Trash2` control reused on more rows, not a new menu. D-342's `updateTag` does not exist in `apps/web`; that matters in 08-06, not here.

Purpose: prove the kernel-log architecture end to end on the agent's freshest tokens, before every later plan writes through `recordModerationAction`.
Output: the schema and migrations, pgTAP 154, the kernel writer and reader, the widened feed delete, `GET /v1/admin/moderation-log`, the moderator control, and the Moderação screen at tracer depth.
</objective>
