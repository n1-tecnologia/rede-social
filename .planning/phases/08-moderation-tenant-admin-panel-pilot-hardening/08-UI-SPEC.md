# Phase 08 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design authority.** `reference/frontend-design/` has **no admin screens at all** (PROTOTYPE.md §"ADMIN-01..04: no admin UI at all"). Every Phase 8 surface is therefore **[designed]** in the prototype's language from primitives that already ship: the Configurações `Row`/`Group`, list rows, `BottomSheet`, `ConfirmDialog`, `Chip`, `SearchBar`, `StatusPill`, `Textarea`, `InfiniteScroll`, and the platform branding editor (`BrandingForm`, `ContrastFeedback`, `BrandPreview`) reused unchanged. **There is no sketch gate** (D-343, mirroring 08.1's D-319): this document is the only design artifact, and nothing waits on a `/gsd-sketch` approval. The design language, spacing scale, type scale and colour model are **inherited unchanged** from the approved `02`–`07-UI-SPEC.md`; this document restates them for the checker and records only the Phase 8 deltas.

**Upstream decisions.** `08-CONTEXT.md` decisions are cited as **D-330..D-349** and are not re-litigated. `08-RESEARCH.md` patterns are cited as **R-Pn** and pitfalls as **R-Pitfall n**. Earlier visual decisions keep their numbers (UI-D-08, UI-D-14, UI-D-24, UI-D-206, UI-D-262, UI-D-263). The UI questions CONTEXT left to Claude's Discretion are decided below as **UI-D-269..UI-D-288**. The block continues after 07-UI-SPEC's UI-D-268, so it cannot collide with 08.1's UI-D-320..UI-D-327 or with CONTEXT's D-330..D-349. No question was put to the user: CONTEXT locks every user-owned choice, and the remaining items are Claude's Discretion.

**Two CONTEXT statements corrected here, with evidence.**
1. D-340 and the Specific Ideas speak of the comment **"⋯" menu** showing "Remover". The shipped comment row has **no menu**: it has one 14px `Trash2` control, named "Excluir comentário", that opens the shared `ConfirmDialog` directly (`packages/modules/feed/ui/CommentItem.tsx:213-227`, whose comment says the control becomes a menu only when "Denunciar" arrives, which is MODER-05 / Phase 11). The intent of D-340 ("admins should feel no new place to learn") is honoured by **reusing that same control** on every comment for moderators (UI-D-276). No menu is introduced.
2. D-342 says the tenant-lane branding editor is "the platform one, reused", and the form's actions take `(tenantId, …)`. `BrandingForm` has **no display-name field** (R-P5), so ADMIN-01's name edit is a separate card above the unchanged form (UI-D-279). The tenant-lane actions **ignore** the `tenantId` argument (R-P5, anti-pattern "trusting a tenantId from the browser").

**Research assumptions closed here.** A6: the block/unblock reason is capped at **500** characters and the comment excerpt at **280** (UI-D-274, UI-D-278). A7: invited memberships get **no** block, unblock or role action in the UI; their sheet is read-only (UI-D-272). Open question 1: the click-to-play YouTube/Vimeo player ships in this phase as the visible half of the CSP work (UI-D-282). Open question 4: invited rows are shown read-only, with no resend or cancel here. "Should role changes be logged?": this contract **assumes yes** (R-P2's CHECK lists `role_changed`) and draws its row and its filter chip. If the planner decides otherwise, the "Papéis" chip and the role row variant are simply not built.

## Interaction & Accessibility

- **Prefetch-safe:** no GET render changes anything. Every admin mutation is a server action from a button press.
- **No role comparison in the web tier:** every row, trigger and control is gated on `bootstrap.permissions` (`tenant.manage`, `members.manage`, `moderation.manage`). The API re-enforces every gate, and the D-332 guards live only in the API (UI-D-273, UI-D-284).
- **`tenantId` never comes from the browser:** the tenant-lane branding actions ignore the form's `tenantId` argument, and every admin URL carries no tenant id (R-P5).
- **Optimistic updates:** none for block, unblock, role change or comment removal. Each waits for the server, shows a pending state, then updates in place. These actions are logged and partly irreversible, so the UI never shows a state the server has not confirmed.
- **Keyboard:** Enter in the search field does nothing extra (the debounce drives it); arrow keys move within the role `radiogroup`; Escape closes the sheet, the dialog and the rules preview (shipped). The confirm step's "Voltar" is reachable before the confirm button in tab order on desktop (`md:flex-row` order: "Voltar", then the confirm).
- **Focus, live regions, motion, clock and text safety:** UI-D-288.
- **CSP note (R-Pitfall 11):** admin forms submit through server actions (`fetch` with JS loaded), so `form-action 'self'` does not affect them on alias hosts. No admin form relies on a no-JS POST.
