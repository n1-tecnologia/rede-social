# Phase 11.1 Plan 06: store service half of buyer permissions Summary

**The product form's save now carries the five buyer flags per linked community (`communityLinks`), written with the links in the product transaction, with an idempotent `on conflict ... do update ... where is distinct from` for a changed flag, and read back to the administrator only for links that differ from the defaults.**

## Performance

- **Duration:** about 10 min of wall clock
- **Started:** 2026-11-25T11:58:00Z (approximate, from the first command)
- **Completed:** 2026-11-25T12:08:00Z
- **Tasks:** 3 (one tracer, two auto)
- **Files modified:** 3 (service, routes docs, one new integration file)

## Accomplishments

- `createProduct` and `updateProduct` take `communityLinks` through the same `resolveCommunities` check as `communityIds`; the links are written in the product transaction, the lock preview and the access OR are untouched (D-886).
- `replaceLinks` takes a `LinkSet`: the `ids` form keeps `do nothing` (stored flags survive, new links take the defaults), the `links` form upserts the five flags and writes nothing when they are unchanged (T-11.1-23). The delete branch and the archived-link survival rule (CR-02) are unchanged.
- The manager detail (create answer, patch answer, GET for `store.product.manage`) carries `communityPermissions` only for active, live links whose flags differ from (true, true, true, false, false); no member-readable payload names a flag.
- 15 integration cases pinning the write path, the update path, the refusals and the member-payload absence; a mutation check confirmed the idempotency case fails when the `where ... is distinct from` is removed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Ordering] Task 2's service code landed in the Task 1 commit**
- **Found during:** Task 1
- **Issue:** `replaceLinks`, `updateProduct` and the upsert had to change in the same pass as `createProduct` because they share the `LinkSet` type; the failing-tests-first order of Task 2 was not kept for the code.
- **Fix:** Task 2's tests were written afterwards and then proven to have teeth with a mutation check (removing the `where ... is distinct from` made cases b and c fail; restored, no diff). Task 2's commit is therefore tests only.
- **Files modified:** packages/modules/store/server/service.ts
- **Committed in:** dd11b17f

**2. [Placement] The upsert is in `insertLinkFlags`, not inline in `replaceLinks`**
- **Found during:** Task 2
- **Issue:** the acceptance line says `is distinct from` "inside replaceLinks"; one helper serves the create insert (plain) and the replace upsert.
- **Fix:** `replaceLinks` calls `insertLinkFlags(..., true)`; the grep over the file passes and the `communityIds` path still has its own `do nothing` arbiter.
- **Committed in:** dd11b17f

**3. [Rule 2 - Missing critical] The create answer also carries `communityPermissions`**
- **Found during:** Task 1
- **Issue:** the plan names the manager read; the create route answers a manager detail too, and a form that saves a new product needs the flags back.
- **Fix:** `createProduct` spreads `permissionsKey(...)`; omitted at defaults, so a `communityIds`-only create is unchanged.
- **Committed in:** dd11b17f
