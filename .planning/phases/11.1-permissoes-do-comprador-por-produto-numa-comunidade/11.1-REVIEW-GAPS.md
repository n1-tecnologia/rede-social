## Warnings

### WR-01: `social` turned off while the composer is open now answers `generic` and logs, instead of the neutral `refused` sentence

**Resolution (orchestrator, 2026-11-25): FIXED in 0004849b.** The lane predicate is now "a community in the body AND no `content.publish`" (no `social.participate` needed); new case W7 pins a buyer with an empty bootstrap as `refused` and a staff bootstrap without a `social` key as `generic` + logged. A mutation back to the old predicate turned W7 red. The text below is the reviewer's original finding.

**File:** `apps/web/app/(app)/criar/actions.ts:64-66` (lane predicate), with `apps/web/lib/feed-view.tsx:303-305` (`isMemberComposer`)
**Issue:** The member lane is decided from the live bootstrap, after the failed write:
`isMemberComposer(permissions)` = `social.participate` present AND `content.publish` absent. But `social.participate` is composed only while the `social` module is effective (`apps/api/src/modules/registry.ts:229-250`, `permissionsFor` reads `effectiveKeys`; the module manifest grants it to `member` only). The member's write path is gated by `feed.post.create`, which `permissionsFor` composes under that same `effective.has('social')` condition (`registry.ts:243-245`).

So the sequence is: the buyer opens the pinned composer, the tenant admin switches `social` off, the buyer publishes. The API answers a bare 403, and `getBootstrap()` then returns permissions with no `social.participate`. `isMemberComposer` is false and the lane resolves to `false`. The member gets `{ code: 'generic' }` plus a `feed.post.write_failed` error log. They do not get `refused`, and the community page is not revalidated.

That is the scenario UI-D-892 and UI-D-893 name ("Refusal after the fact (refund, `social` turned off, community archived while the composer is open)"). It is also the scenario the code comment at `actions.ts:77-79` lists as producing `refused`. The comment and the code disagree. The composer then shows its generic error and stays editable and re-submittable, instead of disabling "Publicar" with the one neutral sentence.

The tests miss it. `MEMBER_LANE` always contains `social.participate` and `STAFF_LANE` always contains `content.publish`. Nothing exercises a 403 whose bootstrap is a member with `social` off (permissions with neither `social.participate` nor `content.publish`). The refund and community-archived cases are fine, because role-level permissions survive them.

**Fix:** Decide the lane by "not the organization's composer" instead of by a permission the very refusal may have removed. Keep the fail-safe for an unreadable bootstrap:
```ts
mapRefused: async () => {
  if (body.data.communityId === undefined) return false;
  const { permissions } = await getBootstrap(); // a rejection is already false in resolveLane
  return !permissions.includes('content.publish');
},
```
Optionally also accept `isMemberComposer`, but the second clause above is what covers `social` off. A staff 403 still has `content.publish`, so it stays generic and logged (W1 unchanged). A member with no community still short-circuits to false (W3 unchanged).

Add a test next to W1..W6: `getBootstrap` resolves `{ permissions: ['feed.post.create'] }` or `[]` (member, `social` off), `createPost` rejects with a bare 403, and the result is `{ ok: false, code: 'refused' }` with no `console.error` and a `/comunidades/{id}` revalidation. Also fix the broken hard-wrap of the comment at `actions.ts:77-79` while there.

If the owner prefers to keep today's behaviour, then drop "`social` turned off" from the comment at `actions.ts:77` and from UI-D-892/893, and record the choice, so the code and the contract agree.
