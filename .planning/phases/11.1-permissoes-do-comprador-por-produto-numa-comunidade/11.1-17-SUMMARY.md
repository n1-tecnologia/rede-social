# Phase 11.1 Plan 17: The buyer's post flow Summary

**A buyer posts from the community page into the shipped member composer pinned to the organization community; a refusal after the fact (refund, `social` off, archived) is the one neutral sentence with the caption and media kept, "Publicar" disabled and the destination pinned so the words can never be re-sent to Explorar; the buyer's Playwright walk is written and listed for the owner.**

## Performance

- **Completed:** 2026-11-25T16:01:44Z
- **Tasks:** 3 (one tracer, two auto)

## Accomplishments

- **The tracer is the proof, not new wiring.** `/criar` already resolved `?comunidade=` against `viewer.actions.post` for any member (plan 10-14) and the community page already passed `canPost` and `createHref`. The new cases show the whole buyer path through the real code: the page keeps the organization community only on the fact (Q1 to Q3), the composer is the pinned member composer with the read-only audience line and no picker (U1 to U4), and the REAL `FeedList`, rendered over the exact props the community page captured, draws the desktop button, the floating button and the empty-state CTA only when the fact holds (E1 to E5). Each group was shown to fail under a one-line mutation of the page (12 cases red), then the source was restored.
- **The refusal.** `createPostAction` now answers the one word `refused` for a bare 403 (`attemptPostWrite(..., { mapRefused: true })`, status only, tried after the bootstrap redirects, no log line) and revalidates `/comunidades/{id}`, the page the compose entries live on. The pinned `ComposerForm` keeps the caption and media, disables "Publicar" for good, shows `composer.member.errors.communityForbidden` in the form-error slot and returns before any second send.
- **The destination can never change silently.** The composer pins its community in state at first paint; a re-render that hands it no community (the server re-read the facts) leaves the audience line, the landing and the body untouched (V4). No `router.refresh()` is called on `/criar` for the same reason.
- **The silent fallbacks** (unknown id, failed read, archived, not allowed, foreign member community) are one quiet answer (F1), `social` off keeps the shipped redirect without reading the community (F2) and the buyer composer never reads the destination list (F3).
- **`buyer-permissions-member.spec.ts`**: four serial steps per project at 390 then 320 (desktop at its own width), registered in eight affected-map groups, listed (8 tests) and never run.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `lib/feed-write.ts` and its test are outside the plan's file list**
- **Found during:** Task 2
- **Issue:** the plan names `actions.ts` for "the action's refusal mapping", but the mapping from an API error to a result code lives in `attemptPostWrite` (`feed-write.ts`), which plan 15 owns for the like and comment actions.
- **Fix:** an optional `{ mapRefused }` on `attemptPostWrite` and `'refused'` in `PostWriteResult`; only the create action asks for it, so the edit path is unchanged.
- **Files modified:** `apps/web/lib/feed-write.ts`, `apps/web/lib/feed-write.test.ts`
- **Committed in:** `a19d1817`

**2. [Rule 3 - Blocking] Two additive fixture helpers in shared e2e files**
- **Found during:** Task 3
- **Issue:** the spec has to raise single permission flags of a link and open a highlight to buyers; no helper existed and the helpers' SQL client is module-private.
- **Fix:** `setLinkPermissions` in `e2e/store-admin.ts` and `setHighlightOpenToBuyers` in `e2e/admin.ts`, both additive.
- **Committed in:** `ca8a81bd`

**3. [Plan wording] `criar/actions.test.ts` was created**
- no test of the create action existed; the refusal mapping needs one (R1 to R7).

**4. [Plan wording] The refusal does not "re-read the page facts" of `/criar`**
- the plan says the composer "re-reads the page facts so the compose entries disappear". The entries are on the community page, and a `router.refresh()` of `/criar` would re-render the composer with no community, which is the silent change of destination the same truth forbids. The action revalidates the community page instead and the composer pins its community.

**5. [Plan wording] The community page's entries are proved with the real list**
- the page test mocks `CommunityPosts`; the DOM-level proof renders the real `FeedList` from the module over the props the page captured.

**6. [Process] Test order**
- Task 1's cases passed on first run (the wiring existed) and were proved non-vacuous by mutation. Task 2's cases were written after the implementation in the same sitting; the composer cases were proved non-vacuous by removing the pin, the submit guard and the disabled term (4 cases red), then restoring the file.
