### Locked Decisions
(copied verbatim from `11.1-CONTEXT.md` `## Implementation Decisions`)

**Postar na comunidade (post in the community)**
- **D-880:** The "post" permission exists only for **organization communities**. Member-created communities cannot be linked to products (D-713: the creator's form has no products field), so the permission never applies to them and the creator-only rule of D-706 is untouched there. This fills the third path that Phase 10 left open in the owner rule for an organization community with a member author (`resolveCommunityTarget` branch 3, `communityActionAllowed`). — **Reversibility:** costly — the rule lands in the post write seam, in RLS and in the permission composition, like D-706.
- **D-881:** A buyer's post is the **same post a member publishes** (D-709). It is stamped `visibility = 'community'`, never `'tenant'`: it appears **only on the community's page**, for whoever can read the community, and **notifies nobody** (D-702; community posts notify nobody). It does not go to Início or Explorar.
- **D-882:** "Post" **requires the `social` module effective** for the tenant. The route stays behind `feed.post.create` (members hold it only with `social` effective, D-707); no second publish path is created. With `social` off the buyer still reads the community and can still like and comment if the product allows (D-718: only writes that exist because of `social` stop). The database insert gate must carry its own `social_enabled()`, active-community, not-deleted and tenant terms: the reserved fourth clause in `feed_posts_social_insert_gate` has none of them today.

**Postar story (post a story)**
- **D-883:** The "story" permission means the buyer can **save one of their own stories into a highlight of that community**. A story still has no community column; no "story of the community" concept is added. Saving it is the act of publishing it in the community: it is readable by everyone who can see the community, including after the 24 hours (D-716), and the publish and highlight screens keep the warning ("Todos os membros verão este story na comunidade").
- **D-884:** The buyer can use **only highlights the administrator marked as open to buyers**: a new per-highlight switch on highlights of organization communities (the admin sets it on the highlight screens of 05.2/05.1). Highlights that are not open stay administrator-only. A buyer cannot create a highlight and cannot edit or reorder one (D-713 is unchanged for creators). — **Reversibility:** costly — a new column on the highlight, the three database gates `HIGHLIGHT_OWNER`, `ITEM_OWNER` and `ITEM_STORY_AUTHOR` widen for it, and the audience gate (`stories_audience_gate` branch 3) already makes saved stories readable to the community.
- **D-885:** A buyer adds and removes **only their own stories** in an open highlight. An administrator can remove any item from any highlight, as today. Which of the buyer's stories can be saved is the buyer's own (member story rules of Phase 10: member stories exist with `social` on).

**Duas compras e reembolso (two purchases and refunds)**
- **D-886:** Permissions **add up**. A member's permissions in a community are the union of the five flags of every linked product that has an **active entitlement** for that member. This is how access already works (any active linked product unlocks; the gate is an OR in `app.community_locked_ids()`), now carrying the flags.
- **D-887:** Refund, chargeback, revoke or cancel ends the permission **at once, because the flags are read from active entitlements** (the gateway path already sets the entitlement to `revoked`). What the buyer already published (posts and stories saved in highlights) **stays**. Nothing is hidden automatically; the administrator removes content through the moderation that exists (D-711 log for admin actions on member content). If the buyer loses every product of the community, the locked-community behavior of 08.2 applies as today.

**O que o membro vê (what the member sees)**
- **D-888:** A control the product does not allow **disappears**: no heart, no comment field, no post button, no "+" for a story, no disabled state, no notice. The server **refuses the same action regardless** of the screen (HTTP 403; the error code and body must not leak which product or which flag, the planner decides the code). Staff roles always have every action.
- **D-889:** "Share" is **only hidden**. It is a screen control with no server gate; a person who copies the link cannot read the community without access anyway. No server-issued share link is built. — **Reversibility:** reversible — adding a controlled share link later is additive.
- **D-890:** In the product form, linking a community shows **five checkboxes for that community**. A new link starts as today's products: like, comment and share ticked, post and story unticked. The migration fills every existing link with those values, so nothing changes for anyone until the administrator edits the product. Links are written only in the product form (D-363).
- **D-891:** The flags are stored **per link (product × community)**, not per product, so one product can allow different things in different communities. — **Reversibility:** costly — the flags are read by the like, comment, post and highlight gates, the viewer-actions contract and the product form; moving them later touches all of those.

**Unchanged (carried forward, not re-asked)**
- **D-892:** A community with **no linked product** is open and behaves as today. Staff (`admin_tenant`, `support_tenant`) always hold every action. A locked community (member without an active entitlement) stays read-only sample access (D-356: the newest post, all-or-nothing, 403 `community_locked`); the permissions only split what an unlocked buyer may do.

## Summary

The phase is a **database-first** change that sits on three existing seams and needs no new library. (1) The access OR already ranges over a member's active entitlements and the linked products (`app.community_locked_ids()`); the flags are the same join with `bool_or` per flag. (2) Phase 10 left a constant-false kernel stub (`app.community_action_allowed`), a reserved fourth OR clause in `feed_posts_social_insert_gate`, a TypeScript wrapper (`communityActionAllowed`) and the one site that builds `viewer.actions` (`viewerOf`). (3) Highlights and items already have restrictive member gates (`HIGHLIGHT_OWNER`, `ITEM_OWNER`, `ITEM_STORY_AUTHOR`); only the **item** insert/delete gates need a buyer alternative, the highlight-level gates (create, update, delete, reorder) must stay creator-only because D-884 says a buyer cannot create, edit or reorder (this narrows CONTEXT D-884's list of "three gates widen": `HIGHLIGHT_OWNER` and `ITEM_STORY_AUTHOR` do not widen).

The recommended shape is one kernel-visible **scope function** `app.community_buyer_scope() jsonb` (a map community id -> the five flags plus `openHighlight`, only for a non-staff member, only org communities of the tenant, only from active entitlements, store module on), evaluated once per statement as an InitPlan, and two thin wrappers: `app.community_action_allowed(community, action)` (replaces the stub; "does a product grant this action", false for everything else, so most of the existing pgTAP 230 section 9 assertions still hold as negative controls) and `app.community_action_denied_ids(action)` (a `uuid[]` in the shape of `LOCKED_COMMUNITY_IDS`, used by the like and comment restrictive gates). The flags are five `boolean not null default` columns on `store_product_communities` (a constant-default `ADD COLUMN` backfills every existing row with like/comment/share true, post/story false and is metadata-only on this project's Postgres 17.6), plus `story_highlights.open_to_buyers boolean not null default false`.

Two items need Igor's decision before planning: **(A)** the locked-community free sample (`app.feed_sample_post_ids`) takes the newest live post of a locked community with no visibility filter, so a buyer's post could become the public sample shown to non-buyers; **(B)** `stories_audience_gate` branch 3 has no locked-community term, so a buyer's story held by an organization highlight is readable by id by a locked member. Both are recommended fixes inside this phase (section 6, Open Questions).

**Primary recommendation:** build the SQL scope function and the gates first (plans 02-04), put every new response key behind "emit only when it differs from today's default" so the previous web and API stay compatible in both directions, release in the order migrations -> API and worker -> web, and keep sketch 026 as plan 01 with every web plan carrying the `approved: true` precondition.

### Pattern 1: scope function + wrappers (the `community_locked_ids` shape)
**What:** one definer computes the caller's grants; wrappers expose the two shapes callers need.
**When to use:** every gate and every projection. **Source:** pattern copied from `20261008171645_store_functions.sql:92-110` (staff by claim, tenant pinned, `search_path = ''`, EXECUTE revoked from PUBLIC and granted to `authenticated`).
```sql
-- plpgsql so story_highlights.open_to_buyers binds at first call, not at creation
create or replace function app.community_buyer_scope() returns jsonb
language plpgsql stable security definer set search_path = '' as $$
begin
  -- fail closed: only an explicit member claim with a tenant and a user holds a product grant
  if app.tenant_id() is null or app.user_id() is null
     or app.tenant_role() is distinct from 'member' then
    return '{}'::jsonb;
  end if;
  return coalesce((
    select jsonb_object_agg(g.community_id::text, jsonb_build_object(
             'like', g.can_like, 'comment', g.can_comment, 'share', g.can_share,
             'post', g.can_post, 'story', g.can_story, 'openHighlight', g.open_highlight))
      from (
        select l.community_id,
               bool_or(l.can_like) as can_like, bool_or(l.can_comment) as can_comment,
               bool_or(l.can_share) as can_share, bool_or(l.can_post) as can_post,
               bool_or(l.can_story) as can_story,
               exists (select 1 from public.story_highlights h
                        where h.tenant_id = l.tenant_id and h.community_id = l.community_id
                          and h.open_to_buyers) as open_highlight
          from public.store_product_communities l
          join public.store_entitlements e
            on e.tenant_id = l.tenant_id and e.product_id = l.product_id
          join public.communities c
            on c.id = l.community_id and c.tenant_id = l.tenant_id
         where l.tenant_id = app.tenant_id()
           and e.user_id = app.user_id() and e.status = 'active'
           and c.kind = 'organization' and c.deleted_at is null
           and exists (select 1 from public.tenant_modules tm
                        where tm.tenant_id = l.tenant_id and tm.module_key = 'store' and tm.enabled)
         group by l.tenant_id, l.community_id) g), '{}'::jsonb);
end
$$;
```
```sql
-- replaces the stub with create or replace, SAME signature, so feed_posts_social_insert_gate keeps the OID
create or replace function app.community_action_allowed(p_community_id uuid, p_action text) returns boolean
language sql stable security definer set search_path = '' as $$
  select p_action in ('like','comment','share','post','story')   -- 'openHighlight' must never answer
     and coalesce(((select app.community_buyer_scope()) -> p_community_id::text ->> p_action) = 'true', false)
$$;
-- like and comment need a uuid[] shape (InitPlan, same idiom as LOCKED_COMMUNITY_IDS):
create or replace function app.community_action_denied_ids(p_action text) returns uuid[]
language sql stable security definer set search_path = '' as $$
  select case when app.tenant_role() in ('admin_tenant','support_tenant') then '{}'::uuid[]
    else (select coalesce(array_agg(distinct l.community_id), '{}'::uuid[])
            from public.store_product_communities l
            join public.communities c on c.id = l.community_id and c.tenant_id = l.tenant_id
           where l.tenant_id = app.tenant_id() and c.kind = 'organization'
             and exists (select 1 from public.tenant_modules tm
                          where tm.tenant_id = l.tenant_id and tm.module_key = 'store' and tm.enabled)
             and not (p_action in ('like','comment','share')
                      and coalesce(((select app.community_buyer_scope()) -> l.community_id::text ->> p_action) = 'true', false)))
  end
$$;
```
Notes the planner must keep: (a) the denied-ids function uses the **claim** for staff like `community_locked_ids` does (a null or unknown role takes the member branch and denies: fail closed), while the scope function requires an explicit `'member'` (a null role holds no grant); (b) a locked community (no entitlement) is also "denied" for like/comment, which is consistent and harmless because the locked check runs first in `assertPostInteractive`; (c) neither function uses `limit 1` (pgTAP 040 pins the exact set of `app` functions whose body matches `ilike '%limit 1%'`, `040-schema-conventions.sql:301`); (d) `expires_at` exists on `store_entitlements` but the access OR ignores it (`e.status = 'active'` only), so the flags must too, to stay in lockstep `[VERIFIED: packages/modules/store/db/schema.ts:376 and store_functions.sql:86]`.

### Pattern 2: "emit only when it differs from today" for every new optional key
The 08.2 Pitfall 10 rule (every new response key `.optional()`, the web parses `.strict()`) is satisfied for this phase without a web-first release by **never emitting a new key at default values**: `post.community.actions` only when at least one of like/comment/share is false for the viewer; the manager's per-link `permissions` only for a link whose flags differ from `{like, comment, share}` true and `{post, story}` false; `openToBuyers` only when true and only on curator reads. Because the migration backfills defaults, no response of any tenant changes at release, so an old web never meets a new key until an administrator edits a product with the new web.

### Anti-Patterns to Avoid
- **Putting `like`/`comment` into `assertPostInteractive` for every caller.** `listComments` also calls it; reading comments must stay open (UI-D-890). Add an optional `action` parameter used only by `likePost`, `unlikePost`, `createComment`.
- **Reading the flags in TypeScript and deciding in the service only.** The RLS gate must call the same SQL function; a pgTAP equivalence test between the map and the wrappers prevents drift.
- **Widening `HIGHLIGHT_OWNER`.** A buyer must not create, edit, reorder or delete a highlight (D-884); only the item gates get the buyer alternative.
- **A `left join app.community_buyer_scope()` in the list projections** (see alternatives; measure before any join form).

## Common Pitfalls

### Pitfall 1: the comment-heart branch of `feed_likes_community_gate` hits the story-comment FK
**What goes wrong:** rewriting the comment branch as `exists (... join feed_posts p ...)` makes a like on a STORY comment fail the RLS check with 42501 before the foreign key can raise 23503, so `likeComment` answers 500 instead of `400 story_comment_not_likeable` (STORY-05 second half). **How to avoid:** `left join feed_posts p on p.id = c.post_id` and `(p.community_id is null or p.community_id <> all (DENIED_LIKE))`, so a post-less (story) comment passes the policy and reaches the FK. **Warning sign:** pgTAP 110/integration story-comment-like case turns 500.

### Pitfall 2: `unlikePost` and own-content deletes
`unlikePost` already calls the guard, so a buyer who lost `like` (or the whole community) cannot unlike (the locked rule: "a like placed before stays", `service.ts:2135-2137`). Pass `'like'` to it for consistency, but do **not** gate deleting one's own post, comment or story on the flag (D-887: content stays; the riders `canEdit`/`canDelete` drive the menu). A refunded buyer can still soft-delete their own story, which removes it from every highlight read (`s.deleted_at is null`).

### Pitfall 3: TOCTOU between revoke and write
The service guard and the RLS check are separate statements in one READ COMMITTED transaction; a gateway revoke that commits between them is seen by the RLS check (new statement snapshot) and raises 42501. `createPost` already maps a member 42501 to 403 (`service.ts:1398`); `likePost`, `createComment`, the item insert and `publishStory` need the same member-only 42501 -> 403 map (never mask a 42501 for staff). A revoke that commits after the insert statement leaves the content in place, which D-887 accepts; no entitlement row lock is added.

### Pitfall 4: the feed sample exposes a buyer's post (Open Question 1)
`app.feed_sample_post_ids()` selects the newest live post of each locked community with no visibility predicate (`20261008171520_feed_community_sample.sql:22-34`). With D-881 the newest post can be a buyer's `visibility = 'community'` post, shown with the buyer's name and avatar to members who did not buy. Recommended: add `and p.visibility = 'tenant'` to that function (an organization post only), pinned by a pgTAP case; needs Igor's word because D-892 says the sample is "the newest post".

### Pitfall 5: `stories_audience_gate` branch 3 has no lock term (Open Question 2)
Branch 3 opens any story held by a highlight of a community with `c.deleted_at is null` (`stories/db/schema.ts:229-239`); the inner `communities` read does not consult the store lock. Before this phase an organization highlight only held organization stories (`visibility = 'tenant'`, readable anyway); after it, buyer stories (`'followers'`) sit in organization highlights, so a locked member who learns a story id reads it, its likes and comments. Highlight reads already answer 404 for a locked reader (`resolveHighlightPlace`, `service.ts:1991`). Recommended: add `and c.id <> all (coalesce((select app.community_locked_ids()), '{}'::uuid[]))` to the inner `exists`.

### Pitfall 6: `ADD COLUMN ... default` ordering with the generated policy file
The new policies call functions that must exist when `CREATE POLICY` runs (the EP-54 precedent: the hand-written functions file must sort **before** the generated policy file). For `app.community_action_denied_ids` declare a constant `'{}'::uuid[]` kernel stub first (the `community_gate_seam` precedent), then the store body, so a project using feed without store keeps working. Name the three files so the order is columns -> functions -> gates.

### Pitfall 7: `viewer.actions.story` for a buyer

## Section answers for the planner (the eight questions)

### 1. Database design

**Where the flags live.** Five columns on `store_product_communities`, named `can_like`, `can_comment`, `can_share`, `can_post`, `can_story` (not `like`: reserved word). Each `boolean not null`, defaults `true, true, true, false, false`. A constant-default `ADD COLUMN ... NOT NULL DEFAULT` rewrites nothing and fills every existing row at once, so the "backfill" is the default itself (no `UPDATE`, no lock beyond the brief ALTER); this project runs Postgres 17.6 (`stories/db/schema.ts` docblock). Highlight: `story_highlights.open_to_buyers boolean not null default false` (UI name "Aberto a compradores"). Write access: the link columns follow the table's admin-only insert/update policies (`store_product_communities_update_admin` exists, `store/db/schema.ts:35-40`); `open_to_buyers` is written only by the manage-holder through the PATCH, and a member creator could in theory update it on their own member-community highlight under `story_highlights_member_update_gate`, which is **inert** because every buyer gate requires `c.kind = 'organization'`; the service additionally refuses it for member and Início places (new closed issue code, e.g. `open_unavailable`, appended to `STORY_HIGHLIGHT_ISSUES`, `contracts/index.ts:624`, pinned by a contract test).

**Migration order (expand-only, all three files forward-only):**
1. Generated (`pnpm db:generate --name=buyer_permissions_columns`): the five link columns and `open_to_buyers`. No policy.
2. Hand-written `--custom`, timestamp **before** file 3: kernel stub `app.community_action_denied_ids(text)` returning `'{}'::uuid[]` is declared **in the same file ahead of** the store bodies, then `create or replace` of `app.community_buyer_scope()` (new), `app.community_action_allowed` (replaces the stub, same signature and attributes so the dependent policy keeps its OID) and `app.community_action_denied_ids`. `search_path = ''`, fully qualified, `revoke all ... from public; grant execute ... to authenticated;` for each. 3. Generated plus hand `ALTER POLICY`: the likes, comments, post and item gates, and (if confirmed) the audience-gate lock term and the `feed_sample_post_ids` visibility term.

### 5. Release and ordering

Per `docs/DEPLOY.md` (Phase 11 section, lines 5545-5600): migrations on every tenant database through the ledgered `migrateAll`, then the services. Recommended here: **migrations -> API and worker -> web**, the opposite of Phase 11, because the new keys are emitted only at non-default values (Pattern 2), so the old web never meets one, while the new web against an old API only fails when an administrator saves a non-default flag (`communityLinks` unknown key, 400) and otherwise sends `communityIds` exactly as today.

| Window | What happens | Failing part |
|--------|--------------|--------------|
| Migrations applied, old API and old web | defaults reproduce today; new gates deny only communities with a false flag, none exist | none (the previous API inserts links without flags: defaults apply) |
| New API, old web | all responses identical until a flag is non-default | none until an admin uses the new web; a stale PWA bundle after that could meet `post.community.actions` (strict parse) until reload; service worker uses `updateViaCache: 'none'` |
| New web, old API | product form works at defaults; a non-default save is `400` (unknown key); `post.community.actions` absent = all true | non-default save only |
| New API against an unmigrated database | held out `updating` by the schema gate | everything of that tenant: never release the API before migrations reach every project |
| Rollback | migrations never roll back (forward-only); rolling the API back leaves flag columns unread (the previous API ignores them) and the new gates still enforce non-default flags | roll forward |
