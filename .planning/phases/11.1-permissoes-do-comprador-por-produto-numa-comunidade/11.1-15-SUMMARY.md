# Phase 11.1 Plan 15: The comment surfaces and the Reels rail Summary

**The comment composer, every Responder and the heart on each comment now disappear per the viewer's per-post facts (a read-only empty line replaces the invitation), the Reels rail closes up control by control or goes entirely, and a bare 403 on a like or a comment is one neutral word that reverts, keeps the draft and re-reads the page.**

## Performance

- **Duration:** about 95 min
- **Completed:** 2026-11-25
- **Tasks:** 3 (one tracer, two auto); the list's empty-line and refusal behaviour landed with the tracer in one `CommentsList` edit
- **Files:** 2 created, 18 modified (plus the BASELINE section)

## Accomplishments
- `CommentsList` takes optional `canComment`, `canLikeComment`, `emptyReadOnlyLabel` and `onRefused`; absent is the shipped list. A false control is not rendered, the edit and delete riders stay, a like count stays text, and the focus after a removal falls to the list when there is no composer.
- The column's one shared sheet (`FeedList`) reads `post.actions` of the post it is open on, the detail page spreads `commentActionProps` (over `postActionsView`) beside `feedCommentsProps`, and `ReelsHost` reads `ReelView.actions` for its sheet and its desktop panel, so one fact governs the card, the sheet, the detail and Reels.
- `ReelRail` has each control optional and draws nothing when none remains; `ReelOverlay` removes like, comment and share individually, makes the double tap inert without `like` and drops the empty wrapper; `ReelView` now carries `actions` from the card builder.
- `isRefusedWrite` (status 403 only) and the server actions' new code `'refused'` give every host one neutral reaction: the shipped generic toast for a like, the shipped inline error and the kept draft for a comment, a page re-read through a shared `useRefusedRefresh` hook, no log line, nothing named.
- Precondition checked: `grep -q '^approved: true'` on the sketch 026 README succeeded at the start; no approval key was written and nothing under `.planning/sketches/` was staged.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The booleans cannot be built once by the registry for the column and for Reels**
- **Found during:** Task 1 (reading `FeedList` and `ReelsHost`)
- **Issue:** the plan has `registry.tsx` build the comment booleans for every host from `postActionsView`. The column's sheet and the Reels sheet are each ONE instance serving many posts, and a function cannot cross the server/client boundary (the same reason as plan 14).
- **Fix:** the facts are read as data from the post the sheet is open on: `FeedList` from `post.actions`, `ReelsHost` from `ReelView.actions`. The registry builds them only for the detail page (one post) through `commentActionProps`, which calls `postActionsView`. `FeedCommentsProps` and `ReelsCommentsBinding` omit the two booleans so a host cannot pass one static value.
- **Files modified:** `packages/modules/feed/ui/FeedList.tsx` (a plan 14 file, touched only for this), `apps/web/lib/registry.tsx`, `apps/web/components/reels/ReelsHost.tsx`
- **Committed in:** `42c8ea5e`, `1b56822d`

**2. [Rule 1 - Bug] `ReelView` did not carry `actions`**
- **Found during:** Task 3
- **Issue:** plan 14's summary says the reel views already carry the fact because `lib/reels.ts` shares `postCardBase`; `reelView` hand-maps the card and dropped the field.
- **Fix:** `ReelView.actions` (optional) copied from `card.actions` in `reelView`.
- **Files modified:** `apps/web/lib/reels.ts`
- **Committed in:** `1b56822d`

**3. [Rule 3 - Blocking] `ReelRail` (not in the plan's file list) had a required like and comment**
- **Issue:** the rail could not drop a control. `like` and `onComment` are now optional and the rail returns null when none of the three remains.
- **Files modified:** `packages/modules/reels/ui/ReelRail.tsx`, `packages/modules/reels/tests/reel-rail.test.tsx`
- **Committed in:** `1b56822d`

**4. [Plan wording] The refusal handling does not live in `feed-write.ts` alone**
- `feed-write.ts` is the post-write module (create and edit); the like and comment actions live in `inicio/feed-actions.ts`. `isRefusedWrite` is in `feed-write.ts` (so it can be unit-tested outside a `'use server'` file), the actions map to `'refused'`, and the re-read is `useRefusedRefresh` in `community-locked.ts`, shared by the three hosts. The artifact `feed-write.ts contains refresh` holds only in prose (the docblock). The existing `feed-actions.test.ts` case "a 403 with any other word is generic" is now split: a WRITE answers `refused`, a read still answers `generic`.
- **Committed in:** `49f9b0b7`

**5. [Plan wording] `ReelOverlay.tsx contains postActionsView` is not literal**
- `feed-view.tsx` is server-side code and `ReelOverlay` is a client component, so it reads the already-derived `view.actions` (built by `postCardBase` from `postActionsView`), the same single builder.

**6. [Plan wording] The tests sit where the harness is**
- `ReelsOverlay.test.tsx` uses a stand-in host and cannot see the rail; the rail and the refusal cases are in `ReelsHost.test.tsx` (real rail, real like engine, real feed sheet) and `reel-rail.test.tsx`. Task 2's verify clause `vitest run "app/(app)/post"` finds no test files and exits 1 (that directory has none); the detail page is proved by `components/feed/PostDetail.comments.test.tsx` through the real catalog.

**7. [Process] Test order**
- The module list cases were seen red first (11 of 20). The host cases (detail page, Reels rail, refusal reactions) were written after the implementation in the same sitting and were not run red first; each sits beside a positive control that flips the one term back.

**8. [Process] Tasks 1 and 2 share the `CommentsList` edit**
