# Phase 11.1: Code Review Report

**Reviewed:** 2026-11-25
**Depth:** standard
**Files Reviewed:** 75
**Status:** issues_found

## Summary

The submitted phase adds per-link buyer flags, a union scope function, five RLS gate changes, a highlight "open to buyers" switch, the service guards and the screen facts. I tried to break it in the order the brief gave.

**SQL and RLS (first priority) held up.** I traced every function and policy and found no cross-tenant leak, no search_path gap and no deny that turns into an allow:

- `app.community_buyer_scope`, `community_action_allowed` and `community_action_denied_ids` are SECURITY DEFINER with `search_path = ''`. Every statement pins `tenant_id = app.tenant_id()` and `user_id = app.user_id()`. EXECUTE is revoked from PUBLIC. The scope fails closed on a null tenant, user or role.
- The `bool_or` union reads `e.status = 'active'` at statement time, so a refund ends the grant at the next statement. It ignores `expires_at` exactly like `community_locked_ids`, which the header says on purpose.
- Every NULL path lands on deny: `coalesce(..., false)` in the allowed wrapper, `case ... else` member branch in the denied wrapper. A null role denies, like the locked function does.
- The `ITEM_BUYER_OPEN` parenthesisation in the item insert and delete gates is correct (I counted it). The buyer branch requires `kind = 'organization'`, `status = 'active'`, `deleted_at is null`, `open_to_buyers`, the story flag and, for items, the author's own story.
- The audience-gate locked term, the `p.visibility = 'tenant'` sample fix (D-893) and the left-join like gate hold. A comment whose post is hidden is itself hidden by the comment gates, so the `p.community_id is null` pass on a null join is unreachable for a real post.
- The `sql.raw(action)` literal is inlined from a closed two-name union and quoted. It is safe today, see IN-02.

**API layer.** I found no authorization hole on a new path:

- Refusals are the bare 403.
- The open-counts route sits before `/highlights/{highlightId}`, is guarded by the literal `stories.story.manage`, and filters to active organization communities of the caller's tenant.
- `openToBuyers` rides only the curator reads (`toHighlight(row, curator)`).
- The contracts are `.strict()`, with the link cap, the duplicate refinement and the `communityIds`/`communityLinks` exclusion.
- The 30/hour limiter is consumed only on the buyer branch.

**What I did find** is one control that stays reachable when its flag is off (WR-01), one log and observability regression (WR-02), and six minor items.

## Warnings

### WR-01: "Copiar link" in the post overflow menu stays reachable when the viewer's `share` fact is false

**File:** `packages/modules/feed/ui/PostMenu.tsx:201`, `packages/modules/feed/ui/FeedList.tsx:511,657`, `apps/web/components/feed/PostDetail.tsx:213,223`
**Issue:** UI-D-888 says a control the viewer's actions do not include is "not rendered ... Share anywhere ← `share`", and D-889 makes share a screen-only control, so the screen is the only guard. `PostActions` correctly drops the send glyph (`show.share === false`), and `ReelOverlay` drops the Reels share. But the post's "..." sheet builds its target from `shareUrl: post.shareUrl` with no look at `post.actions?.share`. `PostMenu` renders the "Copiar link" row whenever `shareUrl && onSharePost`, and the "..." button itself is shown whenever `post.shareUrl` is truthy (`FeedList.tsx:657`, `PostDetail.tsx:213`). The PostMenu docblock even states "Copiar link and the action row's share control are ONE handler". So a buyer whose product withholds share still gets a working share entry in the overflow menu, on every list and on the post detail. That is the forbidden control, reachable and keyboard-focusable. It also contradicts the 11.1-14 and 11.1-15 tests that assert the send glyph is absent: they pin the row, not the menu.
**Fix:** Derive the menu's `shareUrl` from the same fact the row uses. In `FeedList.openMenu` and in `PostDetail`'s `menu` target:
```tsx
const canShare = post.actions?.share !== false;
setMenuTarget({
  postId: post.id,
  shareUrl: canShare ? post.shareUrl : null,
  ...
});
```
Apply the same `canShare` to the "..." visibility test (`post.shareUrl && canShare`). Add a case to `post-actions-show.test.tsx` or `PostDetail.comments.test.tsx` that opens the menu on a `share:false` post and asserts there is no "Copiar link".

### WR-02: `createPostAction` maps every 403 to `refused` for every caller, including the administrator's composer, and drops the error log for them

**File:** `apps/web/app/(app)/criar/actions.ts:56-58`, `apps/web/lib/feed-write.ts:152-154`
**Issue:** The `mapRefused: true` option is documented as being for "the buyer's pinned composer", but `createPostAction` is the one action every composer calls (administrator, member in Explorar, member pinned to a community). A staff 403 (for example `feed.post.create` missing after a role change, or a real policy bug) now returns `{ code: 'refused' }` and skips `console.error('feed.post.write_failed', ...)`. The admin composer shows the generic sentence as before, but the server log loses the only trace of an unexpected staff refusal. The `revalidatePath` branch also runs for any `refused` with a `communityId`, including an admin post into a community. Only the member-pinned UI reads the word.
**Fix:** Make the mapping conditional on the caller being a member. The action already knows the lane through the bootstrap, or the client can pass it. Smallest change:
```ts
const { result, refusal } = await attemptPostWrite(() => createPost(body.data), {
  mapRefused: body.data.communityId !== undefined && isMemberLane,
});
```
or keep the log line for the non-member case inside `attemptPostWrite` (`if (!options.mapRefused || !isRefusedWrite(error)) console.error(...)`).

## Info

### IN-01: A buyer who loses `like` cannot withdraw a like they already placed

**File:** `packages/modules/feed/server/service.ts:2252-2258` (`unlikePost` calls `assertPostInteractive(..., 'like')`), `:2343-2348` (`unlikeComment` calls `assertCommentLikeAllowed`)
**Issue:** The denied test is applied to the delete as well as the insert. When the administrator unticks "Curtir" (or the buyer is refunded, which is already locked behaviour), the like stays and the heart is hidden, so the member has no way to remove their own like and the counter stays inflated. The code comments say this is deliberate ("the heart stays"), and D-887 keeps published content. A like is the member's own reversible act rather than published content, so the trade-off is worth confirming with Igor. This does not leak anything.
**Fix:** If undo should survive, drop the `'like'` action argument from `unlikePost` and skip `assertCommentLikeAllowed` in `unlikeComment`. Keep the locked test. Otherwise record it in the SUMMARY as an accepted behaviour.

### IN-02: `deniedCommunityIds` inlines its argument with `sql.raw` and only a compile-time guard

**File:** `packages/core/db/community-gate.ts:44-46`
**Issue:** `action: 'like' | 'comment'` is a closed union, and every current caller passes a literal. The runtime value is not validated, so a future caller that forwards a request-derived string through a widened type would put it into DDL or a query unquoted-by-parameter. The risk is latent, not live.
**Fix:** Resolve through a lookup so a bad value cannot reach `sql.raw`:
```ts
const DENIED_ACTION = { like: 'like', comment: 'comment' } as const;
export const deniedCommunityIds = (action: 'like' | 'comment'): SQL =>
  sql`coalesce((select app.community_action_denied_ids('${sql.raw(DENIED_ACTION[action])}')), '{}'::uuid[])`;
```
(`undefined` then fails loudly in the SQL.) The same applies to `countOpenHighlights` and `insertLinkFlags`, which build `uuid[]` and `boolean[]` literals from contract-validated input. A service reachable "from the seed or another handler" should re-assert the uuid shape.

### IN-03: `updateHighlight` re-codes `archived` as `open_unavailable` whenever the body names the switch, and refuses closing it

**File:** `packages/modules/stories/server/service.ts:2788-2804` (the `.catch`), `:2809-2818`
**Issue:** A PATCH of `{ title, openToBuyers: true }` on an archived community answers `open_unavailable` instead of `archived`, so the caller loses the correct reason for the title edit. `openToBuyers: false` on an archived, member or Início highlight is also `open_unavailable`, so an administrator cannot close a highlight of an archived community. The buyer gates stay inert while the community is archived (they require `status = 'active'`), but un-archiving reopens the highlight to buyers without the administrator touching the switch.
**Fix:** Re-code only when the body contains `openToBuyers: true` and nothing else. Allow `openToBuyers: false` through the archived refusal, or document that un-archiving restores buyer access to open highlights.

### IN-04: `memberCanHighlight` adds a sequential catalogue request to every Explorar render and logs an error on a 403

**File:** `apps/web/lib/stories.ts:658-662`, `apps/web/app/(app)/inicio/ExplorarBody.tsx:101-111`
**Issue:** For any member without an owned community, `memberCanHighlight` awaits `ownsActiveCommunity` and then `hasHighlightDestination`. The second call is a full catalogue read on the Explorar critical path. If a member holds `social.participate` without `stories.story.publish`, the catalogue answers 403 and `hasHighlightDestination` logs `stories.highlight_destination_failed` on every page view. Whether that combination can occur depends on the tenant's role composition. It is a UX hint, so a miss only hides the door.
**Fix:** Guard the second read with the permission the catalogue requires: `bootstrap.permissions.includes('stories.story.publish') && (await hasHighlightDestination())`. Run both reads concurrently.

### IN-05: Reels removes the comment thread entirely for a viewer whose `comment` fact is false, while the card keeps it readable

**File:** `packages/modules/reels/ui/ReelRail.tsx:157-168,206-217`, `apps/web/components/reels/ReelOverlay.tsx:219-223`
**Issue:** UI-D-890 says reading is never reduced, and the card keeps the comment count as the button that opens the read-only list. In Reels, `canComment = false` passes `onComment` as undefined and drops the comment glyph and its count, so a buyer without `comment` cannot read the thread from Reels even though it is readable from every other surface. This is not a security issue. It is an inconsistency with the card rule.
**Fix:** Either keep the comment control as a read-only opener in Reels (the sheet already gets `canComment={false}`), or record the divergence in the UI-SPEC. The Reels re-read gap listed in the SUMMARYs is a different item.

### IN-06: Orphaned docblock and a latent boundary assumption

**File:** `packages/modules/feed/ui/PostActions.tsx:14-31`, `packages/modules/store/server/service.ts:253-269`
**Issue:** The 11.1-14 edit inserted the `PostActionsShow` docblock and type between the original docblock and `PostActionsProps`, so the original comment ("the action row is always present", the 04-07 and 04-08 handlers) now sits above the new comment with no declaration of its own. Separately, `resolveCommunities` still accepts any active community of the tenant, including a member-created one, although D-880 and D-713 rest on member communities never being linked to products. It is only the form's missing field that enforces this. The buyer scope filters `kind = 'organization'`, so the flags stay inert there, but `community_locked_ids` does not filter kind and would lock such a community for everyone.
**Fix:** Move the original docblock back above `PostActionsProps`. In `resolveCommunities` add `and c.kind = 'organization'` so the invariant the phase relies on is enforced in the API as well, with a pgTAP or integration case.
