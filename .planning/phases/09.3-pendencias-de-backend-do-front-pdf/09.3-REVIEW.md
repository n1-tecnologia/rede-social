# Phase 09.3: Code Review Report

**Reviewed:** 2026-10-27
**Depth:** standard
**Files Reviewed:** 56
**Status:** issues_found

## Summary

The phase is mostly sound. No blocker was found. What was checked and held up:

- Tenant isolation of the two new definers. `app.community_deleted_ids()` and the replaced `app.feed_locked_post_community(uuid)` both pin `search_path = ''`, qualify every name, pin `tenant_id = app.tenant_id()`, are revoked from PUBLIC and granted to `authenticated` only. The deleted-ids function returns ids only. With no tenant claim the `tenant_id = null` predicate yields `'{}'`.
- The RESTRICTIVE policy `feed_posts_deleted_community_gate` can only narrow. It is created by the later-sorted migration (213816 after 213756), so the function exists when the policy resolves it. Comments and likes inherit it through their inner `exists (select 1 from feed_posts)`.
- `feedPage` and `getPost` filter `c.deleted_at is null` in the WHERE, not the ON, so a post is not turned into a community-less one.
- `resolveCommunityTarget` already refuses posting into a deleted community.
- `deleteEvent` is one guarded UPDATE with a bare 404 on unknown, foreign and already-deleted ids. Every event read, RSVP, check-in, enter, photo, notification and reminder path already filters `deleted_at`.
- `deleteCommunity` does the tenant-scoped locking read first, so the 409s are not an existence oracle. `FOR UPDATE` really serialises against the Loja link insert's `FOR KEY SHARE`. Archived products are excluded and the module flag is read as `app.community_locked_ids()` reads it.
- The `iconOwnArt` marker is written in the same statement as `iconUrl`. It is cleared by `removeIconOverride` and by an unmarked `icon` upload. It is read only for the `override` source. It is absent from the public host answer, because `hostBrandingSchema` is strict and `toHostBranding` builds it from known keys. `parseUploadId` handles the `icon_art` / `icon` alternation correctly.
- The migrations are expand-only (CHECK widened, `create or replace` with the same signature). The dashboard migration is byte-identical to `20261018225848` except the one removed predicate, and no later migration redefines `dashboard_member_activity`.
- No dangling reference to `PendingDeleteButton` remains in code, messages or e2e. Only planning documents mention it.

The defects below are logic and consistency gaps, not isolation breaks.

## Warnings

### WR-01: `updateHighlight` counts UTF-16 units, create and the route validator count code points

**File:** `packages/modules/stories/server/service.ts:1813-1818`
**Issue:** `storyHighlightTitleSchema` uses Zod 4.6.2 `.max(50)`. That version counts code points: `$ZodCheckMaxLength` calls `codePointLength` on overflow. The DB `char_length` does too. The service re-check in `updateHighlight` uses `requestedTitle.length`, which counts UTF-16 units. Failure scenario: `PATCH /v1/stories/highlights/{id}` with `{ "title": "😀" x 30 }` (30 code points, 60 units) passes the route schema and the DB CHECK, then the service throws `400 VALIDATION_FAILED { highlight: 'title_invalid' }`. The same title is accepted on create (`POST /highlights`, and `newHighlight` on publish), which only use the schema. Only a direct API client can hit this, because the web `maxLength` counts units and is stricter. The contract comment in `contracts/index.ts:487` and test 7 in `story-highlight-title.test.ts` assert exactly the code-point rule, and the service contradicts it. The test only exercises the schema, so nothing catches the service.
**Fix:**
```ts
const codePoints = (s: string) => Array.from(s).length;
if (
  requestedTitle !== undefined &&
  (codePoints(requestedTitle) === 0 || codePoints(requestedTitle) > STORY_HIGHLIGHT_MAX_TITLE)
) {
  throw new ApiError(400, 'VALIDATION_FAILED', { highlight: 'title_invalid' });
}
```
Add an integration case (50 emoji PATCH returns 200).

### WR-02: Owner member-detail attendance list still drops deleted events, contradicting D-550 and the tile it sits beside

**File:** `packages/modules/dashboard/server/member-detail.ts:262-266`
**Issue:** Plan 04 removed `and e.deleted_at is null` from `app.dashboard_member_activity`, so the member's `attendance { attended, events }` tile now counts a deleted event's RSVP and check-in (D-550: "member insights ... keep counting"). The query that builds the same member's per-event attendance rows in the owner's member detail still has `join public.events e ... and e.deleted_at is null`. Failure scenario: a member attended 4 events in 30 days and an admin deletes one. The tile reads "3 of 4 attended" while the list under it shows 3 rows. The count and the listing disagree, and the member's record shrinks in the owner's view, which is the opposite of D-550. `member-lists.ts:524` handles the same case correctly (it left joins `events` and falls back to `removedEvent`), so the pattern already exists.
**Fix:** drop `and e.deleted_at is null` in `member-detail.ts` and render a removed-event fallback title, as `owner-list-view.ts:472` does. If keeping the filter is intended, say so in D-550 and in the migration header, and make the tile consistent instead.

### WR-03: Reactivating an archived product re-opens the D-554 hole for a deleted community

**File:** `packages/modules/store/server/service.ts:1303-1333` (`setProductStatus`), related `packages/modules/communities/server/service.ts:963-974`
**Issue:** D-554 lets a community be deleted while only ARCHIVED products link it, and the delete never touches `store_product_communities`. `setProductStatus` flips `store_products.status` back to `active` with no check on the linked communities. `updateProduct` and `lock-preview` do reject deleted communities, but only when the body names them. Failure scenario: community X is archived and linked only to archived product P, so the admin deletes X. Later the admin reactivates P. P is `active`, buyable (`app.store_purchase` has no community check), and every buyer pays for access to a community that no longer exists. That is the "nobody pays for access that stops existing" outcome D-554 sets out to prevent. `app.community_locked_ids()` also keeps listing the deleted id.
**Fix:** in `setProductStatus`, when `status = 'active'`, refuse with 409 if any linked community has `deleted_at is not null` (a new closed code, details naming the community count), or have `getProduct`/`isBuyable` treat a product whose only links are deleted communities as unavailable. Add one integration test for archive, delete community, reactivate product.

### WR-04: The new restrictive gate changes the merged-feed plan and the pin test was loosened to hide it

**File:** `supabase/tests/180-store.sql:743-756` (policy at `packages/modules/feed/db/schema.ts` `feed_posts_deleted_community_gate`)
**Issue:** The test comment records that adding the `feed_posts_deleted_community_gate` clause shrinks the merged feed's row estimate (78 to 30), so the planner abandons the ordered walk of `feed_posts_tenant_created_all_idx` under `limit 11` for a Bitmap Heap Scan on `feed_posts_tenant_author_idx` plus a `Sort`. The fix was to add `set local enable_bitmapscan = off` to the P41 pin. The pin used to say "the index is walked in order". It now says it only under a planner forced off the new plan. The shipped query is unchanged and runs without those settings. This is a hot path (Início and Reels). On a populated tenant the first page can become filter, sort and take 11 instead of walk 11. The comment calls it a cost preference, not a defect, and the owner chose the pin shape (P41), but nothing proves the production plan stays good. Performance is out of v1 scope, so this is raised as a test-integrity risk, not a perf finding.
**Fix:** keep the pin honest by adding an assertion that does not force settings, for example `EXPLAIN` on a seeded 5k-post tenant with default settings still matching `created_all_idx`. Alternatively express the gate so it does not depress the estimate, for example a `not exists` against `communities` instead of the `<> all (InitPlan)` array form. Document the owner decision in the migration header.

## Info

### IN-01: OpenAPI text still says the upload kind is `logo/icon`

**File:** `apps/api/src/routes/admin/branding.ts:119`, `apps/api/src/routes/platform/branding.ts:72`
**Issue:** The 400 description of the upload-start route reads "kind not logo/icon". The enum is now `logo | icon | icon_art` (`BRANDING_UPLOAD_KINDS`). The `complete` descriptions were updated, these two were missed, so the published OpenAPI misleads a client integrator.
**Fix:** change both strings to "kind not logo/icon/icon_art".

### IN-02: A 404 caused by a disabled module is shown as "already deleted"

**File:** `apps/web/app/(app)/eventos/[eventId]/DeleteEventControl.tsx:36-43`, `apps/web/app/(app)/comunidades/[communityId]/DeleteCommunityControl.tsx:55-58`
**Issue:** Both controls map any 404 to the info toast "Este evento/comunidade já foi excluído" and replace to the list. `requireModule('events'|'communities')` also answers a bare 404 when the tenant's module is off, so an admin of a tenant that just lost the module is told the item was deleted when nothing was. Rare and harmless, since the landing page then shows the module-off state.
**Fix:** none required. Optionally word the message neutrally ("Não encontramos mais este evento").

### IN-03: `StoryViewer` header wrap applies to every story author, not only highlights

**File:** `packages/modules/stories/ui/StoryViewer.tsx:1011-1014`
**Issue:** D-560 asks that the whole highlight name show in the opened viewer. The change swaps `truncate` for `break-words` on the shared author-name span, so a long member name in an ordinary story header now wraps and grows the header over the media too. A long unbroken token will wrap at any character.
**Fix:** acceptable if intended. Otherwise apply `break-words` only when the group is a highlight.

### IN-04: Media of a deleted community's posts is not covered by `app.media_asset_hidden`

**File:** `supabase/migrations/20261026213756_community_soft_delete_gate.sql` (scope), `supabase/migrations/20261008174609_feed_gate_lookups.sql:48-70`
**Issue:** The phase hides the posts, comments and likes of a deleted community, but `app.media_asset_hidden` still decides media visibility from the locked/sample sets only. An image or video of a hidden post stays fetchable by anyone who holds its asset id or an unexpired signed URL (an old bell notification preview, a shared link, a cached page). Reaching it needs the unguessable asset id, so exposure is limited, and D-555 only promises the posts leave the feed and the post page. Not verified end to end against the storage policy in this review.
**Fix:** if "leave" should mean unreachable, add the deleted-community predicate to `app.media_asset_hidden`. Otherwise record the residual in the phase security notes.
