## Phase Boundary

Five corrections of the client's FRONT.pdf that the front could not finish alone, listed by whoever merged FRONT-AJUSTES on 2026-10-21 (`Pendências de backend - FRONT.pdf`, items 3 and 11 to 14 of `docs/pendencias-backend.md`):

4. **The highlight name limit** rises from 15 characters.

<decisions>
## Implementation Decisions

### Delete an event
- **D-548:** Any event of the tenant can be deleted by whoever may edit events, whether it is active, cancelled or already past, with or without RSVPs or check-ins. The route is `DELETE /v1/events/{id}` and it soft-deletes by filling `events.deleted_at` (the column and the `deleted_at is null` read filters already exist). No extra restriction on which events qualify.
- **D-549:** The delete is silent. No notification or push goes to anyone, exactly as cancelling is silent (D-201, D-214 from Phase 6), and reminder jobs already scheduled become no-ops at fire time (`reminders.ts` already reads the deleted flag, the planner proves it with a test).
- **D-550:** RSVPs and check-ins of a deleted event stay in the database untouched (D-214) and keep counting for the member in the dashboards' member-side numbers (engagement bands, member insights, "Sua atividade"). Only event-centred lists drop the event, and they already filter `deleted_at is null`. No member-side query changes.
- **D-551:** A deleted event's link, whether from a saved link, a push or an old bell notification, answers the existing not-found screen, the same 404 as an invalid or another tenant's link. Old bell notifications stay in the list. No new screen and no "deleted" status in the API.
- **D-552:** The confirmation is the existing `ConfirmDialog` (the pattern of "Reativar comunidade", D-90 from Phase 05.1), saying what disappears and that the confirmations and check-ins are kept. After confirming, the admin lands on the events list. This reverses the Phase 6 rejection ("Deleting an event ... Cancel is the only way out in V1") by the client's request in the FRONT.pdf.

### Delete an archived community
- **D-553:** Only an archived community can be deleted, by whoever manages communities, through `DELETE /v1/communities/{id}` that soft-deletes by filling `communities.deleted_at`. A community that is not archived is refused with its own error code, and another tenant's community answers 404.
- **D-554:** The deletion is refused while an active Loja product still unlocks the community. The answer lists the product names and the screen tells the admin to take the community off those products first. Archived products do not count. The deletion never changes anything in the Loja, so nobody pays for access that stops existing.
- **D-555:** The community's publications leave Início, Reels and the post page (the link answers 404) together with their likes and comments. They stay in the database and there is no restore screen, support recovers by clearing `deleted_at`. The feed's `left join public.communities` gets the deleted filter, and the planner checks the post page's locked-community SQL function (`app.feed_locked_post_community`) for the same case.
- **D-556:** Highlights and pinned stories of the community (`story_highlights`, `story_community_pins`) are hidden by the read filters and not erased, and nothing cascades. `community_members` is born-unused today, so there are no member rows to treat. No row is deleted anywhere.
- **D-557:** The confirmation is the same simple `ConfirmDialog` as the event's, and after confirming the admin lands on the communities list. The slug stays with the deleted row, and a new community with the same name already gets a numeric suffix on create.

### The two limits
- **D-558:** `EVENT_SCHEDULE_MAX_ITEMS` goes from 30 to 200 in `packages/modules/events/contracts/index.ts`, and the CHECK `events_schedule_chk` is replaced by a migration at 200. The form follows the constant by itself. Lowering the limit later would make saved schedules over the new cap fail the CHECK, so it would need a data decision first.
- **D-559:** `STORY_HIGHLIGHT_MAX_TITLE` goes from 15 to 50 in `packages/modules/stories/contracts/index.ts`, in the service check (`packages/modules/stories/server/service.ts`) and in the CHECK `story_highlights_title_chk` by migration. The forms follow the constant by itself. Lowering it later would make saved highlight names over the cap fail the CHECK.
- **D-560:** A highlight name longer than the circle is cut on one line with an ellipsis, so every circle keeps the same height, and the whole name shows when the highlight opens.
- **D-561:** Release order is migrations on every tenant database first through `migrateAll` (09.2), then the API and the worker, then the web, because the forms accept more the moment the constants change. The two limit migrations only relax a CHECK, so an old API on the new database keeps working.

### The Android icon
- **D-562:** The icon editor tells the API that the icon it sends is its own art, and the tenant's branding stores that next to the icon URLs as a new optional field. The change to the contract is additive and leaves the current upload body valid. Any other upload path leaves the field unset.
- **D-563:** `deriveIconSet` fills the whole `maskable512` square when the source is a marked own icon that is also opaque. A transparent own icon, a logo-derived icon and an unmarked icon keep the 80% margin over the primary colour (Phase 2, D-28).
- **D-564:** No backfill. Tenants that already have an icon keep the margin until their admin saves the editor again, nothing is re-derived over existing tenants at the deploy, and no icon is cropped by surprise. The client is told to save the icon again, and that an installed Android app only shows the change when Chrome refreshes the installed app. Both go in the DEPLOY.md notes.
- **D-565:** Scope stays on the PDF. Items 4 (saved editor choices) and 6 (remove the icon of a tenant with no logo) stay out, although both touch the same branding code. The marker field is where item 4's saved choices can live later.

### Carried forward, not re-decided
- **D-214 [informational] (Phase 6):** RSVPs and check-ins are never erased, and every field stays editable after answers exist.
- **D-201 [informational] (Phase 6):** edit and cancel send no notification, only a reactivation does.
- **D-90 [informational] (Phase 05.1):** reactivating an archived community is one tap with a confirmation, the model for these two confirmations.
- **D-28 [informational] (Phase 2):** the PWA icons are derived from the logo by default, and the maskable one keeps a safe-zone margin over the primary colour.
- **D-544 [informational] (Phase 09.2):** migrations reach every tenant project through the ledgered `migrateAll`, databases before API and worker.

### Claude's Discretion

- The exact wording of the two confirmation dialogs and the toast after a delete.
- The name of the new branding field and the shape of the upload field that carries it, as long as the change is additive.
- Whether the delete writes an audit line through the existing logger, and how the tests are split between pgTAP, integration and web.

<code_context>
## Existing Code Insights

### Reusable Assets
- `ConfirmDialog` from `@rede-social/ui`: already carries "Reativar comunidade" and the media library's delete, so both confirmations are not a new design surface.
- `setEventStatus` (events service) and the events `statusRoute`: the shape of an admin write on an event with its permission and tenant lane.
- `events.deleted_at` and `communities.deleted_at` already exist with filters in the events service, the reminders job, the notifications, the photos, the communities service, the Loja and the owner dashboard, so most reads already hide a soft-deleted row.
- `deriveTenantIcons` re-derives under an optimistic `iconVersion` write, so a re-save from the editor already produces a fresh set.

### Established Patterns
- Soft delete by `deleted_at`, never `DELETE`; foreign keys without `on delete` (such as `feed_posts.community_id`) therefore never fire.
- Every new route and read carries a cross-tenant negative test (pgTAP plus integration); the limit CHECKs are covered by pgTAP files 120 and 145, which move with the new values.
- Migrations are written for the 09.2 runner and reach every tenant project in order, databases before API and worker.
- Contract changes are additive because the schemas are `.strict()`.

### Integration Points
- The feed read and the post page are where a deleted community's publications must disappear (Início, Reels, post page); Explorar already excludes community posts.
- The Loja read of `store_product_communities` feeds the refusal in D-554.
- The icon upload confirm in the platform branding code is where the marker is accepted and stored, and `deriveTenantIcons` is where it is read.
- The disabled `PendingDeleteButton` is the seam on the web; the four call sites swap it for the live control.

</code_context>

Wave 2, delete event and delete community (routes, services, read filters, tests).
