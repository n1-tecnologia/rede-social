<planning_decisions>
1. **The marker carrier is a third upload kind, `icon_art` (RESEARCH A4, decided by the orchestrator).** The upload id is stateless (`<kind>-<uuid>.<ext>`), the object key does not carry the kind, and `docs/pendencias-backend.md` item 3 already proposes "um tipo de upload próprio". A body flag on `complete` would change an optional-body route in two lanes and three web call sites. `icon` keeps meaning "unmarked".
2. **The wizard and both Marca screens all use `icon_art` (RESEARCH A5).** The wizard's draft icon is always the editor's composition (`WizardBrandPicker` sets it only through `AppIconEditor`).
3. **No database migration.** The marker lives in the `tenants.branding` jsonb; the central mirror already copies the whole object. No migration means this plan needs no `[BLOCKING schema]` task.
4. **`fit: 'cover'` for the opaque branch (RESEARCH A6).** The editor composes an opaque SQUARE, so `cover` and `contain` agree on its output; `cover` also fills the square for an opaque non-square art (centre crop), which is what the editor's own art mode does.
5. **Fixtures.** The api package has no `sharp`. An opaque square of one colour is `deriveIconSet(svg, { primaryHex: <that colour> }).maskable512` (the background and the logo are the same colour, alpha 255 everywhere); a transparent square is `deriveIconSet(wordmark).i512` (transparent margins). Assert the fixture first (`readPixel` corner alpha) so a fixture mistake can never pass a branch for the wrong reason.
6. **Precondition for the integration runs.** The local Supabase stack is up and seeded (`pnpm db:reset && pnpm db:seed` ran after the last migration); this plan adds no migration, so it does not reset by itself.
</planning_decisions>
