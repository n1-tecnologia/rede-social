## User Constraints (from CONTEXT.md)

### Locked Decisions

**Delete an event**
- **D-548:** Any event of the tenant can be deleted by whoever may edit events, whether it is active, cancelled or already past, with or without RSVPs or check-ins. The route is `DELETE /v1/events/{id}` and it soft-deletes by filling `events.deleted_at` (the column and the `deleted_at is null` read filters already exist). No extra restriction on which events qualify.
- **D-549:** The delete is silent. No notification or push goes to anyone, exactly as cancelling is silent (D-201, D-214 from Phase 6), and reminder jobs already scheduled become no-ops at fire time (`reminders.ts` already reads the deleted flag, the planner proves it with a test).
- **D-550:** RSVPs and check-ins of a deleted event stay in the database untouched (D-214) and keep counting for the member in the dashboards' member-side numbers (engagement bands, member insights, "Sua atividade"). Only event-centred lists drop the event, and they already filter `deleted_at is null`. No member-side query changes.
- **D-551:** A deleted event's link, whether from a saved link, a push or an old bell notification, answers the existing not-found screen, the same 404 as an invalid or another tenant's link. Old bell notifications stay in the list. No new screen and no "deleted" status in the API.
- **D-552:** The confirmation is the existing `ConfirmDialog` (the pattern of "Reativar comunidade", D-90 from Phase 05.1), saying what disappears and that the confirmations and check-ins are kept. After confirming, the admin lands on the events list. This reverses the Phase 6 rejection ("Deleting an event ... Cancel is the only way out in V1") by the client's request in the FRONT.pdf.

**Delete an archived community**
- **D-553:** Only an archived community can be deleted, by whoever manages communities, through `DELETE /v1/communities/{id}` that soft-deletes by filling `communities.deleted_at`. A community that is not archived is refused with its own error code, and another tenant's community answers 404.
- **D-554:** The deletion is refused while an active Loja product still unlocks the community. The answer lists the product names and the screen tells the admin to take the community off those products first. Archived products do not count. The deletion never changes anything in the Loja, so nobody pays for access that stops existing.
- **D-555:** The community's publications leave Início, Reels and the post page (the link answers 404) together with their likes and comments. They stay in the database and there is no restore screen, support recovers by clearing `deleted_at`. The feed's `left join public.communities` gets the deleted filter, and the planner checks the post page's locked-community SQL function (`app.feed_locked_post_community`) for the same case.
- **D-556:** Highlights and pinned stories of the community (`story_highlights`, `story_community_pins`) are hidden by the read filters and not erased, and nothing cascades. `community_members` is born-unused today, so there are no member rows to treat. No row is deleted anywhere.
- **D-557:** The confirmation is the same simple `ConfirmDialog` as the event's, and after confirming the admin lands on the communities list. The slug stays with the deleted row, and a new community with the same name already gets a numeric suffix on create.

**The two limits**
- **D-558:** `EVENT_SCHEDULE_MAX_ITEMS` goes from 30 to 200 in `packages/modules/events/contracts/index.ts`, and the CHECK `events_schedule_chk` is replaced by a migration at 200. The form follows the constant by itself. Lowering the limit later would make saved schedules over the new cap fail the CHECK, so it would need a data decision first.
- **D-559:** `STORY_HIGHLIGHT_MAX_TITLE` goes from 15 to 50 in `packages/modules/stories/contracts/index.ts`, in the service check (`packages/modules/stories/server/service.ts`) and in the CHECK `story_highlights_title_chk` by migration. The forms follow the constant by itself. Lowering it later would make saved highlight names over the cap fail the CHECK.
- **D-560:** A highlight name longer than the circle is cut on one line with an ellipsis, so every circle keeps the same height, and the whole name shows when the highlight opens.
- **D-561:** Release order is migrations on every tenant database first through `migrateAll` (09.2), then the API and the worker, then the web, because the forms accept more the moment the constants change. The two limit migrations only relax a CHECK, so an old API on the new database keeps working.

**The Android icon**
- **D-562:** The icon editor tells the API that the icon it sends is its own art, and the tenant's branding stores that next to the icon URLs as a new optional field. The change to the contract is additive and leaves the current upload body valid. Any other upload path leaves the field unset.
- **D-563:** `deriveIconSet` fills the whole `maskable512` square when the source is a marked own icon that is also opaque. A transparent own icon, a logo-derived icon and an unmarked icon keep the 80% margin over the primary colour (Phase 2, D-28).
- **D-564:** No backfill. Tenants that already have an icon keep the margin until their admin saves the editor again, nothing is re-derived over existing tenants at the deploy, and no icon is cropped by surprise. The client is told to save the icon again, and that an installed Android app only shows the change when Chrome refreshes the installed app. Both go in the DEPLOY.md notes.
- **D-565:** Scope stays on the PDF. Items 4 (saved editor choices) and 6 (remove the icon of a tenant with no logo) stay out, although both touch the same branding code. The marker field is where item 4's saved choices can live later.

## Summary

All five FRONT.pdf items are narrow, and almost everything needed already exists. Event reads, the reminders job, notifications and photos already filter `events.deleted_at is null`, so deleting an event is one guarded UPDATE on the tenant lane. A deleted community is the hard one: its posts must leave Início, Reels and the post page, and the design pitfalls are in how the feed joins `communities`, in a SECURITY DEFINER function that would turn a deleted community into a 403 "locked" answer, and in the comment-id routes that rely on RLS only. The two limit changes are constant edits plus two drizzle-generated DROP/ADD CHECK migrations. The icon work needs a marker carried from the editor to the worker, a new optional field in the branding schema, and an `isOpaque` branch in `deriveIconSet`.

Three findings contradict or extend the locked decisions and need the planner to confirm before work starts (Open Questions 1 to 3): (1) D-550 says member-side numbers keep counting, but the member's "Sua atividade" attendance tile is built by a function that excludes deleted events today; (2) D-556 names `story_community_pins`, a table dropped in Phase 05.2; (3) D-555's "left join gets the deleted filter" is correct only as a WHERE predicate, and the comment-id routes need an RLS backstop or four more patched queries.

**Primary recommendation:** Implement the two deletes as guarded single-statement writes on `withTenantTx` (404 on a miss, `409 CONFLICT` with `details.community` for the two community refusals), hide a deleted community's posts with a service predicate plus a RESTRICTIVE `feed_posts` policy and a one-line fix to `app.feed_locked_post_community`, relax the two CHECKs with drizzle-generated migrations created at execution time (after 09.2 closes), and carry the icon marker as a new upload kind stored in `tenants.branding.iconOwnArt`.

### Delete community (PEND-04, PEND-06)

**"Archived" means** `communities.status = 'archived'` (`communities/db/schema.ts:118`: `check('communities_status_chk', sql\`${t.status} in ('active','archived')\`)`). There is no `archived_at`; the archived list orders by `updated_at`.

**Closed refusal vocabulary pattern.** `COMMUNITY_ISSUES = ['name_required', 'archived', 'cover_invalid', 'order_stale']` (`communities/contracts/index.ts:63-68`). Its docblock fixes the rule: input problems are `400 VALIDATION_FAILED`, state refusals are `409 CONFLICT`, a miss is a bare 404 with no details. Add `'not_archived'` and `'unlock_active'` to `COMMUNITY_ISSUES`, throw `new ApiError(409, 'CONFLICT', { community: 'not_archived' })`, and update `communities/tests/contracts.test.ts` (it pins the vocabulary). `unlock_active` carries `products` (names) and `count`.

**The service (one transaction, serialised):**

```ts
// Source: pattern of updateCommunity (communities/server/service.ts:683) and getCommunity (:391)
export async function deleteCommunity(ctx: RequestContext, communityId: string): Promise<void> {
  const storeOn = await moduleFlags.isEnabled(ctx, 'store'); // kernel flags-cache, see README pitfall
  await withTenantTx(ctx, async (tx) => {
    // FOR UPDATE, not a plain UPDATE: a concurrent product-link insert takes FOR KEY SHARE on this row through
    // store_product_communities's FK, and only FOR UPDATE conflicts with it. The plain UPDATE (FOR NO KEY UPDATE) would not.
    const rows = await tx.execute<{ status: string }>(sql`
      select status from communities
       where tenant_id = ${ctx.tenantId}::uuid and id = ${communityId}::uuid and deleted_at is null
       for update`);
    const row = rows[0];
    if (!row) throw new ApiError(404, 'NOT_FOUND');
    if (row.status !== 'archived') throw new ApiError(409, 'CONFLICT', { community: 'not_archived' });
    if (storeOn) {
      const products = await tx.execute<{ id: string; name: string; total: number }>(sql`
        select p.id, p.name, count(*) over ()::int as total
          from store_product_communities l
          join store_products p on p.id = l.product_id and p.tenant_id = l.tenant_id
         where l.tenant_id = ${ctx.tenantId}::uuid and l.community_id = ${communityId}::uuid
           and p.status = 'active'
         order by p.created_at desc, p.id desc
         limit 5`);
      if (products.length > 0) {
        throw new ApiError(409, 'CONFLICT', {
          community: 'unlock_active',
          products: products.map((p) => ({ id: p.id, name: p.name })),
          count: products[0]?.total ?? products.length,
        });
      }
    }
    await tx.execute(sql`
      update communities set deleted_at = now(), updated_at = now()
       where tenant_id = ${ctx.tenantId}::uuid and id = ${communityId}::uuid and deleted_at is null`);
  });
}
```

### Hiding a deleted community's posts (PEND-05)

**Pitfall that D-555's wording invites.** `postProjection` (`feed/server/service.ts:137-182`) joins `left join public.communities c on c.id = p.community_id and c.tenant_id = p.tenant_id`, and its comment explains "there is NO c.status and no c.deleted_at predicate". ### Anti-Patterns to Avoid
- **A deleted filter in a LEFT JOIN's ON clause.** It turns a deleted community's posts into community-less posts (see above).
- **A hard `DELETE`.** `feed_posts.community_id` and the event child tables use no `on delete` or `cascade` that you want to fire; the project rule is soft delete by `deleted_at`.
- **`emit()` on delete.** Silent by D-549; a new bus event also forces README edits.
- **Editing an applied migration.** `checksum_changed`.
- **Putting the marker in a response schema as required.** The web parses with `.strict()` elsewhere; keep it optional/defaulted.
- **Leaking names or titles into logs or error text** (T-05-06, Pitfall 12).

## Common Pitfalls

### Pitfall 1: Deleted community posts reappear as community-less posts
**What goes wrong:** the "deleted" filter is put in the `left join ... on`.
**Why it happens:** D-555 says "the feed's `left join` gets the deleted filter".
**How to avoid:** put it in `where` (`c.deleted_at is null`), test with a post in a deleted community AND a post with no community in the same page.
**Warning signs:** the community-less post count in Início rises after a delete.

### Pitfall 2: A deleted community answers 403 "locked", not 404
**What goes wrong:** members without an entitlement to an archived product that still links the community get `403 community_locked` and a buy section for a community that no longer exists.
**Why it happens:** `app.community_locked_ids()` reads `store_product_communities` regardless of product or community state; `feed_locked_post_community` reads only `feed_posts`.
**How to avoid:** the `create or replace function` fix above, plus a pgTAP assertion that it returns NULL for a post of a deleted community that is in the lane's locked set.

### Pitfall 3: The marker disappears on the next colour save
**What goes wrong:** `iconOwnArt` is stripped because `resolveBranding` rebuilds the object and writers replace the jsonb wholesale.
**How to avoid:** add the field to `tenantBrandingSchema`, `ResolvedBranding` and `resolveBranding`; add a test "colour change keeps the marker".

### Pitfall 4: A stale marker applies to a later unmarked icon
**How to avoid:** a plain `icon` completion writes `iconOwnArt: false`; `removeIconOverride` clears it.

### Pitfall 5: A race between "delete" and "link a product to this community"
**What goes wrong:** a link inserted between the refusal query and the update leaves an active product unlocking a deleted community.
**How to avoid:** `SELECT ... FOR UPDATE` first (only that mode conflicts with the FK's KEY SHARE).

### Pitfall 6: Migration generated too early
**What goes wrong:** a 09.3 file timestamped before a later 09.2 file is `out_of_order` for any project that already applied the head.
**How to avoid:** run `pnpm db:generate` when executing, after 09.2 closes; never copy an older timestamp.

### Pitfall 7: Local stack answers "Comunidade em atualização" after a new migration
**Why:** the gate derives its required version from the repo files and the tenant has a schema-state row (`docs/DEPLOY.md`, "The local gate").
**How to avoid:** `pnpm db:reset` (it runs migrations, `db:central` and the role script) or `pnpm db:migrate-all`; run pgTAP before the integration suite (a residue trips pgTAP 154) [CITED: MEMORY.md "Integration filter and seed drift"].

### Pitfall 8: Rollback after a long schedule exists
**What goes wrong:** an OLD web's editor normalises with `.slice(0, 30)` (`normaliseEventSchedule`, shared contract), so saving a 200-moment event from an old web silently drops moments 31 to 200; and the old CHECK cannot be re-added over rows longer than 30.
**How to avoid:** DEPLOY.md rollback limit: migrations are never rolled back; if the web is rolled back, do not save events that have more than 30 moments until the web is forward again; the same for highlight names over 15 (old `maxLength={15}` clips the field).

### Pitfall 9: README drift
**What goes wrong:** adding `moduleFlags` to the communities service without listing `@rede-social/core/server/modules/flags-cache` fails `module-readmes.test.ts`.

### Pitfall 10: Integration filter
`pnpm test:integration -- <file>` does not filter [CITED: MEMORY.md]; run `pnpm --filter @rede-social/api exec vitest run tests/integration/<file> -t "<title>"`.

export async function deleteEvent(ctx: RequestContext, eventId: string): Promise<void> {
  await withTenantTx(ctx, async (tx) => {
    const rows = await tx.execute<{ id: string }>(sql`
      update events

  );
}
