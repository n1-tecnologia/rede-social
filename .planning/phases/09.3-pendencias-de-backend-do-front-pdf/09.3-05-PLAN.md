<planning_decisions>
1. **No migration in this plan.** `communities.deleted_at` and every read filter already exist. This plan has no `[BLOCKING schema]` task; its first migration-free proof is the integration suite. The feed's hiding (migrations) is plan 06.
2. **The store flag is read in SQL, not through `moduleFlags` (assumption A1).** Both are allowed by the orchestrator's decision "the refusal honours the store module flag". The in-transaction `exists (select 1 from tenant_modules ...)` matches the way `app.community_locked_ids()` reads the flag, is uncached (a 30 s cache could contradict the gate for one request) and adds no `@rede-social/core/...` import, so `module-readmes.test.ts` needs no README "Kernel dependencies" change. The README still gets the new server name.
3. **Product names are capped at 5 plus a total (assumption A2).** The constant `COMMUNITY_UNLOCK_NAMES_MAX = 5` is exported by the contract so the service and the web read one number; the web says "e mais N" from `count`.
4. **`409 CONFLICT` with `details.community`, in the existing closed vocabulary.** The contract's docblock fixes the rule: input problems are 400 `VALIDATION_FAILED`, state refusals are 409 `CONFLICT`, a miss is a bare 404. `not_archived` and `unlock_active` join `COMMUNITY_ISSUES`, so the web narrows them with the existing `COMMUNITY_ISSUE_SET`.
5. **Silent, like the event delete.** No `emit(...)` (no README "Events emitted" change); one ids-only `communities.deleted` log line.
6. **Finding to carry into the SUMMARY and the DEPLOY notes (not a plan change).** The Loja deliberately KEEPS links to archived communities on a product edit (the CR-02 rule in `store/server/service.ts` `replaceLinks`: the product form can list only active communities). So for a community archived while an active product links it, the admin's way out of the `unlock_active` refusal is: reactivate the community, remove it from the product in the product form, archive it again, then delete. The refusal copy of the approved UI-SPEC ("Tire a comunidade dele primeiro") does not say "reactivate first"; this is recorded for the owner to decide in a later phase and appears as a manual UAT row in plan 09. D-554 is implemented exactly as locked.
7. **Precondition for the integration runs.** The local Supabase stack is up and seeded (`pnpm db:reset && pnpm db:seed` ran after the last migration).
</planning_decisions>
