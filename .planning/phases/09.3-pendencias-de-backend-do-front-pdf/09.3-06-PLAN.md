<objective>
The publications of a deleted community leave Início, Reels and the post page (the link answers 404), together with their comments and likes, while every row stays in the database and support can restore them by clearing `deleted_at` (D-555, D-556, PEND-05).

Purpose: a soft-deleted community must not leak through the feed. The feed joins `communities` with no deleted filter on purpose (an archived community's posts stay), the post page has a SECURITY DEFINER function that would turn a deleted community into a 403 "locked" answer, and the comment-id routes rely on RLS alone. The user chose the structural backstop: a RESTRICTIVE `feed_posts` policy beside the service predicates.
Output: two migrations (a custom function pair and a generated policy), the service predicates, the policy in the Drizzle schema, pgTAP 112, additions to the EXPLAIN-asserting 090 and 130, and the end-to-end integration file.

Tracer: Task 1 is the thinnest path through every layer: an admin deletes a community through the route and its post leaves Início, Reels and the post page, including the "archived product still locks it" variant that would answer 403 without the definer fix. Task 2 expands to every other post and comment route and to pgTAP; Task 3 is the full schema gate with the hot-path plan files.

<planning_decisions>
1. **Order of the two migrations is load-bearing.** (a) Create the custom file FIRST with `pnpm db:generate --custom --name community_soft_delete_gate`; (b) THEN edit `packages/modules/feed/db/schema.ts` and run `pnpm db:generate --name feed_posts_deleted_community_gate`. The second command's timestamp is later, so the function exists when the generated `CREATE POLICY` runs. Never hand-number either file; both are generated at execution time, after Phase 09.2 closes (RESEARCH Pitfall 6). Acceptance criteria match the globs on the slugs.
2. **Function name `app.community_deleted_ids()`.** It follows the RESEARCH and PATTERNS name; it reads `public.communities` by SQL name, as feed already does in `postProjection`, and mirrors the shape of `app.feed_sample_post_ids()` (definer, `search_path = ''`, array result). It is not row-picking (no `limit`), so pgTAP 040's convention holds.
3. **Why a definer, not an invoker.** Called from a `feed_posts` policy, an invoker function reading `communities` would evaluate `communities_tenant_isolation` inside every feed statement; the definer pins `tenant_id = app.tenant_id()` itself, like every function of the gate.
4. **The service predicates are the precise rule; the policy is the backstop** (the `memberPostVisible` plus `feed_posts_social_gate` house style). The research also listed `not exists` forms for `assertPostInteractive`, `listReplies` and `getCommentThread`; with the policy in place those three read `feed_posts` under it (their reads miss and fall through to the definers, which now answer null, then to the bare 404), so this plan adds no per-route SQL there and proves each route by test instead. `likeComment` and `unlikeComment` have no guard at all and are covered by the comments policy through the hidden post.
5. **Accepted side effect, recorded.** The policy applies to every tenant-lane read of `feed_posts`, so the owner dashboard's TypeScript post lists (`packages/modules/dashboard/server/content-lists.ts`, `content.ts`, `member-lists.ts`, `finance.ts`) also stop listing a deleted community's posts, while the SECURITY DEFINER snapshot builders (`app.dashboard_*`) keep their counts. The SUMMARY records whether any dashboard test or fixture notices; the integration gate in Task 3 runs the two dashboard owner files that read `feed_posts`.
6. **`app.media_asset_hidden` is left alone.** An asset of a hidden post is still fetchable by its unguessable id; the asset is not discoverable without the post (RESEARCH). Recorded as an accepted residual in the threat model.
7. **If a hot-path plan assertion goes red because of the policy**, do NOT loosen an assertion. First check the policy text is the InitPlan form (`coalesce((select app.community_deleted_ids()), '{}'::uuid[])`). If a file stays red, stop and record `blocked: policy plan regression` with the failing EXPLAIN in the SUMMARY: the user chose this backstop knowing it touches hot-path RLS and asked for exactly these files to be re-run.
8. **Precondition for the integration runs.** The local Supabase stack is up and seeded; pgTAP runs BEFORE integration (project memory), and `pnpm test:integration -- x` does not filter, so single files use `pnpm --filter @rede-social/api exec vitest run <file> -t "<title>"`.
