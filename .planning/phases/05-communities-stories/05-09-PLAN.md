<objective>
Close GAP 1 of `05-VERIFICATION.md`: the one Phase 5 write that can persist and reveal another
tenant's data.

**As an** organisation whose members' media lives beside eleven other organisations' media, **I want
to** know that no request from another tenant can plant a reference to my assets or learn that they
exist, **so that** "zero leakage between tenants" is a property of the code and not of the fact that
nobody has tried yet.

The capability already ships — `admin_tenant` creates, edits and archives communities with a cover
image, and truth 1 of the verification verified it. What does not ship is the check. `createCommunity`
and `updateCommunity` interpolate the client's `coverAssetId` into SQL with no `SELECT` against
`media_assets`: no tenant check, no purpose, no kind, no status. The single-column foreign key cannot
save it, because Postgres referential integrity runs as the table owner and therefore bypasses RLS —
so another tenant's asset id persists, and the 23503-vs-201 split (random uuid → unhandled 500; real
foreign id → 201) is a working cross-tenant existence oracle.

Three sibling write paths in this same codebase already do it right. This plan does not invent a
fourth way; it makes the fifth reference match the four.

Purpose: remove a realised high-severity tenant-isolation defect and the test that would have caught it.
Output: an in-transaction cover resolution, a bare 404 with no oracle, a closed `cover_invalid` code,
the cross-tenant integration case with its positive control, and a form that says something true.
</objective>

<assumption_delta_decision>
**Signal:** `assumption-delta` fired `detected: true` over the phase scope (`kind: optional`, term
`optional`, from 05-CONTEXT.md's "image or video up to ~60 s … optional caption"). Advisory,
non-blocking. The checkpoint's real question — *does the current primary key / identity model still
name the right noun, and has a configuration decision become a modeling decision?* — lands squarely
on this gap, so it is answered on its merits rather than waved through.

**Noun now primary:** *a media asset reference*. Its identity today is `media_assets.id` alone.

**The candidate generalization:** promote `(tenant_id, id)` to a referencable identity — add a
unique index on `media_assets(tenant_id, id)` and re-point `communities.cover_asset_id` at a
composite `(tenant_id, cover_asset_id)` foreign key, as this phase already did twice for the
story-comment `target_kind` discriminator and the two-column like FK.

**Decision: `no-change`.** Keep `media_assets.id` as the primary identity; do not promote the
composite; do not add alongside.

**Rationale, four parts:**
1. *It would not close the gap.* A composite FK can enforce the tenant and nothing else. It cannot
   see `purpose`, `kind` or `status`, and its refusal arrives as a 23503 that surfaces as a 500 —
   which is the existence-oracle shape this gap is about. The service check is required either way,
   and once it exists the FK is pure redundancy.
2. *It would deepen the inconsistency rather than close it.* Five places reference `media_assets`:
   `stories.media_asset_id`, `feed_post_media.media_asset_id`, `member_profiles.avatar_asset_id`,
   `communities.cover_asset_id`, and the cover picker's upload. Four of the five are guarded at the
   service layer inside `withTenantTx`. The root cause of this gap is that the fifth diverged from
   the four. Hardening only the fifth in a new, sixth way leaves the pattern MORE divergent.
3. *The cost lands on the kernel.* The unique index would be added to `packages/core/db/schema/
   media-assets.ts`, a Phase 3 table four modules reference, to close a Phase 5 service defect —
   a migration on shared ground for a local fault.
4. *Defense in depth is already two-deep and stays so.* Layer 3 (`communities_tenant_isolation` RLS
   plus `with check (tenant_id = app.tenant_id())`) already prevents a forged tenant stamp; the
   `media_assets_tenant_select` policy already prevents this lane from READING another tenant's
   asset. What was missing is a cross-table read, which is inherently service-layer work.

**Reversibility:** `reversible`. If a later phase generalises media references properly, the unique
index and the composite FK can be added then, with all five references migrated together — which is
the correct shape for that change and the wrong shape for this one.

**Contract test encoding the generalized intent** (optional per the capability, taken up here,
matching 05-08's pinned-story-for-every-`now()` precedent): case 27 of Task 2 asserts that for a
cover write the service's answer depends only on the asset's `(tenant_id, purpose, kind, status)`
tuple and never on which of the two write verbs was used — one intent, two call sites, one rule.
</assumption_delta_decision>
