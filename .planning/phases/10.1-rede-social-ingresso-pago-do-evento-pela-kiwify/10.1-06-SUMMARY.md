# Phase 10.1 Plan 06: The admin write side of the paid event Summary

**Three mapping routes (`GET`, `PUT`, `DELETE /v1/payments/event-products/{eventId}`) that link an event to its gateway product and purchase link under a per-event sales lock, an optional reference price in integer cents on the event itself, and a delete that frees the gateway product when nothing was sold and keeps it when something was.**

## Accomplishments

- Task 1 (tracer, test first: the route answered 404 before the code existed). `eventMappingBodySchema` is strict with both fields required and its own machine code for each refusal (`gateway_product_id_required`, `link_required`, `link_invalid`, `product_id_too_long`). `putEventMapping` follows `putStoreMapping` line by line (central reservation first, one `withTenantTx`, upsert on `(tenant_id, event_id) where kind = 'event'`, compensation, retire after commit) and adds the event lock and the sales rule.
- Task 2: `getEventMapping` and `deleteEventMapping`. The removal is one transaction (lock, `ticket_locked` when `sold > 0`, delete the row, `app.event_ticket_reset`), then the central route is released. The recurring hint comes from the delivery log. - Task 3: `ticketPriceCents` joins the input, summary, detail and edit schemas and the `events` statements. `releaseUnsoldEventMapping` runs after the soft delete commits: the same advisory key, a sale count, and only at zero the mapping row goes and the route is released.
- The EP-10 test is sensitive: with the sold check temporarily disabled, iteration 0 ended in the forbidden state (mapping gone, ticket present) and the lock test failed; both pass with the real code.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The compensation of a failed PUT could delete the route the winner of a race holds**
- **Found during:** Task 1 (designing EP-05)
- **Issue:** the central reservation reports `inserted: false` for the same tenant reserving a key again, so of two parallel PUTs of one product id for two events of ONE tenant the loser can be the one that inserted the route; its compensation would delete the route the winner's committed mapping needs, and a webhook for that product would then find no tenant. `putStoreMapping` has the same latent shape for two store products.
- **Fix:** the event path compensates only when no mapping of the tenant still holds that key (`keyIsMapped`, one tenant-lane read on the failure path). The store path is untouched (out of scope) and noted below.
- **Files modified:** packages/core/server/payments/setup.ts
- **Verification:** EP-05 test, eight iterations, always one success, one `gateway_product_taken`, one mapping row and exactly one route
- **Committed in:** e13981fa

**2. [Rule 1 - Bug] A pinned member-facing key set did not know the new price key**
- **Found during:** Task 3 (running the events integration files)
- **Issue:** `events-rsvp.test.ts` pins the detail key set (D-206); the plan's own schema change adds `ticketPriceCents` to it
- **Fix:** added the key and a dated line to the comment
- **Files modified:** apps/api/tests/integration/events-rsvp.test.ts
- **Verification:** the file passes (16 tests)
- **Committed in:** 19eaad67

**3. [Rule 3 - Blocking] A module unit test mocks the job queue module, so a static import of the payments setup broke it**
- **Found during:** Task 3
- **Issue:** `tests/events-payload.test.ts` failed at import (`registerJobQueues` missing on its mock) once the events service imported the payments setup, whose barrel registers a queue
- **Fix:** `deleteEvent` imports `releaseUnsoldEventMapping` on demand inside its try, which also keeps the events module's static graph free of the gateway adapters
- **Files modified:** packages/modules/events/server/service.ts
- **Verification:** module-events suite 166 tests pass; boundaries clean; the integration delete cases exercise the real import
- **Committed in:** 19eaad67

**4. [Rule 3 - Blocking] The price column sits at the END of the pinned SQL lists**
- **Found during:** Task 3
- **Issue:** two earlier tests pin the text `category, capacity, schedule` in the create insert and the update tuple
- **Fix:** `ticket_price_cents` is the last column of the insert, the last item of `next`, the last `set` item and the last item on both sides of the tuple (still on both sides, as the acceptance criterion requires)
- **Verification:** `grep -n ticket_price_cents` shows all four places; module suite passes unchanged
- **Committed in:** 19eaad67

**5. [Rule 3 - Blocking] `packages/core/server/payments/index.ts` was not modified**
- **Issue:** the plan lists it and asks for the new functions to be exported from it, but that file is the adapter barrel that `setup.ts` itself imports (`enabledProviders`, `gatewayAdapter`); re-exporting setup from it would create an import cycle, and every existing caller (routes, the apply job) imports `setup` by path
- **Fix:** the functions are exported from `setup.ts`, the same way as the store ones; the routes and the events module import that path
- **Files modified:** none

**6. [Rule 3 - Blocking] The PUT route entered the isolation inventory one commit later than it was mounted**
- **Issue:** the plan places the isolation rows in Task 2, but the PUT route is mounted in Task 1, so the API unit suite (`isolation-inventory.test.ts`) was red between `e13981fa` and `6110b40f`; the Task 1 verify command does not run it
- **Fix:** Task 2 adds the three rows and the case; the suite is green from `6110b40f` on

**7. [Rule 3 - Blocking] A new admin-lane site and a README line**
- **Issue:** the recurring hint needs `payment_events`, which has no policy, so one tenant-pinned `withAdminTx` site (`hasRecurringDelivery`) was unavoidable; the plan allows it with an inventory row. The module README also lists every route (a drift test reads it)
- **Fix:** inventory row (class T, migrated, plan 6) in `e13981fa`; README table rows in `7b91fb2b`
