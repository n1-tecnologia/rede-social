# Phase 10.1 manual proofs (P1 to P18)

This file is the ledger of the proofs only the owner can run: the first real sale of a real gateway product and its
real refund, a real phone against a hosted host in both themes under a tenant brand, the homolog deploy and every
production step, the full `pnpm verify` (it resets and seeds the local database, so it is his), and the reading of
the assumptions, defaults and wording the plans left to him. Everything an agent could build is built and proved on
the local stack (plans 01 to 15: unit, component, pgTAP, integration and the Playwright journey of plan 15); what is
left here cannot be faked, so nothing in this file is ever recorded as done by an agent.

**The rule.** Every row ships `pending`. A row becomes `passed` only when Igor pastes the evidence of its steps and
the date, in the row, himself. An agent never edits a Status line and never writes evidence it did not see. A phase
whose ledger has a `pending` row closes `human_needed`, never green. (Project memory: a blanket UAT pass is checked
against `docs/DEPLOY.md` before it is recorded, and a phone cannot reach `*.localhost`, so a row that needs a phone
needs a homolog or production host.)

**The evidence rule.** Paste shapes, counts, statuses, HTTP codes, exit codes and the words the screens show.
**Never** a key, a password, a token, a connection string, a webhook token, an e-mail address of a member or a
project ref. Replace a ref by `<ref>` and a host by `<host>` in what you paste.

**The procedures** are in `docs/DEPLOY.md`, "Phase 10.1 release (paid events through the payment gateway)".

**The design approval is yours.** Sketch `021` (the design gate, D-33, D-365) carries `approved: true` because you
approved it provisionally and the orchestrator wrote the approval on your instruction. No executor wrote it. The
approval confirms the drawn defaults as a whole, not one product call at a time; rows P2, P3, P12 and P13 are where
that provisional approval meets a real screen and a real reading.

## P1 - The first real sale and its real refund (TICK-24, EP-45)

- **Proves:** that the product id format and the refund's order id, which have only been seen in the gateway's own
  test deliveries (random ids), behave on a real account: a real purchase confirms a real presence and the real
  refund removes it. This is the phase's real proof; every other sale in this repository used the `fake` adapter.
  EP-45 (TICK-24) had no probe category; a reviewer should confirm none is missing.
- **Needs:** a tenant with the `payments` module on and the real gateway connected, one test event, one real gateway
  product (a cheap one), a member account, a real card, and the gateway panel to refund.
- **Steps:**
  1. In the event form of a new test event, turn Cobrar ingresso on and type the real product's id, its purchase link
     and a reference price. Save. The event page of a member shows Pago and one Comprar ingresso link to that address.
  2. As the member, open the event page and keep it open. Buy the product with the member's e-mail.
  3. See the presence appear by itself: the open page becomes Presença confirmada, the bell lists the row, and
     Participantes marks the member Pago.
  4. In the gateway panel, refund the order. See the presence go: the member's page returns to Comprar ingresso and
     Participantes no longer lists the member.
- **Evidence to paste:** the words the screens showed at each step, the Pagamentos "Eventos recentes" rows (state and
  effect line, no e-mail), and whether the product id and the order id were accepted as they came.
- **Status:** pending
