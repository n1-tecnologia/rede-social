# Phase 10.1 Plan 14: Participantes marks, Liberar presença and Acima do limite Summary

**The admin's Participantes screen of a paid event now marks every presence with its origin, removes a courtesy and releases a presence (toolbar search sheet or Não vão row) behind confirms that change a row only from the server's answer, and shows when the event is over its limit on the screen, the manage card and the rows.**

## Performance

- **Duration:** about 14 min
- **Started:** 2026-11-13T12:14Z (approximate; the start time was not captured at spawn)
- **Completed:** 2026-11-13T12:28Z
- **Tasks:** 3 (1 tracer, 2 auto)
- **Files modified:** 15 (4 created, 11 modified)

## Accomplishments

- **Marks and removal (task 1, tracer).** `AttendeeRow` gained `marks` (a `mt-1 flex flex-wrap gap-1` pills line under the meta, absent when empty) and `action` (a `shrink-0` sibling that wraps under the column below 360 px, `flex-wrap` only when an action exists), props-only. `ParticipantsList` turns the `attendeeView` marks into `StatusPill`s in the fixed order and tones and, with the manage permission, offers a `ghost sm text-danger` "Remover cortesia" only on a courtesy row; `removeCourtesyAction` answers `ok | locked | not_courtesy | not_found | generic`. A free event's row keeps the exact shipped className and two-child column.
- **Liberar presença (task 2).** `ReleasePresenceSheet` is prompt-first (no request until the admin types), debounces 300 ms into `searchCourtesyMembersAction` over the admin members read, asks the holders read once per page (at most 50 ids) and draws "Já inscrito" instead of the button; 5 skeleton rows on a search, 3 at the sentinel, empty and error with retry, stale answers dropped. The Não vão rows carry "Liberar presença" by `attendanceId`. Both doors share `ReleaseConfirmDialog` and `useReleaseToast`; `grantCourtesyAction` validates the strict body first and returns `granted | already_in | event_ended | event_cancelled | event_not_paid | not_found | generic`. The toolbar door shows for a paid event and the events manage permission only.
- **Over limit (task 3).** `OverLimitNotice` (`CircleAlert`, two ICU plurals, static text) above the chips while the server flags the event, the "Acima do limite" pill under the Participantes sub-line of the manage card for an organiser of a paid event past its limit, and `participants.empty.confirmed.bodyPaid` for a paid event's Confirmados.
- **Tests:** module-events 186 passed (12 files); web `app/(app)/eventos` + `i18n` + `lib/events-view`: 31 files / 2359 passed; payments-neutral 12 passed; turbo typecheck (web, module-events and their dependencies) 4/4; check-ui-literals OK; `pnpm boundaries` clean; Biome clean on the touched folders.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `apps/web/lib/events.ts` was not in the plan's file list**
- **Found during:** Task 1
- **Issue:** the plan says the actions call the API "through the file's existing fetch helper", but the fetch helpers live in `lib/events.ts`, not `actions.ts`, and no client existed for the grant or the removal.
- **Fix:** added `grantCourtesy` and `removeCourtesy` there (the holders client was already plan 08's).
- **Files modified:** `apps/web/lib/events.ts`
- **Committed in:** 758c493c

**2. [Rule 3 - Blocking] The toolbar door lives in the page, not in `ParticipantsList.tsx`**
- **Found during:** Task 2
- **Issue:** the plan places the toolbar button "above the chips" yet in `ParticipantsList.tsx`; the list renders below the chips nav, so it cannot draw above them.
- **Fix:** `ReleasePresenceToolbar` (button plus sheet) is exported from `ReleasePresenceSheet.tsx` and rendered by `participantes/page.tsx` for a paid event with the manage permission; the Não vão row door stays in the list.
- **Committed in:** 4a1c4aa3

**3. [Rule 3 - Blocking] The page reads the event for the limit**
- **Found during:** Task 3
- **Issue:** the attendance summary carries `paid`, `overLimit` and `confirmedCount` but not `capacity`, which the notice sentence needs; the plan says the page passes `capacity`.
- **Fix:** the page calls `loadEvent` only when `summary.overLimit` is true and draws no notice if that read fails or the limit is null. No API or contract change.
- **Committed in:** a34d5d1b

**4. [Rule 3 - Blocking] Test scaffolding the plan did not list**
- **Found during:** Tasks 1 and 3
- **Issue:** `ParticipantsList` now calls `useToast`, so its existing client tests needed a `ToastProvider` (a `renderList` helper); the manage-card pill had no test file to extend because the event detail page had none.
- **Fix:** `renderList` in `ParticipantsList.test.tsx`; a new `[eventId]/page.test.tsx` with the client islands stubbed.
- **Committed in:** 758c493c, a34d5d1b

**5. [Process] The web-side tracer tests were written after the code**
- The module slot tests (`participants-ui.test.tsx`) were run red before `AttendeeRow` changed; the `ParticipantsList` tracer case was written right after the implementation rather than shown failing first. The plan marks TDD not applicable; coverage of the tracer path is complete.
