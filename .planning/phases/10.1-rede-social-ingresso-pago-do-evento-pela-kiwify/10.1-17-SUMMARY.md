# Phase 10.1 Plan 17: Manual release under the order lock (WR-01) Summary

**`releaseTicket` now takes the same `tenant:provider:external_ref` advisory lock as the apply job (one helper, `order-lock.ts`, key text pinned by a unit test) and re-reads the applied-refund fact under it, so a refund that applies between the release's read and its grant is seen: 409 `not_grantable`, nothing written.**

## Performance

- **Duration:** about 6 min (start 2026-11-13T14:28:20Z, end 2026-11-13T14:34Z)
- **Tasks:** 3 (1 tracer, 1 auto/tdd, 1 gate)
- **Files:** 2 created, 3 modified, no migration

## Accomplishments

- WR-01 closed: the check that decides the manual release now runs under the order lock, in the same admin transaction as the definer call. The deterministic race test (a holder connection on the literal key, the release observed waiting in `pg_locks`, a refund committed as applied, the lock freed) answers 409 `not_grantable`, zero presence rows, and the delivery stays `no_membership`.
- One definition of the key: `apply.ts` no longer builds the key text; `lockPaymentOrder` and `appliedRefundExists` are the only copy (single-copy check exits 0). The webhook path is unchanged (same lock point, after the event row lock and only when an external reference exists; same predicate).
- EP-G5: the helper renders `$1::text || ':' || $2::text || ':' || $3::text, 0` with the parameters tenant, provider, reference in that order, pinned by 5 unit tests.
- No `withAdminTx` site was added; the admin-lane inventory unit test stays green.
