## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A holder's check-in would have been refused by plan 02's own walk-in backstop**
- **Found during:** Task 2 (writing the holder positive controls), by reading guard step 6b against the old definer bodies
- **Issue:** the old definers write `insert ... values (..., 'walk_in', ...) on conflict do update`. The guard trigger judges the proposed INSERT tuple before the arbiter (plan 02's own finding), and in a mapped event step 6b refuses a new `walk_in` tuple, so a `going` ticket holder checking in would have been `payment_required` instead of `checked_in`, breaking the truth that holders "pass through the old steps untouched".
- **Fix:** in a mapped event both definers move a `going` holder with a plain `UPDATE ... set status = 'checked_in'` (origin, order and refund columns never named); the free branch keeps the exact old upsert, so free events stay byte-identical. If the holder row vanished under the write (a refund), the answer is `ticket_required`, never `already` with a URL. No change to the guard.
- **Files modified:** `supabase/migrations/20261113004658_event_ticket_doors.sql`
- **Verification:** pgTAP 233 section 3 holder assertions (ticket row stays `checked_in/ticket/fake/ORD-F1-T` and `checked_in/ticket/ORD-F2-T`), integration #2 and #3, pgTAP 142 unchanged and green.
- **Committed in:** `b801ed65`

**2. [Rule 1 - Bug] `not (v_answer in (...) or ...)` is NULL when the member has no row**
- **Found during:** Task 1 (the tracer test still read `confirm_first` after the first apply)
- **Issue:** with a NULL `v_answer` the membership test is NULL, so the non-holder branch never fired.
- **Fix:** wrapped in `coalesce(..., false)`; the check-in door reads the row into `v_own` and tests `v_own is null or ...`.
- **Verification:** the Task 1 test turned green; pgTAP 233 no-row cases.
- **Committed in:** `26eb2541` (the fix was applied before the commit)

**3. [Rule 3 - repo state] `_journal.json` loses its trailing newline when drizzle-kit rewrites it**
- Restored by hand, as in plans 01 and 02.

**Total deviations:** 3 (two bugs fixed inline, one cosmetic). **Impact:** none on the contract; the behaviour matches every truth in the plan. The migration was edited in place after its first apply, so the local database got the final body by re-running the file (it is `create or replace`, re-run safe); `supabase_migrations` already records the version.
