# Phase 10.1: Rede Social - Ingresso pago do evento pela Kiwify - Research

**Researched:** 2026-11-12
**Domain:** extending the Phase 09.1 gateway pipeline (signed webhook -> inbox -> apply job) with a third mapping kind (`event`), and the Phase 06 events data model (attendance row, guard trigger, check-in definers) with a payment-gated presence
**Confidence:** HIGH on the codebase facts (every discrete value below was read from the file this session); MEDIUM on the Postgres trigger-ordering behaviour (the repo's own pgTAP 141 supports it, the planner proves it first); LOW on the real Kiwify product id and on refund-finds-approval for a real one-off sale (never exercised against a real sale: Wave 0 risk R1)

## Summary

The phase is mostly a database design problem with a thin TypeScript shell. The webhook pipeline of 09.1 already gives signature check, per-tenant mapping lookup, dedupe, row lock, a per-sale advisory lock, stale detection from `payment_events`, `Eventos recentes`, `Liberar manualmente`, and the post-commit notification. What is missing is (1) a third mapping kind whose target is an event, (2) an origin and an order reference on the attendance row, (3) a database-level refusal of a member's own `going` in a paid event, with explicit, narrow exceptions for the paid path, (4) closing walk-in in the two check-in definers, and (5) two SQL definers (`app.event_gateway_grant` / `app.event_gateway_revoke`) the apply job calls, because the kernel cannot import `module-events`.

Three design choices carry the whole phase and are settled below with evidence: **a new `payment_products.event_id` column with a composite FK, not a reuse of `target_id`** (the unconditional store FK makes reuse impossible without a drop); **an `origin` column on `event_attendances` (`rsvp` / `ticket` / `courtesy`) plus `order_provider`, `order_ref`, `refunded_at`, with no new status** (the confirmed count `going + checked_in` and pgTAP 141's copied expressions stay byte-identical); and **the guard trigger bypassing start-time and capacity only for rows whose `origin` is `ticket` or `courtesy`, with the member lane's RLS `WITH CHECK` pinning `origin = 'rsvp'`** (so the bypass cannot be requested by a member, and no GUC is trusted). A refund **deletes** the going row (as the UI-SPEC says "removes the row") and **keeps and flags** a checked-in row.

**Primary recommendation:** Plan the work as five backend plans before any UI plan (UI waits for the owner's `approved: true` on sketch 021): (A) schema + contracts, (B) guard / check-in / enter and the member-lane policies, (C) definers + apply branch + outcomes + manual release, (D) mapping and courtesy routes + event payload fields + notification, (E) validation fixtures; then the web plans. Ship migrations (every tenant database) -> web -> API, expand-only.

### Locked Decisions

**What a paid event is, and who gets a presence**
- **D-740: A paid event is an event with a linked gateway product.** The link is the only switch. An event with no linked product keeps today's behaviour untouched (D-204, D-205, D-206).
- **D-741: In a paid event only two things create a presence: an approved purchase, or the admin's `Liberar presença`.** The member's own `Vou` write is refused with a stable machine code (for example `payment_required`, HTTP 409) by the API **and by the database**, including the direct self-RSVP policies on `event_attendances`. Hiding the control in the UI is not enough (same rule as D-204). — **Reversibility:** costly — a trigger/policy change on `event_attendances` plus a new refusal code that the web and the native app (13) will read.
- **D-742: Walk-in is closed for a paid event.** `app.events_enter` (online `Entrar`) and `app.events_check_in` (venue code) accept only a member who already holds a presence (`going` or `checked_in`). Anyone else is refused with a machine code and the screen shows the `Pago` state with `Comprar ingresso`. For an event with no product, D-207 and D-208 stay as they are, including walk-ins. The calendar export (D-211) is unchanged: the `/eventos/{id}/entrar` URL is still gated at click time.
- **D-743: The admin can release a presence without payment (`Liberar presença`, shown as `Cortesia`).** It is an action on the member's row in `Participantes`, in the pattern of `Liberar manualmente` (D-503). A courtesy presence is not revenue and does not lock the product field (D-747). The admin can remove a courtesy presence; a paid presence leaves only by refund or chargeback (default, see Claude's Discretion).

**Linking the product to the event**
- **D-744: The link lives in the event form, in a new `Ingresso` section.** Fields: the gateway product code and the purchase link, **both required together** (the form does not save one without the other; without a link the member has no way to buy and the system never releases for free, D-508), plus the optional reference price (D-755). This follows D-502: mappings live where the admin already works. The mapping is a third kind in the one mapping table of D-488 (an `event` kind whose target is the event), written through the payments module's mapping services; the event form is the single writer.
- **D-745: One gateway product serves one event.** The pair (provider, external product id) stays globally unique (D-488, PAY-01); a second event needs its own product, and saving a product that is already in use answers the existing `gateway_product_taken` conflict.
- **D-746: If the `payments` module is turned off, or the gateway is disconnected, after an event was linked, the event shows `Venda indisponível` to everyone without a presence.** Presences already held stay. Nobody gets in for free and nothing falls back to the instant `Vou`. Turning the module back on restores the flow. Linking a product requires the module on.
- **D-747: Once an event has at least one paid presence, its product is locked.** The form shows `N ingressos vendidos` and refuses a change or a removal; without paid presences the admin changes or removes it freely. The lock exists so a later refund still finds the event. Removing the product (when allowed) returns the event to the instant `Vou`. — **Reversibility:** reversible — a form/service rule.
- **D-748: Presences that exist when the product is linked stay.** They are not charged and are marked as made before the ticket (`Anterior ao ingresso`). Only answers given after the link pay.

**Odd purchases**
- **D-749: The buyer's e-mail must equal the e-mail of a live member of the event's tenant (D-490).** If it matches nobody, the delivery is kept in `Eventos recentes` as `sem conta` and the admin releases it by hand with the existing `Liberar manualmente`, extended to ticket deliveries. **There is no wait-for-account mechanism in this phase**: the store path has none either (`no_membership` is final). The member is already logged in when they buy, so the case is rare. Deferred: confirm automatically when the e-mail later becomes a member.
- **D-750: An approved payment confirms while the event is active and has not ended, even after `starts_at`.** The check-in window runs to `ends_at` (D-209), so someone who pays while the event is under way gets in. After `ends_at`, or if the event is cancelled, nothing is confirmed and `Eventos recentes` shows the reason (`evento encerrado` / `evento cancelado`) so the admin can refund at the gateway. The in-app `Comprar ingresso` button disappears at `starts_at`, in line with D-204. The paid path therefore needs an explicit exception to the guard that refuses `going` at or after `starts_at`.
- **D-751: A payment that arrives at a full event confirms anyway** (decided by Igor, 2026-11-12). The paid path bypasses the capacity trigger explicitly; the `Comprar ingresso` button is replaced by `Esgotado` when the confirmed count (`going + checked_in`, D-219) reaches `capacity`, and the admin sees an `acima do limite` mark on the event and in `Participantes`. A member's own `Vou` over capacity remains refused as today.
- **D-752: A refund or chargeback removes the presence and frees the seat** (decided by Igor, 2026-11-12; same cut as D-505, D-496). The presence row must record how it was confirmed (paid, courtesy or before the ticket) and the gateway order reference, so a refund finds it without a member. — **Reversibility:** costly — new columns on `event_attendances` that paid rows depend on; dropping them loses the link to refunds. A refund **after check-in keeps the checked-in row** (the database already locks a checked-in row) and the list shows `Reembolsado`. A late approved delivery for an order already refunded is stale and changes nothing (PAY-30).

**What the member and the admin see**
- **D-753: A member without a presence, in a paid event, sees the `Pago` badge on the poster card and the detail, and a single action, `Comprar ingresso`, instead of the `Vou` / `Não vou` pair.** `Comprar ingresso` opens the tenant's purchase link and creates nothing locally, with no "processando" state (D-506). A line says that the presence appears by itself after paying; when the webhook confirms, the open page refreshes into the confirmed state through the existing Realtime user signal (PAY-34 pattern). Other states: `Esgotado` (D-751), `Vendas encerradas` from `starts_at` (D-750), `Venda indisponível` (D-746), `Presença confirmada`.
- **D-754: A confirmed member (paid or courtesy) has no `Não vou`.** The detail shows `Presença confirmada` with a line saying that, to give up, the member asks the gateway for the refund, which removes the presence by itself; for a courtesy the line points to the organisation instead. Exact copy is the UI-SPEC's.
- **D-755: The event carries an optional reference price.** When the admin fills it, the card and the button read `Comprar ingresso · R$ 80,00`; without it only the `Pago` badge shows. The amount actually charged is the one the gateway reports (D-507); the reference never decides anything. New optional field on the event (the event PUT is a whole-event replacement, so the key must be `.optional()`; release-order rule).
- **D-756: The member gets an in-app notification and a push `Presença confirmada em {evento}` when the payment is approved,** the same family as `Compra confirmada` (D-506). The 24 h and 1 h reminders (EVENT-07) already reach every `going` member, so a payer gets them with no change.
- **D-757: Only an approved purchase grants; refund and chargeback revoke.** Subscription-type deliveries (`renewed`, `late`, `canceled`) on an event product are recorded in `Eventos recentes` and change no presence. Linking a recurring product to an event is a mistake the form should warn about when it can tell.
- **D-758: `Participantes` marks the origin of each presence:** `Pago`, `Cortesia`, `Anterior ao ingresso`, `Reembolsado`. The confirmed count keeps its meaning (`going + checked_in`, D-219). The Pagamentos hub lists ticket deliveries in `Eventos recentes` with the neutral type and the reasons of D-749 and D-750. Note the naming trap: that tab lists **payment deliveries**, not tenant events.

### Claude's Discretion
- Table and column names (for example a payment reference and a `confirmed_via`-style origin on `event_attendances`), the definer function names (`app.event_gateway_*`, modelled on `app.store_gateway_*`), and how the status CHECK and the count expressions copied into pgTAP 141 change if a status is added.
- How members read the purchase link: members cannot read `payment_products` (admin RLS), so a tenant-pinned definer returns it, as `app.payments_checkout_url` does for store products.
- Which route carries the event mapping (not `/v1/payments/events`, already the deliveries list).
- Exact pt-BR copy and the machine codes, always through the gateway-neutral rule: the brand `Kiwify` must not appear outside the adapter, so copy uses the `{gateway}` placeholder (`packages/core/tests/payments-neutral.test.ts`).
- Whether an admin may remove a paid presence by hand (default: no), duplicate purchases by the same e-mail for the same event (default: idempotent, one presence), and how subscription-type events are recorded.
- The split into plans, fixtures and the release order (every tenant has its own database: expand-only migrations, push migrations before the API, as in 09.1).

### Deferred Ideas (OUT OF SCOPE)
- Confirm automatically when a purchase arrives for an e-mail that only later becomes a member (needs an e-mail-keyed pending record and a replay on membership creation; the store path lacks it too).
- A sales and revenue panel per event (tickets sold, revenue, capacity used).
- Several products, price lots or ticket types per event; coupons and guest tickets created inside the system.
- A list or export of paid members for a cancelled event, to ease refunding at the gateway.
- Selling at the door and QR check-in (V2-EVENT-01).

*(Also out of this phase by the Phase Boundary: refunding from inside the system; the Financeiro dashboard; subscriptions on an event product beyond "recorded, no effect on presence".)*

## Project Constraints (from CLAUDE.md)

- Stack is fixed: Next.js 16 on Vercel, Hono API on Cloud Run, Drizzle schema with RLS in TS, Supabase CLI applies migrations, Biome, Vitest 5, pgTAP, Playwright. This phase **adds no dependency** (the UI-SPEC says so too).

- **GSD workflow enforcement:** repo edits go through a GSD command; this research writes only `10.1-RESEARCH.md`.

### Supporting / Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| New column `payment_products.event_id` + composite FK | Reuse `target_id` for the event id | Reuse is blocked by the unconditional FK `payment_products_target_fk` to `store_products`; fixing it means dropping that FK (not expand-only in spirit, loses the store guarantee) or a trigger-based check (weaker than a real FK). | `origin` column, no new status | A new status such as `paid` / `courtesy` | A new status touches the status CHECK, both count expressions copied into pgTAP 141, every `status in ('going','checked_in')` predicate, the dashboard functions, the chips and the web view. Rejected. |

### (C) The guard trigger: where `payment_required` lives, and the exceptions

**Evidence (full current function read):** step 1 immutable; step 2 event read `for share`, `deleted_at is null`; step 3 checked-in lock; step 4 `if v_status = 'cancelled'` -> `event_attendances_event_active / cancelled`; step 5 `if new.status in ('going','not_going') and now() >= v_starts_at` -> `event_attendances_rsvp_open / rsvp_closed` (note: **any** update of a going row after start trips it, not only a status move); step 6 check-in window; step 7 capacity under `pg_advisory_xact_lock(hashtextextended('event_capacity:' || new.event_id::text, 0))`, only for a move INTO `going` [VERIFIED: supabase/migrations/20261003233626_event_capacity_guard.sql:28-110].

The function is `create or replace`d (same signature, expand-only). It needs to know whether the event is paid while running as `authenticated`, which cannot read `payment_products` (admin-only policies [VERIFIED: 20261020234833_payments_tables.sql:84-87]); so it calls a tenant-aware `SECURITY DEFINER` helper `app.event_ticket_mapped(p_tenant uuid, p_event uuid) returns boolean` (`stable`, `search_path = ''`, EXECUTE to `authenticated` and `service_role`; when claims are present it answers false unless `p_tenant = app.tenant_id()`). | New step | Condition | Result |

**Service mapping (API half).** `GUARD_ISSUES` maps constraint names to the closed `EVENT_ISSUES` vocabulary [VERIFIED: service.ts:612-618]; add `event_attendances_payment_required: 'payment_required'`, `event_attendances_ticket_locked: 'ticket_locked'`, `event_attendances_event_ended: 'event_ended'` (the last code already exists in `EVENT_ISSUES` [VERIFIED: contracts/index.ts:168]). **A holder repeating `Vou` trips 3b** because the guard judges the proposed INSERT tuple before the arbiter (same trap the capacity step has; `fullEventAnswer` exists for it [VERIFIED: service.ts:663-690]). `rsvpEvent` must therefore, on `payment_required`, read the caller's own row in a fresh transaction exactly as `fullEventAnswer` does: `going` -> unchanged 200; `checked_in`/`walk_in` -> `attendance_locked`; otherwise `409 { event: 'payment_required' }`. ### (G) `payment_events` vocabulary

### Anti-Patterns to Avoid

- **Trusting a GUC or an `IF current_user` to grant the bypass.** Use the `origin` column and pin it in RLS.
- **Raising from inside a definer the apply job calls.** Return outcomes (Pitfall 1 of 06; `apply.ts` retry loop).
- **Letting a third kind fall through to `applyStore`.** Add an explicit branch and an exhaustive guard.
- **Reading `payment_products` as a member** or returning `checkout_url` from anything but `app.event_checkout_url`.
- **Editing pgTAP 141 fact 10 or the status CHECK.** No status is added.
- **Naming the gateway in any new key, column, route, fixture string or catalog entry** (`TICK-20`); use `{gateway}` and `gatewayName`.
- **Counting a refunded paid row as "no longer sold"** to unlock the product; keep the lock on `origin = 'ticket'` rows.

## Common Pitfalls

### Pitfall 1: The guard fires on a holder's repeated `Vou` (and on a bookkeeping update)
**What goes wrong:** a stale tab of a paid member sends `Vou`; the INSERT tuple (origin `rsvp`) trips `payment_required` before the arbiter turns it into an update. Separately, step 5 trips on **any** update of a going row after `starts_at`, so an origin upgrade or a `refunded_at` write after the start raises.
**How to avoid:** the follow-up read in `rsvpEvent` (as `fullEventAnswer`); the bookkeeping early-exit (2c); a test that pays after `starts_at` and then upgrades.
**Warning signs:** a webhook event stuck in `failed` with SQLSTATE 23514.

### Pitfall 2: A definer raising inside the apply transaction
**What goes wrong:** cancelled/ended/deleted/foreign member inside the guard raise -> transaction rollback -> `markFailed` -> pg-boss retries forever.
**How to avoid:** the definers pre-check every guard condition and return an outcome; keep the guard as a backstop only. Test each outcome through `runApply` and assert the event ends `ignored`, not `failed`.

### Pitfall 3: Refund on a cancelled event, or after the event ended
**What goes wrong:** the checked-in row update (`refunded_at`) is refused by step 4.
**How to avoid:** the bookkeeping exit (2c) and a DELETE (no trigger) for going rows. Test: cancel after check-in, then refund.

### Pitfall 4: `updateEvent` drops a price-only change
**What goes wrong:** the guarded `UPDATE` compares an explicit column tuple; a new column left out of both tuples is never written when it is the only change.
**How to avoid:** add `ticket_price_cents` to `next`, the `set` list and both sides of `is distinct from` [VERIFIED: service.ts:1031-1066]; extend `events-admin.test.ts` "identical PUT writes nothing" with a price-only change.

### Pitfall 5: A courtesy row in an event returned to the free `Vou`
**What goes wrong:** the member cannot answer `Não vou` (policy pins `origin = 'rsvp'`), a 500.
**How to avoid:** `app.event_ticket_reset` on mapping removal, same transaction; and `ticket_locked` is judged only for `ticket`/`courtesy` rows.

### Pitfall 6: The mapping removal racing a sale
**What goes wrong:** the apply job read the mapping, the admin removes it (sold = 0), the grant lands on an unmapped event.
**How to avoid:** both take `pg_advisory_xact_lock('event_ticket:' || event)`; the grant re-checks the mapping row under the lock and answers `not_mapped` -> `unknown_product`.

### Pitfall 7: New `withAdminTx` call sites and routes break the inventories
**What goes wrong:** `admin-lane-inventory.test.ts` and `isolation-inventory.test.ts` fail the unit suite.
**How to avoid:** add the inventory rows and isolation case ids in the same plan as the route.

### Pitfall 8: Contracts leaking server-only imports into the web bundle
**What goes wrong:** the web imports the events and payments contracts; a `node:fs`-using helper pulled into a contracts index breaks only `next build`.
**How to avoid:** keep the new schemas/constants in `packages/contracts/src/payments.ts` and `packages/modules/events/contracts/index.ts` free of server imports; run `next build` once per contract plan.

### Pitfall 9: Brand neutrality in fixtures
**What goes wrong:** a test fixture or catalog key containing the brand fails `payments-neutral.test.ts`.
**How to avoid:** the fake adapter (`provider: 'fake'`) in every new test; `{gateway}` in copy.

### Pitfall 10: The real Kiwify "test delivery" proves nothing about order ids
The six committed real captures send a random `order_id` per delivery and an approved body that already carries `subscription_id`, so approval and refund of one sale cannot be correlated from them [VERIFIED: packages/core/tests/fixtures/payments/kiwify/trigger-compra_aprovada.json:3,134 vs trigger-compra_reembolsada.json:3: different order ids]. Only a real one-off sale proves that the refund carries the approval's `order_id` (the adapter keys a one-off by `order_id` [VERIFIED: kiwify.ts, `externalRef: recurring ? (subscriptionId ?? orderId) : orderId`]). This is TICK-24.

### Known Threat Patterns (the planner's threat model; ids are proposals)

| # | Pattern | STRIDE | Standard Mitigation |
|---|---------|--------|---------------------|
| T-10.1-01 | Webhook signed with tenant A's token naming tenant B's event product | Spoofing / Elevation | Mapping lookup is `tenant_id = integration tenant and provider and external_product_id` (apply.ts:364-373); the definer takes `p_tenant` and re-pins event, membership and mapping to it; composite FK keeps `payment_products.event_id` in the mapping's tenant; pgTAP + integration negative in both directions |
| T-10.1-02 | Same gateway product id registered by two tenants | Tampering | Global unique `(provider, external_product_id)` + central reservation before write (unchanged) |
| T-10.1-03 | Member forces `going` in a paid event by direct SQL / crafted RSVP | Elevation | Guard 3b + `WITH CHECK origin='rsvp'`; data API is closed but API-process SQL can reach it, so the refusal is in the DB (D-741); pgTAP as `authenticated` |
| T-10.1-04 | Member forges `origin='courtesy'|'ticket'` to bypass start/capacity | Elevation | Insert/update `WITH CHECK` pins `origin = 'rsvp'`, `order_ref is null`, `refunded_at is null`; test the insert as the member role |
| T-10.1-05 | Walk-in bypass: `events_enter` / `events_check_in` / direct `walk_in` insert | Elevation | `ticket_required` in both definers before any counting, guard 6b backstop, policy keeps `checked_in`/`walk_in` out of the member lane (existing T-06-11) |
| T-10.1-06 | Code brute force by a non-payer | Info disclosure | Refusal precedes the attempts read and the comparison |
| T-10.1-07 | Replay of an approved delivery | Repudiation / Tampering | Row lock + state check, advisory lock per reference, `event_attendances_order_uq`, `already_in` |
| T-10.1-08 | Late approval re-granting a refunded order | Tampering | `payment_events` prior-terminal fact -> `stale` (also in the manual release) |
| T-10.1-09 | Refund of a courtesy / before-ticket presence | Tampering | Revoke matches on `order_ref` only; courtesy/rsvp rows have none, so a refund never touches them |
| T-10.1-10 | E-mail spoofing at checkout / claiming another person's ticket by registering their address unconfirmed | Spoofing | Match = exact `lower(btrim())` live member (PR-7); add `app.membership_email_unconfirmed` check -> `unconfirmed` -> `sem conta` (A4). Typing someone else's e-mail at checkout only gifts them a presence |
| T-10.1-11 | Leaking the purchase link or product id to members | Info disclosure | `payment_products` admin-only; link only via `app.event_checkout_url`; `event_ticket_admin` requires the admin claim; no id/link in list payloads |
| T-10.1-12 | Courtesy abuse by non-admin | Elevation | `forbidden` outcome unless `app.tenant_role() = 'admin_tenant'` inside the definer, whatever route reached it; route guarded by `events.event.manage` |
| T-10.1-13 | Cross-tenant ids on new routes (`eventId`, `membershipId`, `attendanceId`) | Info disclosure | Bare 404 (D-23), every statement `tenant_id =` pinned, isolation inventory rows |
| T-10.1-14 | Tenant teardown / move blocked by a lock trigger | DoS | No delete trigger on `payment_products`; lock is a service rule under an advisory lock |
| T-10.1-15 | Mapping removed mid-sale leaves an unmapped paid presence | Tampering | Grant re-checks the mapping under the per-event advisory lock |
| T-10.1-16 | Unbounded member search | DoS | Reuse the admin members read (limit clamps 1..50, query max 80); the sheet shows no list before typing |
| T-10.1-17 | Injection via event title / names into notification, push or catalog | Tampering | Titles are React text / catalog placeholders; push body cut on a word; no `dangerouslySetInnerHTML` (UI-D-766) |

- **R1 (HIGH impact, unproven):** the real gateway `Product.product_id` and its relation to the id in the admin's panel (A1). The six captured deliveries use random ids; the adapter header lists it as unconfirmed. Mitigation: TICK-24 as an owner row; the admin copy says "ID do produto no {gateway}" and the form helper tells where to copy it; consider logging `external_product_id` of `unknown_product` deliveries in `Eventos recentes` (it already shows `externalProductId`).

- **R6:** `supabase/migrations/meta` snapshots: `pnpm db:generate` must be run, never hand-editing a generated file; the custom migration is added with `--custom` so the snapshot chain stays consistent.
- **R7:** one-statement query budget (`feed-query-budget.test.ts` has a ceiling and a floor): the new per-row function calls must stay inside the existing projection.
