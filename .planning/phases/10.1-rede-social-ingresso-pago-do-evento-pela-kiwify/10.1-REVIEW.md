# Phase 10.1: Code Review Report

**Reviewed:** 2026-11-13T12:00:00Z
**Depth:** standard
**Files Reviewed:** 64
**Status:** issues_found

## Summary

Reviewed the nine migrations, the apply/mapping/manual-release server code, the events and payments module routes and services, and the web form, zone, door, Participantes and live-swap code. The payment path is carefully built. The definers pin `search_path`, scope every statement by tenant, grant the gateway pair to `service_role` only, and return business outcomes instead of raising. Replay, out-of-order refund-before-approval, double approval, checked-in refund (`refunded_at`, row kept), and the ended, cancelled and full cases all trace correctly. No gateway brand appears in any changed non-adapter file. Buy links go through `safeCheckoutHref` plus `rel="noopener noreferrer"`, and the price is integer cents end to end.

One defect undermines the core invariant of the phase. The member lane can rewrite the origin and order columns of its own paid row (CR-01), which the guard's bookkeeping exit lets through. The four warnings are a manual-release/refund race, an unrecoverable orphan mapping, a misleading outcome on a replay after the event ended, and the free-`Vou` window left by the create-then-link second write.

## Critical Issues

### CR-01: A member can strip `origin` and `order_ref` from their own paid or courtesy row (refund then no longer revokes the seat)

**File:** `packages/modules/events/db/schema.ts:381-386` (update policy), `supabase/migrations/20261113003640_event_ticket_member_lane.sql:1`, `supabase/migrations/20261113003918_event_ticket_guard_exceptions.sql:49-55` (step 1b)

**Issue:** `event_attendances_self_rsvp_update` keeps `USING = SELF_RSVP`, which does not pin `origin`. Only the new row is pinned, by `WITH CHECK = SELF_RSVP_PLAIN` (`origin = 'rsvp' and order_ref is null and refunded_at is null`). The guard's bookkeeping exit (step 1b) returns the row immediately for any UPDATE that changes only `origin`, `order_provider`, `order_ref`, `refunded_at` or `updated_at`. The two compose into a hole.

Failure scenario, with no API route involved (any authenticated-lane SQL, for example a Data API that is not closed on a customer-owned Supabase project, 09.4):
1. A member buys the ticket, so their row is `status = 'going', origin = 'ticket', order_provider = 'x', order_ref = 'ORD-1'`.
2. The member runs `update event_attendances set origin = 'rsvp', order_provider = null, order_ref = null where user_id = <me> and event_id = <e>`.
3. `USING` passes (status is `going`). `WITH CHECK` passes (new row is `rsvp` with a null order). The CHECK constraints pass (`origin = 'ticket'` is false and `order_ref is not null` is false). The guard hits step 1b and returns before step 3c (`ticket_locked`) or 3b.
4. The row is now a plain `rsvp` presence with no order reference. The member asks the gateway for a refund. `app.event_gateway_revoke` finds no row by `(tenant, provider, order_ref)` and returns `not_found`, so the delivery settles `no_effect`. The member keeps the seat after being refunded.
5. As a side effect `sold` (`origin = 'ticket'` count) drops, so the D-747 product lock (`app.event_ticket_lock`, `app.event_ticket_admin`) releases even though a real order exists. The member can also now press `Não vou`, because 3c no longer matches.

This is the exact "DB must refuse, not only the UI" requirement of D-741/D-752, and pgTAP 233 has no test of a member updating the origin or order columns of their own row (the only `set origin` hit is the service-role upgrade at line 305). The schema comment ("`using` stays `SELF_RSVP`, so the guard trigger still runs first") only considered status moves, not the bookkeeping exit.

**Fix:** Do not just add `origin = 'rsvp'` to `USING`. For `INSERT ... ON CONFLICT DO UPDATE` (the `rsvpEvent` upsert) a failing `USING` becomes a bare 42501 and the named `ticket_locked` refusal is lost. Refuse the change in the guard itself, before the bookkeeping exit, for the member lane:

```sql
-- in app.event_attendance_guard(), immediately before step 1b
if tg_op = 'UPDATE'
   and current_user = 'authenticated'          -- definers run as their owner, the apply lane as service_role
   and (new.origin is distinct from old.origin
        or new.order_provider is distinct from old.order_provider
        or new.order_ref is distinct from old.order_ref
        or new.refunded_at is distinct from old.refunded_at) then
  raise exception using errcode = '42501', constraint = 'event_attendances_bookkeeping_locked',
                        message = 'bookkeeping_locked';
end if;
```

Ship it as a new migration that replaces the guard (it is the latest definition of the function), and add a pgTAP case in `233-event-tickets.sql` that a member updating `origin`, `order_provider`, `order_ref` or `refunded_at` on their own ticket and courtesy rows fails, with the definers still passing.

## Warnings

### WR-01: "Liberar manualmente" on a ticket can create a presence for an order that was refunded a moment earlier

**File:** `packages/core/server/payments/events.ts:208-252` (stale read) and `packages/core/server/payments/events.ts:326-345` (`releaseTicket`)

**Issue:** `grantEventManually` reads `stale` (an applied refund or chargeback of the same order) in one admin transaction. `releaseTicket` then runs `app.event_gateway_grant(..., true)` in a second, separate transaction without re-checking it and without taking the `tenant:provider:external_ref` advisory lock that the apply path holds. The apply job serialises the approval and the refund on that lock, so the webhook path is safe, but the manual path is not.

Failure scenario: the admin clicks release on a delivery whose order was just refunded. The refund event applies between the two transactions, and `revoke` finds no presence yet and settles `applied/no_effect`. The grant then writes a `ticket` presence carrying an order that is already refunded. Nothing will ever revoke it, because the refund event is final. The result is a free seat and a refunded buyer holding a paid-origin row.

**Fix:** Inside the `withAdminTx` of `releaseTicket`, take the same lock and re-run the stale `exists` before calling the definer:

```ts
await tx.execute(sql`select pg_advisory_xact_lock(
  hashtextextended(${ctx.tenantId}::text || ':' || ${facts.provider}::text || ':' || ${orderRef}::text, 0))`);
// re-run the 'applied refund or chargeback of the same order' query here; if true, throw 409 not_grantable
```

### WR-02: A gateway product can stay bound to a deleted event forever, with no recovery path

**File:** `packages/modules/events/server/service.ts:1459-1475` (swallowed failure) with `packages/core/server/payments/setup.ts:884-918` (`releaseUnsoldEventMapping`)

**Issue:** The mapping release runs after the soft delete has committed and its failure is only logged. The comment in `deleteEvent` says the orphan "can be cleared by the next delete or admin action". That is false:
- `deleteEvent` on an already-deleted event throws 404 before reaching the release (`written.length === 0`).
- `app.event_ticket_lock` requires a live event, so `putEventMapping`, `getEventMapping` and `deleteEventMapping` all answer 404 for it.

Failure scenario A: a transient DB error (or a failed `releaseProductRoute`) during the release leaves the `payment_products` row and the central route for that gateway id. The id then answers `gateway_product_taken` to every future event of the tenant, and nothing in the product can remove it.

Failure scenario B: `releaseUnsoldEventMapping` runs in the caller's lane. `payment_products` has `admin_tenant`-only RLS. If a tenant composes `events.event.manage` for a non-admin role (settings allow it), the select returns nothing and the function returns silently, with the same permanent orphan and no log line.

**Fix:** Run the release in the tenant-pinned admin lane (`withAdminTx({ tenantId })`) so the caller's role is irrelevant. When the delete's release fails, or the mapping is present but not visible, log it at `error` with the event id. Add an admin path that can clear a mapping whose event is deleted, for example let `deleteEventMapping` accept a deleted event when `sold = 0`, or sweep orphaned `kind = 'event'` mappings in the existing hourly job.

### WR-03: A repeated approval after the event ended is reported as "not confirmed, refund at the gateway" although the buyer holds a presence

**File:** `supabase/migrations/20261113005835_event_gateway_grant_revoke.sql:156-171` (steps 6 and 7), `packages/core/server/payments/apply.ts` (`case 'event_ended'`)

**Issue:** `app.event_gateway_grant` checks cancelled/deleted and `now() >= ends_at` (step 6) before the replay check (step 7: the order reference already names a presence). A re-sent approval for an order that was granted earlier, whose body differs in bytes from the first (so the inbox does not dedupe it, for example a manual resend from the gateway panel), returns `event_ended` or `event_cancelled` instead of `already_in` once the event is over. The delivery is then listed as `ignored` with "Presença não confirmada: o evento já tinha terminado. Reembolse no {gateway} se for o caso."

Failure scenario: an admin follows that hint and refunds a customer who attended and still holds a valid presence. The refund then arrives as `ticket_kept`/`ticket_revoked` and flags or removes them.

**Fix:** Move step 7 (the `order_ref` already-present check, and the member's own `ticket` row check from step 8) above the cancelled/ended returns. A replay is `already_in` regardless of the event's state. Add a pgTAP case: grant, advance past `ends_at`, grant the same reference again, and expect `already_in`.

### WR-04: A failed second write on create leaves a published event with the free `Vou` open

**File:** `apps/web/app/(app)/eventos/EventForm.tsx:854-862` (and `apps/web/app/(app)/eventos/ticket-actions.ts`)

**Issue:** For a new paid event the form creates the event first (`createEventAction`) and links the product afterwards. If the link fails (`gateway_product_taken`, a locked id, an API error), `createdId` makes the retry update the same event. But the event is already live and unmapped. If the admin closes the tab, or just takes time to fix the id, every member sees the instant `Vou` and can confirm for free. Per D-748, those presences are then marked "Anterior ao ingresso", are never charged, and stay `going` after the product is finally linked.

This follows from D-744's accepted "event first, then product" order, but the revenue consequence and the lack of any mitigation is not recorded.

**Fix:** Cheapest mitigation: after a failed second write on create, send the admin to the edit page of the new event (not leave them on the create form), with a persistent banner "ingresso não vinculado", so the unmapped window is visible. Stronger: create the event as unpublished (or cancelled-style hidden) until the link succeeds, or add a one-statement "create and map" path in the API.

## Info

### IN-01: Any member lane can read every attendee's `origin`, `order_ref` and `refunded_at` through the tenant-wide select policy

**File:** `packages/modules/events/db/schema.ts:371-375`

**Issue:** `event_attendances_tenant_select` is `tenant_id = app.tenant_id()` and the table now carries the gateway order reference and the paid/courtesy origin of every attendee. D-206 treats "who is going" as an API property, and the API never projects other members' rows. A direct query from a member lane (the same exposure as CR-01) would now also reveal who paid, who got a courtesy and the order references. The API surface is unaffected.

**Fix:** Move the order columns out of the member-readable relation (a `event_attendance_orders` admin-only table), or have the select policy hide them, for example expose a view for the member lane without `origin`, `order_provider`, `order_ref` and `refunded_at`. If that cost is not wanted, record it as an accepted risk next to the D-206 note.
