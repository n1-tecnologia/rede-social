## Summary

This pass judges what gap plans 10.1-16..19 changed since the first pass (commit cc3ca8b2): the guard step 1a (CR-01), the shared order-lock helper (WR-01), the replay-first reorder of `app.event_gateway_grant` (WR-03), and the release notes. The two generated drizzle snapshots were left out on purpose.

**All three fixes close their findings, and I found no regression and nothing worse introduced.** The things I traced:

- **CR-01 (guard step 1a).** I diffed the new guard body against `20261113003918_event_ticket_guard_exceptions.sql`. The only difference is the added 1a block, so every other step, name and message is byte-identical. 1a sits after step 1 (a row never moves) and before the bookkeeping exit (1b), so a member's rewrite of `origin`, `order_provider`, `order_ref` or `refunded_at` is refused before 1b can return it.
  - `current_user` is the right key. The guard is a plain SECURITY INVOKER trigger function, so inside a definer it reports the definer's owner and not the caller. The courtesy definers, `event_ticket_reset` and the grant and revoke pair therefore pass even when called from an `authenticated` session, and the new pgTAP case proves it with the admin reset. The apply and refund lanes run `set local role service_role` (`packages/core/db/lanes.ts:40`) and pass. The member lane runs `set local role authenticated` (`tenant-tx.ts:45`) and is judged.
  - `api_user` is `noinherit` (`20260912030541_app_helpers.sql:7`), so there is no bare-`api_user` path that policies would accept while 1a ignored it.
  - The `rsvpEvent` upsert never names the four columns, so its DO UPDATE leaves them unchanged and 1a does not fire. I found no other `authenticated` writer of those columns in `packages` or `apps`; the tenant move copies by INSERT.
  - There is no delete policy on the table, so a member cannot work around 1a with delete and reinsert.
- **WR-01 (order lock).** The key text is identical to the old inline apply code, in the same position and with the same casts: `<tenant>::text || ':' || <provider>::text || ':' || <ref>::text`, seed 0. `payments-order-lock.test.ts` pins the rendered SQL and parameter order. The integration cases hold the literal text `${tenantId}:fake:${ref}` from a second connection, so they prove the helper builds the same key as a real lock.
  - Lock order has no cycle. Apply takes the delivery row lock, then the order lock, then (inside the definer) the event advisory lock, the event row and the attendance row. The manual release takes the order lock, then the same definer path, then updates its own delivery row. The only way to deadlock would be an apply job running on the same delivery that the release is settling. The release requires `state = 'no_membership'`, and the apply job returns before taking the order lock for any state other than `received` or `failed`.
  - The throw of `409 not_grantable` inside `withAdminTx` rolls the transaction back, so nothing is written.
  - `appliedRefundExists` is called with the delivery id as the excluded id, which matches the first read's `t.id <> e.id`.
- **WR-03 (replay first).** I diffed the new grant against the one in `20261113005835_event_gateway_grant_revoke.sql`. Only the position of the cancelled/deleted/ended returns and the step numbers changed. Arguments, live membership, unconfirmed, the per-event lock, the mapping re-read and the `not_found` event read still come first, so a replay cannot answer for an unmapped event, another tenant's event (the event read is pinned by `tenant_id`) or an unconfirmed account. The replay lookup is tenant-pinned and cannot match a null `order_ref`. A first-time grant for a member with no row, or with a non-ticket row, still reaches the cancelled, deleted and ended refusals, because only a ticket row or a reference that already names a presence returns early.
- **Checks run.** `pnpm supabase test db supabase/tests/233-event-tickets.sql` passes 354 of 354 on the local stack. The journal has 191 consecutive entries with increasing `when` values and a snapshot chain (`prevId`) that follows. The expand-only grep over the eleven files prints nothing. The neutral walk's regex matches exactly the eleven files, and no gateway brand appears in the new migrations, the pgTAP file or `order-lock.ts`.

One gap in test coverage remains on the riskiest part of the reorder, plus three low-impact notes.

## Warnings

### WR-01: No test covers a FIRST-TIME grant over an existing non-ticket row after the reorder (the one path where `v_att` is set and the end/cancel refusals must still win)

**File:** `supabase/tests/233-event-tickets.sql:1620-1693` (section 9), `apps/api/tests/integration/payments-apply-tickets.test.ts:267-302`

**Issue:** Moving the cancelled, deleted and ended refusals below the replay and the member-row lookup creates exactly one new way for the refusal to be skipped by a future edit. When the member already has a `going`, `checked_in` or `walk_in` row of origin `rsvp` or `courtesy` (an upgrade, A10b), `v_att` is not null and the code falls through to step 9. Section 9 only asserts the first-time refusal for members with NO row (`S9-R1c`, `S9-R2b`, `S9-R3b`). The pre-existing upgrade cases (section 4, lines 742-822) run on a live event. So nothing asserts that a payment after the end, or on a cancelled or deleted event, does not upgrade a pre-link presence. If someone later "simplified" the `v_att_origin = 'ticket'` early return to `v_att is not null`, every test would still pass. D-750 and D-760 (a payment never confirms an ended or cancelled event) would be broken for exactly the members who had a plain Vou before the link.

**Fix:** Add three cases to section 9, one per state of the event. Seed the member with a pre-link `rsvp` going row, move the event to ended, cancelled or deleted, then assert `event_ended`, `event_cancelled` and `event_cancelled` for a new reference. Also assert that the row still reads origin `rsvp` with null order columns. For example, for the ended event:

```sql
-- event 814 mapped later: user 108 has a plain Vou made before the link, then the event ends
select results_eq(
  $$ select outcome from app.event_gateway_grant(tests.tk('1'), tests.tk('208'), tests.tk('814'), 'fake', 'S9-R4') $$,
  $$ values ('event_ended'::text) $$,
  'D-750 control: a pre-link Vou is NOT upgraded by a first-time payment after the end');
select is((select origin from public.event_attendances where event_id = tests.tk('814') and user_id = tests.tk('108')),
  'rsvp', '...and the row still reads origin rsvp');
```

## Info

### IN-01: The replay lookup is not scoped to the event or the member, so `already_in` can name a caller who does not hold the presence

**File:** `supabase/migrations/20261113144645_event_gateway_grant_replay_first.sql:120-128`

**Issue:** Step 7 matches on `(tenant, provider, order_ref)` only, which is the documented "one reference is one presence, whoever holds it" rule (EP-36). Before this change that answer was shadowed by `event_ended` and `event_cancelled`. Now it wins in every state. The row returned is `already_in, v_user, v_title`, where `v_user` and `v_title` are the CALLER's member and the requested event, not the holder's. pgTAP 9 even pins the cross-member case (`S9-R1` sent for member 202 answers user 102). The apply code ignores `user_id` on `already_in`, so nothing leaks or is granted wrongly today. Two consequences are worth a conscious decision. A reference that names a presence on a DIFFERENT event of the tenant now settles `applied / no_effect` instead of `ignored / event_ended` or `event_cancelled` once the requested event is over. And a manual release for a member who is not the holder settles the delivery as applied with no effect.

**Fix:** None required for this gap round. If the order-sharing case (one order, two events) is ever supported, scope step 7 by `a.event_id = p_event` and let the other-event case fall through. Until then, a one-line comment on step 7 stating that the answer is deliberately not scoped would stop a later reader from "fixing" the pgTAP expectation.

### IN-02: The refund predicate now lives in two places: the helper and the inline first read of the manual release

**File:** `packages/core/server/payments/events.ts:217-226` vs `packages/core/server/payments/order-lock.ts:46-55`

**Issue:** WR-01 introduces `appliedRefundExists` as the single definition of "an applied refund or chargeback of the same order", used by the apply job and by the release's re-read under the lock. But `grantEventManually` still carries its own inline copy of the same predicate (the `stale` column of the first read). The two copies are identical today. If a refund type is ever added to one (for example a new neutral type for a dispute), the first read and the locked re-read would diverge, and the re-read, the one that matters, could be the stale one. The comment in `order-lock.ts` says the helper is "the one the manual release re-runs", which is true but invites the assumption that the first read uses it too.

**Fix:** Either drop the inline `stale` expression and rely on the locked `appliedRefundExists` check alone (the first read only decides whether to try), or add a pointer comment next to the inline SQL: "keep in step with `appliedRefundExists`".

### IN-03: Two small inaccuracies in the Phase 10.1 section of DEPLOY.md

**File:** `docs/DEPLOY.md:4612-4617`, `docs/DEPLOY.md:4678-4682`

**Issue:**
- Item 10 says it "replaces the function that item 5 created". Item 4 (`20261113003644_event_ticket_guard.sql`) created `app.event_attendance_guard`, and item 5 redefined it. The replacement is still correct, because 10 supersedes 5.
- The compatibility note says the previous API "reaches the grant only through the apply job's unchanged call". The previous revision's manual release ("Liberar manualmente", `releaseTicket`) also calls `app.event_gateway_grant`. It is safe, because it gets `already_in` and settles it as no effect, which the old code already maps. But the sentence understates the surface, and a reader checking the fan-out could think the manual path is untouched.

All file names, version stamps, the count "eleven", the smoke-check queries (marker `WR-03 replay first` really is inside the function body) and the expand-only grep match the repository.

**Fix:** Say "redefined by item 5" and "reaches the grant through the apply job and the manual release, both unchanged calls".
