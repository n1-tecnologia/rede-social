<objective>
Let an admin find archived communities through the API without knowing their ids — the data half
of ROADMAP criterion 2 — while members' list stays exactly what it is today.

`listCommunities` hard-codes `c.status = 'active'` (`service.ts:137`), so an archived community
leaves every list and can only be reached by typing its uuid. This plan adds a closed `status`
filter to `GET /v1/communities`: `active` (the default, today's statement untouched) or `archived`
(a second literal statement, most recently archived first). Asking for `archived` without
`communities.community.manage` is refused 403 by the API (D-89). There is no schema change and no
new index (D-91): the archived set is small, and the budget test proves the read is still one
statement.

Purpose: the endpoint 05.1-03's `Arquivadas` chip reads.
Output: the extended query contract, the guarded handler, the two-branch service, and integration,
budget and pgTAP evidence.
</objective>

<planning_decisions>
1. **D-89 discretion: the API REFUSES (403), the web COERCES.** A crafted `?status=archived` from a
   member gets an explicit `403 FORBIDDEN` — the answer `requirePermission` gives everywhere else,
   and one a test can pin. The web page (05.1-03) only ever sends `status=archived` when the viewer
   holds the manage permission, so a member who opens a shared `/comunidades?status=arquivadas`
   link sees today's active list and never an error card. Both halves are tested: member → 403,
   admin → 200 (positive control).
2. **`status` is `z.enum(COMMUNITY_STATUSES).default('active')`** — absent means active, an unknown
   or differently-cased value is a 400. Unlike `limit`, it does not clamp: no navigation tab ever
   sends it (the web translates its own pt-BR URL value), so a bad value can only come from a
   crafted call, and an explicit 400 is the honest answer.
3. **Two literal statements, chosen in TypeScript (RESEARCH Pattern 2).** `status` is never a bound
   parameter, so the partial index's `status = 'active'` predicate is provably implied for the
   active statement regardless of plan caching, and pgTAP 17-18 keep describing the statement the
   service really runs.
4. **The extra cursor column follows `storyProjection(viewerUserId, extra)`.** `communityProjection`
   becomes a function taking an optional extra select column; every existing call site passes
   nothing and renders the same column list. The archived statement passes the microsecond-formatted
   `updated_at` aliased `cursor_at`, which `toCommunity` never reads.
5. **A cursor carries no status.** An active-list cursor replayed against `status=archived` simply
   pages the archived set from that timestamp; it can only be sent by a caller who already holds the
   manage permission, so it discloses nothing.
</planning_decisions>
