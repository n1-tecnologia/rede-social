<objective>
Make a story creatable **born attached** to a community, at the API, in one transaction — the
mechanism under ROADMAP criteria 3, 4 and 5 — and do the Wave 0 test hygiene every later plan's
verification depends on.

Today pinning is a second editorial step (`PUT /v1/stories/{id}/pins/{communityId}` from
`/stories/meus`), so an admin who publishes "into" a community can forget or half-apply it. This
plan gives `POST /v1/stories` an optional `communityId` and writes the pin row inside the same
`withTenantTx` as the story (D-99), with the same target checks `pinStory` applies, the same refusal
shapes, the manage permission the pin routes already require, and the events a pin already emits.
Nothing about a no-community publish changes. The web never learns a new field in a response.

It also closes two hazards RESEARCH measured this session: the API Vitest config lets a developer's
`VIDEO_PROVIDER=mux` reach the integration workers (Pitfall 2), and the local database has drifted
from the seed through manual UAT (Pitfall 4). The first is pinned in code; the second is reset only
after the developer says so, because the reset wipes their manual Mux-backed test data.

Purpose: the one write every 05.1 story surface (plans 04 and 05) calls, proven end to end first.
Output: the extended contract, the guarded route, the one-transaction service, the Wave 0 pin, and
the integration + unit evidence.
</objective>

<planning_decisions>
Decisions this plan takes where CONTEXT left discretion or RESEARCH left an open question. Each is
recorded so a later reviewer does not "fix" it.

1. **API shape (CONTEXT discretion): a flat optional `communityId` on the existing publish body**,
   `z.uuid().optional()` — the `createPostSchema.communityId` shape verbatim. Not nullable and not
   nested: "no destination" is the absence of the key, which is exactly how the post composer
   already sends it. Additive to the request; nothing added to any response (Pitfall 3).
2. **Attach permission (RESEARCH OQ-1): `stories.story.publish` AND `stories.story.manage`.** The
   route middleware keeps `requirePermission('stories.story.publish')`; the handler additionally
   requires the literal manage permission only when the body carries `communityId`, through the
   kernel's own `permissionsForRequest` (the resolver `requirePermission` uses). The contracts'
   docblock already says the two permissions are separate "because V2 hands `publish` to members
   without handing them the moderation half", and pinning is a manage act. D-92 names
   `stories.story.publish` as the Destaques `+` gate; plans 04 and 05 gate the composer row and the
   `+` on the SAME pair (UI-D-53/UI-D-56 explicitly defer this choice to the planner). In V1 exactly
   `admin_tenant` holds both, so no V1 user sees a difference.
3. **Events (CONTEXT discretion): `story.published` unchanged, plus ONE `story.pinned` when a pin
   row was written.** A pin-tracking subscriber sees every pin through one event whichever path
   wrote it (born attached ≡ pinned later); the two pinned key-set assertions on `story.published`
   stay untouched; and the history screen counts pin ROWS (`pinned_community_count`), never events,
   so nothing is counted twice. **Phase 7 caveat (RESEARCH A3):** a born-attached story emits both
   `story.published` and `story.pinned`; a member-notification consumer must dedupe by `storyId` or
   ignore `story.pinned`, or members get two notifications for one story.
4. **Statement order (RESEARCH Pattern 3): destination first.** With a `communityId`: community
   lookup → asset lookup → story insert → pin insert → projection read-back. This mirrors
   `createPost` (`feed/server/service.ts:694-699`): a refused destination costs no asset validation
   and is the first thing the caller is told, and a refusal never follows a (rolled-back) insert.
   Without a `communityId` the sequence is today's three statements exactly, which keeps
   `tests/events.test.ts`'s call-index mock green.
5. **Deploy order:** API before web. Recorded for Phase 01.1; local-only now (cloud deferred).
</planning_decisions>

<assumption_delta_decision>
**Signal:** `assumption-delta scan 05.1` returned `detected: true`, `kind: pluralization`, on "a
second editorial step" and "ADDITIONAL communities". The real question it raises: a story now
reaches a community by a SECOND path (at publish) beside the first (the post-hoc pin) — does the
identity of "a story's attachment to a community" still name the right noun?

**Noun that is primary:** the **pin row** (`story_community_pins`, many-to-many, unique on
`(story_id, community_id)`). It already generalises "one story, many communities".

**Decision: `no-change`.** The pin row stays the single representation of attachment. This plan
deliberately does NOT add a `stories.community_id` column alongside it (which would be the
"add-alongside" failure: a born-attached story would then have two sources of truth, and a story
pinned later would never be "its community"). Born-attached is simply a pin row written by a second
caller of the same INSERT. No schema change (ROADMAP Notes, CONTEXT).

**Reversibility:** `reversible` — the new path writes ordinary pin rows; removing it strands nothing.

**Invariant test (taken up):** Task 3 asserts born-attached ≡ pinned-later on pin-row columns,
`pinnedCommunityCount`, Destaques membership and the `story.pinned` key set. It goes red the moment a
later phase gives the two paths different semantics.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
