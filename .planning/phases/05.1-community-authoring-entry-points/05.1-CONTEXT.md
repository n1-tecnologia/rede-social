# Phase 05.1: Community Authoring Entry Points - Context

**Gathered:** 2026-09-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Wiring, not invention. Every community and story action Phase 5 built for an `admin_tenant` gets a control on a screen reachable from a phone, with no URL typing and no memorised UUIDs:

1. Create-community reachable from a **non-empty** `/comunidades`.
2. Archived communities **findable and reactivatable** without knowing their id.
3. A story publishable **from a community page**, born attached to that community.
4. That attachment written **in the same transaction** as the story.
5. The story composer **itself** asks which community (or none); "none" stays the zero-effort default.

Criteria 3 and 5 are ONE mechanism: a community selector in `/stories/publicar` that arrives pre-filled via `?comunidade=`. **No schema change** — `story_community_pins` is already many-to-many. The post-hoc pin flow in `/stories/meus` (`PinStorySheet`) stays exactly as shipped and remains how a story reaches ADDITIONAL communities.

Out of scope: anything that isn't an entry point to an existing capability (new community features, member authoring, story editing, story grouping).

</domain>

<decisions>
## Implementation Decisions

### Create-community CTA (criterion 1)
- **D-86:** `/comunidades` renders a **"Criar comunidade" control in the title row**, right of the `Comunidades` heading — a compact brand button (an icon-only `+` with an accessible label is acceptable on narrow phones), present in BOTH the empty and non-empty states, same on phone and desktop. Not a FAB (creation is rare and a floating control would cover cards and compete with the post FAB's meaning), not a first-card (it would scroll away and inject a fake item into a keyset list). Gated on `communities.community.manage` exactly as `canManage` is today. It stays a LINK to `/comunidades/nova` (the shipped `createCta` rule).
- **D-87:** The **empty state keeps its own "Criar comunidade" action** (D-77 unchanged). Two routes to one form on the empty screen is fine.

### Archived communities in the list (criterion 2)
- **D-88:** Archived communities live behind **two filter chips under the heading — `Ativas` (default) / `Arquivadas`** — shown only to managers. `Ativas` is today's list, unchanged. `Arquivadas` renders the same `CommunityCard`s carrying the existing `Arquivada` pill (`communities.archived.pill`). Each chip is its own keyset query with a single `status` predicate, so the cursor never spans two statuses. Rejected: inline mixed list (the tester's literal wording, but it needs a two-status ordering in one keyset), and interleaving by activity (dead communities between live ones).
- **D-89:** **Only callers with `communities.community.manage` can list archived communities, and the API enforces it** — the list endpoint takes a status filter, and asking for `archived` without the permission is refused (or silently coerced to active; planner picks and pins with a test), never served. Members' `/comunidades` is byte-for-byte today's. The archived community PAGE by direct link keeps its shipped behaviour.
- **D-90:** **Reactivation is one tap from the archived community page**: the existing archived note under the header (`communities.page.archived` / `archived.note`) gains a **`Reativar` action with a confirm**, visible only to managers. The edit-form control (`CommunityForm.tsx:458-470`) stays as a second route. Rejected: a button on each list card (a second tap target inside a card that is itself a link).
- **D-91:** `Arquivadas` is ordered **most recently archived first**. There is no `archived_at` column and none is added (no schema change), so the order is `updated_at desc, id desc` — equal to archive time unless an archived community is edited afterwards, which is accepted. No new index: the archived set is small, and the planner confirms this rather than adding a migration. The cursor carries `updated_at` read back from the projection (the `listCommunities` precision rule).

### Story from a community page (criterion 3)
- **D-92:** The admin starts a community story from a **leading `+` circle in that community's Destaques row** — the same "Seu story" circle D-80 put on the home strip — linking to **`/stories/publicar?comunidade={id}`**. It sits exactly where the result will appear. For a caller with `stories.story.publish`, the Destaques section **renders even with zero pins** (the `+` alone); for members it still renders nothing when empty. Rejected: the post FAB opening a Post/Story choice (taxes every post with a tap), a second header icon (easy to miss).
- **D-93:** An **archived community offers no story entry at all** — not a disabled one (UI-D-37's rule for posts, restated for stories; pinning to an archived community is already refused with `pin: 'archived'`). The composer treats a `?comunidade=` that is unknown, another tenant's, or archived exactly like `/criar` does: it **silently falls back to "Nenhuma comunidade"** (first value wins if repeated).
- **D-94:** After publishing from a community origin, the admin **lands back on `/comunidades/{id}`**, where the new circle in Destaques confirms the attachment. Publishing with no community context keeps today's `/inicio` destination. The discard/close path from a community origin also returns to the community.

### Composer community choice (criteria 4 and 5)
- **D-95:** The composer attaches a story to **one community or none** — the post's "Publicar em" model exactly. It reuses **`CommunityPickerSheet`** in its check-mark (`onSelect`) variant with a leading **`Nenhuma comunidade`** row supplied by the host (the picker ships no words). Additional communities are still pinned afterwards in `/stories/meus`. Rejected: multi-select in the composer (array contract + switch UI for a rare case the pin sheet already covers).
- **D-96:** A story published into a community **still appears in the home strip for its 24 h** AND stays in that community's Destaques after expiry. The community is where the story *also stays*, not where it is hidden — the same rule as D-73 (community posts appear in the main feed), and identical to what a post-hoc pin already produces. The strip predicate does not change. — **Reversibility:** costly — hiding community stories from the strip later would make "born pinned" and "pinned later" behave differently, and would need a strip predicate the viewer's sequence and its tests depend on.
- **D-97:** The choice is a **`Publicar em: {Nenhuma comunidade | nome} ›` row in the composer's bottom bar, above `Publicar`**, next to the caption, opening the sheet. It is visible before publishing (criterion 5: stated up front), costs zero taps when the default is right, and is never a mandatory step. Rejected: a chip over the media (overlaps the preview), a pre-publish step (adds a tap to every tenant-wide story, violating "no community must not get harder").
- **D-98:** The "no community" label is **`Nenhuma comunidade`**, not "Feed principal" — a story has no feed, and a tenant-wide story is still in the strip either way.
- **D-99:** **One write, one transaction.** `publishStory` accepts an optional community id; the story insert and the `story_community_pins` insert happen inside the SAME `withTenantTx`, with the same target checks `pinStory` already applies (tenant-scoped, not deleted, `status = 'active'`, else refuse with the existing `pin: 'archived'` / bare 404 shapes). No client-side "publish then pin" sequence exists anywhere. — **Reversibility:** reversible — additive optional field on the publish contract.

### Claude's Discretion
- The exact API shape: an optional `communityId` on the existing publish body vs. a nested field; whether `story.published` carries the community id or a separate `story.pinned` event is also emitted (keep payloads Phase-7-ready; do not double-emit a pin the history screen would then count twice).
- Whether an unauthorised `status=archived` list request is a 403 or coerced to `active` (D-89) — pick one, test both the refusal and the positive control.
- The race where a community is archived while the admin is composing: the D-99 transaction refuses; the composer shows a legible pt-BR error and lets the admin re-pick or publish with no community.
- Chip component choice (existing `Tabs`/segmented control from `@tria/ui` vs. a chip row) and the `+` icon-button breakpoint for D-86 — the UI-SPEC step settles both from the design system.
- pt-BR copy for new strings (`Ativas`, `Arquivadas`, `Reativar`, the reactivate confirm, `Publicar em`, `Nenhuma comunidade`) in the existing `communities` / `stories` catalogs.

</decisions>

## Existing Code Insights

### Reusable Assets
- `packages/modules/communities/ui/CommunityPickerSheet.tsx`: the one community-row sheet behind both "Publicar em" and "Fixar em"; the check-mark/`onSelect` variant is the story composer's picker (D-95). The host prepends the "none" row.
- `packages/modules/stories/ui/StoriesStrip.tsx`: already renders the admin's leading circle when the bootstrap carries `stories.story.publish` — the Destaques row is the same component (`StoriesSurface`, `ringVariant="neutral"`), so D-92 is a prop/href on it, not a new circle.
- `apps/web/app/(app)/criar/page.tsx`: the `?comunidade=` server-side read — first value wins, validated against `listAllCommunities()`, silent fallback to null. D-93 copies this for `/stories/publicar`.
- `StatusPill` + `communities.archived.pill` ("Arquivada") and the archived note already render on the community page.

### Established Patterns
- Authorisation by composed PERMISSION, never role: `communities.community.manage`, `stories.story.publish`, `feed.post.create` read off the bootstrap and re-enforced by the API's `requirePermission`.
- Keyset paging with an over-fetch-by-one cursor whose value is read back from the projection (`listCommunities`, `packages/core/server/paging.ts`, `@tria/ui` `InfiniteScroll`).
- Entry points to full-screen routes are LINKS, not buttons (the `ComposeFab` / `createCta` rule).
- Events are queued with `emit` after `withTenantTx` resolves (MOD-03).

### Integration Points
- `apps/web/app/(app)/comunidades/CommunitiesList.tsx:153-193` — `createCta` built but only rendered in the empty branch (criterion 1); chips + status-aware load-more go here.
- `apps/web/app/(app)/comunidades/page.tsx` + `apps/web/lib/communities.ts` — `loadCommunities()` gains a status argument.
- `packages/modules/communities/server/service.ts:137` — `listCommunities` hard-codes `status = 'active'` (criterion 2); routes.ts query schema gains the status filter.
- `apps/web/app/(app)/comunidades/[communityId]/page.tsx` — the `highlights` render (renders nothing when empty) and the archived note (D-90 Reativar); the reactivate write reuses the existing status-write route/action used by `CommunityForm`.
- `apps/web/app/(app)/stories/publicar/page.tsx` + `StoryComposer.tsx` — reads `searchParams.comunidade`, loads the community list, adds the D-97 row; post-publish `router.push('/inicio')` (lines 169, 180, 458) becomes origin-aware (D-94).
- `packages/modules/stories/server/service.ts` `publishStory` (~line 333) — pin insert inside the same `withTenantTx`, reusing `resolvePinTarget`'s checks (~line 974); `packages/modules/stories/contracts` publish schema gains the optional field; `apps/web/app/(app)/stories/story-actions.ts` `publishStoryAction` passes it through.
- Module boundary: the stories module already reads community status for pins via its own query; no new cross-module import is introduced (MOD-02).

## Specific Ideas

- The tester's own words for criterion 2: "ver as que foram arquivadas com uma tag pra pessoa conseguir entrar sem ter que decorar um id". The filter keeps the tag (`Arquivada` pill) and adds the "find it" half.
- The composer row should read like the post composer's "Publicar em" so the admin sees one concept in two places.
- UAT for this phase should replay the three Phase 5 reports end to end on a phone: create a second community from a non-empty list; archive one, find it under `Arquivadas`, reactivate it from its page; publish a story from a community page and see it in both the home strip and that community's Destaques.
