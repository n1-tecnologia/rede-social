## Summary

This is a narrow, code-only pass, as the user asked at the research gate. No library or ecosystem research was done and **no new package is installed**. Every mechanism the phase needs already exists. The phase adds one optional field to the publish contract, one query parameter to the community list, a new pin-row write inside the existing publish transaction, and controls on three existing screens.

I re-checked every file:line reference from the ROADMAP and from CONTEXT.md `<code_context>` against the current tree (it now includes plans 05-09..05-12 and quick task 260924-fwv). Most still hold. Five need correcting, and the planner must not inherit them. **(1)** `CommunityCard` has **no** status-pill slot, so D-88's "cards carrying the existing Arquivada pill" needs a new optional prop on a module UI component. **(2)** `/stories/publicar/page.tsx` does **not** read `searchParams` today; the `?comunidade=` read has to be added (copied from `/criar/page.tsx`). **(3)** `resolvePinTarget` is defined at `service.ts:912-935`; `~974` is the line where `pinStory` calls it. **(4)** The shared `communityProjection` does not select `updated_at`, so D-91's archived cursor needs an extra column that must stay off the wire. **(5)** The ROADMAP's "non-empty branch (line 193+)" actually starts at `} else {` on line 194.

Three findings outrank the wiring itself. **First, a privilege seam:** today pinning requires `stories.story.manage` and publishing requires only `stories.story.publish`. The contracts say these are separate so that V2 can give members `publish` without the moderation half. If D-99's in-transaction pin is guarded only by the publish route's `requirePermission('stories.story.publish')`, pinning becomes reachable through publish. **Second, the automated suites are not isolated from the real Mux environment:** `apps/api/vitest.config.ts` copies *every* key of `apps/api/.env.local` into `test.env`, and `VIDEO_PROVIDER` is not in the list of keys an exported variable can override. I checked empirically that a Vitest `test.env` value beats an exported variable, so `VIDEO_PROVIDER=fake pnpm test:integration` does **not** force the fake provider today. **Third, the local database has drifted from the seed** because of manual UAT (a renamed community, extra stories): 8 of 90 existing communities/stories integration cases fail on it right now, so every validation run must begin with a reset and seed.

**Primary recommendation:** plan in three waves. Wave 0 test hygiene: pin `VIDEO_PROVIDER=fake` in the API Vitest env, and add a reset+seed checkpoint. API wave: list `status` filter plus publish `communityId`, each with its permission guard and integration tests. Web wave: `/comunidades` title-row CTA + chips, the community page `+` circle + Reativar, and the composer "Publicar em" row seeded from `?comunidade=`. Build criteria 3 and 5 as the single mechanism the ROADMAP demands: one selector, pre-filled from the query string.

### Locked Decisions

### Create-community CTA (criterion 1)
- **D-86:** `/comunidades` renders a **"Criar comunidade" control in the title row**, right of the `Comunidades` heading — a compact brand button (an icon-only `+` with an accessible label is acceptable on narrow phones), present in BOTH the empty and non-empty states, same on phone and desktop. - **D-87:** The **empty state keeps its own "Criar comunidade" action** (D-77 unchanged). Two routes to one form on the empty screen is fine.

### Archived communities in the list (criterion 2)
- **D-88:** Archived communities live behind **two filter chips under the heading — `Ativas` (default) / `Arquivadas`** — shown only to managers. `Ativas` is today's list, unchanged. `Arquivadas` renders the same `CommunityCard`s carrying the existing `Arquivada` pill (`communities.archived.pill`). Each chip is its own keyset query with a single `status` predicate, so the cursor never spans two statuses. Rejected: inline mixed list (the tester's literal wording, but it needs a two-status ordering in one keyset), and interleaving by activity (dead communities between live ones).
- **D-89:** **Only callers with `communities.community.manage` can list archived communities, and the API enforces it** — the list endpoint takes a status filter, and asking for `archived` without the permission is refused (or silently coerced to active; planner picks and pins with a test), never served. Members' `/comunidades` is byte-for-byte today's. The archived community PAGE by direct link keeps its shipped behaviour.
- **D-90:** **Reactivation is one tap from the archived community page**: the existing archived note under the header (`communities.page.archived` / `archived.note`) gains a **`Reativar` action with a confirm**, visible only to managers. The edit-form control (`CommunityForm.tsx:458-470`) stays as a second route. Rejected: a button on each list card (a second tap target inside a card that is itself a link).
- **D-91:** `Arquivadas` is ordered **most recently archived first**. There is no `archived_at` column and none is added (no schema change), so the order is `updated_at desc, id desc` — equal to archive time unless an archived community is edited afterwards, which is accepted. No new index: the archived set is small, and the planner confirms this rather than adding a migration. The cursor carries `updated_at` read back from the projection (the `listCommunities` precision rule).

### Story from a community page (criterion 3)
- **D-92:** The admin starts a community story from a **leading `+` circle in that community's Destaques row** — the same "Seu story" circle D-80 put on the home strip — linking to **`/stories/publicar?comunidade={id}`**. It sits exactly where the result will appear. For a caller with `stories.story.publish`, the Destaques section **renders even with zero pins** (the `+` alone); for members it still renders nothing when empty. Rejected: the post FAB opening a Post/Story choice (taxes every post with a tap), a second header icon (easy to miss).
- **D-93:** An **archived community offers no story entry at all** — not a disabled one (UI-D-37's rule for posts, restated for stories; pinning to an archived community is already refused with `pin: 'archived'`). The composer treats a `?comunidade=` that is unknown, another tenant's, or archived exactly like `/criar` does: it **silently falls back to "Nenhuma comunidade"** (first value wins if repeated).
- **D-94:** After publishing from a community origin, the admin **lands back on `/comunidades/{id}`**, where the new circle in Destaques confirms the attachment. Publishing with no community context keeps today's `/inicio` destination. The discard/close path from a community origin also returns to the community.

### Composer community choice (criteria 4 and 5)
- **D-95:** The composer attaches a story to **one community or none** — the post's "Publicar em" model exactly. It reuses **`CommunityPickerSheet`** in its check-mark (`onSelect`) variant with a leading **`Nenhuma comunidade`** row supplied by the host (the picker ships no words). Additional communities are still pinned afterwards in `/stories/meus`. Rejected: multi-select in the composer (array contract + switch UI for a rare case the pin sheet already covers).
- **D-96:** A story published into a community **still appears in the home strip for its 24 h** AND stays in that community's Destaques after expiry. The community is where the story *also stays*, not where it is hidden — the same rule as D-73 (community posts appear in the main feed), and identical to what a post-hoc pin already produces. The strip predicate does not change. — **Reversibility:** costly — hiding community stories from the strip later would make "born pinned" and "pinned later" behave differently, and would need a strip predicate the viewer's sequence and its tests depend on.
- **D-97:** The choice is a **`Publicar em: {Nenhuma comunidade | nome} ›` row in the composer's bottom bar, above `Publicar`**, next to the caption, opening the sheet. It is visible before publishing (criterion 5: stated up front), costs zero taps when the default is right, and is never a mandatory step. Rejected: a chip over the media (overlaps the preview), a pre-publish step (adds a tap to every tenant-wide story, violating "no community must not get harder").
- **D-98:** The "no community" label is **`Nenhuma comunidade`**, not "Feed principal" — a story has no feed, and a tenant-wide story is still in the strip either way.
- **D-99:** **One write, one transaction.** `publishStory` accepts an optional community id; the story insert and the `story_community_pins` insert happen inside the SAME `withTenantTx`, with the same target checks `pinStory` already applies (tenant-scoped, not deleted, `status = 'active'`, else refuse with the existing `pin: 'archived'` / bare 404 shapes). No client-side "publish then pin" sequence exists anywhere. — **Reversibility:** reversible — additive optional field on the publish contract.

- **Route guards.** `POST /` uses `requirePermission('stories.story.publish')` (`routes.ts:155-179`). `PUT|DELETE /{storyId}/pins/{communityId}` and `GET /{storyId}/pins` use `requirePermission('stories.story.manage')` (`:348-392`). The publish route's documented responses are 201, 400 `details.story`, 403 and 404 for the asset.
- **`publishStory` transaction** (`service.ts:333-403`). Inside one `withTenantTx`: (1) asset lookup `select kind, purpose from media_assets where id = ? and tenant_id = ? and deleted_at is null` → missing gives a bare 404; wrong purpose/kind gives `400 { story: 'media_invalid' }`. (2) `insert into stories (tenant_id, author_user_id, media_asset_id, media_kind, caption) … returning id`. (3) Projection read-back. After the transaction: `emit(ctx, 'story.published', {…})` and a shape-only log. A processing video is accepted.
- **Pin target rules** (`resolvePinTarget`, `:912-935`). This is one statement joining `stories s` to `communities c on c.id = ? and c.tenant_id = ? and c.deleted_at is null where s.id = ? and s.tenant_id = ? and s.deleted_at is null`. No row gives a **bare `404 NOT_FOUND`**. Then `pinStory` refuses `target.community_status !== 'active'` with `ApiError(400, 'VALIDATION_FAILED', { pin: 'archived' })` (`:975-977`).
- **Pin write** (`:979-986`). `insert into story_community_pins (tenant_id, story_id, community_id, pinned_by_user_id) values (…) on conflict (story_id, community_id) do nothing returning id`. `story.pinned` fires only when `inserted.length > 0` (`:994-1001`).
- **Destaques read** (`listCommunityHighlights`, `:1106-1157`). It carries **no expiry predicate and no readiness filter**, and orders by `p.pinned_at desc, p.id desc`. A born-pinned story therefore appears on the community page immediately, even while its image variants are still processing (it renders a neutral box meanwhile). The home strip *does* filter on readiness (R-P8), so the strip half of D-96 needs the worker in e2e.
- **Web publish path.** `publishStoryAction(input)` → `publishStorySchema.safeParse` → `attemptStoryPublish` (`lib/stories.ts:135-156`) → `revalidatePath('/inicio')` (`story-actions.ts:53-67`). The refusal mapper `storyWriteIssue` reads **only** `details.story` and maps a 404 to `not_found` (`lib/stories.ts:120-125`). A `details.pin = 'archived'` answer from publish would therefore surface as `generic` unless the mapper is extended. `storyPinIssue` (`:378-385`) already reads `details.pin`.
- **Composer.** `StoryComposer({ historyHref })` (`StoryComposer.tsx:44-47,74`) sends `{ mediaAssetId, mediaKind, caption }` (`:159-163`). The error union is `StoryIssue | 'not_found' | 'generic'` (`:141-149`). The bottom bar (`:402-440`) holds the caption textarea and `Publicar` and exists **only after a pick** (the post-pick black frame). The pre-pick state has no bottom bar and no `Publicar` control.
- **Post precedent (`/criar`).** `ComposerForm` keeps `communityId` state (`null` = default). It sends `...(communityId ? { communityId } : {})`, omitting the key rather than sending `null` (`ComposerForm.tsx:445-448`). The sheet is `CommunityPickerSheet` with `onSelect` + `Check` trailing and a host-built `leadingRow` default row (`:936-984`). On the API side, `createPost` resolves the destination **first** inside the transaction: `if (communityId !== null) await resolveCommunityTarget(ctx, tx, communityId);` before assets (`feed/server/service.ts:694-699`). That function refuses archived with `{ community: 'archived' }` (`:651-652`). `createPostSchema.communityId` is `z.uuid().optional()` (`feed/contracts/index.ts:201`). `PostPublished` carries `communityId: string | null` (`:502-508`).

### Pattern 1: A guarded query parameter on an unguarded list route (C2, D-89)
**What:** keep `listRoute` open to every member. When `status === 'archived'`, check the composed permission inside the handler with the kernel's own resolver, the same one `requirePermission` uses.
**Why this and not a second route:** `permissionsForRequest(ctx)` is exported from `@tria/core/server/rbac/permissions` and is exactly what the middleware evaluates (`permissions.ts:40-48,60-69`). No caller outside the middleware uses it yet, so this is its first direct use. [VERIFIED: grep this session, only `permissions.ts` references it]
**Example (sketch; `permissionsForRequest`, `ApiError(403, 'FORBIDDEN')` and the literal permission are verbatim from the files cited):**
```ts
// communities/server/routes.ts — listRoute handler
.openapi(listRoute, async (c) => {
  const ctx = c.get('ctx');
  const query = c.req.valid('query');
  if (query.status === 'archived') {
    const granted = await permissionsForRequest(ctx);
    if (!granted.includes('communities.community.manage')) throw new ApiError(403, 'FORBIDDEN');
  }
  return c.json(await listCommunities(ctx, query), 200);
})
```
**Recommendation for the D-89 discretion item:** the API returns **403**, and the web tier **coerces**. The page passes `status` to the API only when `canManage`, so a member who opens a shared `/comunidades?status=arquivadas` link sees today's active list and never an error card. A crafted API call gets an explicit 403 that a test can pin, which matches `requirePermission`'s answer everywhere else. Test both: member → 403; admin → 200 with only archived rows (positive control).

### Pattern 2: Two literal status branches in one statement (C2, D-91)
**What:** choose the predicate and ordering in TypeScript as two **literal** SQL fragments. Do not bind `status` as a parameter.
**Why:** the active branch must stay byte-identical to today's statement, which is what pgTAP case 15 ("the LIST predicate, verbatim from `listCommunities`") and cases 17-18 (`communities_tenant_activity_idx`, no seq scan) assert. A literal `c.status = 'active'` is provably implied by the partial index predicate `status = 'active' and deleted_at is null`. Whether the planner can prove that implication for a *bound parameter* depends on custom-vs-generic plan choice [ASSUMED]. Literals remove the question.
**Cursor:** the archived branch orders by `c.updated_at desc, c.id desc`, and its cursor `n` must be `updated_at` formatted by `ISO_MICROSECONDS` in SQL, for the same reason `last_activity_at` is (`service.ts:49-60`). Add it as an **extra selected column** used only for the cursor. Do **not** add it to `toCommunity` or `communitySummarySchema` (see Pitfall 3). The `extra` projection pattern already exists in the stories module (`storyProjection(viewerUserId, extra)`, `stories/server/service.ts:107-110,1118-1122`).

### Pattern 3: Born-pinned story, one transaction (C4, D-99)
**What:** the target check comes first, then the story insert, then the pin insert, all in one `withTenantTx`, and the events go out after commit.
**Recommended statement order** (mirrors the post precedent `feed/server/service.ts:697-699`, "a refused destination must cost neither an asset validation … and it must be the first thing the caller is told"):
1. `if (input.communityId)`: a community lookup with **the identical predicate** `resolvePinTarget` joins on (`c.id = ?::uuid and c.tenant_id = ?::uuid and c.deleted_at is null`). No row gives `ApiError(404, 'NOT_FOUND')` (bare). `status !== 'active'` gives `ApiError(400, 'VALIDATION_FAILED', { pin: 'archived' })`.
2. Asset lookup (unchanged).
3. `insert into stories …` (unchanged).
4. `if (input.communityId)`: the pin insert with the same column list as `pinStory` (`tenant_id, story_id, community_id, pinned_by_user_id`). Extract the INSERT into one helper that both `pinStory` and `publishStory` call, so the pin row is written by exactly one statement text.
5. Projection read-back (unchanged).

With no `communityId`, the statement sequence stays exactly (asset, insert, projection). That keeps `packages/modules/stories/tests/events.test.ts`'s order-based mock (`executeCall === 1/2/3`, `:57-66`) green. **Alternative:** call `resolvePinTarget(tx, ctx, newStoryId, communityId)` verbatim *after* step 3. This literally reuses the function, but a refusal then comes after a (rolled-back) insert, and the unit mock needs a fourth branch. Either satisfies D-99; pick one and say which in the plan.

**Events (Claude's discretion):** recommend emitting `story.published` **unchanged**, plus `story.pinned` (the existing `StoryPinned` shape, `actorUserId: ctx.userId`) once, after commit, only when a pin row was written. Rationale: (a) a subscriber that tracks pins sees every pin through one event whichever path created it, which is D-96's "born pinned ≡ pinned later"; (b) the key-set assertions on `story.published` (`events.test.ts:134-140`, `stories.test.ts:411-417`) stay untouched; (c) the "counted twice" worry does not apply to the history screen, which counts `story_community_pins` rows (`readPinnedCount`, `service.ts:938-944`; `pinned_community_count` in the projection), not events. The alternative is to add `communityId: string | null` to `StoryPublished`, following the `PostPublished` precedent. It is also valid, but it changes two pinned key-set assertions and gives pin-tracking subscribers two sources. **Phase 7 caveat:** if Phase 7 turns `story.pinned` into a member notification, a born-pinned story would produce "new story" + "pinned" notifications. Record this in the plan's decisions so Phase 7 dedupes by `storyId` or ignores pin events for notifications. [ASSUMED: Phase 7's consumer design]

### Pattern 4: `?comunidade=` → pre-filled selector (C3 + C5 as one mechanism)
Copy `criar/page.tsx:47-53` into `stories/publicar/page.tsx`: `searchParams: Promise<{ comunidade?: string | string[] }>`, first value wins, matched against `listAllCommunities()` (active only, so archived, unknown and cross-tenant all fall back to `null`, which is D-93). Pass `communities` (mapped to `CommunityPickerRow` with `coverAlt` from the catalog) and `initialCommunityId` to `StoryComposer`. The composer keeps `communityId` state exactly like `ComposerForm` (`:193-196`). It sends `...(communityId ? { communityId } : {})` so the no-community body stays `{ mediaAssetId, mediaKind, caption }` (this keeps `StoryComposer.test.tsx` case 4 green). The origin for D-94 is `initialCommunityId`.

### Pattern 5: The Destaques `+` is the existing `own` prop (D-92)
On the community page, compute `canPublishHere = bootstrap.permissions.includes(STORY_PERMISSIONS.publish) && !archived` (Open Question 1 RESOLVED that way: `&& …manage` is added, `05.1-05-PLAN.md` Task 2). Render the `<section>` + `SectionTitle` when `highlightItems.length > 0 || canPublishHere`, and pass `own={canPublishHere ? { href: \`/stories/publicar?comunidade=${community.id}\`, … } : undefined}` to `StoriesSurface`. `StoriesStrip` already renders an own-only row when `items` is empty (`:93`, test `stories-strip.test.tsx` case 2). Members keep today's behaviour because `own` is undefined and the list is empty, so the component returns `null`. The permission is composed only from *enabled* modules (`registry.ts:91-111`), so a tenant with stories OFF never shows the `+`.

### Anti-Patterns to Avoid
- **Client-side publish-then-pin.** D-99 forbids it. Do not call `pinStoryAction` after `publishStoryAction` anywhere.
- **A second picker component.** Reuse `CommunityPickerSheet`. The host supplies the "Nenhuma comunidade" `leadingRow`; the module ships no words (`CommunityPickerSheet.tsx:18-27`).
- **Adding a field to `communitySummarySchema` or to the publish *response*.** Both are `.strict()` and parsed by the web, so a skewed deploy breaks parsing (Pitfall 3).
- **A button inside `CommunityCard`.** D-90 rejects it; the card is itself a link.
- **`IconButton` for the create control.** It is a `<button>`, and D-86 requires a link.
- **Binding `status` as a SQL parameter.** See Pattern 2.
- **Importing `@tria/module-communities` from `packages/modules/stories`.** `turbo boundaries` denies it; use raw SQL like `resolvePinTarget`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Keyset cursor for the archived list | A new envelope or offset paging | `encodeCursor`/`decodeCursor` from `@tria/core/server/paging` | Total decode, versioned envelope, one implementation (R-11) |
| Permission check in a handler | Role comparison or re-reading memberships | `permissionsForRequest(ctx)` | Same composed set the middleware and `bootstrap.permissions` read |
| Community picker for stories | New sheet | `CommunityPickerSheet` (`onSelect` + `Check` + `leadingRow`) | UI-D-45/UI-D-41 already share it |
| `?comunidade=` validation | Client fetch or UUID regex | `listAllCommunities()` membership test on the server | Handles unknown, foreign and archived in one rule |

| Pin idempotency | Pre-check select | `story_community_pins_uq` + `on conflict … do nothing` | DB is the arbiter (T-05-49 posture) |

## Common Pitfalls

### Pitfall 1: Publish becomes a pin backdoor (privilege seam)
**What goes wrong:** `POST /v1/stories` is guarded by `stories.story.publish` only. If it now writes a pin row, any holder of `publish` can pin, although pinning is documented as a `manage` act (`contracts/index.ts:209-215`; pin routes `routes.ts:348-392`).
**Why it happens:** in V1 `admin_tenant` holds both (`stories/module.ts:94-96`), so no V1 test can observe the gap.
**How to avoid:** when `communityId` is present, also require `stories.story.manage` (403 `FORBIDDEN` through `permissionsForRequest`), and gate the composer row and the Destaques `+` on the same pair. Or record an explicit product decision that attaching at publish is a *publishing* act, as it is for posts (`feed.post.create` alone allows community posts). This is Open Question 1 (RESOLVED: the first route is adopted, see Open Questions).
**Warning signs:** a test that passes a role with `publish` but not `manage` and expects 201 with a pin row. Testing this needs a temporary resolver: `setPermissionResolver` is documented as "Last registration wins (tests)" (`permissions.ts:28-31`) and no test uses it yet.

### Pitfall 2: The integration suite silently runs against real Mux
**What goes wrong:** `apps/api/vitest.config.ts` builds `test.env` as `{ ...defaults, ...readEnvFile(), ...fromProcess }`. `readEnvFile()` returns **every** key in `apps/api/.env.local` (`:11-31`), while `fromProcess` rescues only the `KEYS` list (`:33-48`), which does **not** contain `VIDEO_PROVIDER` or `MUX_*`. Vitest's `test.env` overrides an exported variable. Probe run this session with the repo's Vitest 5.0.0 (`PROBE_VAR=from-process`, config `env: { PROBE_VAR: 'from-config' }`):
```
Expected: "__show__"
Received: "from-config"
```
So with the current local `.env.local` (`VIDEO_PROVIDER=mux` per memory), the in-worker app builds `createMuxVideoProvider` (`packages/core/server/media/video/index.ts:36-45`). Tests asserting `provider === 'fake'` (e.g. `mux-webhook.test.ts:269,278,309`) fail, and paths that mint video uploads would call the real Mux Development API.
**How to avoid (Wave 0):** force `VIDEO_PROVIDER: 'fake'` as the **last** spread in `apps/api/vitest.config.ts` `test.env` (tests never want a vendor), or add `VIDEO_PROVIDER` to `KEYS` and export it in every command. The first is safer because it holds no matter which command is typed.
**Where exported variables DO win:** `node --env-file-if-exists` and `process.loadEnvFile` do not override an already-set variable. Probe on Node v24.14.0: `loadEnvFile: from-process`, `--env-file: from-process`. So for Playwright's API webServer (`pnpm --filter @tria/api dev` = `tsx watch --env-file-if-exists=.env.local`), the e2e worker (`e2e/worker.ts:47-49`) and the integration global-setup listener (`global-setup.ts:29-30`), `VIDEO_PROVIDER=fake <cmd>` works, **unless an API is already listening on 8787**. Playwright's `reuseExistingServer: true` (`playwright.config.ts:62-66`) would then reuse the developer's Mux-configured server. (That tsx passes `--env-file` through with Node semantics is [ASSUMED]; the Node behaviour itself was probed.)
**Warning signs:** `provider: 'mux'` in any automated log; Mux dashboard assets appearing during test runs.

### Pitfall 3: Deploy skew against `.strict()` contracts
**What goes wrong:** `communitySummarySchema`, `communityPageSchema`, `publishStorySchema` and `storySummarySchema` are all `.strict()` and shared by API and web, which deploy separately (Cloud Run vs Vercel). An API response with a new key fails the old web's `parse`; a web request with `communityId` or `status` fails an old API's validation with a 400.
**How to avoid:** add no response fields (keep the archived cursor column off the wire; do not echo `communityId` in the publish response). Ship API before web; this is local-only now, since cloud is deferred, but record the order for Phase 01.1.
**Warning signs:** `ZodError: Unrecognized key` in web logs.

### Pitfall 4: Seed drift makes the existing suites red before any change
**What goes wrong:** the local DB was modified by manual UAT. Running `communities.test.ts` + `stories.test.ts` this session gave **8 failed / 82 passed**. Example: communities case 1 received `"Avisos da diretoria renomeado Avisos da diretoria renomeado Avisos da diretoria"` where the seed name was expected.
**How to avoid:** every validation run starts with `pnpm db:reset && pnpm db:seed` (the root `verify` script already does this before e2e). **This wipes the user's manual Mux-backed test data**, so make it a `checkpoint:human-verify` before the first reset.
**Warning signs:** seed-fixture cases (communities 1-2, stories 1, 4-8) failing on untouched code.

### Pitfall 5: Order-based unit mocks
**What goes wrong:** `stories/tests/events.test.ts` answers `tx.execute` by call index (1 = asset, 2 = insert id, 3 = projection). An extra statement on the no-community path shifts every answer.
**How to avoid:** issue the community statements only when `communityId` is present, and add a separate mock branch or test for the community path.

### Pitfall 6: The active list's index plan regresses
**What goes wrong:** parameterising `status`, or merging the two orderings into one statement, can stop the planner using `communities_tenant_activity_idx`. pgTAP cases 17-18 then fail, or worse, pass on a different statement than the service runs.
**How to avoid:** Pattern 2 (two literal branches). Keep pgTAP case 15's predicate verbatim. If a pgTAP case is added for the archived predicate, bump `select plan(58);` accordingly.

### Pitfall 7: The web cannot say why a community publish failed
**What goes wrong:** `storyWriteIssue` reads only `details.story`, so the `{ pin: 'archived' }` refusal for the archived-while-composing race becomes `generic` ("Não foi possível publicar seu story").
**How to avoid:** extend the `StoryWriteResult` code union with `'archived'` (from `STORY_PIN_ISSUES`, reusing `STORY_PIN_ISSUE_SET`), map it to new pt-BR copy, and keep the picker open or re-selectable. A bare 404 stays ambiguous between asset and community. That is acceptable and conservative, since V1 has no community delete UI.

### Pitfall 8: Router cache after publish or reactivate
**What goes wrong:** landing on a page the client Router Cache still holds shows stale Destaques or a stale archived note.
**How to avoid:** the composer already pairs `router.push` with `router.refresh()` for exactly this reason (`StoryComposer.tsx:168-175`). Do the same for the community origin, and add `revalidatePath(\`/comunidades/${communityId}\`)` to `publishStoryAction` when a community was attached. After Reativar on the page, call `router.refresh()`.

### Pitfall 9: The status choice is lost on refresh and load-more
**What goes wrong:** `refreshCommunitiesAction()` and `loadMoreCommunitiesAction(cursor)` take no status. Pulling to refresh on `Arquivadas` would replace the list with active communities.
**How to avoid:** thread `status` through both actions, validated by the extended `communityQuerySchema`. The server-action argument is untrusted, but the API enforces D-89 anyway.
