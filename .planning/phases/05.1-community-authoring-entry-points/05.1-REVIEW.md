## Narrative Findings (AI reviewer)

## Summary

I reviewed the diff from `16b8cdd^..HEAD` across the 37 files, focusing on the areas the orchestrator asked about.

**Tenant isolation holds.** The archived list keeps the explicit `c.tenant_id = ctx.tenantId` predicate under RLS. The born-attached publish reads the destination with the tenant predicate (`resolvePublishCommunity`) and writes the pin with `ctx.tenantId`. A foreign, unknown or removed community gets one bare 404 with no `details`. `isolation.test.ts` b6 and `communities.test.ts` case 40 pin these with positive controls.

**The permission gates are in the right places.** `status=archived` is refused with 403 unless the caller holds `communities.community.manage`. The route checks this with the same resolver `requirePermission` uses. A publish that carries `communityId` requires `stories.story.manage` before any lookup, so a publish-only caller cannot learn anything about the id. The web tier offers the destination row, the `?comunidade=` pre-fill and the Destaques `+` only to viewers who hold both `publish` and `manage`.

**The born-attached publish is atomic.** The community lookup, story insert, pin insert and projection all run in one `withTenantTx`. Events are queued only after it resolves, and the integration tests show a refusal writes nothing.

**The archived-list query is correct.** Keyset is `(updated_at, id) desc` with a microsecond-formatted cursor. The only writer of `communities.updated_at` is `updateCommunity`; the post-count trigger touches only `post_count` and `last_activity_at`. So "most recently archived first" holds and pages cannot repeat rows.

No BLOCKER-level defect was found. Remaining concerns:
- A lookup-then-write race lets a story be pinned to a community that is being archived at the same moment.
- A crafted cursor can still produce a 500 (the new branch copies an existing gap).
- The composer can get stuck on a non-archived refusal of the destination.

## Warnings

### WR-01: Born-attached publish can pin a story to a community archived concurrently (unlocked read, then write)

**File:** `packages/modules/stories/server/service.ts:367-371, 1036-1050` (also `resolvePinTarget`, `:956-979`)
**Issue:** `resolvePublishCommunity` reads `c.status` with a plain `select`, `assertCommunityPinnable` checks it, and only later does `insertStoryPin` write the row. At READ COMMITTED, a concurrent `updateCommunity(..., { status: 'archived' })` can commit between the status read and the pin insert. The publish then commits a new pin into an archived community, which breaks the rule the phase enforces ("an archived container takes no new content", D-99 / `pin: 'archived'`). The FK `story_community_pins_community_fk` does not help: its check takes only a `KEY SHARE` lock, which does not conflict with the archive's non-key `UPDATE`. No trigger or constraint on `story_community_pins` backstops this. The window is small, but the new write path widens it. It runs community → asset lookup → story insert → pin, all between the status read and the pin write. The same pattern exists in `pinStory` and in feed `createPost` (`feed/server/service.ts:644`), so this is systemic.
**Fix:** Lock the community row for the rest of the transaction so an archive either waits for the publish or is seen by it. In READ COMMITTED, a `FOR SHARE` re-read returns the committed `archived` version:
```ts
const rows = await tx.execute<{ status: string }>(sql`
  select c.status
    from communities c
   where c.id = ${communityId}::uuid
     and c.tenant_id = ${ctx.tenantId}::uuid
     and c.deleted_at is null
   limit 1
   for share`);
```
Apply the same fix to `resolvePinTarget` (`... limit 1 for share of c`) so both pin write paths share the guarantee. Optionally add a pgTAP or integration test with two connections that interleave the archive and the publish.

### WR-02: A crafted cursor with a non-timestamp `n` returns 500 on the new archived branch (the "decodeCursor is TOTAL" claim is false)

**File:** `packages/modules/communities/server/service.ts:161-181` (with `packages/core/server/paging.ts:30`)
**Issue:** `cursorSchema` validates `n` only as `z.string()`. The cursor is unsigned base64url JSON, so a caller can send `{"v":1,"n":"x","id":"<any uuid>"}`. It passes `decodeCursor`, and `${afterAt}::timestamptz` then raises Postgres `22007 invalid_datetime_format`. That surfaces as 500 INTERNAL, not the "degrades to page 1" behaviour the docblock promises (T-05-05). No rows leak, but it is an unhandled error any authenticated member can trigger on the active list, and any manager on the archived list. The new branch copies the gap from the active branch. The integration suite tests only a non-base64 cursor (`communities.test.ts:271`), which never reaches SQL.
**Fix:** Validate the ordering key before it reaches SQL and treat a bad value as "no cursor":
```ts
const after = decodeCursor(query.cursor);
const validAt = after && !Number.isNaN(Date.parse(after.n)) ? after : null;
const afterAt = validAt?.n ?? null;
const afterId = validAt?.id ?? null;
```
A better fix is a per-call key schema (for example `z.iso.datetime({ offset: true })`) in `decodeCursor`'s callers. Add an integration case that sends a well-formed envelope whose `n` is not a timestamp, on both statuses, and expects 200 page 1.

### WR-03: StoryComposer keeps a refused destination on 404/403, so the admin can retry forever

**File:** `apps/web/app/(app)/stories/publicar/StoryComposer.tsx:237-249`
**Issue:** Only `archived` resets the selection (UI-D-58). Every other refusal keeps `selectedId` and shows the generic "Não foi possível publicar seu story" (`refusalCopy`). Two refusals are caused by the destination itself:
- A 404 when the chosen community was soft-deleted after the composer loaded.
- A 403 FORBIDDEN when `stories.story.manage` was withdrawn mid-session. `bootstrapRedirectPath` returns null for `FORBIDDEN`, so there is no navigation either.

In both cases every retry sends the same `communityId` and fails the same way. Nothing tells the admin that the destination is the problem, and the media and caption are stranded until they guess to switch to "Nenhuma comunidade".
**Fix:** When the failed publish carried a destination and the code is `not_found` (or the action surfaces a `forbidden` code for 403), do what the archived branch does: add the id to `refused`, reset `selectedId` to null and show a destination-specific message. Alternatively, have `attemptStoryPublish` map a 403 on a body with `communityId` to a distinct code the composer can act on.

## Info

### IN-01: `?comunidade=` silently falls back to "none" past the picker ceiling

**File:** `apps/web/app/(app)/stories/publicar/page.tsx:58-68`, `apps/web/lib/communities.ts` (`PICKER_MAX_PAGES = 10`, `COMMUNITY_MAX_PAGE_SIZE = 25`)
**Issue:** The requested id is resolved only against `listAllCommunities()`, which stops after 250 active communities. On a tenant with more, the community page's `+` ("Publicar um story em {community}") opens a composer that is not addressed to that community, and closing it returns to `/inicio` instead of the community. The row does visibly read "Nenhuma comunidade", so this is not silent mis-publishing.
**Fix:** When `requested` is a uuid not in `communities`, resolve it with `loadCommunity(requested)`. If that returns an active community, add it to `rows` and use it as `initialCommunityId`.

### IN-02: A publish with a destination does not check that the communities module is enabled

**File:** `packages/modules/stories/server/routes.ts:412-423`, `packages/modules/stories/server/service.ts:1036-1050`
**Issue:** The route checks `stories.story.manage` but not whether the tenant's `communities` module is enabled. Community rows can exist while the flag is off (the lab seed is an example), so a crafted body can pin a story to a community whose module is disabled. `pinStory` behaves the same way, so this is parity rather than a new regression, and it stays within the tenant.
**Fix:** If this matters, reject a destination when `moduleFlags.flags(ctx)` does not include `communities`, with the same bare 404.

### IN-03: The `publish` check in `canAttach` is redundant

**File:** `apps/web/app/(app)/stories/publicar/page.tsx:52-54`
**Issue:** The page has already redirected any viewer without `STORY_PERMISSIONS.publish` (line 49), so `bootstrap.permissions.includes(STORY_PERMISSIONS.publish)` inside `canAttach` is always true.
**Fix:** Reduce it to `bootstrap.permissions.includes(STORY_PERMISSIONS.manage)`, or keep it with a comment saying it mirrors the API's two-permission rule on purpose.

### IN-04: pgTAP case 16b does not test the archived ordering it names

**File:** `supabase/tests/110-communities-stories.sql:259-271`
**Issue:** The fixture has exactly one archived community, so `order by c.updated_at desc, c.id desc` cannot fail this assertion. The ordering and the tie-break are really covered by integration cases 36, 37 and 41, so the pgTAP case only proves the predicate.
**Fix:** Either reword the description to "predicate only", or add a second archived row with a different or equal `updated_at` so the order is actually asserted.
