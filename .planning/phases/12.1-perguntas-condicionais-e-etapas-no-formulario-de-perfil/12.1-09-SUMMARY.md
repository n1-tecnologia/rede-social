**Create in a step, move across steps, reorder questions and steps, reactivate, archive, delete and replace now all run on one global layout: one pure operation, a D-623 check against the conditions stored in the database, and a set-based renumber, with the legacy `{ ids }` body kept for one release.**

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug in the plan text] The layout-writer SQL of the plan is rejected by Postgres (relayed from plan 07)**
- **Found during:** Task 1 (read before writing)
- **Issue:** the plan's Task 1 action writes `from jsonb_to_recordset(<json>::jsonb) with ordinality as o(id uuid, step_id uuid, ord int)`. Postgres rejects it (SQLSTATE 42601, "WITH ORDINALITY cannot be used with a column definition list"; proved in `supabase/tests/225-profile-form-steps-conditions.sql`).
- **Fix:** `writeLayout` uses form (a) of plan 07: `from rows from (jsonb_to_recordset(<json>::jsonb) as (id uuid, step_id uuid)) with ordinality as o(id, step_id, ord)`, for questions, and the same shape with `(id uuid)` for steps. The rejected form is not used anywhere.
- **Files modified:** `packages/core/server/profile-form/layout-store.ts`
- **Commit:** `71052b75`

**2. [Rule 1 - Bug in the plan design] Locking every active row on every write broke the Phase 12 adjacency rule**
- **Found during:** Task 3 verification (`profile-form-concurrency.test.ts`: "a create, a reactivate and the reads did not wait for the save", and the next case timing out behind the held lock)
- **Issue:** the plan has `readLayout` take every active row `FOR UPDATE`. A member's save holds those rows `FOR SHARE`, so a create or a reactivation would wait for it; Phase 12 pins that they never do (only an edit of an active question waits).
- **Fix:** `readLayout` takes the rows only when asked (`lockRows`: a reorder and a move, which can change any question's place). `writeLayout` locks, in the member's canonical order, just the rows whose place actually changes, and an append to the very end of the form (create or reactivate whose question is last) writes nobody else, using `max(position) + 1` as Phase 12 did. Archive, delete and replace change only rows after their target (or none), so the ordered acquisition cannot cycle with a save's ordered share locks.
- **Files modified:** `packages/core/server/profile-form/layout-store.ts`, `packages/core/server/profile-form/admin.ts`
- **Verification:** `profile-form-concurrency.test.ts` 12 of 12 pass; Phase 12 `profile-form-admin.test.ts` (36) and `profile-form-lifecycle.test.ts` pass with NO edit to any Phase 12 assertion (an earlier edit of two assertions that pinned `max(position) + 1` was reverted once the append path kept that behaviour).
- **Commit:** `21be9ba6`

**3. [Rule 3 - Blocking] Fixture helper beyond the plan's list**
- `seedProfileFormQuestion` gains `conditionQuestionId` and `conditionValues` (the plan names this, in `setup.ts`). No other file outside `files_modified` changed.
