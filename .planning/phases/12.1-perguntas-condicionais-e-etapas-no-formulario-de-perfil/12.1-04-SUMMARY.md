# Phase 12.1 Plan 04: Pure condition, opener, lock and layout rules Summary

**Every condition, opener-change, reactivation, lock and layout refusal the admin services will state is now defined once in dependency-free TypeScript (`condition-rules.ts`, `layout.ts`), with the trigger codes PF006 and PF007 mapped to `condition_locked` and `has_dependents`.**

## Performance

- **Duration:** about 5 min (started 2026-11-05T19:47Z, finished about 19:52Z)
- **Tasks:** 3 of 3
- **Files:** 6 (4 created, 2 modified)
- **Commits:** 6 (three RED, three GREEN)

## Accomplishments

- `checkCondition` applies, in order and returning the first refusal: subject is not its own opener; opener present in the list and in the layout and active; opener type in `PROFILE_FORM_CONDITION_OPENER_TYPES`; opener carries no condition (D-622, a chain never passes, tested for three orders); subject is not an active opener; opener's flattened index is lower (`condition_order` naming `questionId` and `openerId`, D-623); values non-empty, unique, each a `'true'`/`'false'` or an option id (D-621, "Outro" has no id). A null condition (removal) is never checked.
- `checkConditionLock` (D-625) refuses a gained or changed condition on an answered question, comparing value sets without order and also the opener; removal and an unchanged condition pass at any answer count.
- `dependentsOf`, `checkOpenerChange` (archive, retype, removed option ids referenced by an active dependent, listing only the affected dependents) and `checkReactivation` (re-runs the condition; unknown question is `unknown_question`) state D-632 once.
- `layout.ts`: nine exported functions over one global sequence cut into steps; every operation returns a fresh layout or a coded refusal (`unknown_step`, `order_mismatch`, `step_not_empty`, `last_step`), proven on deep-frozen input; `renumber` gives 1..n over the flattened order including layouts with empty steps in the middle; `checkLayoutOrder` names the first violated pair.
- `GUARD_CODES` gained `PF006` and `PF007`; the header comment of `lock-rules.ts` says so. The only changed lines in that file are the comment and the two map entries.
