# Phase 12.1: Code Review Report

**Reviewed:** 2026-11-05T22:00:00Z
**Depth:** standard
**Files Reviewed:** 54 (Drizzle schema, 3 SQL migrations, core server, routes, web). TypePicker.tsx, e2e/profile-form.ts and e2e/affected-map.json were only skimmed (no logic of risk found).
**Status:** issues_found

## Summary

No structural (fallow) findings were supplied, so there is no "Structural Findings" section.

The security-critical surface holds up under adversarial reading:

- `app.profile_form_purge_closed()` is SECURITY DEFINER, `search_path = ''`, EXECUTE revoked from PUBLIC and granted only to `authenticated, api_user, service_role`. It accepts no argument and joins `memberships` on `app.tenant_id()` and `app.user_id()`, so it can only reach the caller's own answers in the caller's tenant (a session with no tenant claim matches nothing). All column references inside are qualified, so the `question_id` OUT parameter does not shadow anything.
- `app.profile_form_missing` keeps its signature, so `create or replace` preserves the `api_user, service_role` grants; the two short circuits are untouched. `app.profile_form_answer_tokens` is the exact SQL twin of the TypeScript `answerTokens` (boolean, `optionIds`, `optionId`, everything else empty; checked case by case, including a non-array `optionIds` falling through to `optionId`).
- Every new route carries `requireAuth` then `requireModule('profile_form')` then `requirePermission('profile_form.manage')`; the tenant always comes from `ctx.tenantId`; every write statement has an explicit `tenant_id` predicate; foreign ids are the bare 404 or the same `unknown_step`/`condition_invalid` as a missing id. All Zod bodies are `.strict()`. All dynamic SQL goes through bound parameters (`textArray`, `jsonb_array_elements_text`), and the only `sql.raw` is a constant.
- Lock order (steps `FOR UPDATE`, then questions in `position, created_at, id`; member `FOR SHARE` in the same order) and the per-tenant and per-member advisory locks do not form a cycle in any path I traced (create, update with and without move, reorder, archive, reactivate, replace, delete, delete step, member save).
- Server-side visibility is recomputed on every save from stored answers overlaid with the submitted openers, a value for a hidden question is dropped, and a closed answer (active or archived dependent) is purged in the same transaction. The web holds one copy of the rule (`isQuestionVisible` in the contracts); no answer value reaches the erase dialog, logs, toasts or live regions.

The defects below are therefore about edges of the model rather than the happy path: one invariant (one level of conditions) that is only enforced for ACTIVE dependents and that the tenant-move copy order relies on, an unlocked backfill insert, a replace flow whose UI offers choices the server ignores or refuses, a reopening rule that misses condition widening, and a privacy inference that the data model allows.

## Warnings

### WR-01: Replace flow shows the "Etapa" field but the server ignores it

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/QuestionEditorSheet.tsx:186,705-731`; `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.ts:226`; `packages/core/server/profile-form/admin.ts:1057-1062,1082`
**Issue:** `showStepField = steps.length >= 2` does not look at `mode`. In replace mode the select is live, `replaceDraftFrom` pre-selects the old step, `toCreateBody` sends `stepId`, and `replaceQuestion` only validates that id (`unknown_step`) and then inserts the replacement in `old.step_id` ("does not move the replacement"). An admin who picks another step gets a success toast and the question stays in the old step: the UI promises something the server silently drops.
**Fix:** hide or disable the step select when `mode === 'replace'` (and add a one-line helper if desired), and do not send `stepId` from `toCreateBody` for a replace:
```tsx
const showStepField = steps.length >= 2 && mode !== 'replace';
...
const body = toCreateBody(draft);
if (mode === 'replace') delete body.stepId;
```

### WR-02: Replace flow offers openers the server refuses, and the refusal reads as "another admin changed it"

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.ts:810-835`; `apps/web/app/(app)/configuracoes/formulario-de-perfil/QuestionEditorSheet.tsx:331-352`; `packages/core/server/profile-form/admin.ts:1070-1084`
**Issue:** `eligibleOpeners` treats a replace like a create ("goes to the END of its step"): with `storedStepId === null` it keeps every question whose step rank is `<=` the target. But the server swaps the replacement into the OLD question's slot (`swapQuestion`), so a sibling that sits AFTER the old question in the same step is offered by the editor and refused with 409 `condition_order`. `applyFailure` has no case for `condition_order` (or `condition_locked`) and falls to `setConflict(true)`, whose text says another admin changed the question, which is false and sends the admin to a refresh that changes nothing.
**Fix:** in replace mode compute `before` from the old question's index (`stays`-style: `ordered.slice(0, indexOf(question.id))`), and map `condition_order` (use `result.openerId`/title) and `condition_locked` to their own sentences in `applyFailure` instead of the generic conflict banner.

### WR-03: The one-level invariant (D-622) is enforced only against ACTIVE dependents; archived dependents can create chains that break the tenant move

**File:** `supabase/migrations/20261105195403_profile_form_steps_functions.sql:193-224`; `packages/core/server/profile-form/condition-rules.ts:72-80,143-146`; `packages/core/server/projects/move/fk-order.ts:24-32`; `packages/core/server/projects/move/copy-rows.ts:61-66`
**Issue:** PF007 and `checkCondition` ("the subject is not an active opener") look only at `archived_at is null` dependents. Sequence: O has one dependent D, D is archived (allowed), O is then edited to gain a condition on P (allowed: no ACTIVE dependents). The database now holds the chain D -> O -> P. `fk-order.ts` justifies its self-reference ordering with "an opener never carries a condition, so every NULL-condition row is read before every conditional row" and orders `condition_question_id asc nulls first`. With the chain, D (opener O) can sort before O (opener P) by UUID, so the batch insert hits the non-deferrable `profile_form_questions_condition_fk` and the move of that tenant fails mid-copy. The same chain makes `profile_form_purge_closed` order-dependent (D's retention is judged against O's answer as it was at statement start).
**Fix:** close the hole at the source: make the rule "an opener has no condition" count archived dependents too (PF007 and `checkCondition`: drop the `archived_at is null` filter for the "gains a condition" branch only), or clear the archived dependents' condition when an opener gains one. Alternatively make the copy order depth-aware instead of relying on the invariant.

### WR-04: The default-step backfill insert does not take the per-tenant advisory lock the trigger relies on

**File:** `supabase/migrations/20261105195400_profile_form_steps_backfill.sql:34,60-67`
**Issue:** the header says the advisory lock makes concurrent inserts create ONE default step, but the backfill `insert ... where not exists` never takes `pg_advisory_xact_lock(hashtextextended('profile_form_steps:' || tenant_id, 0))`. The trigger is installed first precisely because the previous API revision keeps inserting questions without a step during the fan-out. If such an insert for tenant T commits its default step between the backfill statement's snapshot and its insert, T ends with two steps titled "Informações gerais" at position 1 (no unique on `(tenant_id, position)`), the questions split between them and the admin sees a duplicate step. Probability is low (a question created during the milliseconds of the statement), but it fans out to every tenant project and is not self-healing.
**Fix:** run the backfill per tenant under the same lock, e.g. a `do $$` loop over `select distinct tenant_id ...` that does `perform pg_advisory_xact_lock(...)` then the guarded insert, or take the lock inside a `where` via a locking function; the following `update` can stay as is.

### WR-05: Condition changes that widen who owes an answer are not treated as "reopening the form"

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.ts:531-555`
**Issue:** `reopeningOf` covers create, replace, optional->required and `remove_condition` only. Editing an unanswered REQUIRED conditional question so that more members see it (adding values to its condition, or switching to a broader opener) goes straight to `write(false)`: no impact count, no confirmation dialog, no pending-members toast, although every newly matching member now owes an answer. The same gap hits optional->required combined with removing the condition in one save: the `make_required` impact is computed server-side against the STORED condition, so it undercounts (only members who see it today).
**Fix:** when the draft is required and the stored condition is replaced by a different one (or removed while also becoming required), read the impact of the NEW condition (reuse `create_required`-style `conditionQuestionId`/`conditionValues`) and confirm when it is above zero; if that is deliberately out of scope, record it in the release notes.

### WR-06: A public dependent of a private opener lets any member infer the private answer

**File:** `packages/core/server/profile-form/answers.ts:104-113`; `packages/core/server/profile-form/admin.ts:441-451`; `packages/contracts/src/profile-form.ts:386-408`
**Issue:** the member-viewer query returns every answered row of a `show_on_profile` question. Nothing relates the privacy flags of an opener and its dependent: an opener "Tem alguma condição de saúde?" (private) with the dependent "Qual?" (public) exposes, by the mere presence of the dependent's public answer and title, that the private opener was answered with a value that opens it. The one-way ratchet (PF004) protects the opener's own value but not what its dependents disclose.
**Fix:** either refuse (409 `condition_invalid` or a new code) a public dependent whose opener is private, with the editor explaining it, or make `publicAnswersOf` omit a conditional answer unless its opener is also public. If this is an accepted product decision, say so in the phase notes.

### WR-07: "A hidden question's answer is never stored" is enforced only in the API, with no database backstop

**File:** `packages/core/server/profile-form/member.ts:491-533`; `supabase/migrations/20261105195403_profile_form_steps_functions.sql:157-179`
**Issue:** T-12.1-02 is implemented by `saveAnswers` (skip hidden, then purge at the end of the same transaction). Every other layer of this module has an RLS/trigger twin (tenant scoping, PF001..PF007), but there is no trigger or policy on `profile_form_answers` that refuses an insert/update for a question whose opener answer does not open it. Any path that writes answers outside `saveAnswers` (a future import, a worker, a customer-owned project where the Data API is reachable, a bug in a later phase) can store a hidden answer, and it will then be read by `staffAnswersOf`/`publicAnswersOf` and exported by `exportAnswers` until that member happens to save again (the purge only runs inside a member save).
**Fix:** add a `BEFORE INSERT OR UPDATE` trigger on `profile_form_answers` that uses `app.profile_form_answer_tokens` and the question's condition to reject (or silently skip) closed answers, or at minimum filter on the same predicate in `staffAnswersOf`, `publicAnswersOf` and the export query.

### WR-08: `condition_order` and `condition_locked` 409s are not mapped on the reactivate and save paths

**File:** `apps/web/app/(app)/configuracoes/formulario-de-perfil/actions.ts:214-253`; `apps/web/app/(app)/configuracoes/formulario-de-perfil/ArchivedList.tsx:126-158`
**Issue:** `reactivateQuestionAction` maps only `condition_invalid`. The server also answers 409 `condition_order` with `openerId` for a conditional question whose active opener now sits after its step (reachable by reordering steps after the question was archived). It falls into the `else` branch: a `console.error` and the generic "falha ao reativar" toast, with no explanation and no hint of which opener. The editor sheet has the same hole (see WR-02).
**Fix:** add `if (res.status === 409 && detail === 'condition_order')` returning `{ ok: false, code: 'conditionOrder', openerId }` and render the existing "opener must come first" sentence with the opener's title.

**Fix:** add an SQL helper (e.g. `app.profile_form_condition_open(p_tenant, p_membership, p_question)` or an inline-able set-returning view) and call it from all sites.

### IN-04: Duplicated helpers

### IN-05: Copy promises navigation that does not happen outside the stepper layout

**File:** `apps/web/components/profile-form/ProfileForm.tsx:419-431`; `apps/web/messages/pt-BR/profileForm.member.json` (`stepper.pendingElsewhere`)
**Issue:** when the gate still reports a missing question, `elsewhere` is set for every layout, but `goToStep(target)` runs only `if (stepperOn)`. In the one-card or sectioned layout the notice still says "Levamos você até lá."
**Fix:** use a variant of the sentence without the second half when `!stepperOn`.

### IN-06: A 409 `form_changed` raised after writes carries a form that includes the rolled-back writes

**File:** `packages/core/server/profile-form/member.ts:369-376,402`
**Issue:** `reportMissing` throws `formChanged` after the writes and the purge of the same transaction; `formChanged` builds the fresh form with the same `tx`, so its `answer` fields contain values that the rollback is about to discard. The web then seeds `stored` from it, so the erase warning later believes those answers exist. Rare path (FA-32), small consequence.
**Fix:** read the fresh form before the writes, or build `formChanged` from a new transaction after the rollback.

### IN-07: Fixtures live in the production `lib` tree; two comments contradict the code

**File:** `apps/web/lib/profile-form/test-fixtures.ts`; `apps/web/app/(app)/configuracoes/formulario-de-perfil/editor-state.ts:204-205,153-161`
**Issue:** `test-fixtures.ts` is imported only by tests but sits next to production modules (it is type-checked into the app and can be pulled by a mistaken import). In `editor-state.ts` the `CreateBody.condition` comment says "a replacement does not inherit one", while `replaceDraftFrom` copies the old condition by design.
**Fix:** move the fixtures to a `__fixtures__`/test-utils path excluded from the build, and fix the comment.
