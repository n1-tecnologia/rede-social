### The condition rule
- **D-620:** Only a question of type dropdown, multiple choice, single choice or yes/no can OPEN other questions. Number, date, text, phone, e-mail, link, acceptance and rating never open anything. — **Reversibility:** reversible — widening the list later is one more validator, no table change.
- **D-621:** The condition lives on the question that APPEARS (the "shown" question), not on the opener and not on the step: "show only if [opener question] is [option, or any of these options]". It is stored as the opener's question id plus the set of option ids (for yes/no, the set holds the answer true or false). For a multiple-choice opener the shown question appears when the member ticked ANY option of the set. A step whose questions are all hidden disappears by itself (D-628). — **Reversibility:** costly — the columns, the contract schema and the SQL gate all read this shape.
- **D-622:** ONE LEVEL only: the opener must itself be always visible (it carries no condition), so a shown question never depends on another shown question. The gate stays a plain join with no recursion. — **Reversibility:** reversible — widening to a chain changes the validation rule and the SQL, not the tables.
- **D-623:** The opener must come BEFORE the shown question: in the same step at an earlier position, or in an earlier step. A write or a reorder that would put the opener after the question it opens is refused with a coded error. Otherwise the member would face a question whose opener they have not answered yet. — **Reversibility:** reversible.

### What happens to answers that stop applying
- **D-624:** When the member changes the opener's answer so that some shown questions close, the answers of those closed questions are DELETED in the same transaction that saves the opener (same save, same snapshot). What is stored is always what the member sees. If they go back, they answer again. Because nothing hidden is ever stored, the public answers block, the staff view, the CSV and the impact count need NO visibility filter and a stale answer cannot leak to other members. — **Reversibility:** costly — "stored equals visible" is a promise to members and removes the filter from every reader; reversing it means adding the visibility filter to each read path and the privacy tests of D-593.
- **D-625:** A question that already has answers cannot GAIN or CHANGE its condition (a new database lock in the family of PF001..PF005, same path as D-587: create a new question and archive the old one). REMOVING a condition is allowed at any time: it widens who sees the question, discards nothing, and when the question is required it reopens the form for members who lack the answer (D-585), with the impact dialog counting them. — **Reversibility:** costly — one more trigger code and a service rule; loosening it means deciding what to do with answers that no longer apply.
- **D-626:** The member is never surprised by D-624: before a save that would delete answers (an opener changed on "Avançar" or on "Salvar"), the screen tells them which answers will go. The wording and shape (confirmation dialog versus inline notice) are left to the UI-SPEC and its sketch; the constraint is that no answer is deleted without the member having been told in that interaction. — **Reversibility:** reversible.

### Steps
- **D-627:** A STEP is a tenant-owned row with a title and a position; EVERY question belongs to exactly one step. The questions that exist when this ships are moved into one default step, and a form with a single step renders as today: one screen, no progress bar. The builder shows steps as cards holding their questions and allows moving a question between steps. — **Reversibility:** costly — a new table, a column on the questions, a backfill migration that fans out to every tenant project (09.2, 09.4), and the builder's shape.
- **D-628:** A step with no visible question for this member is skipped and does not count in the progress ("Etapa 2 de 3" is computed over the steps the member actually has). — **Reversibility:** reversible.
- **D-629:** "Avançar" validates the step and SAVES it. Closing the app mid-form returns the member to the first step that still has something missing. The save must therefore stop refusing "a required question still unanswered" for questions OUTSIDE the saved step: today `saveAnswers` recounts `app.profile_form_missing_self()` after writing and refuses the whole save when anything required is missing (Phase 12 member.ts, D-585 recount). The step save keeps the per-value validation and the `formEtag` conflict check, drops that recount for other steps, and reports `missingRequired`; the hard gate (D-581) still releases only when nothing visible and required is missing, so the member leaves the form only after the last step closes. — **Reversibility:** costly — this changes the contract of `PUT /v1/me/profile-form/answers` that Phase 12 published and its tests; Phase 13's native shell reuses these web screens, so it inherits the change.
- **D-630:** EDIT from the profile ("Minhas respostas") is ONE scrollable screen with every step stacked under its title and a single "Salvar", not the stepper. RETURN after the admin adds a required question shows only the steps that have something missing for that member. First fill is the stepper. — **Reversibility:** reversible — presentation only.

### Effects on the Phase 12 rules
- **D-631:** D-585 is extended, not replaced: completeness is still computed and never stored. A question counts as owed when it is active, required, has no answer row AND is VISIBLE to the member: it has no condition, or its opener has an answer row whose value is one of the condition's options. The rule stays one SQL function (`app.profile_form_missing`) behind the same `_gate` twins, one round trip, no per-type logic and no recursion (D-622). A tenant with the module off still pays one primary-key probe. — **Reversibility:** costly — the SQL function is the hot path of every request and its twins are published to every tenant project.
- **D-632:** A question that still OPENS others cannot be archived, cannot change its type and cannot lose an option that a condition references (even an option with no answer). The service refuses with a coded 409 that carries the list of dependent questions; the admin removes the condition or archives the dependents first. Reactivating a shown question whose opener is archived is refused the same way. — **Reversibility:** reversible — it is a refusal; relaxing it later is a service rule.
- **D-633:** Limits: the 30 active questions of Phase 12 stay (the first client's form fits), plus a maximum of 10 steps per form. The number lives in `PROFILE_FORM_LIMITS` and in a database CHECK that reads it, like the others. If the client's list grows past 30 the limit moves in a small migration. — **Reversibility:** reversible.
- **D-634:** The admin impact dialog ("X members will have to answer") counts only members who SEE the question: the opener's answer matches the condition and they lack the answer. The CSV keeps one column per question (archived included) with an empty cell where a question never applied. The public answers block, the staff view and the "Minhas respostas" section need no new filter (D-624). — **Reversibility:** reversible.
- **D-635:** The sketch gate applies (UI-04): sketch 016 has no steps and no condition editor, and sketch 017 belongs to Phase 13, so this phase needs a new sketch (018) of the screens it adds: the builder with step cards, the condition editor on a question, the dependent badge and the refusal lists, the stepper, the delete-answers warning, the one-scroll edit with titles, and the admin preview following steps and conditions. The executor never writes the approval. — **Reversibility:** reversible.

### Deferred Ideas (OUT OF SCOPE)
- A condition on a WHOLE step ("show the step 'Sua clínica' only if..."), the Google Forms style jump. Rejected for now in favour of the condition on the question (D-621); revisit if admins repeat the same condition on many questions of one step.
- Chains of conditions (A opens B opens C), up to a few levels. Rejected for the hot path (D-622); widening is a rule change, not a table change.
- Conditions that read a number, date, text, acceptance or rating answer.
- Keeping the closed answers hidden (and restoring them if the member goes back) instead of deleting them (D-624). Rejected for privacy and simplicity; would need the visibility filter on every reader.
- A "go to step" jump or an early end of the form.
- Notifying members (notification center or Web Push) when the admin changes the form.
- State/city and file/photo answer types (deferred since Phase 12).

## Project Constraints (from CLAUDE.md)

Read from `./.claude/CLAUDE.md` this session; the directives that bind this phase:

- **Tenant isolation (core value):** `tenant_id` first in every index, RLS on every table, three-layer scoping (host, explicit predicate, RLS). A new table gets the shape of `profile_form_questions`; every policy needs a cross-tenant negative pgTAP test.

- **Memory/process constraints that shape plans:** execution is sequential on the main tree; do not run `db:reset` without the user's word; pgTAP before integration; `test:integration -- x` does not filter; Vitest never emits TAP; disk is tight (5.9 GiB free on 2026-11-05 per `df -h`, so no `turbo build`, Playwright only under a free-space watchdog).

## Summary

Phase 12.1 is a **vertical extension of one closed module**: a new tenant table (`profile_form_steps`), three new columns on `profile_form_questions` (`step_id`, `condition_question_id`, `condition_values`), a body change of one SQL function, one new definer lock function, a changed member save, a steps + conditions admin API, and a stepper / one-scroll / builder UI. No package is added (the UI-SPEC and this research agree: `motion`, `lucide-react`, `next-intl`, `react-hook-form` are already installed; see Package Legitimacy Audit).

The design that fits the repo with the least blast radius is: **keep `position` as ONE global order** (steps are contiguous ranges of it). Then every reader that already does `order by q.position, q.created_at, q.id` (member form, lock function, public/staff answers, CSV header) keeps working with no change, "opener comes before the shown question" is a plain `opener.position < question.position`, and every structural write (add to a step, move between steps, reorder, reorder steps, delete a step) is one pure in-memory "layout" computation followed by one set-based renumbering statement. **Store the condition as columns on the shown question** (`condition_question_id uuid`, `condition_values text[]`) so the gate stays a plain join with one extra unique-index probe per conditional required question; match with Postgres array overlap (`&&`) through one small immutable helper that turns any stored answer value into text tokens (option ids, or `'true'`/`'false'`). The same helper powers a **purge** statement that deletes the answers of closed questions inside the save's transaction, and a pure TypeScript twin (`isQuestionVisible`) that the stepper, the preview, the readers and the server validator all share, pinned to the SQL by a parity test.

Four things the CONTEXT does not name were found in the code and must be planned: (1) a self-referencing foreign key on `profile_form_questions` **breaks the tenant move engine** unless `SELF_REF_ORDER` gets an entry (one line plus a test); (2) `getSummary` ("complete" members), `getImpact` (create/replace counts) and `newOptionalCount` read completeness or "every member" without visibility and are wrong the day the first conditional required question exists; (3) `app.profile_form_lock_active()` returns a fixed column list, so adding columns needs a **new function name** (expand-only), not `create or replace`; (4) members cannot read archived questions under RLS, so the purge of an archived dependent needs a definer function.

**Primary recommendation:** ship in four waves: (W1) contracts (shapes, visibility function, limits, issue codes) + Drizzle schema + two migrations + pgTAP; (W2) kernel services (member read/save with scope and purge, admin steps / layout / conditions / locks / counts) + routes + integration + isolation inventory + move-engine entry; (W3) sketch 018 plan (user-gated) then the web (stepper, one-scroll edit, readers, builder, preview); (W4) e2e, release notes, ledger. Server and SQL plans never wait for the sketch.

### Pattern 1: Global `position` with steps as contiguous ranges ("layout")

**What:** `profile_form_questions.position` stays 1..n over ACTIVE questions across the whole form. A step is a row; its questions are a contiguous slice. A pure `layout` is `[{ stepId, questionIds[] }]` in step order. Every structural write reads the locked layout, mutates it in memory, validates D-623 over the flattened order, and writes it back in ONE set-based statement (the shape of the existing `reorderQuestions` UPDATE ... FROM `jsonb_array_elements_text(...) with ordinality`).
**When to use:** create in a step, move to another step (UI-D-647: lands at the end of the target step), reorder inside a step, reorder steps, reactivate, replace, delete a step.
**Why this fits:** the existing readers `order by q.position, q.created_at, q.id` [VERIFIED: member.ts:157 `order by q.position, q.created_at, q.id`; answers.ts:111; admin.ts:172; export.ts:109-112] are untouched.

### Pattern 2: The condition as two columns plus an overlap helper (D-621, D-631)

```sql
-- hand migration (custom): the one helper both the gate and the purge use
create or replace function app.profile_form_answer_tokens(p_value jsonb)
returns text[] language sql immutable set search_path = '' as $$
  select case jsonb_typeof(p_value)
    when 'boolean' then array[p_value #>> '{}']                       -- yes_no: 'true' / 'false'
    when 'object'  then case
        when jsonb_typeof(p_value -> 'optionIds') = 'array'
          then coalesce(array(select jsonb_array_elements_text(p_value -> 'optionIds')), '{}'::text[])
        when jsonb_typeof(p_value -> 'optionId') = 'string' then array[p_value ->> 'optionId']
        else '{}'::text[] end                                          -- "Outro" (optionId null) opens nothing
    else '{}'::text[] end
$$;
```
The stored shapes it reads are the contract's: yes/no is `z.boolean()`, single/dropdown is `{ optionId: string|null, otherText }`, multiple is `{ optionIds: string[], otherText }` [VERIFIED: packages/contracts/src/profile-form.ts:311-336 `choiceOne` / `choiceMany` / `z.object({ type: z.literal('yes_no'), value: z.boolean() })`].

### Pattern 3: Pure rules module + service + trigger backstop (D-625, D-632)

Mirror `lock-rules.ts` (pure `checkLocks` + `guardIssueOf` SQLSTATE map) [VERIFIED: lock-rules.ts:63-115]. ### Anti-Patterns to Avoid
- **Per-step `position` or step as a column-only on the question with no table:** rejected above (D-627 locks a table).
- **A row-level trigger that enforces D-623 order:** the bulk renumber updates rows one at a time inside one statement, so a row trigger would see intermediate states and refuse legal moves. Order is a service rule under the per-tenant advisory lock (`adminLock`), tested by integration, not a trigger.
- **`create or replace function app.profile_form_lock_active()` with more columns:** changes the OUT row type; Postgres refuses it (see Pitfall 3). Use a new name.
- **`ON DELETE RESTRICT` on the new self-FK and the step FK:** RESTRICT is checked per row, so a statement that deletes an opener and its dependent together fails; fixtures and `removeProfileFormByPrefix` delete in bulk. Use the default NO ACTION and the coded service refusal (Pitfall 8).
- **Putting the visibility rule only in React:** the server re-validates; the gate is SQL (UI-D-662).

## Condition rules (pure module `condition-rules.ts`)

A condition `{ questionId, values: string[] }` on question Q is valid iff (service, under `adminLock`, against the locked layout):
1. opener exists in the tenant, is ACTIVE, is not Q, and its type is in `dropdown | multiple_choice | single_choice | yes_no` (D-620);
2. opener has NO condition (D-622) and Q is not itself an opener of an active question (a question with dependents cannot gain a condition);
3. opener's flattened index is lower than Q's (D-623), which covers "earlier step";
4. `values` is non-empty, no duplicates, and each is an id in `opener.options` (choice) or `'true'`/`'false'` (yes/no); "Outro" has no id, so it can never be in the set (discretion: no);
5. Q has no answers if the condition is created or changed (D-625; removal always allowed).

Layout-level checks (every write that moves things): for every conditional question in the NEW layout the opener's index must still be lower; the refusal names the offending pair so the UI can print the two titles (UI-D-646).

Dependents (D-632): ACTIVE questions whose `condition_question_id = opener`. The three refusals (archive, retype, remove an option referenced by an active dependent) answer `409 CONFLICT` with `details: { profileForm: 'has_dependents', dependents: [{ id, title }] }` (shape is discretion; titles are tenant configuration, not member content). Reactivation of a dependent whose opener is archived (or no longer eligible: has a condition now, type changed, option removed, now after it) re-validates the whole condition and refuses with `condition_invalid`. Refusal codes to append LAST to `PROFILE_FORM_ISSUES` (the test pins the length 21 and must change [VERIFIED: contracts/tests/profile-form.test.ts:122 `expect(PROFILE_FORM_ISSUES).toHaveLength(21)`]): `condition_locked`, `condition_invalid`, `condition_order`, `has_dependents`, `step_not_empty`, `last_step`, `unknown_step`, plus reuse of `limit_reached` for steps. ## Common Pitfalls

### Pitfall 1: A self-referencing foreign key stops the tenant move engine
**What goes wrong:** `profile_form_questions` gains a composite FK to itself. The move planner builds its copy order from `pg_constraint` and refuses any self reference not named in `SELF_REF_ORDER`: `if (column) selfReference[edge.child] = column; else selfRefused.push(edge.child);` then `throw new MoveError('unsortable_tables', ...)` [VERIFIED: packages/core/server/projects/move/fk-order.ts:115-132]. Every tenant move would fail at planning.
**Why it happens:** Phase 12's Pitfall 7 said "both new tables ... their FKs are plain and acyclic" [VERIFIED: 12-RESEARCH.md Pitfall 7]; that stops being true here.
**How to avoid:** add one entry next to the existing one, whose current value is `feed_comments: 'parent_depth',` [VERIFIED: fk-order.ts:25-27]: `profile_form_questions: 'condition_question_id'`. ## Code Examples

### The shared pure visibility function (`packages/contracts/src/profile-form.ts`)
```ts
// Design for UI-D-662. Tokens: option ids for choice answers, 'true'/'false' for yes/no.
export type ProfileFormCondition = { questionId: string; values: string[] };

/** The tokens a STORED answer value contributes: the TS twin of app.profile_form_answer_tokens. */
export function answerTokens(stored: unknown): string[] {
  if (typeof stored === 'boolean') return [String(stored)];
  if (typeof stored !== 'object' || stored === null) return [];
  const rec = stored as Record<string, unknown>;
  if (Array.isArray(rec.optionIds)) return rec.optionIds.filter((v): v is string => typeof v === 'string');
  return typeof rec.optionId === 'string' ? [rec.optionId] : [];
}

export function isQuestionVisible(
  question: { condition: ProfileFormCondition | null },
  tokensOf: (questionId: string) => readonly string[] | undefined,
): boolean {
  if (question.condition === null) return true;
  const opener = tokensOf(question.condition.questionId);
  return opener !== undefined && question.condition.values.some((v) => opener.includes(v));
}
```
