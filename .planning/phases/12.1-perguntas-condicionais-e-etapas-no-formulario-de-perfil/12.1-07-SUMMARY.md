## Findings for later plans

**A5, closed with a correction that matters for plan 09.** RESEARCH Pattern 1 and the `<action>` of plan 09 (and the `layout-store.ts` it creates) write the layout writer as
`from jsonb_to_recordset(<json>::jsonb) with ordinality as o(id uuid, step_id uuid, ord int)`.
Postgres REJECTS that: `WITH ORDINALITY cannot be used with a column definition list` (SQLSTATE 42601, hint "Put the column definition list inside ROWS FROM()"). 225 asserts the rejection and proves the two forms that run, both renumbering positions and steps together in one set-based UPDATE:
1. `from rows from (jsonb_to_recordset(<json>::jsonb) as (id uuid, step_id uuid)) with ordinality as o(id, step_id, ord)` (position from the array order);
2. `from jsonb_to_recordset(<json>::jsonb) as o(id uuid, step_id uuid, ord int)` with `ord` carried inside each JSON element.
Plan 09's writer must use one of them; the literal text in its Task 1 action fails on first execution. The other statements of A5 (array overlap with the helper, the BEFORE INSERT trigger filling a NOT NULL column, ADD COLUMN nullable then SET NOT NULL, the composite self-reference) ran as written.

**Backfill and trigger behave as designed on legacy-shaped rows.** Replay on tenants R1 and R2 (with an archived question) gave one default step each, R3 (no question) none, a second replay changed nothing (md5 of steps and question links equal), and `SET NOT NULL` then succeeded.

## Gate cost (A4, T-12.1-04)

Measured on the local stack, in a throwaway transaction that was rolled back: one tenant, 200 members, 35 questions (5 optional openers, 15 unconditional required, 10 conditional required, 5 spare required that are the 15 above counted once, so 30 active required of which 10 conditional), 3000 answers, `analyze` run. The target member answered the 5 openers with the matching option and 10 of the 15 unconditional required questions, so the gate returns 15 (5 unconditional plus 10 revealed).

- `explain (analyze, buffers) select app.profile_form_missing(...)`: `Result ... Execution Time: 0.227 ms` and 0.256 ms on the second run, `Buffers: shared hit=54`, warm. A SQL definer function is not inlined, so this line shows only the total.
- Plan shape of the body of the third branch (copied verbatim as a plain query), `Execution Time: 0.086 ms`, `Buffers: shared hit=49`:
  - `Index Scan using profile_form_questions_required_idx` on questions (tenant probe, the partial index), 25 rows;
  - `Hash Anti Join` against `Index Only Scan using profile_form_answers_member_question_uq` with `Index Cond: (tenant_id, membership_id)`, 15 rows, Heap Fetches 15;
  - `SubPlan 1` (the opener lookup): `Index Scan using profile_form_answers_member_question_uq` on `(tenant_id, membership_id, question_id)`, 10 loops (one per conditional question), 1 row each, `Filter: (q.condition_values && app.profile_form_answer_tokens(value))`.
  - No sequential scan of `profile_form_answers` anywhere.
  A regression to a sequential scan of answers would show up as a `Seq Scan on profile_form_answers` node in this plan. The data is local and small (3000 answers); a reading on production-size data is not claimed.
