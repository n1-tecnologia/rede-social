# Phase 12.1 Plan 10: Conditions API, dependents refusals and visibility-aware counts Summary

**The admin can write, change and remove a condition under the pure rules (type, chain, order, tokens, tenant), a condition locks once the question has answers, an opener that still opens others refuses archive, delete, retype, option removal and replace with the list of its dependents, and the summary and the impact count only the members who see a question, pinned to the gate function by an integration assertion.**

## Performance

- **Duration:** about 11 min wall clock (start 2026-11-05T20:57:04Z, end 2026-11-05T21:08Z)
- **Tasks:** 3 of 3 (Task 1 is the tracer)
- **Files:** 1 created, 5 modified

## Accomplishments

- Contract (non-additive, fixed in the same plan): `condition` (nullable) and `opensCount` on the admin and archived question; `remove_condition` appended last to `PROFILE_FORM_IMPACT_CHANGES`; optional `conditionQuestionId` and `conditionValues` on the strict impact query; `parseConditionValues`. Web fixture builders default `condition: null` and `opensCount: 0`.
- `admin.ts`: `StoredQuestion` and `COLUMNS` carry the condition; `countsFor` returns the ACTIVE dependents per opener in the same pass for the list, the single row and the archived list; create and replace check the condition on the candidate layout (a probe id placed where the new question will sit); update compares the wanted condition with the stored one as a set, locks it (`checkConditionLock` with the stored answer count), then checks it (`checkCondition`); `null` removes it.
- Opener side: `checkOpenerChange` in update (retype and removed option ids), archive, delete and replace, answered as 409 `CONFLICT` `{ profileForm: 'has_dependents', dependents: [{ id, title }] }`. `reactivateQuestion` runs `checkReactivation` with the row added to the active questions and names `openerId` (the stored one when the opener is no longer in the form).
- Race backstop: `attempt` runs a write inside a savepoint; `guardedWrite` maps PF001..PF007 to the same coded 409 and, for PF007, re-reads the dependents of the opener after the savepoint rollback. Delete maps a 23503 to `has_dependents` (fresh list) or `has_answers`.
- `getSummary`: one set-based statement repeating the gate predicate (required active question, no answer row, and no condition or an overlapping opener answer through `app.profile_form_answer_tokens`). `getImpact`: a shared `SEES_THROUGH` / `LACKS_ANSWER` predicate pair for `create_required`, `replace`, `make_required`, `reactivate` and the new `remove_condition`.
- Route descriptions name the new fields, codes and the `dependents` list.
- 20 integration cases in `profile-form-conditions.test.ts` and 3 contract cases.

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Delete of an opener whose dependents are all archived would end in the foreign key**
- **Found during:** Task 2 (reading the schema: the condition foreign key is NO ACTION and archived dependents keep their condition columns)
- **Issue:** the plan says archived dependents do not block and that the same edits succeed once dependents are archived, but a delete of the opener would fail with 23503 because the archived dependents still reference it.
- **Fix:** before the delete, the archived dependents' `condition_question_id` and `condition_values` are set to null in the same transaction (removing a condition is allowed at any answer count and discards no answer). A reactivated former dependent therefore comes back unconditional. This is a design choice the plan did not state; flagged for the web plans (16, 17) so the UI can say so if it wants to.
- **Files modified:** `packages/core/server/profile-form/admin.ts`
- **Verification:** integration case "archived dependents do not block ... Delete with only ARCHIVED dependents"
- **Commit:** `08018140`

**2. [Rule 1 - Bug in the plan test design] "Impact counts of 1, 2 and 3 for a three-member fixture" cannot be literal**
- **Found during:** Task 3
- **Issue:** the seed tenants already have active members, and every member who does not see the question counts in `remove_condition` and in the unconditional counts, so the totals are not 3.
- **Fix:** the test reads `total` from the summary and asserts the exact values 0, 1, 2 and 3 for the conditioned `create_required` counts (which are independent of the seed), and `total - 1`, `total - 2` and `total` for the others.
- **Files modified:** `apps/api/tests/integration/profile-form-conditions.test.ts`
- **Commit:** `6b4879f6`

## Issues Encountered

- The first PF007 race design (insert a new dependent in a second connection) could not reproduce the race: the insert's foreign-key share lock on the step blocks the service's locked read of the steps, so the service read the dependent in time. The final test gives an EXISTING question its condition from a second connection that holds the opener's row, which touches neither the steps nor the layout reads, and the service then reaches the trigger with a stale view, as intended.
