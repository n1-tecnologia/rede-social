# Phase 12.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 12.1 adds two things to the profile form of Phase 12: STEPS (the form is split into groups the member answers one at a time) and CONDITIONAL QUESTIONS (a question that appears only when an earlier choice or yes/no question was answered a certain way). It reverses D-582 (one scrollable screen) for the first fill and the return, and keeps it for edit. Most of the phase is model, SQL gate and API; the UI is the same two audiences as Phase 12, on screens that already exist.

**Baseline.** `.planning/phases/12-formulario-de-perfil-do-tenant/12-UI-SPEC.md` (UI-D-564..UI-D-599) is inherited whole: Manrope, `#f5f7fb` ground, white cards, 12px radii, 44px targets, the 12/14/16/24 type scale with weights 400/700, the tenant brand as the single accent, the `(auth)` frame, `BottomSheet`, `ConfirmDialog`, `StatusPill`, `Switch`, `SegmentedControl`. **Phase 12.1 declares no new token, colour, font, type size, weight or dependency.** This file lists only what is new and says which shipped component each new surface extends.

**Upstream decisions.** `12.1-CONTEXT.md` D-620..D-635 are LOCKED and honoured (traced in "How each locked decision shows up"). The visual and interaction questions this phase opens are decided as **UI-D-642..UI-D-664**, continuing after `UI-D-641`, the highest id in any UI-SPEC (`grep -rhoE "UI-D-[0-9]+" .planning | sort -t- -k3 -n -u | tail -1` returned `UI-D-641` on 2026-11-05).

**Non-interactive session.** No question could be asked in this run. Every choice CONTEXT left open took a default and is repeated under **To confirm with Igor** (PU-1..PU-16), so the orchestrator can confirm or overturn it with one line. The headline one is D-626 (PU-1): **a confirmation dialog, not an inline notice**.

**Sketch gate (UI-04).** This phase has no approved sketch. Sketch 018 is a **plan-time deliverable gated by Igor's approval**; the executor never writes the approval (see "Sketch gate" below).

## Data the screens read (for the planner; not a UI decision)

- **Admin read:** the steps (id, title, position, active question count), and per question `stepId`, `condition` (`openerId` plus the option ids, or the yes/no value) or `null`, `opensCount`, and for the editor the list of dependents (`id`, `title`) and which options are referenced. The opener list for the sheet can be derived on the client from this read (active, eligible type, no condition, earlier).
- **Member read:** `steps`, per question `stepId` and `condition`, the stored answers (the erase dialog's baseline), `mode`, `missingRequired`, `formEtag` (covers steps and conditions, CONTEXT discretion).
- **Member save:** the body gains the step scope; the response reports `missingRequired` and may report the erased question ids (optional). The `form_changed` 409 carries the fresh form as today.
- **409s:** a `dependents` list (`id`, `title`) for archive, delete, retype and remove-option; an order refusal that names the pair (opener, shown question); a step-not-empty refusal; a step-limit refusal.
- **Visibility:** one pure `isQuestionVisible` in contracts, parity-tested against `app.profile_form_missing` (UI-D-662).
- **No answer value** ever reaches a toast, an announcement, a log or the erase dialog.

**Planner-owned items this contract does not decide:** (1) where the archived questions of a deleted step go and where a reactivated question lands when its step is gone (UI-D-645 assumes delete is refused while any non-archived question remains; a message for archived-only steps is the planner's); (2) the exact step-save contract of `PUT /v1/me/profile-form/answers` (D-629) and what "Concluir" does when the server still reports missing questions (UI-D-654 specifies the screen's behaviour); (3) whether the stored-answer baseline for the erase list comes from the form read or from a save response; (4) the shape and codes of the refusals (D-632, CONTEXT discretion).

## Findings against CONTEXT (surfaced, not decided here)

- **F-1 (D-634).** CONTEXT says "Minhas respostas" and the staff view need no new filter. True for stored answers (D-624), but both readers also draw **rows for questions with no answer** ("Sem resposta"). A hidden conditional question would read "Sem resposta" for a member who never sees it. UI-D-659 adds two derived-row rules (omit in "Minhas respostas", "Não se aplica" for staff) that need the visibility function in those two readers. If the team prefers no rule at all, the alternative is to show "Sem resposta" for hidden questions, which is misleading and not recommended.
- **F-2 (D-629, D-630).** In `returning` mode with per-step save, a member who left a first fill midway comes back as `returning` (stored answers exist, something required missing) and walks only the steps with something missing; an all-optional step never visited is not on that path. That is consistent with "optional never gates" (D-586), but means such a member is not led back to it. UI-D-657 accepts this.
- **F-3.** The brief asked for focus to move to the revealed question. UI-D-655 keeps focus on the opener and announces instead (PU-7), because moving focus while the member is still choosing is a WCAG 3.2.2 problem; the revealed control is the next Tab stop.
