# Phase 12.1 Plan 15: Erase warning, one-scroll edit and the readers' rules Summary

**A member is shown which answers will be deleted (titles only, danger dialog, cancel saves nothing) before any save that closes a question with a stored answer, edits the whole profile form on one titled scroll with a single Salvar, and "Minhas respostas" and the staff view stop reading a question that never applied as "Sem resposta".**

## Accomplishments

- **Tracer (Task 1):** one path from a changed opener to the dialog to the confirmed step save. `closedWithAnswers()` (over `answersToErase`) runs after step validation; non-empty opens `EraseAnswersDialog` (kind `advance` for Avançar, `save` for Concluir and Salvar) and the save runs only on confirm. Rever respostas closes with nothing saved and the opener still changed. A failed save closes the dialog and the shipped alert shows (FA-UI-2). While the confirmed save runs the dialog stays open, both buttons disabled, the confirm button reads "Salvando…" (FA-UI-1).
- **Baseline kept honest:** the stored-answer set is seeded from the form read and updated after every good save and every 409 refresh, so an answer saved on an earlier step is still listed when a later change would close it (otherwise the server would delete it without a warning).
- **Edit as one scroll (Task 2):** for two or more configured steps, one `section` per step that holds a visible question, `aria-labelledby` its `h2` (16/700, `break-words`), its own `Card p-4 flex flex-col gap-6`, `gap-6` between sections, one Salvar, Cancelar below (still the page's). One configured step renders exactly Phase 12. A step whose last visible question closes drops its h2 and card at once. Salvar sends the whole form with no `stepId`.
- **Readers (Task 3):** the loader flags a conditional row whose opener answer does not match; `MyAnswersSection` filters it before the empty check and the "Ver todas" count and stays flat; `StaffAnswersBlock` reads "Não se aplica" (tertiary, no pill) via `isNotApplicable`. The public block and stored answers are untouched.

## Decisions Made

See `key-decisions`. The product-weight one: the erase list is built from a session-current stored set, not the original form read, because the stepper saves each step and the plain read would let a later step-1 change delete a step-2 answer saved a minute earlier with no warning.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The loader had to carry the derived-row flag**
- **Found during:** Task 3
- **Issue:** the plan names `MyAnswersSection.tsx` as the place that filters rows through `storedVisibleQuestionIds(form)`, but the section only receives `MyAnswerRow`s from `loadMyAnswers`, which carry no condition or form. Re-reading the form in the section would double the API read.
- **Fix:** `loadMyAnswers` (in `profile-reads.ts`) sets an optional `hidden` flag per row from `storedVisibleQuestionIds(form)`; the section does the filtering as the plan says. `hidden` is optional so existing rows and tests are unaffected.
- **Files modified:** `apps/web/lib/profile-form/profile-reads.ts`, `apps/web/lib/profile-form/profile-reads.test.ts` (one new case; no existing assertion changed). Both are outside the plan's `files_modified` list.
- **Committed in:** 5524cd0d

**2. [Rule 1 - Bug] Double press closed the dialog before the first save settled**
- **Found during:** Task 1 (own test)
- **Issue:** a guard that returned an already-resolved promise to the second press made the shipped dialog close while the first save was still running.
- **Fix:** the second press gets the in-flight promise.
- **Files modified:** `ProfileForm.tsx`; **Committed in:** ae7ca5ef

**3. [Rule 2 - Correctness] Stored baseline follows the session**
- **Found during:** Task 1
- **Issue:** `answersToErase(view, answers)` over the original read misses answers saved earlier in the session (see Decisions).
- **Fix:** `stored` set updated on good saves and 409 refreshes; the overlay passes a presence marker as `answer` (visibility never reads it when drafts are given). No answer value is read, logged or passed on.
- **Files modified:** `ProfileForm.tsx`; **Committed in:** ae7ca5ef

**4. [Rule 2 - Correctness] Step heading focus after a confirmed advance**
- **Found during:** Task 1
- **Issue:** the dialog's focus trap returns focus to the Avançar button when it closes, after the step heading took focus.
- **Fix:** the heading focus effect waits for the dialog to close (`focusPending` ref, `eraseOpen` dependency), so a cancel does not steal focus.
- **Files modified:** `ProfileForm.tsx`; **Committed in:** ae7ca5ef

**5. [Informational] No visible question shows the none state in every non-preview layout**
- The plan states this for edit; the check is `!preview && !stepperOn && visible.size === 0`, so a first-mode form with nothing visible also shows the shipped none state instead of an empty card.

**6. [Informational] Wording**
- UI-SPEC copy contract gives "e mais {count, plural, one {# pergunta} other {# perguntas}}"; the plan text says "e mais {count}". The UI-SPEC string was used verbatim ("e mais 2 perguntas", as the sketch frame draws it).
- The plan's verify for Task 3 uses `turbo typecheck`, which triggers a `next build`; per the run rules typecheck was `next typegen && tsc --noEmit` (clean).
