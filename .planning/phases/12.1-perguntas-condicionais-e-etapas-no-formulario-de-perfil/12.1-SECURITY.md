# Phase 12.1 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| Member browser → API (`PUT` save of one step) | A member submits answers for one step; the server decides which questions are visible and writes only those | Member answers (personal data, some private), step id, question keys |
| Admin browser → API (builder routes) | An admin with `profile_form.manage` creates steps, conditions and layouts | Step titles, question ids, condition option ids (tenant configuration, not member content) |
| API → Postgres (RLS + `SECURITY DEFINER` functions) | Gate `app.profile_form_missing`, purge `app.profile_form_purge_closed()` and lock `profile_form_lock_active_v2()` run with the caller's session claims | Tenant id and member id from claims, answer rows |
| Tenant ↔ tenant | Steps, conditions and answers must never reference or reveal another tenant's rows | Composite `(tenant_id, …)` foreign keys, tenant-scoped reads |
| Release path (migrate-all → API → worker → web) | Three migrations change a table that holds production rows; the new routes call functions that exist only after them | Schema, backfilled `step_id`, release order |
| Design gate (sketch 018 approval) | No screen of this phase is built before the human approval line exists | Approval keys in the sketch README |
