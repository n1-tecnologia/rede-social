# Phase 12.3 Plan 15: Phone menu in the tenant brand Summary

**The tenant keeps the phone menu its admin arranged in `tenants.branding.phoneMenu`: saved and cleared by two `tenant.manage` routes that apply the web's rules on the server, delivered by the bootstrap to every role, kept out of the public host answer, and preserved by the three branding writers that used to erase unknown keys.**

## Performance

- **Duration:** about 45 min
- **Tasks:** 3 (one tracer, two auto), RED commit before GREEN for tasks 1 and 2; task 3 is proving tests on code that already existed
- **Files modified:** 11, none created, no migration

## Accomplishments

- **Contract.** The constants (values verbatim from `apps/web/lib/phone-nav-layout.ts`), `phoneMenuSchema` (strict, three key lists, each key against the pattern, 16 per list), `PHONE_MENU_ISSUES` (six codes), `validatePhoneMenu`. `tenantBrandingSchema.phoneMenu` is `.optional().catch(undefined)`, so `parse({})` is byte-identical and a corrupt stored value reads as the shell's own menu. `ResolvedBranding.phoneMenu?` and a conditional spread in `resolveBranding` carry it.
- **Pitfall 1 closed.** `completeBrandingUpload`, `applyBrandColors` and `removeIconOverride` rebuild the object from `resolveBranding`; before the change the keeps-the-menu cases read `null` after each of them (confirmed RED), after it they hold. Proved on both lanes.
- **Kernel.** `setPhoneMenu` (validates before the transaction, `for update`, `branding || jsonb_build_object('phoneMenu', <json param>::jsonb)`, mirror push, host-cache drop, counts-only log) and `clearPhoneMenu` (`branding - 'phoneMenu'` only when the key exists; nothing pushed or invalidated otherwise).
- **Routes.** `PUT` and `DELETE /v1/admin/branding/phone-menu`, `middleware: [manage] as const`, `ctx.tenantId` only, `brandOf` answer, `Cache-Control: no-store`.
- **Inventories.** Two `T` rows (plan 15) for the writers in site order, two isolation inventory entries and the case `phase 12.3 sweep: phone menu`.
