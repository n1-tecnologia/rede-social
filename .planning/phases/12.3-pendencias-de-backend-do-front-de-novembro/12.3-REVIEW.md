# Phase 12.3: Code Review Report

**Reviewed:** 2026-11-09
**Depth:** standard
**Files Reviewed:** 56
**Status:** issues_found

## Summary

The four areas were traced end to end: the second covers (courses, tracks, modules, events), the store categories / front / promo / featured writes, the four migrations, and the phone menu stored in `tenants.branding`.

What held up (verified, no finding):

- **Tenant isolation of the new ids.** Every new asset id (`topCoverAssetId`, module `coverAssetId`/`topCoverAssetId`, `posterAssetId`) is resolved inside the writing transaction with `tenant_id = ctx.tenantId and deleted_at is null` and the ready `cover` image tuple. Courses answer `400 *_invalid`, events a bare 404 (accepted by design). Category slugs are resolved by exact slug equality for the caller's tenant (`findCategory`), promo and featured ids by `countActiveProducts` for the caller's tenant. The `delete` in `replaceCategories` only takes slugs already proven to exist for the tenant, so the text-array literal cannot be injected. The phone menu is bound as a JSON parameter cast to jsonb, never interpolated.
- **Seed race.** `store_seed_categories_for` claims through `insert ... on conflict (tenant_id) do update ... where categories_seeded_at is null returning`; a second concurrent first call waits on the first's row, re-evaluates the predicate and writes nothing. The admin-save-versus-first-read interleavings all end with one set of rows. The definer function takes no argument and reads only `app.tenant_id()`.
- **Whole-list save.** The two-pass rename (placeholder `chr(1) || slug`, at most 25 chars against the `char_length <= 30` check) cannot trip `store_categories_tenant_name_uq` on a swap; `slug <> all('{}')` correctly deletes everything for `[]`; `newCategoryId` stays within the 24-char slug check for up to 20 rows.
- **SQL and grants of the four migrations.** RLS is enabled with select-by-tenant and admin-only writes on both new tables, `truncate` is revoked, the two owner-only functions are revoked from every lane, the lazy seed is granted to `authenticated` only, and the backfill is idempotent (the marker row). The SQL guess is pinned to the web rule.
- **Client bundles.** Every `'use client'` file in scope imports `@rede-social/contracts/branding`, `/media`, `/money` or the module-store contracts subpath. The only file importing `phoneMenuSchema`/`PHONE_MENU_ISSUES` from the package index (`apps/web/lib/phone-menu.ts`, the menu `actions.ts`, `page.tsx`) is server-only.
- **pt-BR error mapping.** Every new store, course, module, track, event and menu refusal code has a catalogue entry and a UI branch (`category_invalid`, `promo_invalid`, `featured_invalid`, `too_many_*`, `top_cover_invalid`, `poster_invalid`, the menu `rules`/`generic`).
- **PATCH semantics.** Absent keeps, `null` clears, for `category`, `topCoverAssetId`, module covers and `imageAssetId`; the events `PUT` is a whole replacement and the form always sends `posterAssetId`.

No blocker was found. Three warnings (a lost-update race on `tenants.branding`, a narrow deadlock window, a rollout-fragility of the "tolerant" front read) and five info items follow.

## Warnings

### WR-01: The three other branding writers rebuild `tenants.branding` from an unlocked read, so a concurrent phone-menu save can be silently overwritten

**File:** `packages/core/server/platform/branding.ts:109-116, 285-304, 506-529, 751-775`
**Issue:** `setPhoneMenu` and `clearPhoneMenu` correctly lock the tenant row (`for update`) and merge one key. But `completeBrandingUpload`, `applyBrandColors` (reached from `setBrandingColors` and `updateTenant`) and `removeIconOverride` read the row through `loadTenant`, which takes **no lock**, then write the whole object back (`next = { ...resolveBranding(row.branding), ... }`). The phase's fix for "preserve `phoneMenu`" only makes the stale snapshot carry the menu that existed at read time. If a phone-menu save (or restore) commits between that read and the write, the writer overwrites it with the old value: the saved menu reappears after a "Restaurar o padrão", or a fresh save is lost. The window is small, but the saves are done by the same admin in two open tabs (Marca and Menu do app), and the loss is silent (the menu editor already toasted success). `setBrandingLook` shows the right pattern (lock first, merge).
**Fix:** Make the read-modify-write paths lock the row, for example give `loadTenant` a `lock?: boolean` argument and call `.for('update')` from `completeBrandingUpload`, `setBrandingColors` and `removeIconOverride`:
```ts
async function loadTenant(tx: Tx, tenantId: string, opts: { lock?: boolean } = {}) {
  const q = tx.select({ id: tenants.id, branding: tenants.branding })
    .from(tenants).where(eq(tenants.id, tenantId)).limit(1);
  return (opts.lock ? await q.for('update') : await q)[0];
}
```
(`deriveTenantIcons` keeps the unlocked read; its write is already a guarded `branding || patch` merge.)

### WR-02: A product edit and a category delete can deadlock, which surfaces as a bare 500

**File:** `packages/modules/store/server/service.ts:179-191, 1672-1683, 1124-1127`
**Issue:** `updateProduct` takes the product row (`lockProduct`, `for update`) and then, when `patch.category` is a slug, the category row (`findCategory`, `for key share`). `replaceCategories` deletes a category first (exclusive row lock) and the `on delete set null` action then has to update every product that points at it, which needs that product's row. If admin A saves a product that already sits in category C (re-sending `category: 'c'`, or moving it to C) while admin B removes C, A holds product P and waits for C, B holds C and waits for P: Postgres aborts one with `40P01`, and nothing maps it, so the loser gets a 500 and a lost edit. The comment on `replaceCategories` correctly argues the product write never sees a half state; it does not cover this lock-order inversion. The window is narrow (two admins, the same product and category), so this is a warning, not a blocker.
**Fix:** Make the two paths acquire in the same order, or retry. Cheapest: have `updateProduct` (only when `patch.category` is present) and `createProduct` take the `store_front` row lock through `lockFront` before the product lock, since `replaceCategories` already holds it for its whole transaction; or map `40P01` in `withTenantTx`'s caller for these two services to a retry-once. Add a pgTAP/integration case that races the two.

### WR-03: The web's "tolerant" front read rejects the whole answer on an unknown icon, and the setup panel would then crash on it

**File:** `apps/web/lib/store.ts:96-98` (with `packages/modules/store/contracts/index.ts:308` and `apps/web/app/(app)/loja/StoreSetupPanel.tsx:192`)
**Issue:** `tolerantFrontSchema` exists so that "a key the API adds later is ignored instead of refusing the whole answer" (D-696). It strips unknown **keys**, but each category still parses through `storeCategorySchema`, whose `icon` is a closed `z.enum(STORE_CATEGORY_ICONS)`. Adding a glyph to the list is documented as a contract change with no migration (`schema.ts`, the icon CHECK is length and class only). During a rolling release (new API, older web) or if a tenant is ever loaded with a glyph the deployed web does not know, `safeParse` fails: `getStoreFront` returns `null`, the storefront silently degrades to the plain grid (no chips, no hero), the Início loses the promo, and Gerenciar hides the whole setup panel. Separately, anything that bypasses the schema and reaches `STORE_CATEGORY_GLYPH[category.icon]` renders `<undefined />` and throws.
**Fix:** Make the tolerant schema accept any string icon and resolve it with a fallback glyph:
```ts
const tolerantCategory = storeCategorySchema.extend({ icon: z.string() }).strip();
const tolerantFrontSchema = storeFrontSchema
  .extend({ categories: tolerantCategory.array() }).strip();
// category-glyphs.ts: export const glyphFor = (icon: string) => STORE_CATEGORY_GLYPH[icon as StoreCategoryIcon] ?? Tag;
```

## Info

### IN-01: Category-name folding leaves invisible and format characters, and the web and the server fold differently

**File:** `packages/modules/store/server/service.ts:1021-1027`; `packages/modules/store/contracts/index.ts:271-276`
**Issue:** `foldCategoryName` drops `\p{Cc}` and folds `\s+`, but zero-width and format characters (`U+200B`, `U+200C`, `U+200D`, `U+2060`, bidi marks; all `\p{Cf}`) survive, so `Livros` and `Livros plus a zero-width space` are two "different" names under the `lower(name)` unique index and the duplicate check, and look identical in the UI. The web's `cleanCategoryName` does not apply NFC or strip controls at all, and it truncates to 30 code points where the server refuses (`category_name_too_long`); the dedupe in the sheet uses `toLocaleLowerCase('pt-BR')` while the server uses `toLowerCase()` and the DB `lower()`. The `maxLength` attribute and the server's `category_name_taken` fallback hide most of this, so it is a polish item.
**Fix:** Also strip `\p{Cf}` in `foldCategoryName` (`/[\p{Cc}\p{Cf}]/gu`) and make the web helper call the same fold (move one implementation into the contract).

### IN-02: The new foreign keys do not carry the tenant, so the database alone does not stop a cross-tenant id

**File:** `supabase/migrations/20261109190836_store_categories.sql:28-35`; `supabase/migrations/20261109185807_second_covers.sql:6-10`
**Issue:** `store_products.category_id`, `store_front.promo_product_id` and the five new media columns reference the parent by its uuid only. Referential-integrity checks bypass RLS, and the admin-lane `WITH CHECK` only tests `tenant_id`, so an admin lane that reached SQL directly could point a product at another tenant's category or a module at another tenant's asset. The API closes every one of these (verified) and the reads join on `tenant_id`, so nothing leaks today; this matches the existing `cover_asset_id` pattern. Noted only because the project states tenant isolation as defense in depth.
**Fix:** Optional hardening, not for this release: a `unique (tenant_id, id)` on `store_categories`/`store_products` and composite foreign keys `(tenant_id, category_id)`.

### IN-03: Migration hygiene: no index on the new asset foreign keys, and `truncate` is revoked from `authenticated` only

**File:** `supabase/migrations/20261109185807_second_covers.sql:1-10`; `supabase/migrations/20261109190954_store_categories_functions.sql:39`
**Issue:** The five new `media_assets` foreign keys (`ON DELETE no action`) have no supporting index, so a hard delete of a media row (or a tenant cascade) scans the referencing tables. And `revoke truncate ... from authenticated` follows the 08.2 precedent but leaves the default `truncate` grant to `anon` on the two new tables (RLS does not apply to TRUNCATE); reachable only if the Data API or a direct `anon` connection is open.
**Fix:** Add partial indexes (`where ... is not null`) on the new columns in a later expand migration, and `revoke truncate on ... from anon, authenticated` for the new tables.

### IN-04: The OpenAPI descriptions of the product routes omit `category_invalid`

**File:** `packages/modules/store/server/routes.ts:338-341, 390-393`
**Issue:** The `400` text of `POST /products` and `PATCH /products/{productId}` lists the closed `details.store` codes but not `category_invalid`, which both routes now return (a slug that is malformed or not a category of the caller's tenant). The web already handles it; the contract document, which the team's front reads, does not mention it.
**Fix:** Add `category_invalid` (and the absent / `null` / slug semantics) to both descriptions.

### IN-05: `validatePhoneMenu` counts keys it cannot know, so a menu can pass with fewer than two visible bar items

**File:** `packages/contracts/src/branding.ts:221-262`
**Issue:** By design (D-697) the server keeps unknown keys, and the bar minimum counts them. A menu such as `bar: ['home', 'x-retired']` is valid and persisted, but `phoneChrome` ignores the key with no item (a module switched off later), so the phone draws a one-item bar for every member of the tenant. Likewise a saved menu cannot express choices for items that exist only in a member's shell (the editor sends only the keys of the admin's own shell).
**Fix:** Accept as documented, or have `phoneChrome` fall back to the shell's own menu when the saved bar resolves to fewer than `PHONE_BAR_MIN` items.
