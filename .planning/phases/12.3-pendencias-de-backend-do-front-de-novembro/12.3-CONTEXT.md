## Phase Boundary

The ten items of Part 1 of the team's document "O que mudou no front" (branch `ATUALIZAÇÕES-NOVEMBRO`, merged into master locally on 2026-11-09 as `be6374a3`) stop being front-only previews or per-device cookies and are kept by the backend. In scope, in four blocks.

- **Block A, item 1.1.** The three track texts (subtitle, "Para quem é", description) reach the member read of tracks. No migration.
- **Block B, items 1.2 to 1.5.** A track, a course, a module and an event keep a second cover (the "Topo" of a track, of a course and of a module; the vertical poster of an event). Optional columns, API writes and reads, and the forms send the second image.
- **Block C, items 1.6 to 1.9.** The store keeps the Início's "Destaque da loja" (one product), the storefront's "Em destaque" (up to 5, ordered), the admin's own categories (name, icon, order) and each product's category.
- **Block D, item 1.10.** The tenant keeps the phone menu its admin arranged (bar, top, hidden) and the bootstrap returns it.

The web then deletes its provisional code (the cookies `rede_home_promo`, `rede_store_setup`, `rede_store_cats`, `rede_nav_layout` and the older `rede_nav_order`, and the admin-only local preview of the track texts) and reads the API, so what the admin sets is what every member sees.

Not in this phase. Part 2 of the document (17 front-only screens) is already merged. Selling physical goods (shipping, stock, sizes) touches checkout and the payment gateway. The "Continue de onde parou" 40% example shown to the admin stays as the layout aid it is (the API stores no admin progress).

The source brief with the code evidence per item is `12.3-SOURCE.md`.

<decisions>
## Implementation Decisions

Numbered from D-690 so they never collide with the UI-SPEC's `UI-D-665..684` of Phase 12.2.

### Store categories and the products that already exist (area 1)
- **D-690:** The store keeps its categories as rows owned by the tenant, with a name, an icon and a position. The limits are the ones the web already enforces, now owned by the server and exported through the store contract: at most 20 categories per store, a name of at most 30 characters, an icon from the 20 allowed glyphs, and an order that is the order of the storefront's shelves. Deleting a category leaves its products with no category.
- **D-691:** Every store shows the eight built-in categories (cursos, livros, materiais, roupas, perfumes, equipamentos, servicos, outros, with the web's built-in icons) as real, editable rows until its admin changes them. Stores that already exist get them from the migration, and a store enabled later gets them without anyone acting. The seeding runs once per store and never again, so an admin who deleted a category or all of them is not re-seeded. Idempotency and the "once" marker are the planner's to design, and the same must hold in every tenant project (Phase 09.2).
- **D-692:** A one-time initial load puts each existing product into the category its name suggests, with the same rule the web uses today (`guessStoreCategory` in `apps/web/lib/store-categories.ts`; a name that matches nothing goes to "Outros"). The storefront is therefore the same on the day of the deploy. — **Reversibility:** costly — it writes data into every tenant's products, and undoing it would also erase any category an admin chose afterwards.
- **D-693:** After the load a product has no category only when the admin picks "Sem categoria" or when its category is deleted, and such a product sits in no shelf (the same as today's explicit "Sem categoria"). The web's name-guess fallback (`categoryOf` in `apps/web/lib/store-setup.ts`) is removed in this phase, because the server is now the single source.
- **D-694:** The product keeps an optional category tied to the categories table; the contract's `category` on the product card and the product page stops being the fixed enum of eight and carries the category the web compares against the list of categories. Create and edit product accept it. A product with none answers as it does today (absent).

### What was already chosen in the browser (area 2)
- **D-695:** The cookies are ignored once the API answers, with no import and no migration of their values. The code that reads and writes them (`home-promo.ts`, `home-promo-cookie.ts`, `store-setup*.ts`, `phone-nav-layout*.ts`) is deleted in the block that replaces it. This holds because the web of this branch is not released before the back (D-696).
- **D-696:** The web of this branch ships only together with, or after, the back of every block it reads. The release order stays the one in `docs/DEPLOY.md` (migrations, then API and worker, then web). A web build that calls a route the API does not have yet must never reach production. Every new field in an API answer enters the contract as optional, because the web parses answers with strict contracts (most reject an unknown key, and the bootstrap strips one), so a web that does not know a field breaks or silently drops it.

### The phone menu (area 3)
- **D-697:** The phone menu lives in the tenant's brand (`tenants.branding`) as a new optional key, absent meaning "the shell's own menu", added without any backfill as `iconOwnArt` was in Phase 09.3. A new admin route beside the other branding routes saves it for a caller holding the same permission as the branding editor (`tenant.manage`). It validates the rules the web already applies, now on the server: the bar holds 2 to 6 items, the top holds up to 2 own items beside Notificações and Suporte (always at the top), Início stays in the bar, Perfil never goes to the top, keys follow the existing key pattern and at most 16 keys. The bootstrap returns it inside the tenant's branding (declared in the contract, optional, because that schema strips unknown keys). It is an authenticated fact and never enters the public host answer.
- **D-698:** One menu per school, the same for every role on the phone, as the web applies it today. There is no menu per role or per language in this phase. An admin cannot lock themselves out, because Perfil and Configurações stay reachable through the avatar.

### Delivery and proofs (area 4)
- **D-699:** The phase is delivered in four blocks, each with its own exit gate and its own release notes, in this order: A (1.1), B (1.2 to 1.5), C (1.6 to 1.9, with the categories before the product's category), D (1.10). Inside a block the database and API plans come before the web plans. Because of D-696 each block releases its migrations and API alone and early, and the web (with the team's whole front and every rewiring) releases once, after the last block's API is in production. If Igor wants the web released per block, that conflicts with D-695 and must be reopened.
- **D-700:** Proofs follow the house standard. Claude delivers unit tests, integration tests and pgTAP cross-tenant negatives for every new table, column and route, and updates the Playwright specs that the change breaks, without adding a new spec per item. The real-phone rows (the menu, the covers on a phone) and every production step are the owner's, listed as rows of the phase's UAT and release ledger.

### Claude's Discretion
The owner did not ask to decide these, and the web or the document already points the way.
- The category's stable link slug. The `?categoria=` link of the storefront keeps working after a rename, so the slug is set at creation, unique per store and unchanged by a rename. The built-in eight keep their current slugs.
- The name of the second cover columns and the media purpose. They reuse the existing `cover` purpose and the media broker. An empty top cover falls back to the card cover (and an empty module cover to the course cover), as the web does today. No backfill, so existing rows stay as they are.
- Where 1.6 and 1.7 are stored. Research decides between `tenant_modules.settings` of the `store` row (the document's suggestion, no migration) and a small store table. `tenant_modules` today has only a member select policy, so the admin write path is the design point. Whatever is chosen is written through an `admin_tenant` store route guarded by `store.product.manage`, never with a RLS-bypassing role for tenant queries.
- A featured product that is archived, deleted or no longer active is dropped at read time and the rest is completed with the newest products, as the web does today. "Usar os mais recentes" clears the saved list.
- "Restaurar o padrão" in the menu clears the saved key, so a module enabled later appears at its own default place. An item the saved layout does not name keeps its own place after the named ones, and a key with no item (a module off) is ignored, as `phoneChrome` already does.
- Refusal codes and their pt-BR copy for the new validations, following each module's existing `details.<module>` pattern and the bare 404 for an unknown or foreign id (D-23).

### Carried forward from earlier phases (informational)
- [informational] D-69 (Phase 05) — a missing cover takes the brand gradient, never a broken image.
- [informational] D-411 (Phase 08.3) — categories are a per-tenant list managed by the admin; the course categories table is the pattern for a per-tenant ordered list with admin routes.
- [informational] D-23 — an unknown or foreign id is one bare 404.
- [informational] D-562 to D-564 (Phase 09.3) — a branding fact added with a default and no backfill, a panel fact kept out of the public answer.
- [informational] The plan-checker's rules from Phases 09.3 and 12.2 hold — every new table gets RLS and a cross-tenant negative in `supabase/tests/010-rls-coverage.sql` and `020-tenant-isolation.sql`, migrations are generated expand-only and applied only with the owner's word.

## Existing Code Insights

### Reusable Assets
- The `course_categories` table and its admin screens (`apps/web/app/(app)/cursos/categorias/`) — the pattern for a per-tenant ordered list with an admin sheet.
- `StoreSetupPanel.tsx`, `StoreBrowseScreen.tsx`, `StoreManageScreen.tsx`, `ProductForm.tsx` — the store's setup UI already built on the cookie, to rewire to the API.
- `PhoneMenuEditor.tsx` and `apps/web/app/(app)/configuracoes/menu/page.tsx` — the menu editor, to rewire.
- `CoverField.tsx` with `TrackForm.tsx`, `CourseForm.tsx`, `ModuleSheet.tsx` and `EventForm.tsx` — the two-block cover fields, to send the second image.
- The media broker (`useSignedUpload`, `/v1/media/uploads`) and the existing `cover` purpose.

### Established Patterns
- Optional additive fields in contracts, with `.strict()` object parsers on the web (a field the web does not know breaks it), and `.default()` or `.optional()` on the bootstrap.
- Admin routes guarded by `requirePermission('<module>.…')`, with the permission string written as a literal.
- Tenant tables carry `tenant_id`, RLS with `SAME_TENANT` and `adminWritePolicies`, and a cross-tenant negative test.
- Migrations are generated by drizzle-kit as expand-only SQL and applied only with the owner's word. Production releases are the owner's.

### Integration Points
- The member read of tracks, the course read, the module in the course read, the events list and the Início read gain fields.
- The storefront read gains categories and the featured list, and the product card and page gain the category.
- The bootstrap gains the phone menu through the tenant's branding.
- Every tenant project receives the new migrations (Phase 09.2 fan-out).
