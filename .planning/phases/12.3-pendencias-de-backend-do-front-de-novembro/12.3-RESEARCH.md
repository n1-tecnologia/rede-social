## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-690:** The store keeps its categories as rows owned by the tenant, with a name, an icon and a position. The limits are the ones the web already enforces, now owned by the server and exported through the store contract: at most 20 categories per store, a name of at most 30 characters, an icon from the 20 allowed glyphs, and an order that is the order of the storefront's shelves. Deleting a category leaves its products with no category.
- **D-691:** Every store shows the eight built-in categories (cursos, livros, materiais, roupas, perfumes, equipamentos, servicos, outros, with the web's built-in icons) as real, editable rows until its admin changes them. Stores that already exist get them from the migration, and a store enabled later gets them without anyone acting. The seeding runs once per store and never again, so an admin who deleted a category or all of them is not re-seeded. Idempotency and the "once" marker are the planner's to design, and the same must hold in every tenant project (Phase 09.2).
- **D-692:** A one-time initial load puts each existing product into the category its name suggests, with the same rule the web uses today (`guessStoreCategory` in `apps/web/lib/store-categories.ts`; a name that matches nothing goes to "Outros"). The storefront is therefore the same on the day of the deploy. — **Reversibility:** costly — it writes data into every tenant's products, and undoing it would also erase any category an admin chose afterwards.
- **D-693:** After the load a product has no category only when the admin picks "Sem categoria" or when its category is deleted, and such a product sits in no shelf (the same as today's explicit "Sem categoria"). The web's name-guess fallback (`categoryOf` in `apps/web/lib/store-setup.ts`) is removed in this phase, because the server is now the single source.
- **D-694:** The product keeps an optional category tied to the categories table; the contract's `category` on the product card and the product page stops being the fixed enum of eight and carries the category the web compares against the list of categories. Create and edit product accept it. A product with none answers as it does today (absent).
- **D-695:** The cookies are ignored once the API answers, with no import and no migration of their values. The code that reads and writes them (`home-promo.ts`, `home-promo-cookie.ts`, `store-setup*.ts`, `phone-nav-layout*.ts`) is deleted in the block that replaces it. This holds because the web of this branch is not released before the back (D-696).
- **D-696:** The web of this branch ships only together with, or after, the back of every block it reads. The release order stays the one in `docs/DEPLOY.md` (migrations, then API and worker, then web). A web build that calls a route the API does not have yet must never reach production. Every new field in an API answer enters the contract as optional, because the web parses answers with strict contracts (most reject an unknown key, and the bootstrap strips one), so a web that does not know a field breaks or silently drops it.
- **D-697:** The phone menu lives in the tenant's brand (`tenants.branding`) as a new optional key, absent meaning "the shell's own menu", added without any backfill as `iconOwnArt` was in Phase 09.3. A new admin route beside the other branding routes saves it for a caller holding the same permission as the branding editor (`tenant.manage`). It validates the rules the web already applies, now on the server: the bar holds 2 to 6 items, the top holds up to 2 own items beside Notificações and Suporte (always at the top), Início stays in the bar, Perfil never goes to the top, keys follow the existing key pattern and at most 16 keys. The bootstrap returns it inside the tenant's branding (declared in the contract, optional, because that schema strips unknown keys). It is an authenticated fact and never enters the public host answer.
- **D-698:** One menu per school, the same for every role on the phone, as the web applies it today. There is no menu per role or per language in this phase. An admin cannot lock themselves out, because Perfil and Configurações stay reachable through the avatar.
- **D-699:** The phase is delivered in four blocks, each with its own exit gate and its own release notes, in this order: A (1.1), B (1.2 to 1.5), C (1.6 to 1.9, with the categories before the product's category), D (1.10). Inside a block the database and API plans come before the web plans. Because of D-696 each block releases its migrations and API alone and early, and the web (with the team's whole front and every rewiring) releases once, after the last block's API is in production. If Igor wants the web released per block, that conflicts with D-695 and must be reopened.
- **D-700:** Proofs follow the house standard. Claude delivers unit tests, integration tests and pgTAP cross-tenant negatives for every new table, column and route, and updates the Playwright specs that the change breaks, without adding a new spec per item. The real-phone rows (the menu, the covers on a phone) and every production step are the owner's, listed as rows of the phase's UAT and release ledger.

## Summary

All ten items are additive and fit the repo's existing patterns; nothing needs a new package. Block A is a three-column select plus two pure-function fields. Block B is four nullable FK columns (and two more for modules) with the existing `cover` validation. Block C is the only structural work: two new tenant tables, a seeding seam, a one-time SQL load, and the product category. Block D is one optional jsonb key, two kernel-lane routes beside the branding ones, and one trap (below) that would silently erase the menu.

Three findings change the plan the CONTEXT assumed. (1) **A module needs two new image columns, not one**: the PDF (p.5) shows "Cartão · página do curso (16:9)" and "Topo · página do módulo (4:1)" in the module sheet and `course_modules` has no cover column at all today, while CONTEXT block B calls the module's cover "a second cover". (2) **Three branding writers rewrite the whole `branding` jsonb from `ResolvedBranding`**, so a `phoneMenu` key that is not added to `resolveBranding`/`ResolvedBranding` is erased by the next logo upload, colour save or icon removal (the 09.3 "marker disappears" pitfall, verified in code below). (3) **`tenant_modules.settings` is wrong for 1.6/1.7**: it ships to every member in the bootstrap, is cached 30 s per instance, can only be written through the RLS-bypassing admin lane, and the module cannot even import that lane; a small RLS table written through the normal tenant lane is safer and costs one migration that must exist anyway for categories.

**Primary recommendation:** Add `store_categories` (rows) and `store_front` (one row per tenant: promo product, featured array, once-marker) with `tenantReadAdminWritePolicies`, seed through one owner-only SQL function used by both the migration load (products-driven, never `tenant_modules`-driven) and a tenant-pinned lazy definer for stores enabled later; expose `GET /v1/store/front`, `PUT /v1/store/front/promo|featured`, `PUT /v1/store/categories`, and `category` on product create/edit/read; add `phoneMenu` to `tenantBrandingSchema` as `.optional()` and to `ResolvedBranding`/`resolveBranding` in the same change, with a "colour/logo/icon save keeps the menu" test.

### Pattern 1: tenant-read, admin-write table (the store's own)
**What:** `tenantReadAdminWritePolicies('<table>')` — SELECT for the tenant, INSERT/UPDATE/DELETE only for `app.tenant_role() = 'admin_tenant'`; plus `revoke truncate … from authenticated` in the functions migration.
**When to use:** `store_categories`, `store_front`.
**Example (existing):**
```typescript
// Source: packages/modules/store/db/schema.ts:27-41
const tenantReadAdminWritePolicies = (table: string) => [
  pgPolicy(`${table}_select_tenant`, { for: 'select', to: authenticatedRole, using: SAME_TENANT }),
  pgPolicy(`${table}_insert_admin`, { for: 'insert', to: authenticatedRole, withCheck: TENANT_ADMIN }),
  /* update, delete likewise */
];
```
The helper is module-local in `store/db/schema.ts` (courses has its own copy), so the new tables go in the store schema file.

### Pattern 2: owner-only SQL function so pgTAP can run the same logic on a fixture
**What:** the one-off data move is a function, called once by the migration, revoked from every role.
**Precedent:** `20261020230441_access_allowlist_migrate.sql` ("EXECUTE revoked from public, anon, authenticated, service_role; nothing in the running system calls it after this migration") and the 12.1 backfill order (trigger first, backfill second, `SET NOT NULL` last, `not exists` guards make a re-run a no-op).

### Pattern 3: write inside the kernel lane only for tenant-row jsonb (branding)
**What:** `packages/core/server/platform/branding.ts` is the ONLY branding file allowed to import `withAdminTx`; every writer locks the row, merges, calls `pushToCentral(tenantId, ['branding'])`, then `invalidateAllTenantHosts`. A new `setPhoneMenu` follows `setBrandingLook` (lock `for update`, `branding || jsonb_build_object(...)`), and needs one row in `apps/api/tests/admin-lane-inventory/platform.ts` (class `T`).

### Anti-Patterns to Avoid
- **Seeding or loading by `tenant_modules` rows.** In project 0 the central mirror holds a `tenant_modules` row for tenants that live elsewhere; seeding from it plants `store_categories` rows in central for foreign tenants, which `central-clean` reports as residue (and `--strict-empty` requires zero). Drive both the migration and the lazy seed by data that physically exists in the project (products, the tenant lane's own tenant id).
- **A trigger on `tenant_modules` insert/update.** Same residue problem, plus it fires on every mirror push and reconcile.
- **Hand-written `begin`/`commit`/`concurrently` or any `platform.` reference in a migration.** `packages/core/tests/tenant-set-no-platform.test.ts` fails the file.
- **A new `app.*` function containing `limit 1`.** `supabase/tests/040-schema-conventions.sql` pins the set of such functions (`feed_sample_post_ids,membership_for_user,profile_form_default_step`); either avoid the phrase (use `min()`/`order by … fetch first 1 row only`) or extend that assertion deliberately.
- **A tenant table without `tenant_id` as the FIRST index column.** 040 asserts it; and the move engine marks a table with no `tenant_id` as `uncovered_tables` and refuses the move.

## Question 1 — Where 1.6 and 1.7 are stored (recommendation: a table)

**Recommendation: `store_front`, one row per tenant**, `tenant_id` PK, `promo_product_id uuid null references store_products(id) on delete set null`, `featured_product_ids uuid[] not null default '{}'` with `check (cardinality(featured_product_ids) <= 5)`, `categories_seeded_at timestamptz null` (the once-marker of Question 2), `updated_at`. Policies: `tenantReadAdminWritePolicies('store_front')`. A missing row means "defaults" (no promo, empty list, not seeded); writes upsert. Reads need no `moduleFlags` cache and no new role.

Evidence, point by point:

1. **RLS.** `tenant_modules` has exactly one policy, a select one. [VERIFIED: packages/core/db/schema/tenant-modules.ts:44-48] `// Read-only for members: the flags decide what the shell renders, never what it may write.` / `pgPolicy('tenant_modules_tenant_select', { for: 'select', ...`. So an `admin_tenant` write cannot go through the tenant lane.
2. **Writer.** The only writer of `settings` is `patchModuleSettings`, which opens `withAdminTx({ tenantId }, …)` (service_role lane). [VERIFIED: packages/core/server/platform/modules.ts:133-165] That import is Biome-restricted: [VERIFIED: packages/core/db/admin-tx.ts:19-22] "`@rede-social/core/db/admin-tx` is import-restricted by Biome `noRestrictedImports` to `packages/core/server/{tenancy,platform,projects,migrations,secrets}` and `scripts/`". The store module cannot call it; a store route would need a new kernel service that takes module-specific keys (MOD-02 says the kernel knows no module's keys: "this kernel function knows nothing of any module's keys (MOD-02)").
3. **Exposure.** The bootstrap returns every enabled module's `settings` to every member: [VERIFIED: packages/contracts/src/bootstrap.ts:62] `settings: z.record(z.string(), z.unknown()),`, filled from `enabledModulesForBootstrap(flags.keys, flags.settings)` (`apps/api/src/routes/me.ts:279`). `permissionsFor(role, keys, settings)` also composes permissions from the same blob. A product-id list there is public to members and mixed with permission knobs.
4. **Freshness.** Flags are cached per instance for 30 s and `invalidate()` clears only the local instance: [VERIFIED: packages/core/server/modules/flags-cache.ts] `export const MODULE_FLAGS_TTL_MS = 30_000;` and "`invalidate(tenantId)` makes it immediate on the local one". A saved "Em destaque" would flicker for up to 30 s on other instances. A table read has no cache.
5. **Move engine.** `settings` is copied by a special statement, `update public.tenant_modules t set settings = s.settings …` (`projects/move/copy-rows.ts:148`), so it survives a move, but only if the target row exists. A table with `tenant_id` is copied by the catalog-derived plan with no list to maintain; the FK order is computed from the catalog (`fk-order.ts`, `plan.ts:286`). New tables need `tenant_id` or the plan reports `uncovered_tables`.
6. **Phase 09.2 ownership.** `settings` is TENANT-owned and not mirrored (`mirror.ts:62-65`); a table is simply tenant data. No `mirror-fields.test.ts` change (it covers `tenants`/`tenant_modules` columns only).
7. **Referential integrity.** `promo_product_id` gets a real FK (`on delete set null`, which keeps the tests' `delete from public.store_products where name like …` working: store.test.ts:104, store-gate.test.ts:149, payments-*.test.ts, e2e `store-admin.ts:191`). The array has no FK, which is acceptable because the contract is "dropped at read time": products are archived, not deleted (no product-delete path exists in `packages/` or `apps/api/src`; the only hits are test cleanups).
8. **Phase 09.2 fan-out.** One more generated migration in the tenant set; no special handling.

Read shape (member, module on): `GET /v1/store/front` →
```
{ categories: [{ id, name, icon }],          // ordered (see Question 3 for `id`)
  promoProductId: uuid | null,               // only if the product is ACTIVE now
```

## Common Pitfalls

### Pitfall 1: The logo upload erases the phone menu
**What goes wrong:** a key missing from `resolveBranding` is dropped by `completeBrandingUpload`/`applyBrandColors`/`removeIconOverride`, which write the resolved object back.
**How to avoid:** add the key to `ResolvedBranding` + `resolveBranding` in the same plan; three tests.
**Warning signs:** an admin saves the menu, uploads a logo, the menu is the default again.

### Pitfall 2: Seeding in central
**What goes wrong:** a `tenant_modules`-driven or trigger-driven seed writes `store_categories` rows for tenants that live in other projects.
**How to avoid:** products-driven migration, tenant-pinned lazy definer; assert `central-clean` still prints zero in a two-database case.

### Pitfall 3: A `settings` read or write path "because the PDF said so"
**What goes wrong:** members receive the featured ids in the bootstrap, the save needs `withAdminTx`, and flags lag 30 s.
**How to avoid:** the table.

### Pitfall 4: Strict contracts reject a new key
**What goes wrong:** `.strict()` read schemas parsed by an older web, and `bootstrapSchema` silently STRIPS an undeclared key.
**How to avoid:** every new response key `.optional()`; `phoneMenu` declared in `tenantBrandingSchema`; release order migrations → API → web.

### Pitfall 5: SQL and TS guess rules drift
**How to avoid:** one corpus run through both; the TS rule moves into the store contract; the migration is the only SQL copy and never edited later.

### Pitfall 6: Poster-only event edit is a silent no-op
**What goes wrong:** the `update … where (cols) is distinct from (cols)` tuple omits the new column.
**How to avoid:** add the column to both tuples and `LockedEventRow`; integration test that changes only the poster.

### Pitfall 7: Whole-list replace by a stale editor deletes a category another admin just made
**How to avoid:** lock `store_front` `for update`; an item whose `id` no longer exists is a `400 category_invalid` (the web refreshes) and deletion only removes rows omitted from the sent list; the log line carries counts, never names.

### Pitfall 8: `plan.tables.length` pin and the `010` list
**How to avoid:** bump `move-copy.test.ts` to 58 and extend assertion 4 of 010 in the same plan that adds the tables.

```typescript
async function resolveCategory(tx: Tx, ctx: RequestContext, slug: string | null): Promise<string | null> {
  if (slug === null) return null;
```
