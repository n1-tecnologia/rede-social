# Phase 12.3 Plan 13: Storefront and setup sheets on the API front Summary

**The storefront now reads categories, "Em destaque" and the Inicio's promo from one `GET /v1/store/front` call with no cookie, never guesses a category, degrades to a plain product grid when the call fails, and Gerenciar's two setup sheets save to the API through validating server actions with pending, refusal and stale-draft handling.**

## Performance

- **Duration:** about 30 min (17:57 to 18:06 local for the commits)
- **Tasks:** 3 (one tracer, two auto), every behavior task with a RED commit before its GREEN commit
- **Files:** 3 created (all tests), 14 modified

## Accomplishments

- **Read path (Task 1, tracer).** `getStoreFront()` in `lib/store.ts` parses the contract's `storeFrontSchema` made tolerant (`extend` + `strip`, so an added key is ignored) and returns `null` on any failure. `page.tsx` reads it next to the bootstrap and hands it to `StoreBrowseScreen`, which builds a `StoreFrontContext` (`storeFrontContext`): the API categories, the featured ids (the saved list, else the promo product, else the newest), and `plain`. `storeItems` keeps a product's API category only while the store still holds the slug, with no name guess. `storeCategoryTiles` keeps a tile for every category (count 0 reads "Nenhum produto") and `storeFrontView` still skips an empty shelf. `plain` (front missing, or no category) renders `StoreListing` as the whole catalogue newest-first with no chips and no hero.
- **Write path (Task 2).** `setStoreFeatured` and `saveStoreCategories` share one `putFront` that maps the closed `details.store` refusals to `issue`, a bootstrap navigation to `redirect`, anything else to `error`. `setStoreFeaturedAction` and `saveStoreCategoriesAction` validate with the contract's strict schemas before any request, redirect outside any try/catch and revalidate the store screens on success.
- **Sheets.** `StoreSetupPanel` takes `products`, `categories`, `counts`, `featured` (the `custom`/`builtIn` props and the device notes are gone). Save shows "Salvando…" and the sheet cannot be closed while in flight (backdrop, Escape and drag go to a no-op; Cancelar and every field disabled); success closes, toasts ("Destaque salvo.", "Categorias salvas.") and refreshes; a refusal keeps the sheet and the draft with one 14/400 `role="alert"` line directly above Save that takes focus; `featured_invalid` and `category_invalid` refresh and re-seed the draft from the refreshed props. The limits, glyph list and name length come from the contract constants. A new row is sent with no id; a reset replaces only the draft (built-in slugs the store still holds keep their id, the rest are new rows because the API refuses an unknown id).
- **Manage screen (Task 3).** `StoreManageScreen` reads the front (and draws no panel when it cannot), computes counts from the API category of each product, and passes the front's featured ids still on sale. The old name-guess branch is gone from the manage list.
- **Catalog.** `store.json` gets `setup.saving`, `featured.scope`, `categories.scope`, the featured and categories refusal sentences and the two generic failures; `setup.device` is removed.

### Notes, not deviations

- **The grid for a store with no category.** The plan says "with no category there are no chips and the whole catalogue shows" but does not say how. A storefront with a front and zero categories renders the plain grid (`StoreListing`) like the failed-front case, so an admin who has deleted every category and kept a featured list sees the grid and not the hero until a category exists. Flagging in case Igor wants the hero kept in that one case.
- **The old tile rule changed.** The shipped storefront showed a tile only for a category with products; the plan and UI-D-690 keep every category's tile at count 0, so the old view test was rewritten to the eight tiles. The tile of an empty category opens the shipped empty category page.
- **`productCategory` removed.** Its only caller was its own test; it was the name-guess fallback D-693 retires. `isStoreCategory` stays (the chip tag rule uses it).
- **Reset semantics.** "Restaurar as categorias padrão" sends the eight built-ins; slugs the store still holds keep their `id`, the others go without one and the server mints the same slug from the same name (unless taken). No category of the store's outside the eight survives a reset-and-save, which is what "restore" means.
- **TDD gate.** The tasks are `tdd="true"` inside a `type: execute` plan with `workflow.tdd_mode` unset. Every behavior task has its `test(12.3-13)` commit failing before its `feat(12.3-13)` commit. `check tdd-red-evidence` was not run (Vitest emits no TAP, see project memory) and no evidence record was fabricated. The three RED failures are missing-export and missing-behavior failures on the planned behavior, not syntax or discovery errors.
- **No test of `StoreManageScreen` or `StoreBrowseScreen` themselves.** They are server components that compose tested helpers (`storeFrontContext`, `storeItems`, `storeFrontView`, `StoreSetupPanel`); the plan names no test for them.
