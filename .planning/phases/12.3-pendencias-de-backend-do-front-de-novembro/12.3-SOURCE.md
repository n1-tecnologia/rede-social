## The ten items, and what the code shows today

Legend: DB = migration needed; API = route or read needed; WEB = front to rewire once the API answers.

### 1.1 Track texts (subtitle, audience "Para quem é", description) on the member read
- DB: none. `course_tracks` already has `subtitle`, `audience`, `description`
  (`packages/modules/courses/db/schema.ts:434-437`); the admin form already writes them.
- Contract: already OPTIONAL on `learnTrackSchema` (`courses/contracts/index.ts:1668-1676`).
- API: `readMemberArea` reads only `t.id, t.title, t.cover_asset_id` of the tracks
  (`courses/server/learn-service.ts`, the `trackRows` query) and `trackStates` builds the view from that. Add the
  three columns to the select and to the view. `GET /v1/courses/learn/tracks` is the route.
- WEB: remove the admin-only "local preview" that fetches the texts from the management read.

### 1.2 and 1.3 Second cover (the "Topo") of a track and of a course
- DB: `course_tracks` has ONE `cover_asset_id` (`schema.ts:438`) and `courses` has ONE (`schema.ts:163`). Add an
  optional second asset column to each. Empty = the card cover is used for both places, as the web does today.
- API: create and edit (`/v1/courses/tracks*`, `/v1/courses/*`) accept it; the member reads return it.
- WEB: `TrackForm.tsx` and `CourseForm.tsx` (with `CoverField.tsx`) already show two blocks (card 4:3 or 16:9, top
  4:1) but save one image; send the second one, and make the track/course page use the top cover.

### 1.4 Module cover
- DB: `course_modules` (`schema.ts:220`) has no cover column. Add an optional one.
- API: the edit-module route accepts it; the course read returns it.
- WEB: `ModuleSheet.tsx` has the field (card 16:9 and top 4:1) as a local preview only; the module card and the
  module page keep using the course cover until then.

### 1.5 Vertical cover of an event
- DB: `events` (`events/db/schema.ts:83`) has ONE `cover_asset_id`. Add an optional vertical one (1080x1350, 4:5).
- API: create and edit accept it; the events list uses it for the poster.
- WEB: `EventForm.tsx` has "Vertical · lista de eventos" as a browser preview only (`messages/pt-BR/events.json`,
  `cover.as.poster`).

### 1.6 "Destaque da loja" on the Início (one product, chosen by the admin)
- Today: cookie `rede_home_promo` (`apps/web/lib/home-promo.ts`, `home-promo-cookie.ts`), a product id; only the
  admin's device sees it; a member always sees the newest active product.
- Needed: keep the choice per tenant (the document suggests the store module's settings, no migration), a route
  for the admin to save it, and the Início read returning that product for everyone.
- WEB: `HomePromoChoice.tsx`, `HomePromoBody.tsx`, `HomeDashboard.tsx`, `MemberHomeTab.tsx`, `StoreBrowseScreen.tsx`.

### 1.7 "Em destaque" of the storefront (up to 5 products, in order)
- Today: cookie `rede_store_setup`, field `featured` (UUID list, max `STORE_FEATURED_MAX = 5`)
  (`apps/web/lib/store-setup.ts`). First = the big card; the rest is completed with the newest products.
- Needed: keep the list per tenant (same place as 1.6), a route to save it, the storefront read returning it.
- WEB: `StoreSetupPanel.tsx`, `StoreBrowseScreen.tsx`, `StoreManageScreen.tsx`.

### 1.8 Store categories made by the admin
- Today: cookie `rede_store_setup`, field `categories` (`[id, name, icon]`): max 20 categories, name max 30
  characters, id `^[a-z0-9](?:[a-z0-9-]{0,22}[a-z0-9])?$`, 20 allowed icons (`STORE_CATEGORY_ICONS`), and the
  eight built-ins (cursos, livros, materiais, roupas, perfumes, equipamentos, servicos, outros) when untouched.
  The order is the order of the shelves; deleting a category leaves its products with no category.
- DB: no categories table exists in the store (`packages/modules/store/db/schema.ts`). New table per tenant
  (name, icon, position) with RLS and a cross-tenant negative pgTAP test (project rule).
- API: create, rename, reorder, delete; the storefront read returns the categories.
- WEB: `StoreSetupPanel.tsx` and the storefront (blocks, shelves, category page, card chip).

### 1.9 Category of each product
- Today: cookie `rede_store_cats` (`key~category` pairs, key = last 12 hex digits of the product id); with no
  choice the web guesses the category from the product name (`apps/web/lib/store-categories.ts`).
- DB: `store_products` (`store/db/schema.ts:85`) has no category column. Add an optional one tied to 1.8
  (deleting a category must leave the product with none).
- Contract: `category` is already OPTIONAL on `productCardSchema` and `productDetailSchema`, but limited to the
  enum `STORE_PRODUCT_CATEGORIES` of the eight (`store/contracts/index.ts:221`); it becomes the category id.
- API: create and edit product accept it; the card and the product page return it.
- WEB: `ProductForm.tsx`, `loja/[productId]/page.tsx`, `loja/[productId]/editar/page.tsx`, `loja/novo/page.tsx`.

### 1.10 Phone menu ("Menu do app", Configurações › Administração)
- Today: cookie `rede_nav_layout`, value `b:<keys>|t:<keys>|h:<keys>` (bar, top, hidden), plus the older
  `rede_nav_order` (`apps/web/lib/phone-nav-layout.ts`). Rules: bar 2 to 6 items (`PHONE_BAR_MIN/MAX`), top up to
  2 own items (`PHONE_TOP_MAX`), Início only in the bar, Perfil never at the top, Notificações and Suporte always at
  the top; keys `^[a-z0-9][a-z0-9-]{0,31}$`, at most 16. Phone only; the desktop menu does not change.
- Needed: keep the layout per tenant, a route for the admin that validates the same rules, and the bootstrap
  returning it. The bootstrap schema STRIPS unknown keys and every additive field must be `.optional()` or
  `.default()` (`packages/contracts/src/bootstrap.ts`).
- Where: the menu belongs to no module, so `tenant_modules.settings` does not fit it; `tenants.branding` (jsonb,
  `tenantBrandingSchema`) is the candidate. OPEN POINT 1 of the ROADMAP entry.
- WEB: `components/admin/PhoneMenuEditor.tsx`, `app/(app)/configuracoes/menu/page.tsx`, `app/(app)/layout.tsx`,
  the `PhoneLayout` type of `@rede-social/core/ui` (the team also changed `AppShell`, `BottomNav`, `nav.ts`).

## Risks the document itself names

- The web validates API answers with strict contracts: a new field breaks a web version that does not know it. The
  fields entered this branch as optional, so the web of this branch ships before or with the API.
- Every migration runs in production at the merge of master, and homolog shares the same database. With the
  per-tenant Supabase project (Phase 09.2) new migrations join the tenant set and run in every project.
- Existing products stay without a category until someone picks one (or an initial load applies the name guess).
- Provisional front to remove when the API exists: the four cookies above, the admin-only local preview of the
  track texts (1.1), and the "Continue de onde parou" 40% example for the admin (the API stores no admin progress;
  this one is only a layout aid and stays).
- Out of scope in the document: selling physical goods (clothes, perfume, equipment) needs shipping, stock and
  sizes, which touch checkout and the payment gateway.

4. The menu 1.10 (after the open point of where it lives).
