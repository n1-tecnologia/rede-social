# Phase 12.3 Plan 14: Product form category, Destaque da loja and the end of the store cookies Summary

**The product form now chooses a category from the store's own list and sends its slug (or null) to the API, the Inicio's "Destaque da loja" is kept by `PUT /v1/store/front/promo` for every member and loaded by id on the server when it sits outside the newest products, and the seven per-device cookie library files are deleted.**

## Performance

- **Duration:** about 45 min
- **Tasks:** 3 (one tracer, one auto with tdd, one auto verification-only), each behavior task with a RED commit before its GREEN commit
- **Files:** 18 modified, 7 deleted, 0 created

## Accomplishments

- **Task 1 (tracer): the product form.** `novo/page.tsx` and `editar/page.tsx` read `getStoreFront()` and pass the categories (`storeCategoryList`) to `ProductForm`; an unreadable front gives none and the field is hidden. The form starts a create on `guessStoreCategory(name)` (the contract's, the server's own rule) while the store holds that slug, else on "Sem categoria", following the name until the admin touches the menu. Create sends `category: slug | null` exactly as the field shows (no key when the field is hidden); edit starts on the stored slug (`product.category`) and sends the key only when it changed. `category_invalid` draws "Essa categoria não existe mais. Escolha outra." in a `role="alert"` line under the field, keeps every other value and clears on the next pick. The product page reads the chip from the API product's slug, shown only while the store holds it. The four cookie-library files and their test are deleted.
- **Task 2: the Inicio promo.** `setStorePromo` (lib/store.ts, on the shared `putFront`) and `setStorePromoAction` (parse with `frontPromoBodySchema`, redirect outside try/catch, revalidate the store screens). `MemberHomeTab` reads `promoProductId` from `getStoreFront()` for every viewer; `promoProductFor` picks the named product from the products read, else the one loaded by its own id (`loadPromoProduct`, only while active), else the newest. `HomePromoChoice` is now a draft-until-Save sheet: pending (disabled controls, no dismiss), "Destaque da loja salvo." toast and refresh, one alert line above Save for a refusal, stale `promo_invalid` refreshes and re-seeds, "Todos os membros veem este produto no Início." in place of the device note. The three promo library files are deleted.
- **Task 3: exit gate.** No Playwright spec or helper needed an edit (see Deviations); the gate below was run.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] A product-page chip test depended on the deleted name guess**
- **Found during:** Task 1 RED
- **Issue:** the existing page test "draws the state pill beside the category chip ('Mentoria' reads as a service)" relied on the web guessing a category from the name, which D-693 retires.
- **Fix:** the test now gives the product `category: 'servicos'` (what the API sends), and three cases were added: a product with none shows no chip even when its name tells one, an unreadable front shows none, a slug the store no longer holds shows none. The cookie mock of that test file became a `getStoreFront` mock. **Commit:** `65531f00`.

**2. [Rule 3 - Blocking] The promo strings live in `courses.member.json`, not `courses.json`**
- **Found during:** Task 2
- **Issue:** the plan's file list names `messages/pt-BR/courses.json`, but the `courses.member.home.promo.edit.*` keys (and the old `device` note) are in `courses.member.json`.
- **Fix:** edited `courses.member.json`: removed `device`, added `scope`, `saved` and an `errors` pair (`promo_invalid`, `generic`). The refusal sentences are two more strings than the plan counted ("add the two strings"), required by UI-D-686's refusal line. Save, Salvando and Cancelar reuse `store.setup.*`. **Commit:** `f0aef5fd`.

**3. [Rule 1 - Dead code] `promoWithProduct` and the `HomePromoProduct` module removed instead of moved**
- **Issue:** the plan says to keep the pure promo shaping by moving it into `courses-home-view.ts`. With the server building the invitation from the saved promo (`homePromoView({ product: featured })`), the client-side swap `promoWithProduct` has no caller; keeping it would be dead code held up only by its own test.
- **Fix:** dropped it and its equivalence test; the pure selection the view needs now is `promoProductFor` and `promoNeedsLoad` in `courses-home-view.ts`. The `HomePromoProduct` type moved into `HomePromoChoice.tsx`, where the option type uses it.

**4. [Rule 3 - Blocking] One comment edited in a file outside the plan's list**
- `apps/web/lib/phone-nav-layout.ts` named the deleted `lib/store-setup.ts` in a comment; reworded in the Task 1 commit (comment only, that file's own cookie is untouched).

**5. Tests added outside the plan's file list:** `lib/store-front.test.ts` (setStorePromo) and `app/(app)/loja/front-actions.test.ts` (setStorePromoAction), the existing homes of the plan 13 write-helper and action tests, plus `app/(app)/loja/[productId]/page.test.tsx` (named by the plan).

### Task 3: no spec edits

None of `e2e/store.spec.ts`, `e2e/store-admin.ts` or `e2e/payments-store.spec.ts` names a store or promo cookie, and none drives the create form or reads the category field (the payments spec edits an existing product and sends no category unless one is picked; the helper that deletes products by name needs no change). So nothing the change breaks needed an edit, and I added no spec. **Finding, pre-existing, not touched:** `store.spec.ts` asserts a `list` named "Produtos de {tenant}" on `/loja` (lines about 229, 430, 583), but that name belongs to `ProductGrid` and `ProductsManageList`; the storefront redesign of 2026-10-27 (hero, tiles, shelves) does not render it, so those steps were already stale before this plan. Also, the fixtures that `createProduct` inserts have no category, so on an API-driven storefront with categories they sit in no shelf (only in the hero while among its products). Both need an e2e pass on a running stack before the web ships; plan 17 owns the release order.
