# Phase 12.3 manual proofs (M1 to M16)

This file is the ledger of the proofs only the owner can run: a real phone, the homolog deploy, every hosted
tenant project, the production steps of each block, the browser runs that need more disk than the build machine
had, and the reading of the choices the planner took on his own. Everything an agent could build is built and proved
on the local stack (plans 01 to 16, and the exit gate recorded at the end of this file); what is left here cannot
be faked, so nothing in this file is ever recorded as done by an agent.

**The rule.** Every row ships `pending`. A row becomes `passed` only when Igor pastes the evidence of its steps and
the date, in the row, himself. An agent never edits a Status line and never writes evidence it did not see. A
phase whose ledger has a `pending` row closes `human_needed`, never green.

**The evidence rule.** Paste shapes, counts, statuses, HTTP codes, exit codes and the words the screens show.
**Never** a key, a password, a token, a connection string, an e-mail address of a member or a project reference.
This repository is public: replace a project reference by `<ref>`, a host by `<host>`, a tenant or a customer
name by `<tenant>`.

**The procedures** are in `docs/DEPLOY.md`, "Phase 12.3 release (the November front's backend)" (written by plan
17), one subsection per block.

**The order that binds the production rows.** The migrations of every block reach every hosted project first, then
the API and the worker from a rebuilt image, and the web of this branch releases once, after block D's API is live
(D-695, D-696, D-699). A web released earlier would call routes the API does not have.

## M1 to M3, M4: the phone rows

- **Proves:** that what an admin sets is what another person sees on a real device, against the deployed app.
  Phones cannot reach `*.localhost`, so no local run stands in for it.
- **Needs:** the homolog deploy of the release in `docs/DEPLOY.md` "Phase 12.3 release", the store module and the
  courses module on for one homolog tenant, one admin account and one member account of the same tenant, and a
  phone (a home-screen install is welcome, not required). Use iOS Safari and Android Chrome, once with a custom
  tenant brand.
- **M1 steps.** As the admin, open Configurações, Menu do app, move an item from the bar to "Ocultos" and another
  to the top, save ("Menu salvo."). As the member, reload: the phone chrome follows the saved menu. As the admin,
  press "Restaurar o padrão": the member's next load shows the shell's own menu. Then arrange **6 items in the bar
  and 2 at the top** with one long label, at 320 px: no overflow, save and reload keep it (the E9 overflow backstop
  of plan 16). Save a new logo or a new colour afterwards: the saved menu is still there.
- **M2 steps.** As the admin, give a track, a course and a module a card image and a different Topo, and an event a
  horizontal cover and a vertical poster. As the member on the phone: the track page, the course page and the
  module page draw the Topo (a Topo left empty falls back to the card image, then the brand gradient); the
  module cards on the course page draw their own image, else the course's; `/eventos` draws the poster, the event
  page draws the horizontal cover. The track subtitle, "Para quem é" and description show, and an empty one leaves
  no gap (block A; the 320 px clamp of a long subtitle and a long title over the 4:1 banner are the E8 backstops
  of plan 02).
- **M3 steps.** As the admin, save a featured list of up to five products, a "Destaque da loja" for the Início and
  a changed category order. As the member: the storefront shows the chips in that order with each category's
  count, "Em destaque" starts with the first featured product, a product with a category sits in its shelf, and the
  Início's "Destaque da loja" shows the saved product for every member (not only the admin).
- **M4 backstops (plans 02, 07, 08, 13, 14, 16), tick each at 320 and 390 px:** the Topo block's helper wrapping
  in the track, course and module forms and the module and event helpers with a long tenant name; a long subtitle
  clamp; 20 category chips wrapping; 30-character product and category names truncating; no layout shift when the
  Início's promo product is loaded by its own id; the promo sheet with 0 and with 1 product; the phone menu editor
  with 6 in the bar and 2 at the top; the module cards and page with their own images and without.
- **Evidence to paste:** one line per step ("worked" or what you saw), the device and browser, the date.

## M12 and M13: the hosted checks of the load

- **M12.** On every project after M9, for every tenant that had products: `store_categories` holds the eight
  built-in rows (`select tenant_id, count(*) from public.store_categories group by tenant_id`) and no product that
  existed before the load is left without a category (`select count(*) from public.store_products p join
  public.store_front f on f.tenant_id = p.tenant_id where p.category_id is null and f.categories_seeded_at is not
  null` is `0` right after the load, before any admin edit). A store with no product has no row yet; its first
  read seeds it.
- **M13.** On every project right after M9, before any admin edit: `select count(*) from public.store_products p
  join public.store_front f on f.tenant_id = p.tenant_id where p.updated_at > f.categories_seeded_at` is `0`: no
  product's `updated_at` moved because of the load (this is also the property the undo query relies on).
- **Evidence to paste:** per project, the counts only (no tenant id, no project reference).

## M14: the Playwright specs that could not run

- **Why this row exists.** The web plans of the phase (07, 08, 13, 14, 16) could not run Playwright (the disk and
  no server), so every spec they touched is unrun, and the exit gate of plan 17 runs the affected specs only
  behind the disk and Docker preconditions (the result is the "Phase exit gate" section below). Known trips, to be
  fixed in the plan that owns the code and not here:
  - `apps/web/e2e/store.spec.ts` still asserts a list named "Produtos de {tenant}" (around lines 229, 430 and 583)
    that the 2026-10-27 storefront redesign no longer draws, and its `createProduct` fixture inserts products with
    **no category**, so on the API-driven storefront they sit in no shelf. A pass on a running stack is needed
    before the web ships.
  - `courses-admin.spec.ts` (the module sheet's two pickers and the E08 case: a card image and a different Topo, the
    reopened card preview at 16:9), `events.spec.ts` (the poster beside the cover, the list card and the rename),
    `courses-member-area.spec.ts` and `shell.spec.ts` (the phone menu), `payments-store.spec.ts`: written or listed,
    never executed against the stack by the plans; a selector that is off is a run-time fix, not a regression of the
    product.
  - `pnpm --filter @rede-social/web check:static-routes` needs a **fresh** `next build` (the lesson of the wave 6
    gate).
- **Needs:** more than 12 GiB of free disk, no `next dev` running, the local stack and the worker up, the free-space

## M15: Igor's reading of what the planner decided

Answer "keep" per item, or the wording you want instead. Each stands as built until you overturn it.

### The planner's recorded answers OQ-1 to OQ-6 (taken from RESEARCH Open Questions, no locked decision contradicts them)

- **OQ-1** A module keeps TWO optional images, its own card cover and its Topo (`cover_asset_id` and
  `top_cover_asset_id` on `course_modules`), because the table had no cover and the team's sheet has both blocks.
  Lives in plans 03 and 05 and the module contracts.
- **OQ-2** A category's identity in the contract is its **slug** (kept by a rename; the `?categoria=` link and the old
  eight values stay valid); the table keeps its own uuid primary key. Lives in plans 09 and 11
  (`STORE_CATEGORY_SLUG_RE`, `category` on the product card and page).
- **OQ-3** A product CREATE with no `category` key applies the server's name guess, an explicit `null` is "Sem
  categoria"; an edit with no key leaves the category alone, `null` clears, an unknown slug is `400` with
  `details.store = 'category_invalid'`. This keeps D-693 true across the window in which the previous web still
  creates products. Lives in plan 11.
- **OQ-4** The categories are replaced as ONE whole list (draft-and-Save, atomic, one `PUT /v1/store/categories`), not
  by fine-grained create, rename, reorder and delete routes. Lives in plan 12.
- **OQ-5** The phone menu's rules on the server: 16 keys per list (the web's behaviour), Início required in the bar,
  Perfil never at the top, no key in two lists; unknown keys are not rejected. Lives in plan 15
  (`validatePhoneMenu`, `PHONE_MENU_ISSUES`).
- **OQ-6** Category names are unique per store ignoring case (the `lower(name)` index and `category_name_taken`), as
  the web already refused duplicates. Lives in plans 09 and 12.

### The seven UI-SPEC defaults PU-1 to PU-7 (the checker approved the contract, not these rows)

- **PU-1** The "só neste aparelho" lines became "who sees this" lines ("Todos os membros veem este produto no
  Início.", "Vale só no celular. Todos os membros veem este menu."), not deleted.
- **PU-2** A module's Topo falls back to the module's card cover, then the course's cover (not straight to the course).
- **PU-3** If the store front call fails the storefront still shows the products, without chips or hero, and says
  nothing (no visible notice).
- **PU-4** A product with no category sits in no shelf and the admin gets no "{n} sem categoria" counter.
- **PU-5** No sketch gate: no new screen exists.
- **PU-6** "Restaurar as categorias padrão" only resets the draft; Save commits it.
- **PU-7** "Usar os mais recentes" and "Mais recente da loja" save "none" (an empty list or no id), not the id of the
  newest product.

### The judgment calls the executors flagged for you

- **Plan 13.** (1) A store with no category left, or whose front call failed, shows the plain product grid (no
  chips, no hero, newest first); the hero is not kept when the admin deleted every category but kept a featured
  list. (2) Every category keeps its chip at count 0 ("Nenhum produto"), an empty shelf is not drawn. (3) With no
  saved featured list, the Início's promo product leads the hero for every member (before: only the admin's
  cookie). (4) Gerenciar draws no setup panel when the front cannot be read (a whole-list save would delete the real
  one). (5) "Restaurar as categorias padrão" sends the built-in slugs the store still holds with their id, the rest
  as new rows.
- **Plan 12, the slug-history gap.** A slug deleted in an earlier save can be minted again by a later one (no
  history table); only an old `?categoria=` bookmark could land on a different category. Keep, or ask for a history
  table (an architectural change).
- **Plans 04 and 05, the refusal of a foreign or unknown image.** On a course, track or module it is a `400` by name
  (`cover_invalid` / `top_cover_invalid`), not the bare `404` the plan text named; a literal `404` is one line in
  the shared checker plus the card cover's tests.
- **Plans 07 and 08, what an edit sends.** The forms send each image id only when it changed (the existing patch
  rule), not "both on every save"; the event form always re-sends the poster.
- **Plan 08.** The profile events rail still draws the horizontal cover (the poster is only on `/eventos`; one call
  of `eventListPoster` would change it); the lesson cards on the module page keep the course cover.
- **Plan 07.** The admin course page hero still draws the card cover, not the Topo (the Topo is scoped to the member
  pages).
- **Plan 06.** An older web that saves an event without the poster key clears its poster (acceptable because the web
  ships last).
- **Plan 15.** 17 keys in one list is a plain `400` with no `details.phoneMenu` code.
