# Phase 12.3 Plan 12: Store front writes (promo, featured, whole-list categories) Summary

**Three admin routes keep the store front under the tenant lane and RLS: `PUT /v1/store/front/promo`, `PUT /v1/store/front/featured` and the atomic whole-list `PUT /v1/store/categories`, all serialized on the tenant's one `store_front` row lock, with every limit, refusal, stale-draft and delete-versus-product-write race proved.**

## Performance

- **Duration:** about 35 min
- **Tasks:** 3 (one tracer, two auto), each with a RED commit before its GREEN commit
- **Files modified:** 7, no file created

## Accomplishments

- **Contract.** `frontPromoBodySchema`, `frontFeaturedBodySchema` (schema cap 100) and `categoriesBodySchema` with `categoryEntrySchema` (cap 50 entries; an optional slug `id` whose malformed value is `category_invalid`; raw name cap 200 mapped to `category_name_too_long`), all strict.
- **Service.** `lockFront` (seed claim, row ensure, `for update`), `countActiveProducts`, `setPromo`, `setFeatured`, `replaceCategories`, and `readFront` extracted from `getFront` so each write answers from its own transaction. `replaceCategories` validates in a pure function first (count, per-entry name, length, icon, then duplicate names, then repeated ids), then under the lock rejects any unknown id, deletes omitted rows with `slug <> all(...)`, renames in two passes and inserts new rows with `newCategoryId(name, slugs held before the save)`. Log lines carry counts only.
- **Routes.** Three `createRoute`s with the literal `requirePermission('store.product.manage')` (9 occurrences in `routes.ts`), 200/400/403/404 descriptions, mounted on the existing router (the `requireModule` 404 comes from the router middleware).
- **Proofs.** 19 new integration cases in a `store front writes (12.3-12)` describe, one new cross-tenant `it` in `isolation.test.ts`, three inventory entries, 3 contract unit cases.

## Decisions Made

- OQ-4 and OQ-6 recorded as planned (see key-decisions).
- The placeholder of the two-pass update is `chr(1) || slug` and control characters are dropped from names, so no kept name can equal a placeholder (a name such as `~livros` would otherwise collide).
- `lockFront` calls `ensureSeeded` first, so a promo or featured write on a store that never read its front still claims the seed marker and the eight built-ins; the answer carries them.

### Notes, not deviations

- **Contract bodies landed with the tracer.** The three body schemas were written in Task 1's GREEN commit (one contract edit), so Task 3's three contract unit cases passed on their first run; they are proving tests, not a RED. The integration cases of every task have a genuine RED (404 on the missing route).
- **`cleanCategoryName` is not used by the save.** It truncates to 30, but the save must REFUSE a longer name (`category_name_too_long`), so the service folds the name itself (NFC, control characters dropped, space folded, trimmed) and counts code points. `newCategoryId` is used as planned.
- **"Every slug the tenant has ever held" is not tracked.** There is no slug-history table (a new table would be a Rule 4 architectural change). The save mints against every slug held BEFORE the save, which already stops a new row from reusing a slug deleted in the same save (`livros-2`, tested). A slug deleted in an earlier save can be minted again by a later one. Products are left with no category on delete, so no product keeps a stale slug; flagging it for the orchestrator in case the web caches slugs.
- **TDD gate.** `type: execute`, `workflow.tdd_mode` false. `check tdd-red-evidence` was not run (Vitest emits no TAP, see project memory) and no evidence record was fabricated.
- **Commit ledger.** The `gsd-plan-head-before` ledger file of protocol 0c was not written; `commits: 7` and `plan_head_before` were measured with `git rev-list --count 49106926..HEAD`.
- **Residue.** Lazy seeding (plan 11) makes any test that creates a product seed the eight built-ins for rede-demo and rede-lab; `store-gate`, `payments-admin` and the full isolation file leave `store_front` and `store_categories` rows (2 and 16).
