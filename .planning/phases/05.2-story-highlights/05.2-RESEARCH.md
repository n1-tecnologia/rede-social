# Phase 05.2: Story Highlights - Research

**Researched:** 2026-09-25
**Domain:** In-repo refactor + migration: Drizzle/Supabase schema (a one-way table replacement with a data backfill), Hono module routes, raw-SQL services in `@rede-social/module-stories`, the client-side story viewer (grouped sequences, seen state), Next.js 16 App Router surfaces, and Vitest/Playwright/pgTAP validation
**Confidence:** HIGH for the code map, the migration mechanics and the query plans (all of them opened, rehearsed or EXPLAINed against the local Postgres 17.6 this session). MEDIUM for the Instagram-parity viewer choices (secondary sources only). The discretion choices below are recommendations, and each one is pinned by a named test.

## Summary

The phase does not install a package. Everything it needs is already in the tree: Drizzle 0.45.2 / drizzle-kit 0.31.10, Supabase CLI 2.117.0, `motion` 13.3.0 (`Reorder`), and the media broker's `cover` purpose. The work is a model replacement with three new tenant tables, `story_highlights`, `story_highlight_items` and `story_views`. The first two replace `story_community_pins`; the third backs the seen ring. It also needs a group-aware viewer and a rewrite of every surface that reads pins.

I proved the migration shape end to end on this machine. I ran the backfill (one data-modifying CTE) inside a rolled-back transaction against the real local database, which currently holds **6 pins over 3 communities in 2 tenants, 5 distinct stories**. All 6 became items under three "Destaques" highlights. The seeded expired story (`…d4`) was still reachable in both tenants. A negative control (one item deleted) made the in-migration guard raise. I also confirmed that Supabase CLI 2.117 applies a migration file **atomically**: a guard `RAISE` rolled back the whole file, and `supabase_migrations.schema_migrations` recorded nothing. Two drizzle-kit facts shape the plan. First, one `generate` that both creates and drops tables opens an **interactive rename prompt** (`promptNamedWithSchemasConflict`), which a non-TTY executor cannot answer. Second, the generator emits `DROP TABLE` **before** the new tables' FKs, indexes and policies. The migration is therefore **two generated files**: an additive one that carries the hand-written FK, backfill and guard, and a drop-only one that is the gated one-way step.

D-106 keeps `110-communities-stories.sql` green with no index change. Keep `GET /v1/stories` exactly as it is (`expires_at desc, id desc`, an index-only scan on `stories_tenant_expires_idx`) and reverse one bounded page (`limit=25`) in the Início projection. I also measured the alternative: flipping the SQL to `asc` gives `Index Only Scan Backward using stories_tenant_expires_idx`, even with a `>` keyset row comparison. Either option is legal, and the reverse-in-projection one touches no pgTAP assertion. The seen ring stays **one statement**. Add an `exists (… story_views …)` column to `storyProjection` with a **constant** tenant predicate and a `(tenant_id, user_id, story_id)` unique index; this plans as an index-only scan. With the correlated `v.tenant_id = s.tenant_id` form it degraded to a hashed seq scan (measured).

**Primary recommendation:** Build in waves. First, schema and a two-file migration, with the one-way drop behind a `checkpoint:decision` and a backup-then-`migration up` replay on the live local DB. Second, the API (highlight CRUD/reorder/items, publish into a highlight, views batch) with the pin routes deleted. Third, the module UI (group-aware `StoryViewer`, circle variants, shared `HighlightSheet`, `Reorder` list). Fourth, the web wiring (Início row, community row, manage screens, composer row, "Seus stories", viewer "Destacar"). Last, seed, pgTAP, isolation and e2e rewritten, not deleted.

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Highlight model
- **D-100:** **A story can belong to many highlights at once.** The model is a many-to-many join between highlight and story. Today's pins are already many-to-many (one story pinned to several communities), so the migration loses nothing. — **Reversibility:** costly — narrowing to one highlight per story later needs a data migration that decides which membership survives for every multi-highlight story.
- **D-101:** **A highlight's cover defaults to a frame of one of its stories** (the image itself, or the video's thumbnail through the existing media broker). The admin can pick a different story from the highlight **or upload an image**, like the prototype's icon-style covers (`/images/members/cat-full-face.svg`). An uploaded cover rides the Phase 3 signed-upload path with the existing `cover` purpose (`packages/contracts/src/media.ts:32`). It is validated with 05-09's shape: purpose `cover`, kind `image`, status `ready`, resolved inside `withTenantTx`, one bare 404 for any miss.
- **D-102:** **An empty highlight is kept.** It is shown to the admin with an empty state and never shown to members. A highlight is empty when it was created with no stories or when its last story was removed or deleted. Removing or deleting a story never deletes a highlight, so its title, cover and position survive, and the admin can set up highlights before posting.
- **D-103:** **A highlight plays its stories by publish time, oldest first** (Instagram). When the admin added a story doesn't matter, and there is no per-story order inside a highlight: the item row has no `position` column. — **Reversibility:** reversible — an item `position` is additive later.

#### Início row and viewing
- **D-104:** **Início's grouped circle shows the tenant's logo, labelled with the tenant's display name.** This is the same author identity the viewer header already shows (`bootstrap.tenant.branding.logoUrl` / `displayName`, `apps/web/lib/registry.tsx:374-376`). The circle says who is speaking; highlight circles show their covers and titles. This **reverses D-78** (roadmap criterion 2; the docblock at `packages/modules/stories/ui/StoriesStrip.tsx:18` must be rewritten, not left contradicting the code). — **Reversibility:** costly — D-78's own warning applies: the strip's query shape and what the viewer treats as a sequence both change.
- **D-105:** **Server-side seen state ships in this phase.** It promotes V2-CONT-05's seen ring and **reverses D-79**. A per-member `story_views` record is written when a story is shown in the viewer. It is tenant-scoped with RLS and pgTAP cross-tenant negative tests. The grouped circle's ring is **brand-coloured while any active story is unseen** by the caller and neutral once all are seen. **Opening the circle resumes at the first unseen story**; if everything is seen, playback starts at the first story. The state is identical across devices. D-79 rejected a device-local variant (`localStorage`), and that stays rejected. The admin's "quem viu" list is **not** built. It stays V2 on the same table. — **Reversibility:** reversible — the table is additive, and dropping it only removes the ring.
- **D-106:** **The grouped circle plays active stories oldest → newest**, reversing today's newest-first sequence. The sequence order is the contract. The planner decides whether the API read flips its ordering or the projection reverses one bounded page. Either way, `110-communities-stories.sql`'s EXPLAIN assertions (index-only scan on `stories_tenant_expires_idx`, schema docblock item 2) must stay green.
- **D-107:** **At the end of a circle's sequence the viewer moves on to the next circle in the same row.** On Início: grouped circle → first highlight → next highlight… On a community page: highlight → next highlight. The viewer closes after the row's last circle, and swipe-down still closes anywhere. This replaces the "end closes" rule at `packages/modules/stories/ui/StoryViewer.tsx:219`.

#### Admin doors and curation
- **D-108:** **The admin's publish door stays the leading "+" circle ("Seu story", D-80)** in front of the grouped circle on Início. The community page keeps its leading "+" (D-92). The admin's Início row reads **[+ Seu story] [tenant circle] [highlights…] [manage circle]**. Members never see the "+" or the manage circle. An admin with no active stories and no highlights still sees both admin circles, extending UI-D-26's admin exception. A member with nothing to see still gets no node at all (UI-D-26's all-or-nothing rule).
- **D-109:** **Highlight curation sits behind an admin-only trailing circle** at the end of each row (Início and every active community). It opens a **per-place "Destaques" manage screen** listing that place's highlights in row order. The screen offers **drag-to-reorder**, a **"Novo destaque"** action, and tap → an **edit sheet**: title, cover (D-101), the highlight's stories with remove, "Adicionar stories", and delete-highlight behind a confirm. There is one visible door for all curation and no long-press gestures. Instagram-style long-press was rejected as hard to discover, and dragging circles inside a scrolling row is fiddly on phones.
- **D-110:** **A story is added to or removed from highlights through ONE shared highlight sheet.** The sheet is a checklist of highlights grouped by place (Início first, then active communities). Three routes reach it:
  1. an admin-only **"Destacar"** action in the viewer on any story. It pauses playback while open, like the comment sheet (D-82).
  2. the **refactored `PinStorySheet`** on "Seus stories" (`/stories/meus`). D-84's history screen stays the admin's story home.
  3. **"Adicionar stories"** inside a highlight's edit sheet, which picks from the admin's story history, expired stories included.

  All three are the same component with the same rows. None of them forks it.

#### Composer and publishing into a highlight
- **D-111:** **05.1's "Publicar em: {Nenhuma comunidade | nome}" row (D-97, UI-D-54) becomes ONE row: "Destaque: {Nenhum | ‹lugar› · ‹destaque›} ›".** It sits in the same bottom-bar spot and opens the shared sheet (D-110) in single-select mode. Place and highlight are one choice. **"Nenhum" is the zero-tap default** when `/stories/publicar` has no context, which carries 05.1 criterion 5: a tenant-wide story must never become harder to publish. **Every published story is in Início's grouped circle for its 24 h, whatever highlight it goes into** (D-96 carried, roadmap criterion 2 "ONE circle holds all of the tenant's active stories").
- **D-112:** **Opened from a community's "+"** (`?comunidade={id}`, with D-93's resolution rules carried: unknown, foreign or archived falls back silently, first value wins), **the row arrives pre-filled with that community's first highlight in row order**. The admin can change it to any other highlight or to "Nenhum". **If the community has no highlights yet**, the row reads **"Escolher destaque"** and the sheet puts **"Novo destaque"** first. From a community origin, the composer must not publish silently into "Nenhum" unless the admin has seen that choice (the roadmap's "publishing from a community asks for one of that community's highlights"). "Nenhum" stays selectable explicitly. The exact gate (open the sheet on "Publicar", or disable "Publicar" until a choice is made) is a UI-SPEC decision.
- **D-113:** **At publish, a story goes into ONE highlight or none.** D-95's one-or-none carries over and the publish contract stays a single optional id. More highlights are added afterwards through D-110's routes. — **Reversibility:** reversible — widening to an array is additive.
- **D-114:** **The composer's sheet can create a highlight inline.** "Novo destaque" asks only for a title. The new highlight, the story and the membership row are written in the **same `withTenantTx`**, carrying D-99's one-write rule: no client-side "create, then publish, then add" sequence exists anywhere. The new highlight's cover defaults to this story.
- **D-115:** **Where the admin lands** generalises UI-D-57. After publishing into a community highlight → `/comunidades/{id}`. Into an Início highlight or none → `/inicio`. Close or confirmed discard returns to the origin. The success toast names the destination.

#### Retiring the pin model (roadmap criteria 4 and 5)
- **D-116:** **Loose pinning is removed, not kept alongside highlights.** These all get highlight equivalents or go away:
  - `story_community_pins`
  - `PUT`/`DELETE /v1/stories/{storyId}/pins/{communityId}` and `GET /v1/stories/{storyId}/pins`
  - `GET /v1/stories/pinned` (`listCommunityHighlights`)
  - the `story.pinned`/`story.unpinned` events
  - `publishStory`'s optional `communityId` (05.1)

  **Migration default** (the roadmap's proposal; the user did not re-open it): **every community with pins gets ONE highlight titled "Destaques"** holding exactly its pinned stories. Each pin's `pinned_by_user_id`/`pinned_at` carries over as the item's added-by/added-at, and the cover is the community's most recently pinned story. No pin is lost: the migration's pgTAP asserts that the pre-migration pin count per community equals the post-migration item count, and that the seeded expired-but-pinned story (`scripts/seed.ts:731-739`) is still reachable through its highlight. — **Reversibility:** one-way — it drops a table and a published API contract (the pin routes and 05.1's `communityId` publish field). Roadmap criterion 5 requires this migration to be "planned and reviewed explicitly", so the planner gates it with a `checkpoint:decision`.

### Claude's Discretion
The user moved on without deciding the items below. Decide them in research/planning, record the choice and pin it with tests. Do not ask the user again.

**Highlight ownership and rules**
- **Each highlight belongs to exactly ONE place**: Início (tenant-level) or one community. This follows the roadmap ("on Início and on any community", "a community page shows only its highlights"). Recommended shape: a nullable `community_id` where null means Início. The FK is hand-written SQL inside the migration, because a drizzle `.references()` across modules is the edge `turbo boundaries` denies (05-03/05-05 precedent). A tenant-first index serves the row order. The shape has to leave room for Phase 10's creator-scoped publishing without being reshaped.
- Title rules: a length cap (Instagram uses 15; a 10px label under a 64px circle truncates), required and trimmed, and whether duplicate titles in one place are allowed.
- Row order: an admin-defined `position` per place, where a new highlight lands (start or end of the row), and how a reorder is written (dense renumber in one transaction vs fractional keys).
- Default cover when the admin never picked one (most recently added story vs first by publish time), and the fallback when the cover story is removed or deleted: the next default, else D-69's brand gradient with the title's initial. Also the uploaded cover's lifecycle when it is replaced.
- Delete semantics. Recommended: deleting a highlight hard-deletes it and its item rows, and removing a story from a highlight hard-deletes the join row. This follows the schema docblock's item 5 reasoning for pins: no authored content, no moderation evidence, and the unique pair is the idempotency arbiter. Stories are never touched.
- **The expiry override carries over:** a highlight item row IS the override (schema docblock item 6). Highlight reads carry no expiry predicate, and that is asserted under a clock the test controls.

**Seen state mechanics**
- What counts as "seen": the segment starting vs completing. Also the write's idempotency (unique per story + member, `on conflict do nothing`), batching, whether the admin's own views are recorded, the endpoint shape, and the query budget for the ring (one bounded check per strip render, no N+1).
- Whether watching a story inside a highlight marks it seen for the grouped circle. Default: yes, because it is the same story id.
- **Seen rings on highlight circles: recommended NONE** (neutral ring, as on Instagram). Highlights are an archive, not news.

**Viewer navigation**
- Tapping back on a circle's first story goes to the previous circle. Also: whether a horizontal swipe skips whole circles, and pre-mounting the next circle's first media.
- What the admin sees when the viewer reaches an empty highlight (skip it; members never have one in their row).

**Edges**
- **Archived community:** its highlights stay readable on the read-only page opened by direct link. It gets no "+" and no manage circle (D-93's analogue), the shared sheet lists active communities only, and adding a story to an archived community's highlight is refused with the successor of `pin: 'archived'`, including 05.1's composer race (UI-D-58).
- **`communities` module off:** community highlights are unreachable along with their pages, and their rows stay untouched. Início's highlights are unaffected, and the sheet lists Início only. **`stories` module off:** the whole row is gone (today's rule).

**API, permissions and events**
- Which permission guards curation and publishing into a highlight. Recommended: `stories.story.manage`, already composed for `admin_tenant`. Compose the check so Phase 10's "only a community's creator publishes in it: posts, stories and highlights" becomes a seam, not a rewrite. Guards use permissions, never roles (04-01).
- Route shapes: highlight CRUD, reorder, item add/remove, the publish body's `highlightId` plus the inline new-highlight payload (D-114), and the list reads for the Início row and a community row.
- Event vocabulary (e.g. `story.highlighted`/`story.unhighlighted`, `highlight.created/updated/deleted`). Payloads are **ids only**: no caption and no title in a log line (T-05-29, T-05-06). Events count **transitions, not requests**, the same rule as the pin events. They are queued with `emit` after `withTenantTx` resolves (MOD-03).
- Highlights live **inside `@rede-social/module-stories`** (recommended): the same registry key `stories` and no new module key.

**UI**
- The manage screen's routes (e.g. `/stories/destaques` for Início, `/comunidades/{id}/destaques`). Drag reorder can use `motion`'s `Reorder`; `motion@13.3.0` is already a dependency of `@rede-social/module-stories` and `@rede-social/ui`. It needs an accessible alternative (move up/down) for keyboard and screen-reader users.
- What a "Seus stories" row shows in place of the pinned state (e.g. "Em 2 destaques").
- New pt-BR copy in the `stories` / `communities` catalogs, with no literals (`scripts/check-ui-literals.sh`).

**Seed and tests**
- Replace the two seeded pins with highlights: one Início highlight and the migrated community "Destaques", including the expired story a highlight keeps alive and one empty highlight only the admin sees. Seed `story_views` so a member's ring shows both states.
- Extend the two-tenant pgTAP and API isolation suite with every new table, and `010-rls-coverage.sql` with its policies. Every cross-tenant case asserts its positive control in the same test (03-08).

### Deferred Ideas (OUT OF SCOPE)
- **"Quem viu" (the admin's viewer list)**, the other half of V2-CONT-05. It reads the same `story_views` table D-105 creates, so it arrives later as a read with no migration.
- **Seen rings on highlight circles.** Recommended none (Claude's discretion); revisit only if the pilot asks.
- **A per-story order inside a highlight** (D-103 chose publish time).
- **Adding a story to several highlights at publish** (D-113 chose one or none).

- **Member stories grouped per author in Explorar**, and creator-scoped highlight publishing. Both are Phase 10, built on this phase's grouped viewer.

### Pattern 2: The two-file migration (the one-way step isolated)

### Pattern 3: The highlight service block

- **`resolveHighlightPlace(tx, ctx, { communityId })`** is the ONE place-resolution seam (D-K). For `communityId === null` (Início) it returns the tenant place. Otherwise it: (a) answers a bare 404 when `communities` is off, verbatim from `feed/server/service.ts:390`; (b) runs `select c.status from communities c where c.id = $1 and c.tenant_id = $2 and c.deleted_at is null for share`; (c) turns a miss into a bare 404; (d) for write intents that add content, refuses a non-`active` community with `400 { highlight: 'archived' }`. `FOR SHARE` closes 05.1's residual R-1 ("reads community status without `FOR SHARE`", STATE.md) for the new path.
- **`resolveHighlight(tx, ctx, highlightId, { lock })`** selects the highlight in-lane (`tenant_id` predicate + RLS), then resolves its place. A miss is a bare 404.
- **Writes to one place's row order** (create, reorder) first `select id from story_highlights where tenant_id = $t and community_id is not distinct from $c for update`. That serialises appends and renumbers per place.
- **Item add:** `insert into story_highlight_items (…) select $t, h.id, s.id, $u from story_highlights h, stories s where h.id=$1 and h.tenant_id=$t and s.id=$2 and s.tenant_id=$t and s.deleted_at is null on conflict (highlight_id, story_id) do nothing returning id`. A zero-row insert with an existing pair is a repeat (200). A miss is resolved first, so it is always the bare 404. Emit `story.highlighted` only when `returning` produced a row. Optionally cap `STORY_HIGHLIGHT_MAX_ITEMS = 100` → `400 { highlight: 'full' }` (count under the highlight row lock).
- **Reads:** row read = one statement over `story_highlights` with a `lateral` (or correlated subqueries) for the member-visible item count and the default-cover story's asset. Items read = one statement joining items → stories → media_assets, `order by s.published_at, s.id` (D-103), `limit 100`, with no expiry predicate.

The refusal vocabulary is `STORY_HIGHLIGHT_ISSUES = ['archived', 'title_invalid', 'order_stale', 'full'] as const`, carried in `details.highlight`. Every miss is a bare 404. `communityId` is **removed** from `publishStorySchema`. Because the schema is `.strict()`, a stale client that still sends it gets `400 VALIDATION_FAILED`.

### Pattern 5: Seen state

- **Projection column** (one statement, measured):
  ```sql
  exists (select 1 from story_views v
           where v.tenant_id = ${ctx.tenantId}::uuid   -- CONSTANT, not v.tenant_id = s.tenant_id
             and v.user_id   = ${viewerUserId}::uuid
             and v.story_id  = s.id) as viewer_seen
  ```
  Measured with 50,200 view rows and 400 stories: the constant form planned `SubPlan -> Index Only Scan using story_views_probe_uq … Index Cond: ((tenant_id = …) AND (user_id = …))`. The correlated form (`v.tenant_id = s.tenant_id`) planned `SubPlan -> Seq Scan on story_views_probe v Filter: (user_id = …)`. A story-first index `(tenant_id, story_id, user_id)` also degraded to a hashed Seq Scan (`Rows Removed by Filter: 50000`). [VERIFIED: EXPLAIN / EXPLAIN ANALYZE on local Postgres 17.6, rolled back] The index order is therefore `(tenant_id, user_id, story_id)`.
- **Write:** `insert into story_views (tenant_id, user_id, story_id) select ${t}, ${u}, s.id from stories s where s.id = any(${ids}::uuid[]) and s.tenant_id = ${t} and s.deleted_at is null on conflict (tenant_id, user_id, story_id) do nothing`.
- **Client:** the viewer reports `onSegmentShown(storyId)` when the current segment's media is ready. `StoriesSurface` keeps a session `Set` (optimistic ring + resume without a refresh) and a buffer, flushed on group change, on close, when the buffer reaches 10, and on `visibilitychange → hidden`. Failures are logged and swallowed; the ring is not worth an error toast.

### Pattern 6: Group-aware viewer

**What:** `StoryViewer` takes `groups: readonly { key: string; items: readonly StoryViewerItem[] | null; header? }[]`, `initialGroup`, `initialIndex`, `onNeedGroup(g)` (for lazy highlight items) and `onSegmentShown(storyId)`. Existing single-sequence callers (history, deep link) pass one group.
**Rules:** the position is `(g, i)`. Progress bars show `groups[g]` only. **Every per-segment key is `${group.key}:${item.id}`** (see Pitfall 4). The neighbour window covers `i±1` in the group plus `groups[g+1].items[0]` when `i` is last. A group with `items === null` shows the loading state and calls `onNeedGroup`. An empty group is skipped in both directions.

### Anti-Patterns to Avoid
- **A combined create+drop `drizzle-kit generate`:** it prompts, and it orders DROP before the new FKs.
- **Backfill in a separate `--custom` file:** the `drop_example_module` header's argument applies. Keep the copy and its guard in the same file as the table creation.
- **Flipping `GET /v1/stories` to `asc` just for D-106:** it is legal (measured backward scan), but it changes the keyset contract and every desc-order test for no gain. Reverse one bounded page in the Início projection instead.
- **Correlated tenant predicate in the seen subquery:** it turns into a seq scan at volume (measured).
- **Loading every highlight's items into `/inicio` SSR:** the payload is N×M. Fetch lazily per circle and prefetch the next.
- **A role check anywhere, or reading `bootstrap.membership.role` for the manage circle:** use `bootstrap.permissions.includes('stories.story.manage')`.

## Common Pitfalls

### Pitfall 1: drizzle-kit's rename prompt stalls the executor
**What goes wrong:** `pnpm db:generate` hangs or fails when the schema diff has both created and deleted tables.
**Why:** `promptNamedWithSchemasConflict` (bin.cjs:32794).
**How to avoid:** use two generate steps (Pattern 2).
**Warning signs:** a "created or renamed" question in the output.

### Pitfall 2: The projection still counts pins after the drop
**What goes wrong:** every story read 500s (`relation "story_community_pins" does not exist`).
**Why:** `storyProjection` (`service.ts:131-134`) and `readPinnedCount` read the table.
**How to avoid:** the plan that applies file 2 also switches the projection to `(select count(*)::int from story_highlight_items hi where hi.story_id = s.id) as highlight_count`.
**Warning signs:** 500s on `/v1/stories` right after `migration up`.

### Pitfall 3: Fresh reset "proves" no-loss vacuously
**What goes wrong:** pgTAP passes with zero pins migrated.
**Why:** the seed runs after migrations.
**How to avoid:** the guard in file 1 plus the live replay on the current DB, plus an optional rehearsal: `supabase db reset --version <file-1 predecessor>` → insert an edge fixture (a story in two communities, an expired story, a soft-deleted story, an archived community) → `migration up` → assert. The regular 120 pgTAP asserts post-seed facts only (the seeded expired story reachable through "Destaques").

### Pitfall 4: Duplicate segment keys in the grouped viewer
**What goes wrong:** React key collisions and a shared `mediaState` / `canPlay` / `blocked` between two segments.
**Why:** a story published into an Início highlight is in BOTH the tenant circle and that highlight (D-111). D-100 also allows one story in two highlights. `StoryViewer` keys by `item.id` (`:497`, `mediaState[item.id]`).
**How to avoid:** use the composite segment key `${group.key}:${item.id}` everywhere.
**Warning signs:** the React key warning; a video's "blocked" badge appearing on another circle.

### Pitfall 5: The EXPLAIN pins in 110 go red
**What goes wrong:** a changed strip statement no longer matches the pinned index plan.
**Why:** 110 assertions 44-45 EXPLAIN the literal desc statement.
**How to avoid:** keep `listActiveStories` SQL unchanged except the added `viewer_seen` column. It is a subplan, and the outer plan stays `Index Only Scan using stories_tenant_expires_idx` (measured). Add a new EXPLAIN in 120 naming `story_views_uq` for the subplan, with no `Seq Scan on story_views`.

### Pitfall 6: Member sees an empty or broken highlight
**What goes wrong:** a circle opens onto nothing, or onto a processing video.
**How to avoid:** the member row read filters on the member-visible item count > 0 (D-H), computed with the same predicate as the items read. One SQL fragment is shared by both.

### Pitfall 7: Next static/dynamic route collision
**What goes wrong:** `/stories/destaques` could be shadowed by `/stories/[storyId]`.
**How to avoid:** App Router resolves a static segment before a dynamic sibling [ASSUMED]. An e2e loads `/stories/destaques` as an admin and asserts the manage screen, and `check-static-routes.sh` gets the new REQUIRED_KEYS.

### Pitfall 8: Stale catalog in e2e
**What goes wrong:** new pt-BR keys are not visible to Playwright.
**How to avoid:** use the 05.1-05 precedent: run e2e against a production `next start` on :3100 through a scratchpad config (STATE.md 05.1-05).

### Pitfall 9: Publish-into-highlight privilege seam
**What goes wrong:** a V2 member with only `publish` curates through the publish route.
**How to avoid:** keep 05.1's in-handler manage check (`routes.ts:418-421`), keyed on `highlightId || newHighlight`, and run it BEFORE any lookup.
