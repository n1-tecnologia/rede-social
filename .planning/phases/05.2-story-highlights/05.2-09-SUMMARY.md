# Phase 05.2 Plan 09: The Highlight Manage Screen and the Admin Doors Summary

**An admin can now curate highlights from one door per place. A dashed "Gerenciar" circle ends the Início row and every active community's row. It opens a "Destaques" screen where the admin creates, renames, re-covers, reorders and deletes highlights, and adds stories to them, expired ones included.**
- **Reordering** works by dragging the handle, with the keyboard arrows, or with the edit sheet's up/down buttons. Each move is saved as one full permutation.
- **The cover** is a story frame, an uploaded image, or the automatic rule. The upload uses the Phase 3 machinery with purpose `cover`, and no asset is ever deleted.
- **"Adicionar stories"** uses the same toggle machine as the other two routes.
- **Empty highlights** appear only in the admin's row, inside the dashed ring, and open their edit sheet directly.

## Accomplishments

- **`HighlightManageList`** (UI-D-72/73) is a `motion/react` `Reorder.Group`, and each item disables its own drag listener. The drag starts from a 44x44 `GripVertical` handle with `touch-action: none`, so a finger on the row body scrolls the page.
  - With the handle focused, ArrowUp/ArrowDown moves the row one place and focus stays on the handle. One polite live region says "{title} agora está na posição {position} de {total}.".
  - Each gesture sends one save with the full permutation. The list keeps the last order the server confirmed, and a refused save reverts to it.
  - Reduced motion makes the layout transition instant. A lifted card gets the UI-SPEC shadow and `z-10`, with no scale.
- **`HighlightEditSheet`** (UI-D-74..76) is one `BottomSheet` with three body steps. Focus goes to each step's heading, and "Voltar" returns it to the control that opened the step.
  - **Main step:** a 64px cover preview with "Trocar capa". The name has an explicit "Salvar nome", enabled only by a trimmed, non-empty, changed value. "Posição {p} de {t}" sits beside up/down buttons that are disabled at the ends.
  - **Stories:** listed oldest first. A non-ready story shows its Phase 3 pill, and the resolved cover story shows the "Capa" pill. Each row has an optimistic remove with no confirm.
  - **Delete:** a ghost danger "Excluir destaque" opens a `ConfirmDialog tone="danger"`.
  - **Cover step:** the host's upload tile first, then one circle per image story, with the current cover badged. "Usar capa automática" appears only when a cover was chosen, and a "no images" note shows when there are none.
  - **Picker step:** `HighlightMembershipList` with story rows, the host's `InfiniteScroll` and the host's empty node.
  - **Variants:** an archived community keeps only remove and delete. An empty highlight shows `EmptyState plain` with "Adicionar stories".
- **Six validated curation actions** (create, rename, cover, delete, reorder, and the edit read).
  - Each checks its input with the contract's Zod before any request and maps refusals to `archived | title_invalid | order_stale | full | generic`.
  - On success, each revalidates `/inicio` or `/comunidades/{id}`. Session refusals redirect outside the try/catch.
  - Logs carry the action, the ids and the issue code only.
- **Two manage routes**, both dynamic and in `REQUIRED_KEYS`. A caller without `stories.story.manage` gets `notFound()`. Each page reads the curator row once.
  - `?editar=` is honoured only for a uuid in that place's list (T-05.2-41).
  - An archived community renders the UI-D-80 note, with no "Novo destaque" and no handles.
  - The `HighlightManager` island owns the create sheet, the list, the edit sheet and its three data paths: the edit read, the upload, and the history pager.
- **Admin doors in both rows** (UI-D-63, D-108, D-109). A curator reads `scope: 'all'`.
  - Highlights with a member-visible story stay viewer groups.
  - An empty highlight becomes a dashed link to `…/destaques?editar={id}` and takes no group number.
  - A trailing dashed "Gerenciar" link ends the row. An admin with nothing else still gets "+ Seu story" and "Gerenciar".
  - An archived community keeps the member read and gets no "Gerenciar".
- **WINDOWS.md 45 and 46 are closed.** Both empty-state "Criar destaque" links now reach a real route.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Correctness] `isCover` reads the resolved cover asset, not `coverStoryId`**
- **Found during:** Task 2
- **Issue:** the plan signs the view `highlightEditStoryView(story, coverStoryId, …)`. `coverStoryId` is null under the automatic rule (R-D-D rule 3), and it can name a chosen story that no longer resolves (a video, or a removed item). The "Capa" pill would then miss the real cover, or mark a wrong one.
- **Fix:** the view takes `coverAssetId`, and `isCover` is true when the story is an image whose media asset is the resolved cover asset. This covers rules 2 and 3 with one comparison, and marks nothing for an uploaded cover (rule 1). Case 27 pins all three.
- **Committed in:** `a088e35` / `915c598`

**2. [Rule 3 - Blocking] Files touched outside the task lists**
- **Found during:** Task 3
- **Issue:** the plan's lists leave out four files the work depends on:
  - `loadMoreOwnStoriesAction(cursor: string)` could not read the first page.
  - The circle builders had to be shared by both rows.
  - The manage routes needed a read that tells a 404 from a failure.
