<objective>
The phase's tracer: highlights exist, end to end, at the API — without touching anything that
still reads pins.

An `admin_tenant` creates a named highlight on Início, puts a story (an EXPIRED one, to prove the
override) into it, and a member reads the Início row and the highlight's stories back. That one
path runs through every layer the rest of the phase builds on: the two new tables, migration file
1 (with the pin → highlight backfill and its no-loss guard), the Zod contract, the service with the
ONE place-resolution seam, the guarded routes, and the integration suite. Because the migration is
additive, it is also applied to the developer's LIVE local database — after a data-only backup —
which is the no-loss replay on real pins that a fresh reset can never give (RESEARCH Pitfall 3).

The second half proves the new tables are tenant-isolated inside Postgres and at the API, and
seeds the highlights every later plan's screens and e2e read. It runs on a freshly reset database,
and the reset happens only after the developer says so.

Purpose: the one mechanism every later 05.2 plan (curation, rows, sheets, composer, seen state,
retirement) extends — proven on the agent's best early-context tokens.
Output: schema + migration file 1, the highlight contract and four routes, the tracer integration
cases, pgTAP 120, the isolation extensions, and the seeded highlights.

Budget note: this plan exceeds a 100k projection on purpose — the tracer is one coherent vertical
slice (DB → migration → contract → service → route → test) plus its isolation proof, and slicing it
thinner would leave a migration without its guard or tables without their isolation tests.

Task-count note: its three tasks (a raw tag count reads 4 because it also counts the tasks wrapper element) stay one plan because the reset-consent checkpoint must sit between the tracer that writes migration file 1 and the task that proves it on the reset database — split apart, the migration would ship without its isolation proof.

D-101 scope: covers are image-only in 05.2 — the developer's recorded plan-time decision (2026-09-25), taken before this plan builds any cover code; see planning decision 4.

<planning_decisions>
Decisions this plan takes where CONTEXT left discretion. Each is pinned by a named test.

1. **Ownership shape (R-D-A):** `story_highlights.community_id uuid NULL` — null means Início. The
   FK to `communities` is hand-written SQL in file 1 (`ON DELETE CASCADE`), never a drizzle
   `.references()` (MOD-02). No `place_kind` column: two places only, and Phase 10's creator seam
   lives in the service (`resolveHighlightPlace`), not in the shape.
2. **Title (R-D-B):** required, trimmed, 1..15 UTF-16 units (`STORY_HIGHLIGHT_MAX_TITLE = 15`),
   duplicates allowed inside a place. DB backstop `char_length(title) between 1 and 15 and title =
   btrim(title)`.
3. **Order (R-D-C):** `position int not null check (position >= 0)`, no unique index, read `order by
   position, id`; a new highlight appends at the end under a lock on its place's rows.
4. **Cover (R-D-D):** resolved at READ time in the row statement (rules 1-3 in the frontmatter).
   Image items only, because the media broker serves no video poster (RESEARCH Open Question 1).
   **D-101 video-thumbnail branch: developer chose image-only at plan time, 2026-09-25, before any
   cover code exists; poster variant deferred as additive.** Only image stories supply a highlight's
   automatic cover or a chosen story cover; a highlight whose items are all videos gets the fallback
   cover (rule 3 finds nothing, so none). A later broker `poster` variant slots into rules 2 and 3 as
   one more branch, with no schema change and no migration. The decision is recorded in D-101
   (`05.2-CONTEXT.md`), so no plan asks it again.
5. **Member-visible item (R-D-H):** `s.deleted_at is null and a.status = 'ready'`, written ONCE as a
   SQL fragment shared by the row read (for `itemCount` and the member filter) and the items read,
   so the two can never disagree about what "empty" means (Pitfall 6).
6. **Views live in their own migration.** `story_views` (HIGHLIGHT-06) is created by plan 10's own
   create-only generate, so this file carries exactly the two tables the backfill needs.
7. **Pins stay.** This plan adds; plan 11 removes. Every intermediate commit of the phase stays green
   because no surface loses its data source before its replacement ships.
8. **Deploy order:** API before web (recorded for Phase 01.1; local-only now, cloud deferred).
</planning_decisions>

belongs to exactly one PLACE (Início or one community). It generalises the pin (a story's membership
in a community) by adding the name, the cover, the row position and the Início place.

its 24 h". The pin is demoted to a migration SOURCE: file 1 copies every pin into an item, and plan
09 drops the table, its routes, its events and 05.1's publish `communityId`. The phase deliberately
builds highlights BEFORE deleting pins (plans 01-10 add, plan 11 removes) so every intermediate
commit stays green — that is sequencing inside one phase, not add-alongside: at the phase's end
exactly one representation exists, and plan 11's grep gate proves no source file still names the
old one.

and is gated by plan 11's `checkpoint:decision` (D-116, roadmap criterion 5).

**Invariant tests (taken up):** (a) the in-file guard — every pin maps to exactly one item under its
own community's highlight, or the migration aborts; (b) this plan's live replay on real pins; (c)
plan 08's "born in a highlight ≡ added later" case; (d) plan 11's rehearsal across file 1 + file 2
on an edge fixture.
