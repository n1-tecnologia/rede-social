## Narrative Findings (AI reviewer)

## Summary

This review covers the highlights model that replaced community pins, across the API (stories service and routes, contracts), the database (the three migrations, the drizzle snapshots and journal, and the pgTAP suites) and the web tier (server actions, the Início and community rows, the viewer, the composer, the manage screen and "Seus stories").

**Tenant isolation holds on every new path I traced.** Every new statement runs inside `withTenantTx` and carries an explicit `tenant_id` predicate. The one exception is the `highlight_count` subquery, which relies on RLS alone (see IN-03). Every write that takes an id from the path does an insert-select, so an id outside the caller's lane writes nothing. `story_views` is read only for `ctx.userId`. The route guards match the documented matrix: reads carry no permission, and writes and the catalog require `stories.story.manage`. A `scope=all` request from a caller without manage is refused, and a publish that names a destination is refused without manage before any lookup.

I also checked two other exposure paths:
- **PostgREST.** A member cannot reach the new tables through PostgREST. `app.tenant_id()` reads `request.jwt.claims.tenant_id`, which only `withTenantTx` injects. There is no access-token hook, so a Supabase JWT carries no tenant claim and every tenant policy matches nothing.
- **Migration chain.** The snapshot chain (`prevId` links) and the journal agree with the three SQL files. The backfill guard is sound.

No finding rises to BLOCKER. The defects are correctness and robustness problems at the edges of the new model:
- Items that point at soft-deleted stories cannot be removed and still count toward the item cap.
- Curators get unplayable segments in the member viewer.
- The `full` refusals are never explained to the admin, and no test covers them.
- An unbounded server-action fan-out exists on the seen-state write.
- A `no action` foreign key on the cover asset collides with the media sweeper's hard delete.

## Warnings

### WR-01: A soft-deleted story leaves a ghost item that fills the highlight's capacity and cannot be removed

**File:** `packages/modules/stories/server/service.ts:1347-1362`, `:1844-1849`, `:1596`; `:530-540`
**Issue:** `deleteStory` only sets `stories.deleted_at`, and nothing removes the story's `story_highlight_items` rows. No trigger exists either: the only migration that touches `story_highlight_items` is the one that creates it. Three code paths then disagree about that orphaned item:
- `assertHighlightHasRoom` counts **every** item row of the highlight (`count(*) from story_highlight_items where highlight_id = …`), deleted stories included. So each removed story permanently uses one of the 100 slots (`STORY_HIGHLIGHT_MAX_ITEMS`).
- The curator's detail read filters `s.deleted_at is null` (line 1596), so the curator never sees the ghost item in the edit sheet.
- `removeStoryFromHighlight` resolves the story with `s.deleted_at is null` (lines 1844-1849) and answers 404 before it reaches the `delete`. The item can never be taken out.

The result: a highlight can report `full` while the curator sees fewer than 100 stories, and nothing in the product can free the slot.
**Fix:** Count only live items against the cap, and let a take-down remove an item whatever state its story is in. Better still, drop the items in the same transaction as the soft delete:
```ts
// assertHighlightHasRoom
select count(*) filter (where s.deleted_at is null)::int as n,
       coalesce(bool_or(i.story_id = ${storyId}::uuid), false) as present
  from story_highlight_items i
  join stories s on s.id = i.story_id
 where i.highlight_id = ${highlightId}::uuid and i.tenant_id = ${ctx.tenantId}::uuid

// removeStoryFromHighlight: resolve the ITEM, not a live story
delete from story_highlight_items
 where highlight_id = ${highlightId}::uuid and story_id = ${storyId}::uuid
   and tenant_id = ${ctx.tenantId}::uuid
returning id
```
If items should go away with their story, delete them from inside `deleteStory`'s `withTenantTx` as well.

### WR-02: Curators play processing and rejected stories in the member viewer

**File:** `packages/modules/stories/server/routes.ts:633-639`; `apps/web/app/(app)/stories/highlight-actions.ts:57-75`; `packages/modules/stories/server/service.ts:1596`
**Issue:** `GET /v1/stories/highlights/{highlightId}` computes `curator` from the caller's permissions alone, with no `scope` opt-in. The list route, by contrast, requires `scope=all`. When `curator` is true the items read drops `MEMBER_VISIBLE` and keeps every live story, including `processing` and `rejected` media. The viewer's lazy group read, `loadHighlightItemsAction` → `getHighlight`, goes through that same route. So an admin who taps a highlight on `/inicio` or a community page gets segments that cannot load: an error frame and a retry for a video still transcoding, or a neutral box for a refused image. Members never see those segments.

The circle's `itemCount` is computed with `MEMBER_VISIBLE`, so the row and the group the admin opens also disagree about how many stories the highlight holds. Only the edit sheet needs the curator view.
**Fix:** Mirror the list route. Serve the curator view only when it is asked for explicitly, and keep the viewer on the member read:
```ts
// routes.ts
request: { params: highlightIdParam, query: z.object({ scope: z.enum(['all']).optional() }).strict() },
…
const { scope } = c.req.valid('query');
if (scope === 'all' && !curator) throw new ApiError(403, 'FORBIDDEN');
return c.json(await getHighlight(ctx, highlightId, { curator: scope === 'all' }), 200);
```
Then add `scope=all` in `loadHighlightEditAction` only, and leave `loadHighlightItemsAction` without it.

### WR-03: The `full` refusal reaches the admin as "try again" (and the place cap has no copy at all)

**File:** `apps/web/components/stories/HighlightManager.tsx:541`; `apps/web/app/(app)/stories/publicar/StoryComposer.tsx:273-283`; `apps/web/messages/pt-BR/stories.json` (`highlights.errors.full`)
**Issue:** The API has two different `full` refusals: a place that already holds 50 highlights, and a highlight that already holds 100 stories. The web handles them as follows:
- `create` in `HighlightManager` maps every code except `archived` to `generic`, so a 51st highlight shows "Não foi possível salvar. Tente novamente."
- The composer maps `full` to `publish.errors.failed` ("Tente novamente") for both an existing highlight at 100 items and a `newHighlight` in a place at 50.
- The only `full` copy in the catalog is about stories per highlight ("chegou ao limite de {limit} stories"). If the manage screen forwarded the place-cap code as-is, the message would be wrong.

In every case the admin is told to retry an operation that will fail deterministically.
**Fix:** Add a place-cap message (for example `highlights.errors.placeFull` with `{limit}` = `STORY_HIGHLIGHT_MAX_PER_PLACE`). In `HighlightManager.create`, map `full` to it. In the composer, map `full` according to the destination: `newHighlight` gets the place cap, `highlightId` gets the item cap. Do not fold either into `failed`.

### WR-04: `markStoriesSeenAction` turns one public server action into an unbounded number of API calls

**File:** `apps/web/app/(app)/stories/story-actions.ts:392-414`
**Issue:** A server action is a public endpoint, and this one accepts an array of any length. It chunks the array into batches of 50 and calls the API **sequentially** for each chunk. With the default 1 MB action body, one POST of about 26k valid UUIDs costs about 530 authenticated `POST /v1/stories/views` round trips and holds the server function for their whole duration. The client never sends more than 10 ids (`SEEN_FLUSH_AT`), so chunking buys no real resilience and only enlarges the amplification surface.
**Fix:** Refuse anything larger than a single batch, after deduplicating:
```ts
const list = Array.isArray(storyIds) ? [...new Set(storyIds)] : [];
const parsed = markStoriesSeenSchema.safeParse({ storyIds: list });
if (!parsed.success) return false;
await markStoriesSeen(parsed.data.storyIds);
```

### WR-05: `story_highlights.cover_asset_id` is `ON DELETE no action`, which collides with the media sweeper's hard delete

**File:** `supabase/migrations/20260925191156_story_highlights.sql:87`; `packages/modules/stories/db/schema.ts:185`
**Issue:** The orphan sweeper (`packages/core/server/media/sweep-job.ts`, via `purgeAsset` in `packages/core/server/media/service.ts:983-1060`) removes the Storage objects of a `deleted` or `rejected` asset first, then hard-deletes its `media_assets` row. Suppose an uploaded highlight cover is later soft-deleted, for example through `DELETE /v1/media/{id}`. The Storage objects are purged, the row delete then fails with `23503` on `story_highlights_cover_asset_id_media_assets_id_fk`, and the row stays. The next hourly sweep selects the same row again (the selection is ordered by `created_at` and limited to a batch), fails again, and logs `media.sweep.purge_failed`. Enough stuck rows would fill the batch and stall collection for the tenant.

The read side already self-heals: cover rule 1 filters `ca.deleted_at is null`. The FK is the only thing preventing cleanup. `communities.cover_asset_id` follows the same pattern, but this phase adds a second table that repeats it.
**Fix:** Make the pointer nullable on delete. The read-time cover rule already falls back to automatic.
```sql
ALTER TABLE "story_highlights" DROP CONSTRAINT "story_highlights_cover_asset_id_media_assets_id_fk";
ALTER TABLE "story_highlights" ADD CONSTRAINT "story_highlights_cover_asset_id_media_assets_id_fk"
  FOREIGN KEY ("cover_asset_id") REFERENCES "public"."media_assets"("id") ON DELETE set null;
```
Mirror it in `schema.ts` with `.references(() => mediaAssets.id, { onDelete: 'set null' })`.

### WR-06: Neither `full` refusal (the item cap or the place cap) has any test

**File:** `apps/api/tests/integration/stories.test.ts`; `packages/modules/stories/tests/story-highlights.test.ts`; `supabase/tests/120-story-highlights.sql`
**Issue:** `grep` finds no `'full'` assertion anywhere in the API integration suite, the module unit tests or pgTAP. The route docs and the contract advertise both caps (`STORY_HIGHLIGHT_MAX_ITEMS` = 100 and `STORY_HIGHLIGHT_MAX_PER_PLACE` = 50) as 400 `{ highlight: 'full' }`, and the publish-into-highlight path depends on `assertHighlightHasRoom` and `lockHighlightPlace` to refuse them atomically. By contrast, `archived`, `order_stale` and `title_invalid` all have coverage. Without it, the WR-01 miscount went unnoticed, and so would a regression that lets the cap drift or stops rolling the publish back.
**Fix:** Add integration cases that seed 100 items (or 50 highlights) directly through the admin DB helper and assert all of the following:
- `PUT …/stories/{id}` answers 400 `{ highlight: 'full' }` for a new story and 200 for a repeat.
- `POST /v1/stories/highlights` answers `full` at 50.
- `POST /v1/stories` with `highlightId` or `newHighlight` answers `full` and writes no story row.

### WR-07: The seen-state flush on page hide is not delivery-safe

**File:** `apps/web/components/stories/StoriesSurface.tsx:239-254`, `:283-292`
**Issue:** The buffer is flushed on `visibilitychange: hidden`, which the comment calls "the last chance to send". It is sent through a Next server action, which is a normal `fetch` POST without `keepalive`, so the browser is free to abort it when the page is discarded. That happens when the PWA is swiped away or the tab is closed from inside the viewer. Up to nine shown ids are then lost (`SEEN_FLUSH_AT` is 10), and the member's ring stays unseen on every other device, which is exactly the cross-device behaviour HIGHLIGHT-06 exists for. `sent` is also updated optimistically, so a later showing in the same page never retries.
**Fix:** For the `hidden` path, post through something that survives unload. Two options: `navigator.sendBeacon('/api/stories/views', blob)` to a small same-origin route handler that forwards with the session cookie, or `fetch(url, { method: 'POST', keepalive: true, … })`. Keep the server action for the in-page flushes.

## Info

### IN-01: The count on "Seus stories" and the highlight sheet disagree about which highlights a story is in

**File:** `packages/modules/stories/server/service.ts:155-158`, `:2042-2069`, `:1999-2032`
**Issue:** The two reads diverge:
- `highlight_count` (the projection) counts every item row, including highlights of archived or soft-deleted communities, and community highlights while the `communities` module is off.
- `listStoryHighlightIds` hides module-off places but still returns highlights of archived and soft-deleted communities.
- The catalog hides all of them.

So a row can read "Em 2 destaques" while the sheet shows one switch on and offers no way to reach the other.
**Fix:** Use one place predicate (active, not deleted, module on) for all three reads, or document the difference in the UI.

### IN-02: `insertHighlightItem` is exported, although it bypasses the place and cap checks

**File:** `packages/modules/stories/server/service.ts:1431`
**Issue:** Its only callers are inside `service.ts`. Exporting it publishes a write primitive that skips `resolveHighlight` (the archived community check) and `assertHighlightHasRoom`, which contradicts the "one seam" rule (R-D-K).
**Fix:** Remove `export`.

### IN-03: The new tables' foreign keys are not tenant-composite, so cross-tenant pointers are representable in the database

**File:** `supabase/migrations/20260925191156_story_highlights.sql:81-99`; `supabase/migrations/20260926002810_story_views.sql:31-33`
**Issue:** `story_highlight_items(highlight_id, story_id)`, `story_highlights(community_id, cover_story_id, cover_asset_id)` and `story_views(story_id)` all reference `id` alone. FK checks bypass RLS, so a tenant-A row pointing at tenant B's story, community or asset satisfies both the FK and `WITH CHECK (tenant_id = app.tenant_id())`. Only the API's insert-select prevents it. This matches the repo's existing posture, and I found no API path that writes such a row. It is still a gap in layer 3 of the defense-in-depth model, and the `highlight_count` subquery (lines 155-158) is the one new read with no explicit `tenant_id` predicate.
**Fix:** Consider `unique (tenant_id, id)` on the parents and `foreign key (tenant_id, story_id) references stories (tenant_id, id)` on the children for new tables. At minimum, add `and hi.tenant_id = ${ctx.tenantId}::uuid` to the `highlight_count` subquery.

### IN-04: The cover step offers image stories that are not `ready`

**File:** `packages/modules/stories/ui/HighlightEditSheet.tsx:368`
**Issue:** `imageItems` filters by `mediaKind` only. The curator read includes `processing` and `rejected` images, and choosing one yields the API's bare 404, which the admin sees as the generic toast.
**Fix:** Carry the story's readiness on `HighlightEditItem` (the `status` field is already there) and exclude items that have a `status`.

### IN-05: The title field can cut an emoji in half

**File:** `packages/modules/stories/ui/HighlightTitleStep.tsx:172`
**Issue:** `value.slice(0, limit)` counts UTF-16 units. An astral character at position 15 is split into a lone surrogate, which the server's UTF-8 encoding turns into U+FFFD, so the stored title ends in "�".
**Fix:** Truncate on code points or graphemes (`Array.from(value).slice(0, n).join('')`, checked against the 15-unit cap), or reject rather than slice.

### IN-06: The edit sheet's dates are formatted in the server's time zone

**File:** `apps/web/lib/story-view.ts:215`, `:826`
**Issue:** `highlightEditStoryView` is new and reuses the pre-existing `HISTORY_DATE` formatter, which has no `timeZone`. It runs server-side (UTC on Vercel), so a story published late in the evening in Brazil is labelled with the next day. `lib/platform.ts` already pins `timeZone` for the same reason.
**Fix:** Add `timeZone: 'America/Sao_Paulo'`, or the tenant's zone, to the formatter.

### IN-07: The tenant circle only ever holds the newest 25 active stories

**File:** `apps/web/lib/registry.tsx:376`
**Issue:** `loadStories({ limit: STORY_MAX_PAGE_SIZE })` reads a single page. Any older active stories beyond 25 are never in the circle, never played and never marked seen, while the resume and ring logic assumes the sequence is complete.
**Fix:** Page until `nextCursor` is null (the window is at most 24 h), or document the cap.

### IN-08: If the catalog read fails, the composer quietly offers only "Novo destaque"

**File:** `apps/web/app/(app)/stories/publicar/page.tsx:117-123`
**Issue:** `readCatalog` swallows the error and returns `[]`, and the places are then built with `includeEmptyPlaces: true`. The admin sees every place with no existing highlights and may create duplicates of highlights that do exist.
**Fix:** Render the composer without destinations (the `!canCurate` branch), or show an error, when the catalog read fails.

### IN-09: A stale section heading still refers to pins

**File:** `apps/web/lib/stories.ts:330`
**Issue:** `/* ── Community pins (STORY-04, D-68) ── */` now sits above `loadOwnStories` and `deleteStory`. The pin model was retired in 05.2-11.
**Fix:** Rename the heading to "Seus stories (D-84)".
