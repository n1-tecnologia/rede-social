# Phase 05.2 Plan 03: Highlight curation API — rename, re-cover, reorder, delete, remove, catalogue and memberships Summary

**The whole admin curation contract for highlights at the API: six manage-only Hono routes, all resolved through one `resolveHighlight` → `resolveHighlightPlace` seam. They cover rename, image-only re-cover (story or uploaded asset), reorder in one `with ordinality` statement under the place lock, idempotent removal and delete. Two sheet reads, a per-story `highlightCount`, four transitions-only ids-only events, and a one-statement row-read budget come with them.**

## Accomplishments

- **Curation writes.**
  - `PATCH /highlights/{id}` renames and/or re-covers the highlight. The cover can be `{ storyId }` (a live IMAGE item of this highlight), `{ assetId }` (a ready `cover`/`image` asset of this tenant) or `null`.
  - `DELETE /highlights/{id}` answers 204, and the bare 404 on a repeat.
  - `DELETE /highlights/{id}/stories/{storyId}` is an idempotent 200 that clears a chosen cover in the same transaction.
  - None of them ever writes `stories`.
- **Archived rules (R-D-F).** An archived community refuses curation (`archived`) before any write, and still allows take-downs (remove, delete).
- **Reorder (R-D-C).** `PUT /highlights/order` takes the place's full permutation.
  - The place's rows are locked, and the locked set is compared with the request. Any mismatch is `order_stale`, and nothing is written.
  - One dense renumber statement writes the new order. An equal order moves nothing and emits nothing.
- **Sheet reads (D-110).**
  - `GET /highlights/catalog` is one statement: Início first, then active communities, and nothing from communities while the module is off.
  - `GET /{storyId}/highlights` returns ids only.
- **`highlightCount`.** It is on every story projection, in the same statement. `pinnedCommunityCount` is kept until plan 11.
- **Communities off (HIGHLIGHT-04).** Every community highlight route is the bare 404, while Início answers. The rows survive and come back when the module is turned on again.
- **Events and handlers.**
  - `highlight.updated`, `highlight.reordered`, `highlight.deleted` and `story.unhighlighted` are declared. Each fires only on a real transition, and each key set is asserted.
  - Six ids-only manifest handlers now exist, which closes 05.2-01's deviation 6.
- **Budget.** `GET /v1/stories/highlights` costs exactly 1 statement against the story tables, with a ceiling AND a floor.

## Decisions Made

- **Chosen-cover cleanup.** `removeStoryFromHighlight` clears `cover_story_id` only when a row was really removed. `resolveChosenCover` accepts only a live item of this highlight, and item rows disappear only through this removal or the story/highlight cascades (and `cover_story_id` is `on delete set null`). So no other path can leave a stale pointer, and removing an absent pair stays write-free.
- **`getHighlight` keeps its own read.** Its single projection read already resolves the highlight in-lane. Routing it through `resolveHighlight` would add a statement to a member-facing read and change no behavior. `addStoryToHighlight` was moved onto the new seam.
- **Membership ids and the module flag.** `listStoryHighlightIds` leaves out community highlights while the communities module is off, the same rule the catalogue applies.
- **Reorder ids as one literal.** The reorder's ids cross drizzle as ONE Postgres array literal. Every element is a Zod-validated uuid that is also in the set just locked.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Correctness] Unit "4" checks TWO statements, not ONE, before the archived refusal**
- **Found during:** Task 1 (unit tests)
- **Issue:** The plan says "refuses rename … after ONE statement". A rename resolves the highlight and then its place through the separate `resolveHighlightPlace` seam (planning decision 5 / R-D-K keeps ALL place logic there). A community highlight therefore costs two reads before the refusal.
- **Fix:** The unit asserts the exact sequence `['highlight', 'place']`, with no UPDATE and no read-back. This is the property the "ONE statement" wording protects: the refusal comes before any write.
- **Committed in:** `6d78657`

**2. [Rule 1 - Performance] `getHighlight` is not refactored onto `resolveHighlight`**
- **Found during:** Task 1
- **Issue:** The plan asks to refactor both `addStoryToHighlight` and `getHighlight`. For `getHighlight`, that would add one statement to a member read for no behavioral gain, because its projection read already resolves the highlight in-lane and it already calls `resolveHighlightPlace`.
- **Fix:** Only `addStoryToHighlight` was moved. Its statements are identical, with extra columns read.
- **Committed in:** `68718a0`

**3. [Measurement] `grep -c "highlightCount: z.number().int()"` prints 2, not 1**
- **Issue:** 05.2-01's `highlightMembershipResultSchema` already had `highlightCount: z.number().int().min(0)`, which contains the grepped prefix. The planner's count missed it.
- **Result:** `storySummarySchema.highlightCount: z.number().int()` is the one field this plan added.
- **Commit:** none.

**4. [Test design] 05.2-14 proves the literal "positions 0, 1, 2" in a fresh community place**
- **Issue:** Início holds the seeded `Bastidores`/`Aulas` and earlier cases' highlights. Positions 0..2 for A, B, C are therefore impossible there without moving the seeds, and 05.2-7 and later plans read the seeds at positions 0 and 1.
- **Fix:** The case covers two places:
  - It reorders a community holding exactly A, B, C and asserts `[C,0],[A,1],[B,2]`, the inert repeat, and the three stale sets.
  - It then reorders Início with the FULL set: three new highlights move to the end, and the seeds stay at 0 and 1. It also asserts that a member gets 403.
- **Committed in:** `cf1ed6a`

**5. [Rule 2 - Consistency] `listStoryHighlightIds` honors the communities flag**
- **Issue:** The plan did not say whether the membership read filters on the module flag. The catalogue hides community highlights while the module is off (T-05.2-16).
- **Fix:** The membership read hides them too, so the sheet never gets an id it cannot show.
- **Committed in:** `16e4c26`

**6. [Rule 1 - Bug avoided] The reorder's uuid array is passed as a Postgres array literal**
- **Issue:** drizzle's `sql` expands a JS array into `($1, $2, …)`. That would break `unnest(…::uuid[])`.
- **Fix:** One `{id,id,…}` literal is passed instead. The elements are Zod uuids that are also verified against the locked set.
- **Committed in:** `16e4c26`

**7. [Tooling] `pnpm test:integration -- <file>` does not filter (05.2-01's deviation 8, again)**
- **Result:** Each `-- stories`, `-- feed-query-budget` and `-- isolation` ran the WHOLE suite (519/519), which is stricter than written.
- **Counts:** The "≥ 13" and "≥ 18" counts were taken with `vitest run tests/integration/stories.test.ts -t "05\.2"` (escaped), which gave 13 and 18.
- **Commit:** none.

**8. [Style] The six handlers use a `logIds(event, message)` helper**
- **Result:** Each handler is still `log.info({ event, ...payload }, …)`, as the plan specifies. The helper keeps one line per event, which is the plan's `grep … module.ts` = 6. Inlining the log call would name each event twice, giving 12 lines.
