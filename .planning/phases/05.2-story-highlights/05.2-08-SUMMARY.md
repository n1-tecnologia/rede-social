# Phase 05.2 Plan 08: Publishing Into a Highlight, and the Community Page's Highlights Summary

**An admin can now publish a story straight into a highlight, whether it already exists or is created by the same request. The highlight lookup, the story, any new highlight and the item are written in one transaction, and every refusal writes nothing. The composer's single "Destaque" row replaces 05.1's "Publicar em" row:**
- **From `/stories/publicar`:** publishing tenant-wide still takes zero extra taps.
- **From a community's `+`:** the row arrives pre-filled with that community's first highlight.
- **From a community with no highlight:** the admin cannot publish into "Nenhum" without first seeing the choice.

**A community page now shows only its own highlights, which is where such a story lands.**

## Accomplishments

- **One destination, one write (D-113, D-114, D-99).** `POST /v1/stories` takes `highlightId` or `newHighlight: { communityId | null, title }`, and at most one of these plus the retiring `communityId`.
  - With `highlightId`, the transaction runs: the highlight (`for update`), its community for `curate`, the room count, the asset, the story insert, the item, then the projection.
  - With `newHighlight`, it runs: the place for `curate`, the place lock and cap, the asset, the story insert, the highlight insert at the end of the place, the item, then the projection.
  - With no destination, the publish is still exactly three statements with no module-flag read.
- **One statement creates highlights.** `insertHighlight`, `lockHighlightPlace` and `assertHighlightHasRoom` were factored out of `createHighlight` and `addStoryToHighlight`. The inline create and the manage-screen create are therefore the same row, and born-in and added-later are the same item (proved by case 05.2-23).
- **The permission seam (T-05.2-32).** Whenever any destination key is present, the publish handler checks `stories.story.manage` before any lookup.
- **Events after commit, ids only:** `story.published`, then `highlight.created` if a highlight was created inline, then `story.highlighted`. The log gains `highlightId` and `newHighlight: boolean`, never a title.
- **The composer asks "Destaque" (UI-D-69).** The row has three children and only the value truncates. The value is "Nenhum", "{place} · {title}" or "Escolher destaque". It opens `HighlightSheet` in single mode with the origin's group first.
  - **The D-112 gate:** while the row reads "Escolher destaque", "Publicar" opens the sheet focused on the origin's "Novo destaque" and sends nothing.
  - **Pending new highlight:** a confirmed title is pending and becomes `newHighlight` in the publish.
  - **Landings and toasts** follow UI-D-70.
  - **Refusals** follow UI-D-71: `archived` resets the row to "Nenhum" and drops that community's group from the sheet for the session; `title_invalid` returns the row to "Escolher destaque" or "Nenhum"; a 404 keeps the selection.
- **The page resolves the origin on the server.** It reads the active communities and the catalogue in parallel and builds the places with `includeEmptyPlaces`. The origin gets its first highlight, or the `choose` state when it has none.
- **The community row (HIGHLIGHT-04, UI-D-64).** The row shows the `+` (gate unchanged) followed by one circle per highlight, each opening its own lazily loaded group. There is no tenant circle and no pinned row, and an archived community's row is read-only. `loadCommunityHighlights` is deleted.
