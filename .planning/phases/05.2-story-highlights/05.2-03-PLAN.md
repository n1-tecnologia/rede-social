<planning_decisions>
1. **Cover by story id is a bare 404 when it is not a live image item of this highlight.** The UI
   never offers anything else (UI-D-75), so a separate 400 code would be vocabulary for a request
   only a crafted client sends; D-101's "one bare 404 for any miss" covers it.
2. **Delete highlight is idempotent-by-404** (the `deleteStory` rule): a second delete is the bare
   404, because "already deleted" answering 204 would confirm an id existed.
3. **The catalogue is its own route** (`GET /highlights/catalog`), not a flag on the row read: the
   sheet needs every place at once, the rows need one place at a time, and each stays ONE statement.
4. **`highlightCount` is additive now; `pinnedCommunityCount` goes in plan 11**, so no web read
   changes shape before the web is ready for it.
5. **Phase 10 seam (R-D-K):** every write keeps the literal route middleware; all place logic stays
   in `resolveHighlightPlace`, so creator-scoped publishing later edits one function.
6. **D-101 video-thumbnail branch: developer chose image-only at plan time, 2026-09-25; poster
   variant deferred as additive.** The developer answered the image-only / poster-now / stop question
   during planning, before any cover code exists, so this plan carries no checkpoint for it. A video
   item is never a chosen cover (bare 404, planning decision 1) and never the automatic one (plan 01's
   rule 3). A later broker `poster` variant (a 302 to a signed Mux thumbnail) slots into rules 2 and 3
   as one more branch, with no schema change and no migration.
</planning_decisions>
