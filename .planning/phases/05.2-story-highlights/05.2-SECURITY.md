## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| browser → web → `/v1/stories/highlights…` curation routes | An authenticated caller supplies highlight, story, asset and community ids, titles, permutations and cover choices, all untrusted | tenant-scoped ids, curator-written titles |
| browser → web → `POST /v1/stories` (publish into a highlight) | Untrusted destination ids (`highlightId` / `newHighlight`), a new title and a landing id | tenant-scoped ids, title |
| browser → `markStoriesSeenAction` → `POST /v1/stories/views` | Any member can send any list of story ids | behavioural data about members |
| browser → `POST /api/stories/views` (page-hide beacon route handler) → `POST /v1/stories/views` | Untrusted ids in a `text/plain` body; a route handler gets no framework Origin check (added by quick 260926-d8f, review WR-07) | behavioural data about members |
| browser → highlight server actions (`highlight-actions.ts`) | Any client can call a server action with any arguments; the API re-authorises every call | ids, issue codes |
| browser → Storage (signed upload of a cover) | The Phase 3 upload machine; the API validates the resulting asset tuple | image file |
| API route → service | The permission decision (`requirePermission`, `curator` from `permissionsForRequest`) is made in the route; the service never compares roles | resolved permissions |
| API service → Postgres | `api_user` under `set local role authenticated` inside `withTenantTx`; RLS plus explicit tenant predicates; `for update` / `for share` locks | tenant-scoped rows |
| API → RSC home slot / community page | Highlight titles and covers are tenant content rendered into every member's screens | titles, cover asset ids |
| migration chain → any environment's data | File 1 copies pins into highlights under a guard; file 2 drops the pins table, one-way | curated story placement |
| review artifact (`.planning/sketches/004-…`) → application code | A mockup must never become a runtime dependency | none |
| e2e spec → local stack | The phase-exit spec writes into the seeded tenants and must leave them clean | test rows |

## Residuals (not open threats)

Code-review findings from `05.2-REVIEW.md` that touch the register but do not reopen a threat:

- **WR-01** (integrity, not security): `assertHighlightHasRoom` counts items of soft-deleted stories, so a highlight can refuse `full` while showing fewer than 100 stories, and `removeStoryFromHighlight` 404s on a soft-deleted story, so such a ghost item can never be removed. Confirmed by the Nyquist audit's probe (see `05.2-VALIDATION.md`). It makes the T-05.2-08 cap stricter, not weaker. Resolved 2026-09-26 by quick 260926-d8f (cap counts live stories; ghost items removable; integration 05.2-33/34).
- **WR-05**: `cover_asset_id` is `ON DELETE no action`, which blocks the media sweeper's hard delete of a soft-deleted cover asset. The sweeper retries and logs, so no data leaks and nothing is corrupted.
- **WR-07**: the seen-state flush on page hide is not `keepalive`, so up to 9 seen ids can be lost when the PWA is killed from inside the viewer. This is a correctness gap in HIGHLIGHT-06 and discloses nothing. Resolved 2026-09-26 by quick 260926-d8f (page-hide flush via sendBeacon / fetch keepalive to POST /api/stories/views).
- **Deep-link viewer**: `/stories/[storyId]` records no seen state. This is known and becomes relevant when Phase 7 notifications deep-link to stories.
