## Narrative Findings (AI reviewer)

## Summary

I reviewed the phase's changes (`git diff 507091b..HEAD`) in priority order: the courses API routes and service, the five migrations and their RLS, the kernel course gate, the media pipeline changes, the web server actions, forms and view helpers, and then the tests, checking only for wrong or vacuous assertions.

Tenant isolation holds where it matters most. Every service statement pins `tenant_id = ctx.tenantId` and runs in the caller's RLS lane. Every by-id lookup locks the parent first and returns a bare 404 for unknown or foreign ids. Reference resolution (cover, photo, category, products, video, materials, track courses, replay lesson) is tenant-scoped, so the plain FKs that bypass RLS cannot be pointed at another tenant's rows through the API. The route inventory lists all 32 routes. The gate functions are SECURITY DEFINER, use `search_path = ''`, pin the tenant and fail closed. The Data API is closed (`schemas = ["data_api_closed"]`), so the RLS gaps below are defense-in-depth gaps, not open doors.

The serious defect is in the publish guard. It counts lessons under a removed module, which the editor, the list and the detail all hide. One unready video under a removed module blocks publishing for good, and the UI offers no way to fix it. The other findings are broken invariants (first module, replay before the live ends), an RLS gap on lives, a DST conversion that disagrees with its own doc comment, silent truncation in two pickers, and some media capacity and robustness issues.

Items already accepted in `deferred-items.md` (T-08.3-05, T-08.3-08, the progress plain FK, lessons under removed modules being reachable by id, the in-flight upload save, the Phase 6 line-clamp, the signup e2e) are not repeated. CR-01 is related to the removed-module residual but is a different and unrecorded consequence: publishing gets blocked.

## Critical Issues

### CR-01: The publish guard blocks on lessons under a removed module, which no screen shows, so the course can never be published

**File:** `packages/modules/courses/server/service.ts:1733-1749` (also `:601-617`, `:860-874`; `apps/web/lib/courses-view.ts:551-572`; `apps/web/app/(app)/cursos/[courseId]/PublishZone.tsx:66-80`)

**Issue:** `deleteModule` soft-deletes only the module row. Its lessons keep `deleted_at is null` (by design, lines 1153-1160). The publish guard selects every lesson of the course with `l.deleted_at is null and l.video_asset_id is not null and (a.id is null or a.status <> 'ready')`. It never checks that the lesson's module is live. Every other reader does filter on the module:
- `readModulesOf` drops lessons whose module is not in `moduleRows`, so the detail's `unreadyLessonIds` and `hasUnreadyVideo` leave them out.
- The `listCourses` lateral joins through `m.deleted_at is null`, so `hasUnreadyVideo` is false.

How it fails: an admin removes a module that holds a lesson whose video is pending, failed or rejected (for example, a lecture over the 4 h cap). The hub row and the course page show no blocking lesson, and the Publish button is enabled. Publishing returns `409 video_not_ready` with a `lessonIds` entry that `publishBlockedView` cannot match to any visible lesson. The notice reads "1 aula ainda processa o vídeo" with no link, and the button disables. A refresh re-seeds `unreadyLessonIds` from the server (empty), which enables the button again and leads to the same 409. The only way out is to type `/cursos/{id}/aulas/{lessonId}` by hand and detach the video. No test covers this: P12 (1) checks a soft-deleted lesson, not a lesson under a soft-deleted module.

**Fix:** make the guard read the same set as the detail, meaning live lessons under live modules:
```sql
select l.id
  from course_lessons l
  join course_modules m
    on m.id = l.module_id and m.tenant_id = l.tenant_id and m.deleted_at is null
  left join media_assets a on a.id = l.video_asset_id and a.tenant_id = l.tenant_id
 where l.tenant_id = ${ctx.tenantId}::uuid
   and l.course_id = ${courseId}::uuid
   and l.deleted_at is null
   and l.video_asset_id is not null
   and (a.id is null or a.status <> 'ready')
 order by m.position asc, l.position asc, l.id asc
```
Add an integration case: a module holding an unready-video lesson is removed, then the course publishes. Alternatively, have `deleteModule` also stamp `deleted_at` on its live lessons, which also frees their videos (see the deferred residual).

## Warnings

### WR-01: `course_lives` and `course_live_products` have no live gate in RLS, so a gated live's `external_url` is readable by any member lane

**File:** `packages/modules/courses/db/schema.ts:475` (`tenantReadAdminWritePolicies('course_lives')`); `supabase/migrations/20261013205511_courses.sql:321`

**Issue:** D-416 gives a live "optional products (same gate as courses)". The kernel declares `app.live_locked_ids()`, the store gives it a body, and pgTAP 190 tests the function. But no policy consumes it. `course_lives_select_tenant` is just `tenant_id = app.tenant_id()`. For courses, the gated payload is protected by a RESTRICTIVE policy (`course_lessons_course_gate`). For lives, the gated payload is `external_url` (the paid Zoom/Meet/YouTube link), and it is readable by every member lane of the tenant. Today the Data API is closed and no member route exists, so only the application layer protects it. That is one layer where CLAUDE.md requires three. Nothing in the threat register or `deferred-items.md` records this as accepted.

**Fix:** add a restrictive select policy that mirrors the lesson gate:
```ts
pgPolicy('course_lives_live_gate', {
  as: 'restrictive', for: 'select', to: authenticatedRole,
  using: sql`app.tenant_role() = 'admin_tenant' or id <> all (${LOCKED_LIVE_IDS})`,
}),
```
Add a pgTAP negative test. Alternatively, record the gap in `deferred-items.md` and make it a precondition of the member phase.

### WR-02: The "first module never requires the previous one" invariant is only enforced on create and patch, not by reorder or remove, and the UI hides the stored value

**File:** `packages/modules/courses/server/service.ts:1200-1276` (reorder), `:1161-1184` (delete); `apps/web/lib/courses-view.ts:445-448`; `apps/web/app/(app)/cursos/[courseId]/ModuleSheet.tsx:73-99`

**Issue:** `createModule` and `updateModule` force `requires_previous = false` on the first module (UI-D-396). `reorderModules` and `deleteModule` do not. Moving module 2 (`requires_previous = true`) to the top, or removing module 1, leaves the new first module with `requires_previous = true` in the database. `moduleCardView` hides the badge for `position === 1`, so the admin cannot see the stored state. The member phase will read the column and see a first module that requires a module that does not exist. Separately, `ModuleSheet` initialises the switch to `false` for a first module while `startRequires` is `true`. The sheet therefore opens already dirty: a close with no edits prompts the discard dialog, and any save silently writes the flag.

**Fix:** in the same transaction as the reorder and the module delete, normalise the flag after renumbering:
```sql
update course_modules set requires_previous = false, updated_at = now()
 where tenant_id = $1 and course_id = $2 and deleted_at is null
   and requires_previous
   and id = (select id from course_modules
              where tenant_id = $1 and course_id = $2 and deleted_at is null
              order by position, created_at, id limit 1)
```
In the sheet, base `startRequires` on the effective value (`firstModule ? false : module.requiresPrevious`).

### WR-03: The "replay only after the live ended" rule (A5) can be bypassed by a later patch to `startsAt` or `durationMin`

**File:** `packages/modules/courses/server/service.ts:2457-2472`; `apps/web/app/(app)/cursos/lives/LiveForm.tsx:356-360`

**Issue:** `replay_too_early` is evaluated only when the patch carries a non-null `replayLessonId`. A live that already has a replay can then be patched with `startsAt` in the future (the form sends `replayLessonId` only when it changed). The result is a `scheduled` live that points at a "recording", which is exactly the state A5 forbids, and the member phase will render it.

**Fix:** evaluate the rule whenever the resulting row would have a replay:
```ts
const replayAfter = patch.replayLessonId !== undefined ? patch.replayLessonId : live.replay_lesson_id;
if (replayAfter !== null && (patch.replayLessonId != null || patch.startsAt !== undefined || patch.durationMin !== undefined)) {
  if (liveStatusOf(after, now) !== 'recorded') throw new ApiError(409, 'CONFLICT', { courses: 'replay_too_early' });
}
```
This requires `lockLive` to also select `replay_lesson_id`. Alternatively, clear the replay when the new window has not ended.

### WR-04: Any change to a course's or live's product set forces dropping archived-product links, which revokes their buyers' access

**File:** `packages/modules/courses/server/service.ts:489-504`, `:956`, `:2383`, `:2456`; `apps/web/app/(app)/cursos/CourseForm.tsx:70-75`

**Issue:** `resolveProducts` requires every id in the replacement set to be `status = 'active'`, including ids that are already linked. A course gated by a product the store later archives can keep that link only while nobody touches the set. To add a new product, the admin must remove the archived one (the form's documented "way through"). That deletes the `course_products` row, and every holder of the archived product's entitlement loses the course. This contradicts the store's Assumption A4 ("an archived product still locks and its holders keep access"), which the gate migration's header repeats. The same applies to lives.

**Fix:** validate only the ids being added and keep already-linked archived ids:
```sql
select count(*)::int from store_products p
 where p.tenant_id = $tenant and p.id = any($ids)
   and (p.status = 'active'
        or exists (select 1 from course_products l
                    where l.tenant_id = p.tenant_id and l.course_id = $course and l.product_id = p.id))
```

### WR-05: `tenantWallClockToInstant` resolves a DST-gap wall clock to the instant before the gap, sometimes on the previous day, which contradicts its doc comment

**File:** `apps/web/lib/courses-view.ts:867-894`

**Issue:** The doc comment says a wall clock that does not exist "lands on the instant after the gap". A run of the function shows the opposite: `2026-03-08 02:30 America/New_York` returns `06:30Z`, which is 01:30 local, and `2026-09-06 00:30 America/Santiago` returns `03:30Z`, which is 23:30 on 2026-09-05 local. The second iteration uses the pre-transition offset whenever the first estimate crosses the transition. A live scheduled at the start of a DST night in a tenant zone that observes DST therefore lands an hour early and on the wrong date. The DST test (`courses-view.test.ts:647-700`) checks only Lisbon summer and winter instants, never a gap.

**Fix:** after the two passes, check the result. If `wallClockOf(instant)` differs from the requested wall clock (a gap), retry with the later offset (`guess - zoneOffsetMs(guess + 3 * 3600_000, tz)`), or reject with `startRequired`. Add gap and overlap cases for `America/New_York` and `America/Santiago`.

### WR-06: The track course picker and the replay lesson picker silently truncate (50 courses / 200 lessons) with no paging

**File:** `apps/web/lib/courses.ts:835`; `packages/modules/courses/server/service.ts:2569-2582`

**Issue:** `listTrackFormCourses` reads one page of `filter=published` at `COURSE_MAX_PAGE_SIZE` (50). Published courses older than the 50 newest can never be added to a track. `listCourseFormProducts` walks pages; this function does not. `listLessonsForPicker` stops at 200 rows ordered by course creation, so the lessons of older courses can never become a replay. Neither picker tells the admin anything was left out.

**Fix:** walk the keyset in `listTrackFormCourses` as `listCourseFormProducts` does (bounded, for example 4 pages), and give the lesson picker a cursor or a course filter. At minimum, show a "showing the N most recent" hint when the cap is hit.

### WR-07: Opening a material calls `window.open` after an awaited server action, which mobile Safari's popup blocker drops

**File:** `apps/web/app/(app)/cursos/[courseId]/aulas/LessonForm.tsx:272-286`

**Issue:** `openMaterial` awaits `materialUrlAction` and then calls `window.open(url, '_blank', …)`. By then the user gesture has ended. iOS Safari, the primary target of this mobile-first PWA, blocks the popup, so "abrir material" silently does nothing. With `noopener` the return value is always `null`, so the code cannot even detect the block.

**Fix:** open the window synchronously in the click handler and navigate it once the URL arrives (`const w = window.open('', '_blank'); … w.location.href = url`, then set `w.opener = null`). Alternatively, render the minted URL as an `<a target="_blank" rel="noopener noreferrer">` for the user to tap.

### WR-08: The course page hard-codes `image.mux.com` thumbnails and mints full playback credentials per ready lesson on every render

**File:** `apps/web/app/(app)/cursos/[courseId]/page.tsx:17-19`, `:63-86`

**Issue:** `thumbnailUrl` builds a Mux URL by hand. That bypasses the `VideoProvider` seam (D-409 names Cloudflare Stream as the swap behind it). With `VIDEO_PROVIDER=fake`, which every non-production environment runs, every ready lesson's poster is a broken image request. Each page view also calls `GET /v1/media/{id}/playback` for every ready lesson. That mints video, thumbnail and storyboard bearer tokens, each with a lifetime of up to 4.5 h now that the TTL scales with duration, only to keep the thumbnail token. A 100-lesson course mints 100 credential sets per page view.

**Fix:** have the provider expose a thumbnail URL builder (`videoProvider.thumbnailUrl(playbackId, token)`) or a dedicated thumbnail-only credential route, and use it here. Fall back to the glyph when the provider is `fake`.

### WR-09: Lesson materials share the tenant's 800 MiB byte ceiling with the feed, so a modest catalogue blocks every photo upload

**File:** `packages/core/server/media/limits.ts:36`; `packages/core/server/media/service.ts:405-417`

**Issue:** 08.3-03 gave lesson video its own 200 h budget so the school "does not refuse the feed's next reel". Materials (D-410: up to 10 per lesson, 50 MiB each) still count against `MEDIA_TENANT_BYTES_CEILING` (800 MiB) together with every feed photo, cover, avatar and attachment. Sixteen maximum-size materials use up the tenant's whole storage budget. After that, every image and file upload in the tenant (feed photos, avatars, covers) answers `413 quota_exceeded`. The doc comment shows the problem was understood for video but not for files.

**Fix:** split the byte sum the way the video sum was split (`purpose = 'attachment'` against its own ceiling, or a school budget keyed on materials). Alternatively, document the shared ceiling as an accepted residual with the Supabase plan constraint, and warn the admin in the materials list as usage nears the cap.

### WR-10: `completeUpload` downloads the whole object (now up to 50 MiB) into API memory to check an 8-byte signature

**File:** `packages/core/server/media/service.ts:648-668`; `packages/core/server/media/inspect.ts:103-112`

**Issue:** The attachment cap went from 25 MiB to 50 MiB, and the new office mimes are judged by a 4- or 8-byte magic prefix, yet `downloadObject(key)` buffers the entire object. With the documented Cloud Run concurrency of 80 to 200, concurrent material completions can hold several GiB of heap and crash the instance (OOM), which also drops every other in-flight request on it. Image attachments do need the bytes for the sharp decode, but PDF, ZIP and OLE need only the prefix.

**Fix:** for non-image `file` mimes, download a range (`Range: bytes=0-15`) or stream and stop after the signature length. Keep the full download only for the image branch, which is already bounded by the pixel limits.

### IN-02: `productIds` dedupe is case-sensitive, so the same uuid in two cases fails as `product_invalid`

**File:** `packages/modules/courses/contracts/index.ts:123`, `:180`, `:203`, `:880`; `packages/modules/courses/server/service.ts:501`

### IN-03: A live dated in years 100–999 produces a cursor the service then refuses

**File:** `packages/modules/courses/server/service.ts:768`; `packages/modules/courses/contracts/index.ts:848-850`
**Issue:** `isCursorInstant` rejects `year < 1000`, but `liveStartsAtField` accepts any ISO instant with an offset, and the date input allows years like 0999. If such a live is the last row of a `past` page, `nextCursor` encodes its `starts_at`, and the next request gets `400 cursor_invalid`. The list's "load more" then fails every time.
**Fix:** bound `startsAt` in the contract (for example, year 2000–2100) so the stored values and the cursor rule agree.

### IN-05: Saving a track's course list permanently unlinks any course that is momentarily unpublished, which works against D-415
