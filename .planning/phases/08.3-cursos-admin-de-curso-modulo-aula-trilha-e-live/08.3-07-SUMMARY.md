## Decisions Made

- **`products: CourseFormProduct[] | null` instead of `storeOn` + `canManageStore` booleans.** The page computes the gate and hands the rows or `null`; the form never knows about the store module, and `null` is also what keeps `productIds` out of every body (D-405). The truth's "gated on `storeOn && canManageStore`" holds at the page.
- **`returnHref` defaults to `/cursos` for both modes.** Plan 08's course page is not built yet; a client push to an unmatched URL renders the root not-found outside the `ToastProvider` and would swallow the success toast (the e2e's "sees 'Alterações salvas.'" would be flaky). The archive flow lands on `/cursos?filtro=arquivados` as the plan says. Plan 08 passes `returnHref="/cursos/{id}"` from the edit route once the page exists — a one-prop change.
- **An archived saved product is sent with a changed set and refused by name.** The API requires `status = 'active'` (08.3-04); the form's `product_invalid` line is precisely "Um dos produtos não está mais disponível. Confira a lista." The admin removes that row and saves. A silent drop would have changed the link set behind the admin's back.
- **Two new catalog keys** (`courses.form.errors.categoryInvalid`, `courses.category.form.errors.nameExists`), both pinned in the i18n describe; no existing key was reworded.
