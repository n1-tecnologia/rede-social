## Decisions Made
- **Gate bodies read the `courses` flag as well as the `store` flag.** P02 states the gate answers `'{}'` for a tenant without a `courses` row even when link rows exist; the plan's threat row T-08.3-13 described the bodies as reading `store` only. Both flags are now required: with the module off nothing the gate protects is reachable (every route is `requireModule`'d), so an inert gate changes nothing observable, and success criterion 3 ("with `courses` off, nothing changes") holds literally. Documented in `course-gate.ts`, the kernel README and the migration header.
- **Progress ledger delete made impossible at the privilege level.** With RLS alone, a lane without a delete policy deletes zero rows silently; the plan's truth "a delete raises 42501 in every lane" needed `revoke delete, truncate … from authenticated` (the `store_orders` precedent), added to `*_courses_functions.sql`. Insert/update stay with the lane (own rows only).
- **Draft cascade applied up front.** Task 2 allowed adding `exists (select 1 from public.courses …)` to the module select if the draft rule did not cascade; it was built into both `course_modules_select_tenant` and `course_lessons_select_tenant` in the first generated migration, avoiding a second one (COURSE-15).
- **Catalogue update/delete refusals proved as "touches 0 rows".** The truth text says 42501 for member-lane update/delete; RLS filters rather than raises, and revoking the privileges would also stop the admin lane (the same `authenticated` role). Inserts are 42501; updates and deletes are proved to touch nothing (the 180 CR-01 shape).
- **`video_invalid` by name for unknown and foreign asset ids**, never the bare 404 (plan instruction), so the sweep names the refusal.
- **160's B-side member question is asked via the null-claim lane**: S is `admin_tenant` in B, so the staff claim can never be locked; the fail-closed branch plays the member and proves S's A entitlement opens nothing in B.
- **The lane forms inline the body** (the store's shape) rather than calling the `_for` form — one InitPlan either way, and the two forms stay independently readable in pgTAP.
