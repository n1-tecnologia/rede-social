### WR-05: `tenantWallClockToInstant` resolved a DST-gap wall clock before the gap

**Commit:** c7b64b5a
**Status:** fixed: requires human verification (logic change, covered by new unit cases that failed before the fix)
**Applied fix:** The function now tries the zone offset one day before and one day after the guess. ### WR-10: `completeUpload` buffered the whole object to check an 8-byte signature

**Files modified:** `packages/core/server/media/storage.ts`, `packages/core/server/media/service.ts`, `packages/core/server/media/inspect.ts`, `packages/core/tests/media-storage.test.ts`
**Commit:** c85dc6be
**Status:** fixed
**Applied fix:**
- New `downloadObjectPrefix(key, n)`: it mints a one-shot 60 s signed read (never logged, never kept), GETs it with `Range: bytes=0-(n-1)`, reads the body only until `n` bytes arrive, then cancels. A Storage that ignores Range therefore costs one chunk.
- A 416 (empty object) returns an empty buffer, which then fails its signature check by name. Any other refusal returns `null`, the same as `downloadObject`.
- `inspect.ts` exports `fileSignaturePrefixBytes(mime)`: 16 for signature-judged mimes, `null` for image mimes that need the sharp decode.
- `completeUpload` uses the prefix read for `file` kinds judged by signature when Storage reported a size. Images and image attachments keep the full download.

New unit tests cover the Range header, a server that ignores Range (cut at 16 bytes, reader cancelled, at most 2 pulls of 5), and the null and 416 cases. The `media.test.ts` integration file (PDF, xlsx, pptx-as-PDF mismatch) passes against the local Storage.

## Skipped Issues

### WR-08: The course page hard-codes `image.mux.com` thumbnails and mints full playback credentials per ready lesson

**File:** `apps/web/app/(app)/cursos/[courseId]/page.tsx:17-19`, `:63-86`
**Reason:** This needs a design change in the kernel media seam: a `VideoProvider` thumbnail builder or a thumbnail-only credential route, a contract update, the Mux and fake adapters, and an update to the route and isolation inventories. That is beyond a scoped review fix. Some context for the decision:
- The web tier is already coupled to Mux for playback through `MuxPlayer` in `VideoPlayer`, `FeedVideo`, `ReelVideo` and `StoryVideo`.
- Under `VIDEO_PROVIDER=fake` the row already falls back to its glyph when the image fails (the e2e notes that `image.mux.com` is unreachable locally).
- Only the thumbnail token reaches the HTML.

Recommend a planned task: add `videoProvider.thumbnailUrl` or a thumbnail-only route, and skip minting when the provider is `fake`.
**Original issue:** `thumbnailUrl` builds a Mux URL by hand, bypassing the `VideoProvider` seam, and each page view mints video, thumbnail and storyboard tokens for every ready lesson, only to keep the thumbnail token.

### WR-09: Lesson materials share the tenant's 800 MiB byte ceiling with the feed

**File:** `packages/core/server/media/limits.ts:36`; `packages/core/server/media/service.ts:405-417`
**Reason:** This needs a product or infra decision, not a code fix. `MEDIA_TENANT_BYTES_CEILING` is sized to stay under the Supabase Free plan's 1 GB total storage, so a separate materials budget would let a tenant exceed what the plan can hold. Materials also use the shared `attachment` purpose, so splitting the sum also needs a new purpose or a course-scoped join. The reviewer's alternative is to record it as an accepted residual tied to the plan constraint and warn the admin near the cap. Recommend adding it to `deferred-items.md` (with a Pro-plan upgrade, or a per-tenant budget column, as the exit), or planning a "materials budget" task.
**Original issue:** Up to 10 materials of 50 MiB per lesson count against the same 800 MiB as every feed photo, cover and avatar, so sixteen maximum-size materials block every image upload in the tenant with `413 quota_exceeded`.
