# Phase 08.3: Cursos (Admin de Curso, Módulo, Aula, Trilha e Live) Verification Report

**Phase Goal:** Each tenant can run a school. `admin_tenant` authors the whole catalogue from the admin panel: courses (with modules and lessons), lesson materials, learning tracks and a lives agenda. Lesson video rides on the Mux pipeline Reels and Stories already use; materials ride on the Phase 3 upload pipeline. The member side is not in this phase, but its data model is: lesson progress per membership, the sequential lock between modules and access gated by a store product are modeled, policy-covered and pgTAP-tested here, so the next phase only reads.
**Verified:** 2026-10-14T14:40:22Z
**Status:** gaps_found
**Re-verification:** No (initial verification)

## Goal Achievement

The school is substantially built and wired. The module toggle, the 32 admin routes (each behind `requireAuth`, `requireModule('courses')` and `requirePermission('courses.manage')`), the eleven tables with RLS, the kernel gate seam and its store bodies, the progress ledger, lesson video on the `lesson` media purpose, materials on the widened attachment pipeline, tracks, lives, and every admin screen reached from Configurações all exist and pass their tests. Two invariants break when a module is removed or reordered. Both come from the same root: module removal and module reorder do not maintain the state they derive. ### Gaps Summary

One root concern accounts for both gaps: **removing or reordering modules does not maintain the state derived from them.**

1. **CR-01 (SC 2 / COURSE-03).** The publish guard counts lessons whose own row is live but whose module was removed. Every reader shown to the admin hides those lessons, so a course can become unpublishable from the UI. The 409 notice names a lesson with no link, and Publish keeps flipping back to enabled. The fix is about 3 lines of SQL (join `course_modules … m.deleted_at is null`) plus one integration case, or soft-deleting a module's lessons with the module.
2. **WR-02 (SC 4 / COURSE-05).** The first-module `requires_previous = false` rule holds only on create and patch. Reorder and module delete can store a first module that requires a non-existent predecessor, and the next phase is meant to only read it. The fix is one normalising `update` in the two transactions, a `ModuleSheet` initial-value fix, and one integration case.

Everything else in the goal is achieved and tested. The ten review warnings do not break a success criterion. WR-01 (the live gate is not applied in RLS) should be recorded in `deferred-items.md` as a precondition of the member phase, beside T-08.3-05 and T-08.3-08. If the product owner prefers to ship now, a `/gsd-quick` fix of CR-01 and WR-02 is smaller than a gap-planning round. Overriding CR-01 is not recommended: the course stays stuck in production with no UI way out.
