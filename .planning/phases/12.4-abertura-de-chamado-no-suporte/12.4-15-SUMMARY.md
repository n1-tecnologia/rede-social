# Phase 12.4 Plan 15: The team's thread with cases, first half Summary

**Staff case bar with a server-driven primary action and Mais ações sheet, four confirm dialogs with stale protection, the reply-takes and closed composer rules, and a coalesced live re-read, none of which a member viewer can render**

## Accomplishments

- The staff thread now shows a two-row case bar under the shipped `ThreadHeader`: one 44px button that asks for the details sheet, the meta text, the state's primary action and the 44px "Mais ações" button. The primary action is drawn only when the server listed its verb, so no role or transition is computed in the client.
- "Mais ações" is a `BottomSheet` (centred card from `md`) with exactly the server's `actions[]` plus "Ver detalhes e histórico"; there is no row that gives a case back, and a closed case's menu holds the details row alone.
- `useCaseActions` sends the intent with the state the screen showed (and the stored owner for a take) and maps the closed answer to a toast and a re-read. Resolve, close and reopen always ask; a take asks only for a live owner other than the viewer, and an unowned case or one whose owner left is taken at once.
- Composer rules: the hint "Ao responder, você assume este chamado." on an unowned `Aberto` case, an enabled composer on `Resolvido`, the read-only closed strip with `Lock` replacing the composer on `Fechado`, and the blocked or removed notice winning over it.
- The pane re-reads the staff header through the BFF handler on `chat.case` and `chat.message` signals, on subscribe and on refocus, one in flight and one queued, with no toast or focus move on a live change. A member viewer, even handed a staff-shaped case, draws none of it.

**4. [Rule 3 - Blocking] A shipped test pinned the old behaviour**
- **Found during:** Task 1
- **Issue:** `ThreadPane.member.test.tsx` asserted that the staff pane re-reads no header. The staff pane now re-reads the staff header.
- **Fix:** the pin moved to "the staff pane never draws the member bar": it re-reads once, and a member-shaped answer draws no bar.

**5. [Plan wording] The closed state is not folded into the page's `readOnlyNotice`**
- **Issue:** the plan says the page computes one `readOnlyNotice` with the precedence blocked, removed, closed. A closed case can arrive live while the page is open, which a page-time value cannot follow.
- **Fix:** the page keeps computing blocked then removed; the pane draws the closed strip from the live case state only when `readOnlyNotice` is null, so the precedence holds on every render. The tests assert both orders.

**6. [Plan wording] The "Atribuir" roster load is not in this plan**
- **Issue:** the hand-off says the Atribuir sheet of this plan must call `useStaffRoster().load()`. This plan mounts no assign sheet (the row only calls `onOpenSheet('assign')`; the sheet is plan 12.4-19's), so there is nothing here to call it from.
- **Fix:** none; recorded for plan 19, whose assign sheet must call `useStaffRoster().load()` on open because the roster does not read itself.
