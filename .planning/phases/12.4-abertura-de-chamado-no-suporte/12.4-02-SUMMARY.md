# Phase 12.4 Plan 02: Activation, backfill and the first-message flow Summary

**A member whose case was closed now gets the next numbered case on the next message: every legacy support conversation is backfilled into a case, the one-per-member index is replaced by an active-case index in one atomic block, and the message trigger refuses any message on a closed case for every writer.**

## Accomplishments

- **Tracer:** a member writes, the admin lane closes the case, the member writes again and the API answers 201 on a NEW case numbered one higher, with two `opened` events; `GET /v1/chat/support` answers the second case.
- **Backfill** (`app.chat_cases_backfill`): numbers by (first message instant, or creation when there is none; then id) after the larger of the counter and the tenant's highest number, `open` when the last message is the member's and `last_seq > staff_last_read_seq`, `closed` otherwise with `closed_at`, one `opened` event per case and a `closed` event with no actor per closed one; idempotent; a tenant with only direct or group rows gets nothing and no counter row. On the local stack the one existing conversation (the e2e seed thread `1d000000-0000-4000-8000-000000000001`) already had a state from plan 01 and stayed a valid case.
- **Message trigger:** under the row lock, CS004 for any message on a closed case (member, staff and the table owner alike, no sequence consumed), member-on-resolved reopens with `resolved_at` cleared and a `reopened` event carrying the message id, staff-on-open-unowned takes with a `taken` event; owned, resolved, direct and null-state rows move counters only.
- **Activation:** lock, backfill, `chat_conversations_support_state_chk` added NOT VALID then validated, `chat_conversations_one_active_case_per_member`, drop of `chat_conversations_one_support_per_member`, all one statement. `pg_indexes` shows 0 old, 1 new; the constraint is validated.
- **Service:** `sendSupportMessage` selects the active case, inserts `on conflict (tenant_id, created_by_user_id) where kind = 'support' and state in (...) do nothing`, and on CS004 runs one more attempt in a new transaction; `chat.message_sent` fires once, after the attempt that committed.
- **Concurrency proofs:** 20 simultaneous first messages make one case with seqs 1..20; after a close, 20 more make exactly one next case numbered first + 1; 20 members of the tenant opening together get base+1..base+20; a member send racing a staff close (held row lock, polled lock wait, no sleep) lands in a new case and never in the closed one.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The activation file could not run as a bare statement list**
- **Found during:** Task 2
- **Issue:** `pnpm supabase migration up` failed with `LOCK TABLE can only be used in transaction blocks (SQLSTATE 25P01)`: the local CLI sends the statements of a file one by one. An explicit `begin`/`commit` would clash with the ledgered runner, which wraps each file in its own transaction.
- **Fix:** the five steps are one `do $activation$ ... $activation$` block, a single statement and therefore atomic under both runners. The statements and their order are exactly the plan's; the file lists, in order, the lock, the backfill call, the constraint NOT VALID then VALIDATE, the create index and the drop index; `grep -c 'drop index'` prints 1 and the expand-only grep prints nothing.
- **Files modified:** `supabase/migrations/20261117084235_chat_cases_activate.sql`
- **Commit:** `55550107`

**2. [Rule 1 - Bug] The new constraint and the new arbiter broke plan 01's pgTAP**
- **Found during:** Task 2
- **Issue:** `235` section 2 (B1) stores a legacy support row with a null state, which the validated support-state constraint now refuses, and EP-008 used the old `on conflict ... where kind = 'support'` text, which answers 42P10.
- **Fix:** the constraint is dropped once at the top of the file (DDL is transactional and the file rolls back) so sections 1 to 5 keep proving the legacy-safe CHECKs and trigger branch; section 6 re-adds it and proves it. EP-008's insert repeats the new index predicate.
- **Files modified:** `supabase/tests/235-chat-cases.sql`
- **Commit:** `55550107`

**3. [Rule 3 - Blocking] Validation failed on rows left by sections 2 and 5**
- **Found during:** Task 2
- **Issue:** `validate constraint` in section 6 failed because tenant A still held two legacy-shaped rows of earlier sections.
- **Fix:** section 6 backfills tenant A first (an assertion: 2 rows numbered), which is the order of the activation file.
- **Commit:** `55550107`

**4. [Rule 2 - Missing] `CASE_ACTIVE_STATES` added to the contracts**
- **Found during:** Task 2
- **Issue:** the plan lists no file that could carry the one spelling of the index predicate that the service and the EP-013 test both need.
- **Fix:** a constant in `packages/modules/chat/contracts/index.ts` (a closed tuple, no pinned test touches it); the service builds its arbiter from it and the integration test compares it with the list read from `pg_indexes`.
- **Commit:** `55550107`

**5. [Rule 1 - Detail] A second CS004 in a row is a bare 409**
- **Found during:** Task 2
- **Issue:** the plan says retry once; it does not say what a second refusal returns, and the issue list is closed (plan 08).
- **Fix:** `ApiError(409, 'CONFLICT')` with no `chat` issue code.
- **Commit:** `55550107`

**6. [Rule 3 - Blocking] The staff reply on a closed case is an unmapped refusal today**
- **Found during:** Task 3
- **Issue:** `replyToConversation` does not map CS004 (plan 08 does). The integration test therefore asserts only a non-2xx answer with nothing written, as the plan's action says.
