**Researched:** 2026-11-16
**Domain:** Postgres state machine + Hono API + pg-boss sweeper + Realtime + notifications inside an existing multi-tenant chat module (no new libraries)
**Confidence:** HIGH on the repo facts and on the database semantics (probed on the local PG 17.6); MEDIUM on the three product defaults listed in the Assumptions Log

## Summary

The case is the conversation row itself. `chat_conversations` (kind `support`) gains a number, a state, an owner, a category, a priority and two instants; the existing `subject` column (never written, confirmed) holds only a typed or edited subject. Everything that already works for a conversation keeps working per case: the gapless `seq` trigger, the member's participant row and read mark, `staff_last_read_seq`, the `conv:<id>` and `support-inbox` topics, the push tag, the e2e seed id. A separate case table would need a join on every read, a deferred "every support conversation has a case" invariant and would still have to drop the same unique index, so it buys nothing. Two new tables carry what a column cannot: `chat_case_counters` (one row per tenant) and `chat_case_events` (append-only history).

The state machine lives in the database, in three places that are each the only writer of what they touch: (1) the replaced `chat_messages_before_insert` trigger handles every message-driven transition under the conversation row lock (member message on `Resolvido` reopens, staff reply on an unowned `Aberto` takes, any message on a `Fechado` case is refused); (2) `security definer` functions `app.chat_case_act` / `app.chat_case_edit` are the only writers of the staff actions, with no new column grant to `authenticated`; (3) one sweep function `app.chat_cases_auto_close(p_batch)` registered in the chat manifest's `sweepFunctions` is the 7-day auto-close, run by the kernel's existing hourly sweeper in the worker (no new queue, no new arm code). The case number is assigned by an AFTER INSERT trigger, not a BEFORE one: probed on the local database, a BEFORE INSERT trigger fires even when `on conflict do nothing` skips the row, so a BEFORE design would burn a number on every message the API sends with the current "insert first" shape and on every seed re-run.

The three things that can hurt: the unique-index swap makes the previous API revision fail every member send with `42P10` until the new API serves (probed); the D-814 backfill turns every answered conversation into `Fechado`, so on release day most members open an empty opener with their history behind "Meus chamados"; and the count/dashboard rules are spread over six places (badge, dot, inbox filter, builder, member detail, overview alert) that must all learn "active = not Fechado" together.

**Primary recommendation:** Build the case on `chat_conversations`, write every state change through definer functions and the message trigger (never a staff column grant), number cases in an AFTER INSERT trigger over a per-tenant counter row, close `Resolvido` cases with a `sweepFunctions` entry, keep every old response shape and add new keys as `.optional()`, and ship the migration as one atomic file (lock, backfill by a re-runnable function, triggers, validated CHECKs, index swap) in the order migrations, web, API and worker.

### Locked Decisions

#### The case model (the biggest change)
- **D-800:** This phase formally reverses D-221 (no resolve/close status, one thread per member forever) and the "nothing is assigned" half of D-225 for the support kind. The other half of D-225 stays: any staff member may reply to any case, whoever owns it. Phase 7 itself listed both as "revisit if a pilot tenant's support volume demands it"; Igor chose to do it now. `kind = 'direct'` and `kind = 'group'` conversations keep every rule they have today.
- **D-801:** A member has several cases over time. Each case has its own number, its own beginning and end and its own list of messages. When the member writes after their case is `Fechado`, a new case opens; the old one stays as history. — **Reversibility:** one-way — once a member has two cases the model cannot go back to one conversation per member without merging message sequences, and the database loses the unique index per member; the new partial unique index of D-802 replaces it.
- **D-802:** One active case per member at a time. "Active" means not `Fechado`. Every message from the member goes to that case. The database guarantees it with a partial unique index (tenant, member) where the kind is support and the state is not `Fechado`, in place of `chat_conversations_one_support_per_member`. The lazy creation keeps the `insert … on conflict do nothing` shape of `sendSupportMessage` so the 20-way concurrency test still holds, now against the active-case index.
- **D-803:** What the member sees. The chat bubble in the top bar opens the active case directly, or, when there is none, an empty composer that creates the case on the first message. There is no "Ajuda" hub (D-220 stays). The member's earlier cases are reached through a "Meus chamados" link inside the conversation, newest first, each opening that case read-only when it is `Fechado`.
- **D-804:** The case number is sequential per tenant, starting at 1, shown as `#42` ("Chamado #42"). A per-tenant counter is bumped safely when two cases open together. The member sees only their own numbers. — **Reversibility:** costly — the number is shown to members and staff and quoted in notices, so renumbering later breaks references.

#### States, owner and reopening
- **D-805:** Four states, with these labels in pt-BR: `Aberto` (nobody took it), `Em atendimento` (a staff member took or was given it), `Resolvido` (the team thinks it is over, the member can still answer) and `Fechado` (over; the next message from the member opens another case). A new case is born `Aberto`. Resolving works from `Aberto` and from `Em atendimento`. Closing works from any state. A member message on a `Resolvido` case moves it back to `Aberto` in the same case and tells the team (D-809). A member message on a `Fechado` case never touches it (D-801).
- **D-806:** Any `support_tenant` or `admin_tenant` can take a case for themselves ("Assumir"). Only `admin_tenant` assigns a case to another person. Anyone on the staff can reply regardless of who owns the case. A case is owned by at most one person; a case with no owner is `Aberto`.
- **D-807:** Closing. The team has a "Fechar" action. A background job also closes, by itself, every case that has stayed `Resolvido` for 7 days without a message from the member. The 7 days are fixed in code in this phase, not a tenant setting. The job runs in the existing worker queue (`apps/api/src/worker.ts`, pg-boss), idempotent, and writes the same history row as a manual close with no actor.
- **D-808:** The member's notice. Only when a case becomes `Resolvido`: a push and a row in the bell ("Seu chamado #N foi resolvido"). Closing, by hand or by the job, is silent; the conversation shows the state. This is the first chat entry in the bell, so it needs a renderer in `apps/web/lib/notification-renderers.tsx`, a catalog entry and a kind in `CHAT_NOTIFICATION_KINDS`; today chat kinds are push-only.
- **D-809:** The team's notices. A new case, a case assigned to you and a reopened case notify the team as the cronograma describes. When the member writes in a case that has an owner, only the owner gets the push; with no owner, every active staff member does, as today. The numeric badge of the team (D-238) keeps counting all cases that await the staff (last message from the member, unread by the staff under the shared read state), whoever owns them.
- **D-810:** History. Every step (opened, taken, assigned, resolved, closed, reopened, a field changed) is a row in a table of case events of its own, with who did it, when and from which state to which. It is append-only and tenant-scoped.

#### Fields
- **D-811:** A case has a subject (short text), a category and a priority, besides its number, state and owner. The categories are a fixed list in code, from the design prototype: `Check-in`, `Eventos`, `Pagamento`, `Conta`, `Outro`. The priority is `Baixa`, `Normal` or `Alta`. No attachments in this phase.
- **D-812:** Who fills them. Above the composer of the first message of a new case, the member taps a category (`Outro` is preselected) and may type a subject. With no subject, the case takes the start of the first message as its subject (one line, trimmed, the length is the planner's call). The priority is born `Normal` and only the staff change it. The staff can also correct the category and the subject. The member cannot change any field after the case exists, and the picker is not shown again for replies.
- **D-813:** The category is what feeds the owner's "Atendimentos por assunto" card, which is "Em breve" today (`bySubject: { measured: false, reason: 'needs_support_subject' }` in `packages/modules/dashboard/contracts/support.ts`).

#### Existing conversations and the owner's panel
- **D-814:** Migration of what exists. Each existing support conversation becomes the case of its member, keeping all its messages and its id. Cases are numbered per tenant by the date of the first message (ties broken by id). A case is `Aberto` when its last message is from the member and the staff has not read it, and `Fechado` otherwise. Category `Outro`, priority `Normal`, no subject (the list falls back to the preview of the first message). The e2e seed conversation id `1d000000-0000-4000-8000-000000000001` must stay a valid case. The release is expand-only, like the previous phases' migrations. — **Reversibility:** costly — the backfill renumbers nothing that was shown before, but the states it assigns drive the first day's inbox and counters.
- **D-815:** The owner's "Atendimento" panel keeps its numbers, now counted per case. "Awaiting a reply" counts active cases whose last message is from the member and unread by the team. First-response time is per case (the first staff message after the case's first member message), replacing today's per-turn rule in `app.dashboard_area_support`. Cases per week and cases answered per staff member (names only) stay. "Em aberto" and the overview alert read the state (`Aberto` plus `Em atendimento`). "Atendimentos por assunto" leaves "Em breve" and counts by category. New numbers (cases by state, time to resolve) are deferred.

### Pattern 1: Number the row that survived, not the row that was attempted
**What:** assign `case_number` in an AFTER INSERT row trigger (definer) from a per-tenant counter upsert. **When:** any `insert … on conflict do nothing` whose row may be skipped.
**Evidence (probed 2026-11-16 on the local PG 17.6.1.166, a TEMP table in a rolled-back transaction):** two `insert … on conflict (tenant, member) where kind = 'support' do nothing` produced `before | 2` and `after | 1` in the trigger log: BEFORE ROW triggers fire for the skipped row, AFTER ROW triggers do not [VERIFIED: local PG probe]. The repo already knows the BEFORE half: `scripts/seed.ts` says "the seq trigger fires BEFORE the conflict arbiter, so a conflicting re-insert would still burn a seq" [VERIFIED: scripts/seed.ts:1692-1695 comment, quoted: "never with `on conflict`: the seq trigger fires BEFORE the conflict arbiter, so a conflicting re-insert would still burn a seq (a gap)"].
```sql
-- proposed (design, not a repo fact)
create function app.chat_conversations_after_insert() returns trigger
  language plpgsql security definer set search_path = '' as $$
declare v_n int;
begin
  if new.kind <> 'support' then return null; end if;
  insert into public.chat_case_counters (tenant_id, last_number) values (new.tenant_id, 1)
    on conflict (tenant_id) do update set last_number = public.chat_case_counters.last_number + 1
    returning last_number into v_n;
  update public.chat_conversations set case_number = v_n where id = new.id and tenant_id = new.tenant_id;
  insert into public.chat_case_events (tenant_id, conversation_id, kind, actor_user_id, to_state)
    values (new.tenant_id, new.id, 'opened', new.created_by_user_id, 'open');
  return null;
end $$;
```
The counter row lock is held to commit, so concurrent opens in one tenant serialise on it for the rest of their (short) transactions and get distinct consecutive numbers; a rollback undoes the bump (no gap).

### Pattern 2: One definer per staff action, no new column grant
**What:** `app.chat_case_act(p_conversation uuid, p_action text, p_expected_state text, p_expected_owner uuid, p_target uuid)` and `app.chat_case_edit(...)`. They: pin `c.tenant_id = app.tenant_id() and c.kind = 'support'`, check the caller's claim `app.tenant_role() in ('admin_tenant', 'support_tenant')` (assign: `= 'admin_tenant'`), `select … for update`, compare the expected state and owner (stale), apply the transition table, write the event row, publish `chat.case`, and return the new case row. Custom SQLSTATEs follow `RP001`/`BL001` precedent [VERIFIED: packages/core/server/safety/reports.ts:115-135 `mapReportError` maps `RP001`, `RP002`, `RP004`, `BL001`, `22023`, `42501`]. `CS` is unused in the repo [VERIFIED: grep of `errcode = '` over supabase/migrations lists `42501 23514 22023 PF001..PF010 23503 RP001 RP002 RP004 BL001 AD001`].
**Why not a column grant:** the grant file today allows only `staff_last_read_seq` on conversations [VERIFIED: supabase/migrations/20261001004638_chat_rls_grants.sql:20-21, quoted: "revoke update, delete, truncate on public.chat_conversations from authenticated;" and "grant update (staff_last_read_seq) on public.chat_conversations to authenticated;"]; keeping it untouched means a dropped API predicate still cannot move a state.

### Anti-Patterns to Avoid
- **BEFORE INSERT numbering** (burns numbers; see Pattern 1).
- **Computing a transition in the browser or the server action.** The client sends intent plus `expectedState`; the database decides (UI-D-835).
- **A staff UPDATE policy widened to new columns.** Keep `chat_conversations_staff_update` as is [VERIFIED: packages/modules/chat/db/schema.ts:120-125].
- **Counting "awaiting" without the state.** Every count that reads `last_message_side = 'member' and last_seq > staff_last_read_seq` gains `state <> 'closed'`.
- **Putting the 7 days in two places.** One SQL literal in `app.chat_cases_auto_close`; the TS constant only pins it in a drift test.

### Q2. State machine in the database

**Transition table (enforced in SQL; "any staff" = `chat.support` holder, no owner check):**

| From | Action (who) | To | Owner after | Side effects |
|------|--------------|----|-------------|--------------|
| (new) | member first message | open | none | `opened` event; counter |
| open | `take` (staff) | in_progress | actor | `taken` |
| open, in_progress | `assign` (admin only; target = live staff, not the current owner) | in_progress | target | `assigned` + notice to target |
| in_progress | `take` over another person (staff; `expectedOwner` required) | in_progress | actor | `taken` |
| open, in_progress | `resolve` (staff) | resolved | kept | `resolved`; `resolved_at = now()`; `staff_last_read_seq = last_seq`; notice to member |
| open, in_progress, resolved | `close` (staff) | closed | kept | `closed`; `closed_at = now()`; `resolved_at = null`; `staff_last_read_seq = last_seq`; silent |
| resolved | `reopen` (staff) | open | none | `reopened`; `resolved_at = null`; member not told |
| resolved | member message | open | none | `reopened` (actor member, `message_id`); team push |
| open (unowned) | staff reply | in_progress | author | `taken` (`message_id`) |
| resolved | auto-close after 7 days (sweep) | closed | kept | `closed`, no actor |
| closed | anything | refused | | message insert raises `CS004` for both sides |
| any | `edit` category/subject/priority (staff, not closed) | same | same | one `edited` row per changed field |

Marking resolve and close as read for the team keeps the badge from counting a case nobody can answer (a `Fechado` case with an unread member message would otherwise count forever). The badge and every awaiting rule still add `state <> 'closed'` as a second guard.

**Message-driven transitions live in `app.chat_messages_before_insert`** (same name and signature, `create or replace`; the trigger binding stays). Today it is one UPDATE that bumps `last_seq` and the side fields under the row lock and raises `conversation_not_found` (`23503`) when nothing matched [VERIFIED: chat_functions.sql:54-76]. Replace the single UPDATE with a `select … for update` of `(state, owner_user_id)`, then the UPDATE that also applies the transition. This keeps the guarantee that a message and its transition commit together. Race rules that follow: a member message arriving while the sweeper or a staff `close` holds the row waits, then sees `closed` and raises `CS004`; the API retries once through the open path, so the message lands in a new case (D-805: a member message on a `Fechado` case never touches it). The sweeper uses `for update skip locked`, so a row a message is updating is simply skipped and re-evaluated next hour.

**Stale actions.** Every action carries `expectedState` (and `expectedOwnerId` for a take-over). The definer raises `CS002` when the locked row differs; the API answers `409 CONFLICT { chat: 'case_stale' }` and the UI shows "Este chamado mudou enquanto você olhava" (UI-D-827). No `case_rev` column.

### Q4. Worker: the 7-day auto-close

**Recommendation: a sweep function, not a new queue.** The manifest field exists for this: "SQL functions the kernel's hourly sweeper runs for this module … `app.<name>(p_batch int) returns int`" [VERIFIED: packages/core/server/modules/manifest.ts:161-171]; names must match `^[a-z_]+$` (no digits) [VERIFIED: packages/core/server/jobs/sweep-functions.ts `SWEEP_FUNCTION_NAME = /^[a-z_]+$/`], so `chat_cases_auto_close`. The sweeper is a pg-boss job of the worker (`kernel.media-sweep-orphans`), per project, re-arming itself hourly, so D-807's "existing worker queue, pg-boss, idempotent" is satisfied; granularity is one hour (a case closes between 7 days and 7 days 1 hour after `resolved_at`).
```sql
-- proposed
create function app.chat_cases_auto_close(p_batch int) returns int
  language plpgsql volatile security definer set search_path = '' as $$
declare v_n int := 0; r record;
begin
  for r in
    select c.id, c.tenant_id from public.chat_conversations c
     where c.kind = 'support' and c.state = 'resolved'
       and c.resolved_at <= now() - interval '7 days'
     order by c.resolved_at
     limit greatest(1, least(coalesce(p_batch, 1), 5000))
     for update skip locked
  loop
    update public.chat_conversations
       set state = 'closed', closed_at = now(), resolved_at = null
     where id = r.id and tenant_id = r.tenant_id and state = 'resolved';
    insert into public.chat_case_events (tenant_id, conversation_id, kind, from_state, to_state)
      values (r.tenant_id, r.id, 'closed', 'resolved', 'closed');
    perform realtime.send(jsonb_build_object('conversationId', r.id), 'chat.case',
      'tenant:' || r.tenant_id::text || ':conv:' || r.id::text, true);
    perform realtime.send(jsonb_build_object('conversationId', r.id), 'chat.case',
      'tenant:' || r.tenant_id::text || ':support-inbox', true);
    v_n := v_n + 1;
  end loop;
  return v_n;
end $$;
revoke all on function app.chat_cases_auto_close(int) from public, authenticated;
grant execute on function app.chat_cases_auto_close(int) to service_role;
```
Definer, not invoker like `notifications_prune`, because `realtime.send` is invoker and only the owner can insert into `realtime.messages` [VERIFIED: chat_functions.sql header, "The owner (`postgres`, rolbypassrls) can insert"]. Cross-tenant by design (T-07-26 posture): each UPDATE and event row pins the row's own `tenant_id`. Idempotent: the predicate is the state; a second run finds nothing. The history row has `actor_user_id` null. A closing is silent for the member's bell/push; the open thread learns through `chat.case`. `apps/api/tests/unit/module-readmes.test.ts` fails when a manifest's `sweepFunctions` is not in the module README's "Jobs" section [VERIFIED: its header, "the manifest (…, jobs, sweep functions)"], so `packages/modules/chat/README.md` must list `chat_cases_auto_close`, the new events and the new permission.

## Common Pitfalls

### Pitfall 1: Numbers burned by a skipped insert
**What goes wrong:** gaps in `#N`, one per send. **Why:** BEFORE ROW triggers fire before the arbiter (probed). **Avoid:** AFTER INSERT numbering (Pattern 1); a pgTAP case inserts the same member twice with `on conflict do nothing` and asserts the counter moved once. **Warning sign:** `last_number` far above `count(*)`.

### Pitfall 2: Old API during the gap
**What goes wrong:** every member send 500s, staff replies to backfilled `Fechado` conversations 500. **Avoid:** one atomic activation file; web then API in one sitting; the release notes name the window; never leave the web ahead of the API for longer than that.

### Pitfall 3: An illegal row the CHECK cannot catch because the writer is a trigger
**What goes wrong:** the message trigger flips `resolved` to `open` but leaves `resolved_at` or `owner` set. **Avoid:** the coherence CHECK runs on every UPDATE, including the trigger's, so the trigger must set all four columns together; a pgTAP test per transition asserts the final row.

### Pitfall 4: Race at the close boundary
**What goes wrong:** a member message lands on a case the sweeper just closed, or a staff `close` runs between the API's "select active" and the message insert. **Avoid:** the row lock plus `CS004` plus one retry through the open path; the sweeper's `skip locked`; two-connection integration tests (never `sleep`).

### Pitfall 5: Counts that forget the state
**What goes wrong:** the staff badge, the awaiting toggle, the dashboard queue and the member dot count `Fechado` cases. **Avoid:** one shared predicate (`state <> 'closed'`) in `chatCounters`, `listInbox`, the builder, and resolve/close mark the case read.

### Pitfall 6: Strict contracts break the neighbour revision
**What goes wrong:** a new key on an existing response makes the previous web's strict parse fail, and a new key on the first-message request makes the previous API refuse it. **Avoid:** release order web before API; response keys optional; the request keys are sent only by the new web; document that rollback of the web after the API is forbidden.

### Pitfall 7: Role literal in five places
**What goes wrong:** a later role change updates four literals and misses a definer. **Avoid:** extend the drift test to every policy and definer (list them in the test), and to the assign literal.

### Pitfall 8: Grapheme versus code point on the subject
**What goes wrong:** `cutOnWord(…, 80)` counts graphemes, the DB CHECK counts code points; a derived subject of ZWJ emoji passes one and fails the other. **Avoid:** never store a derived subject (read-time derivation, A1); typed subjects are validated by code points like the body (`codePointLength`), and the CHECK is `between 1 and 80` code points on the typed value only.

### Pitfall 9: Realtime partition and signal shape
**What goes wrong:** `realtime.send` is a silent no-op from an invoker, or pgTAP flakes when no partition covers `now()` [VERIFIED: 152-chat.sql header fact 6]. **Avoid:** definers publish; a new pgTAP signal assertion fails with a named reason, never a vacuous skip, like fact 6; payload keys pinned (`conversationId`, `id`).

### Pitfall 10: e2e and seeds that assume one conversation per member
**What goes wrong:** `ensureConversation` picks an arbitrary case; `resetMemberConversation` leaves counters. **Avoid:** make the helpers select the active case and reset events/counters deliberately; keep the seed id.

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| IDOR on a uuid route | Information disclosure | participant/staff predicate + bare 404 |
| Mass assignment | Tampering | strict schemas, no column grant, insert WITH CHECK |

| Signal content leak | Information disclosure | ids-only payloads, pinned keys |

### Support cases (chamados)

Phase 12.4 turns the member's one support thread into a numbered case with a state, an owner, a subject, a category and a priority: the team takes, answers, resolves and closes it, the member sees its number and state and a list of past cases, the existing conversations become cases, and the owner's Atendimento panel reads per case (D-800..D-815, UI-D-816..UI-D-835). `kind = 'direct'` and `'group'` conversations are not touched.

- [ ] **CASE-01**: A support conversation is a case: `chat_conversations` of kind `support` gains a number, a state, an owner, a category, a priority and the resolve and close instants, all added expand-only; `direct` and `group` rows keep every case column null; a per-tenant counter table and an append-only case-events table are added, each with RLS and a tenant-first index *(D-800, D-810, D-804)*
- [ ] **CASE-02**: The case number is sequential per tenant starting at 1, assigned by the database only to rows that exist (a skipped `on conflict do nothing` insert consumes none), gapless under rollback, distinct under 20 concurrent opens in one tenant, shown as `#N` and never used as a lookup key *(D-804, UI-D-816)*
- [ ] **CASE-03**: A member has at most one active case: a partial unique index on (tenant, member) where the kind is support and the state is not closed replaces the one-per-member index; 20 concurrent first messages create exactly one case, and a message after `Fechado` opens a new case with a new number while the old one stays as history *(D-801, D-802)*
- [ ] **CASE-04**: A case is `Aberto`, `Em atendimento`, `Resolvido` or `Fechado` (stored as `open`, `in_progress`, `resolved`, `closed`); CHECK constraints make a case with no owner `Aberto`, an owned open case `Em atendimento`, and tie the resolve and close instants to their states *(D-805, D-806)*
- [ ] **CASE-05**: The database enforces the transition table (take, assign, resolve, close, reopen, edit, and the three automatic moves); an illegal move, a stale expected state and any message on a `Fechado` case are refused with stable codes, for every writer *(D-805, D-801, UI-D-817, UI-D-827)*
- [ ] **CASE-06**: A member message on a `Resolvido` case moves it to `Aberto` in the same case, clears the owner, records a `reopened` event and notifies the team; a member message on a `Fechado` case never touches it and opens a new case, including when the close races the message *(D-805, D-809, A-UI-9)*
- [ ] **CASE-07**: Any `chat.support` holder may reply to any case; a reply to an unowned `Aberto` case takes it for the replier (`Em atendimento`) in the same transaction, a reply to an owned case or to a `Resolvido` case changes neither owner nor state *(D-806, A-UI-1, UI-D-828)*
- [ ] **CASE-08**: Any staff member takes a case for themselves (a take-over of another person's case needs the expected owner); only the `chat.support.assign` holder (`admin_tenant`) assigns, only to a live staff member of the same tenant; the permission is declared in the chat manifest and re-enforced by the database role literal, pinned by the drift test *(D-806, UI-D-826)*
- [ ] **CASE-09**: The team resolves from `Aberto` or `Em atendimento`, closes from any state, and reopens `Resolvido` only (to `Aberto` with no owner, the member not told); resolve and close mark the case read for the team; every action carries the state the screen showed and a stale action answers `409 case_stale` with the case unchanged *(D-805, D-807, UI-D-827, UI-D-830)*
- [ ] **CASE-10**: The member sets the category (five fixed codes, `Outro` default) and an optional subject (80 code points) only on the message that opens the case; the priority is born `Normal` and unreachable to the member; staff edit category, subject and priority of a case that is not `Fechado`; unknown or forbidden keys are `400` and write nothing *(D-811, D-812)*
- [ ] **CASE-11**: A case without a typed subject shows the start of its first message, one line cut on a word at 80 characters with `…` only when it cut; a migrated case has no stored subject and shows the same fallback *(D-812, D-814, UI-D-819)*
- [ ] **CASE-12**: Every step (opened, taken, assigned, resolved, closed, reopened, a field changed) is an append-only, tenant-scoped row with actor, instant and states; the automatic close has no actor; no lane can update or delete it; only staff read it; a member never does *(D-810, UI-D-829, UI-D-835)*
- [ ] **CASE-13**: A case that stayed `Resolvido` for 7 days (fixed in code) is closed by the hourly worker sweep, idempotently, skipping a row a member message is changing, with a history row with no actor and a live signal, never a notice, for every tenant of the project and only through its own tenant's rows *(D-807, D-808)*
- [ ] **CASE-14**: The member's thread read answers the active case (null when none, which shows the opener) and whether any case exists; "Meus chamados" answers the current case and the closed ones newest first, 20 per page by keyset, own cases only; a closed case opens read-only and a foreign id is the bare 404 *(D-803, UI-D-818, UI-D-821)*

- [ ] **CASE-16**: The team's inbox has the tabs `Em aberto` (default), `Resolvidos`, `Fechados` and the filters owner, priority and "Aguardando resposta", sorted by latest activity with a stable keyset, rows carrying the case facts and the list of legal actions; a roster route answers live staff names only *(D-805, D-806, D-809, UI-D-823, UI-D-824, UI-D-826)*
