# Phase 12.4 Plan 01: Case columns, per-tenant numbering and event history Summary

**A member's first support message through the unchanged API is now stored as a born-open case numbered per tenant by an AFTER INSERT trigger over a locked counter row, with an append-only opened event, expand-only schema, legacy-safe CHECKs and pgTAP plus integration proofs.**

## Performance

- **Duration:** 12 min
- **Started:** 2026-11-17T08:21:00Z
- **Completed:** 2026-11-17T08:33:00Z
- **Tasks:** 4
- **Files modified:** 11 (plus 3 migration snapshots)

## Accomplishments

- Tracer: `POST /v1/chat/support/messages` with the API code unchanged creates a conversation that the database numbers `highestNumber + 1`, with state open, priority normal, category other and one `opened` event whose actor is the member; the answer shape is byte-identical (no `case` key).
- Expand-only schema: seven nullable columns, `chat_case_counters` (RLS, no policy, privileges revoked) and `chat_case_events` (cascade on the conversation, set null on both users, no foreign key on `message_id`, staff-only select, UPDATE/DELETE/TRUNCATE revoked).
- Numbering negatives in pgTAP: a skipped `on conflict do nothing` moves the counter once and writes one event, a savepoint rollback leaves no gap, two members number consecutively, tenants number independently, directs and groups are never numbered, counted or given an event, and the number is a 32-bit integer.
- Legacy rows (all case columns null) still take a member message and a staff reply, in pgTAP and through the API on the seeded demo thread: the shape and coherence CHECKs are VALID and spelled so a null state passes.
- Isolation: tenant B reads no case column, event or counter of tenant A (positive controls included); no lane updates any of the seven columns; a direct DML on the history changes nothing.

**2. [Rule 2 - Hardening] Counter table privileges revoked, not only policy-less**
- **Found during:** Task 3
- **Issue:** the plan states both "the counters answer zero rows to every lane" and "no privilege at all on `chat_case_counters`". Both cannot hold; a policy-less table with default grants answers zero rows, a revoked one refuses.
- **Fix:** kept the stricter reading: `revoke all ... from authenticated` in the constraints migration, so a lane gets 42501. pgTAP asserts zero policies, no table privilege for `authenticated` or `anon`, and the 42501 refusal.
- **Files modified:** `supabase/migrations/20261117082657_chat_cases_constraints.sql`, `supabase/tests/235-chat-cases.sql`
- **Committed in:** `009fd2e2`, `6f9beaa9`

**3. [Rule 1 - Spec reading] The state value list reports through the coherence CHECK**
- **Found during:** Task 2
- **Issue:** Postgres evaluates CHECKs by name, so a bogus `state` is reported by `chat_conversations_case_coherence_chk` before `chat_conversations_state_chk`.
- **Fix:** the pgTAP test asserts the coherence constraint name for that refusal and pins `chat_conversations_state_chk` separately by catalogue (valid, lists the four states).
- **Committed in:** `009fd2e2`

**4. [Rule 2 - Coverage] `chat_case_events_kind_chk` added**
