# Phase 12.4 Plan 19: The team's thread with cases, second half Summary

**Assign, edit and read-only details sheets (history, earlier cases) mounted on the staff thread from the server's actions[], with changed-fields-only edits, stale-protected writes, a polite live region and a member-viewer wall around all of it**

- **Completed:** 2026-11-17T12:17:20Z

## Accomplishments

- "Atribuir a…" opens a real sheet: a radiogroup of the live staff from the shared roster (read when the sheet opens), the current owner marked "responsável hoje", "Atribuir" disabled until a different person is picked, and a call that sends only `assign`, the state the sheet opened on and the picked id. Success toasts "Chamado #42 atribuído a Ana.", a stale or failed answer toasts and keeps the picked row.
- "Editar…" opens the edit sheet: category and priority chips with one always selected, the subject prefilled with the TYPED subject only, and a save that sends just the changed fields (a blanked subject as null), keeping every draft on a failure. It never exists on a closed case.
- "Ver detalhes e histórico" and the bar's row 1 open the read-only details sheet: Dados (state pill, category, priority, owner or "Sem responsável", "Aberto em" in the tenant clock), the history read lazily on open (three skeleton rows, oldest first, actor in bold, the automatic close with no actor, inline retry) and up to five earlier cases of the member as anchors.
- The staff bar holds one persistent polite live region ("assumido, resolvido, fechado por {name}", only for a change that arrives while the page is open, never moving focus) and hands focus back to the control that opened a sheet. The `data-staff-sheet` stub of plan 15 is gone (WINDOWS row 149 closed).
- A member viewer, even handed a staff-shaped case, mounts none of the sheets and makes zero roster and history calls.

## Decisions Made

See `key-decisions` above. In short: the sheets' facts ride on the staff header view (no new route, no bootstrap read in the BFF), the typed subject is the edit baseline, and every sheet captures the state it opened on so the server, not the screen, decides staleness.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The staff header carried none of the details and edit facts**
- **Found during:** Task 1
- **Issue:** the plan notes the BFF header has no "Dados" fields and the edit sheet needs the TYPED subject; `StaffCaseHeaderView` held only the meta text, the subject label and the owner facts.
- **Fix:** `caseHeaderView` now copies `category`, `priority`, `typedSubject` and `openedAt` for the staff viewer (the member header is still built from named fields only). The BFF handler and the write actions already return `caseHeaderView`, so no route, inventory or handler change was needed; the pane's re-read rebuilds the new fields from named properties and ignores an answer without them. `openedAt` stays an ISO string and is worded by the pure `caseOpenedMoment` with the day keys and the tenant zone, so no bootstrap read was added to the write path.
- **Files modified:** `apps/web/lib/chat-view.ts`, `apps/web/lib/chat-view.test.ts`, `ThreadPane.tsx`, four test fixtures
- **Verification:** `chat-view.test.ts` (3b), the BFF handler tests, the whole web suite and `tsc`
