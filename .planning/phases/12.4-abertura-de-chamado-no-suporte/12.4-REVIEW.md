## Warnings

### WR-05: History sentences are inferred from names and state, so migrated and same-name cases read wrongly (carried over, deferred)

**File:** `apps/web/lib/chat-view.ts` (`caseHistoryView`, the `byMember` and `actorGone` lines)
**Issue:** Unchanged from round 1. The API history row has no flag for "the actor is the member" or "the actor left".
The web guesses `byMember = reopened && actor name === opened actor name` and `actorGone = closed && fromState !==
'resolved'`. (1) Backfilled `closed` events have a null actor and `from_state = 'open'`, so they print as "closed by
someone who has since left" although no person closed them. (2) A staff member whose name equals the member's makes a
team reopen read as "reopened by the member". (3) If the member left the tenant, a member-caused reopen reads as a
team reopen by a departed person. It is an audit trail shown in the staff details sheet.
**Fix:** Have the history query return explicit `actorIsMember` and `actorGone` booleans and render a null actor as the
system close; for backfilled `closed` rows write `from_state = null` or add an `automatic` flag.

### WR-06: A refetch that lands while "load more" is in flight replaces the list and permanently drops one row the server still lists

**File:** `apps/web/app/(app)/suporte/SupportInbox.tsx:286-298` (refresh) against `:333-352` (`loadMore`), with `apps/web/lib/chat-view.ts:333-353`
**Issue:** `refreshPage1` decides "whole" from `pagesRef.current <= 1`, and `pagesRef` is incremented only when a
loaded page is APPENDED, after the server action answers. While a `loadMoreInboxAction(cursor)` is in flight the list
holds one page and `pagesRef` is still 1, so a refetch answer is treated as the whole view. Failing scenario: the staff
scrolls to the end of page 1 (rows 0..N-1, cursor = row N-1) and the sentinel fires `loadMore`. A `chat.message` signal
arrives a few hundred ms later and a fresh page 1 returns one NEW case on top: `[new, row0..row(N-2)]`, `hasMore` true.
`reconcileInboxPage` returns `whole: true`, the list becomes those N rows and the cursor becomes the fresh tail's
cursor. Then the `loadMore` answer (rows N..2N-1, taken from the OLD cursor) is appended and the cursor jumps past it.
Row N-1 is in neither the fresh page nor the loaded page, so it is never shown (until a reload or a view change), and
the next refetch cannot bring it back because it now lies deeper than page 1's window with `pagesRef` at 2. The round 1
code (`mergeTop`) kept every loaded row, so this is a regression introduced by the WR-01 fix. A realtime signal during a
scroll is the normal case on a busy inbox. The pure function is not at fault; its input is.
**Fix:** Treat a read in flight as "more than page 1". Add `const loadingMoreRef = useRef(false)`, set it to true before
`await loadMoreInboxAction` and false in a `finally`, and call
`reconcileInboxPage(itemsRef.current, page.items, { holdsOnlyPage1: pagesRef.current <= 1 && !loadingMoreRef.current, hasMore })`.
Alternatively bump a `wholeEpochRef` in the `whole` branch and make `loadMore` discard its page (and keep the cursor the
refetch set) when the epoch changed while it waited. Add a test: first-page list with a cursor, `loadMore` held open,
signal with a new row on top, release `loadMore`, assert the row between is still shown or re-requested.

### WR-07: After a stale answer the assign sheet keeps its frozen baseline, so every retry is stale again until it is closed

**File:** `apps/web/app/(app)/suporte/AssignSheet.tsx:107-109` and `:128-147`
**Issue:** `openedOn` and `openedOwner` are `useState` initial values and are never updated; `AssignBody` stays mounted
while the sheet is open. On `stale` the toast says "A tela foi atualizada" and `onStale()` re-reads the header, so the
roster mark moves to the new owner and the screen looks current. The sheet stays open on purpose with the pick
(asserted by the new test). The admin then taps "Atribuir" again and the web re-sends the SAME `expectedState` and
`expectedOwnerId` it opened with, so the server answers `case_stale` again, and again, with no way out except closing
and reopening the sheet. Before WR-04 this needed a state change while open; with the owner check it now happens
whenever a colleague assigns or takes the case in the same minute, which is exactly the case WR-04 exists for. The
sheet tells the admin to retry and then refuses the retry.
**Fix:** Re-baseline on a stale answer so the next confirm carries what the admin now sees, and clear the pick so the
admin re-chooses against the new owner: keep the baseline in state (`const [base, setBase] = useState({ state:
header.state.state, owner: header.ownerUserId })`), and after `onStale()` set `stale` true and, in an effect keyed on
`header.state.state` and `header.ownerUserId`, call `setBase(...)` and `setPicked(null)` when `stale` is set. The
simpler alternative is to close the sheet on `stale`. Update the new WR-04 test, which currently pins the dead-end.

## Info

### IN-01: `chat.case_assigned` push is not re-validated against the case's current owner (carried over, deferred)

**File:** `packages/modules/chat/server/notifications.ts:233-266` (`resolveCaseAssigned`)
**Issue:** Unchanged. The worker resolver checks only that the actor is not the assignee. If the case is reassigned
again before the worker runs, the first assignee still gets "O chamado #N ... foi atribuído a você." for a case that is
no longer theirs. WR-04 makes a quick double assignment less likely to be silent but does not remove this.
**Fix:** Add `and c.owner_user_id = ${payload.assigneeUserId}::uuid and c.state = 'in_progress'` to the select.

### IN-02: Builder v9 shipped in one migration and the median rule changed in the next without a version bump (carried over, deferred)

**File:** `supabase/migrations/20261117092952_dashboard_cases_first_response.sql:1-15`
**Issue:** Unchanged. A project that applied only `20261117092714` keeps weekly medians under the per-turn rule until
the following day, because the builder's "already built at this version" guard will not rebuild them.
**Fix:** If neither file has shipped to a shared project, fold the rule into the first file; otherwise add a migration
that restates the builder with `v_version := 10`.

### IN-03: Stale prose about which action carries `expectedOwnerId`, and the contract does not say when it is required

**File:** `apps/web/app/(app)/suporte/actions.ts` (docblock above `runCaseActionAction`, "and, for a take-over, the owner"), `packages/modules/chat/contracts/index.ts:356-362`
**Issue:** The server-action docblock still says the owner travels only for a take-over; assign now carries it too. The
`caseAssignInputSchema` marks `expectedOwnerId` optional with no note that it is mandatory for an in-progress case, so
the generated OpenAPI shows no hint that omitting it yields a 409 (only the route description says so). Also the route
description says "any other value, or none, is case_stale" while the code (and an unowned `in_progress`, which the CHECK
forbids) makes that exact for in-progress only; the wording is correct but easy to read as all assigns.
**Fix:** Update the docblock, and add a one-line `.describe()` or comment on `expectedOwnerId` in the schema stating
"required when the case is in progress".

### IN-04: The "send lands in an already existing case" branch of the member pane is untested

**File:** `apps/web/app/(app)/suporte/ThreadPane.tsx:673-683` against `apps/web/app/(app)/suporte/ThreadPane.member.test.tsx` (describe "a send that lands in a NEW case")
**Issue:** Every new test answers `case.opened: true`, so the `else if (switched)` branch (a send that switches to a
different case that is not newly opened, for example the member opened another one in a second tab) never runs; the
header built there has an empty `subject` until the re-read. A regression there would not be caught.
**Fix:** Add one test with `case: { id: NEW_ID, number: 43, state: 'in_progress', opened: false, reopened: false }` and
assert the bar shows "Chamado #43", the topic moves and the old thread is replaced.
