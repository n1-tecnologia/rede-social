# Phase 12.4: Code Review Report

**Reviewed:** 2026-11-17
**Depth:** standard
**Files Reviewed:** 70
**Status:** issues_found

## Summary

The tenant-isolation core holds. Every SECURITY DEFINER function pins `search_path = ''`, takes the tenant and the
user from the JWT claim plus a LIVE membership (`status = 'active'`, not blocked, not deleted, role equal to the
claim), pins `tenant_id` and `kind = 'support'` in every statement, locks the conversation row `for update` before
reading the state, and builds no dynamic SQL. Grants are `authenticated` for the staff definers and `service_role`
only for the sweep and the backfill. `chat_case_counters` has RLS and no grant, `chat_case_events` is append-only,
and the `UPDATE` column grant on `chat_conversations` still covers `staff_last_read_seq` only, so a lane cannot move a
case column. The activation migration is one `do` block under `share row exclusive`, the backfill runs before the new
unique index exists, and the legacy numbering and idempotence are correct. The number comes from an AFTER trigger on
the counter row lock, so it has no gaps and no duplicates. Realtime signals carry `{ conversationId }` only. Member
read paths select no owner, priority, event or staff id, and a staff message author reaches a member as a first name.
I found no cross-tenant leak and no authorization bypass.

What remains is client-side state handling and two small contract inconsistencies. One of them (WR-04) is the
"expected-owner" check you asked about.

## Warnings

### WR-01: Staff inbox keeps rows that left the tab after a realtime refetch

**File:** `apps/web/app/(app)/suporte/SupportInbox.tsx:41-44` (`mergeTop`), used at `:228`
**Issue:** `refreshPage1` merges the fresh page 1 into the list with `[...fresh, ...current.filter(not in fresh)]`.
Nothing ever removes a row. The component docblock (and A-UI-12) says "a row whose state no longer belongs to the tab
leaves on the next refetch", but a row that left the view is absent from `fresh`, so it stays in `current`.
Failing scenario: on "Em aberto", staff A resolves case #42. The `chat.case` signal on `support-inbox` refetches page
1 of "Em aberto"; #42 is not in it, so it stays on screen with its stale "Em andamento" pill and "Com Carla" meta. The
same happens for every other team member's open list, for "Eu" or "Sem responsável" after an assign or take, and for
the "Aguardando resposta" toggle after a team read. The row only goes away on a reload or a view change. The stale
pill then disagrees with the thread header on the right (resolved) in the desktop split.
**Fix:** Drop rows that page 1 should have contained but did not. When the list holds only page 1 (`pagesRef.current
<= 1`) replace it with `page.items`. When more pages are loaded, keep only the loaded rows older than the oldest
fresh row, or re-read the loaded pages. Add a test that a row missing from a refetch disappears.

### WR-02: Member pane does not adopt the new case when a send lands in a different conversation

**File:** `apps/web/app/(app)/suporte/ThreadPane.tsx:564-570` and `:596-614`
**Issue:** When staff close (or the 7-day sweep closes) the member's case and the member sends before the `chat.case`
signal or the refocus re-read has updated the header, the API retries and opens a NEW case (D-801), so
`SendResult.conversationId` is the new conversation. `onSend` only adopts the id when `conversationRef.current` is null
(`if (!conversationRef.current) {...}`). Here it is the OLD id, so it is kept. Consequences: `setCaseView` builds the
header of the new case, then the `void refreshCase()` on the next lines reads the OLD conversation, gets the closed
header, and `setCaseView(closed)` replaces it. The composer is swapped for the "Fechado" strip even though the
member's new case is open. Catch-up, the read mark and the realtime topic all stay on the old conversation, so the
team's replies in the new case do not appear until a reload. The old thread also shows the new message at seq 1
inside the old message list.
**Fix:** After a member send, compare `result.conversationId` with `conversationRef.current`. When they differ, reset
the pane to the new case: set the conversation id and ref, replace `views` with `[view]`, reset `cursorRef`,
`readSeqRef` and `hasOlder`, and build the header from `sentCase`. Do this before calling `refreshCase()`.

### WR-03: "Anteriores" count is off by one while a current case exists (`total` contract mismatch)

**File:** `apps/web/app/(app)/suporte/chamados/MyCasesList.tsx:178` against `packages/modules/chat/server/cases.ts:197-204`
and `packages/modules/chat/contracts/index.ts` (`myCasesPageSchema` doc)
**Issue:** The API's `total` counts CLOSED cases only (`and c.state = 'closed'`; the integration test pins 1 active +
2 closed = `total` 2, and the route description says "the count of closed cases"). The contract docblock says "`total`
counts every case of the member", and the web follows that: `previousCount = Math.max(total - (current ? 1 : 0),
items.length)`. With 1 active and 25 closed cases the API sends 25, the list holds 20, and the header reads
"Anteriores 24". The `Math.max(..., items.length)` hides the bug for small lists, so the unit tests, which model
`total` as "all cases", pass.
**Fix:** Pick one meaning. Smallest change: the web should use `total` as the closed count (`previousCount =
Math.max(total, items.length)`), fix the docblock in `contracts/index.ts`, and change the `MyCasesList` tests that model
`total` as all cases.

### WR-04: `assign` accepts `expectedOwnerId` but never checks it, so a stale assign silently overwrites another admin's assignment

**File:** `supabase/migrations/20261117085928_chat_cases_actions_matrix.sql:131-147` (assign branch), `packages/modules/chat/contracts/index.ts` (`caseAssignInputSchema`), `apps/web/app/(app)/suporte/AssignSheet.tsx:119-123`
**Issue:** Take-over uses `p_expected_owner` to answer CS002 when the owner changed. Assign checks only the expected
STATE. Failing scenario: admin A opens the assign sheet on an `in_progress` case owned by Carla. Admin B assigns the
case to Davi. A picks Eduardo and confirms. The state is still `in_progress`, so the definer reassigns to Eduardo, and
B's assignment is lost with no stale answer. The route schema accepts `expectedOwnerId` on assign and the route passes
it to the definer, which ignores it. The web never sends it. The same applies to Resolver and Fechar, but D-842 lets
any staff member do those on any case, so only assign is a defect.
**Fix:** In the `assign` branch raise `CS002` when `v_state = 'in_progress' and p_expected_owner is distinct from
v_owner`. In `AssignSheet` send `expectedOwnerId: header.ownerUserId` when the owner is set. Otherwise drop
`expectedOwnerId` from `caseAssignInputSchema` so the contract does not promise a check that does not exist.

### WR-05: History sentences are inferred from names and state, so migrated and same-name cases read wrongly

**File:** `apps/web/lib/chat-view.ts` (`caseHistoryView`, the `byMember` and `actorGone` lines)
**Issue:** The API history row has no flag for "the actor is the member" or "the actor left". The web guesses:
`byMember = reopened && actor name === opened actor name`, and `actorGone = closed && fromState !== 'resolved'`.
(1) Every case the backfill closed has a `closed` event with a null actor and `from_state = 'open'`
(`20261117084153_chat_cases_transitions.sql`, the `closed` CTE). The guess reads that as "closed by someone who has
since left" and prints `history.closed` with `history.actorGone`, for cases the system migrated and no person closed.
(2) A staff member whose display name equals the member's name makes a team reopen read as "reopened by the member".
(3) If the member left the tenant, the name is absent, `openedBy` is undefined, and a member-caused reopen reads as a
team reopen by a departed person. Only the staff details sheet shows this, but it is an audit trail.
**Fix:** Have the history query return explicit booleans: `actorIsMember` (`actor_user_id = c.created_by_user_id`) and
`actorGone` (a non-null actor id with no live membership), and render a null actor as the system close. For backfilled
`closed` rows, either write `from_state = null` so they read as "migrado", or add an `automatic` flag.

## Info

### IN-01: `chat.case_assigned` push is not re-validated against the case's current owner

**File:** `packages/modules/chat/server/notifications.ts:233-266` (`resolveCaseAssigned`)
**Issue:** The resolver runs in the worker after the commit and checks only that the actor is not the assignee. If the
case is reassigned again before the worker runs, the first assignee still gets "O chamado #N ... foi atribuído a você."
for a case that is no longer theirs.
**Fix:** Add `and c.owner_user_id = ${payload.assigneeUserId}::uuid and c.state = 'in_progress'` to the select, as
`resolveCaseResolved` does for `resolved_at`.

### IN-02: Builder v9 shipped in one migration and the median rule changed in the next without a version bump

**File:** `supabase/migrations/20261117092952_dashboard_cases_first_response.sql:1-15`
**Issue:** `20261117092714` moves `v_version` to 9 and rebuilds yesterday for every tenant. `20261117092952` then redefines
`dashboard_area_support` with the per-case first-response rule but keeps version 9, and the header says nobody has a v9
snapshot built under the old rule "outside the local stack". Any project that applied only the first file (homolog, a
tenant project migrated in two steps, a rolled-back deploy) keeps weekly medians under the per-turn rule until the
following day's build. The builder's "already built at this version" guard (`payload_version = v_version`) will not
rebuild them.
**Fix:** If neither file has shipped to a shared project, fold the first-response rule into the first file. If it has,
add a third migration that restates `dashboard_build_snapshot` with `v_version := 10`.
