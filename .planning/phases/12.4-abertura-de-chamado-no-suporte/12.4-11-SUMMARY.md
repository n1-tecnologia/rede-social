# Phase 12.4 Plan 11: Web view layer and case catalog Summary

**The web now has one pure view layer for support cases (state to word, tone and glyph; finished headers for staff and member; card, inbox row and history sentences) over a pt-BR catalog that holds every UI-SPEC sentence once, test-pinned, with the CASE-27 forbidden-word scan and the shipped pins that D-800 reverses moved to the new copy.**

## Performance

- **Duration:** 8 min
- **Started:** 2026-11-17T09:52:21Z
- **Completed:** 2026-11-17T10:00Z
- **Tasks:** 3
- **Files modified:** 6 (1 created)

## Accomplishments

- `caseStateView` is the single mapping of the four states to catalog label, pill tone and glyph name; `caseTitle` writes the number as a plain integer (1204 stays 1204); `caseHeaderView` builds the member header from named fields only (a hostile payload carrying `priority`, `ownerName`, `ownerUserId` or `actions` yields none of them) and the team header with the meta text ('Pagamento · Normal · Com Carla') and the server's `actions[]` untouched.
- `inboxRowView` gains `case` (subject line, state view, priority pill only for Alta and Baixa, meta text), `caseCardView` finishes the "Meus chamados" card with the 'Você: ' and 'Equipe: ' prefixes, and `caseEventSentence` returns one sentence per event kind split into bold and plain parts (actor in the bold slot, automatic close with no actor, 'Alguém da equipe' for an actor who left, 'Membro removido' for a member who left).
- `chat.json` carries every key of the UI-SPEC copy table (148 case keys) plus `history.actorGone` and `inbox.filter.rosterError`; the flat `inbox.empty.title|body` pair is replaced by `inbox.empty.{open,awaiting,resolved,closed,filtered}.title|body`.
- `chat-cases-messages.test.ts` pins the exact key set (shipped-unchanged keys plus the case copy, nothing extra, nothing missing), every sentence verbatim, every placeholder, no empty or placeholder-only value, and the CASE-27 scan over parsed values (whole-word, NFC, format characters stripped, sorted report; `prioridade` banned only in `case.`, `open.`, `mine.`, `live.`, `notFound.`, `member.`).

## Decisions Made

- The translator comes first in every function that needs the catalog (`caseSubjectLine(t, number, label)`, `caseMetaText(t, facts)`, `caseEventSentence(t, event)`), like the plan's `caseTitle(t, number)`.
- `caseHeaderView(kase, { viewer, t })` returns a discriminated union (`viewer: 'member' | 'staff'`); the staff arm adds `meta` and `actions`.
- The plural cases the plan mentions for "section counts" do not exist in the chat table (the counts beside the "Meus chamados" section titles are numbers, not messages), so the catalog test formats the placeholders and the one shipped plural instead of inventing a plural.

**3. [Rule 2 - Missing critical] Two optional event hints on `caseEventSentence`**
- **Found during:** Task 2
- **Issue:** the history row (`caseEventSchema`) has no field that separates a member's reopen ('{member} respondeu e o chamado foi reaberto.') from a team reopen, or an actor who left the tenant from the automatic close (both have no `actorName`). Without a rule the view would print the wrong sentence.
- **Fix:** the input type is `CaseEvent & { byMember?: boolean; actorGone?: boolean }`. Without hints a reopen reads as the team's and a close with no actor reads as the automatic close, which is what the job and the backfill write.
- **Needs follow-up:** plan 07's history route or plan 20's mapping should set the hints (the reopen event carries a `message_id` in the database; the actor-gone case is a close whose `actor_user_id` is set but no longer live staff). Nothing in this plan could fill them.
