# Phase 12.4 Plan 03: Staff action definers, history and the chat.case signal Summary

**The staff half of the case state machine now lives in two security definers, app.chat_case_act (take, assign, resolve, close, reopen) and app.chat_case_edit, each locking the case row, checking the state the caller saw, writing its history row and publishing an ids-only chat.case signal, with the staff role literal pinned by an eight-source drift test.**

## Performance

- **Duration:** 8 min (2026-11-17T08:54Z to 09:02Z)
- **Tasks:** 4 of 4 (Task 1 is the tracer)
- **Files modified:** 10 (three migrations, three snapshots, the journal, the pgTAP file, the realtime contract, the chat integration test)

## Accomplishments

- **Tracer (Task 1):** the failing pgTAP section 9 first (the function did not exist), then `app.chat_case_signal` and the take-only `app.chat_case_act`. A support staff lane takes an open case: the case becomes in_progress with the caller as owner, one `taken` event, and three `chat.case` signals (`conv:<c>`, `support-inbox`, `user:<member>`) whose payload keys are exactly `conversationId` and `id`. A member lane is 42501 and tenant B's staff is CS001. The tracer feedback gate (end-of-phase mode, automated-only verify) was re-run green before the expansion tasks.
- **Action matrix (Task 2):** `20261117085928_chat_cases_actions_matrix.sql` redefines `app.chat_case_act` whole. Take works from open and, as a take-over, from in_progress owned by another person only with `p_expected_owner` equal to the live owner; assign is `admin_tenant` only, to a live same-tenant staff membership that is not the current owner (CS005 otherwise); resolve works from open and in_progress; close from open, in_progress and resolved and clears `resolved_at`; reopen from resolved only and clears the owner. Resolve and close set `staff_last_read_seq = last_seq`. One UPDATE sets every column the coherence CHECK reads. Stale expected state is CS002, an illegal pair CS003, invalid input 22023.
- **Edit definer (Task 3):** `app.chat_case_edit` with the same guard chain, a null argument leaving a field alone and `p_blank_subject` clearing the subject, one `edited` row per changed field with its own `from_value` and `to_value` sharing one instant, no write and no signal for a no-op, CS003 on a closed case.
- **Drift test (Task 4):** the Pitfall 4 test now compares eight sources (five policies including `chat_case_events_select`, `app.realtime_topic_allowed`, and the two definers) with the TypeScript staff roles, asserts the assignee list inside the act definer, and asserts the `tenant_role() = 'admin_tenant'` guard appears exactly once there and never in the edit definer.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] The staff check also requires a live membership**
- **Found during:** Task 1
- **Issue:** the plan names the claim literal only. A staff member blocked or removed after sign-in keeps a valid token for up to its TTL, and the claim alone would let them act.
- **Fix:** both definers also require a membership of the caller in the tenant with `role = app.tenant_role()` (the claim must be backed), `status = 'active'`, not blocked, not deleted; otherwise 42501. The literal stays the first match the drift test parses. pgTAP covers a blocked staff, a removed staff and a support member claiming admin.
- **Files modified:** `20261117085644_chat_cases_actions.sql`, `20261117085928_chat_cases_actions_matrix.sql`, `20261117090105_chat_cases_edit.sql`
- **Commits:** `bbcaa720`, `e26597b8`, `ee4ee910`

**2. [Rule 3 - Blocking] The events policy has another name**
- **Found during:** Task 4
- **Issue:** the plan names `chat_case_events_staff_select`; plan 01 created it as `chat_case_events_select`.
- **Fix:** the drift test lists the real name; the count is 5 as the plan says.
- **Commit:** `85bf6361`

**3. [Rule 1 - Detail] clock_timestamp() instead of now() for the case and history instants**
- **Found during:** Task 2
- **Issue:** `now()` is the transaction start, so two actions in one transaction (EP-027) and an action after the born `opened` event would tie on `created_at` and read in random uuid order.
- **Fix:** one `clock_timestamp()` per call stamps `resolved_at`, `closed_at` and every event of the call (the rows of one edit still share one instant, EP-034). The `opened` row of the trigger keeps `now()` and sorts first.
- **Commits:** `e26597b8`, `ee4ee910`

**4. [Rule 3 - Blocking] A shared signal helper**
- **Found during:** Task 1
- **Issue:** the plan has both definers publish the same three signals; spelling them twice would let the topics drift.
- **Fix:** `app.chat_case_signal(tenant, conversation, member)`, a definer with `revoke all ... from public` and no grant, called only by the two definers (pgTAP asserts neither `anon` nor `authenticated` can execute it).
- **Commit:** `bbcaa720`

**5. [Rule 3 - Blocking] Command spelling**
- **Found during:** all tasks
- **Issue:** the plan writes `pnpm supabase ...` and `@tria/api`; the workspace is `@rede-social/*` and the repository rule is to use `bash scripts/supabase.sh`.
- **Fix:** migrations applied and pgTAP run through the wrapper (`migration up`, `test db`), drizzle-kit through `pnpm --filter @rede-social/api exec`. No `db:reset`, no `db:seed`, no hosted command, no push.
