# Phase 12.4 Plan 08: The team's write API Summary

**The team now takes, assigns, resolves, closes, reopens and edits a support case through six routes that only call the two definers, with one closed SQLSTATE mapper, two ids-only notice events emitted after the commit, and a closed-case reply refused as `case_closed`.**

## Accomplishments

- **Tracer (Task 1):** the failing mapper unit test and the "case resolve" integration test first (both red for the right reason: no export, then a 404 on the missing route), then `mapCaseError`, `runCaseAction`, `runCaseEdit` and the routes. Staff resolves an in_progress case: 200, `state` resolved, `actions` offering reopen and close and not resolve, exactly one `chat.case_resolved` with only `tenantId`, `conversationId` and `resolvedAt`; the same request repeated is `409 case_stale` and emits nothing.
- **Routes:** take, resolve, close, reopen with the literal `requirePermission('chat.support')`, assign as its own greppable route with the literal `chat.support.assign`, and `PATCH .../case`. Every route sends the intent and the state the caller saw to the definer and answers `staffCaseOf` re-read in the same transaction; no route computes a transition.
- **Mapper:** CS001 is the bare 404 with no details, CS002 `case_stale` and CS003 `transition_not_allowed` are distinguishable by `details.chat`, CS004 `case_closed`, CS005 `assignee_invalid`, 42501 403, 22023 400 and the subject CHECK `subject_too_long`. The unit test asserts no input message, SQLSTATE or constraint text reaches the answer.
- **Events:** resolve emits `chat.case_resolved`, assign emits `chat.case_assigned` (ids only), both after `withTenantTx` returned (`grep -n "emit(" cases.ts` shows lines 634 and 641, outside any callback). Take, close, reopen, edit and every refused or stale action emit nothing, asserted by the observed spies.
- **Reply path:** `replyToConversation` maps CS004 to `409 { chat: 'case_closed' }` with nothing written; a blocked or removed member still wins over closed.
- **Races (Promise.all, no sleep):** two staff taking one case give exactly one 200 and one `case_stale`; a close racing a resolve gives one winner and one 409 (and the resolved event exists only when resolve won); a member message and a reply racing a close never deadlock or answer 5xx.
- **Isolation:** six inventory rows and a `chat case actions` case (lab admin and lab support against a valid demo id and a random uuid on every route plus the history: identical bare 404; wrong host `TENANT_HOST_MISMATCH`; demo admin runs every route on the same id). EP-074..EP-078 are named tests in `chat-cases-actions.test.ts`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Routes, inventory rows and the isolation case land with the tracer, not in Tasks 2 and 3**
- **Found during:** Task 1 gate (`tests/unit/isolation-inventory.test.ts` fails on any mounted route with no case)
- **Issue:** the plan puts the inventory rows and `isolation.test.ts` case in Task 3 and the other routes in Task 2, which would leave the shipped unit gate red at the Task 1 commit.
- **Fix:** all six routes, the six rows and the `chat case actions` case are in `a470989b`; Task 2 carries the reply-path change and the behaviour tests, Task 3 the EP tests.
- **Commit:** `a470989b`

**2. [Rule 1 - Bug in the plan's assertion] EP-075 "highest plus one" is false after a sweep**
- **Found during:** Task 3
- **Issue:** the counter is never reset, so after `sweepCases` the lab tenant has no case (highest 0) while its counter is at 45; "each new number is its own highest plus one" failed with 46.
- **Fix:** cases of the two tenants are interleaved; each tenant's numbers advance by exactly +1 whatever the other did, and each first number is above that tenant's own highest. This proves independence without resetting the counter.
- **Commit:** `eee24c1c`

**3. [Rule 2 - Missing critical] A CHECK violation maps only when it is the subject one**
- **Found during:** Task 1
- **Issue:** the plan says "a subject CHECK violation" maps to `subject_too_long`; a bare `23514` map would also relabel the coherence CHECK (a server bug) as a client error.
- **Fix:** `mapCaseError` reads `constraint_name` down the cause chain and maps only `chat_conversations_subject_chk`.
- **Commit:** `a470989b`

### Notes, not deviations

- **42501 through the API:** `requireAuth` answers `MEMBERSHIP_BLOCKED` and `requirePermission` answers `403 FORBIDDEN` before the definer is reached for a member, a demoted staff member (tested) or a blocked one, so a 42501 from the definer has no API path today. EP-078's "produces them through the API" is met for CS001..CS005 and for the 403; the 42501 definer branch itself is proved by pgTAP section 9..11 (plan 03) and the mapper unit test.
