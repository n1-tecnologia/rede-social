# Phase 12.4 Plan 20: Web BFF handlers and server actions for support cases Summary

**The web now has the four finished-view BFF read handlers (case header, history, roster, my cases), the inbox handler with the case filters in the API vocabulary, and the typed server actions (take, assign, resolve, close, reopen, edit, my-cases paging, the opener send) that plans 12 to 19 stand on, each with an inventory row, a closed result type and a test.**

## Accomplishments

- The case header handler (the tracer) answers `{ viewer, header }` for a staff `in_progress` case (meta "Pagamento · Normal · Com Carla", the server's `actions[]` untouched) and for a member (title, state and subject only), in one API call, `no-store`. A priority, owner or action list the mocked API wrongly sends a member appears nowhere in the body.
- History, roster and my-cases handlers, and the inbox handler's `tab`, `owner`, `priority` and `awaiting=1` pass-through (an unknown value is dropped by the single `parseInboxFilters` before the forward). Every handler refuses a cross-site request and an anonymous one with zero API calls, forwards once, and logs status and code only.
- `runCaseActionAction` sends the intent plus `expectedState` (and `expectedOwnerId` for a take-over, `assigneeUserId` for an assign) and nothing else; a forged owner, state or extra key is `invalid` with zero API calls. `editCaseAction` sends only the changed fields (a blank subject as null). Results are the closed `ok` / `stale` / `closed` / `not_allowed` / `invalid` / `failed`.
- `sendSupportMessageAction(body, category?, subject?)` returns the API's `case` object unchanged (and no `case` key when the API sent none); `loadMoreMyCasesAction(null)` and `(cursor)` both answer `{ current, items, total, nextCursor }` (checker W11); `loadMoreInboxAction(cursor, filters)` is the one signature plan 14 calls (checker R-I8).

- **Files modified:** `apps/web/lib/chat-view.ts`
- **Committed in:** `e28198da`
