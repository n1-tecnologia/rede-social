<objective>
The server half of Web Push. A member's subscription is stored safely, every pushable kind reaches it with the tenant's name and icon, dead endpoints clean themselves up, and all of it plugs into the channel abstraction 07-01 started.

**As a** member who turned push on, **I want to** get a banner with my organisation's name and icon that opens the right screen, **so that** I hear about new content and replies even when the app is closed. This story comes from NOTIF-03, NOTIF-04 and ROADMAP Phase 7 SC 2.

Purpose: push is the only surface outside the app, so it must carry the tenant's identity (the core value) and must never become an SSRF lever, a duplicate storm or a leak after blocking. It is proved here against a fake transport and deterministic headers, before 07-07 builds the browser side and 07-08 hands it the chat kinds.
Output: `push_subscriptions` with its definers and routes, the push adapter, the `notifications.push-send` job, the transport seam, the VAPID env rules, and the push integration suite.

<planning_decisions>
1. **The transport lives in the notifications module and reads the kernel env.** It is the first module to import `@rede-social/core/server/env`, which is allowed by the `./server/*` export and by Biome. The alternative, a kernel push seam, would move module-specific delivery into the kernel for no gain.
2. **Per-subscription outcomes never fail the whole job.** Re-throwing would make pg-boss resend to subscriptions that already succeeded. Failed-only re-enqueue is the rule, and the job throws only on its own database failure, before any send.
3. **Tenant-scoped endpoint uniqueness** (`(tenant_id, endpoint)`), not global. An endpoint is bound to one origin, so one tenant, and a tenant-first unique index follows SCHEMA-CONVENTIONS while never letting a tenant lane touch another tenant's row.
4. **The badge is computed per recipient** through the kernel counters resolver, in a lane opened as that recipient (role read from the membership). This is one short transaction per recipient, acceptable at pilot scale in a background job.
5. **The push-service host allow-list** is a defence against the worker POSTing to an internal URL (SSRF). It is kept as a named constant, `PUSH_SERVICE_HOST_SUFFIXES`, with the real-device plan confirming it; widening it is a one-line change.
</planning_decisions>
