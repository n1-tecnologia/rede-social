<objective>
The support conversation, server side. A member can write to their organisation's team, any staff member can answer, every message is ordered and signalled in real time, and the badges know who is waiting on whom.

**As a** member of a tenant, **I want to** send a message to my organisation's team and get their answer in the same thread, **so that** I can get help without leaving the app. This story comes from ROADMAP Phase 7 SC 3 and CHAT-01..05.

It reuses 07-01's topic authorisation, 07-03's provider and 07-06's push channel, and adds only what chat owns: the reshaped tables, a gapless per-conversation sequence, trigger-published signals, and the shared staff read state D-225 asks for.

<planning_decisions>
1. **Lazy creation on first message (D-220, decided).** A creating GET would be a side-effecting GET (the 06-06 prefetch rule), and it would fill the staff inbox with empty threads.
2. **Participant/staff-aware RLS instead of tenant-wide.** Support threads are the first data private between members of the same tenant. An API bug that dropped a participant predicate would leak one member's thread to another, and the policy closes that at layer 3. Policies:
   - `chat_conversations_access` (all commands): `tenant_id = app.tenant_id() and ((kind = 'support' and app.tenant_role() in ('admin_tenant','support_tenant')) or created_by_user_id = app.user_id() or exists (select 1 from chat_participants p where p.conversation_id = chat_conversations.id and p.tenant_id = app.tenant_id() and p.user_id = app.user_id()))`.
   - `chat_participants_access`: `tenant_id = app.tenant_id() and (user_id = app.user_id() or app.tenant_role() in ('admin_tenant','support_tenant'))`.
   - `chat_messages_access`: `tenant_id = app.tenant_id() and exists (select 1 from chat_conversations c where c.id = chat_messages.conversation_id)`, which relies on the conversation policy. The insert `withCheck` also requires `author_user_id = app.user_id()`.
   No recursion: participants never reference conversations. The worker lane's `support_tenant` role (07-01 planning decision 6) lets the chat source read support threads.
3. **Staff read state is a conversation column (`staff_last_read_seq`)**, not staff participant rows (D-225): new staff see every thread, and one read clears "awaiting" for all.
4. **Counters get the caller's permissions.** The manifest's `counters(tx, ctx, permissions)` gains a third argument that `countersFor` fills from `permissionsFor`, so the chat module decides dot or count by `chat.support` instead of re-listing roles in TypeScript.
5. **Author side is stored (`author_side`)**, set by the API from the caller's permission, so bubbles and previews need no role join, and V2 direct messages are `member` on both sides.
6. **`last_read_at` is kept** beside the new `last_read_seq` and stamped on read. This avoids a drizzle-kit rename prompt (07-01 planning decision 8), and the instant is useful context.
</planning_decisions>
