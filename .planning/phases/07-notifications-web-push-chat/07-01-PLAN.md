<planning_decisions>
1. **Realtime RLS shape (RESEARCH "Research needed", decided): a SECURITY DEFINER topic function, not a JWT claim.** No custom access token hook exists, and `memberships` is RLS-scoped by a claim only `withTenantTx` injects. A `realtime.messages` policy can therefore use neither a claim nor a plain join (RESEARCH Pattern 2). The definer reads `tenant_modules` directly because no `app.module_enabled` helper exists. The staff role list `('admin_tenant','support_tenant')` is a literal here. 07-08 pins it against the TypeScript `permissionsFor` with a drift test (RESEARCH Pitfall 4).
2. **`realtime.send` from definer code, never a trigger that ships rows (decided).** Broadcast-from-rows ships the record, which breaks ids-only. The REST broadcast endpoint is not transactional. Both are opted out in `COVERAGE.md`.
3. **Topics (decided, the one-way-ish contract).** `tenant:<t>:all`, `tenant:<t>:user:<u>`, `tenant:<t>:support-inbox`, `tenant:<t>:conv:<c>`. The builders live in ONE file, `packages/contracts/src/realtime.ts`, exported through a new `@rede-social/contracts/realtime` subpath. It must be a subpath because the contracts index re-exports server-only `legal`, and the browser provider (07-03) imports these builders. The regex in the SQL function is the spec, and the two are pinned by a unit test that feeds every builder's output through the same regex literal.
4. **Fan-out mechanics (decided): eager rows through a definer, one statement per intent.** A broadcast kind at pilot scale is one `insert … select from memberships … on conflict do nothing returning user_id`. The definer (not a tenant-lane INSERT) exists because the owner-scoped SELECT policy would make `returning` fail for a system lane. Chunking past ~5k members is not built (RESEARCH Pattern 6).
5. **Quota (decided):** broadcast kinds publish ONE signal on `tenant:<t>:all`, not one per member. That is 1 message plus one per online receiver, against the Free plan's 100 msg/s (RESEARCH Pattern 4).
6. **Worker lane.** `notificationsSystemCtx(tenantId)` = `{ userId: '00000000-0000-0000-0000-000000000000', tenantId, role: 'support_tenant', requestId: 'job:notifications', events: [] }`. The zero user is never a real user. `support_tenant` (not `member`, the unfurl precedent) is chosen so that 07-08's participant-aware chat policies admit the chat source, while `event_secrets` (an `admin_tenant`-only policy) stays closed to the worker. RLS still pins the tenant.
7. **Dedupe from natural keys (RESEARCH Pattern 6).** Bus records carry no event id, and handlers get only the payload, so the stub's `(event_id, user_id)` index is replaced by `(tenant_id, user_id, dedupe_key)`. The sink stamps `sinkAt` (ISO, once per bus delivery) into the job payload, which a retried job reuses unchanged. 07-05 uses it to tell two reactivations of one event apart.
8. **Column reuse to avoid drizzle-kit rename prompts.** The stub's `payload jsonb` is KEPT and holds the facts (CONTEXT's own wording: "rendered from `kind` + payload"), and `read_at` is kept. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → web BFF → `/v1/notifications/*` | Query strings, path ids and the POST calls are untrusted; the session rides in an HttpOnly cookie. |
| browser → Supabase Realtime (private channel join) | The topic string is attacker-chosen; Realtime evaluates the join with the user's own JWT. |
| API service / worker → Postgres (tenant lane) | `set local role authenticated` with `{ tenant_id, tenant_role }` claims; the worker uses a system context. |
| domain-event bus → pg-boss job payload | The job payload is written by the API and replayed by the worker. |
