<planning_decisions>
1. **Keep and mark on retraction, not delete.** The UI-SPEC's removed-target variant (UI-D-251, UI-D-254, rows E03 partial/error) is part of the approved contract. Marking keeps it coherent, while replacing `payload` wholesale drops every fact (the privacy reason RESEARCH gave for deleting). No new column: `removed` is a payload key, so the table needs no boolean (SCHEMA-CONVENTIONS).
2. **Subject and object vocabulary.** Comment kinds use `subject: { type: 'post', id: postId }` and `object: { type: 'comment', id }`. Story kinds use `subject: { type: 'story', id }`, and story comments add `object: { type: 'story_comment', id }`. So `post.deleted` retracts every row about the post, and `comment.deleted` only those about that comment.
3. **The sweeper runs functions by name.** The kernel sweeper may not name a module table (MOD-02) and modules may not use the admin lane, so a manifest declares `sweepFunctions: ['notifications_prune']`. The kernel validates each name against `^[a-z_]+$` and executes it through `withAdminTx` with `sql.identifier`; a name comes from code, never from input.
4. **`app.notifications_prune` is SECURITY INVOKER and granted to `service_role` only.** The admin lane already bypasses RLS, so a definer adds nothing. A global `notifications_created_idx` on `created_at` is the documented SCHEMA-CONVENTIONS exception, because the prune is deliberately cross-tenant.
5. **Personal-kind push tags.** Replies use `feed-comment-replied` and story comments `stories-comment`, both with `renotify: true` and `urgency: 'normal'`; UI-D-266 names tags only for broadcast kinds, reminders and chat.
6. **The comment thread read lives in the feed module.** The web may not open another module's tables, and only the feed may read feed comments. It answers the root plus every reply up to the replies page cap, plus the target reply when it lies beyond that cap, all in one transaction.
</planning_decisions>
