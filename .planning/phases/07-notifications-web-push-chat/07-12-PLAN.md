<objective>

1. **The platform host comes from the harness, not from the developer's env file.** Today the web server Playwright launches reads `PLATFORM_HOST` from `apps/web/.env.local`, which still names a pre-rename host. Purpose: the gate stops depending on a developer-owned file and on dev-server warmth, so a green run means the product is green.

<planning_decisions>
1. **The harness owns `PLATFORM_HOST` for the servers it launches. The developer's file is not changed.** The verifier's suggested remedy offered two routes: the developer edits one line, or the gate stops depending on the file. This plan takes the second. The specs already hard-code every seed host (`fixtures.ts`), so the server under test must be told the same platform host the specs browse. Taking it from a personal env file made the gate measure the developer's machine instead of the product. `bash scripts/local-env.sh --write` is NOT recommended anywhere: it rewrites both env files from the template and drops hand-set values such as the Mux keys. 07-15's consent checkpoint tells the developer that the one-line change is still worth making for their own hand-run `next dev`, and that it is optional for the gate.
2. **Why this does not mask a real configuration defect:**
   - Production's `PLATFORM_HOST` is a Vercel and Cloud Run variable (DEPLOY.md), set by the release steps and never read from this file.
   - CI writes the same value from `local-env.sh`, and `apps/web/.env.example` documents it.
   - The platform-shell logic (`tenant-host.ts`) is still exercised end to end by the 34 platform cases and by its unit test.
   - An exported value still wins, so a deliberate override stays possible.
   - What the harness no longer catches is a stale value in the developer's own `apps/web/.env.local`, which affects only their hand-run `next dev`. The config warns (without echoing the value) whenever it replaces one.
3. **One source for the e2e hosts** (`e2e/hosts.ts`), read at call time, so the config and the specs cannot drift and the config never imports `fixtures.ts`.
4. **feed-comments: match by the `next-action` header plus the target id in the arguments.** Rejected: keeping the video card out of the viewport (fragile against feed order), and matching by action id (the ids are build-generated and unknown to a spec).
5. **No schema change: schema push not required.** No package is installed. No external-API capability is added, so `COVERAGE.md` stands.
6. **Out of scope by name** (orchestrator instruction): the real-device rows, the open-socket block residual, the C-WR-02 policy decision and the prohibition sign-off. No task here touches them.
</planning_decisions>
