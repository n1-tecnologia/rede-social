# Phase 07 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design authority.** `reference/frontend-design/` is the visual source of truth for everything it covers (D-66, UI-01). Values marked **[proto]** come from `app/(app)/notifications/page.tsx`, `components/notifications/NotificationItem.tsx`, `components/notifications/NotificationList.tsx` ("Novas" / "Anteriores", the unread tint, the avatar with a type glyph, the 44px target thumbnail) and `app/(app)/suporte/[ticketId]/page.tsx` (the bubble pair, the `ShieldCheck` staff label, the reply composer). The ticket protocol, category, priority, status pill, "Marcar como resolvido", FAQ, attachments, lightbox and the `/suporte` hub are **not ported** (CONTEXT carried decisions, D-220, D-221). Surfaces the prototype lacks are marked **[designed]** and go through D-33 (this contract, then a `/gsd-sketch 7` mockup review) before they are coded. The design language, spacing scale, type scale and colour model are **inherited unchanged** from the approved `02`/`03`/`04`/`05`/`05.1`/`05.2`/`05.3`/`06-UI-SPEC.md`. This document restates them for the checker and records only the Phase 7 deltas.

**Upstream decisions.** `07-CONTEXT.md` decisions are cited as **D-220..D-240** and the carried D-40, and they are not re-litigated. `07-RESEARCH.md` "UI-SPEC Constraints" are honoured row by row (switch states, the iOS gate, Badging support, foreground suppression, Novas/Anteriores semantics, chat attribution, fallback screens, no realtime-dependent spinners). Earlier visual decisions keep their numbers (UI-D-08, UI-D-14, UI-D-26, UI-D-38, UI-D-42, UI-D-47, UI-D-81, UI-D-203). The UI questions CONTEXT left to Claude's Discretion are decided below as **UI-D-250..UI-D-268**. The block starts at 250 so it cannot collide with Phase 6's UI-D-200..217 or with CONTEXT's D-220..D-240. No question was put to the user, because CONTEXT marks every open UI item "decide, record, do not re-ask".

**Research assumptions closed here.** A11: only `comment.liked`, replies on the member's comment and `story.commented` (to the story author) produce personal rows. Post and story likes do not notify. A12: a reel notification opens `/post/{postId}`, because `/reels` takes no deep-link parameter today. Open question 4: `support_tenant` and `admin_tenant` open the member's existing profile from the staff thread header (PROF-02), with no change.

**Design review (D-33).** These **[designed]** surfaces are drawn in the mockup package before they are coded: (1) the staff inbox list (mobile), (2) the desktop split view, (3) the soft-ask card, (4) the Configurações push row in all six states, (5) the `InstallHint` push variant, (6) the member thread header and empty greeting, (7) the notification row's actor-less and "removed" variants, (8) the comment highlight on the post page, (9) the dot badge on the chat slot. Two **[proto]** deltas must also be shown, because they change what the design team drew: (a) the staff sender label moves **above** the bubble and turns neutral (UI-D-259), and (b) the composer loses the attachment control and grows to five lines (UI-D-260).

## Interaction & Accessibility

- **Links for routes, buttons for in-place actions.** Notification rows, inbox rows, the staff header profile link, back controls and the TopBar slots are `<a>`. Mark-all, "Ativar notificações", dismiss, send, "Carregar mensagens anteriores", the pill, the switch and removed-target rows are `<button>`.
- **Prefetch-safe:** no GET render records anything. Seen, read and the thread read marks are client POSTs after mount, gated on `visibilityState === 'visible'` (the 06-06 rule).
- **Gesture rule (iOS):** `Notification.requestPermission()` / `pushManager.subscribe()` is the first awaited call in the click handler, and the VAPID key is already in memory (RESEARCH Pitfall 6). No prompt on load, after a chat send, or from any effect (D-233).
- **No role comparison in the web tier:** the inbox, the member thread and the staff thread choose by `bootstrap.permissions` (`chat.support`). The API re-enforces every gate.
- **Accessible names = visible catalog strings.** Slot links carry their state (UI-D-253). Unread rows carry "Não lida.". Inbox rows append ", aguardando resposta". Staff sender labels append ", da equipe" for screen readers. The composer field is labelled "Mensagem".
- **Live regions:** the message list is `role="log"` with `aria-live="polite"`, so arriving messages are announced once. Inline errors are `role="alert"`; toasts are `role="status"`. The notification list is **not** a live region: new rows would re-announce the whole list, and the slot's name already carries the count.
- **Focus:** after a send, focus stays in the composer. After "Carregar mensagens anteriores", focus stays on the button (or moves to the first loaded message if the button disappears). The soft-ask dismiss moves focus to the "Novas" heading, or to the first row.
- **Keyboard:** Enter sends on fine pointers and Shift+Enter adds a new line (UI-D-260). Escape closes `InstallHint` (shipped).
- **Clock and timezone:** no `Date.now()` in render. Every time string comes from the server (UI-D-14), and chat day labels compare server-provided day keys (UI-D-259). A Playwright case with a device timezone different from the tenant's asserts that bubble times and inbox times show the tenant's wall clock.
- **Motion:** only opacity fades (the soft-ask card leaving, 150 ms) and the comment-highlight fade (600 ms). Under `prefers-reduced-motion: reduce` both are instant, and the highlight stays until the first interaction. Badges never animate.
- **Text safety:** message bodies and excerpts render as React text, and links come only from the one http(s) linkifier (T-04-43). There is no raw-HTML path anywhere in the notifications or chat UI.
