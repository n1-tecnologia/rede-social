# Phase 08.5 Plan 08: The Member's Player and the Lesson Lock Page Summary

**Members now watch a lesson from where they stopped and complete it by watching 90% (decided by the server from a 15-second throttled write) or by tapping "Marcar como concluída". They open its materials through ten-minute signed URLs and move on with "Próxima aula", which turns brand once the lesson is complete. A pagehide beacon keeps their last position through a same-origin route. A locked lesson URL lands on one of two notices, built from the course outline only: "Aula exclusiva" with the buy path, or "Aula ainda bloqueada" with "Continuar o curso" to the lesson that unblocks the path. The admin previews all of it at `?ver=aluno` and nothing is written.**

- **Role split** (`[lessonId]/page.tsx`).
  - A `courses.manage` holder without `?ver=aluno` keeps the shipped lesson form, unchanged.
  - Everyone else makes one `getLearnLesson` read:
    - `ok` gives the player;
    - `locked` gives the lock page;
    - `not_found`, or a lesson of another course, gives "Aula indisponível";
    - a failure gives the course error card with a retry.
- **Player** (`MemberLessonPage`):
  - the header ("Voltar para o curso", course title) and the banner in preview;
  - `LessonPlayer`, only when the lesson has a video;
  - the pills, the title (24/700, wrapping anywhere) and the instructor;
  - the completion zone, absent in preview;
  - "Sobre esta aula", the materials, "Neste módulo" (current row with `aria-current="page"`), and previous / next.
- **VideoPlayer** gains `startTime` and `onProgress(position, duration, reason)`. A tick reports only while the element is playing. Feed and story callers pass neither prop and render as before (`FeedVideo.test.tsx` is green).
- **Cadence** (`lib/progress-reporter.ts`).
  - At most one tick per 15 s window. Pause and end send at once. Positions are integers ≥ 0.
  - The reporter keeps the last position seen, which the pagehide beacon sends.
- **Beacon** (`POST /api/courses/progress`). A clone of `/api/stories/views` with the same gate order.
  - Only `{ positionSeconds }` is forwarded, for a uuid `lessonId`.
  - Locks keep 403 / 409 and a removal is 404.
  - The log is by shape only. The route is in the inventory.
- **Session** (`LessonSession`, keyed by lesson id):
  - Completion flips once: the done block, the "Aula concluída." toast, and `router.refresh()`.
  - A lock or removal pauses playback, toasts the UI-D-433 copy, and refreshes or navigates. Writes stop after that.
- **Lock page** (`LessonLocked`, Task 2, gated by sketch 010):
  - The media block has no image, the 56px lock disc and the "Exclusiva" / "Bloqueada" pill. The identity comes from the outline.
  - Purchase uses the course's buy variants with the lesson words, plus the free-lesson door.
  - Sequence uses the store's `LockedSection` geometry: "Aula ainda bloqueada", the lock sentence, and "Continuar o curso" to `nextLessonId`, or the outline "Voltar para o curso".
  - `getLearnLesson` is never called on this page (grep count 0).

## Decisions Made

Planning decisions 1-4 were implemented as written (see `key-decisions`). Five choices were made during execution:

- **Ticks only while playing.** `VideoPlayer` drops a `timeupdate` from a paused element. Otherwise the load and the `startTime` seek could write position 0 over the member's stored place, which would defeat D-430's resume.
- **Labels through the plan-07 formatter.** The nav's "Conclua esta aula" / "Conclua o módulo" / "Aula exclusiva" and the lock page's sentences map `lessonLockLabel`'s keys. The player still only labels the server's `lockReason`.
- **Reuse over new geometry.** The sequence notice is the store's `LockedSection`, which matches the UI-SPEC card exactly. The purchase notice is `CourseActionZone`'s locked variants.
- **Read failure.** A member lesson read failure uses the shipped course error copy, because the contract has no lesson error line.
- **The beacon cannot complete a lesson.** It forwards `positionSeconds` only.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Added `LessonSession.tsx` (not in `files_modified`)**
- **Found during:** Task 1
- **Issue:** The player, the completion zone, the materials and the nav are separate client islands of a server page. They must share the one-way completion (the button and a ≥ 90% tick both flip it, and the nav's brand follows it) and the UI-D-433 refusal reaction.
- **Fix:** A small client context provider, keyed by lesson id, with `completed`, `markCompleted`, `refuse` and `stopped`.
- **Committed in:** `8481d771`

**2. [Rule 1 - Bug] Ticks from a paused element are not reported**
- **Found during:** Task 1
- **Issue:** `timeupdate` also fires on load and on the `startTime` seek. A tick at 0 would overwrite the stored place (the server keeps the last write).
- **Fix:** `VideoPlayer` reports a `tick` only when `paused` is false.
- **Committed in:** `8481d771`

**3. [Rule 3 - Blocking] The e2e fixture sets `requires_previous` by SQL, not through the admin API**
- **Found during:** Task 3
- **Issue:** The plan said "set through the admin API of plan 03". The member harness writes its rows through a superuser connection and has no admin-API token helper.
- **Fix:** `createCourseTree` takes a lesson-level `requiresPrevious` and writes the same column the API writes. It is set only on lesson 2, so `normaliseFirstLesson` is not involved.
- **Committed in:** `1e58babc`

**4. [Rule 3 - Blocking] Material fixtures upload real bytes to Storage**
- **Found during:** Task 3
- **Issue:** `signReadFor` throws when Storage has no object at the key, so the existing `createMaterials` rows (with no bytes) could never open.
- **Fix:** `createLessonMaterials` uploads a small PDF to `<tenant>/media/<asset>/original` with the service key. `deletePlayerStorage` removes the objects in `afterAll`.
- **Committed in:** `1e58babc`

**5. [Sketch alignment] The lesson not-found follows sketch 010's `aula-indisponivel` frame**
- **Found during:** Task 2
- **Change:** It now has the header back control and the alert glyph. It was built in Task 1 and adjusted in the Task 2 commit.
- **Committed in:** `e7f61c3a`

### Not delivered as written (recorded, WINDOWS entry 86)

**6. A lock change is not recognised from the playback mint**
- **Plan truth:** UI-D-433 lists "the playback mint" among the answers that pause, toast and refresh.
- **Why it is not met:** The mint is the media route (`fetchPlaybackTokenAction`). It answers its own generic refusal for a hidden course asset, not `lesson_locked` / `lesson_sequence_locked`, so the player cannot tell a lock from another failure.
- **Current behaviour:** The mint shows the shipped player error. The next progress write, the button or a material tap catches the lock and refreshes onto the lock page.
- **Fix needs:** A lock code on the media refusal, which is out of this plan's scope.
