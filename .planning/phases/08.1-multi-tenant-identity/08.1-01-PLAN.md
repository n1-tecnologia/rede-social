<objective>
The Phase 08.1 tracer. It proves the new identity model end to end on the path where it matters most: a person who belongs to one community signs in on another community's address and joins it. <planning_decisions>
1. **Join mechanics (CONTEXT discretion, decided).** The password is verified in the web tier by GoTrue (`signInWithPassword`, CLAUDE.md exception 1); the membership write is `POST /v1/join`, authenticated by that session's Bearer, running in the admin lane in `packages/core/server/tenancy/join.ts` behind explicit guards (the `memberships` policy comment). The login path of this plan needs no password step at all, because `/entrar` already produced B's session. The API never sees a password outside sign-up.
2. **Identity lane.** A new middleware, not a flag on `requireAuth`, so the hot path of every request stays strict and small (RESEARCH Alternatives) and no tenant-lane route can ever be mounted behind a membership-less guard by accident.
3. **`GET /v1/join/state` is tenant-host only.** `/participar` is reached only through `TENANT_HOST_MISMATCH`, which only a tenant host produces. The sign-up path on generic hosts (08.1-02) posts the join directly with `body.slug`.
4. **Refusal codes.** No new error code for the join: blocked reuses `MEMBERSHIP_BLOCKED`, a pending invite reuses `INVITE_STATE_INVALID` with the new reason `invite_pending`, and soft-deleted or platform-admin identities get `FORBIDDEN` with no details. `TENANT_CHOICE_REQUIRED` is the only new code (and `x-tenant-choice` the only new header), both needed by `requireAuth` now.
5. **Generic-host rule lives in one pure function** (`pickGenericMembership`), unit-tested without a database, so `requireAuth` and the 08.1-03 picker agree by construction.
6. **Expand only (D-318).** `app.membership_for_user` and `membershipForUser` stay: the old Cloud Run revision calls the SQL function during `supabase db push`, and `resolveMailTenant` calls the wrapper until 08.1-05. Both go in 08.1-05 (wrapper) and 08.1-08 (function).
7. **Throwaway identities only.** No test or e2e joins a SEED user to a second tenant, because count-based suites (members, stories) would drift (project memory). Every case creates `mti-<run>-…@rede-demo.local` identities and deletes them in `beforeAll` and `afterAll`.
</planning_decisions>
