<objective>
Per-community names, the expand half of D-310. `member_profiles` is already one row per membership and every module already renders authors through it; what still reads or depends on the global `users.name` are the bootstrap's `user.name`, the platform panel's admins list, the sign-up (through the trigger) and the seed. This plan moves each of them to the membership's own profile while the column and the triggers stay, so the release can ship before 08.1-08 drops the column.

**As a** person who belongs to two communities, **I want to** have a separate name in each community, **so that** editing my profile in one never changes what the other community sees. Derived from ROADMAP 08.1 success criterion 1 ("blocking, role and profile apply per membership") and CONTEXT D-310/D-311.

Output: the reader and writer switches, the explicit seed names, the D-313 assertions and the per-host profile tests.

**Commits.** No `Co-Authored-By` trailer. Stage only the files this plan lists.
</objective>

<planning_decisions>
1. **Triggers are re-pointed in the contract, not here (D-318 refinement).** If `app.ensure_member_profile` stopped copying `users.name` in this release, a sign-up handled by the OLD API revision during `supabase db push` would get an empty profile name forever, because the old code relies on the trigger. Keeping both triggers until 08.1-08 costs nothing: every NEW code path that creates a membership sets the name explicitly (sign-up here, join in 08.1-01, invite in 08.1-06), so D-311 holds in this release.
2. **`user.name` stays in the bootstrap contract**, filled from the profile, so no web-before-API ordering is introduced (RESEARCH Pattern 6.3).
3. **The admins list joins the profile by membership id** inside the tenant filter, so a person who is admin of two tenants shows each tenant's own name.
</planning_decisions>
