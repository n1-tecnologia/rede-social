# Phase 08.1 Plan 06: Existing-Identity Invites Summary

**A super_admin can now invite someone who already belongs to another community as a new community's first admin. That person gets an `invited` membership and a tokenless mail in the new community's brand saying "use a senha que você já tem". They sign in on that community's `/entrar` and accept its rules without a password step. Only platform accounts are still refused.**

## Accomplishments

- **The password fact.** `app.identity_has_password(uuid)` is SECURITY DEFINER with `search_path = ''`. It returns a boolean only, has no row cap, and only `api_user` and `service_role` may execute it. The TypeScript wrapper is `identityHasPassword`.
- **Classification.** `identityKind` sorts an invite address into one of four kinds. It replaced `identityConflict` in `sendPendingInvites`, `resendInvite` and `createTenant`.
- **The tokenless mail.** For an identity with a password, one shared helper does two things in order:
  1. It commits, in one transaction, the `admin_tenant`/`invited` membership (with its profile name set to '', D-311) and `tenant_invites.user_id`.
  2. It sends `renderInviteExisting` to `<origin>/entrar` through `mailTransport`, with the key `invite-existing:<id>:<sentAt>`.

  GoTrue is never called on this path.
- **Resend.** `resendInvite` branches on `identityKind` before any GoTrue call. An identity with a password therefore never reaches the `generateLink` → `email_exists` → recovery-link branch (Pitfall 6).
- **Retired code.** These are gone:
  - `identityConflict`, `isOneTenantPerUserViolation` and `NIL_TENANT_ID`;
  - both race-catch blocks;
  - the `user_in_other_tenant` reason, its OpenAPI documentation, the panel toast mapping (`AdminsPanel.tsx`) and the `admins.resendUserInOtherTenant` catalog key.
- **API.** `GET /v1/me/invite` answers `{ passwordRequired }`, and an `invited` membership can reach it.
- **Web.** The accept page hides the password field when the identity already has one and shows `subtitleExisting` instead. The accept action asks the API again on the server before it chooses its schema, so it calls `updateUser` only when a password is required.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `encrypted_password <> ''` does not mean "has a password"**
- **Found during:** Task 3, in the e2e verify. Invite tests 1 and 2 lost the `#password` field after `/auth/confirm`.
- **Issue:** GoTrue writes a random 60-character `$2a$` hash when an invite link is verified. Probed locally:
  - after `inviteUserByEmail`: `''`;
  - after `verifyOtp`: a hash.

  As a result, every confirmed-but-unaccepted admin read as `existing_with_password`. That had two effects:
  - the new-admin accept screen dropped the password step;
  - WR-04's recovery-link resend turned into the tokenless mail, sent to someone with no known password.

  GoTrue's admin `createUser` without a password also stores a random hash. RESEARCH A3 assumed the hash was reliable.
- **Fix:** the function now counts a hash only when one of these holds:
  - `invited_at is null`, or
  - the identity holds a membership whose status is not `invited`, meaning it accepted or joined somewhere.

  The migration was never pushed, so it was corrected in place.
- **Consequence for the plan's must-have:** the truth "reads only `auth.users.encrypted_password`" no longer holds literally. The function also reads `auth.users.invited_at` and `public.memberships`. It still returns a boolean only, for one id.
- **Verification:**
  - pgTAP gained 2 cases (64 → 66);
  - the R4 fixture now reproduces the real GoTrue state (`invited_at` plus a random hash);
  - invite tests 1 and 2 pass on both projects.
- **Committed in:** `d146aab`.

**2. [Rule 3 - Blocking] The isolation-inventory gate needed the new route**
- **Found during:** Task 1.
- **Issue:** the TENANT-05 gate rejects a mounted route that has no isolation case.
- **Fix:** `GET /v1/me/invite` is classified in `isolation-inventory.ts` under `inventory sweep: me and media`. The sweep now asserts 200 `{ passwordRequired: false }` on the member's own host and 403 on the lab host.
