<planning_decisions>
1. **Existing-identity invite mail (CONTEXT discretion, decided): a direct app mailer, not the Send Email Hook.** The hook only fires for GoTrue-originated mail, and every GoTrue action available for a confirmed identity mints a login token, which D-314 forbids ("no magic link"). The app mail reuses `mailTransport`, the layout and the brand resolution of the resend path.
2. **The split is "has a password", not "is confirmed".** An identity our own invite created and `/auth/confirm` confirmed, but that never set a password, still needs a link to set one (WR-04). An identity with a password needs none. `auth.users.encrypted_password <> ''` is read through a SECURITY DEFINER function (RESEARCH A3), proved by pgTAP.
3. **Write before send.** The `invited` membership and `tenant_invites.user_id` commit before the mail goes out, so the person can sign in the moment the mail arrives; a transport failure reverts only the claim.
4. **`GET /v1/me/invite` rather than a column on `tenant_invites`**, because a delivery column goes stale if the person sets a password elsewhere before accepting (RESEARCH A3 alternative rejected).
</planning_decisions>
