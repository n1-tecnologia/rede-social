## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Carried forward (locked before this discussion — do not re-open)
- **D-23 (Phase 1):** the membership is the authority. The host can only **deny** (403 `TENANT_HOST_MISMATCH`), never grant. Under 08.1 the host **selects among the user's own memberships** and still grants nothing: no membership on that host means no access.
- **D-04 (Phase 1):** the duplicate e-mail answer never names another tenant.
- **D-06 (Phase 1):** the `tenant_slug` cookie is a hint, never authority. D-308 reuses it on generic hosts, always validated server-side against the user's memberships.
- **D-21 (Phase 1):** the platform domain serves `super_admin` only. The community picker (D-308) is for generic hosts (Vercel Preview, localhost), not for the platform host.
- **D-29 (Phase 2):** an invite pre-creates an `invited` membership. `/aceitar-convite` flips it to `active` and records per-tenant consents.
- **D-37 (Phase 2):** the mail tenant comes from the membership, else from the `redirect_to` host. D-315 refines this to "the membership that matches the flow's host".
- **Phase 7:** Realtime topics are authorised by an active membership in the topic's tenant. Push subscriptions are unique per `(tenant_id, endpoint)`. Both are already per-tenant.

#### "Já tem conta" — sign-up on a second tenant
- **D-301: One-step join on the sign-up screen.**
  1. `/cadastro` on tenant B receives an e-mail that already has an identity.
  2. The form turns into "Você já tem uma conta. Digite sua senha para participar de [B]".
  3. A correct password plus B's two consents creates the B membership and signs the person in on B.
  4. A wrong password creates nothing.
  - **Reversibility:** reversible.
- **D-302: The sign-up may reveal that the e-mail has an account on the platform, never in which community.** This keeps the D-04 posture. The response, logs visible to tenants and UI copy never carry the other tenant's id, name or slug.
- **D-303: Forgotten password during a join goes through normal recovery started on B's host.**
  - The recovery e-mail carries B's branding (D-315).
  - After resetting, the person lands back on B's join flow and confirms with the consents.
  - Resetting the password does NOT by itself create a membership.
- **D-304: Blocks are per tenant.**
  - A member blocked in A can join B, and B never learns about the block in A.
  - A block in B keeps the person out of B. Their existing B membership is `blocked`, so re-joining B hits it and is refused. There is no second membership.
  - `blocked_at` must be evaluated on the host-selected membership only. Today's `limit 1` in `app.membership_for_user` would leak A's block into B.

#### Login on another tenant
- **D-305: A correct password on B's `/entrar` without a B membership leads to "Participar de [B]".** This replaces today's host-mismatch sign-out screen for that case.
  - The join screen follows D-306.
  - Confirming creates the membership. Declining signs the person out of B.
  - A session whose user has no membership on the host still gets `TENANT_HOST_MISMATCH` from the API for every tenant-lane route. The join screen is the only way in.
- **D-306: One join screen shared by every path.** Sign-up with an existing e-mail, login and invite acceptance all use it.
  - It shows B's branding, B's rules text and both consents (B's rules + the platform terms), the same as `/cadastro` minus the password fields.
  - It reuses the `/cadastro` consent component.
  - Consent rows are recorded per tenant, as today.
- **D-307: Membership selection by host is the new tenant-of-record rule.**
  - On a registered tenant host, the request's membership is the user's non-deleted membership **in that host's tenant**, and nothing else.
  - The "oldest by `joined_at`" rule is removed everywhere it is used:
    - `app.membership_for_user`
    - `requireAuth`
    - `resolveMailTenant`
  - **Reversibility:** costly. `supabase/tests/040-schema-conventions.sql` pins the `order by joined_at` / "only function picking one row" shape and the unique index, so those assertions are rewritten.
- **D-308: Generic hosts (Preview, localhost) with more than one active membership show a "Escolha a comunidade" picker after login.**
  - The choice is stored in the `tenant_slug` cookie and validated server-side against the user's memberships.
  - With a single membership, the person enters directly.
  - Production tenants always have their own domain, so the picker is a dev/Preview affordance.
- **D-309: Each tenant app is isolated.**
  - A tenant app never lists, links or names the person's other communities.
  - Switching means opening the other domain or installed PWA.
  - Bootstrap returns only the host's membership, never a list.

#### Profile and account per tenant
- **D-310: Name, photo and bio are per community.**
  - The display name moves from the global `public.users.name` into the per-membership profile. `member_profiles` is already keyed by membership.
  - Editing the profile in A never changes B.
  - Existing names are backfilled into each membership's profile.
  - **Reversibility:** one-way. It is a schema migration that moves `name` off `public.users` and backfills it. Directory search, bootstrap `user.name` and every author/participant rendering switch to the membership profile.
- **D-311: A new membership starts with an empty profile.** Only the name typed at sign-up or join is filled. The D-02 first-access nudge card appears as for any new member. Nothing is copied from A.
- **D-312: Neutral notice about the shared password.** `/redefinir-senha` (the only password screen today) shows "Sua senha é a mesma em todas as comunidades desta plataforma." The notice never names other communities.
- **D-313: Model rule for leaving vs deleting (UI deferred to V2-PROF-02).**
  - Leaving a community soft-deletes only that membership and its profile.
  - The identity is deleted only when no membership remains.
  - 08.1 builds no UI for this. The planner must make sure nothing in the new model prevents it: no cascade from one membership to the identity or to other memberships.

#### Invites to existing identities
- **D-314: Inviting an e-mail that already has an identity sends a B-branded invite, with no password setup.**
  - GoTrue refuses `inviteUserByEmail` for an existing e-mail, so this is a different mail path.
  - The invite text says "use a senha que você já tem" and never names the other community.
  - The link opens `/entrar` on B's domain. After login, `/aceitar-convite` shows only B's rules and consents (the D-306 component), with no password step.
  - The `user_in_other_tenant` refusal disappears. The invite pre-creates the `invited` membership as D-29 does.
  - No magic link: the person always signs in with their password.
- **D-315: Auth and invite e-mails are branded by the tenant the flow started on.**
  - This covers recovery, invite and confirmation mails.
  - The tenant is the one that owns the redirect host, provided the identity has, or is being invited to, a membership there.
  - This replaces "the membership" in `resolveMailTenant`.
  - `decideLinkHostRefusal` refuses only when the identity has no membership, and no open invite, on the redirect host's tenant.
- **D-316: A `super_admin` identity is still refused (`email_in_use`).** Platform accounts never become tenant members (D-23). A person who wants both uses another e-mail.

### Claude's Discretion
- **Realtime host binding:** today any JWT of a user can join the topics of every tenant where it has an active membership. That holds regardless of host, because topic auth checks the membership, not the host.
  - This is not a leak: the user is a legitimate member of each.
  - The planner decides whether to also bind topic subscriptions to the host's tenant.
  - The isolation tests in success criterion 5 must at least prove that a topic of a tenant without membership stays closed.
- **Join mechanics:** the planner decides whether the password check for D-301 happens in the web server action (sign in, then call a join endpoint in the tenant lane) or in an API endpoint. The rule: the membership write stays in the admin lane behind explicit guards, as the `memberships` policy comment requires.
- **The existing-identity invite mail:** the planner decides whether it goes through the Send Email hook path or a direct app mailer, as long as D-314 and D-315 hold.
- **Go-live gate placement:** the Phase 8 roadmap says its gate closes the MVP. After 08.1 the planner must re-run the full two-tenant isolation suite plus the shared-identity fixture as 08.1's exit gate. The roadmap wording can be reconciled when Phase 8 is discussed.

### Deferred Ideas (OUT OF SCOPE)
- **Self-service "sair da comunidade" and account deletion / data export** (V2-PROF-02, LGPD Art. 18): the rule is captured in D-313, and the UI is deferred.
- **An in-app "trocar de comunidade" switcher:** considered and rejected for V1 (D-309). Revisit only if tenants ask for a federated experience.
- **Magic-link sign-in for invites:** rejected in favour of password sign-in (D-314).

## Project Constraints (from CLAUDE.md)

- All business logic goes through the Hono API on Cloud Run. The web talks to Supabase directly only for (1) Supabase Auth login/refresh/recovery via `@supabase/ssr` in the Next.js server, and (2) read-only Realtime Broadcast. **The join password check therefore belongs in the web server action's `signInWithPassword` (exception 1), and the membership write belongs in the API.**
- Multi-tenant from day one, RLS/defense in depth, "zero leakage between tenants". Three layers: the membership lookup in `requireAuth`, the explicit tenant predicate (`membershipOfRecord`), and RLS.
- Schema must anticipate V2 without migrations that rewrite core tables. `member_profiles` already hangs off the membership, so D-310 is a reader switch plus dropping a column, not a table rewrite.
- `service_role` / `postgres` must never run tenant queries. Membership and consent writes use `withAdminTx`, which Biome confines to `packages/core/server/{tenancy,platform,media}/**` and `scripts/**` [VERIFIED: biome.json:34-58].
- Drizzle is the schema source. `drizzle-kit generate` writes to `supabase/migrations`, the Supabase CLI applies, and hand-written SQL goes in `--custom` migrations. Never run `drizzle-kit migrate`.
- pgTAP via `supabase test db`: every policy gets a cross-tenant negative test.
- pt-BR UI. Every string lives in `apps/web/messages/pt-BR/*.json`. `scripts/check-ui-literals.sh` fails on JSX literals with diacritics.
- `proxy.ts`, not `middleware.ts`. Async `cookies()`/`headers()`. Never call `redirect()` inside try/catch.
- Tokens stay in HttpOnly cookies (BFF). Never in `localStorage`.
- `supabase.auth.signOut()` defaults to **global** scope. This repo always passes `{ scope: 'local' }` [VERIFIED: apps/web/app/auth/blocked/route.ts:18, host-mismatch/route.ts:14, (app)/actions.ts:22].
- Git and commits: no `Co-Authored-By` trailer (project memory). Commit only the 08.1 phase directory.

## Summary

Most of the ground for multi-membership is already in place. `member_profiles` is one row per membership, created by a trigger, and every author, participant and directory rendering already reads `member_profiles.display_name` through a membership join. `app.realtime_topic_allowed` and every push-subscription function scope by the topic's or claim's tenant. The tenant lane gets `app.tenant_id()` from `withTenantTx` claims, not from a JWT hook (the custom access token hook is only a comment in `supabase/config.toml:330`), so RLS needs no change once `ctx.tenantId` is the host-selected membership's tenant.

The single-membership rule lives in a small number of places:
- the index `memberships_one_tenant_per_user_v1`;
- `app.membership_for_user` (`order by joined_at limit 1`) and its two callers, `requireAuth` and `resolveMailTenant`;
- the invite identity rule (`identityConflict`, `isOneTenantPerUserViolation`) and `createTenant`'s `adminEmail: in_use`;
- the sign-up 409 path;
- the `users.name` → trigger seed;
- tests that pin all of the above.

The work that needs care is the new paths, not the removal:
1. an **identity lane**: a verified Bearer with no membership check, used only by the join and picker endpoints;
2. the join transaction in the admin lane;
3. the generic-host choice header;
4. the mail-tenant rewrite;
5. the existing-identity invite mail;
6. an **expand/contract** migration order, because production is live and the deploy runs migrations before the API.

Three GoTrue facts were read at the exact tag the local stack runs (`gotrue:v2.197.0`):
- `inviteUserByEmail` refuses a **confirmed** existing e-mail with `email_exists` but re-sends to an **unconfirmed** one.
- `admin.createUser` refuses any existing e-mail with `email_exists`.
- A password update (`updateUser`) **logs out every other session of the identity** (`LogoutAllExceptMe`). Resetting the password on B therefore signs the person out of A at A's next token refresh (≤ 1 h). That is an unavoidable cross-tenant side effect of a shared password, and UAT and the D-312 notice should acknowledge it.

`signOut` defaults to global scope, which would break D-304 if Phase 8 used it for blocking.

**One contradiction in CONTEXT needs a user decision before planning locks it.** D-303 requires a B-branded recovery e-mail for a person who is joining B and has **no** B membership yet. D-315 as written ("provided the identity has, or is being invited to, a membership there" / "refuses only when the identity has no membership, and no open invite") refuses exactly that mail. The existing hook test `send-email-hook.test.ts` #9 asserts today's refusal for that scenario. Recommendation: for `recovery` only, brand by the verified redirect-host tenant even without a membership (Open Question 1).

**Primary recommendation:** Add three SECURITY DEFINER lookups: `app.membership_in_tenant(user, tenant)`, `app.memberships_of_user(user)` and `app.identity_by_email(email)`. Rewrite `requireAuth` so it resolves the host first and then selects the membership. Add an identity-lane `/v1/join` route group (state, join, picker list) whose writes run in `withAdminTx` in `packages/core/server/tenancy/join.ts`. Verify the password in the web server action with `signInWithPassword`, which creates B's session in the same call. Send existing-identity invites through the kernel `mailTransport` with a tokenless link, never through GoTrue. Ship D-310 as expand (stop reading `users.name`, re-point both triggers) then contract (drop the column) in a later deploy.

### Pattern 1: Host-first membership selection in `requireAuth` (D-307, SC 3)

**What:** resolve the host first, then fetch **only** the membership of the host's tenant. `order by joined_at limit 1` disappears.

**Today** [VERIFIED: packages/core/server/auth/require-auth.ts:51-105]: `membershipForUser(userId)` runs first (oldest membership), then suspended → blocked → host check → invited scope. The host can only compare. This leaks A's block and suspension into B's host: a member blocked or suspended in A gets `MEMBERSHIP_BLOCKED` / `TENANT_SUSPENDED { tenantName: A }` on B's host (test `auth-middleware.test.ts` "h. while blocked, another tenant's host still yields MEMBERSHIP_BLOCKED" pins this and must flip).

**New order:** verify → resolve host → select membership → (none: tenant host ⇒ `TENANT_HOST_MISMATCH`; generic ⇒ choice rules) → tenant suspended → blocked → invited scope. `TENANT_HOST_MISMATCH` on a tenant host stays detail-less. The existing platform-admin branch (today lines 58-69) collapses: on a tenant host everyone without a membership gets `TENANT_HOST_MISMATCH`, and the platform-admin query moves to `/v1/join/state`, off the hot path.

**Generic / unknown hosts** (localhost, `*.vercel.app` Preview, the platform host, a missing header):
1. read `memberships_of_user(user)` (non-deleted rows only);
2. if the `x-tenant-choice` header names a slug among them, use it;
3. else, if exactly one, use it;
4. else, if zero, `NO_MEMBERSHIP`;
5. else `403 TENANT_CHOICE_REQUIRED` (no details).

The header can only pick among the caller's own memberships, so a forged value grants nothing (D-06). The API ignores the header whenever the host resolves to a tenant.

**Why SQL functions, not a Drizzle query:** `requireAuth` runs before any lane exists, on the bare `api_user` connection, which may only EXECUTE definer functions [VERIFIED: supabase/migrations/20260912031029_app_membership_lookup_and_grants.sql:24-25 `revoke all on function app.membership_for_user(uuid) from public; grant execute on function app.membership_for_user(uuid) to api_user;`]. Keep that shape.

**Expand/contract for the function:** create `app.membership_in_tenant` and `app.memberships_of_user` in 08.1's first migration, but **keep `app.membership_for_user`** until the contract migration. The Cloud Run revision still serving during `supabase db push` calls it. Drop it together with `users.name`. `040` then asserts that zero `app` functions contain `limit 1`.

### Pattern 2: Identity lane + join transaction (join mechanics, discretion — recommended)

**Recommendation (with reasons):** the password check happens in the **web server action** with `supabase.auth.signInWithPassword` on B's origin. The membership write is `POST /v1/join`, authenticated by the Bearer that sign-in just produced, running `withAdminTx` in `packages/core/server/tenancy/join.ts`.
- The password is verified by GoTrue exactly once, by the same call that creates B's HttpOnly session cookie. This is the established `/entrar` pattern [VERIFIED: apps/web/app/(auth)/entrar/actions.ts:29-31].
- The API never sees the password. Sign-up is the only exception, because `createUser` needs it.
- The authority for "which tenant" matches sign-up's (D-22): on a tenant host the host decides, and on a generic host the form's slug decides. That parity is what keeps "host selects" from becoming "host grants": joining is the one explicit, consented, admin-lane write where the host names the tenant, exactly like `/cadastro`.
- Every other path (recovery session per D-303, an already signed-in visitor) reuses `POST /v1/join` with the existing session. One write implementation.

**`requireIdentity` (new middleware):** `verifyBearer` (reuse, [VERIFIED: require-auth.ts:16-30]) plus host resolution. It sets `c.var.identity = { userId, host }`. It never sets `ctx` and never opens `withTenantTx`, so no tenant-lane route can be mounted behind it by accident. Mount it only on `/v1/join/*`.

**`joinTenant` guards, in order, one admin transaction:**
1. The tenant comes from a verified tenant host (`resolveTenantHost`). On a generic host only, it comes from `body.slug` via `getTenantIdBySlug`, the sign-up precedent [VERIFIED: signup.ts:142-143]. An unknown tenant is 404 `TENANT_NOT_FOUND`. A suspended tenant is 403 `TENANT_SUSPENDED`. The platform host is refused (404).
2. Platform admin → 403 `FORBIDDEN` (D-316). Check `platform_admins` in the same tx.
3. Consent versions must equal `tenants.rules_version` and `PLATFORM_TERMS_VERSION`, else 400 `VALIDATION_FAILED { consents: 'stale' }` (same rule as sign-up and accept-invite [VERIFIED: signup.ts:145-150; accept-invite.ts:75-80]).
4. `select … from memberships where tenant_id = T and user_id = U for update`:
   - `active` and not blocked → 200 `{ outcome: 'already_member' }` and **write nothing**;
   - `blocked_at is not null or status = 'blocked'` → 403 `MEMBERSHIP_BLOCKED` (D-304: "re-joining B hits it and is refused");
   - `invited` → 409 `INVITE_STATE_INVALID { reason: 'invite_pending' }`, and the web routes to `/aceitar-convite`;
   - `deleted_at is not null` → refuse (Open Question 3; recommended 409 `MEMBERSHIP_REMOVED` or reuse `FORBIDDEN`). `memberships_tenant_user_uq` is not partial, so a second row is impossible anyway.
5. `insert into memberships (tenant_id, user_id, role, status) values (T, U, 'member', 'active') on conflict (tenant_id, user_id) do nothing returning id`. Zero rows means a concurrent join won: re-read and answer `already_member`. The `member_profiles_from_membership` trigger inserts the profile row.
6. `update member_profiles set display_name = :name where membership_id = :id`. D-311: only the name typed at sign-up or join. Nothing is copied from A.
7. Both `consent_records` rows (`tenant_rules`, `platform_terms`) with `ip`/`userAgent` from `X-Client-IP`/`User-Agent`, `onConflictDoNothing` [VERIFIED: accept-invite.ts:117-130 pattern].
8. Log `join.created { tenantId, userId }`. Never log another tenant's id (D-302).

**`GET /v1/join/state`** answers exactly one of `joinable | member | invited | blocked | removed | platform_admin | suspended` **for the host's tenant only**, plus B's public facts the screen needs (display name, rules text, both versions — or the page fetches `/v1/public/tenants/{slug}` as `/aceitar-convite` does [VERIFIED: aceitar-convite/page.tsx:58-65]). It never answers about other tenants (D-302/D-309).

### Pattern 3: Sign-up with an existing e-mail (D-301, D-302, SC 2)

The API's sign-up stays as it is: 409 `EMAIL_ALREADY_REGISTERED`, no details [VERIFIED: signup.ts:181-182]. Only the web changes:
1. `signup` action: on 409, set a short-lived **HttpOnly** cookie holding `{ email, name }` (never the password, never in the URL; the `CONTINUE_COOKIE` precedent in `proxy.ts:217-224`). Redirect to `/cadastro?estado=ja-tem-conta` (or `/cadastro/{slug}?…` on generic hosts).
2. The page renders the state:
   - title "Você já tem uma conta. Digite sua senha para participar de [B]";
   - the e-mail shown read-only;
   - `PasswordField` with `autoComplete="current-password"`;
   - `ConsentFields` (both unchecked, D-03);
   - an "Esqueci a senha" link to `/esqueci-senha`, which D-303 starts on B's host.
3. `joinFromSignup` action: re-read the cookie → `signInWithPassword({ email, password })`.
   - Wrong password: redirect back with `erro=senha`. Nothing written (D-301.4).
   - Right password: `POST /v1/join { name, consents }` with the **access token from `signInWithPassword`'s returned session** (see Pitfall 5), then map the outcome:
     - `joined`/`already_member` → `/inicio`;
     - `MEMBERSHIP_BLOCKED` → `/auth/blocked`;
     - invite pending → `/aceitar-convite`;
     - platform admin / removed → local sign-out plus a generic refusal line.

The "already a member of B" and "blocked in B" facts surface **only after** the password proves ownership, so the unauthenticated 409 keeps revealing nothing beyond "has an account on the platform" (D-302).

Do **not** auto-try the password typed into the original sign-up form. It was entered as a *new* password (`autoComplete` new-password). D-301's wording asks for the password explicitly, and an explicit step lets password managers fill it [ASSUMED — UX judgement].

### Pattern 8: Invites to existing identities (D-314, D-316)

Today, `identityConflict` [VERIFIED: packages/core/server/platform/invites.ts:77-91] answers `null | 'email_in_use' | 'user_in_other_tenant'`, and `createTenant` refuses any identity with 400 `{ adminEmail: 'in_use' }` [VERIFIED: tenants.ts:204-205].

Replace it with `identityKind(tx, email, tenantId)`:
- `new` → no identity. Unchanged GoTrue `inviteUserByEmail` path.
- `platform_admin` → refuse `email_in_use` (D-316; `createTenant` keeps `adminEmail: 'in_use'` **only** for this case).
- `existing_with_password` → **direct app mailer**:
  1. insert the `invited` membership (`onConflictDoNothing` on `(tenant_id, user_id)`) and `tenant_invites.user_id` in one admin tx;
  2. render the new template "use a senha que você já tem", naming only B;
  3. link = `${publicWebOrigin(primaryHost)}/entrar`, **no token**;
  4. `mailTransport.send(..., idempotencyKey: 'invite-existing:<inviteId>:<sentAt>')`.

  This is the same transport path `resendInvite` already uses [VERIFIED: invites.ts:580-609]. After login on B, `requireAuth` selects the `invited` B membership, `requireBootstrap` sends the person to `/aceitar-convite` [VERIFIED: bootstrap.ts:136-139], and the page hides the password step.
- `existing_without_password`: an identity created by a still-unaccepted invite of another tenant, unconfirmed and never set a password. The earlier tenant's link is superseded, and that tenant's resend later takes the WR-04 recovery branch. This is a rare edge; document it.

**Why the direct mailer (discretion item):** the Send Email hook only fires for GoTrue-originated sends. The only GoTrue actions available for a confirmed identity (`generateLink` recovery/magiclink) mint login tokens, which D-314 forbids. `inviteUserByEmail` refuses confirmed e-mails [CITED: github.com/supabase/auth v2.197.0 internal/api/invite.go — confirmed existing user → `NewUnprocessableEntityError(ErrorCodeEmailExists, DuplicateEmailMsg)`; unconfirmed → the invite is re-sent].

**`/aceitar-convite` without a password:** the page must know whether the identity already has a password. Recommended: a SECURITY DEFINER `app.identity_by_email(p_email)` / `app.identity_has_password(p_user)` that reads `auth.users.encrypted_password <> ''` (the migration role can read and write `auth.users`, since `tests.auth_user` inserts into it [VERIFIED: supabase/tests/000-helpers.sql:22-36]). Alternative: a `tenant_invites.delivery` column set at send time. It is simpler, but it goes stale if the person sets a password elsewhere before accepting [ASSUMED].

**`resendInvite` for an existing identity** must **skip** the `generateLink(invite)` → `email_exists` → **recovery link** branch [VERIFIED: invites.ts:512-555]. That branch would mail the existing identity a login-capable recovery link, a magic link in all but name, which D-314 forbids. Branch on `identityKind` first.

`isOneTenantPerUserViolation`, `refuseInvite(..., 'user_in_other_tenant')` and the `user_in_other_tenant` member of `INVITE_STATE_REASONS` [VERIFIED: packages/contracts/src/invites.ts:70-76 `'already_accepted', 'no_verified_primary', 'not_invited', 'email_in_use', 'user_in_other_tenant'`] go away. ### Anti-Patterns to Avoid
- **Selecting a membership by `user_id` alone anywhere.** Every lookup is `(tenant_id, user_id)` or a membership `id` (`membershipOfRecord` [VERIFIED: membership-scope.ts:20-29]).
- **`signOut()` without `{ scope: 'local' }`, or `auth.admin.signOut(jwt, 'global')`.** Global is the default and revokes every refresh token of the identity, in every tenant [CITED: supabase.com/docs/reference/javascript/auth-signout — "the default scope is 'global'"; github.com/supabase/auth v2.197.0 internal/api/logout.go].
- **Honouring `x-tenant-choice` on a tenant host.** The host wins. The choice only disambiguates on generic hosts.
- **A join endpoint in the tenant lane.** `memberships` is SELECT-only there by design [VERIFIED: memberships.ts:40-51].
- **Copying name, avatar or bio from another membership** (D-311), or pre-filling the join name field from A.
- **Listing other communities anywhere on a tenant host** (D-309). That includes the join screen ("você já participa de…") and the picker endpoint.
- **Putting the e-mail in the `/cadastro` redirect query string.** Use the HttpOnly draft cookie.

## Common Pitfalls

### Pitfall 1: Deploy order drops a column the live API still reads
**What goes wrong:** `supabase db push` runs before the new Cloud Run revision [VERIFIED: deploy-api.yml:88 "Production (migrations -> API -> worker)", :103-111]. Dropping `users.name` or `app.membership_for_user` in the same push breaks the running API (bootstrap 500, every `requireAuth` 500).
**How to avoid:** expand/contract (Patterns 1 and 6). The contract migration is its own plan and its own push, after production runs the expand revision.
**Warning signs:** a migration that both drops something and is in the same commit range as the code that stops using it.

### Pitfall 2: Block and suspension bleed across tenants
**What goes wrong:** keeping "membership first, host second" means A's `blocked_at` / suspension still refuses the identity on B (D-304 violated), and `TENANT_SUSPENDED { tenantName: A }` names A on B's host (D-302/D-309).
**How to avoid:** host first (Pattern 1). Test: blocked in A, 200 on B. Suspended A, 200 on B.

### Pitfall 3: Global sign-out in Phase 8's block
**What goes wrong:** `signOut()` default or `auth.admin.signOut(jwt)` with global scope revokes the identity's sessions in every tenant.
**How to avoid:** Touchpoints design. Add the reconcile grep.

### Pitfall 4: Password reset on one tenant logs the person out of the others
**What goes wrong (unavoidable):** GoTrue's `UpdatePassword` calls `LogoutAllExceptMe` when a session exists [CITED: github.com/supabase/auth v2.197.0 internal/models/user.go `UpdatePassword` — "log out user from all other sessions to ensure reauthentication after password change"]. A reset on B revokes A's refresh token. A's device keeps working until its access token expires (`jwt_expiry = 3600` [VERIFIED: supabase/config.toml:201]), then lands on `/entrar`.
**How to avoid:** you can't. Document it in UAT. The D-312 notice sets the expectation. Do not treat it as a leak: it is the identity owner's action.

### Pitfall 5: The join call uses a stale or absent session in the same server action
**What goes wrong:** `apiFetch` re-reads the session from `cookies()` [VERIFIED: api.ts:15-23]. In the same action that just called `signInWithPassword`, relying on that re-read is fragile, and `apiFetch` overwrites any `Authorization` passed in `init` when an old session exists.
**How to avoid:** add a helper that sends `Authorization: Bearer <data.session.access_token>` from the `signInWithPassword` result explicitly, together with `x-tenant-host`.

### Pitfall 6: Invite resend mints a login link for an existing identity
**What goes wrong:** `resendInvite`'s `generateLink('invite')` → `email_exists` → `generateLink('recovery')` branch [VERIFIED: invites.ts:517-555] mails a token that logs the person in without the password, violating D-314.
**How to avoid:** branch on `identityKind` before any GoTrue call. Existing identities get only the tokenless mail.

### Pitfall 7: `openInviteTenantId` picks the wrong tenant
**What goes wrong:** the newest open invite by e-mail [VERIFIED: mail-tenant.ts:115-129] across tenants brands a mail for tenant X when the flow started on Y.
**How to avoid:** always ask "open invite **for H**" (Pattern 7).

### Pitfall 8: Rate limiting is effectively per Vercel egress IP
**What goes wrong:** `signInWithPassword` runs server-side, so GoTrue sees the Next server's IP. The limits (`sign_in_sign_ups = 30` per 5 min per IP [VERIFIED: supabase/config.toml:249], token endpoint 150/5 min [CITED: supabase.com/docs/guides/auth/rate-limits]) throttle everyone behind one IP and never one attacker. This already applies to `/entrar`. The "já tem conta" state adds no new oracle beyond the existing 409 (D-302 accepts it).
**How to avoid:** out of scope for 08.1 (WR-05's pending product decision [VERIFIED: signup.ts:167-169]). Optionally forward the client IP with `Sb-Forwarded-For` [CITED: supabase.com/docs/guides/auth/rate-limits] in a later hardening phase.

### Pitfall 9: The unique index is not partial, so a soft-deleted membership blocks re-joining
**What goes wrong:** `memberships_tenant_user_uq` covers soft-deleted rows. `on conflict do nothing` then silently "succeeds" with zero rows for a removed member.
**How to avoid:** the join guard reads the existing row first (`for update`) and answers `removed` explicitly. The seed already has a soft-deleted member (`SEED_REMOVED_MEMBER` [VERIFIED: grep scripts/seed.ts:1775]) to test it.

### Pitfall 10: Realtime keeps delivering after a block until the JWT changes
**What goes wrong:** Realtime authorization is evaluated on join and cached for the connection. Revoked users "keep receiving messages until their JWT expires or a new one is sent" [CITED: supabase.com/docs/guides/realtime/authorization].
**How to avoid:** Phase 8's block publishes a revoke signal and the client re-`setAuth`s or leaves (Touchpoints). 08.1 only needs the topic tests.

### MODER-02 — "the member's session is revoked immediately" — per-membership design
What Supabase offers, and why none of it is per tenant:
- `auth.admin.signOut(jwt, scope)` acts on the session **of the given JWT** (the admin does not hold the blocked member's JWT) with scope `global | local | others`. Global revokes all refresh tokens of the identity [CITED: github.com/supabase/auth v2.197.0 internal/api/logout.go; supabase.com/docs/reference/javascript/auth-signout].
- There is no admin route to sign out a single session by id [CITED: v2.197.0 internal/api/admin.go].
- Access tokens cannot be revoked before expiry [CITED: supabase.com/docs/reference/javascript/auth-signout].
- **Therefore any GoTrue-level revocation is identity-wide and would violate D-304.**

**Recommended per-membership revocation (Phase 8 adopts):**
1. **API:** set `memberships.blocked_at` on `(tenant_id = ctx.tenantId, id = :membershipId)`, never `where user_id = …`. `requireAuth` (Pattern 1) refuses on the very next request **only on B's host**. That is already "immediate" for every API call.
2. **Web BFF:** every `(app)` render calls bootstrap → `MEMBERSHIP_BLOCKED` → `/auth/blocked` → `signOut({ scope: 'local' })`, which revokes only B's origin session.
3. **Realtime:** in the block transaction, publish an ids-only signal on `tenant:<B>:user:<u>` through `app.realtime_signal` (tenant from the admin's lane claim [VERIFIED: 20260930123213_realtime_authorization.sql `app.realtime_signal` uses `app.tenant_id()`]). `LiveShell` reacts with a navigation (→ bootstrap → `/auth/blocked`) and a re-`setAuth`, which forces policy re-evaluation. `app.realtime_topic_allowed` already refuses `blocked_at is not null` for the topic's tenant only.
4. **Push:** call `app.push_subscriptions_delete_dead(array[u])` in B's lane. It is already written for "Phase 8's block action can call it eagerly" [VERIFIED: 20260930180227_push_subscriptions_functions.sql comment above `push_subscriptions_delete_dead`] and is tenant-scoped.
5. **Sign-up / re-join:** already refused per tenant by `joinTenant` (D-304). MODER-02's "cannot re-register with the same e-mail through the sign-up link" holds.
6. Optional hardening Phase 8 may add: record `(membership_id, session_id)` from the JWT `session_id` claim to show "sessões ativas" per tenant. **Not** needed for correctness.

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |

### Known Threat Patterns for this stack
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Host header grants a membership | Elevation | The host only selects among own memberships. Join requires a proven password/recovery session and consents. |
| Forged `x-tenant-choice` | Elevation / Tampering | Honoured only on non-tenant hosts, and only if the slug is one of the caller's own memberships |
| Block/suspension of A bleeds into B | DoS (integrity of D-304) | Host-first selection. Tests. |
| Global sign-out revokes other tenants | DoS | Local scope only. Reconcile grep. |
| E-mail enumeration via sign-up | Information disclosure | Accepted by D-302 (pre-existing 409). Membership facts only after the password. |
| Cross-tenant name leak via profile join | Information disclosure | RLS-scoped joins + explicit tenant predicates. pgTAP proves A's lane shows A's name. |
| Recovery mail branded for a community the person never joined | Spoofing (low) | Open Question 1. Link only to a verified tenant host. Constant form answer. |
| Existing-identity invite as a login link | Elevation | Tokenless link to `/entrar`. The resend never calls `generateLink` for existing identities. |
| super_admin joining a tenant | Elevation | D-316 refusal in the join and invite paths |
| Concurrent join double-write | Tampering | `memberships_tenant_user_uq` + `for update` read + `onConflictDoNothing` consents |
| Password guessing on the join form | Spoofing | Same GoTrue limits as `/entrar` (Pitfall 8). Pending product decision (WR-05). |
