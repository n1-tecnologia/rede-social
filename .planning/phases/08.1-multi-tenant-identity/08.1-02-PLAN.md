<objective>
The sign-up path into a second community (D-301). Today an existing e-mail on B's `/cadastro` ends in "Este e-mail já está cadastrado"; after this plan it becomes a one-step join confirmed with the existing password and B's two consents, reusing the `POST /v1/join` write and the per-tenant consents proved in 08.1-01.

**As a** person who already has an account in one community, **I want to** sign up on another community's page with my e-mail and just confirm my existing password, **so that** I join it without a second account and without the page telling anyone where else I am a member. <planning_decisions>
1. **Do not reuse the password typed into the sign-up form** (RESEARCH A2). It was entered as a NEW password (`autocomplete="new-password"`); D-301 asks for the existing password explicitly, and an explicit step lets password managers fill it.
2. **The draft cookie holds `{ email, name }` only**, base64url JSON validated with Zod on read, HttpOnly, 10 minutes, per origin. A forged cookie gains nothing: the password still has to match the e-mail it names.
3. **`apiFetchWithToken` never reads the cookie session.** It sends exactly the token it is given plus `x-tenant-host`, so the join in the same action cannot pick up a stale or absent session.
4. **A refused join signs the fresh session out locally** (`FORBIDDEN`), because the person holds a B-origin session with no B membership; blocked goes through `/auth/blocked`, which already signs out.
</planning_decisions>
