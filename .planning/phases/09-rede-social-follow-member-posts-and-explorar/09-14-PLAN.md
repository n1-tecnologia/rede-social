<planning_decisions>
1. **Assumption delta: no-change.** The detector fired on the word 'another' in 'follow another member'; this round hardens existing gates and introduces no second platform, tenant or identity model. No architecture checkpoint.
2. **WR-07's UPDATE half is a BEFORE UPDATE guard, not the review's UPDATE policy.** The counter triggers `app.feed_like_count()` and `app.feed_comment_count()` run with the invoker's rights. A restrictive UPDATE policy narrowed to the author would make the counter UPDATE of every non-author's like or comment match zero rows WITHOUT an error (an UPDATE that fails USING is filtered, not refused), so `like_count` and `comment_count` would drift silently for every post a member reacts to. The guard compares OLD and NEW instead: a non-author member may move only the two counter columns, and no member may move `author_user_id`, `visibility`, `community_id` or `tenant_id`. The DELETE side has no such trap (the service never hard-deletes), so it uses plain restrictive policies as the review asked.
3. **`feed_comments` gets the DELETE policy only.** An author soft-deleting their own root comment cascades to every live reply in one UPDATE, including replies by OTHER members (D-334), and `app.feed_like_count()` moves `feed_comments.like_count` as the invoker; an UPDATE guard on comments would refuse both legitimate paths. Comment audience is already enforced by `feed_comments_community_gate` through `feed_posts`. Recorded as a deliberate non-guard, not an omission.
4. **The deleted-post branch mirrors the live-post staff exemption.** The review and the gap text say 'except admin_tenant and the system lane'. The live-post branch grants that exemption only while `social` is enabled (D-483: off hides everything, the admin included), so the new branch does the same; a divergence would let an admin play a member video through a deleted post while `social` is off but not through a live one.
5. **`app.social_can_read_for(p_user, p_author)` is the explicit-user mirror of `app.community_locked_ids_for` (08.2).** `app.social_visible_author_ids()` is claims-based and answers the empty array in the worker lane (role `support_tenant`, zero user), so the reply notice cannot reuse it; and the feed module may not read the social module's table (MOD-02). It is declared here (the SQL half, with its pgTAP) and wired in plan 09-15. No kernel stub is added: it is asked only about followers posts, which exist only where `social` ships. It answers about other users only to the system lane (no oracle).
6. **Local application without a wipe.** Each task applies its own migration with `pnpm supabase migration up` and runs only its own pgTAP files. The ONE `pnpm db:reset` of the gap round is Task 3's clean-apply gate (it needs Igor's consent), which also clears the moderation_log rows the integration runs leave behind before the full pgTAP suite runs (pgTAP 154 trips on that residue).
7. **Reversibility.** Task 1 and Task 3 are reversible (`create or replace` back to the previous body, or a later migration that replaces the function). Task 2 is rated costly: restrictive policies and a guard on the tables every later member-authoring phase writes through; folding them back needs a coordinated migration and a re-test of every member write path.
</planning_decisions>
