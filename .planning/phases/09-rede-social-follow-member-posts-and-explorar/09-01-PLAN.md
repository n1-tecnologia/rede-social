<planning_decisions>
1. **The legacy flag is ignored, not removed (D-482 allows either).** `feedSettingsSchema` and `FEED_POSTING_POLICIES` stay exported and parsed nowhere on a request path; removing them would break the older web during the deploy window for no gain. The registry simply stops reading them, and a regression test proves a `feed` blob carrying the old members value grants nothing.
2. **The permission branch lives in the app-tier registry**, not in the social manifest, because composing `feed.post.create` from the social module would make the social package name a feed permission string and a module-to-module import is denied by the boundary rules (MOD-02). The manifest carries only its own `social.participate`.
3. **No routes in the manifest yet.** The `routes` loader is added by plan 02 with the first route file; declaring it here would point at a file that does not exist.
4. **`requires` is enforced in the composition only.** `requireModule('social')` reads the flags cache for `social` alone (RESEARCH Pattern 1); plan 02 chains `requireModule('feed')` beside it on every social route. This plan proves the composition half.
5. **Seed:** `social` is ON for rede-lab and OFF for rede-demo, so the two-tenant isolation suite and the e2e exercise the module while the older rede-demo specs ("a member holds no `feed.post.create`") stay valid. The real tenant stays off.
</planning_decisions>
