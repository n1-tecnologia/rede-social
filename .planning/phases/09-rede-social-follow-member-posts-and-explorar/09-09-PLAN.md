<planning_decisions>
1. **One form, one prop marks the variant**: `memberLimits` (absent for the administrator's composer, present for a member's). Everything the variant changes is conditional on that prop, so the administrator's composer is byte-identical and its 04 tests stay as they are.
2. **The limits are read from the bootstrap**, parsed by the same tolerant schema the registry uses; there is no fetch and no second source. The page passes parsed numbers, the form never reads a blob.
3. **The pick-time cap is a hook option**, not a fork: `useSignedUpload` gains an optional `maxBytes` (and the refusal key for it) used only by the member variant; the API's 413 stays the authority.
4. **The moderator row reuses the existing delete route and action**: `DELETE /v1/feed/posts/{id}` already handles the moderator branch (plan 07), so the web adds a dialog variant and a toast, not an action.
5. **Redirect after publish**: for the member variant the post-publish target is `/inicio?aba=explorar`; the administrator's stays `/inicio` (D-472).
6. **Sketch gate**: the member composer is a designed surface of the UI-SPEC; the precondition below repeats the gate of plan 08.
