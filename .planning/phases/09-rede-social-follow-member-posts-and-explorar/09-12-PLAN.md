1. **`ModuleToggles` stays list-agnostic**: the page builds an optional per-key `extras` map (note, disabled flag, confirmation labels, trailing node) from facts and catalog strings; the component renders what it is given. Rows without extras render exactly as today.
2. **The confirmation is the component's, the copy is the page's**: `ModuleToggles` opens a `ConfirmDialog` when a row has `confirmEnable` and the next value is true; it has no social-specific string.
3. **Pure conversion helper**: `socialLimitsToPatch` / `socialLimitsFromSettings` convert between the form's units (MB, seconds, counts) and the contract's bytes, so the conversion and the ranges are unit-tested without a DOM.
4. **The ranges come from the shared constants** (the same ones the API validates with), so the form and the API cannot disagree on a bound.
5. **No new column or route in this plan**: everything it calls exists from plan 06.
6. **Sketch gate**: the `social` row, its confirmation and the limits sheet are designed surfaces; the precondition below repeats the gate.
