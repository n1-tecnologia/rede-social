<planning_decisions>
1. **Migration order is the contract.** Three files, generated in this order so their timestamps sort: (a) `pnpm db:generate --custom --name=social_gate_seam` (the two seam declarations), (b) `pnpm db:generate --name=social_follows` (the table and its policies, whose insert policy calls `app.social_enabled()`), (c) `pnpm db:generate --custom --name=social_functions` (the seam bodies, `app.social_counts` and the grant/revoke hardening). The seam declaration must sort before the policy that names the function (the community-gate reason).
2. **The seam bodies live in the social migration, the constants in the kernel** (`packages/core/db/social-gate.ts`), exactly the 08.2 split: a project that reuses the feed without `social` keeps the default bodies and the gate is a no-op for authors.
3. **`social_visible_author_ids()` joins `memberships`** and keeps only live member followees (`role = 'member'`, `status = 'active'`, `blocked_at is null`, `deleted_at is null`). RESEARCH Pattern 2 left liveness to the service; putting it in the seam makes D-484 true at the RLS layer too, for the cost of one indexed join per statement (an InitPlan). The caller's own user id is always appended.
4. **Lists and counts exclude non-live parties in SQL**, never in JavaScript, so a page is never short because of a filter applied after the limit.
5. **The social profile read is its own route** (`GET /v1/social/members/{membershipId}`), independent of the base profile read (`GET /v1/members/{id}`), so a failure of one never hides the other and the strict D-45 schema is untouched.
6. **Permission, not role, on every social route** (`requirePermission('social.participate')` after the two module guards); the permission is composed for role `member` only (plan 01), so staff get 403 and a disabled module gets 404 first (ROLE-06 order: auth, module, permission).
7. **`GET /v1/members` gate is a small middleware**, not `requireRole`: staff pass; a `member` passes only when `permissionsForRequest(ctx)` contains `social.participate`; anything else is the old 403. It runs before query validation, as the staff-only middleware did (261016-jsq).
</planning_decisions>
