<planning_decisions>
1. **The locked card is a props-only module component** (heading, body, avatar node, action node), exactly because the module ships no language and knows no route; the host builds the avatar link, the lock disc and the action.
2. **The access value is matched by name.** `ACCESS_REFUSALS[0]` is the community code and stays so; `follow_required` is found with a lookup by value (and a test pins that `ACCESS_REFUSALS` contains it), so reordering the list can never swap the two meanings.
3. **Focus survives the refresh through a one-shot module variable** (`post-focus.ts`: `markFocusAfterFollow(postId)` / `consumeFocusAfterFollow(postId)`), because the locked screen unmounts when the server re-renders the same URL as the real post; `PostDetail` consumes it on mount. No query parameter, so the URL stays the shared one.
4. **The skeleton during the refresh is the card's own shape**, drawn by the host screen from the shipped `Skeleton`, not a route `loading.tsx` (which would also cover every normal post).
5. **The comment list's refusal type is widened, not forked**: `CommentAccessRefusal` becomes the two closed values and `onLocked` receives the code, so one list serves both reactions.
6. **A support user never gets this screen**: the API answers them the bare 404 (plan 05), so the web has no branch for them (UI-SPEC pending item 3).
</planning_decisions>
