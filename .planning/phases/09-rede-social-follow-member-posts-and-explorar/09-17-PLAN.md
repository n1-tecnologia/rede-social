<planning_decisions>
1. **Resync during render, not by key and not by effect.** Re-keying the row on the server value would remount the control and drop an in-flight tap; an effect paints one stale frame. The 'adjust state when a prop changes' pattern (a `seen` copy of the prop compared during render) fixes both and is allowed by the React compiler setting of the app. Only a CHANGED prop replaces local state, so a confirmed local tap survives a re-render with the same value.
2. **No e2e for the resync.** The failure that makes the state arrive late (the batch read failing) cannot be produced in the local e2e, so the unit tests are the proof and the browser check is a `backstop` truth that abstains to human verification. The e2e sample at the end is a regression sample of the specs the affected map assigns to `apps/web/components/social/**`, run on one project to spare the disk.
