<planning_decisions>
1. **The module owns three props-only components, the host owns everything else** (MOD-02): `FollowButton`, `FollowCounts` and `FollowListRow` take already-translated strings, already-formatted numbers and slots; the optimistic state, the server actions, the toasts and every route live in `apps/web`.
2. **One `FollowControl` for every placement**, taking `membershipId`, `name`, `size`, the initial `following` (or a pending marker), and an `onChange` for hosts that want the new count (the profile). It owns the optimistic flip, the reconcile with `{ following, followerCount }`, the revert and the toast.
3. **State reads are batched on the server**: the directory and the lists call `followState` once per page (server-side for page 1, with each load-more result) so a row is never N requests; until it arrives the slot keeps its width.
4. **`canBrowseMemberDirectory` takes the viewer** (`{ role, permissions }`), not a role: the permission `social.participate` is the single switch (D-482), the same composed value the API checks.
5. **The social block is a small server component** (`SocialProfileBlock`) so the page's loading and error states are Suspense/inline states of that block alone and can never hide the base profile.
6. **Catalog:** every string goes to `social.json` (created in plan 08); `members.json` is not duplicated.
</planning_decisions>
