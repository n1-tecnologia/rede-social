# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** Phase 13 stage 1 is a native shell around the web's own screens (D-600, D-603). Every member and staff screen of the web keeps its existing contract (Phases 2-12) and is NOT redrawn here. The new UI is the thin layer around those screens: five surfaces drawn natively, six small additive pieces of web that exist only inside the app (plus one web screen that exists for everyone), and one platform tab. All text is pt-BR.

| # | Surface | Drawn by | Audience | Route / place (proposed, the planner owns the final names) |
|---|---------|----------|----------|--------------------------------------------------------------|
| 1 | Splash, icon label, launch sequence | native + build | everyone | build asset, first 10 s |
| 2 | Shell frame: safe areas, status bar, keyboard, back, links, loading bar | native | everyone | around every web screen |
| 3 | "Sem internet / Não foi possível abrir" screen | native | everyone | replaces the web view when nothing can render |
| 4 | "Atualize o app" screen | native | everyone | replaces the web view when the app is too old |
| 5 | Lock screen and privacy cover | native | members and staff who turned the lock on | over the web view |
| 6 | Notification explainer ("Ativar" / "Agora não") | web, in the app only | everyone, once | bottom sheet over Início |
| 7 | Notification row states and "Bloqueio do app" row | web, in the app only | everyone | `/configuracoes`, group Preferências |
| 8 | What the app hides from the web (install gate, home-screen hint, Web Push button) | web, in the app only | everyone | existing components, inert in a browser |
| 9 | Offline reading of the last feed | web, in the app only | members and staff | `/inicio` |
| 10 | Purchase switched off: neutral padlock | web, in the app only (per store) | members | Loja, product, locked community/course/live/lesson/post |
| 11 | "Excluir minha conta": row, page, dialog, "Exclusão agendada" screen | web, **browser and app** | members and staff | `/configuracoes/excluir-conta`, `(auth)` screen |
| 12 | The "App" tab: identity, store accesses, links, purchase switches, store listing, checklist | web (platform panel) | `super_admin` | `/plataforma/tenants/[id]/app` |

**What has no UI** (said plainly): a "Gerar app" button and build progress (Deferred, D-605); the platform panel inside the app (Deferred); a community picker (D-608); any native rebuild of feed, Reels or chat (stage 2); in-app purchase; a soft "there is a new version" prompt (only the blocking "Atualize o app" exists); a setting for the lock's grace time; a per-tenant theme editor for the native screens (they take the tenant's existing branding).

**Design authority.** The app takes the web's own design, adapted to the phone (Igor, 2026-11-03): there is no design-team prototype for this phase. Every new surface is **[designed]** (UI-04) in the prototype's language (Manrope, `#f5f7fb` ground, white cards, 12px radii, 44px targets raised to 48 on native, the tenant's brand as the single accent) from primitives already in `@rede-social/ui` and from the Phase 2, 09.2, 09.4 and 12 contracts. PROTOTYPE.md's token rules apply (no hex in TSX, no literal text in TSX); its porting rules do not (nothing is ported).

**Inherited, not re-decided.** Spacing, type scale, colour model, `(auth)` frame and `AuthBrand` (UI-D-521), settings `Row`/`Group` (UI-D-269), `BottomSheet` and `ConfirmDialog` (UI-D-516), `EmptyState`, `StatusPill` tones, the platform tenant tabs (UI-D-536), the write-only sheet pattern (UI-D-538, UI-D-555), the notice-row geometries (09.4), the first-open ask sheet (`FirstOpenAsk`, quick 261007-kyp), `OfflineBanner`, `PullToRefresh`, the back stack, `--safe-top`/`--safe-bottom`. **Phase 13 declares no new token, no new colour, no new type size and no web dependency.** The native layer re-uses the same tokens by value (UI-D-601).

**Upstream decisions.** `13-CONTEXT.md` D-600..D-615 are LOCKED and honoured; each is traced in "How each locked decision shows up". There is no `13-RESEARCH.md` yet: the shell technology, the bridge and the store-rule wording are the researcher's. This contract is written so that it holds for any shell technology that satisfies D-600. The visual and interaction questions this phase opens are decided as **UI-D-600..UI-D-631**, continuing after `UI-D-599`, the highest id in any UI-SPEC (`grep -rhoE "UI-D-[0-9]+" .planning | sed 's/UI-D-//' | sort -n -u | tail -1` returned `599` on 2026-11-03).

**Non-interactive session.** No question could be asked in this run. Every choice that was genuinely open took its recommended default and is repeated in **Pending User Confirmation** (PU-1..PU-14), so the orchestrator can confirm or overturn it with one line. The sketch gate is a recommendation, not an approval; no sketch was drawn and no approval was written.

## Phase 13 Visual Decisions (UI-D)

### The layer rule and the native tokens

| # | Question | Decision | Rationale |
|---|----------|----------|-----------|
| **UI-D-600** | Who draws what (D-603, D-608). | **Three kinds of surface, never mixed.** (1) **Native screens** are drawn by the shell and must work with no web page loaded: splash, load-failure, update, lock, privacy cover. They take colours, logo and name from a small cached branding record (UI-D-601), never from the web. (2) **Web pages inside the app** are the existing screens, unchanged; sign-in, sign-up, recovery, invite, the refusals (`MEMBERSHIP_BLOCKED`, `SUBSCRIPTION_PENDING`, `PROFILE_FORM_PENDING`, `TENANT_*`) and every module screen render exactly as the web renders them. (3) **Additive web pieces** (surfaces 6-10) are web components that read one in-app marker (UI-D-606) and render nothing different in a browser. A new native screen is added only when the web cannot paint it (no network, wrong version, locked). Everything that can be a web screen IS a web screen, so the PWA, the browser and the app share one copy and one catalog. | The fewest native screens that D-600 allows; stage 2 later replaces whole web screens, not these. |
| **UI-D-601** | Native tokens, type, spacing, themes. | **Colour** (values copied from `packages/ui/src/styles/tokens.css`, light / dark): ground `#f5f7fb` / `#0f1118`; card `#ffffff` / `#181c26`; text `#16233b` / `#f2f5fa`; text-secondary `#51617c` / `#a6b1c4`; text-tertiary `#8595ad` / `#64718a`; border `rgba(22,35,59,.10)` / `rgba(255,255,255,.08)`; danger `#ef4444`; and the **tenant brand**: `primary`, `onPrimary` (light) and `primaryDark`, `onPrimaryDark` (dark) from the by-host branding answer. **Brand record:** the shell stores, in secure storage, the last by-host answer's `displayName`, `logoUrl` (and the logo file itself), the five colours and the theme choice; the build bakes the same record, so the very first launch with no network still paints the right brand. Refreshed on every successful launch. **Theme:** follows the web's `rede_theme` choice when the cookie is known, else the system setting. **Type:** Manrope 400 and 700 bundled in the binary (the offline screen cannot fetch a font); the four web sizes only: 12 caption, 14 body (button labels 14/700, 16/700 on a `lg` button), 16/700 heading, 24/700 title (`tracking -0.02em`); line height 1.5 body, 1.2 headings. **Font scale:** native text follows the system font scale up to **130%** (`maxFontSizeMultiplier` 1.3) and every native layout reflows (no fixed-height text boxes). **Spacing:** the 4/8/12/16/24/32/48/64 scale in dp. **Targets:** **48dp** minimum on native screens (Android's floor, above the web's 44px; the web inside the view keeps 44px). **Radii:** 12 on cards and fields, full on pills and icon discs. **Motion:** none added; every fade is skipped when the system "reduce motion" is on. | Native cannot read CSS variables; copying the values by number keeps one palette and the offline screen identical to the online one. |

### Native: launch, frame, failure, update, lock

| # | Question | Decision | Rationale |
|---|----------|----------|-----------|
| **UI-D-602** | Splash, store name and icon label (D-607). | **Splash** (build asset from the branding by extending `packages/core/server/branding/icons.ts`, a pure sharp function like the maskable icon): background = tenant `primary`; the logo centred at one third of the short side (never above 160dp), inside the maskable icon's 80% safe zone; no text, no spinner, no progress; the same image for light and dark. A tenant with no logo gets its `displayName` in 24/700 `onPrimary`, centred, up to three lines. **Icon**: the existing 1024-square derivation (logo over `primary`, no transparency, no rounded corners: the OS rounds). **Icon label (under the icon):** the same `short_name` the per-tenant manifest route returns, at most 12 characters; if it has none, `displayName` cut at 12. **Store name:** `displayName`, at most 30 characters; a longer one is cut at a word boundary by the build and the App tab shows the cut (UI-D-621) before anything is sent. The splash and icon change only with a new build (Deferred: automatic rebuilds). | The icon pipeline already handles contrast and safe zone; reusing its colours makes the splash look like the icon the member just tapped. |
| **UI-D-603** | Launch sequence and the first paint. | (1) System splash (UI-D-602). (2) The shell asks the by-host answer and the version check in parallel and loads the tenant's primary host in the web view; the web view's own background is set to `primary` until its first paint, so there is no white flash. (3) First paint of the web page: a 200ms cross-fade from the splash colour to the page ground (skipped under reduce motion). (4) **Loading bar:** a 4dp bar in `primary`, `onPrimary`-edged, fixed under the status bar, shown only when a navigation takes longer than 400ms and removed at load; it is the only native loading signal (the web has its own skeletons). (5) **Timeout:** 10s without a first paint of the first document shows the load-failure screen (UI-D-611, "Não foi possível abrir"); a later navigation that stalls keeps the bar and, after 15s, shows the web's own error. (6) A cold start with the lock on (UI-D-610) shows the lock screen over the splash colour, never the web page. | One launch story with one signal per phase; the timeouts guarantee the member never stares at a blank screen. |
| **UI-D-604** | The frame: status bar, safe areas, keyboard, gestures, orientation. | **Edge to edge:** the web view fills the whole screen; the web already paints under the status bar and reads `env(safe-area-inset-*)` through `--safe-top`/`--safe-bottom` (root layout keeps `viewportFit: 'cover'`), so the shell adds no padding of its own. **Status bar:** transparent; icon colour follows the page theme (dark icons on the light ground, light icons on the dark ground), switched by the shell when the theme changes. **Keyboard:** content resizes above the keyboard (Android resize mode; iOS scrolls the focused field into view); the web's fixed bars (composer, chat input, BottomNav) are the web's own and must stay above the keyboard, a regression test per bar. **Pull to refresh:** only the web's `PullToRefresh` (mobile widths); the web view's own bounce/overscroll is off so two refresh gestures never stack. **Zoom:** page pinch-zoom off (the app is not a document); the web's image/media viewers keep their own zoom. **Text:** no OS text-size override of the page (the web's own sizes stand). **Long-press:** text selection allowed; link previews and the image context menu off. **Orientation:** phones portrait (a video in full screen may rotate); tablets free. **Tablets and iPad:** the web's responsive layout from `md` up (rail, `max-w` columns) runs unchanged inside the view; native screens are a centred `max-w-sm` column (UI-D-631). **Screenshots and the app switcher:** allowed, except the privacy cover of UI-D-610. | The web has already solved safe areas and refresh; the shell's job is to get out of its way. |
| **UI-D-605** | Navigation, back and links. | **Inside the view:** only the tenant's primary host (and the tenant's other verified hosts, if the by-host answer lists them); the shell can open no other host in the view (D-608). **Everything else opens in the phone's browser** (the system browser, not an in-app browser): every `checkoutUrl` (D-615), post links to other sites, `mailto:`, `tel:`, store links. The member returns by switching apps; no "Voltar ao app" chrome. **Back:** iOS edge-swipe goes back through the view's history; Android's back first lets the web close a sheet/dialog (the web already handles the system back for them), then goes to the web back stack (`goBack`), and at the root of Início hands back to the OS (the app goes to the background; no "press again to exit"). **Links that open the app** (D-611): `/auth/confirm`, shared post links and a tapped notification land in the view on the target path and keep the session in the shell; a link whose path the app cannot show is opened by the same view as the web would. **A tapped notification** opens the payload's same-origin path in the view (no intermediate screen). | A closed host list is the app's fixed-to-tenant guarantee made visible; the OS browser for purchases is what D-615 decided. |
| **UI-D-606** | Telling the web it is in the app (D-603). | One marker the shell sets before the page runs (a user-agent token or an injected flag; the technology is the researcher's), read by one tiny helper `isNativeApp()` plus the store platform (`ios` / `android`). **Inside the app the web: (a)** never renders the install gate (`InstallGate` returns children; `data-install-gate` stays `open`), the iOS "Adicionar à Tela de Início" hint (`InstallHint`) or the Android "Instalar app" button; **(b)** replaces the Web Push enable button and switch by the native versions of surfaces 6-7 and never calls `Notification.requestPermission`, `serviceWorker.register` for push, or `FirstOpenAsk`; **(c)** shows the unread number on the icon through the bridge, nothing on screen; **(d)** shows the "Bloqueio do app" row (UI-D-609). **In a browser none of this exists**: `isNativeApp()` is `false`, the server HTML and the first client render are identical to today (the hydration rule of `InstallGate`), and each change ships with a test showing the browser output is unchanged. The helper is evaluated after mount, so no in-app piece is ever in the server HTML. | One marker, one reading point, one test pattern; hiding by default and revealing after mount keeps the browser byte-identical. |
| **UI-D-611** | Load-failure screen ("Sem internet" / "Não foi possível abrir"). | Native, full screen, ground colour, a centred `max-w-sm` column: the shipped `EmptyState` look re-drawn natively: 64dp disc in `bg-tertiary` with the icon in `text-secondary` (`WifiOff` or `CloudOff`, 28), `h1` 16/700 title, 14/400 secondary body, then a brand fill button "Tentar novamente" (48dp, full width, `onPrimary` on `primary`) with pending "Tentando…" and the button disabled. Above the disc, the tenant logo (48dp high, `max-w` 160) or, with no logo, nothing. **Two variants** chosen by what failed: the device is offline -> **"Você está sem internet"**; the device is online but the host did not answer, timed out or refused -> **"Não foi possível abrir"** (the body names the tenant). It retries by itself when the connection returns and on every tap; success replaces it with the page. It shows **only** when no web page can be rendered (first load, or a navigation with no cached copy); a connection lost while a page is on screen keeps the page and uses the web's `OfflineBanner` (UI-D-612). A tenant status refusal (`TENANT_SUSPENDED|PREPARING|UPDATING|UNAVAILABLE`) is the web's own screen, not this one. | D-612's branded "sem internet" screen, without taking over the web's own refusal screens. |
| **UI-D-613** | "Atualize o app" screen (Claude's Discretion). | Native, full screen, same column as UI-D-611: disc with `Download` 28, title **"Atualize o app"**, body, and one brand fill button "Atualizar" that opens this app's own store listing (App Store or Google Play, a constant baked at build). **No dismiss, no "Agora não", no back**: it appears only when the installed version is below the API's minimum for this platform, i.e. the native contract changed. The check runs at launch and at every return from background; a failed check never blocks (the app opens). The API stays backward compatible, so the screen is rare by design. | A hard floor, used only when a contract broke; anything softer would let an incompatible app run. |
| **UI-D-610** | Lock screen, privacy cover, when it locks (D-613a). | **When:** a cold start, and a return from background after **60 seconds or more** (PU-2); returning sooner does not lock. **Unlocked state is kept:** the web view is not reloaded after a successful unlock. **Lock screen** (native, over the web view, ground colour): centred column: logo (64dp high) or `displayName` 16/700, below it the body "Desbloqueie para continuar." (no lock glyph is drawn), a brand fill button (48dp) **"Desbloquear com Face ID"** (iPhone with Face ID), **"Desbloquear com Touch ID"** (Touch ID), **"Desbloquear com biometria"** (Android) or **"Desbloquear"** when the type is unknown; and a ghost text button **"Sair da conta"** (it runs the web's logout, which forgets this device's push, then clears the lock) so a member is never trapped. The system prompt opens by itself **once** when the screen appears; if it is cancelled the button stays. **The phone passcode is always accepted** (biometric with device-credential fallback), so a failed face or finger never locks anyone out. **Failures:** wrong or cancelled -> inline 12/400 `text-danger` line "Não foi possível confirmar que é você. Tente de novo."; too many tries -> "Muitas tentativas. Use a senha do aparelho."; the system says the device no longer has a passcode or biometrics -> the lock turns itself off, the app opens, and the web shows the toast "O bloqueio do app foi desligado porque este aparelho não tem mais Face ID, digital ou senha." **Privacy cover:** only while the lock is on, when the app goes to the app switcher or background the view is covered by the brand screen (logo centred on ground) so no content appears in the snapshot. **Not locked:** the load-failure and update screens (they show nothing private), and a signed-out device (nothing to protect: the setting is cleared by logout). | Lock behaviour decided once and for all: no setting for the delay, always an exit, always the passcode as a fallback. |

## Data the screens read (for the planner; not a UI decision)

The UI assumes these shapes. Names are proposals; the contract is what is shown and what must never be sent.

- **Native branding record** (public, no session): from `GET /v1/public/tenants/by-host` and the baked build record: `displayName`, `logoUrl`, `primary`, `onPrimary`, `primaryDark`, `onPrimaryDark`, `shortName`, `hosts[]` (primary + verified), and a theme hint. **Version check**: a public read per platform answering `{ minVersion, storeUrl }` (the store URL may be baked instead). Never a session read.
- **In-app marker and platform**: set by the shell before the page runs; the web helper returns `{ native: boolean, platform: 'ios' | 'android' | null }`. The API reads the same platform from a request header to decide purchase visibility; a browser never sends it.
- **Bootstrap** gains `purchaseVisible: boolean` (always `true` for a browser and for a store whose switch is on) and `pendingDeletion: { until } | null` (only to raise the "Exclusão cancelada." toast after sign-in; the account is reactivated by the sign-in itself).
- **Delete account**: `POST` with the password; answers the deadline date; refuses `LAST_ADMIN`, wrong password, session ended. Never returns personal data. Reads: the role and `isLastAdmin` only.
- **Push (app)**: register and delete a device token under the tenant's project and RLS; the explainer's stored answer is a device flag, not a server field.
- **Platform App tab reads** (`.strict()`, no secret field): `identity` (`displayName`, `shortName`, `host`, `bundleId`, `applicationId`, `lastBuild` per store), `credentials[3]` (`held`, `heldAt`), `links` (`teamId`, `fingerprint`, `verdict.ios`, `verdict.android`), `purchase` (`ios`, `android`), `listing` (`name`, `description`, `ageRating`, `privacyUrl`, `reviewerEmail`, `reviewerHeld`), `checklist.manual[5]`, plus the derived `appState`. **Writes**: set credential (multipart, never echoed), set IDs (refused when published), set links, set purchase switch, set privacy URL, create/rotate reviewer account, set manual row. Each write re-checks `super_admin` and answers coded errors the sheets map to the sentences above.
- **Per-host verification files**: `apple-app-site-association` and `assetlinks.json` served from the data of the links card (planner); a missing field yields no file for that platform (no partial file).
