# Phase 13: App nativo iOS e Android por tenant (white-label) - Context

**Gathered:** 2026-11-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Each tenant gets its own native iOS and Android app (its own store listing, name, icon and bundle id), fixed to that tenant's host. The app is a third client of the same `/v1/*` API, beside the web BFF. Members and the tenant's staff (`admin_tenant`, `support_tenant`) find in it every feature of the web app, with native push and the web's own design adapted to the phone.

This phase delivers STAGE 1 only: a native shell that opens the tenant's existing web screens inside the app and adds the native layer around them (push, biometric lock, icon badge, links that open the app, offline last feed, camera and library, native share), plus the per-tenant build and release path, the "App" tab in the platform panel where the credentials are stored, the account deletion flow the stores require (also in the web), and the store listing assembly.

What this phase does NOT deliver: screens rebuilt 100% natively (stage 2, a later phase), a "Gerar app" button in the panel, in-app purchase, the platform panel (`/plataforma`, `super_admin`) inside the app, one Firebase project per tenant, anything that changes how the web, the PWA or the API behave for a browser user.

Additive rule (Igor, 2026-11-03): everything that exists is kept. A tenant without a native app is not affected.

</domain>

<decisions>
## Implementation Decisions

### How the app is built
- **D-600:** TWO STAGES. Stage 1 (this phase) is a native shell that loads the tenant's existing web screens (its primary host) inside the app and adds the native layer around them. Stage 2 (screens rebuilt 100% natively where the shell is not good enough; the candidates named are feed, Reels and chat) is a separate later phase, decided after seeing the app in real use. The shell technology must let stage 2 replace single screens inside the SAME app binary (Expo with a WebView is the candidate; the researcher decides). Igor: "os dois, em etapas". — **Reversibility:** costly — the shell-versus-native choice sets the app workspace, the bridge between the web pages and the native layer, and the store binaries every tenant publishes.
- **D-601:** Phase 13 CLOSES at stage 1: the shell published to both stores and working for a pilot tenant. Stage 2 is not in this phase and is not a gate for closing it. — **Reversibility:** reversible.
- **D-602:** The first version published already serves members, `admin_tenant` and `support_tenant` in the same app. The navigation and the admin screens are the web's own, shown by permission as the bootstrap answers. No "member only first" cut. The platform panel (`/plataforma`, `super_admin`) stays web-only, because a `super_admin` has no membership in a tenant (assumption announced to Igor on 2026-11-03 and not contradicted). — **Reversibility:** reversible.
- **D-603:** The web is NOT changed for browser users. The only web changes allowed are additive and inert in a browser: (a) detecting that the page runs inside the app, to hide the PWA install prompt, the iOS "Adicionar à Tela de Início" hint and the Web Push enable button and to hand push, biometric lock and the icon badge to the native layer; (b) the new things the decisions below add: the "Excluir minha conta" screen (D-609, D-610) and the per-host verification files (D-611). Every such change needs a test showing a browser sees no difference.

### Store accounts, credentials and building the app
- **D-604:** ONE STORE ACCOUNT PER TENANT. The tenant creates its own Apple Developer and Google Play accounts and invites the platform with a role that can publish; the store shows the tenant as the publisher (real white-label). Reason: Apple's App Review rules 4.2.6 (apps made from a template and submitted by the service provider are refused) and 4.3 (many near-identical apps in one account), as Igor was told on 2026-11-03; the researcher confirms the current wording. Cost and paperwork (an organisation account on Apple needs a D-U-N-S number) stay with the tenant. TestFlight and Google internal testing may use the platform's account during development. Igor: "conta de cada tenant". — **Reversibility:** costly — bundle ids and listings live in the tenant's account; moving an app between accounts is a store procedure.
- **D-605:** CREDENTIALS ARE ENTERED ON A SCREEN, THE APP IS GENERATED BY A COMMAND. A new "App" tab on the tenant in the platform panel takes, write-only and sealed under the platform master key exactly like the project credentials of D-539 (never returned, never logged): the store publishing access (App Store Connect API key, Google Play service account) and the Apple push key of that tenant. Building and sending the app to the stores runs by one command or CI workflow per tenant that reads them. The "Gerar app" button with build progress is deferred. Igor's standing rule: no `.env` or code edit per tenant. — **Reversibility:** reversible.
- **D-606:** PUSH GOES THROUGH ONE FIREBASE PROJECT (FCM) OF THE PLATFORM for all tenants, with one Android app and one iOS app per tenant and one sender service account in Secret Manager. The Apple push key of each tenant is the one entered in D-605. Isolation between tenants stays where it already is: the device token is stored in THAT tenant's own project under RLS (two-tenant negative test) and the send starts from that tenant's database and worker. Whether the Apple key is handed to Firebase or APNs is called directly is left to the researcher. Igor: "um da plataforma para todos". — **Reversibility:** costly — device tokens are issued per Firebase app; changing the sender project means every installed app re-registers.
- **D-607:** THE PLATFORM ASSEMBLES THE STORE LISTING FROM A TEMPLATE: app name, icon and splash derived from the tenant's branding (the existing icon pipeline in `packages/core/server/branding/icons.ts`), a standard pt-BR description, the age rating, and a reviewer account created in the tenant for App Review. The tenant only checks it and provides its privacy-policy URL. Screenshots are a step of the publication checklist, not generated code. — **Reversibility:** reversible.

### Signing in, deleting the account and links
- **D-608:** Sign-in, sign-up, password recovery, invite acceptance and the session are the web's own pages, unchanged, running inside the app (the session cookie lives in the shell). The app is fixed to its tenant: there is no community picker and the shell can open only that tenant's host. The refusals (`MEMBERSHIP_BLOCKED`, `MEMBERSHIP_INVITED`, `SUBSCRIPTION_PENDING`, `PROFILE_FORM_PENDING`, `TENANT_HOST_MISMATCH` and the `TENANT_*` host states) land on the screens the web already shows.
- **D-609:** DELETE MY ACCOUNT ANONYMISES. The access account, name, photo, bio, e-mail, the profile-form answers and the push devices are removed; posts and comments stay as "Membro removido" so conversations and counts do not break; purchase and access-grant records stay without personal data. The Apple rule requires the option inside the app whenever an account can be created there (the researcher confirms the current wording). The screen is a NEW capability for the web too: it promotes V2-PROF-02. — **Reversibility:** one-way — after the grace period the personal data is gone and the content is detached from the person; nothing restores it.
- **D-610:** The deletion has a 14-DAY GRACE PERIOD, on the same screen in the web profile and in the app. The account is deactivated at once (out of lists, no push, no new activity); signing in again within the 14 days cancels the request; a job anonymises it when the period ends. The confirm text tells the member that deleting the account does not cancel a subscription at the payment gateway. Igor: "prazo de 14 dias, no app e no web". — **Reversibility:** costly — the grace column, the job and the member's notice are published behaviour once the first request is made.
- **D-611:** LINKS OPEN THE APP WHEN IT IS INSTALLED, and the browser when it is not, as today. Universal Links (iOS) and App Links (Android) on the tenant's primary domain: the web serves, per host, the `apple-app-site-association` and `assetlinks.json` files from data held in the tenant's "App" tab (Apple team id, application id, signing-certificate fingerprint). It covers the auth e-mail links (`/auth/confirm`: confirm account, invite, recover password), shared post links (FEED-07) and the tap on a notification. The link is handled inside the shell so the session ends up in the app. Nothing existing changes for a browser. — **Reversibility:** costly — the associated domain is part of the signed build; a tenant that changes its primary domain needs a new build for the links.

### What the phone adds
- **D-612:** THE BASELINE ships without further questions: native push (iOS and Android), camera and photo library for posting, native share, a branded "sem internet" screen with a retry button and pull to refresh.
- **D-613:** THREE EXTRAS are in this phase (Igor chose all three): (a) a re-open lock with Face ID, fingerprint or the phone passcode, switched on by the member in Perfil and off by default; (b) the unread-notifications number on the app icon, from the counter the API already returns; (c) reading the last feed seen without a connection (partly promotes V2-PLAT-03; the researcher checks whether the existing Serwist service worker can serve it inside the shell, for example through the iOS app-bound domains). — **Reversibility:** reversible.
- **D-614:** THE NOTIFICATION PERMISSION is asked after the first sign-in, behind a branded explanatory screen with "Ativar" and "Agora não". Only "Ativar" fires the system prompt; "Agora não" leaves the enable button in Perfil, as in the web. Logging out removes that device's token. — **Reversibility:** reversible.
- **D-615:** PURCHASE keeps the redirect decided on 2026-11-03: the stored `https:` `checkoutUrl` opens in the phone's browser, no in-app purchase, the app never takes a card. PLAN B, already approved: each tenant has a SWITCH PER STORE (iPhone, Android) that, when off, hides price, buy button and link and leaves only a neutral padlock; members who already have access keep seeing their content unlocked. Default is ON in both. If a store rejects the app for the external purchase, the switch is turned off only where it was rejected, the app is rebuilt and resubmitted, with no change on the other store. Igor: "chave por loja e tenant". — **Reversibility:** reversible.

### Claude's Discretion
- The exact shell technology and the bridge between the web pages and the native layer (D-600 fixes only the constraint that stage 2 can replace screens inside the same app).
- The minimum-version behaviour: when a change to the native layer's contract makes an installed app too old, a branded "Atualize o app" screen with the store link; the API stays backward compatible for the apps already in the stores.
- The application id and bundle id of each app (default: the reverse of the tenant's primary host; PERMANENT once published, so the planner flags it as a one-way step).
- Whether the app bakes the tenant's stable slug or its host, and how it follows a changed primary domain (D-611 says the links need a new build in that case).
- The choice of the pilot tenant and the environments (a homologation build against the homolog host and a production build).
- The shape of the migration on `push_subscriptions` (native token, platform, relaxed `p256dh` and `auth`), the new transport beside `web-push`, the register and delete routes, and the mapping of the payload's same-origin `url` to the page the shell opens.
- Whether a device that has both the installed PWA and the native app should receive both pushes (default: yes, they are different endpoints; the planner may dedupe).
- How the build and release command runs (EAS or GitHub Actions macOS runners, fastlane or the stores' own APIs) and the exact `/plataforma` "App" tab layout (a UI-SPEC and sketch gate come first through `/gsd-ui-phase 13`, for that tab and for the delete-account screen).

</decisions>

## Existing Code Insights

### Reusable Assets
- `GET /v1/public/tenants/by-host` and `GET /v1/public/tenants/{slug}`: slug, display name, status, primary host, branding, and for non-central projects the Supabase URL and publishable key — enough to brand the splash and to resolve the tenant at start.
- `GET /v1/me/bootstrap`: user, membership, branding, enabled modules with navigation, permissions, counters (the unread number for D-613b) and the profile-form state — the shell shows the role-based navigation without new work.
- `packages/core/server/branding/icons.ts` plus the per-tenant manifest route: already derives the 192/512/maskable/apple-touch icon set from the tenant logo; the app icon and splash extend it.
- The D-539 sealed-credential registry and the 09.4 write-only token surfaces: the model for the "App" tab and for the Apple push key.
- `push_subscriptions` (unique `(tenant_id, endpoint)`, RLS per tenant), the `isAllowedPushEndpoint` allow-list and the payload v1 with a same-origin path `url`: the native push reuses the fan-out and the tenant scoping.
- Realtime Broadcast private channels with ids-only signals: work in a WebView unchanged, since the web page subscribes itself.
- The Serwist service worker and the `/~offline` page: a starting point for D-613c.

### Established Patterns
- The host selects, the membership decides; `x-tenant-host` goes on every API call: the shell opens only its tenant's host, so this holds without change.
- Every secret is sealed or in Secret Manager, write-only in the panel, never returned or logged: D-605 and D-606 follow it.
- A new screen behind a design gate: UI-SPEC and an approved sketch before any UI task (PFORM-26 is the latest example); the "App" tab and the delete-account screen are the new surfaces of this phase.
- Every new tenant-scoped table or route is covered by the two-tenant isolation suite and pgTAP: the native device token and the deletion request must be too.
- Soft-state over destructive state (archive, `deleted_at`): the 14-day grace of D-610 follows it.

### Integration Points
- New: `apps/mobile` (the shell workspace), the "App" tab and its sealed storage in the control plane, per-host `.well-known` routes in the web, the native transport and routes in the notifications module, the delete-account route, screen and anonymisation job, the build and release command and workflow.
- Touched, additively: the web's install prompts and push UI (hidden inside the app), `push_subscriptions` (native token and platform), the worker's push fan-out, `packages/contracts` (client-safe subpaths, `legal.ts` stays out of the client barrel).
