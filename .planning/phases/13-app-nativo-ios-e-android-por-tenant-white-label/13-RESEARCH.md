### Locked Decisions

**How the app is built**
- **D-600:** TWO STAGES. Stage 1 (this phase) is a native shell that loads the tenant's existing web screens (its primary host) inside the app and adds the native layer around them. Stage 2 (screens rebuilt 100% natively where the shell is not good enough; the candidates named are feed, Reels and chat) is a separate later phase, decided after seeing the app in real use. The shell technology must let stage 2 replace single screens inside the SAME app binary (Expo with a WebView is the candidate; the researcher decides). Igor: "os dois, em etapas". — **Reversibility:** costly — the shell-versus-native choice sets the app workspace, the bridge between the web pages and the native layer, and the store binaries every tenant publishes.
- **D-601:** Phase 13 CLOSES at stage 1: the shell published to both stores and working for a pilot tenant. Stage 2 is not in this phase and is not a gate for closing it. — **Reversibility:** reversible.
- **D-602:** The first version published already serves members, `admin_tenant` and `support_tenant` in the same app. The navigation and the admin screens are the web's own, shown by permission as the bootstrap answers. No "member only first" cut. The platform panel (`/plataforma`, `super_admin`) stays web-only, because a `super_admin` has no membership in a tenant (assumption announced to Igor on 2026-11-03 and not contradicted). — **Reversibility:** reversible.
- **D-603:** The web is NOT changed for browser users. The only web changes allowed are additive and inert in a browser: (a) detecting that the page runs inside the app, to hide the PWA install prompt, the iOS "Adicionar à Tela de Início" hint and the Web Push enable button and to hand push, biometric lock and the icon badge to the native layer; (b) the new things the decisions below add: the "Excluir minha conta" screen (D-609, D-610) and the per-host verification files (D-611). Every such change needs a test showing a browser sees no difference.

**Store accounts, credentials and building the app**
- **D-604:** ONE STORE ACCOUNT PER TENANT. The tenant creates its own Apple Developer and Google Play accounts and invites the platform with a role that can publish; the store shows the tenant as the publisher (real white-label). Reason: Apple's App Review rules 4.2.6 (apps made from a template and submitted by the service provider are refused) and 4.3 (many near-identical apps in one account), as Igor was told on 2026-11-03; the researcher confirms the current wording. Cost and paperwork (an organisation account on Apple needs a D-U-N-S number) stay with the tenant. TestFlight and Google internal testing may use the platform's account during development. Igor: "conta de cada tenant". — **Reversibility:** costly — bundle ids and listings live in the tenant's account; moving an app between accounts is a store procedure.
- **D-605:** CREDENTIALS ARE ENTERED ON A SCREEN, THE APP IS GENERATED BY A COMMAND. A new "App" tab on the tenant in the platform panel takes, write-only and sealed under the platform master key exactly like the project credentials of D-539 (never returned, never logged): the store publishing access (App Store Connect API key, Google Play service account) and the Apple push key of that tenant. Building and sending the app to the stores runs by one command or CI workflow per tenant that reads them. The "Gerar app" button with build progress is deferred. Igor's standing rule: no `.env` or code edit per tenant. — **Reversibility:** reversible.
- **D-606:** PUSH GOES THROUGH ONE FIREBASE PROJECT (FCM) OF THE PLATFORM for all tenants, with one Android app and one iOS app per tenant and one sender service account in Secret Manager. The Apple push key of each tenant is the one entered in D-605. Isolation between tenants stays where it already is: the device token is stored in THAT tenant's own project under RLS (two-tenant negative test) and the send starts from that tenant's database and worker. Whether the Apple key is handed to Firebase or APNs is called directly is left to the researcher. Igor: "um da plataforma para todos". — **Reversibility:** costly — device tokens are issued per Firebase app; changing the sender project means every installed app re-registers.
- **D-607:** THE PLATFORM ASSEMBLES THE STORE LISTING FROM A TEMPLATE: app name, icon and splash derived from the tenant's branding (the existing icon pipeline in `packages/core/server/branding/icons.ts`), a standard pt-BR description, the age rating, and a reviewer account created in the tenant for App Review. The tenant only checks it and provides its privacy-policy URL. Screenshots are a step of the publication checklist, not generated code. — **Reversibility:** reversible.

**Signing in, deleting the account and links**
- **D-608:** Sign-in, sign-up, password recovery, invite acceptance and the session are the web's own pages, unchanged, running inside the app (the session cookie lives in the shell). The app is fixed to its tenant: there is no community picker and the shell can open only that tenant's host. The refusals (`MEMBERSHIP_BLOCKED`, `MEMBERSHIP_INVITED`, `SUBSCRIPTION_PENDING`, `PROFILE_FORM_PENDING`, `TENANT_HOST_MISMATCH` and the `TENANT_*` host states) land on the screens the web already shows.
- **D-609:** DELETE MY ACCOUNT ANONYMISES. The access account, name, photo, bio, e-mail, the profile-form answers and the push devices are removed; posts and comments stay as "Membro removido" so conversations and counts do not break; purchase and access-grant records stay without personal data. The Apple rule requires the option inside the app whenever an account can be created there (the researcher confirms the current wording). The screen is a NEW capability for the web too: it promotes V2-PROF-02. — **Reversibility:** one-way — after the grace period the personal data is gone and the content is detached from the person; nothing restores it.
- **D-610:** The deletion has a 14-DAY GRACE PERIOD, on the same screen in the web profile and in the app. The account is deactivated at once (out of lists, no push, no new activity); signing in again within the 14 days cancels the request; a job anonymises it when the period ends. The confirm text tells the member that deleting the account does not cancel a subscription at the payment gateway. Igor: "prazo de 14 dias, no app e no web". — **Reversibility:** costly — the grace column, the job and the member's notice are published behaviour once the first request is made.
- **D-611:** LINKS OPEN THE APP WHEN IT IS INSTALLED, and the browser when it is not, as today. Universal Links (iOS) and App Links (Android) on the tenant's primary domain: the web serves, per host, the `apple-app-site-association` and `assetlinks.json` files from data held in the tenant's "App" tab (Apple team id, application id, signing-certificate fingerprint). It covers the auth e-mail links (`/auth/confirm`: confirm account, invite, recover password), shared post links (FEED-07) and the tap on a notification. The link is handled inside the shell so the session ends up in the app. Nothing existing changes for a browser. — **Reversibility:** costly — the associated domain is part of the signed build; a tenant that changes its primary domain needs a new build for the links.

**What the phone adds**
- **D-612:** THE BASELINE ships without further questions: native push (iOS and Android), camera and photo library for posting, native share, a branded "sem internet" screen with a retry button and pull to refresh.
- **D-613:** THREE EXTRAS are in this phase (Igor chose all three): (a) a re-open lock with Face ID, fingerprint or the phone passcode, switched on by the member in Perfil and off by default; (b) the unread-notifications number on the app icon, from the counter the API already returns; (c) reading the last feed seen without a connection (partly promotes V2-PLAT-03; the researcher checks whether the existing Serwist service worker can serve it inside the shell, for example through the iOS app-bound domains). — **Reversibility:** reversible.
- **D-614:** THE NOTIFICATION PERMISSION is asked after the first sign-in, behind a branded explanatory screen with "Ativar" and "Agora não". Only "Ativar" fires the system prompt; "Agora não" leaves the enable button in Perfil, as in the web. Logging out removes that device's token. — **Reversibility:** reversible.
- **D-615:** PURCHASE keeps the redirect decided on 2026-11-03: the stored `https:` `checkoutUrl` opens in the phone's browser, no in-app purchase, the app never takes a card. PLAN B, already approved: each tenant has a SWITCH PER STORE (iPhone, Android) that, when off, hides price, buy button and link and leaves only a neutral padlock; members who already have access keep seeing their content unlocked. Default is ON in both. If a store rejects the app for the external purchase, the switch is turned off only where it was rejected, the app is rebuilt and resubmitted, with no change on the other store. Igor: "chave por loja e tenant". — **Reversibility:** reversible.

## Summary

Stage 1 is a thin React Native shell (Expo SDK 58, `react-native-webview` 14) that loads the tenant's own host and adds a native layer around it. **Expo is confirmed over Capacitor**: Capacitor's own configuration reference says `server.url` "is not intended for use in production", and Capacitor has no native-screen path for stage 2, while Expo Router lets a later phase replace one route with a native screen inside the same binary. The web needs one marker to know it is inside the app. Recommended: a **user-agent token** set by the shell (`applicationNameForUserAgent`), because it is readable on the server (needed for the per-store purchase answer and the install-gate attribute without a flash) and on the client, and does not depend on JS injection that is documented as unreliable on Android.

Push should be **direct APNs for iOS and FCM HTTP v1 for Android**. Firebase's own docs describe the APNs key upload only as a console step (no API), and each tenant has its own Apple team and key, so routing iOS through Firebase would force a manual console step per tenant and contradict D-605. The worker already has the whole fan-out, retry and report machinery; it needs two new transports, a migration that relaxes `p256dh`/`auth` under a CHECK, and an additive contract. The iOS device token never needs Firebase.

Seven things in the locked decisions or the UI-SPEC are wrong, risky or incomplete and are surfaced as **Findings F1-F12** (next section), most importantly: (F1) the default "purchase link ON in both stores" conflicts with both stores' payment rules in Brazil; (F3) the Serwist worker cannot serve the saved feed, so the offline feed has to be shell-owned; (F5) the sealed-credential list is missing generated signing material and three manual store steps; (F7/F8) the two likeliest rejection reasons are "repackaged website" (4.2) and missing in-app report/block for user content (Apple 1.2, Google UGC policy), and report/block is not built yet (MODER-05 is Phase 11).

**Primary recommendation:** Build `apps/mobile` as an Expo Router app with one WebView route and a typed zod bridge; mark the app with a UA token; push via direct APNs + FCM v1 from the existing worker; build and upload from a protected GitHub Actions workflow on macOS runners (free for this public repo) using `expo prebuild` + fastlane/Gradle, reading sealed credentials in the job; ship the pilot with the purchase switch OFF on iPhone (and, pending Igor, Android), and decide F8 (report/block) before submitting.

### Pattern 1: WebView configuration (the shell route)
**What:** One route renders `<WebView>` with the tenant host baked from `.tenant/build.json`.
```tsx
// Source: react-native-webview Reference.md props (fetched 2026-11-04)
<WebView
  source={{ uri: `https://${host}${initialPath}` }}
  applicationNameForUserAgent={`RedeSocialApp/${version} (${Platform.OS})`}
  originWhitelist={['https://*']}
  onShouldStartLoadWithRequest={(req) => allowInView(req.url) || (openExternally(req.url), false)}
  onOpenWindow={(e) => openExternally(e.nativeEvent.targetUrl)}   // target=_blank, window.open
  setSupportMultipleWindows={true}                                  // default; false may expose CVE-2020-6506
  injectedJavaScriptObject={{ platform: Platform.OS, version, notifications: permState }}
  onMessage={(e) => handleBridge(e.nativeEvent)}                    // required, or postMessage is not injected
  allowsInlineMediaPlayback mediaPlaybackRequiresUserAction={false} // iOS inline HLS/Mux
  allowsFullscreenVideo                                              // Android
  bounces={false} overScrollMode="never" setBuiltInZoomControls={false}
  allowsLinkPreview={false} textZoom={100} cacheEnabled
  onContentProcessDidTerminate={reload} onRenderProcessGone={reload}
/>
```
Notes: `onShouldStartLoadWithRequest` "is not called on the first load" on Android, so the first URL is the baked host and needs no check; app-bound domains (`limitsNavigationsToAppBoundDomains`) are an optional hardening, see Pitfall 2.

### Pattern 2: The in-app marker
**What:** UA token `RedeSocialApp/<version> (<platform>)`. Server: the root layout and the BFF read it from `headers()`; client: `isNativeApp()` parses `navigator.userAgent` after mount. Never trusted for authorization (any client can send it); it only hides UI and tells the API which store switch to read.
**Why UA and not injected JS:** react-native-webview documents `injectedJavaScriptBeforeContentLoaded` as "not fully reliable" on Android; a UA reaches SSR; `window.ReactNativeWebView` exists only when `onMessage` is set.
**Mandatory consequence:** today the install gate would block the shell. `isInAppBrowser` returns true for an iOS UA with no `Safari` token (`apps/web/lib/install-gate.ts:51`: `return /iPhone|iPad|iPod/.test(userAgent) && !/Safari/.test(userAgent);`) and for Android's `; wv)` token (`install-gate.ts:41` `const IN_APP_TOKENS =`). `decideInstallGate` must check the marker first.

### Pattern 3: Bridge protocol
**What:** `type Msg = { v: 1; type: 'push.enable' | 'push.disable' | 'push.state' | 'badge.set' | 'share' | 'lock.set' | 'lock.state' | 'snapshot.feed' | 'logout.done' ...; id?: string; payload: ... }`, one zod discriminated union in `packages/contracts/src/native.ts`, JSON-stringified (the library accepts "one argument which must be a string"). Native replies with `injectJavaScript("window.dispatchEvent(new CustomEvent('rede-native', {detail: ...}));true;")` ("End the script with `true;`"). The handler accepts only messages whose `nativeEvent.url` host is the baked host, from the main frame, with `v` it knows; the web side ignores events whose shape fails the same schema. Version the union so an old app and a new web (or the reverse) degrade quietly; `minVersion` is the hard floor.

### Pattern 4: Push storage and the additive contract
**Verified current shape** (`packages/modules/notifications/db/schema.ts`): `endpoint: text().notNull()`, `p256dh: text().notNull()` (line 153), `auth: text().notNull()`, `userAgent`, `lastSuccessAt`, `failureCount`, unique `push_subscriptions_tenant_endpoint_uq` on `(tenantId, endpoint)` (line 166), owner-only select/delete policies, no insert/update policy; writers are `app.push_subscription_upsert(text,text,text,text)`, `app.push_subscriptions_for(uuid[])` (returns `id, user_id, role, endpoint, p256dh, auth`), `…_delete_dead`, `…_report`.
**Recommended migration (additive, generated by drizzle-kit + a hand-written functions file, the Phase 7 split):**
```sql
alter table public.push_subscriptions
  add column kind text not null default 'webpush',
  add column platform text,                 -- 'ios' | 'android' | null for web
  add column app_environment text,          -- 'production' | 'sandbox' | null
  add column app_version text;
alter table public.push_subscriptions alter column p256dh drop not null, alter column auth drop not null;
alter table public.push_subscriptions add constraint push_subscriptions_kind_chk
  check ((kind = 'webpush' and p256dh is not null and auth is not null and platform is null)
      or (kind in ('apns','fcm') and p256dh is null and auth is null and platform is not null));
```
`endpoint` stays the unique key and holds the device token for native kinds, so `(tenant_id, endpoint)` keeps "a token belongs to one member of one tenant" and the handoff semantics (`delete … where user_id <> v_u`) carry over. Add `app.push_device_upsert(kind, token, platform, environment, app_version)` rather than changing the 4-argument function, and add `kind`/`app_environment` to `app.push_subscriptions_for` by a new function (`…_for_v2`) or `create or replace` with the extra columns **after** the worker is deployed (rolling deploys: the old worker must still parse the old shape). The existing `pushSubscriptionDeleteSchema` (`endpoint: z.string().min(1).max(PUSH_ENDPOINT_MAX_LENGTH)`, contracts/index.ts:257-258) already accepts a native token for DELETE. The save schema (`z.url()` + keys) needs a union: `{kind:'webpush', endpoint, keys, userAgent?} | {kind:'apns'|'fcm', token, platform, environment, appVersion}`, with the old keyless-`kind` body still parsing as `webpush` (additive rule in `packages/contracts/src/bootstrap.ts:74`: "Every future ADDITIVE bootstrap field follows this rule"). `isAllowedPushEndpoint` (URL allow-list, T-07-33) must not run on native tokens; shape-check instead: APNs token = hex (64 chars historically; **"Don't make assumptions about device token size"**: accept 32-200 hex chars), FCM token = `[A-Za-z0-9_:\-]{100,4096}`.

### Pattern 5: Native transports in the worker
The seam is `PushTransport.send(target: PushTarget, payload: string, opts: PushSendOptions): Promise<PushOutcome>` (`transport.ts:36`) and `outcomeForStatus` (`transport.ts:43`: 201/202 `sent`; 404/410 `gone`; 400/413 `dropped`; else `retry`). `runPushSend` builds the same v1 payload JSON per subscription (`buildPushPayload`, body already cut to 3,072 bytes) and calls `pushTransport().send`. Change: `PushTarget` becomes a discriminated union by `kind`; `pushTransport()` becomes `transportFor(kind)`; native transports parse the v1 JSON and re-shape it.
- **APNs** (`apnsTransport`): `POST https://api.push.apple.com/3/device/<token>` (sandbox host `api.sandbox.push.apple.com` for `app_environment='sandbox'`), HTTP/2, headers `authorization: bearer <ES256 JWT>` (header `{alg:'ES256', kid}`, claims `{iss: teamId, iat}`), `apns-topic: <bundle id>`, `apns-push-type: alert`, `apns-priority: 10|5` from `urgency`, `apns-expiration: now + ttlSeconds`, `apns-collapse-id: <tag>` (**must not exceed 64 bytes**; `PUSH_TAG` allows 64 ASCII chars, which fits), body `{ aps: { alert: {title, body}, badge, sound: 'default', 'thread-id': tag }, url, v: 1 }` (limit 4,096 bytes; the 3,072-byte payload bound already holds). Provider token: "Refresh your token no more than once every 20 minutes and no less than once every 60 minutes"; an `iat` older than an hour gives `ExpiredProviderToken` (403). "You can't map a connection to APNs to multiple teams": **one HTTP/2 session pool per tenant (team)**, reused for hours. Errors: 410 `Unregistered` -> `gone`; 400 `BadDeviceToken`/`DeviceTokenNotForTopic` -> `gone` after one confirmation or `dropped`; 429 `TooManyProviderTokenUpdates` and 5xx -> `retry`; 403 `InvalidProviderToken`/`ExpiredProviderToken` -> `retry` + alert (a broken tenant key must not delete devices) [error strings: CITED handling-notification-responses page not fetched, `[ASSUMED]` for the exact reason names].
- **FCM** (`fcmTransport`): `POST https://fcm.googleapis.com/v1/projects/<PROJECT_ID>/messages:send` with `Authorization: Bearer <OAuth token, scope https://www.googleapis.com/auth/firebase.messaging>`; body `{ message: { token, notification: {title, body}, data: {url, tag, v:'1', badge:'N'}, android: { priority: 'HIGH'|'NORMAL', ttl: '<n>s', collapse_key?, notification: { channel_id, tag, notification_count } } } }`. `data` keys and values must be strings; reserved keys are `from`, `message_type`, `google.*`, `gcm.notification.*`. Errors: 404 `UNREGISTERED` -> `gone`; 400 `INVALID_ARGUMENT` -> `dropped`; 403 `SENDER_ID_MISMATCH` -> `gone` (token belongs to another project); 429 `QUOTA_EXCEEDED`, 503, 500 -> `retry` [CITED: firebase.google.com/docs/reference/fcm/rest/v1/ErrorCode].
- **`notification` vs `data`:** send a `notification` message with `data.url`; the OS shows it with no JS running (needed when the app is killed). In the foreground, `setNotificationHandler` decides display; mirror the web's `decidePushDisplay` (suppress when the page is open and the page already refreshes the bell through Realtime). SDK 58 note: "Foreground notifications now display by default unless your `setNotificationHandler` says otherwise".
- **Badge:** iOS `aps.badge` from the per-recipient count the job already computes (`send-job.ts:152`: `badge = counters.unreadNotifications + counters.unreadConversations;`); while the app is open the page sets the badge through the bridge on every counter change. Android: `notification_count` on launchers that support it, else nothing (`setBadgeCountAsync` "resolves to `false`" when unsupported).
- **Per-tenant credentials in the worker:** read the sealed APNs key through the platform lane with the `open()` helper (`packages/core/server/secrets/sealed.ts:188`), cache the unsealed key in memory per tenant for the process lifetime (never log), cache the signed provider token ~40 minutes. The FCM sender service-account JSON comes from Secret Manager (D-606) into `env` the way `PLATFORM_MASTER_KEYS` does.
- **Both PWA and app on one phone:** different `kind`, both receive (discretion default "yes").
- **CI:** `PUSH_TRANSPORT=fake` already pins CI (`transport.ts` header); add `apns-fake`/`fcm-fake` recording in the same outbox, status chosen by a token suffix the way `fakeStatus` reads `/status/<code>`.

### Pattern 6: Identity derivation (bundle id / application id)
Pure function `deriveAppIds(primaryHost)` in `packages/contracts/src/native.ts`, unit-tested: reverse the dot-separated labels (`comunidade.cliente.com.br` -> `br.com.cliente.comunidade`). Android rules [CITED: developer.android.com/build/configure-app-module]: at least two segments; each segment starts with a letter; only `[a-zA-Z0-9_]`; "Once you publish your app, you should never change the application ID". So: lowercase, replace `-` with `_` for Android (a hyphen is legal in an iOS bundle id, `[ASSUMED]` Apple rule: alphanumerics, hyphen, period), prefix `x` to a label starting with a digit, refuse an empty label. Use the **same** string on both stores when possible (the Android form without hyphens), and let "Mudar IDs" override until "publicado". Uniqueness is global per store, so a collision is detected when the bundle id is registered (fail loudly). Bake the **host**, not only the slug (D-611: links need the host; a host change needs a new build either way), and bake the slug too for the version check and the branding fetch.

### Pattern 7: Per-host verification files
Route handlers `apps/web/app/.well-known/apple-app-site-association/route.ts` and `…/assetlinks.json/route.ts` (dot-folder under `app/` is routable; **verify in the first plan**: `[ASSUMED]`). Format [CITED: Apple "Supporting associated domains" `.md`, fetched 2026-11-04]:
```json
{ "applinks": { "details": [ { "appIDs": ["ABCDE12345.br.com.cliente.comunidade"],
  "components": [ { "/": "/plataforma*", "exclude": true }, { "/": "/api/*", "exclude": true },
                  { "/": "/v1/*", "exclude": true }, { "/": "/m/*", "exclude": true },
                  { "/": "/serwist/*", "exclude": true }, { "/": "/*" } ] } ] } }
```
Android `assetlinks.json`: `[{"relation":["delegate_permission/common.handle_all_urls"],"target":{"namespace":"android_app","package_name":"<applicationId>","sha256_cert_fingerprints":["AB:CD:..."]}}]` [CITED: docs.expo.dev/linking/android-app-links]. Rules: "You must host the file using `https://` with a valid certificate and with no redirects"; iOS 14+ fetches through Apple's CDN ("Apple's content delivery network requests the file... within 24 hours. Devices check for updates approximately once per week"); keep it under 128 KB. Android 15+ re-verifies in the background (changes "up to seven days"), Android 14 and lower only on install/update. The **primary host** is the only one in the entitlement and intent filter; an alias host 308-redirects everything (`proxy.ts` `primaryHostRedirect`), which is correct because aliases are not in the app.
**Data:** extend the by-host/public answer (non-secret) with `app: { appId (teamId.bundleId), applicationId, sha256[] } | null` read through the platform lane; absent or partial data -> 404 for that file (UI-SPEC "no partial file").
**Gates to change in `apps/web/proxy.ts`:** the `PUBLIC` list (`proxy.ts:28`) needs `/^\/\.well-known\//` (otherwise an unauthenticated Apple CDN request is redirected to `/entrar`), and the `!coordinates` branch (`proxy.ts:212`) must let `/.well-known/*` through before it (otherwise a tenant whose project is down answers 307 to `/comunidade-indisponivel` and a fresh install cannot verify). The matcher (`proxy.ts:347`) excludes only image extensions, so `assetlinks.json` also passes through the proxy. Cache-Control `public, max-age=300` is enough; Apple's CDN holds its own copy.

### Pattern 8: Lock and privacy cover
`expo-local-authentication` `authenticateAsync({ promptMessage, disableDeviceFallback: false })`: the passcode fallback is on by default on iOS ("After several failed attempts, the system falls back to the device passcode"); `getEnrolledLevelAsync()` returns `NONE|SECRET|BIOMETRIC_WEAK|BIOMETRIC_STRONG`, `NONE` -> the switch is disabled and an existing lock turns itself off (UI-D-610). iOS needs `NSFaceIDUsageDescription` (config plugin `faceIDPermission`), otherwise "the module will authenticate using device passcode". The lock is a **UI gate over a loaded page**, not a credential check (the session cookie is valid underneath): it must stop touches and accessibility focus on the web view, and state that in Security Domain. Timer: `AppState` `background` timestamp; 60 s fixed (PU-2). Switch state: plain file in app storage (not Keychain), cleared on logout (UI-D-609).

### Pattern 9: Offline snapshot (shell-owned)
After each successful Início feed load the page posts `snapshot.feed` (first page: author display name, avatar URL, text excerpt, media thumbnail URL and kind, counts, timestamp; at most ~20 posts, zod-bounded, no private data beyond what the feed already shows the member). The shell writes one file keyed by tenant+member, replaces it each time and deletes it on `logout.done` and on a different member signing in. On first-load failure with network down and a snapshot present, a native read-only list shows with the banner; writes are not available there at all (no disabled buttons needed). Images use the platform image cache where present, else the neutral tile (UI-D-612).

### Pattern 10: Account deletion on the existing soft-state
The "live member" predicate everywhere is `m.status = 'active' and m.blocked_at is null and m.deleted_at is null` (e.g. `push_subscriptions_functions.sql:58,115,155`). Reuse it: the request sets `memberships.deleted_at = now()` plus a new `deletion_due_at = now() + 14 days` (and a reason marker so moderation soft-deletes are not mistaken for a request). Every live-filter (lists, counters, fan-out, push, sessions) then deactivates the member with no new predicate. Revoke sessions at request time. Sign-in within the window clears both columns (in `requireAuth`/the access hook, where the membership is resolved) and raises `pendingDeletion` in the bootstrap once. The job (pg-boss, per tenant project, idempotent on the row) anonymises after `deletion_due_at`: `auth.admin.deleteUser` or equivalent in the tenant's project, profile/answers/devices deletion, content rows keep `author_user_id` null-ed or pointing at a shared tombstone so the web renders "Membro removido" (the notifications schema already says "a departed actor renders 'Membro removido'", `schema.ts` fact 4). Send the completion e-mail **before** erasing the address (Apple: "provide a confirmation when the deletion is complete"). Refuse `LAST_ADMIN`. Rate limit by IP+user; re-verify the password server-side with `signInWithPassword` (PU-3).

### Pattern 11: Sealed data for the App tab
Follow `packages/core/server/secrets/sealed.ts` (AES-256-GCM, `seal(plain, aad)` / `open(sealed, aad)`, AAD `<rowId>:<column>`, "EVERY failure throws a plain `Error('sealed value unreadable')`") and `packages/core/db/central/projects.ts` (`platform` schema; "Every table below is born with RLS on and ZERO policies"). ### Anti-Patterns to Avoid
- **A custom URL scheme (`rede://`) for links.** Any app can claim it; use only verified https links (Security Domain).
- **Opening `checkoutUrl` or any third-party host in the view.** Always the system browser.
- **Native code holding a session token or calling `/v1/*` directly in stage 1.** The page talks to the BFF; the shell only passes a device token over the bridge.
- **Reading the marker during SSR to change what a browser gets.** Only the in-app UA changes output.
- **Deleting devices on an APNs 403/400 caused by our own key problem.** Only 410/Unregistered deletes.
- **Using `expo-secure-store` for non-secret flags** (Keychain survives reinstall).
- **Committing `ios/` and `android/`**, or building from a developer laptop (no Xcode, no JDK there).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Google OAuth for FCM | Your own RS256 JWT-bearer exchange | `google-auth-library` | Token caching, clock skew, retries |
| APNs provider token | A custom JWT encoder | `jose` `SignJWT` with `{alg:'ES256', kid}` | Already a dependency; correct ECDSA encoding |
| HTTP/2 client | A socket-level client | `node:http2` session pool | Required transport; reuse for hours |
| Key encryption | Anything new | `sealed.ts` `seal`/`open`, `PLATFORM_MASTER_KEYS` ring | D-539, rotation, AAD binding |
| Biometric/passcode prompt | Native module | `expo-local-authentication` | Passcode fallback handled by the OS |
| Link verification files | Hand-edited per tenant | One route handler per file reading tenant data | D-605: no per-tenant edits |
| Certificate/profile management | Raw ASC API calls for CSR/profile logic | fastlane `cert`/`sigh` with the API key `[ASSUMED]` | Apple edge cases (limits, expiry) |
| Share sheet | `navigator.share` polyfill injected at load | Bridge message -> RN `Share` | Injection is unreliable on Android |
| Web push to browsers | Replacing `web-push` | Keep it | PWA must keep working |
| Offline HTML cache | Service-worker caching of documents | Shell-owned snapshot | F3 |

**Key insight:** every hard part (APNs/FCM wire format, signing, link verification, WebView quirks) has an official mechanism; the work is wiring them to the existing tenant-scoped fan-out and sealed registry without opening a second trust path.

## Common Pitfalls

### Pitfall 1: The install gate locks the app inside its own shell
**What goes wrong:** the first launch shows "Instale o app" instead of the tenant. **Why:** `isInAppBrowser` is true for a WKWebView UA (no `Safari` token) and for Android's `; wv)`; the root layout also sets `data-install-gate="pending"` and CSS hides `body` for up to 4 s. **Avoid:** marker check first in `decideInstallGate`; the root layout writes `open` server-side for the app UA. **Warning sign:** a white screen for 4 s then the gate.

### Pitfall 2: `WKAppBoundDomains` silently disables the bridge
**What goes wrong:** with the Info.plist key present, "all `WKWebView` instances default to denying JavaScript injection, custom style sheets, cookie manipulation, and message handler use" unless `limitsNavigationsToAppBoundDomains` is set and the page is on a listed domain (max 10). **Avoid:** do not add the key in stage 1 (the host allow-list is enforced in `onShouldStartLoadWithRequest`); if app-bound domains are later wanted for native host enforcement, set both together and test login, Mux and every redirect first. **Do not** rely on service workers on iOS (F3).

### Pitfall 3: Cookies and the first-party session
The Supabase cookies are `httpOnly: true` (`cookie-options.ts:12`) with `@supabase/ssr` default `maxAge: 400 * 24 * 60 * 60` (node_modules constants), so they persist in WKWebView's own store; **do not set `sharedCookiesEnabled`** (it uses the shared `NSHTTPCookieStorage`). Server-set HttpOnly cookies are not hit by ITP's script-cookie cap; script-written storage can be purged after 7 days of no interaction. Android keeps cookies in the WebView `CookieManager` (flush timing: a force-kill right after sign-in may lose them, `[ASSUMED]`): UAT row. Set `android:allowBackup="false"` (`expo-build-properties`) so a cloud backup cannot restore a session on another device.

### Pitfall 4: Universal Links do not fire where you expect
Typing a URL, tapping a link on the same domain inside Safari, and links inside some in-app browsers (Gmail on Android with Custom Tabs, social apps) can open the browser instead; the member can long-press "Open in App". The e-mail confirm link is the main case: test with Mail, Gmail (iOS and Android), WhatsApp. The AASA is fetched at install and update and roughly weekly after; changed paths in production need a new release; `?mode=developer` only helps development-signed builds.

### Pitfall 5: The well-known files get redirected by the app's own gates
See Pattern 7: unauthenticated request -> `/entrar` (307); tenant project down -> `/comunidade-indisponivel` (307); alias host -> 308. All three break verification. Add a Playwright case per gate.

### Pitfall 6: `navigator.share` and the clipboard fallback
`useSharePost` falls back to `navigator.clipboard.writeText` and shows "Link copiado": on Android that is what every member would get. Route through the bridge when `isNativeApp()`; keep the web path untouched. The module `sharePost` takes injected surfaces (`share?`, `clipboard?`), so the bridge is just another `share` implementation.

### Pitfall 7: Android camera and file inputs
The guide: uploads need no storage permission on supported Android versions; an input with `capture` requests the camera permission first and falls back to the chooser on denial; iOS needs `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription`, `NSMicrophoneUsageDescription` (video). Declaring `CAMERA` adds a Play data-safety line. Large videos can kill the web content process (`onContentProcessDidTerminate`/`onRenderProcessGone`): reload and keep the composer draft the web already persists (`join-draft`/composer drafts).

### Pitfall 8: Notification tap path and cold start
A tap with the app killed must read `getLastNotificationResponseAsync()` and call `clearLastNotificationResponse()`; a tap with the app open uses the response listener. Validate `data.url` with the `PUSH_PATH` regex (`contracts/index.ts:269`: `/^\/(?![/\\])[^\\\s]*$/`) before `WebView` navigation; anything else -> Início. Android 13+: the permission prompt does not appear until a notification channel exists: create `default` before `getDevicePushTokenAsync`.

### Pitfall 9: Privacy cover and lock timing
`inactive` also fires for the Face ID system sheet and Control Centre (flicker); `FLAG_SECURE` blocks screenshots. Use the native module (OQ-6), gate the cover on "lock is on" only, and test on a real device in the app switcher.

### Pitfall 10: Account deletion corner cases
Sessions (revoke at request), the push token (forget before the request, UI-D-618), subscriptions at the gateway (not cancelled; say so), last admin, the member who is also the only owner of content-bound communities, e-mail reuse after anonymisation (a new sign-up with the same e-mail must work and be a new member), moderation log rows that name the member, export/CSV of profile-form answers, `notifications.actor_user_id` set-null, the "pendingDeletion" state surviving a cache. The completion e-mail needs the address before it is erased.

### Pitfall 11: Store accounts and review logistics
New personal Play accounts (created after 2023-11-13) need a closed test with at least 12 testers opted in continuously for 14 days before production access; an organisation account avoids it (blogs say so; Google's page read does not state the exemption: `[ASSUMED]`). An Apple organisation account needs a D-U-N-S number. Play requires targeting Android 16 (API 36) for new apps from 2026-08-31 (Expo SDK 58 targets 36). Apple requires Xcode 26+ builds since 2026-04-28 and an iOS 13+ deployment target since 2026-09-09 (SDK 58 supports iOS 16.4+). Android developer verification starts 2026-09-30 for apps from participating stores in Brazil on certified devices: Play-distributed apps are auto-registered; sideloaded test builds in Brazil need the advanced flow, so test through Play internal testing.

### Pitfall 12: Rolling deploys of the push functions
`runPushSend` selects explicit columns from `app.push_subscriptions_for`; a new column in that function while an old worker runs is fine only if added as new columns, not renamed. Deploy order: migration -> API -> worker, the same order `deploy-api.yml` documents.

### Pitfall 13: Identifier traps
Hyphens (legal in a bundle id, illegal in an Android id), labels starting with a digit, labels that are Java keywords (`[ASSUMED]` harmless for applicationId, painful for namespace), a host with a single label, a primary host that changes later (ids stay, links need a build), a collision with an app the tenant already published.

### Pitfall 14: Realtime and background
A suspended WKWebView drops the WebSocket; on return the page must resubscribe and call `setAuth` again (the repo's Realtime client already re-auths on refresh). Whether `visibilitychange` fires reliably in the RN web view on resume is `[ASSUMED]`: UAT row, and the shell may dispatch a `resume` bridge event as a safety net.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Deep-link hijack via a custom scheme | Spoofing | No custom scheme; verified https links only; Android `autoVerify`; AASA only for the primary host |
| Open redirect / host escape through a push `url`, a link or `target=_blank` | Tampering | `PUSH_PATH` same-origin path only; host allow-list in `onShouldStartLoadWithRequest`/`onOpenWindow`; system browser for everything else |
| Bridge spoofing by an iframe or injected script | Spoofing/Elevation | Main-frame and baked-host check on every message; zod; no message can read a token or call the API |
| Spoofed UA marker | Spoofing | Marker only hides UI and selects a store switch; never authorizes; API enforces everything |
| Forged device token (cross-tenant or cross-member) | Tampering | `tenant_id` in the unique key; owner-only RLS; handoff definer scoped to `app.tenant_id()`; two-tenant pgTAP negative |
| Stolen session used to delete the account | Tampering/DoS | Password re-entry, rate limit, 14-day window, completion e-mail, sign-in cancels |
| Reviewer account abuse | Elevation | Plain `member`, sealed rotatable password, tenant-scoped, listed in the panel |
| Credential disclosure in a public repo's CI logs/artifacts | Information disclosure | `::add-mask::`, files in `$RUNNER_TEMP`, deleted last, no artifacts of build inputs, environment with required reviewer, `workflow_dispatch` only, no `pull_request` trigger, WIF with a read-only service account |
| One Firebase sender account for all tenants | Information disclosure/Elevation | Secret Manager, least-privilege role, blast radius = push delivery only (tokens and content stay in tenant projects); documented accepted risk (D-606 deferred per-tenant Firebase) |
| APNs key leak | Spoofing | Sealed; per-tenant; revoke at Apple; connections closed and reopened after rotation ("close all of your existing HTTP/2 connections") |
| Session restored from a device backup | Information disclosure | `allowBackup=false` on Android; iOS WebKit data is in the app container (accepted at L1, noted) |
| App lock bypass | Elevation | Documented as UI gate; overlay blocks input and accessibility; real security remains the session and the device lock |
| Account deletion abuse by an admin (anonymise another member) | Tampering | The route deletes only `ctx.userId`; no admin variant in this phase |
| Subresource/CDN poisoning of the shell's bundled assets | Tampering | Bundled fonts/branding baked in the binary; branding record validated by the same schema as the by-host answer before use |
