<assumption_delta_decision>
The assumption-delta detector fired on two weak cues ("chosen" and "one web client becomes a third client"); the seam is real. `push_subscriptions` was keyed by a Web Push endpoint and now also holds a native token. **Noun** = the push SUBSCRIPTION (an endpoint-keyed delivery address) stays the primary noun; the native device is added ALONGSIDE as a second `kind` of the same row, not promoted to a first-class `devices` table. **Decision** = `add-alongside`. **Rationale**: (1) the unique key `(tenant_id, endpoint)` and the handoff rule already mean "this delivery address belongs to one member of one tenant", which is exactly the native-token invariant; (2) a phone with both the installed PWA and the app has TWO delivery addresses and receives both pushes (CONTEXT discretion default), so "one device = one row" is false and a `devices` noun would need a one-to-many table anyway; (3) the worker, the report path (`app.push_subscription_report`) and `app.push_subscription_delete_dead` key by subscription id, so promoting would rewrite three shipped functions and a rolling deploy would break; (4) it is reversible: if stage 2 needs per-device settings, a `devices` table can reference `push_subscriptions.id` later without moving data. The word "device" is a UI and contract word (`pushDeviceInputSchema`), not a table.
</assumption_delta_decision>
